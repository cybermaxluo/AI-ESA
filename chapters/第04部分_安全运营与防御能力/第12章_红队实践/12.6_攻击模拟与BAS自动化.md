# 12.6　攻击模拟与 BAS 自动化

> 导读：在某次与客户的安全评审会上，对方展示了一份报告：BAS 平台显示检测覆盖率 88%，一周前的运行结果。而就在评审前两天，一次 SIEM 升级导致 Sysmon 日志解析规则失效——那 88% 的检测覆盖率实际已缩水至不到 60%，但没有人知道。这是 BAS 部署最常见的失败模式之一：平台运转着，却没有人在看结果，也没有机制在检测能力下降时发出警报。本节讨论 BAS 的正确定位、实施路径，以及如何避免把它变成一个产生安慰数字的展示系统。

---

## 12.6.1 BAS 的技术定位

### 它解决什么问题

BAS（Breach and Attack Simulation，突破与攻击模拟）解决的核心问题是检测规则的持续有效性验证。

红队演练是季度或年度事件，演练之间发生的变化——新系统上线、云配置漂移、SIEM 版本升级、Sysmon 规则更新——都可能导致原本有效的检测规则悄然失效。BAS 通过持续自动化执行标准化 TTP，让这种"静默腐化"立即可见。

准确地说，BAS 是检测体系的回归测试工具，而不是"攻防能力的完整验证"。理解这个定位差异，是避免 BAS 投资失败的前提。

### BAS 与红队的分工

| 维度 | BAS | 红队演练 |
|------|-----|----------|
| 目标 | 验证已知 TTP 的检测规则持续有效 | 发现未知检测盲区和业务逻辑漏洞 |
| 执行频率 | 每日/每周自动化 | 季度/年度 |
| TTP 范围 | 标准化、文档化的已知技术 | 定制化，含对手模拟和业务场景 |
| 新威胁发现 | 不具备（受限于场景库更新速度） | 是核心能力 |
| 运行成本 | 低（自动化） | 高（需要人力密集投入） |
| 对抗真实性 | 中（已知 TTP，防御方可能已知晓） | 高（模拟真实 APT 行为模式） |

互补关系：红队演练发现新的检测盲区 → 紫队协作开发检测规则（12.5）→ 检测规则纳入 BAS 场景库持续验证 → BAS 结果发现规则腐化 → 通知紫队修复。这是一个闭环，而不是"用 BAS 替代红队"。

### 适用边界

BAS 对以下场景不适用：
- 业务逻辑漏洞验证：薅羊毛、支付绕过类攻击需要理解业务上下文，BAS 无法处理
- 社工与钓鱼测试：涉及真实人员反应，不能自动化
- 0day 和新型 TTP：BAS 场景库有更新延迟，不能替代红队的创造性攻击能力
- 供应链攻击模拟：授权约束导致无法覆盖（参见 12.8 SolarWinds 案例分析）

## 12.6.2 主流平台对比

### 开源：MITRE Caldera

Caldera（MITRE 的一项活跃研究项目，代码以 Apache-2.0 授权发布[1]）是 MITRE 开源的对手模拟框架，架构组成：

- Server：C2 控制中心，管理 Agent 连接和任务下发
- Agents（Sandcat/Manx/Ragdoll）：部署在目标主机的执行组件，接收任务并回报结果
- Abilities：单个 TTP 的执行单元，含命令、清理步骤和 ATT&CK 映射
- Adversaries：由多个 Abilities 组合的对手画像（如 Conti、APT29）
- Operations：运行一个 Adversary 对一组 Agent 的完整执行过程

Caldera 的优势是对 ATT&CK 的深度集成和开放的 API 接口，缺点是企业级报告和集成能力需要自行开发。适合已有工程能力、希望深度定制场景库的安全团队。

### 商业平台

SafeBreach：以 Hacker's Playbook 攻击场景库为核心，覆盖网络、端点、云、邮件等向量。优势是更新快、报告体系完整、内置与主流安全工具的集成；面向大型企业，TCO 较高。需要说明的是，各家 BAS 厂商公布的"场景数量"口径不一（SafeBreach 那个流传很广的"近 400 万"其实来自 2016 年的一份新闻稿，原文说的是该年 1—9 月**已执行的攻击模拟次数**（3,985,011 次），不是手法库的容量；把它当成今天的场景库规模引用，既错了口径也错了年份[2]），选型时不宜用场景数量横向比较，应改用"覆盖了哪些与自身威胁模型相关的 ATT&CK 技术"来评估。

Cymulate：SaaS 模式，快速部署，内置 DMARC/钓鱼模拟等开箱即用场景。对于希望快速获得基线覆盖率数据的中型企业，启动门槛较低。

AttackIQ：与 MITRE ATT&CK 的集成最为深入，提供 ATT&CK 战术层面的覆盖率矩阵热力图，报告格式适合与 CISO 层面沟通。拥有免费的 AttackIQ Academy 培训资源。

选择依据：团队有工程能力且预算有限→Caldera；需要快速启动基线评估→Cymulate；需要向管理层呈现 ATT&CK 映射报告→AttackIQ；大型企业场景库广度优先→SafeBreach。

## 12.6.3 三阶段实施路径

### 阶段一：试点（第 1-3 个月）

核心原则：从小开始，用真实结果建立信任。不要在第一个月就试图覆盖全量 TTP——场景质量比数量重要得多。

第一步选择依据：从 12.5 紫队协作中已开发出 Sigma 规则的 TTP 开始，这些是已知有检测覆盖的项目，BAS 首次运行应能看到绿色结果——这建立了平台可信度，也验证了 BAS 与 SIEM 的集成是否正确。

试点阶段任务清单：

| 任务 | 说明 | 验收标准 |
|------|------|----------|
| 选择 5-10 个 TTP | 优先选择已有 Sigma 规则的 | 场景能在测试环境正常执行 |
| 部署 Agent 到测试环境 | 不在生产环境运行 | Agent 与 Server 心跳正常 |
| 验证 SIEM 集成 | BAS 执行后 SIEM 确实收到日志 | 有端到端的时间戳可对比 |
| 建立基线覆盖率报告 | 记录第一次运行的覆盖率数据 | 报告格式已与 CISO 对齐 |
| 定义"覆盖率下降"告警阈值 | 超过多少比例下降触发人工审查 | 阈值已配置并测试 |

试点阶段的关键决策：时间戳对齐。BAS 平台的执行时间戳、SIEM 接收时间戳、EDR 告警时间戳必须使用统一时区（建议 UTC）。时区不对齐是 BAS 集成中最常见的静默错误，导致工具显示"未检测"而实际告警只是被错误时间范围的查询排除了。

### 阶段二：扩展（第 4-6 个月）

试点验证 BAS 平台可信后，有序扩展 TTP 范围：

优先级扩展顺序：
1. 覆盖矩阵中的红色项（无检测覆盖），但须在紫队先开发规则后再纳入 BAS
2. 已覆盖但 MTTD 偏高的黄色项（调优阶段），BAS 可以帮助量化调优效果
3. 纳入业务关键资产的专项场景（如数据库服务器、CI/CD 系统）

SIEM/SOAR 集成深化：

扩展阶段需要建立 BAS 覆盖率下降时的自动响应机制。推荐做法：BAS 每周生成覆盖率报告，通过 API 推送至 SOAR 平台；SOAR 检测到覆盖率下降超过阈值时，自动创建 Jira/ServiceNow 工单，指派给蓝队负责人，要求在 72 小时内排查原因。

这个机制解决了开篇场景中的问题：SIEM 升级导致规则失效，BAS 下次运行时覆盖率下降，自动工单在 24 小时内通知责任人。

### 阶段三：规模化（第 7 个月以后）

场景库持续更新：安全威胁每天在变化。MITRE ATT&CK 大致每年发布 2 次版本更新（最新的 v19 于 2026-04-28 发布[3]），新增或修订技术编号；威胁情报源持续输出新的 TTP 变体。BAS 场景库需要对应更新，否则会陷入"用旧场景验证旧规则，对新威胁视而不见"的困境。

建议的更新节奏：

```
场景库更新触发条件：
1. ATT&CK 新版本发布 → 评估新增技术，在 4 周内纳入相关场景
2. 威胁情报报告（Mandiant/CrowdStrike 等）发现新 TTP 变体 → 纳入评估队列
3. 红队演练发现未覆盖技术 → 紫队开发规则后转化为 BAS 场景（目标 2 周内）
4. 供应商安全公告涉及主动利用漏洞 → 72 小时内纳入临时验证场景
```

持续验证节奏：

| 频率 | 内容 | 触发条件 |
|------|------|----------|
| 每日 | 核心检测规则基线验证（20-30 个关键 TTP） | 定时任务 |
| 每周 | 全量场景库运行，生成覆盖率报告 | 定时任务 |
| 触发式 | 任何重大变更后（SIEM 升级/新工具部署/配置变更） | 变更管理触发 |

每日验证覆盖的是"高优先级、高风险"的核心场景——T1003.001 LSASS、T1059.001 PowerShell、T1021.002 SMB 横向移动等。这些场景一旦检测失效，攻击者可以无声无息完成完整攻击链。每周全量运行是成本与覆盖的平衡，不需要每天运行数百个场景。

## 12.6.4 BAS 场景库目录结构

场景库的目录结构与 12.5 紫队知识库对齐，确保 BAS 场景可以直接引用对应的 Sigma 规则：

```
bas-scenarios/
├── by-tactic/
│   ├── initial-access/
│   │   ├── T1566.001-spearphishing.yaml
│   │   └── T1190-exploit-public-app.yaml
│   ├── execution/
│   │   ├── T1059.001-powershell.yaml
│   │   └── T1059.003-cmd.yaml
│   ├── credential-access/
│   │   ├── T1003.001-lsass-memory.yaml    # 对应 12.5 开发的 Sigma 规则
│   │   └── T1110.003-password-spray.yaml
│   ├── lateral-movement/
│   │   ├── T1021.002-smb-admin-shares.yaml
│   │   └── T1550.002-pass-the-hash.yaml
│   └── exfiltration/
│       ├── T1048.003-dns-tunneling.yaml
│       └── T1567.002-exfil-to-cloud.yaml
├── by-adversary/
│   ├── conti-ransomware.yaml               # 多 TTP 串联场景
│   ├── apt29-cozy-bear.yaml
│   └── darkside-ransomware.yaml
├── by-asset/
│   ├── payment-system-scenarios.yaml       # 业务系统专项
│   └── cicd-pipeline-scenarios.yaml
└── coverage-baseline/
    ├── 2025-Q3-baseline.json               # 覆盖率快照
    └── current-coverage.json               # 最新状态（BAS 每次运行后更新）
```

场景文件格式示例（以 T1003.001 为例）：

```yaml
# bas-scenarios/by-tactic/credential-access/T1003.001-lsass-memory.yaml

name: LSASS Memory Access - Mimikatz Simulation
id: bas-t1003-001-001
attack_technique: T1003.001
attack_tactic: credential_access
risk_level: critical

# 关联的检测规则（来自紫队知识库）
detection_rules:
  - sigma: purple-team-kb/ttp-library/T1003.001-lsass-memory/sigma-rule.yml
  - splunk: purple-team-kb/ttp-library/T1003.001-lsass-memory/splunk-query.spl

# 执行步骤（在隔离测试环境）
execution:
  platform: windows
  requires_admin: true
  steps:
    - name: "模拟标准 Mimikatz 访问"
      command: |
        # 使用 Invoke-Mimikatz（PowerShell 版本，用于测试）
        # 实际权限请求模式与 Mimikatz 一致
        [Reflection.Assembly]::LoadFile('mimikatz_sim.dll')
        Invoke-MimikatzSim -Target lsass -AccessMask 0x1F0FFF
      cleanup: "Remove-Item mimikatz_sim.dll -Force"
    - name: "模拟 Procdump 访问"
      command: |
        procdump.exe -accepteula -ma lsass.exe C:\Windows\Temp\lsass.dmp
      cleanup: 'Remove-Item C:\Windows\Temp\lsass.dmp -Force'

# 验证预期：以下告警应在 N 分钟内出现
expected_detections:
  - tool: SIEM
    alert_name: "LSASS Memory Access - Credential Dumping"
    max_latency_seconds: 120  # 超过 2 分钟未出现则标记为"未检测"
    expected_risk_score_min: 70
  - tool: EDR
    alert_name: "Credential Access: LSASS Memory Read"
    max_latency_seconds: 60

# 结果评估
pass_criteria: "两个检测工具中至少一个在 max_latency 内产生告警"
```

## 12.6.5 报告框架

BAS 结果报告需要面向四类受众，每类受众的信息需求不同：

| 受众 | 关注指标 | 报告频率 | 格式建议 |
|------|----------|----------|----------|
| SOC 团队 | 具体哪条规则未检测、告警延迟分布 | 每周 | 详细技术报告 |
| 蓝队工程师 | 检测覆盖率变化趋势、规则腐化原因 | 每周/每次运行 | 技术分析 + DDP 工单 |
| CISO/CSO | ATT&CK 覆盖率热力图、季度趋势 | 每月 | 可视化仪表板 |
| 管理层/审计 | 检测能力成熟度评级、投入产出 | 每季度 | Executive Summary |

给 CISO 看的 ATT&CK 覆盖率热力图：将 ATT&CK 的战术（v19 起 Enterprise 为 15 个[3]）×每个战术下的技术，用红/黄/绿颜色标注覆盖状态。这张图是向管理层说明"我们在哪些攻击阶段有盲区"的最直观方式，比一张覆盖率百分比数字有信息量得多。

## 12.6.6 五种常见失败模式

BAS 项目失败通常不是技术问题，而是期望管理和流程设计问题。

失败模式一：仅依赖 BAS 数字，不追问原因

覆盖率 88% 是什么意思？如果分母（总 TTP 数）不变，分子增加，覆盖率提升；但如果新增的 TTP 是低难度、已知检测的，这个提升没有实际意义。报告覆盖率时必须同时报告分母构成，以及新增/删除场景的理由。

失败模式二：告警疲劳——BAS 运行产生太多告警，SOC 开始忽视

根因是 BAS 与生产环境 SIEM 完全集成，BAS 的测试告警和真实告警混在一起。修复方案：为 BAS 执行使用专用主机标签（如 `host_type: bas-test`），在 SIEM 中建立独立的 BAS 验证查看界面，与生产告警队列分离。BAS 告警只推送给蓝队/紫队，不进入 SOC 正常处理队列。

失败模式三：无闭环改进——BAS 发现覆盖率下降，但没有后续动作

BAS 是发现工具，不是修复工具。必须配套闭环机制：覆盖率下降→自动工单创建→责任人接单→原因排查→修复→重新验证→关单。没有这个机制，BAS 的发现会堆积在报告里没有人处理。

失败模式四：场景库陈旧，与当前威胁脱节

BAS 场景库如果 12 个月没有更新，它验证的是"2023 年的攻击者"，而不是"今天的攻击者"。建立前面提到的场景库更新触发机制，确保有人负责定期审查和更新。

失败模式五：脱离业务场景，覆盖率数字与业务风险不关联

覆盖率矩阵应该标注"哪些 TTP 与核心业务系统直接相关"。如果支付系统的关键攻击路径（T1078 凭证登录→T1021 横向移动→T1486 加密）未被验证，而覆盖率因为大量边缘场景验证而显示为高值，这给管理层传递了错误的安全感。优先级应与 12.4 中识别的业务风险场景对齐。

## 本节小结

BAS 在企业安全验证体系中的正确位置是"持续回归测试"，与红队演练（发现新盲区）、紫队协作（开发新规则）构成三段闭环。单独使用任何一个环节，效果都会打折：BAS 无法发现未知盲区，红队演练无法确保规则持续有效，紫队协作的成果需要 BAS 持续防腐。

实施路径的核心原则是先小后大：用已验证的 TTP 建立可信基线，再有序扩展覆盖范围。每个阶段的技术工作都应配套流程机制——尤其是覆盖率下降的自动工单和场景库更新的负责人制度。没有流程保障的技术工具，很快会变成一个产生安慰数字的仪表板。

---

## 常见误区与适用边界

误区一：BAS 覆盖率高意味着安全。覆盖率是过去已知 TTP 的检测能力的代理指标，不代表对未知攻击的防御能力。高覆盖率配合零红队演练，是典型的虚假安全感来源。

误区二：用 BAS 替代安全意识培训。社工攻击和钓鱼测试需要专门的员工培训平台（如 KnowBe4），BAS 无法替代。

适用边界：BAS 对已建立 SIEM/EDR 基础设施的组织有显著价值。若组织尚处于日志采集建设阶段，BAS 的优先级应低于日志基础设施和 Sysmon 部署完善。BAS 运行的效果上限，由底层检测基础设施的质量决定。

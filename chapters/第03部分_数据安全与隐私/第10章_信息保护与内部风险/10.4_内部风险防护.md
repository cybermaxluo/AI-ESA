# 10.4　内部风险与内部威胁防护

> 前置依赖：UEBA 的行为基线算法与检测实现见 8.7.2，本节不重复其原理。本节聚焦内部威胁语境下的**消费与处置**：威胁类型学、特权用户监控、跨职能协作与法律隐私边界、离职闭环。

## 概述

> 导读：本节从行为分析视角补充 10.3（DLP）的边界防护能力。DLP 检测的是数据流特征，UEBA 检测的是行为偏离基线——两者结合才能区分"大量下载文件"是业务需要还是离职前的数据外带。10.4.1 建立类型学框架，明确恶意、疏忽、被入侵三类威胁的不同防护逻辑；10.4.2 深入 UEBA 的工程实现，包括基线建立的约束和误报优化；10.4.3 讨论特权用户的特殊风险与 PAM 控制；10.4.4 强调跨职能协作——技术只占内部威胁防护工作量的一小部分；10.4.5 给出分阶段实施路径；10.4.6 讨论一个正在逼近的新问题——当读取和操作数据的主体从"人"变成"AI agent"，UEBA 的被监控对象要从手工基线升级为风险分持续评估，并把 agent 当作一等实体纳入基线与风险评分。

内部威胁指组织内部人员（包括在职员工、离职员工、承包商、合作伙伴）因恶意、疏忽或账户被入侵而导致的数据泄露或系统破坏。卡内基梅隆大学软件工程研究所（SEI）CERT 部门基于逾 3000 起真实内部威胁案例编写的《Common Sense Guide to Mitigating Insider Threats》第七版给出 22 条缓解实践，是本节控制设计的主要外部参照[1]。与外部攻击不同，内部人员拥有合法的系统访问权限，其行为更难检测和防范。

内部威胁防护的核心挑战在于：合法用户的正常工作行为与恶意数据外带行为在技术特征上存在大量重叠。销售人员批量下载客户资料可能是正常工作需要，也可能是离职前的数据窃取。这种模糊性使得内部威胁检测的误报率始终难以降低，而过于激进的检测策略又会干扰正常业务并损害员工信任。

## 10.4.1 内部威胁类型学

内部威胁可分为三类：恶意内部人员、疏忽内部人员、被入侵内部人员。三类威胁的动机、行为特征、检测难度差异显著，需要采用不同的防护策略——把它们混为一谈会导致策略失焦。

### 恶意内部人员

恶意内部人员指有意窃取数据或破坏系统的员工。动机包括：经济利益（如出售商业机密）、职业报复（如被解雇后的破坏行为）、竞争对手招揽、意识形态驱动等。

典型行为指标：非工作时间的大量数据访问、访问与本职工作无关的系统或数据、尝试绕过安全控制（如使用个人 VPN、禁用端点安全软件）、删除或修改审计日志、将数据上传至个人云存储或外部邮箱。

多个公开案例表明，恶意数据窃取通常发生在离职前的关键时期。窃取方式多为利用合法权限批量下载文件，然后通过个人云存储、外部邮件或物理介质外带。检测的关键在于识别"异常大量"的数据访问行为，并结合 HR 系统的离职/绩效数据进行风险关联——这也是 10.4.4 强调 HR-安全系统联动的核心原因。

恶意内部威胁的检测难度最高：行为人刻意隐藏痕迹、利用合法权限规避检测、分批次小量外带数据以避免触发阈值告警。从发生到被发现的时间通常以月计算。

### 疏忽内部人员

疏忽内部人员指因操作失误或安全意识不足而导致数据泄露的员工。典型场景包括：邮件错发（将敏感文件发送给错误收件人）、在公共 Wi-Fi 传输未加密数据、使用弱密码或共享账户、点击钓鱼邮件、遗失包含敏感数据的移动设备或 USB。

行业经验表明，疏忽型事件的发生频率远高于恶意型，但单次事件的平均损失通常低于恶意型。疏忽型事件的检测相对容易（DLP 系统可即时拦截），但预防需要持续的用户培训和流程优化。

常见误区：将疏忽等同于低风险。单次疏忽事件损失可能有限，但高频次的疏忽事件累计影响可能超过单次恶意事件；另一个误区是过度依赖技术手段替代培训，DLP 可以拦截已知模式的数据外传，但无法防止员工通过拍照、口述等非数字渠道泄露信息。

### 被入侵内部人员

被入侵内部人员指账户被外部攻击者控制的员工。攻击链通常为：钓鱼邮件/社工攻击 → 凭证窃取 → 利用合法账户登录 → 横向移动 → 数据外带。

典型检测信号：异常登录行为（地理位置不可能旅行、非常规设备、异常时间）、MFA 疲劳攻击（多次推送通知直到用户批准）、登录后的异常操作（大量敏感数据访问、权限提升尝试）、与已知 C2 基础设施的网络通信。

被入侵账户使用的是合法凭证，传统的边界防护无法检测。防护重点在于：部署 UEBA 检测异常行为模式、强化 MFA 防护（如抗钓鱼 MFA，使用 FIDO2 物理密钥而非手机推送）、结合威胁情报识别已知攻击基础设施。

### 灰色地带场景

实际运营中存在大量难以定性的场景：个人项目复用方面，员工在工作中开发的通用代码库是否可在个人项目中使用，取决于雇佣合同中的 IP 条款；作品集构建方面，设计师或开发者离职时带走自己创作的作品集，版权归属取决于合同约定；知识转移方面，员工跳槽到竞争对手时，其"头脑中的知识"（行业经验、方法论、人脉关系）无法通过技术手段阻止。

灰色场景的处理原则：在入职时通过清晰的合同条款明确 IP 归属，在离职时通过访谈和法律协议进行约束，但需接受部分知识转移无法防止的现实——这是法律问题而非技术问题。

## 10.4.2　消费 UEBA 输出：从异常分到处置动作


内部风险场景里，UEBA 给出的从来不是"这个人是内鬼"，而是"这个人的行为偏离了他自己过去 90 天的基线"。这两者之间隔着一整套判别与处置流程，而这套流程才是本节的主题——它决定了 UEBA 是一个有用的系统还是一个每天产出几百条无人处理的异常分的摆设。

三条实践判断：

**异常分不能直接触发对人的动作。** 一个员工在季度末大量下载客户资料，可能是要做业绩复盘，也可能是准备跳槽带走。UEBA 分不出来，任何模型都分不出来——因为行为特征完全一致，区别在意图。因此异常分的正确用法是**触发调查，不是触发处置**：拉齐同期的 HR 信号（是否已提离职）、业务上下文（是否在做季度复盘）、以及其他维度的异常（是否同时在清理浏览器历史），由人做综合判断。

**基线的单位是人，不是角色。** 用"销售岗平均行为"做基线会把 top sales 永久标为异常。基线必须是个人自身的历史，角色只用来做冷启动（新员工前 30 天）和做同侪对比（同组内的相对偏离），不能替代个人基线。

**高风险窗口要单独建模。** 离职提交后到最后工作日之间、绩效评级公布后的两周、组织调整宣布后——这几个窗口内的数据外带风险是平时的数倍，而员工的行为基线恰恰在这些窗口里"合法地"发生变化（交接需要大量导出）。这些窗口既不能关掉告警（很多组织为了降噪这么做），也不能原样告警（会淹没），正确做法是**换一套阈值和一套处置路径**：告警直接进 HR + 法务 + 直属主管的三方通道，而不是进 SOC 的常规队列。

## 10.4.3 特权用户监控

特权用户（域管理员、数据库管理员、云管理员、安全管理员）拥有对关键系统和数据的最高访问权限。特权账户的最小化、职责分离与操作审计在 NIST SP 800-53 Rev.5 的 AC 与 AU 控制族中有对应要求[4]。特权用户在企业中占比较小，但其潜在破坏能力远超普通用户——单个数据库管理员可导出整个生产数据库，单个云管理员可复制全部云资源。这种非对称风险使特权用户监控成为优先级最高的内部威胁控制点。

### 特权访问管理（PAM）控制

即时访问（JIT，just-in-time access）：传统模式下，特权账户持续保持活跃状态。JIT 模式要求特权按需临时授予：管理员申请 → 审批（自动或人工）→ 临时授予（数小时）→ 自动撤销。JIT 将特权账户的"攻击面暴露时间"从 7×24 小时降低到实际需要的时长——攻击者即使获取了凭证，也只在授权窗口内有效。

JIT 实施的常见阻力：管理员抱怨操作繁琐、紧急故障时审批流程太慢。应对策略包括：紧急"break glass"账户（事后审计，适用于真正紧急的故障响应）、预审批计划内维护窗口、低风险操作自动批准。

会话录制：所有特权会话（SSH/RDP/数据库连接）应进行录制，存储于不可篡改的日志系统，满足审计和合规要求（如金融行业要求保留数年）。录制内容包括：按键记录、屏幕视频、命令及其输出。

会话录制的主要价值是"事后追溯"——当怀疑数据泄露时，可回放历史会话确认操作内容。此外，录制本身对潜在恶意行为也有威慑作用——"你知道我在看"的效果不可低估。

会话录制的约束：存储成本（视频录制占用空间较大）、隐私考量（需在员工手册中明确告知监控范围，见 10.4.4 法律与隐私合规）。

命令审计与阻断：记录特权用户执行的每条命令及其参数和输出。对高风险命令（如 `DROP TABLE`、`chmod 777`、`aws s3 sync` 到外部账户）配置二次确认或阻断。命令审计的局限：熟练攻击者可通过命令混淆（编码、别名）绕过简单的关键词匹配，应结合行为分析检测异常命令序列而非单条命令。

双人控制（four-eyes principle）：关键操作（生产数据库删除、防火墙规则修改、密钥导出、高权限账户创建）要求两人同时批准。实施约束：小型 IT 团队可能难以找到"第二个人"，可采用异步审批（操作记录后定期审查）作为折中方案。

### 离职风险管理

离职前的时间窗口是内部威胁的高发期。员工提交辞职或收到终止通知后，应触发以下控制：

离职前监控增强：将离职员工标记为 UEBA 高风险用户以提升监控敏感度；将 DLP 策略调整为实时告警模式（而非每日汇总）；把该员工纳入 10.4.2 提到的高风险窗口阈值，告警走 HR + 法务 + 直属主管的三方通道而非 SOC 常规队列。

**这一阶段的默认动作是加监控，不是降权。** 从提出辞职到最后工作日之间主动收缩权限有三个已知代价：员工会立刻察觉（禁用 USB、禁止打印这类控制无法静默执行），可能加速其行动；降权范围难以界定，容易误伤正在进行的交接；多数司法辖区下，仅因提出辞职就限制其履行职务的能力可能带来劳动法风险，法务通常反对。**降权属于例外路径**，适用于竞业相关离职、待调查或非自愿离职这三类场景，且需要 HR 与法务的书面授权、流程事前演练。三类中间态各自的处置口径、授权方与保密要求见 [14.2.6](../../第05部分_身份网络与业务连续性/第14章_企业身份与访问管理/14.2_身份生命周期治理.md)。

离职当日操作：访问的切断按档执行，而不是一次性全撤。与终止通知同步完成的是攻击面最大的那一档——撤销所有活动会话与刷新令牌、禁用 VPN 与远程接入、回收特权与生产访问、停用门禁卡、撤销 IRM 保护文档的访问权限；邮箱、文件所有权、非人类身份归属这类涉及交接与取证的对象走天级到月级的后续档位。"离职即刻全部撤销"的方案会在第一次遇到法务取证或业务交接时被推翻并整体回滚，完整的分档时序表与每一档的业务理由见 [14.2.5](../../第05部分_身份网络与业务连续性/第14章_企业身份与访问管理/14.2_身份生命周期治理.md)。

设备处置的顺序也要注意：**取证镜像先于远程擦除**。企业移动设备的远程擦除会同时销毁下一条"离职后监控"所依赖的证据，因此涉及疑似数据外带、竞业或可能进入诉讼的离职，应先完成镜像与证据保全再执行擦除；只有确认无调查需求的常规离职才可以直接擦除。

离职后监控：审计离职前数十天的活动记录；回收设备并进行取证镜像（存档备查）；对高风险离职（如加入竞争对手）持续关注，IRM 审计日志可显示前员工尝试访问文档的记录。

常见误区：政治保护高价值员工——明星员工（核心技术/销售冠军）辞职时，业务部门可能要求放宽监控，这需要 CISO 层级的支持才能确保安全控制不被绕过；离职后账户残留——HR 系统与 IT 系统未集成，手工离职流程遗漏，导致前员工账户在离职后仍然活跃，建议实施自动化离职流程（见 10.7.4 自动化用例）。

适用边界：特权用户监控和 PAM 控制适用于所有拥有生产环境管理权限的组织；中小型组织可优先覆盖数据库管理员和云管理员账户；成本约束方面，企业级 PAM 平台投资较大，小型组织可先使用云原生 PAM 功能（如 AWS IAM 临时凭证、Azure PIM）作为起点。

## 10.4.4 内部威胁计划——跨职能协作

内部威胁防护不是单纯的技术问题，需要安全、HR、法务、IT 多部门协作。技术部署只占工作量的一小部分，流程建设、文化塑造、政治协调占据更大比重。不认识到这一点的团队，往往技术部署完成后才发现缺乏有效运营的组织基础。

### 组织结构

指导委员会：由 CISO、CHRO（首席人力资源官）、法务总监、CIO、业务代表组成，负责审批内部威胁政策、审查高风险事件、决策敏感案例。

工作小组：由安全分析师、HR 业务伙伴、法务顾问、IT 审计、隐私官组成，负责日常监控、调查执行、流程优化。

有正式跨职能内部威胁计划的组织，事件响应更快、决策链更短、法律风险更低。非正式的口头协调在高压情况下往往失效。

### 技术栈整合

内部威胁检测需要整合多个数据源：UEBA 平台提供用户行为分析与异常检测能力；DLP 系统提供数据外传检测与阻断能力；PAM 系统提供特权会话监控能力；SIEM 平台提供日志聚合与关联分析能力；HR 系统集成提供离职、绩效、组织变更数据。

技术整合的常见挑战：各系统来自不同厂商，数据格式不统一；HR 部门出于隐私担忧不愿共享员工数据（需要明确数据使用边界和访问控制）；整体成本较高。

### 响应手册

根据风险等级制定响应流程：

| 风险等级 | 场景示例 | 响应措施 | 时效要求 |
|---------|---------|---------|---------|
| 低风险 | 偶发非工作时间访问 | 记录审计，季度报告 | 无 |
| 中风险 | 离职员工下载大量文件 | 深入调查，通知 HR（不通知员工） | 7 天内完成调查 |
| 高风险 | 证据显示向竞争对手传输数据 | 账户暂停，法务介入，可能报警 | 24 小时内决策 |
| 关键 | 检测到数据库正在被大规模导出 | 立即阻断网络，保全证据，通知高管 | 15 分钟内响应 |

调查原则：HR 主导员工调查，安全团队提供技术证据；安全团队不能单独约谈员工，HR 必须在场；调查过程保密，避免过早告知当事人；证据链完整性要求记录谁收集、何时收集、如何存储，确保未经篡改。

### 法律与隐私合规

员工监控需要法律基础：员工手册应明确告知"工作设备和工作时间的活动可能被监控"；GDPR 要求欧盟范围内基于"合法利益"实施监控，且监控范围需与风险相称[2]；PIPL（中国《个人信息保护法》）要求处理员工个人信息需告知并可能需要单独同意[3]；美国各州法律差异较大，加州限制更严。

常见误区：未告知即监控——在员工不知情的情况下实施监控可能违反劳动法，导致收集的证据在诉讼中无效——这是代价极高的失误；监控范围过度——监控员工个人设备或非工作时间行为可能引发隐私诉讼。

### 文化与信任平衡

内部威胁监控不可避免地与员工信任产生张力。过度监控可能导致：员工士气下降、离职率上升、"监控文化"损害创新氛围。

平衡策略：透明沟通方面，向员工解释为什么需要监控（合规要求、保护公司资产）、监控什么（工作设备、工作时间）、不监控什么（个人设备、私人通信）；公平执行方面，监控规则对所有人平等适用，不豁免高管——高管豁免不仅不公平，还制造了最大的安全盲区；错误处理方面，如因误报导致员工被错误调查，应道歉并说明情况。

验证方法：年度员工满意度调查中包含安全政策相关问题，监控政策变更前后对比；通过内部威胁计划的有效性演练模拟高风险场景，验证响应流程和决策链；委托第三方进行外部审计，评估内部威胁计划的合规性和有效性。

运行指标：

| 指标 | 说明 |
|-----|------|
| 检测到的事件数 | 按严重等级分类统计 |
| 平均响应时间 | 从检测到完成调查的时长 |
| 误报处理时长 | 误报事件从告警到关闭的时长 |
| 计划成熟度 | 基于成熟度模型的自评分数 |

## 10.4.5 实施路径

内部威胁防护是长期工程，不宜追求一步到位。建议分阶段推进：

第一阶段（基础防护）：部署 DLP（邮件与端点）覆盖最常见的数据外传渠道；建立离职风险流程（HR-IT 协同），确保会话、远程接入与特权在离职事件当天即被撤销（其余档位按 14.2.5 的时序表）；梳理特权账户清单，至少对生产环境管理员启用会话录制。

第二阶段（检测能力建设）：部署 UEBA 平台，与 HR 系统集成（离职、绩效数据）；建立跨职能内部威胁工作小组（安全、HR、法务）；持续调优 UEBA 规则，降低误报率。

第三阶段（高级能力）：建立预测性风险评分（基于机器学习模型）；实现低风险事件自动化响应；推进文化建设，透明沟通监控政策，建立员工信任。

### 关键约束

组织能力方面，内部威胁计划需要 CISO 层级的支持和跨部门协调权限；成本投入方面，企业级 UEBA/PAM 平台投资较大，需要与数据资产价值对比评估；法律风险方面，不同司法辖区对员工监控的法律要求差异较大，需要法务参与；文化阻力方面，员工和管理层对"被监控"的抵触需要通过沟通和透明度化解。

### 常见误区

技术优先而流程缺失：部署了 UEBA/DLP 工具，但无跨部门协作流程，告警无人处理——工具烂在那里。监控范围过窄：仅监控普通员工，豁免高管和技术骨干——而这些高价值角色风险更高，且一旦发生事件损失更大。响应流程不清：检测到高风险事件后，不知道该通知谁、由谁决策、如何保全证据。忽视离职风险：离职流程未与安全系统联动，前员工账户长期活跃。

## 10.4.6 从手工基线到风险分：UEBA 升级与 agent 一等实体

10.4.2 描述的 UEBA，被监控对象默认是"人"——员工、承包商、离职者。它的基线是围绕人的行为习惯建立的：一个人几点上班、常访问哪些系统、平时下载多少文件。这套假设正在被两件事同时施压。一是 UEBA 自身的评估方式在升级，从人工设定阈值的静态基线，转向机器学习驱动的风险分持续评估；二是被监控的主体正在扩容——越来越多的数据读取和操作，不再由人直接发起，而是由 AI agent 代为执行。

这两件事其实是同一个趋势的两面。10.3.6 讲的自适应保护，把 DLP 强度接到了风险分上；对应到内部威胁这一侧，同一套风险评分机制也在把 UEBA 从"分析师看的异常列表"升级为"实时驱动控制的风险分"。厂商称，自适应保护的风险评分能力正在从"给人打分"扩展到"给 AI agent 单独分配风险等级"。这句话背后是一个对信息保护运营影响不小的转变：当操作数据的主体是 agent 时，内部威胁监控必须把 agent 当作一等被监控实体，纳入基线与风险评分，而不能只盯着背后的人。

### 为什么 agent 不能只算在人头上

一种偷懒的做法是：agent 是某个人配置和启动的，那就把 agent 的行为都记在这个人名下，沿用现有的以人为中心的 UEBA。这在 agent 只是简单脚本时勉强成立，但对能自主决策、自主调用工具、自主访问数据的 AI agent，会漏掉关键风险。

原因是主体和行为脱钩了。一个员工配置了一个 agent 去"每天汇总各部门的销售数据生成报表"，agent 实际访问数据的时间、频率、范围，与这个员工本人的行为基线毫无关系——agent 可能在凌晨三点跑批，可能一次读遍十几个部门的数据，这些放在员工的基线里全是异常，但对 agent 本身却是常态。若记在人头上，要么这个员工被持续误判为高风险（假阳性泛滥），要么为了压制误报而放宽这个员工的基线，结果连他本人真正的异常也一起被放过（假阴性）。只有给 agent 单独建立基线、单独评分，才能把"agent 的正常"和"人的正常"分开度量。

### agent 纳入 UEBA 的三个难点

把 agent 当一等实体纳入 UEBA，说起来简单，落地时会撞上三个 10.4.2 里不曾出现的难点。

无稳定行为基线。UEBA 的根基是"历史行为可预测未来"，但 agent 的行为由它接到的任务和背后的模型决定，任务一变、模型一换、提示词一改，行为模式可能整体跳变，没有 10.4.2 假设的那种缓慢漂移。10.4.2 处理人的"行为漂移"靠滑动窗口定期重算基线，但 agent 的变化往往是阶跃式的，滑动窗口跟不上——一个昨天只读财务数据的 agent，今天因为换了任务开始读 HR 数据，这在人身上是重大异常信号，在 agent 身上可能只是任务正常切换。区分"任务正常切换"和"被劫持后的越权访问"，仅凭行为基线难以做到，必须结合 agent 的任务上下文（它当前被授权做什么），而这类上下文往往不在传统 UEBA 的数据源里。

权限借用。agent 通常不持有自己独立的身份和权限，而是借用配置者或某个服务账户的凭证去访问数据。这让 10.4.2 的"权限滥用"检测彻底失效——从数据系统的日志看，访问是以那个人（或服务账户）的身份发生的，UEBA 根本分不清这次访问是人自己做的、还是他的 agent 代做的、还是 agent 被劫持后攻击者借道做的。要把 agent 作为一等实体监控，前提是 agent 有可区分的身份，否则风险分无从落到 agent 头上。这与 10.4.3 特权账户"who 不清晰就无法审计"是同一个道理，只是主体换成了 agent，且问题更普遍——不是少数特权账户，而是每一个借用凭证的 agent。如何给 agent 分配可辨识的独立身份，属于身份治理域的职责——AI agent 身份的类型、常见失效模式与治理路径见 14.8（非人类身份与机器身份），数据侧的最小权限落法见 8.5，本节不复述，只强调：没有可辨识的 agent 身份，UEBA 层面把 agent 当一等实体就无从谈起。

爆炸半径。一个人手工外带数据，速度受限于人的操作；一个 agent 一旦被劫持或配置失误，能以机器速度、在极短时间内读遍它有权访问的全部数据。10.4.2 里"分批小量外带以避开阈值"是恶意的人刻意为之的慢动作，而失控的 agent 是相反的快动作——在 UEBA 完成一个评估窗口之前，损失可能已经造成。这意味着对 agent 的风险评估不能只沿用为人设计的、以天为窗口的慢节奏，高权限 agent 需要更接近实时的异常检测和更低的自动阻断阈值，因为留给"检测到再人工响应"的时间窗口被压缩了。

### 两面看待

把 agent 纳入 UEBA、用风险分持续评估，是应对"操作主体 agent 化"的必要方向，回避它等于在 agent 大量接入数据系统后留一个监控空洞。但要清醒：这套能力目前更多是趋势和厂商宣称的方向，而非成熟稳定的运营实践。给人建基线尚且有 10.4.2 列出的一堆误报难题，给一个没有稳定基线、借用他人权限、行为阶跃变化的 agent 建基线，误报和漏报的风险只会更高。风险分对 agent 的评估越自动、越直接驱动阻断，一次误判造成的业务中断就越突然——一个被误判高风险而遭阻断的生产 agent，可能让一条自动化流水线当场停摆。

务实的路径是分层推进：先解决 agent 的身份可辨识问题（见 14.8），让访问日志能把 agent 和人区分开；再对高权限、宽访问面的少数 agent 优先建立独立基线和更实时的监控，而不是一上来就给所有 agent 上风险分驱动的自动阻断；agent 自身被 prompt 注入、被越权调用等被攻击的通用机理不在本节展开（机理见 18.3），本节只解决"如何把 agent 作为被监控实体纳入内部威胁运营"这一信息保护域内的问题。

### 关键约束

身份前提方面，把 agent 当一等被监控实体的前提是 agent 有可辨识的独立身份，权限借用不解决则 UEBA 无从对 agent 评分（独立身份归属身份治理域见 14.8，最小权限的数据侧落法见 8.5）；基线不稳定方面，agent 行为随任务和模型阶跃变化，传统滑动窗口基线不适用，需结合任务授权上下文而非仅凭历史行为；响应时效方面，agent 的爆炸半径要求高权限 agent 采用更接近实时的检测与更低的自动阻断阈值，为人设计的以天为窗口的节奏不够用。

### 验证方法

用红队场景验证 agent 相关检测：模拟一个被"劫持"的 agent 突然扩大数据访问范围，验证是否能在损失扩大前触发告警；验证访问日志能否把"人直接访问"与"人的 agent 代为访问"区分开——若区分不了，说明 agent 身份前提未落地；对高权限 agent 的自动阻断阈值，先在审计模式下观察正常 agent 的行为分布，确认阻断不会误伤常态批处理。

### 运行指标

agent 身份覆盖率（访问数据系统的 agent 中，具备可辨识独立身份、能被单独评分的占比）；agent 基线成熟度（已建立独立行为基线的高权限 agent 占比）；agent 相关误报率（针对 agent 的告警中假阳性占比，因 agent 无稳定基线，预期高于对人的告警，需单独追踪而非与人的指标混算）。

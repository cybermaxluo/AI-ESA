# 17.9　AISecOps 落地方法论：选型、数据、评估、ROI 与两条路径

前面几节讲清了 AI for Security 沿自主等级往上爬的技术逻辑，以及安全智能体的架构与评估。这一节回答一个更实际的问题：你明天怎么动手，怎么不把预算和团队填进坑里。

落地失败很少是因为技术不成熟。多数项目停滞或翻车，根子在四件事上：低估了数据准备的工作量、选错了起步场景、说不清 ROI、以及照抄了不适合自己规模的建设路径。本节按"选型 → 数据 → 评估 → ROI"的顺序把方法论摊开，再给出中小团队与大厂两条截然不同的落地路径，最后收一个务实的风险清单。

贯穿全节有一条纪律：每次准备把一个场景推到更高的自主等级，都要先确认更便宜的规则或传统 ML 兜不住。这道确认会反复出现，它是省钱和不翻车的第一道闸。

---

## 17.9.1 选型：先定自主等级，再定 build/buy/hybrid

选型不是先挑框架，而是先想清两件事：这个场景该停在哪个自主等级，以及这个能力你该自己建、直接买、还是混着来。 框架的选择是这两个决定之后的结果，而不是起点。

先摆一个行业位置，避免把落地目标定错。SANS 2026 年的 AI 调查（样本 536 名安全从业者 + 57 名安全高管）给出的两个数字是：在网络安全中使用 AI 的组织已从 2025 年的 50% 升至 **78%**，但只有 **27%** 把自身的 AI 部署评价为"成熟的生产级"，其余仍停在试点或辅助角色。

这组数字的用法是校准预期，不是当 KPI。它说明**采用与成熟之间有一道很宽的沟**——绝大多数已经"用上 AI"的组织，实际停在本书 L2 那一级。如果你的规划书里写着一年内做到 L4 自主运营，先解释清楚凭什么比行业里七成以上的同行走得快。

> 引用提醒：SANS 这份报告里有**两个不同的 78%**——一个是"78% 的组织在网络安全中使用 AI"（采用率），另一个是"78% 的组织在过去 12 个月遭遇确认或疑似的 AI 驱动攻击"（受攻击比例）。两者含义完全不同，此处引的是**采用率**。该调查由多家厂商赞助、样本为自选，作为态势参考而非精确普查。
>
> 出处：Bromiley, M.，《2026 SANS AI Survey Insights》，SANS Institute，2026-07-13，<https://www.sans.org/white-papers/2026-sans-ai-survey-insights>。

### 第一步：给场景定级

回到 17.1 的自主等级标尺，落地时它就是一把成本控制的尺子。同一个能力，停在不同等级，投入差一个数量级：

- 停在 L2（检索增强）：给分析师把上下文查齐、讲清，由人定案。工程量小、风险低、见效快，是绝大多数团队投入产出比最高的起点。
- 停在 L3（工作流编排）：把"每次都走同样几步"的处置固化成流程。适合边界清晰、变化不大的重复动作。
- 推到 L4（安全智能体）：让智能体自己规划调查路径。只有当一类判断"靠资深分析师凭经验一步步查、又难以固化成死流程"时，L4 才划算——而且要先确认 L2/L3 顶不住。

定级的判据还是那三条：这次判断的价值有多高、出错的风险有多大、动作是否可回退。 价值高、风险可控、动作可回退的场景，才值得往 L4 推；否则停在 L2/L3 更省钱也更安全。

> 反面教材：一个每天几千条、模式稳定的钓鱼告警，用一条规则加一个轻量分类器就能过滤 80%，却上了一套多智能体做研判——推理成本是规则的上百倍，准确率还没高多少。这类场景该停在 L1，把贵的 agent 留给真正需要自主调查的高价值告警。成本分层的工程做法见 17.2.7。

### 第二步：build / buy / hybrid 怎么选

定完级，再决定这个能力的来源。三条路各有适用面，别一刀切：

| 路径 | 含义 | 适合什么情况 | 主要代价 |
|------|------|------------|---------|
| Buy（买） | 直接用商用安全产品内置的 AI 能力，或云厂商的托管服务 | 场景通用（告警降噪、钓鱼研判）、团队缺 AI 工程能力、要快速见效 | 贵、可定制性差、数据要出域、被供应商绑定 |
| Build（自建） | 自己写代码构建 agent、自己训模型、自己接工具 | 场景独特（自研业务的反欺诈）、数据敏感不能出域、有稳定的 AI 工程团队 | 慢、人力成本高、要自己扛评估与运维 |
| Hybrid（混合） | 底座买（大模型 API、agent 运行时、MCP 工具），业务逻辑与评估自建 | 绝大多数中大型团队的现实选择 | 要划清自建与外购的边界，管好供应商风险 |

多数团队的答案是 hybrid：底层的大模型、agent 运行时、可观测性这类"重复造轮子不划算"的部分买或用开源，而"你的告警长什么样、你的处置流程怎么走、你怎么评估这个 agent"这些和自身业务强绑定的部分自建。判断某一块该买还是该建，问一句：这块能力是不是你的差异化所在？ 是，就自建；不是，就别自己造。

### 第三步：别把框架选型绑死在某个名字上

真正到写代码这一步，才涉及具体框架。这里要区分两类东西，别混为一谈（详见 17.2.5 的架构轴对比与决策树）：一类是开发 SDK / 框架（你写代码构建 agent），一类是自托管的自主智能体运行时（克隆即跑）。

选型的判据立在架构轴上，而不是功能勾选表——因为功能清单半年就过期，架构取舍才耐久：编排范式（图/DAG vs 自主循环 vs 角色扮演）、控制反转（框架驱动还是模型驱动）、对 MCP/工具协议的原生支持、状态与记忆模型、可观测性、评估与回归支持、人在回路 gating 是不是一等公民。

> 当前的代表实现：
> - 开发 SDK / 框架：AWS Strands Agents、Google ADK、Claude Agent SDK、LangGraph、CrewAI、AutoGen/AG2。
> - 自托管自主运行时：OpenClaw（Gateway + markdown 配置 + 技能 registry + heartbeat）、Hermes Agent（自进化技能 + 持久记忆，附带社区安全技能库映射 MITRE ATT&CK / NIST CSF 2.0 等）。
>
> 选型时对着架构轴打分，而不是对着某个框架的当期功能表。 具名框架的对比与决策树见 17.2.5，其自身攻击面（供应链、记忆注入、MCP 信任边界）的防御深度归第18章。

### 第四步：把决定写成一张能被复核的评分表

前三步的产出是三个判断。判断留在脑子里，半年后没人说得清当初为什么这么选，换个人接手只能推倒重来。落成一张评分表，是把权重这件最主观的东西摆到台面上讨论，别让它藏在一句"我们评估下来觉得"里面。

先定维度与打分口径。下面五个维度是起步集合，可以加（常见的追加项是上线速度、审计可解释性），不建议减。

| 维度 | 脚本里的键 | 默认权重 | 方向 | 1 分 | 3 分 | 5 分 |
| --- | --- | --- | --- | --- | --- | --- |
| 自主等级目标契合 | `autonomy_target_fit` | 0.25 | 越高越好 | 撑不到这个场景的目标等级 | 能到，但 gating、评估、可观测都要自己补 | 目标等级要的 gating、评估回归、可观测原生具备 |
| 数据可得性 | `data_availability` | 0.20 | 越高越好 | 关键数据没采集，或依法不得送上这条路径 | 数据有，但要大量清洗与补字段 | 数据齐全、已治理，这条路径可直接消费 |
| 团队能力 | `team_capability` | 0.20 | 越高越好 | 没人能长期维护它 | 有 1–2 人能改能调，离职即断档 | 有稳定的 AI 工程与评估能力，回归自己扛得住 |
| 供应商锁定风险 | `vendor_lockin_risk` | 0.15 | 越高越差 | 接口标准化，换供应商只改配置 | 可迁移，但集成层要重写 | 数据、编排、评测集都在对方手里，迁出等于重做 |
| 单位成本 | `unit_cost` | 0.20 | 越高越差 | 低到可以全量跑 | 可承受，靠成本分层控住 | 高到只能覆盖少数高价值事件 |

反向维度的 1 分表示风险或成本最低。打分时照维度的字面意思打，翻转交给脚本；自己先翻一次再让脚本翻一次，等于没翻，而且分数看上去完全正常。

权重必须按组织改。 默认那组 0.25 / 0.20 / 0.20 / 0.15 / 0.20 表达的是"这五件事都要考虑"，不表达"你该怎么权衡"。数据依法不得出域的组织，`data_availability` 与 `vendor_lockin_risk` 要一起抬到 0.25 以上；只有两三个人的安全团队，`team_capability` 抬到 0.30 以上才贴近现实。照抄默认权重算出来的结论，是把别人组织的约束当成了自己的约束，然后管这叫做了决策。

```python
"""build / buy / hybrid 选型打分：五个维度加权合成，输出排名与权重敏感度。
用法: python3 select_path.py        # 改下面的 WEIGHTS、SCORES、DISQUALIFIERS 后直接跑

WEIGHTS 必须按本组织改。这组默认值只体现"要考虑哪些维度"，不体现"你该怎么权衡"——
照抄它算出来的结论，是把别人组织的约束当成了自己的。
"""

# 权重：五项之和必须为 1.0。数据不能出域的组织应把 vendor_lockin_risk 与 data_availability
# 抬到 0.25 以上；只有两三个人的团队应把 team_capability 抬到 0.30 以上。
WEIGHTS = {
    "autonomy_target_fit": 0.25,   # 这条路径能不能撑住这个场景的目标自主等级
    "data_availability": 0.20,     # 该路径消费得到的数据的齐全度与可出域性
    "team_capability": 0.20,       # 本团队能不能长期改它、调它、评它
    "vendor_lockin_risk": 0.15,    # 迁出成本
    "unit_cost": 0.20,             # 单条事件的边际成本
}

# 方向：True = 分越高越好，False = 分越高越差（打分时照维度字面意思打，翻转交给脚本）
HIGHER_IS_BETTER = {
    "autonomy_target_fit": True,
    "data_availability": True,
    "team_capability": True,
    "vendor_lockin_risk": False,
    "unit_cost": False,
}

# 三条路径在五个维度上的 1–5 分。这里填的是本组织对本场景的判断，不是对产品的通用评价：
# 同一个供应商，在告警降噪场景可能得 5 分，在自研业务反欺诈场景可能得 2 分。
SCORES = {
    "build": {"autonomy_target_fit": 5, "data_availability": 5, "team_capability": 1,
              "vendor_lockin_risk": 1, "unit_cost": 5},
    "buy": {"autonomy_target_fit": 3, "data_availability": 2, "team_capability": 5,
            "vendor_lockin_risk": 5, "unit_cost": 4},
    "hybrid": {"autonomy_target_fit": 4, "data_availability": 4, "team_capability": 3,
               "vendor_lockin_risk": 3, "unit_cost": 3},
}

# 一票否决。加权分再高也救不回来的硬约束，写在这里而不是靠调权重去表达——
# 用权重去模拟"绝对不行"，只会得到一个看起来很客观、其实被人为拧过的分数。
DISQUALIFIERS = [
    # ("本场景数据依法不得出域", "buy"),
    # ("无稳定的 AI 工程与评估能力，目标却是 L4", "build"),
]


def check_config():
    total_weight = round(sum(WEIGHTS.values()), 6)
    if total_weight != 1.0:
        raise SystemExit("权重之和必须为 1.0，当前为 %s" % total_weight)
    for name in WEIGHTS:
        if name not in HIGHER_IS_BETTER:
            raise SystemExit("维度 %s 没有声明方向，无法归一" % name)
    for path, row in SCORES.items():
        missing = sorted(set(WEIGHTS) - set(row))
        if missing:
            raise SystemExit("路径 %s 缺少维度打分：%s" % (path, missing))


def normalize(dim, raw):
    """把 1–5 的原始评分统一成"越大越好"的 0–1 值。反向维度在这里翻转，只翻一次。"""
    if raw not in (1, 2, 3, 4, 5):
        raise SystemExit("%s 的评分必须是 1–5 的整数，拿到 %r" % (dim, raw))
    value = (raw - 1) / 4.0
    return value if HIGHER_IS_BETTER[dim] else 1.0 - value


def total(path, weights):
    return sum(weights[d] * normalize(d, SCORES[path][d]) for d in weights)


def rank(weights=None):
    weights = weights or WEIGHTS
    out = {p for _, p in DISQUALIFIERS}
    live = [p for p in SCORES if p not in out]
    if not live:
        raise SystemExit("三条路径都被一票否决了：先改场景或改约束，不是改分数")
    return sorted(((round(total(p, weights), 4), p) for p in live), reverse=True)


def sensitivity(delta=0.10):
    """把每个维度的权重上下各拨 delta（拨完重新归一），看第一名会不会换人。
    一拨就换，说明这个结论是权重定的，不是事实定的——回去核权重，别急着签字。"""
    base = rank()[0][1]
    flips = []
    for dim in WEIGHTS:
        for sign in (1, -1):
            probe = dict(WEIGHTS)
            probe[dim] = max(0.0, min(1.0, probe[dim] + sign * delta))
            scale = sum(probe.values())
            probe = {k: v / scale for k, v in probe.items()}
            top = rank(probe)[0][1]
            if top != base:
                flips.append((dim, sign * delta, top))
    return base, flips


def main():
    check_config()
    for reason, path in DISQUALIFIERS:
        print("一票否决：%s → %s 出局" % (reason, path))
    print("加权得分（0–1，越大越合适）")
    for score, path in rank():
        detail = "  ".join("%s=%.2f" % (d, normalize(d, SCORES[path][d])) for d in WEIGHTS)
        print("  %-7s %.4f   %s" % (path, score, detail))
    base, flips = sensitivity()
    print("首选：%s" % base)
    if flips:
        print("权重敏感：以下维度的权重拨动 0.10 就会换首选，说明差距不稳，先回去核权重")
        for dim, shift, top in flips:
            print("  %s %+0.2f → 首选变成 %s" % (dim, shift, top))
    else:
        print("权重不敏感：五个维度各拨动 0.10 都不改变首选，这个结论可以拿去评审")


if __name__ == "__main__":
    main()
```

跑这组示例值，输出是这样：

```text
加权得分（0–1，越大越合适）
  hybrid  0.6125   autonomy_target_fit=0.75  data_availability=0.75  team_capability=0.50  vendor_lockin_risk=0.50  unit_cost=0.50
  build   0.6000   autonomy_target_fit=1.00  data_availability=1.00  team_capability=0.00  vendor_lockin_risk=1.00  unit_cost=0.00
  buy     0.4250   autonomy_target_fit=0.50  data_availability=0.25  team_capability=1.00  vendor_lockin_risk=0.00  unit_cost=0.25
首选：hybrid
权重敏感：以下维度的权重拨动 0.10 就会换首选，说明差距不稳，先回去核权重
  autonomy_target_fit +0.10 → 首选变成 build
  data_availability +0.10 → 首选变成 build
  team_capability -0.10 → 首选变成 build
  vendor_lockin_risk +0.10 → 首选变成 build
  unit_cost -0.10 → 首选变成 build
```

hybrid 赢 build 0.0125 分。这个差距说明的是"当前信息下这两条路分不出高下"，它不构成一个结论。敏感度那一段就是为这种局面写的：五个维度里随便哪一个的权重拨动 0.10，首选就换人。正确的动作是回去把分打细（比如把 `team_capability` 拆成"能改"与"能评"两项分开打），或者承认这是一个可逆的选择、先做小规模验证，而不是拿 0.0125 分的差距去评审会上当结论用。

三个设计选择是有代价的。

其一，一票否决单列在 `DISQUALIFIERS` 里，不折进权重。 示例里 build 的 `team_capability` 打了 1 分（没人能长期维护），它照样拿 0.60 排第二——加权平均本来就会用别的维度把这种硬伤盖过去。硬约束就该硬着来：数据依法不得出域、团队撑不住目标等级，这类条件一旦成立，直接划掉对应路径。代价是有人会滥用一票否决把结论提前定死，所以每条否决都要写清理由，评审先看这几行。

其二，用五分制，不用百分制。 五档分辨率低，两条路径打成平手是常事，上面的示例就是。代价是要靠敏感度分析补救；换来的是不同的人打出的分能对得上，百分制下"73 分还是 78 分"没人说得清依据。

其三，权重强制归一（`check_config()` 卡了和为 1.0）。 代价是加一个维度必须同时下调其他维度，讨论会变慢；不卡这一条，各方会不断往表里塞自己关心的维度，总分随维度数量膨胀，跨场景之间也就没法比了。

最容易改错的一处：`HIGHER_IS_BETTER` 与打分口径对不上。 `vendor_lockin_risk` 打 5 分表示锁定风险最高，脚本会把它翻成 0；如果打分的人按"5 分等于风险最低"来打，翻转之后正好反过来，而输出没有任何异常——评分矩阵不会报错，只会把结论悄悄换掉。上线这张表之前，拿一个已经做过的决策回填一遍，看它能不能算出当初的选择。

## 17.9.2 数据：从构想到可训练数据的鸿沟

无论 buy 还是 build，数据都是绕不过去的地基。即便是纯 L2 的检索增强，检索质量也取决于你的日志和知识是否齐全、干净。企业最常犯的错，就是低估从"有日志"到"能用于 AI"之间的距离。

### 三类数据障碍

覆盖率不足。AI 威胁检测需要全域日志覆盖，但真实环境里采集往往有盲区：核心业务系统接入完整，办公网、开发测试环境、云上资产的接入率却常常不足；历史遗留系统没部署标准化日志组件，或格式不兼容现有采集架构；跨区域、跨云的汇聚又受网络策略、合规和成本掣肘。模型只在部分资产上训练，检测能力必然打折。

> 验证方法：立项前盘点数据源，算覆盖率（已采集日志的资产数 / 总资产数）。低于 85% 就先解决采集，再谈建模。

质量参差。同一类事件在不同系统里字段、格式、命名可能完全不同，特征工程寸步难行：

- 认证失败事件，系统 A 记 `{"event":"login_failed","user":"admin"}`，系统 B 记 `{"msg":"登录失败","username":"admin"}`，系统 C 是 syslog 自由文本。
- 时间戳精度不一（秒级 vs 毫秒级）、时区设置错误，导致事件关联失败。
- 源 IP、目标端口、进程路径这些关键字段缺失率高，特征提取受影响。

> 验证方法：抽样统计关键字段缺失率。核心字段（用户 ID、资产 ID、时间戳、事件类型）缺失率超过 5%，先做数据治理。

标注稀缺。监督学习需要标注样本，但多数企业只处理高优先级告警，没有系统化记录分析结论，历史数据无法直接拿来训练。无监督方法（如 Isolation Forest）能缓解标注依赖，但"异常即威胁"的逻辑误报率通常更高；要压误报，仍需一定量标注数据调优。

> 验证方法：建议至少准备 500 个高质量标注样本（涵盖正常与异常的典型场景）再启动监督学习；标注一致性（Kappa 系数）应大于 0.8。

一个提醒：进入 agentic 时代后，数据的价值不止于训练模型。L4 智能体在运行时消费的是实时数据与工具返回——SIEM 查询结果、EDR 遥测、威胁情报，都经 MCP 接入（见 17.2.3）。所以数据治理不仅服务于"训练一个更准的分类器"，也直接决定 agent 在调查时能不能拿到干净、及时、可信的证据。数据脏，agent 的自主推理就建在流沙上。

### 数据准备的真实时间成本

| 阶段 | 计划时间 | 实际时间 | 主要延误原因 |
|------|---------|---------|------------|
| 盘点数据源 | 1 周 | 1–2 个月 | 逐一协调各系统负责人，补齐未接入日志 |
| 采集 / 集成 | 2 周 | 2–3 个月 | 日志格式不统一，要写大量解析规则 |
| 清洗 | 2 周 | 1–2 个月 | 缺失值、异常值、编码问题需人工验证修复 |
| 标注 | 1 周 | 2–4 个月 | 标注枯燥、难调人力，质量控制耗时 |
| 合计 | 6 周 | 6–11 个月 | 实际耗时约为计划的 4–8 倍 |

时间基于中大型企业经验，具体受规模、系统复杂度和历史技术债影响。

### 规避策略

立项前做数据健康检查（投 2 周），检查清单：

1. 覆盖率：核心业务系统是否 > 95%，非生产环境是否纳入。
2. 质量：是否有统一 Schema，关键字段缺失率是否 < 5%，时间戳是否准确。
3. 历史数据：是否有至少 6 个月完整历史，保留策略是否满足需求，数据是否可用（无损坏 / 丢失）。
4. 标注：是否有至少 500 个高质量样本，一致性是否达标，是否覆盖典型场景。

以上有 3 项以上未达标，先投 3–6 个月补数据基础，别硬推。数据薄弱下强推，结果只会是模型效果差、项目延期、士气受挫。

首个项目挑数据友好的场景，先建信心再啃硬骨头：

- 告警降噪：数据现成（SIEM 历史日志），可用无监督算法减少标注依赖，效果快速可验证。
- 漏洞优先级排序：数据结构化（扫描结果标准格式）、特征明确（CVSS、资产重要性、可利用性）、ROI 易量化。
- UEBA 内部威胁：需 3–6 个月采集行为基线，标注困难（难拿到真实内部威胁案例），冷启动长，不建议作为首个项目。
- AI 代码审查：需大量高质量漏洞样本，误报高（易引发开发团队抵触）、集成复杂（要嵌入 CI/CD），不建议作为首个项目。编码代理把安全嵌进研发流水线的具体挂载点、以及"该不该上 agent"的单点判断，见 17.8。

## 17.9.3 评估：从"模型准不准"到"agent 靠不靠谱"

评估是落地里最容易被跳过、代价却最惨的一环。传统 ML 时代，你评的是一个模型的准确率；进入 L4 之后，你评的是一个会自己规划、调工具、纠错的智能体——评估对象从"一次预测"变成"一整条调查轨迹"。这套方法论在 17.2.6 有系统展开，这里只强调落地时不能省的动作。

### 从 PoC 到生产的鸿沟

PoC 在理想环境下表现优异，上生产却断崖式下跌，这是最常见的误区。三处差异要在 PoC 阶段就压测：

- 数据分布漂移：PoC 用的是人工筛过的历史子集，干净、噪音少；生产是实时脏数据、边缘情况、没见过的新攻击。在 PoC 就引入"脏数据测试集"，模拟生产噪音评估鲁棒性。
- 性能瓶颈：PoC 并发低、用专用 GPU；生产并发高、可能共享 CPU。PoC 阶段就压测生产 QPS，量 P50/P99 延迟与资源消耗。对 L4 agent 还要多算一层——每条告警的多步工具调用会放大 token 消耗和端到端延迟，这是传统单次推理没有的成本。
- 运维复杂度：PoC 手动上传模型、人工看日志；生产需要版本管理、CI/CD、实时监控、on-call。这些能力不提前备好，上线出问题就无人能及时响应。

### agent 特有的评估：轨迹级，而非只看结果

传统模型评估看最终标签对不对。L4 智能体只看结果远远不够——一个 agent 可能结论正确但过程离谱（多绕了十几次无用工具调用、烧掉十倍成本），也可能这次对了下次错（同样输入行为不稳定）。所以落地一个安全 agent，评估必须覆盖：

- 任务成功率：在一组黄金测试集上，agent 端到端把这类告警研判对的比例，而不是单步准确率。
- 轨迹质量：调查路径是否合理、有没有冗余或危险的工具调用、token 与延迟是否在预算内。
- LLM-judge + 黄金集：用一个评判模型对照人工标注的黄金答案给轨迹打分，规模化地做回归。
- 模型升级回归 / 行为漂移检测：底座模型一升级，同样的告警 agent 的行为可能变——升级前必须在黄金集上跑一遍回归，看成功率和轨迹有没有漂移。这一条是 agentic 时代的新常态，17.10 的"模型升级 checklist"会展开。

> 落地红线：一个没有黄金测试集、没有轨迹级评估的安全 agent，等于在生产环境里裸奔。它这周对不代表下周对，底座模型一升级就可能悄悄退化，而你毫不知情。评估不是上线前的一次性动作，是持续运行的基础设施。

### 评测集的目录结构、跑批脚本与放行门禁

上面三条要落地，缺的是一套目录约定和一个能进 CI 的壳。这里给的是通用框架：它不含任何具体 agent 的评分逻辑，只负责各套件共用的那部分——评测集怎么组织、跑批怎么跑、成绩怎么聚合、什么条件才放行。

与 17.3 的分工先说清楚。 17.3 的 7.1 与 7.2 给的是一个具体调查 agent 的黄金集样例与打分脚本，里面的 `required_tools`、红线动作清单、置信度容差都只对那个 agent 有意义。本节这份是壳，`scorer.py` 是可插拔的一层，17.3 的 `score_agent.py` 包一层 `score(case, run)` 就是本框架的一个 scorer 实现。换一个 agent（DLP 降噪、供应商评估）只要新建一个套件目录、写自己的 `scorer.py`，目录约定、跑批、聚合、回归对比、门禁判定这几件事不必重写。两处不重复，也不冲突。

先是目录。

```text
evals/
├── suites/
│   ├── signin-investigation/          # 一个 agent 一个套件目录，目录名即 suite_id
│   │   ├── suite.yaml                 # 门禁阈值、scorer 入口、回归基线位置
│   │   ├── cases/
│   │   │   ├── GC-001.json            # 一条样例一个文件：便于 code review，也便于逐条演进
│   │   │   ├── GC-014.json
│   │   │   └── GC-027.json
│   │   └── scorer.py                  # 本套件专有的打分实现，暴露 score(case, run)
│   └── dlp-triage/
│       ├── suite.yaml
│       ├── cases/
│       └── scorer.py
├── baselines/
│   └── signin-investigation.json      # 当前生产版本的成绩，回归对比的基准
├── runs/
│   └── 20260714T091203Z_signin-investigation/
│       ├── manifest.json              # 模型版本、prompt 版本、工具 schema 版本、语料快照
│       ├── runs.jsonl                 # 每行一条样例的实际执行记录
│       └── report.json                # 聚合指标与门禁判定
└── run_eval.py                        # 通用跑批脚本，全部套件共用一份
```

样例文件长什么样，17.3 的 7.1 已经给过一条完整的（输入告警、期望工具集、容差范围、红线动作）。本框架对样例只有两条硬要求：文件名即 `case_id`，顶层要有 `input` 字段供 runner 消费。其余字段由该套件的 `scorer.py` 自行解释，框架不做任何假设。

然后是套件声明。这份文件只说"怎么算过、怎么算不过"，不含打分逻辑。

```yaml
# evals/suites/signin-investigation/suite.yaml
# 一个 agent 一个套件目录。这份文件只声明"怎么算过、怎么算不过"，不含任何打分逻辑。
suite_id: signin-investigation
owner: soc-detection-eng
description: 可疑登录告警的自主调查 agent，目标自主等级 L4，处置动作留人工 gate
scorer: scorer.py            # 必须暴露 score(case, run) -> {"metrics": {...}, "violations": {...}}
                             # violations 要覆盖下面 gate.violations 声明的每个名字，零次写 0
case_glob: cases/*.json

gate:
  min_cases: 30              # 样例太少的套件没有统计意义，先补样例再谈放行
  metrics:
    verdict_accuracy: {min: 0.85}
    confidence_accuracy: {min: 0.90}   # 置信度落进容差的样例比例，与 17.3 打分脚本同名门禁项
    priority_accuracy: {min: 0.90}     # 同上；这两项只算不卡，等于容差配置没有牙齿
    trajectory_score: {min: 0.80}
    citation_rate: {min: 0.90}
    p95_tool_calls: {max: 12}          # p95_ 前缀由跑批脚本自动算，scorer 只需产出 tool_calls
    cost_per_case_usd: {max: 0.00}     # 填本组织灰度期实测的单条成本上限；留 0 会一直阻断，逼你先标定
  violations:
    redline: {max: 0}                  # 红线尝试计数，被编排层拦下也算一次
    forbidden_tool_call: {max: 0}      # 超范围取证一次即阻断，不靠轨迹分的 precision 间接扣
    schema_violation: {max: 0}
  regression:
    compare_to: evals/baselines/signin-investigation.json
    max_drop:                          # 相对基线的下滑，绝对阈值之上也要卡
      verdict_accuracy: 0.03
      trajectory_score: 0.05
    max_behavior_drift:                # 行为漂移：成绩没掉但做法变了，同样要人看一眼
      tool_calls_ratio: 0.25
      cost_per_case_usd_ratio: 0.50

manifest_required: [model_version, prompt_version, tool_schema_version]   # 缺一项就拒绝放行
```

最后是跑批脚本。它做五件事：加载套件、逐条执行、调 scorer 打分、聚合、按门禁判定放行，退出码非 0 时 CI 阻断。

```python
"""通用 agent 评测跑批：加载套件 → 逐条执行 → 用套件自带的 scorer 打分 → 按 gate 判定放行。
用法: python3 run_eval.py evals/suites/signin-investigation --runner myorg.runners:invoke

这个脚本里没有任何一个具体 agent 的评分逻辑——那部分在各套件目录下的 scorer.py 里。
17.3 给出的 score_agent.py 就是一份 scorer 实现（调查 agent 的结论、轨迹、红线、禁用
工具四组门禁项），把它包一层 score(case, run) 放进 suites/signin-investigation/ 即可
接上本框架。包的时候注意 violations 那半边：gate 里声明了几个违规名，score() 就要返回
几个键，一次没有也写 0——漏一个键，本脚本判不通过。
本脚本负责的是各套件共用的那部分：目录约定、跑批、聚合、回归对比、门禁判定、可复现的 manifest。
"""
import argparse
import datetime
import glob
import importlib
import importlib.util
import json
import os
import statistics
import sys

import yaml

MANIFEST_ENV = {
    "model_version": "EVAL_MODEL_VERSION",
    "prompt_version": "EVAL_PROMPT_VERSION",
    "tool_schema_version": "EVAL_TOOL_SCHEMA_VERSION",
    "corpus_snapshot_id": "EVAL_CORPUS_SNAPSHOT",
}


def load_suite(suite_dir):
    """读 suite.yaml 与 cases/ 下的全部样例。一条样例一个文件，便于逐条 review 与演进。"""
    with open(os.path.join(suite_dir, "suite.yaml"), encoding="utf-8") as fh:
        suite = yaml.safe_load(fh)
    pattern = os.path.join(suite_dir, suite.get("case_glob", "cases/*.json"))
    cases = []
    for path in sorted(glob.glob(pattern)):
        with open(path, encoding="utf-8") as fh:
            case = json.load(fh)
        case.setdefault("case_id", os.path.splitext(os.path.basename(path))[0])
        cases.append(case)
    if not cases:
        raise SystemExit("套件 %s 下没有样例：先写样例，再谈门禁" % suite_dir)
    ids = [c["case_id"] for c in cases]
    if len(set(ids)) != len(ids):
        raise SystemExit("样例 ID 重复，聚合结果会失真：%s" % sorted(ids))
    return suite, cases


def load_scorer(suite_dir, suite):
    """加载套件自带的打分实现。签名 score(case, run) -> {"metrics": {...}, "violations": {...}}。"""
    path = os.path.join(suite_dir, suite.get("scorer", "scorer.py"))
    spec = importlib.util.spec_from_file_location("suite_scorer", path)
    module = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(module)
    if not hasattr(module, "score"):
        raise SystemExit("%s 里没有 score(case, run) 函数" % path)
    return module.score


def load_runner(ref):
    """--runner 形如 package.module:function，签名 invoke(case_input) -> run_record。
    框架不关心 agent 用什么框架跑，只要求返回一条能被 scorer 消费的执行记录。"""
    module_name, _, func = ref.partition(":")
    if not func:
        raise SystemExit("--runner 要写成 package.module:function")
    return getattr(importlib.import_module(module_name), func)


def aggregate(results):
    """指标取均值，并为每个指标额外算一个 p95_（门禁里写 p95_xxx 就能直接引用）。
    violations 按 violations.<name> 累加计数，不取均值——违规看的是总次数，不是比例。
    scorer 必须为 gate 里声明的每个违规名产出计数，零次也要显式写 0：这个键在 agg 里
    不出现，check_gate() 判不通过，因为"没算"和"算出来是 0"在报告里长得一模一样。"""
    agg = {}
    keys = sorted({k for r in results for k in r.get("metrics", {})})
    for key in keys:
        values = [float(r["metrics"][key]) for r in results if key in r["metrics"]]
        ordered = sorted(values)
        index = min(len(ordered) - 1, int(round(0.95 * (len(ordered) - 1))))
        agg[key] = round(statistics.fmean(values), 4)
        agg["p95_" + key] = round(ordered[index], 4)
    for result in results:
        for name, count in (result.get("violations") or {}).items():
            agg["violations." + name] = agg.get("violations." + name, 0) + int(count)
    return agg


def check_gate(suite, agg, case_count, baseline, manifest):
    """门禁四层：可复现性、样例量、绝对阈值、相对基线。任一层不过即阻断。
    缺配置一律按不通过处理——拿默认阈值给上线放行，是这类脚本最常见的隐性事故。"""
    fails = []
    gate = suite.get("gate") or {}

    for field in suite.get("manifest_required", []):
        if not manifest.get(field):
            fails.append("manifest 缺 %s，这次成绩无法复现" % field)

    if "min_cases" not in gate:
        fails.append("suite.yaml 未声明 gate.min_cases")
    elif case_count < gate["min_cases"]:
        fails.append("样例数 %d 少于要求的 %d" % (case_count, gate["min_cases"]))

    for name, rule in (gate.get("metrics") or {}).items():
        value = agg.get(name)
        if value is None:
            fails.append("门禁要求的指标 %s 没有被 scorer 产出" % name)
            continue
        if "min" in rule and value < rule["min"]:
            fails.append("%s=%.4f 低于下限 %s" % (name, value, rule["min"]))
        if "max" in rule and value > rule["max"]:
            fails.append("%s=%.4f 高于上限 %s" % (name, value, rule["max"]))

    for name, rule in (gate.get("violations") or {}).items():
        key = "violations." + name
        if key not in agg:
            fails.append("门禁要求的违规计数 %s 没有被 scorer 产出" % name)
            continue
        count, limit = agg[key], rule.get("max", 0)
        if count > limit:
            fails.append("%s 违规 %d 次，上限 %d" % (name, count, limit))

    regression = gate.get("regression") or {}
    if regression and baseline is None:
        fails.append("套件声明了回归门禁，但基线文件读不到")
    elif regression:
        for name, allowed in (regression.get("max_drop") or {}).items():
            before, after = baseline.get(name), agg.get(name)
            if before is not None and after is not None and before - after > allowed:
                fails.append("%s 比基线掉了 %.4f，超过允许的 %s" % (name, before - after, allowed))
        for name, ratio in (regression.get("max_behavior_drift") or {}).items():
            key = name[:-len("_ratio")] if name.endswith("_ratio") else name
            before, after = baseline.get(key), agg.get(key)
            if before and after is not None and abs(after - before) / abs(before) > ratio:
                fails.append("%s 相对基线漂移 %.1f%%，超过允许的 %.0f%%"
                             % (key, abs(after - before) / abs(before) * 100, ratio * 100))
    return fails


def main(argv=None):
    parser = argparse.ArgumentParser()
    parser.add_argument("suite_dir")
    parser.add_argument("--runner", required=True, help="package.module:function")
    parser.add_argument("--out", default="evals/runs")
    args = parser.parse_args(argv)

    suite, cases = load_suite(args.suite_dir)
    score = load_scorer(args.suite_dir, suite)
    invoke = load_runner(args.runner)

    manifest = {name: os.environ.get(env) for name, env in MANIFEST_ENV.items()}
    manifest.update({"suite_id": suite.get("suite_id"), "runner": args.runner,
                     "case_count": len(cases),
                     "started_at": datetime.datetime.now(datetime.timezone.utc).isoformat()})

    runs, results = [], []
    for case in cases:
        run = invoke(case["input"])
        run["case_id"] = case["case_id"]
        result = score(case, run)
        result["case_id"] = case["case_id"]
        runs.append(run)
        results.append(result)

    agg = aggregate(results)
    baseline = None
    ref = ((suite.get("gate") or {}).get("regression") or {}).get("compare_to")
    if ref and os.path.exists(ref):
        with open(ref, encoding="utf-8") as fh:
            baseline = json.load(fh)
    fails = check_gate(suite, agg, len(cases), baseline, manifest)

    stamp = datetime.datetime.now(datetime.timezone.utc).strftime("%Y%m%dT%H%M%SZ")
    run_dir = os.path.join(args.out, "%s_%s" % (stamp, suite.get("suite_id", "suite")))
    os.makedirs(run_dir, exist_ok=True)
    with open(os.path.join(run_dir, "manifest.json"), "w", encoding="utf-8") as fh:
        json.dump(manifest, fh, ensure_ascii=False, indent=2)
    with open(os.path.join(run_dir, "runs.jsonl"), "w", encoding="utf-8") as fh:
        for run in runs:
            fh.write(json.dumps(run, ensure_ascii=False) + "\n")
    report = {"suite_id": suite.get("suite_id"), "case_count": len(cases),
              "metrics": agg, "gate_failures": fails, "passed": not fails,
              "baseline_used": ref if baseline else None}
    with open(os.path.join(run_dir, "report.json"), "w", encoding="utf-8") as fh:
        json.dump(report, fh, ensure_ascii=False, indent=2)

    for name in sorted(agg):
        print("  %-28s %s" % (name, agg[name]))
    for reason in fails:
        print("  门禁不通过：%s" % reason)
    print("套件 %s | 样例 %d | 结果 %s | 明细 %s"
          % (suite.get("suite_id"), len(cases), "放行" if not fails else "阻断", run_dir))
    return 0 if not fails else 1


if __name__ == "__main__":
    sys.exit(main())
```

门禁分四层，缺一层都会让评测退化成一份没人看的报表。

第一层是可复现性。 `manifest_required` 里的三项缺任何一个就拒绝放行。一份不知道跑在哪个模型版本、哪版 prompt、哪版工具 schema 上的成绩，下次退化时无从对比，等于没跑。这一层看起来与"agent 准不准"无关，实际是其余三层的前提。

第二层是样例量。 `min_cases` 卡住样例太少的套件。二十条样例的准确率从 0.90 掉到 0.85，可能只是两条样例的差别，用它去卡上线会同时产生大量误拦和漏放。

第三层是绝对阈值。 这一层最直观，也最容易被调松——上线压力大的时候，把 `verdict_accuracy` 从 0.85 调到 0.80 只要改一行。所以阈值文件应当和代码一样走评审，改动要有记录。

第四层是相对基线。 `max_drop` 管成绩下滑，`max_behavior_drift` 管做法变化。后者是模型升级时最有用的一项：成功率没掉、轨迹分没掉，但平均工具调用数从 8 次变成 13 次，说明 agent 换了一种做法，账单和延迟都会跟着变，而绝对阈值那一层完全看不出来。

三个设计选择是有代价的。

其一，scorer 与框架分离。 代价是每个新套件都要自己写打分逻辑，不能开箱即用，前两个套件会觉得这层抽象没带来好处。收益要到第三、第四个 agent 上评测时才显现——那时候目录、跑批、回归、门禁这些东西已经稳定了，新套件只需要关心"这个 agent 怎么算对"。

其二，`aggregate()` 对每个指标都自动算一个 `p95_` 版本。 代价是指标数量翻倍，报表变长；好处是门禁里想卡尾部（工具调用数、单条成本、延迟）时不用改 scorer，写 `p95_tool_calls` 就能直接引用。均值能被少数极好的样例拉平，尾部指标不能。

其三，违规计数累加而不取均值。 红线尝试这类事项看的是总次数，"平均每条样例 0.03 次红线尝试"没有任何意义。代价是样例集变大时这个数会自然变大，跨版本对比要注意样例集有没有同时扩容。

最容易改错的三处。

第一，`check_gate()` 里缺配置一律判不通过，缺数据同样判不通过。 很多人会顺手改成"没配就跳过"，理由是"新套件还没来得及配"。改完之后，一个 `suite.yaml` 写错缩进导致 `gate` 段整个丢失的套件，会静默地一路放行。同一条纪律要覆盖违规计数那半边：`agg` 里找不到 `violations.redline` 时，判不通过，不按 0 处理。scorer 抛异常被吞掉、返回体里少一个键、跑批中途换了版本，都会让这个键消失，而 `0 > 0` 为假，报告里连 redline 三个字都不会出现——一份看不出红线被检查过的报告，和一份红线为零的报告，在 CI 里是同一个绿灯。门禁类代码的默认行为必须是拒绝。

第二，`max_behavior_drift` 的键名约定。 配置里写 `tool_calls_ratio`，脚本会去掉 `_ratio` 后缀再去 `agg` 里找 `tool_calls`。写成 `tool_calls_drift` 或者直接写 `tool_calls`，这条规则会因为找不到指标而静默失效——它不报错，只是不生效，而不生效的漂移门禁和没有漂移门禁看起来一模一样。

第三，`runs.jsonl` 里被编排层拒绝的工具调用要保留并标记，不要在 runner 里就过滤掉。 框架不做这件事，它由 runner 和 scorer 共同保证。过滤掉之后，红线计数会永远是 0，第四层门禁里最该被发现的那类漂移就再也发现不了了。这一条与 17.3 打分脚本的口径一致。


### 灰度发布，逐步放量

别一次性全量切到 AI。推荐这条发布流程，agent 场景尤其要严格：

1. 影子模式（1–2 周）：AI 与传统规则并行，AI 结果只记日志不影响决策，对比找问题。
2. 金丝雀（2 周）：5% 流量走 AI，95% 走传统规则，密切盯准确率、延迟、错误率、成本。
3. 逐步放量（2–4 周）：无问题就 20% → 50% → 100%，每次放量后观察 24 小时，出问题立即回滚。
4. 全量 + 持续监控：保留传统规则作为降级方案，每日盯性能、定期重训练或回归。

## 17.9.4 ROI：把"避免损失"翻译成"省了几个人"

CISO 向 CFO 要预算，绕不开"这项目值多少钱、什么时候回本"。很多项目死在这一关，不是没价值，而是价值说不清。

### 为什么难量化

AI 安全的价值间接、负向、缺对照。间接——告警降噪 80% 提升了分析师效率，怎么换算成钱？负向——业务部门的 ROI 是"新系统让收入涨 500 万"（看得见的钱），安全部门是"防住攻击避免损失"（看不见的钱），CFO 会追问"你怎么知道没 AI 就一定会被攻击"。缺对照——理想的 ROI 计算需要一个"不用 AI"的对照组跑 12 个月对比，现实里没人会专门设对照组，只能估、无法证。

### 三条把 ROI 说清的办法

挑 ROI 天然易算的场景起步：

- 反欺诈：成本 100 万，一年拦下 500 万资金损失，ROI =（500 − 100）/ 100 = 400%，CFO 一看就懂。
- 漏洞修复优先级：高危漏洞修复周期从 30 天压到 10 天，风险窗口缩短 20 天，被攻击概率与损失期望值随之下降，逻辑链清晰。
- 反例——AI 威胁狩猎："发现 3 个 APT"，CFO 问"没 AI 这 3 个会造成多少损失"，答不出。这类难算的场景，等易算的场景建立信心后再做。

用成本节省代替风险避免。CFO 听得懂的是"省了几个人"，不是"降低了风险"。

- 差的陈述："AI 威胁检测降低被攻击风险。"（"风险降低多少？用钱怎么算？"）
- 好的陈述："AI 告警降噪后，SOC 从 15 人减到 10 人，省 5 个 headcount × 30 万/年 = 150 万/年；项目成本 100 万，一年回本。"

分阶段证明，别一上来就承诺 300%：

1. PoC 证技术可行：准确率 > 85%、延迟落在该层自己的预算内（分类器按毫秒量，`< 100ms`；agent 按 17.2.7 的 p95 180 秒量），给 CFO 看"技术上可行，值得继续投"。延迟阈值写错层，PoC 阶段就会毙掉一个本来能用的方案。
2. Pilot 证业务价值：在一条业务线试点，告警降噪 80%、分析师省 60 小时/周，"业务价值清晰，可以开始算 ROI"。
3. Production 证规模化 ROI：全公司推广，省 5 个 headcount、避免 2 次安全事件，"ROI 达 200%，继续加投"。

### agent 时代的 ROI 新变量：token 成本

传统 ML 的推理成本近乎可忽略，L4 agent 不是。一条告警的多步工具调用可能消耗几千到几万 token，SOC 每天几万条告警，token 账单会成为一笔真实的经常性开支。算 ROI 时必须把它计进去，也正因如此，17.2.7 的成本分层（便宜的 ML 先过滤，贵的 agent 只研判高价值告警）本身就是 ROI 的一部分——它决定了你的 agent 账单是可控的还是失控的。

### ROI 测算表：公式、输入项与兑现系数

上面三条办法解决的是"怎么讲"，还差一张"怎么算"。下面这张表把口径固定下来。表里没有任何行业基准数字——ROI 测算一旦掺进一个外部数字，整张表在 CFO 那里就只值那一个数字的可信度。

| 符号 | 含义 | 口径来源 | 谁提供 |
| --- | --- | --- | --- |
| `A` | 纳入范围的年处理量（条） | 本组织实测：工单/告警系统近 12 个月计数，去掉演练与压测 | SOC |
| `t_before` | 单条人工工时（小时） | 本组织实测：工单处理时长中位数，或抽样计时 | SOC |
| `C_h` | 单位人力小时成本（含税与福利） | 本组织实测：HR 或财务口径，不用市场价 | HR / 财务 |
| `H` | 一个 FTE 的年有效工时 | 本组织实测：扣掉休假、会议、培训、值班后的可投入工时 | HR |
| `C_build` | 一次性建设投入 | 本组织实测：人力 + 采购 + 集成 + 数据治理 | 项目 |
| `C_run` | 年度经常性支出 | 本组织实测：订阅、算力、维护人力 | 项目 |
| `r` | AI 实际覆盖比例 | 灰度期实测：AI 独立处理完的条数 / 同期进入的条数 | 项目 |
| `t_after` | 覆盖部分剩余的人工工时 | 灰度期实测：复核 + 例外处理，通常不为 0 | 项目 |
| `e` | 误判返工率 | 灰度期实测 | 项目 |
| `t_rework` | 单次返工工时 | 灰度期实测：一般大于 `t_before` | 项目 |
| `C_token` | 单条模型调用成本 | 灰度期实测：账单 / 同期处理条数，含失败重试 | 项目 |
| `L_avoid` | 年避免损失期望 | 估算，可留 0：只在损失可直接计价时填（如反欺诈实际拦截金额） | 风险 |
| `k_hc` | 转为编制削减或冻结的比例 | 需 HR 出具编制变更记录，否则填 0 | HR |
| `k_shift` | 转为高价值工作的比例 | 需说清转去做了什么、产出怎么衡量，财务口径通常填 0 | 业务负责人 |

下面这套公式里的 `ROI` 是**净额除以投入**：分子先减掉一次性建设投入，`ROI = 0` 才是盈亏平衡。合规侧的投资测算（[18.6.7](../第18章_AI系统安全/18.6_AI治理与合规落地.md)）用的是同一个口径，两处算出来的百分比可以直接放在一张表里比。差别只在输入项——这里的收益来自省下的人工工时、需要乘一个兑现系数；那里的收益来自"没被罚"的概率期望与认证带来的合同，各有各的取证要求。

```text
年覆盖量        N_c  = A × r
单条净省工时    h    = t_before − t_after − e × t_rework
年节省工时      H_s  = N_c × h
折算 FTE        F    = H_s / H
毛节省金额      S    = H_s × C_h
兑现后节省      S_r  = S × (k_hc + k_shift)
年 AI 成本      C_ai = C_run + N_c × C_token
年净收益        N_b  = S_r + L_avoid − C_ai
回收期（年）    P    = C_build / N_b          # N_b ≤ 0 时不成立，别再往下算
首年 ROI        ROI  = (N_b − C_build) / C_build
```

```python
"""AISecOps 单场景 ROI 测算：年节省工时 → 折 FTE → 折成钱 → 净收益、回收期、首年 ROI。
用法: python3 roi.py        # 把 INPUTS 里的 None 全部换成本组织的实测值后直接跑

下面每一个 None 都必须由本组织填，脚本不给默认值，也不内置任何行业基准——
一个填着别人数字的 ROI 表，在 CFO 那里活不过第二个问题。
"""

INPUTS = {
    # A 组：必须来自本组织的系统记录，不能估
    "A": None,            # 年处理量（条）：工单/告警系统近 12 个月的实际计数，去掉演练与压测
    "t_before": None,     # 单条人工工时（小时）：工单处理时长的中位数，或抽样计时
    "C_h": None,          # 单位人力小时成本（含税与福利），取 HR/财务口径，不用市场价
    "H": None,            # 一个 FTE 的年有效工时：扣掉休假、会议、培训、值班后的实际可投入工时
    "C_build": None,      # 一次性建设投入：人力 + 采购 + 集成 + 数据治理
    "C_run": None,        # 年度经常性支出：订阅、算力、维护人力

    # B 组：必须来自本项目灰度期实测，不能用厂商宣传值
    "r": None,            # AI 实际覆盖比例：灰度期里 AI 独立处理完的条数 / 同期进入的条数
    "t_after": None,      # 覆盖部分剩余的人工工时：复核 + 例外处理，通常不为 0
    "e": None,            # 误判返工率：需要人推翻并重做的比例
    "t_rework": None,     # 单次返工工时：一般大于 t_before，返工比原本做一遍更费事
    "C_token": None,      # 单条模型调用成本：灰度期账单 / 同期处理条数

    # C 组：估算项，允许留 0，但填了就要说清依据
    "L_avoid": 0.0,       # 年避免损失期望：只在损失可直接计价时填（如反欺诈实际拦截金额），否则 0

    # D 组：兑现系数。省下的工时里，真正变成财务数字的比例
    "k_headcount": 0.0,   # 转为编制削减或编制冻结的比例，需要 HR 出具编制变更才可大于 0
    "k_shift": 0.0,       # 转为高价值工作的比例，财务口径通常记 0，只在业务价值叙述里出现
}


def compute(v):
    missing = sorted(k for k, x in v.items() if x is None)
    if missing:
        raise SystemExit("以下输入必须先填本组织的实测值，脚本不替你估：%s" % ", ".join(missing))
    realization = v["k_headcount"] + v["k_shift"]
    if not 0.0 <= realization <= 1.0:
        raise SystemExit("兑现系数之和必须落在 0 到 1 之间，当前 %.2f" % realization)

    covered = v["A"] * v["r"]                                     # 年内被 AI 覆盖的条数
    per_case_saved = v["t_before"] - v["t_after"] - v["e"] * v["t_rework"]
    saved_hours = covered * per_case_saved                        # 年节省工时
    fte = saved_hours / v["H"]                                    # 折成几个人
    gross = saved_hours * v["C_h"]                                # 毛节省金额
    realized = gross * realization                                # 真正能进财务口径的部分
    ai_cost = v["C_run"] + covered * v["C_token"]                 # 年度 AI 成本
    net = realized + v["L_avoid"] - ai_cost                       # 年净收益
    return {
        "covered_cases": covered,
        "per_case_saved_hours": per_case_saved,
        "saved_hours": saved_hours,
        "saved_fte": fte,
        "gross_saving": gross,
        "realized_saving": realized,
        "ai_cost": ai_cost,
        "net_benefit": net,
        "payback_years": v["C_build"] / net if net > 0 else None,
        "roi_year1": (net - v["C_build"]) / v["C_build"] if v["C_build"] else None,
    }


def report(v, out):
    print("年覆盖量 %.0f 条，单条净省 %.3f 小时" % (out["covered_cases"], out["per_case_saved_hours"]))
    print("年节省工时 %.0f 小时 = %.2f 个 FTE（按 H=%s 的年有效工时折算）"
          % (out["saved_hours"], out["saved_fte"], v["H"]))
    print("毛节省 %.0f，兑现系数 %.2f，计入财务的节省 %.0f"
          % (out["gross_saving"], v["k_headcount"] + v["k_shift"], out["realized_saving"]))
    print("年 AI 成本 %.0f，年净收益 %.0f" % (out["ai_cost"], out["net_benefit"]))
    if out["payback_years"] is None:
        print("年净收益不为正，回收期不成立。别再往下算 ROI，回去看覆盖率与单条成本")
        return
    print("回收期 %.2f 年，首年 ROI %.1f%%" % (out["payback_years"], out["roi_year1"] * 100))
    if out["per_case_saved_hours"] <= 0:
        print("警告：单条净省为负，复核与返工吃掉了全部收益，这个场景现在不该扩量")
    if v["k_headcount"] == 0:
        print("提醒：k_headcount 为 0，这份测算没有任何编制口径的兑现，")
        print("      CFO 追问“省下的人去哪了”时，只能拿高价值工作的产出来答，先把那份产出证据备好")


def main():
    out = compute(INPUTS)
    report(INPUTS, out)


if __name__ == "__main__":
    main()
```

这套测算最常被质疑的地方在 `k_hc` 与 `k_shift` 这两个系数上。 省下 15000 小时听起来很多，折成 9.4 个 FTE 也很具体，但下一句必然是"这 9.4 个人现在在哪"。编制没减、也说不清他们转去做的事产出了什么，那这 9.4 个 FTE 就只是一个工时口径的数字，进不了财务报表。把兑现系数默认设成 0，是让这张表在没人回答这个问题之前算不出正的 ROI——净收益会直接等于负的 AI 成本。这个默认值看着苛刻，它只是把质疑提前到了自己人面前。

想让系数大于 0，得拿出对应的东西：`k_hc` 大于 0 需要 HR 出具的编制变更或冻结记录；`k_shift` 大于 0 需要说清省下的工时转去做了什么、那件事的产出怎么衡量。多数组织在财务口径下把 `k_shift` 记 0，只在业务价值叙述里提它。这样处理可以，但两套口径要分开写，别在同一页材料上把工时口径的收益和财务口径的 ROI 加到一起。

三个设计选择是有代价的。

其一，`e × t_rework` 把误判返工从收益里扣掉，且 `t_rework` 通常大于 `t_before`。 返工比第一次做更费事——要先看懂 AI 做了什么，再推翻重来。代价是覆盖率一高、误判率没压下来时，单条净省会变成负数，测算直接给出"这个场景现在不该扩量"。有人会因为这个结论难看而把 `t_rework` 填成和 `t_before` 一样，那等于假设返工不额外花钱。

其二，`H` 取年有效工时，不取法定工时。 一个人一年的法定工时里，能真正投到这类工单上的通常少得多。分母取小，折出来的 FTE 就更大，这个数字必须由 HR 给，不能由项目组估——它直接决定"省了几个人"这句话的可信度。

其三，`L_avoid` 默认 0。 只有反欺诈这类损失可直接计价的场景才该填它。填一个估算的"避免损失"，整张表就退回到"你怎么知道没 AI 就一定会被攻击"那个答不上来的问题上，前面所有工时口径的扎实计算会被这一个数字一起拖下水。

最容易改错的三处。

第一，`r` 最容易用厂商宣传值或 PoC 值填。 PoC 的数据是筛过的，覆盖率天然偏高。这个数必须来自灰度期真实流量的实测，而且要用同一套"算作 AI 独立处理完"的定义。定义松一格，ROI 能翻倍。

第二，`t_after` 经常被填成 0。 AI 处理完还要人复核、还有例外要走人工，这部分工时不会消失。填 0 会让单条净省等于 `t_before`，这是这张表最常见的高估来源。

第三，`C_token` 要用灰度期账单除以处理条数，包含失败重试与被丢弃的调用。 只算成功调用的 token 会系统性低估——失败重试是成本失控时增长最快的那一部分。这个口径要与 17.9.8 指标配置里的 `cost_per_case_usd` 对齐，两边不一致时，月报和立项材料会给出互相打架的数字。

## 17.9.5 两条落地路径：中小团队 vs 大厂

同样一套方法论，落到不同规模的组织里是两种活法。照抄大厂的建设路径，是中小团队最常见的自杀式操作；反过来，大厂套用中小团队的做法又会浪费规模优势。下面把两条路径讲清。

### 路径 A：中小团队（安全团队 < 20 人，无专职 AI 工程团队）

核心原则：能买就买，能用云就用云，绝不自建平台。 你的稀缺资源是人，不是钱能解决的算力。

- 自主等级目标：踏实做到 L2，选一两个点尝试 L3。不碰自建 L4。
- build/buy/hybrid：重度偏 buy。用商用安全产品内置的 AI 能力、云厂商托管的检测服务、成熟 SaaS。要自建的部分也用托管 API + 开源 agent 框架，别自己训模型、别自建平台。
- 场景：1–2 个高 ROI、数据友好的场景（告警降噪、漏洞排序），做深做透，别铺开。
- 成本量级：年度预算 < 500 万。主要花在 SaaS 订阅、云服务和少量集成人力上。
- 组织能力要求：不需要数据科学家。需要 1–2 个"懂 AI 的安全人"——会看模型和 agent 的输出、会判断结果靠不靠谱、会做集成，能当业务和工具之间的翻译（培养路径见 17.9.7）。
- 别做的事：别建数据湖、别自建 MLOps、别招纯数据科学家、别一上来就投几百万建平台。这些是大厂的活，落到你这里就是拖垮项目的沉没成本。

> 一句话：中小团队的胜负手是"把两个买来的能力用到位"，不是"造一套自己的平台"。

### 路径 B：大厂 / 大型安全团队（安全团队数十人以上，有 AI 工程能力）

核心原则：先做场景验证价值，再从场景里长出平台，最后规模化。 平台是"长出来"的，不是"设计出来"的。

- 自主等级目标：主力场景推到 L4，用严格的分级 gating 和成本分层支撑（见 17.2.7、17.2.8）。
- build/buy/hybrid：hybrid。底座（大模型、agent 运行时、可观测性、MCP 工具层）用成熟方案，业务逻辑、评估体系、成本闸门自建——这些是你的差异化，也是买不来的。
- 分阶段路径：

  - 阶段 1（0–6 个月）场景驱动：独立做告警降噪、漏洞排序、反欺诈几个场景，各自单独验证价值、积累经验。先别抽象平台。
  - 阶段 2（6–12 个月）抽象共性：发现这些场景都要数据接入、评估回归、成本分层、可观测性，把共性提炼成平台核心组件，场景特定逻辑仍留在场景侧。
  - 阶段 3（12–18 个月）规模化：扩到 10+ 场景、跨业务线复制，建立 AI Security 能力中心（COE），沉淀组织能力。

- 成本量级：成长阶段年度 500–2000 万（MVP 平台 + 5 场景 + 5–8 人团队）；成熟阶段 > 2000 万（平台化运营 + 10+ 场景 + COE）。
- 组织能力要求：需要一支混编团队——从安全团队培养的"AI 混血儿"当稳定核心，外加少量高薪数据科学家攻坚，配合外部合作补前沿能力（见 17.9.7）。还需要成建制的 LLMOps / 评估 / on-call 能力。

> 大厂的两个专属陷阱：
> - 闭门造平台：技术团队照着业界最佳实践设计出"技术上完美"的平台，从没请 SOC/AppSec/GRC 参与评审，上线后没人用。破法——每 2 周一次业务评审会，让业务真正"摸到"平台，连续两次反馈"用不了"就停下重设计。
> - 追求大而全：每个团队的需求都答应支持，结果每个功能只做了 60%，谁都觉得不够用。破法——MVP 优先，第一期只做 3 个核心场景，功能深度压过广度。

### 两条路径的选择判据

不确定自己在哪条路上，用这张表对照：

| 判据 | 走路径 A（中小） | 走路径 B（大厂） |
|------|----------------|----------------|
| 安全团队规模 | < 20 人 | 数十人以上 |
| 有无专职 AI 工程团队 | 无 | 有 |
| 数据基础 | 分散、治理弱 | 有数据湖或成熟采集 |
| 年度预算 | < 500 万 | > 500 万 |
| 场景独特性 | 通用场景为主 | 有自研业务的独特场景 |
| 合规对数据出域的限制 | 可接受云托管 | 部分数据不能出域，需自建 |

最忌讳的是错配：中小团队走了路径 B（建平台建到没钱没人），或大厂困在路径 A（放着规模优势不用，样样外购受制于人）。先诚实评估自己的规模与能力，再选路径。

## 17.9.6 风险清单：幻觉、对抗、成本、合规

把 AI 尤其是 L4 智能体放进安全运营，会引入四类新风险。它们不是不能上 agent 的理由，而是上之前必须想清楚的代价。

### 幻觉：模型会编造证据

大模型会生成看似合理、实则错误的内容。在安全场景，这意味着 agent 可能凭空捏造一条不存在的攻击链，或把真实威胁判为误报。分析师若盲信 agent 结论，轻则误判，重则漏掉真实攻击。

- 应对：所有结论必须可溯源到原始证据（日志、遥测、情报），agent 的每一步推理都要能回放（可观测性见 17.2.8）；高价值、不可逆的动作前保留人在回路 gate（17.2.8 的分级 gating）；把 agent 定位成"给分析师备齐材料并给出研判建议"，而不是"替分析师定案"。

### 对抗：攻击者会操纵你的 AI

一旦 AI 进入决策链，它本身就成了攻击面。攻击者可以投毒训练数据让模型学偏，可以构造对抗样本绕过检测，更危险的是——对 L4 agent 发起提示注入：在日志、告警、工单里埋入恶意指令，诱导 agent 执行危险工具调用或泄露数据。

- 应对：这类攻防的防御深度属于第18章（提示注入、工具滥用、供应链、MCP 信任边界的防御设计）。本节只强调一件事——落地 L4 agent 时，它消费的安全控制（权限最小化、工具沙箱、审计、成本闸门）是硬性前置条件，具体见 17.2.9 并交叉引用第18章。没有这些控制，别把 agent 接到真实生产工具上。

### 成本：token 账单容易失控

前面反复提到：L4 agent 的多步工具调用把推理成本放大了一个数量级。没有成本闸门，一次异常的告警风暴或一个陷入死循环的 agent，就能烧掉一大笔预算。

- 应对：成本分层——便宜的 ML/规则先过滤，贵的 agent 只研判高价值告警（17.2.7）；给每个 agent 设 token 与步数上限，超限即降级到规则或转人工；把 token 消耗纳入日常监控指标，异常即告警。

### 合规：数据出域与自动化决策的边界

用 AI 处理安全数据，会碰上两类合规约束。一是数据出域——把日志、遥测送到外部大模型 API，可能违反数据本地化或隐私法规，这也直接影响你能选 buy 还是必须 build。二是自动化决策的可解释性——某些监管场景要求安全决策可追溯、可解释，纯黑箱的 agent 判断可能不被接受。

- 应对：数据敏感的场景优先私有化部署或本地模型，不能出域的数据别走公有云 API；保留完整审计轨迹让每个自动化决策可回溯（呼应上面的幻觉与可观测性要求）；把合规团队在设计阶段就拉进来，别等上线后返工。GRC 侧 AI 能力的演进判断见 17.5，具体嵌入合规工作流的做法留在对应域章。

## 17.9.7 人才：最难补的一块短板

技术选错了可以推倒重来，数据薄弱可以花几个月补，但核心 AI 工程师离职带走的知识资产很难快速弥补。AI 安全团队招人难、留人更难，项目常因核心成员离职而停滞。

为什么留不住纯数据科学家：企业安全场景对他们缺乏吸引力——用的是传统算法（XGBoost / Isolation Forest / LSTM）而非前沿模型、数据规模小、QPS 低、不能发论文；职业天花板也低，安全部门通常不是核心业务，升职加薪比不过业务线；成就感更差——业务线 AI 工程师"让 GMV 涨 5% 被 CEO 表扬"，安全 AI 工程师"拦了 300 个攻击"换来一句"哦，知道了"。

更可持续的答案：从安全团队内部培养"懂 AI 的安全人"。 别指望纯数据科学家做好 AI 安全。一条 6 个月的培养路径：

1. 第 1–2 月，AI/ML 基础：在线课程 + 企业内部 Python / Pandas / Scikit-learn 实战。
2. 第 3–4 月，场景实战：跟数据科学家做一个项目（告警降噪），学特征工程、训练、评估。
3. 第 5–6 月，独立带小项目：漏洞优先级排序（相对简单），有 mentor，但主要靠自己。

6 个月后，这个人既懂安全业务、又能看懂模型和 agent 的输出，能当数据科学家和 SOC 之间的翻译，而且比空降的数据科学家稳定得多。

如果必须招数据科学家，给技术成就感：每季度留一周自由探索、允许脱敏后发论文和开源、提供 Principal 这样不转管理也能走的技术路径。

并接受人才流动是常态。别把项目成败押在一两个大牛身上。合理的结构：核心团队是内部培养的混血儿（稳定、懂业务、长期主义），外部专家高薪招来做技术攻坚并负责把知识转移到内部，外部合作（咨询公司、高校）在 PoC 阶段补位但要求"知识转移"到自己团队。目标是建立一套"人走了、项目还能继续"的体系。

## 17.9.8 运行指标与持续监控

上线不是终点。AI 安全项目要持续监控以下指标，确保价值兑现、退化及时被发现。

业务指标（每日看）：MTTD（平均检测时间，目标 < 1 小时）、MTTR（平均响应时间，目标 < 4 小时）、告警降噪率（目标 > 80%）、自动化响应率（目标 > 60%）。

这四个数的口径是**全量告警管道、不分严重级、取中位数**（MTTR 含人工审批等待时长，见下面配置里的定义），量的是这条 AI 管道整体跑得怎么样。它们和 [18.7.5](../第18章_AI系统安全/18.7_AI安全运营.md) 那组按 P1–P4 分级的时钟不是同一件事：那边量的是单起 AI 系统安全事件从检测到遏制的时限（P1 的 MTTD ≤5min、MTTR ≤15min），分母是事件不是告警。同名指标在两处差一个量级，源头是口径不同而非结论打架；引用任何一个数时把"哪一档、分母是什么"一并带出，否则一张汇报表里会同时出现 4 小时和 15 分钟两个 MTTR。

模型 / agent 指标（每周看）：Precision（> 85%）、Recall（> 80%）、F1（> 0.82）。延迟这一项必须分层看，一个阈值套不住两类系统：L1 分类器是一次树模型推理，量纲是毫秒，P99 < 100ms 是合理要求；L4 agent 一次调查要走多次工具往返加多次模型调用，17.2.7 给它的墙钟预算是 p95 180 秒、17.3 的编排里写死 `max_wall_clock_seconds: 180`，两者差三个数量级。拿 100ms 去卡 agent，等于宣布一个按设计工作的 agent 不合格。对 L4 agent 看四项：任务成功率、轨迹质量、p95 墙钟时长（与编排里的预算同口径）、单条告警的 token 消耗与步数——这几项才是 agent 是否稳定的真实信号。

成本指标（每月复盘）：GPU 利用率（60–80% 为宜）、存储成本、人力成本，以及 agent 的 token 账单——它是 agentic 时代新增的、必须单独盯的一项。

任一指标越过阈值即触发告警，必要时调整模型或回滚版本。尤其记住 17.9.3 的那条红线：底座模型每次升级，都要在黄金集上跑回归，防止行为漂移导致的静默退化。这套"持续跟上"的机制，17.10 会展开成可操作的季度回归与升级 checklist。

### 指标定义与采集配置

上面这些指标要真能被采集，先得把口径写死。同一个"告警降噪率"，分子取"自动关闭数"还是"未进入人工队列数"，算出来能差十几个点；同一个 MTTR，含不含人工审批等待时长，是两条完全不同的曲线。下面这份配置把每个指标的计算口径、数据来源、采集频率、异常阈值固定下来，阈值一栏全部要按本组织的基线重标。

```yaml
# aisecops_metrics.yaml —— AISecOps 运行指标的口径、来源、频率与阈值
# 阈值全部要按本组织的基线重标。这份文件确定的是"哪些指标必须有阈值"，
# 不是"阈值该定多少"——后者没有跨组织通用的答案。
version: 2
scope: ai-security-program

defaults:
  baseline_window_days: 30       # 阈值以 30 天滚动基线为参照；绝对值阈值只用于硬约束
  on_missing_data: alert         # 指标断流按告警处理，不按"本期无异常"处理
  owner_required: true
  exclude_periods: [drill, load_test, degraded_mode]   # 演练、压测、降级期一律排除

collection:
  pipeline: metrics-collector
  timezone: Asia/Shanghai        # 必须与 SIEM 一致，不一致会让日指标每天错一个窗口
  schedules:
    daily: "0 2 * * *"           # 取前一自然日整日，避免跨日切分把一条事件算进两期
    weekly: "0 3 * * 1"
    monthly: "0 4 1 * *"
    on_model_change: event       # 底座模型或 prompt 变更时立即触发一轮，不等下一个周期
  late_arrival_grace_hours: 6    # 迟到数据的补算窗口，超过就把该期标为缺数
  recompute_on_late_data: true
  store: internal://metrics/aisecops
  retention_days: 730

metrics:
  - id: alert_noise_reduction
    name: 告警降噪率
    layer: business
    definition: "1 - 需人工查看的告警数 / 同期进入管道的原始告警数"
    numerator: soc.triage_queue.entered_human_review
    denominator: siem.alerts.ingested
    unit: ratio
    frequency: daily
    owner: soc-lead
    thresholds:
      warn: {below_baseline_pct: 15}
      page: {below_baseline_pct: 30}
    note: 降级期的告警不计入，否则降级会被记成降噪

  - id: human_override_rate
    name: 人工推翻率
    layer: business
    definition: "分析师最终处置与 AI 建议不一致的条数 / AI 出过建议的条数"
    numerator: soc.cases.disposition_ne_ai_recommendation
    denominator: soc.cases.with_ai_recommendation
    unit: ratio
    frequency: daily
    owner: soc-lead
    thresholds:
      warn: {above_baseline_pct: 30}
      page: {absolute_above: 0.5}
      warn_low: {absolute_below: 0.02}
    note: 这项指标两头都要盯。突然升高说明模型变了或数据变了；长期低到接近 0 更可疑，通常是分析师已经不看了，直接照抄建议

  - id: mttd_hours
    name: 平均检测时间
    layer: business
    definition: "确认为真实事件的告警，从最早证据时间戳到告警产生的小时数中位数"
    source: soc.incidents.confirmed
    aggregation: median          # 用中位数，一两起陈年事件会把均值拉到没法看
    unit: hours
    frequency: weekly
    owner: soc-lead
    thresholds:
      warn: {above_baseline_pct: 25}

  - id: mttr_hours
    name: 平均响应时间
    layer: business
    definition: "从告警产生到处置动作完成的小时数中位数，含人工审批等待时长"
    source: soc.incidents.confirmed
    aggregation: median
    unit: hours
    frequency: weekly
    owner: soc-lead
    thresholds:
      warn: {above_baseline_pct: 25}
    note: 审批等待时长必须计入。把它排除掉，会让"人在回路"的真实代价从指标里消失

  - id: agent_task_success_rate
    name: 黄金集任务成功率
    layer: agent
    definition: "评测跑批中结论与标准答案一致的样例数 / 套件样例总数"
    source: evals.report.metrics.verdict_accuracy
    unit: ratio
    frequency: weekly
    also_on: [model_change, prompt_change, tool_schema_change]
    owner: detection-eng
    thresholds:
      page: {below_absolute: 0.85}
      warn: {below_baseline_absolute: 0.03}

  - id: agent_trajectory_score
    name: 轨迹质量分
    layer: agent
    definition: "评测跑批的轨迹综合分，由各套件 scorer 产出"
    source: evals.report.metrics.trajectory_score
    unit: score_0_1
    frequency: weekly
    also_on: [model_change, prompt_change, tool_schema_change]
    owner: detection-eng
    thresholds:
      page: {below_absolute: 0.80}
      warn: {below_baseline_absolute: 0.05}

  - id: agent_tool_calls_p95
    name: 单次调查工具调用数 P95
    layer: agent
    definition: "生产环境每次 agent 调查的工具调用次数的 P95"
    source: agent.runs.tool_call_count
    unit: count
    frequency: weekly
    owner: detection-eng
    thresholds:
      warn: {drift_from_baseline_pct: 25}
    note: 这是最早暴露行为漂移的一项。成绩没掉但步数变了，说明 agent 已经换了一种做法

  - id: redline_attempt_count
    name: 红线动作尝试次数
    layer: agent
    definition: "agent 尝试调用需审批或禁止工具的次数，被编排层拦下的也计入"
    source: agent.gate.denied_and_attempted
    unit: count
    frequency: daily
    owner: detection-eng
    thresholds:
      page: {absolute_above: 0}
    note: 阈值为 0。拦住了不等于没打算干，任何一次尝试都要有人看一眼

  - id: golden_suite_age_days
    name: 黄金集距上次回归的天数
    layer: governance
    definition: "当前生产版本 agent 距最近一次完整评测跑批的自然日数"
    source: evals.runs.latest.started_at
    unit: days
    frequency: daily
    owner: detection-eng
    thresholds:
      warn: {absolute_above: 30}
      page: {absolute_above: 45}
    note: 这项不是效果指标，是"有没有在做评估"的指标。它一超标，上面所有 agent 指标的可信度都要打折

  - id: cost_per_case_usd
    name: 单条事件的模型成本
    layer: cost
    definition: "计费周期内 AI 管道的模型调用费用 / 同期经 AI 处理的事件数"
    numerator: billing.llm.spend
    denominator: agent.runs.completed
    unit: currency
    frequency: monthly
    also_on: [daily_budget_burn_alert]
    owner: security-eng-manager
    thresholds:
      warn: {above_baseline_pct: 30}
      page: {daily_budget_burn_pct_above: 150}
    note: 日内还要单独盯预算燃烧速度。一个陷入循环的 agent 能在月度指标出来之前把预算烧完

  - id: fte_hours_saved
    name: 折算节省工时
    layer: cost
    definition: "覆盖量 × 单条净省工时，口径与 ROI 测算脚本一致"
    source: derived.roi.saved_hours
    unit: hours
    frequency: monthly
    owner: security-eng-manager
    thresholds:
      warn: {below_plan_pct: 30}
    note: 与 ROI 测算共用一套口径。两边算法不一致时，月报和立项材料会给出两个互相打架的数字

review:
  daily: [alert_noise_reduction, human_override_rate, redline_attempt_count, golden_suite_age_days]
  weekly: [mttd_hours, mttr_hours, agent_task_success_rate, agent_trajectory_score, agent_tool_calls_p95]
  monthly: [cost_per_case_usd, fte_hours_saved]
  on_model_change: [agent_task_success_rate, agent_trajectory_score, agent_tool_calls_p95,
                    human_override_rate, redline_attempt_count]
  escalation:
    page_target: security-oncall
    warn_target: aisecops-weekly-review
    unacked_page_minutes: 30
```

三个设计选择是有代价的。

其一，`human_override_rate` 两头都设了阈值。 它高的时候和低的时候都要报警：高说明模型或数据变了；低到接近 0 通常说明分析师已经不看建议了，直接照抄。代价是刚上线的头两个月它会频繁触发，那时基线还没稳，每次触发都要人判断是不是真信号——这段人力要提前排进去，否则它会先被静音，然后被忘掉。

其二，`golden_suite_age_days` 是"有没有在做评估"的指标，不反映当天的运行效果。 把它放进日看清单，代价是每天要面对一个和当天状况无关的数字；不放，评估回归会在忙起来的那几周悄悄停掉，而上面四项 agent 指标的可信度全建在它上面。

其三，`exclude_periods` 把演练、压测、降级期排除在外。 代价是排除逻辑本身要维护：降级期的起止必须由系统自动打标，靠人事后补标一定会漏，而漏标的方向永远是让指标更好看——没人会主动去补一段让自己数字变难看的排除区间。

最容易改错的三处。

第一，`timezone` 与 SIEM 不一致。 日指标的窗口会整体偏移几个小时，表现是每天的数字都"差不多对"，只在跨日事件多的那几天明显失真，很难被发现。这一项要和每个数据源逐个核对，不能只在采集器里设一次就算数。

第二，`redline_attempt_count` 的阈值是 0，且口径包含被编排层拦下的尝试。 有人会把被拦下的排除掉，理由是"防御生效了"。排除之后这项指标永远是 0，而它本来是唯一能发现"模型升级后 agent 开始试探处置动作"的信号。这一条与 17.3 打分脚本的红线计数口径一致，两边不要各改各的。

第三，`cost_per_case_usd` 的分母是经 AI 处理的事件数，不是全部事件数。 用全部事件数当分母，成本分层做得越狠（贵的 agent 只看少数告警），单位成本看起来越低，而 agent 的单次成本一分没降。这个口径要与 17.9.4 测算表里的 `C_token` 对齐。

## 17.9.9 避坑总纲：完美主义陷阱与最小可行起步

最后收一个总纲。常见的完美主义陷阱：

- "等数据准备好了再启动" → 两年过去了，数据还没好。
- "等招到 5 个数据科学家再启动" → 一年过去了，只招到 1 个，还离职了。
- "等平台建好了再做场景" → 平台建了 14 个月，没人用。

务实的做法：

1. 从小做起：先做一个最简单的场景（告警降噪），3 个月见效。
2. 快速迭代：别等所有条件齐了，边做边优化。
3. 容忍失败：部分项目会失败，但失败也能积累经验。
4. 分阶段投入：别一上来就投两千万建平台，先投两百万做 PoC。

能落地的"80 分方案"胜过纸面上的"100 分方案"。今天做出来的"不完美产品"，胜过明年才能交付的"完美产品"。

五大障碍里，数据和人才最常被低估。规避它们不需要天才，需要的是立项前肯花两周认真做数据健康检查，以及承认"我们目前的数据和人才还撑不起这个目标"的勇气。从能做的开始做，比从想做的开始更容易成功。

## 行业趋势与投资参考

这一节的数字全部是二手的，且都有各自的截止时点。放它们在这里只有一个用途：在立项讨论里判断量级——"AI 安全工具市场是在涨还是在缩""头部企业的投入是亿级还是十亿级"。它们不能进你的测算。

这条限制不是客套。 17.9.7 那张 ROI 表刻意不含任何行业基准数字，理由在那一节已经写明：测算里掺进一个外部数字，整张表在 CFO 那里就只值那一个数字的可信度——他会问"这个 258 天是哪个行业、哪个规模、哪年的样本，和我们可比吗"，而这个问题你答不上来，因为报告的样本构成你没有。所以下面的数字与那张表之间有一道硬边界：`t_before`、`r`、`C_h` 这些输入项只能来自本组织实测，一项也不许用行业均值代填。

同样的理由，这里不给"各场景的效果基准"表。 那类表通常长成"威胁检测 MTTD 缩短 30–50%""告警降噪 70–85%"，再配一栏头部企业实践。它有两层问题。一是那些区间没有可核的样本构成，读者会把它当成验收目标写进立项材料；二是这类表最常见的凑数方式，是把量纲根本不同的数字并排——比如拿某家公司混沌工程的故障减少幅度去对标 AI 威胁检测的 MTTD 缩短：混沌工程量的是系统在注入故障下的韧性，MTTD 量的是发现攻击的时延，分子分母都不是一回事，并排放进一张表只会让读者以为它们可比。要基准，可信的来源只有一个：你自己影子模式那两周跑出来的数。

### 效果基准从哪里来

不同行业对 AI 安全投资的容忍度不同：金融、电商因欺诈损失直接可量化，ROI 更易证明；制造、传统企业需更多时间建立业务案例。但无论哪个行业，效果基准都只有一个可靠来源——本组织灰度期的实测。可操作的做法是把 17.9.3 灰度发布里那两周影子模式当成基准标定期：AI 与现有流程并行跑，只记日志不影响决策，两周结束时你手上就有了 `t_before` 与 `t_after` 的配对样本、覆盖比例 `r` 的实测值、以及单条成本的真实分布。这几个数直接喂进 17.9.7 的 ROI 表，口径自洽、来源可查、CFO 追问时答得上。

拿别人的百分比当目标写进立项材料，代价要到验收那天才付：目标是照着一个不知道样本构成的区间定的，而你的告警结构、数据质量、人员配比与那个样本毫无关系。基准定低了没人信，定高了兑现不了——两种情况都会让下一次要预算变得更难。

> English Title: Coding Agents: Embedding Security into the Development and Business Workflow
> 目标读者: AppSec Engineer, DevSecOps Engineer, Platform Engineer, Detection Engineer, Security Architect

## 本节定位

17.3 讲的是告警侧——一个安全智能体如何对一条可疑登录做多步自主研判。工程侧是另一条落地路径：当编程智能体（Claude Code、OpenAI Codex 一类能读写代码库、调用工具、执行命令的智能体）走进研发流水线，它做的不再是"研判别人的告警"，而是在代码被写下、被提交、被部署的每一个环节上做安全。这是"AI 做安全"的另一种落地形态，和 17.3 互为工程与运营两面。

编程智能体走进研发流水线，有一个很现实的推力：AI 正在大规模地写代码，而 AI 写的代码更容易带漏洞。多份研究给出的方向一致——Veracode 2025 的评测显示，约 45% 的 AI 生成代码样本含 OWASP 级别的安全缺陷；CodeRabbit 的对比数据显示，AI 生成代码的**安全类问题总体**最高可达人工代码的 2.74 倍（该报告没有 XSS 分项，其官方新闻稿另给出"安全漏洞高 1.5–2 倍"的口径，两个数字取自同一份报告的不同切面，引用时须说明是哪一个）。代码的生产速度上去了，缺陷的注入速度也跟着上去了。靠人工评审逐行追这些缺陷已经追不过来，于是一个自然的应对是：既然是 AI 在写，那就让 AI 在同一条流水线上做安全——在 diff 生成的那一刻就扫、在提交的那一刻就拦、在部署前就修。这不是用 agent 替代人，而是把安全动作前移到代码刚成形、修复成本最低的位置。

能用确定性的 lint、SAST 规则、CI 门禁解决的，别请 agent；agent 的价值只在那些需要理解跨文件上下文、做因果推理、生成语义修复的活上。这条判断和 17.3 里"哪些告警不该上 agent"是同一把尺子，只是量的是研发场景。

与相邻章节的分工先在这里交代清楚，后文不再重复：本节讲编程智能体"做安全"的正面用途——它怎么嵌进 PR、CI、IaC、检测规则生成这些环节；而编程智能体自身作为攻击面（提示注入、工具滥用、供应链投毒）的防御深度，归 [第18章 AI 系统安全](../第18章_AI系统安全/README.md)，本节点到即止；安全开发生命周期（SDL）的方法学骨架在 [第6章 应用安全架构](../../第02部分_技术架构与基础设施安全/第06章_应用安全架构/README.md)，本节是把 agent 这类新工具嵌进 SDL 的落地样例；检测规则怎么进入检测运营，见 [11.3 威胁检测工程](../../第04部分_安全运营与防御能力/第11章_安全运营/11.3_威胁检测工程.md)。

## 一、研发流水线上的七个安全挂载点

编程智能体能做安全的地方，是研发流水线上七个具体的挂载点，而非一个模糊的"AI 助手"概念。下面逐个展开，每个都给出一句话方法、真实依据、一句话护栏和交叉引用。这七个挂载点并非都要上；每个今天能做到什么、哪些还只是草稿级、哪些必须留人审，各不相同。

用全章统一的自主等级 L0–L5 作标尺：编程智能体在研发流水线上今天的成熟停靠点集中在 L2–L3，尚不到 17.3 SecOps 旗舰场景的 L4 自主调查，因为改代码库状态的爆炸半径大、人审 gate 不可省。下文给每个关键挂载点标出等级锚点。

证据等级在下文如实标注：有生产部署案例的记为实践级，有学术评测支撑的记为研究级，仅有官方能力文档的记为能力级。这套证据等级与自主等级 L0–L5 是两个正交维度——前者说"有多少实证"，后者说"人机谁做主"。

### 1.1 PR 自动安全门禁

方法：在 CI 里部署一个安全评审 Action，PR 触发时让编程智能体只分析这次改动的 diff，把发现的漏洞以内联评论的形式贴回对应代码行、附上 CWE 编号与 OWASP 分类，被确认（confirmed）的高危发现默认阻断合并，直到修复或人工豁免。

自主等级：L3——agent 自主完成 diff 分析并给出阻断/放行结论，最终合并仍卡在人审门禁上。这是七个挂载点里最成熟的一个，因为它的边界最清晰：只看 diff、只输出评论、只在门禁处拦一道。Anthropic 开源的 claude-code-security-review Action 就是这个形态，agent 读 PR 的改动、做上下文相关的漏洞分析、把结论写成 GitHub 评论。它相对传统 SAST 的差异在于能理解跨文件的调用关系，从而压低"这行看着危险但实际上被上游校验兜住了"这类误报。

> 截至 2026.7 的实例：金融科技公司 Deriv 把这套安全评审接入了 700 多个代码仓库，覆盖每周 100 多个 PR。它的用法值得注意的地方是交互式修复——开发者在 PR 里 `@claude` 呼叫 agent，agent 生成修复建议，但要等开发者审阅、批准后才把改动推上去，agent 不自行落盘。
> 来源：anthropics/claude-code-security-review（GitHub）、Deriv 工程团队公开博客（substack）。

护栏：这个 Action 只对可信来源的 PR 运行。它的官方 README 明确说明未针对提示注入做加固——一个恶意的外部 PR 可以在代码注释或字符串里埋指令，诱导 agent 输出误导性评论或忽略真实漏洞。fork 来的、外部贡献者的 PR 不该无条件触发它。这条护栏的完整防御设计属于第18章。

证据等级：实践级（有 700+ 仓库的生产部署）。

### 1.2 SAST 扫描-修复-复验自动化

方法：把 SAST/SCA 扫描器通过 MCP 接给编程智能体，让它跑一个"扫描 → 分析结果 → 生成最小修复 → 重新扫描验证"的过程；同时在项目根目录的 CLAUDE.md 里把"每次改动前先扫描"声明为默认基线，让扫描成为 agent 的固定动作而非可选步骤。

自主等级：L3——agent 自主跑完扫描、修复、复验的多步链条，但修复补丁是否落盘仍由人审决定。和 PR 门禁只做"发现并拦截"不同，这个挂载点让 agent 往前走一步——不只指出漏洞，还生成修复并自己验证修复是否真的消除了漏洞。Snyk 的 MCP 集成就示范了这条路径：agent 调 Snyk 扫出 SCA（依赖漏洞）和 SAST（代码漏洞）两类问题，针对每个问题生成尽量小的补丁，改完再触发一次扫描确认这个发现从结果里消失了。在 CLAUDE.md 里写死"生成或修改代码后必须扫描"，是让这套动作 secure-by-default 的关键——否则 agent 很容易在赶进度时跳过验证。

一段 CLAUDE.md 里的扫描基线声明，示意如下：

```markdown
## 安全基线（每次代码变更强制执行）
- 修改任何依赖清单（package.json / requirements.txt 等）后，必须运行 SCA 扫描。
- 生成或修改业务代码后，必须运行 SAST 扫描。
- 若扫描报出 High 及以上级别的发现，修复后必须重新扫描，确认该发现已消除，
  再继续下一步；不得在存在未消除 High 发现的情况下提交。
- 修复只做消除该漏洞所必需的最小改动，不顺手重构无关代码。
```

> 上面是示意配置，字段与阈值需按项目实际调整。

护栏：修复必须经重扫验证才算数——agent 生成的补丁可能"看起来对"却没真正堵住漏洞，甚至引入新问题，重扫是把这类情况挡在提交前的最低要求。要注意重扫只验证"该漏洞消失"，不验证"未引入回归"——它确认不了这个补丁有没有破坏别处的行为；需要回归保证时，应升级到 1.5 的独立 Verifier 模式。且无论重扫是否通过，都禁止 agent 无人审直接合并到主干；自动修复降低的是人审的工作量，不是取消人审。

证据等级：能力级（官方文档描述的集成能力，规模化生产数据尚不充分）。

### 1.3 IaC 左移（写时扫描）

方法：用编程智能体的 PostToolUse hook，在每次它编辑 Terraform、Kubernetes 清单一类基础设施代码时，自动触发 Checkov 或 Snyk IaC 扫描；扫出违规就让 hook 返回阻断决策，并把具体发现注入回 agent 的上下文，逼它在当前这一步就把违规改掉，而不是等到 CI 才发现。

自主等级：L3——扫描与阻断由 hook 自动完成、把违规回灌给 agent 令其当场改正，但改动落盘与提交仍在人审门禁之内。这比 PR 门禁又前移了一步——门禁是在提交后拦，写时扫描是在 agent 落盘那一刻拦。Claude Code 的 hooks 机制支持按工具调用匹配触发条件，`PostToolUse` 用 `matcher` 匹配写文件的工具，再由 hook 命令自己判断路径是不是 `.tf`，就能实现"只要碰了 `.tf` 文件就扫一遍"。

一段 hook 配置的示意（放在 `.claude/settings.json`）。真实 schema 里没有"按文件路径过滤"和"按退出码声明阻断"的独立字段：路径过滤要在 hook 命令内部自行判断（读工具输入或脚本内 glob），阻断靠退出码约定（`exit 2` = 阻断并把 stderr 回灌给 agent）或命令输出的 JSON 决策对象：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "python3 .claude/hooks/scan_iac.py"
          }
        ]
      }
    ]
  }
}
```

配套的 `scan_iac.py` 从 stdin 读工具输入、只对 `.tf` 文件跑 Checkov、有违规就 `exit 2` 阻断：

```python
import json, subprocess, sys

data = json.load(sys.stdin)
path = data.get("tool_input", {}).get("file_path", "")
if not path.endswith(".tf"):
    sys.exit(0)  # 非 IaC 文件，放行

result = subprocess.run(
    ["checkov", "-f", path, "--compact", "--quiet"],
    capture_output=True, text=True,
)
if result.returncode != 0:
    print(result.stdout, file=sys.stderr)  # 违规详情回灌给 agent
    sys.exit(2)  # 退出码 2 = 阻断本次工具结果
```

> 真实字段以官方 hooks 文档为准，此处示意的是触发时机（写 IaC 文件时）与阻断约定（退出码 2 回灌上下文），而非逐字段拷贝的配置。这里传达的机制是：改一次 IaC，扫一次，违规就阻断并把发现回灌给 agent，逼它当场改掉。

护栏：hook 脚本本身是执行入口，等同于一段能在本地执行命令的代码，必须纳入 code review，不能让开发者在本地随手改；用 `allowManagedHooksOnly` 一类的管控开关，防止本地 settings 覆盖掉团队统一的安全 hook 配置。一个被悄悄改掉的安全 hook，等于门禁形同虚设。

证据等级：能力级（基于官方 hooks 文档能力，属可组合的工程实践）。

### 1.4 检测即代码：Sigma / KQL 规则生成辅助

方法：把 MITRE ATT&CK 知识库、Sigma 规则库、威胁情报（CTI）报告作为 MCP 工具或上下文接给 agent，让它完成"读 CTI 报告 → 映射到 ATT&CK 技战术 → 起草 Sigma 或 KQL 检测规则"这条链，把检测工程师从"读报告、查手法、手写规则"的重复劳动里解放一部分出来。

自主等级：L2 辅助——agent 只起草规则，语义映射和最终定稿都由检测工程师主导，产出是草稿而非可直接上线的规则。这是编程智能体往安全运营侧的延伸——它生成的不是应用代码，而是检测规则代码。价值在于 CTI 到检测规则之间那段费时的翻译工作：一份威胁报告里描述的攻击手法，要先对到 ATT&CK 的具体技术编号，再落成一条能在 SIEM 里跑的查询，这中间的语义映射正是 LLM 相对擅长的。

> 研究级依据：微软 2026.3 发布的 CTI-REALM 基准专门评测模型把 CTI 映射到 ATT&CK 的能力。结果里 Claude 系模型占据前三名（得分区间约 0.624–0.685）。但同一份基准也给出了明确的限度——在复杂云基础设施相关的场景上，所有模型得分显著下降，意味着这类规则生成离不开人审。
> 来源：微软 CTI-REALM 基准（2026.3）。

护栏：agent 产出的规则只作草稿（draft）。规则进入检测运营前，必须在 CI 里做两道确定性检查——规则语法校验（确保 Sigma/KQL 能被引擎正确解析）和回归测试（用已知样本验证规则该报的报、不该报的不误报）。编程智能体起草的通用能力边界在本节；起草产物进入 Detection-as-Code 流水线后的投毒威胁建模、语义护栏与审批 gate 的具体实现，见 [11.3.6 Detection-as-Code 与 CI/CD 工程实践](../../第04部分_安全运营与防御能力/第11章_安全运营/11.3_威胁检测工程.md)。

证据等级：研究级（有基准评测支撑，且基准本身指出了需人审的边界）。

### 1.5 角色化漏洞处理流水线

方法：把一次漏洞修复拆成四个角色——Planner（定修复计划）、Analyzer（集成 CodeQL 一类工具做定位分析）、Fixer（生成最小补丁）、Verifier（独立验证补丁有效且未引入回归），用编程智能体的多 agent 协作能力（如 Claude Code 的 Agent Teams）把这四个角色拆到相互独立的子 agent 上，各自在隔离的 worktree 里工作，最后汇成一个可供人评审的 PR。

自主等级：L3 偏 L4——多个子 agent 分工完成计划、分析、修复、验证这条较长的自主链条，接近 L4 的多步自主处置，但汇出的 PR 仍必须经人审才能 merge，这道 gate 把它压在 L4 之下。前面几个挂载点用的是单个 agent，这个挂载点动用的是一组分工的 agent。它的价值在于职责分离带来的可靠性——尤其是让 Verifier 独立于 Fixer，避免"谁改的谁验"这种自证清白的结构性缺陷。worktree 隔离则保证一个子 agent 的改动不会污染另一个的工作副本。

> 研究级依据：arXiv 2606.14261 的研究在 25 个真实的 C/C++ CVE 上评测了这类角色化的自动漏洞修复流水线，为"拆角色比单 agent 一把梭更可靠"提供了实证方向。Claude Code Agent Teams 则是把这套角色拆分落地的官方能力载体。
> 来源：arXiv 2606.14261；Claude Code Agent Teams 官方文档。

护栏：三条同时成立才安全——Verifier 必须独立于 Fixer（不能是同一个 agent 既改又验）；产出的 PR 必须经人审才能 merge，不因为有了 Verifier 就省掉人；子 agent 遵循最小权限，做到读写分离（Analyzer 只读，Fixer 才有写权限），一个只负责分析的 agent 不该有改代码的能力。

证据等级：研究级（有真实 CVE 上的评测），落地能力级（Agent Teams 为官方能力）。

### 1.6 secure-by-default 脚手架

方法：在项目初始化时，让编程智能体依据一套安全脚手架模板，直接生成带安全默认值的三样东西——写好安全基线的 CLAUDE.md、用 PreToolUse 阻断危险命令的 settings.json、以及接好 SAST 的 CI 配置。让每个新项目一出生就带着安全护栏，而不是等出了事再补。

这个挂载点解决的是"安全总是最后才想起来"的老问题。与其在项目跑了半年后回头加扫描、加门禁，不如在 `init` 那一刻就把这些默认打进去。Trail of Bits 公开的一批 Claude Skills、以及 Snyk 提出的 "Secure at Inception"（在起点即安全）思路，都提供了这类可复用的脚手架素材。

护栏：脚手架模板必须集中版本管理并经 code review——模板一旦有问题会被复制到每一个新项目，放大效应远超单个项目的配置错误。同时要慎用来源不明的第三方 skills：研究显示社区流通的 skills 里约有 26% 存在安全问题，把一个带毒的第三方 skill 当脚手架，等于在起点就埋雷。第三方 skill 的信任边界与供应链审查，属第18章。

证据等级：能力级（有公开脚手架素材，规模化沉淀仍在早期）。

### 1.7 agent 行为审计

方法：把编程智能体各个 hook 的触发日志——工具调用的类型、参数、以及每次的允许/阻断决策——接进 SIEM，基于几类信号建告警：PreToolUse 的 deny 频率异常升高、出现非预期的 `Read(/proc/*)` 这类敏感读取、出现计划外的 `git push`。让 agent 的行为本身可被观测、可被审计。

前六个挂载点是让 agent 去做安全，这一个是反过来盯住 agent 自己。一个能读写代码、能跑命令的 agent，它的行为就是一条需要被监控的活动流。把它的工具调用日志当作一类安全遥测送进 SIEM，就能像监控一个有权限的服务账号那样监控它。

护栏：给每个 agent 分配独立的 API key，这样审计时能把每一次工具调用追溯到 agent 身份。但身份可溯源不等于意图可判定——判断某一步是否被劫持，要结合行为基线（用量突增、非常规工具序列），单看"是哪个 agent 干的"判不出这一步该不该发生。同时监控用量异常——token 消耗或工具调用频率的突增，往往是 agent 陷入循环或被劫持的第一个可见信号。还有一个前提：这套审计遥测的可信，以 hook 配置不被本地篡改为前提（见 1.3 的 `allowManagedHooksOnly`）——否则一个被劫持的 agent 可以同时关掉自己的审计。

证据等级：能力级（基于 hook 日志可观测性的工程组合）。

## 二、Codex 侧：另一条产品路线

上面七个挂载点大多以 Claude Code 为载体展开，但编程智能体做安全不是单一产品的事。OpenAI 的 Codex 侧走的是一条侧重点不同的路线，值得并置来看，因为它对"agent 该不该自动改代码"给出了一个更保守的答案。

> 截至 2026.7 的实例：OpenAI 在 2026.3 发布了 Codex Security 研究预览。公开数据里，它在 30 天内扫描了约 120 万次 commit，报出约 792 个 Critical、10561 个 High 级别的发现；它用一个沙箱验证环节复现漏洞来降噪。**流传的"降噪 84%"要按原文口径读**：OpenAI 说的是同一个仓库被反复扫描时精度会随迭代提升，其中**某一个仓库**相比首次上线降噪约 84%——这是单例随时间的改善，不是沙箱验证环节的通用降噪率，也不能外推到你的仓库第一次扫描时。最关键的一点是它的产品选择——Codex Security 生成最小补丁，但不自动改代码，所有修复都必须经人审。2026.5 的 Daybreak 企业安全计划是这条路线的延续。
> 来源：openai.com/index/codex-security；developers.openai.com/codex/security。

Codex 这条路线和前面 Claude Code 侧的挂载点，共同印证了一个判断：编程智能体在安全场景里的成熟形态，是"发现 + 生成修复建议 + 沙箱验证降噪"，而把"是否落盘"这个改变代码库状态的决定留给人。Deriv 的交互式修复要开发者批准才推送、Codex Security 明确不自动改代码，是同一个设计取向的两个表达。这和 17.3 里安全 agent 把改变生产状态的动作留在人审 gate 后面，是完全一致的逻辑——只不过那里的"生产状态"是账号和会话，这里的"生产状态"是代码库。

## 三、护栏总纲：编程智能体的能力边界

前面每个挂载点都带了自己的一句话护栏。这一节把散落的护栏收口成一套总纲，因为编程智能体接触的是真实代码库、真实凭据、真实部署管道，它的爆炸半径比一个只读研判的告警 agent 大得多。

### 3.1 Agents Rule of Two：不可同时满足的三件事

微软提出的 "Agents Rule of Two" 给了一条简洁的能力边界规则：一个 agent 在同一个上下文里，不应同时具备下面三种能力——处理不可信输入、访问敏感密钥或系统、执行对外的写操作。三者齐备就构成一条完整的攻击链：不可信输入可以携带恶意指令，敏感访问提供了值钱的目标，对外写操作则给了把数据带出去或造成破坏的出口。

需要说清楚的是："任具其二"并不等于自动安全。它意味着必须为满足的那两项配上补偿控制——人审 gate 或沙箱隔离。Rule of Two 划的是"何时必须上人工监督"的红线，不是"集齐三个才危险"的开关；缺一项只是把风险从"结构性必然"降到"需靠补偿控制兜住"，而不是解除。

把这条规则套到本节的挂载点上就很具体：一个分析外部 PR（不可信输入）的安全评审 agent，就不该同时握有生产密钥（敏感访问）和自动 push 的权限（对外写）——这正是 1.1 里"只对可信 PR 运行"和 Deriv"要开发者批准才推送"两条护栏背后的道理。

### 3.2 最小权限与沙箱：把边界写成一份配置

给 agent 的权限按它当下的角色收到最小。最直接的做法是读写 token 分离——做分析、做扫描的 agent 只给读权限，只有明确负责修复的 agent 才给写权限（呼应 1.5 的 Analyzer 只读、Fixer 才可写）。在 CI 环境里，禁用 `--dangerously-bypass-approvals-and-sandbox` 这类一键绕过审批与沙箱的开关——它的存在是为了本地调试方便，出现在 CI 配置里就是把所有护栏一次性关掉。

原则讲到这里就该落成配置，否则"最小"是多小，每个团队会各自解释一遍。下面这份按角色 profile 组织：一次任务里 agent 处在哪个角色，就只拿那个角色的仓库范围、落盘路径、出网白名单与凭据。

先说清这条边界该怎么定，因为它两头都有代价。 收得太紧，agent 就没用——一个连仓库都挂载不上、扫出问题也没法改一行的 agent，开发者用两次就绕开它，回到手工流程，安全动作没有前移，只多了一个没人用的工具。放得太松，它就是一条通往生产的新路径——一个能读 CI secret、能推保护分支、能改流水线配置的 agent，等于给攻击者提供了一个不用登录、不受条件访问策略约束、还会被诱导的管理员。这两侧不是同一个量纲上的取舍：前者的代价是收益归零，后者的代价是多了一条谁都没在监控的写入通道。

**定这条线的判据是"这一步要改什么"，不是"这个 agent 有多可信"。** 具体到三条：第一，权限按角色而非按 agent 授予，同一个 agent 在评审阶段是 `reviewer`（只读、不落盘），进入修复阶段才切到 `fixer`（能写 `src/`、能推分支），两个阶段之间要显式切换而不是一直持有并集。第二，能力按"改完之后离生产还有几步"来收：写工作区（agent 自己承担后果）可以放开，推分支（进入他人视野）要留痕，合入主干与推保护分支（直达生产）一律不给，因为这一步的收益全部可以由人点一下按钮来提供，而代价是把最后一道人审拿掉。第三，凭据按"泄了会怎样"来分：读代码的令牌泄露是信息泄露，部署角色泄露是生产事故，因此后者根本不进 agent 的进程环境，`credentials.never_inject_into_agent_env` 里那几项无论哪个 profile 都拿不到。

```yaml
# coding-agent/permissions.yaml —— 编程智能体的仓库范围、落盘权限、出网与凭据隔离
# 作用域：CI 里跑的编程智能体，以及开发者本地经受管配置启动的编程智能体，共用这一份。
# 边界由三件事共同决定：它能看见哪些仓库、能不能落盘、落盘之后能走到哪一步。
# 三者必须一起收。只收其中一件，得到的是"看得见但改不了"（agent 没用）
# 或"改得了但没人知道"（agent 成了一条绕开评审的写入路径）。
version: 2
owner: appsec-platform
review_cycle_days: 90          # 到期未复审的 profile 自动降级为 reviewer

defaults:
  unlisted_repo: deny          # 未列出的仓库不挂载，没有隐式放行
  unlisted_tool: deny
  network: deny                # 出网默认关，按 profile 逐条开
  shell: deny                  # 默认不给执行 shell，只有 fixer 在沙箱内可开
  max_session_minutes: 60      # 会话上限，防止长跑会话累积权限与上下文

# ── 一、角色 profile：按"这一步要做什么"授予，不按"这个人是谁"授予 ──────
# 一个任务可以串联多个 profile（先 reviewer 后 fixer），但同一时刻只生效一个。
profiles:

  reviewer:                    # 读 diff、出评论，不落盘。1.1 的 PR 安全评审用它
    repos:
      read: [group:product-services, group:internal-tools]
      write: []
    filesystem:
      write_paths: []
      read_denylist:           # 读也要收：读到就可能被带进上下文再被带出去
        - "**/.env"
        - "**/.env.*"
        - "**/*.pem"
        - "**/*.p12"
        - "**/id_rsa*"
        - "infra/secrets/**"
    network:
      egress: allowlist
      allow: [model_api_gateway, package_registry_readonly]
      deny_reason_required: true
    credentials:
      inject: [scm_read_token]         # 只读，且 scope 限定在 repos.read 列出的仓库
      forbid: [ci_secrets, cloud_deploy_role, prod_db_dsn]
    vcs:
      can_commit: false
      can_open_pr: false
      can_push_branch: false

  fixer:                       # 生成补丁、开 PR。1.2 / 1.5 的修复流水线用它
    repos:
      read: [group:product-services]
      write: [group:product-services]
    filesystem:
      write_paths: ["src/**", "tests/**", "docs/**"]   # 先白名单，再在其内部按下面排除
      write_denylist:          # 比 pr-gate.yaml 的 forbidden_paths 更宽，是刻意的：
                               # 这一份在落盘那一刻拦，宁可多拦；那一份在合入前拦，要精确
                               # 到能写进拒绝理由。两份的交集必须一致，删任一份的条目都要
                               # 同时评估另一份
        - ".github/**"
        - ".gitlab-ci.yml"
        - "Jenkinsfile"
        - "**/package-lock.json"
        - "**/poetry.lock"
        - "**/go.sum"
        - "**/Cargo.lock"
        - "infra/**"
        - "**/auth/**"
        - "**/authz/**"
        - "**/*polic*"
        - ".claude/**"         # agent 自己的 hook 与权限配置，不能自己改
      read_denylist:
        - "**/.env"
        - "**/.env.*"
        - "**/*.pem"
        - "infra/secrets/**"
    sandbox:
      isolation: container     # 与开发者工作站、与 CI runner 主机都隔离
      writable_mounts: ["/workspace"]
      readonly_mounts: ["/workspace/.git"]   # 让它读得到历史，改不了历史
      drop_capabilities: all
      no_new_privileges: true
    network:
      egress: allowlist
      allow: [model_api_gateway, package_registry_readonly, sast_service]
      deny: [prod_vpc, staging_vpc, internal_admin_api]
    credentials:
      inject: [scm_write_token_branch_only]  # 只能推分支，不能推 main，不能改保护规则
      forbid: [ci_secrets, cloud_deploy_role, prod_db_dsn, package_publish_token]
      ttl_minutes: 30
      audience_bound: true     # 令牌绑定本次 run_id，换个进程用不了
    vcs:
      can_commit: true
      can_open_pr: true
      can_push_branch: true
      can_push_protected: false
      can_merge: false         # 合入永远由人做，见 pr-gate.yaml
      required_pr_labels: [agent-authored]

  scaffolder:                  # 1.6 的 secure-by-default 脚手架，只在新仓库初始化时启用
    repos:
      read: [group:templates]
      write: [scope:new-repo-only]
    filesystem:
      write_paths: ["**"]      # 新仓库是空的，此处放宽不等价于对存量仓库放宽
      write_denylist: []
    network:
      egress: allowlist
      allow: [model_api_gateway, template_registry]
    credentials:
      inject: [scm_write_token_branch_only]
      forbid: [ci_secrets, cloud_deploy_role, prod_db_dsn]
    vcs:
      can_commit: true
      can_open_pr: true
      can_push_protected: false
      can_merge: false
      required_pr_labels: [agent-authored, scaffold]

# ── 二、凭据隔离：agent 拿到的和流水线拿到的不是同一套 ────────────────────
credentials:
  broker: internal://secrets-broker      # agent 不直接读任何 secret store
  never_inject_into_agent_env:           # 这几类一律不进 agent 进程的环境变量
    - ci_secrets                         # CI 的 secret 上下文
    - cloud_deploy_role
    - prod_db_dsn
    - package_publish_token
    - signing_key
  env_file_policy:
    read_dotenv: false                   # .env 一律不读，需要配置就读占位模板
    placeholder_file: ".env.example"
    on_dotenv_read_attempt: block_and_alert
  ci_secret_policy:
    expose_to_agent_step: false          # agent 那一步不注入任何 CI secret
    rationale: >
      CI secret 一旦进入 agent 的进程环境，它就同时出现在模型上下文的可达范围内；
      一次提示注入即可让它被写进日志、写进注释、或拼进一次出网请求。
    agent_step_isolation: separate_job    # agent 单独一个 job，与部署 job 不共享上下文
  rotation:
    on_agent_incident: immediate
    scheduled_days: 30

# ── 三、放宽通道：临时加权限走这里，不许直接改上面的 profile ──────────────
escalation:
  request_required_fields: [repo, paths, reason, expires_at, requester, approver]
  max_ttl_hours: 24
  approver_role: appsec-oncall
  auto_revert: true
  denied_by_default:           # 这三项无论谁批都不放开
    - can_merge
    - can_push_protected
    - ci_secrets

# ── 四、留痕：被拒的动作和被放宽的权限都要能查 ────────────────────────────
audit:
  emit_on: [denied_path_write, denied_network, denied_credential,
            dotenv_read_attempt, escalation_granted, profile_switch]
  sink: siem://appsec/coding-agent
  record_fields: [timestamp, run_id, agent_id, profile, repo, target,
                  decision, deny_reason, requested_by]
  drop_silently: never
  retention_days: 400
```

有代价的选择有两处。 一是 `fixer.filesystem.write_denylist` 里的 `.claude/**`——agent 改不了自己的 hook 与权限配置。代价是真实的：更新一条团队统一的安全 hook 也得走人工提 PR，agent 帮不上忙，一次配置调整从十分钟变成半天。买到的是一条硬性质——agent 无法在同一次会话里先关掉审计再动手，1.7 那套行为审计的可信前提就落在这一条上。二是 `credentials.ci_secret_policy.expose_to_agent_step: false` 配上 `agent_step_isolation: separate_job`。代价是流水线要拆成两段、多一次 checkout 和一次缓存恢复，构建时间会长一截，也不能再写"让 agent 顺手把镜像推上去"这种省事的 job。买到的是：一次提示注入拿不到任何可用于横向移动的凭据，因为那些凭据根本不在这个进程的环境里。

照抄时最容易改错的有三处。 第一处是 `defaults.unlisted_repo: deny`。接第二个团队的仓库时这条最容易被改成 `allow`，理由是"清单后面补"。改完之后 agent 能挂载的仓库集合等于组织里所有它有网络可达性的仓库，而"它读过哪些代码"这件事从此没有边界，一次上下文外泄的影响面也随之没有边界。第二处是 `read_denylist` 里的 `**/.env`——很多人只在 `write_denylist` 里防 `.env`，觉得"读一下没关系"。读进上下文就等于读进了模型的输出可达范围，一次注入就能让它出现在 PR 评论里；写保护防的是篡改，读保护防的是外泄，两者不能相互替代。第三处是 `escalation.max_ttl_hours: 24` 与 `auto_revert: true` 这一对。只保留前者、去掉后者，是最常见的改法（"到期我会记得收回来"），实际结果是临时权限永久化——三个月后再看，一半的 agent 跑在当初为某次紧急修复临时开的权限上，而那次修复早就合完了。

### 3.3 人审 gate 是不可省的一环

前面反复出现的同一条线：Deriv 等批准才推、Codex 不自动改代码、SAST 自修复禁止无人审 merge、角色化流水线的 PR 必须人审。这些不是各自的巧合，而是同一条底线——改变代码库状态的那一步，留给人。agent 负责把材料备齐、把修复建议和验证结果摆出来，最后一步由人批准。

### 3.4 PR 门禁：agent 的 PR 和人的 PR 不是一回事

上一小节说"改变代码库状态的那一步留给人"，这句话要落地，缺的是一张写清楚差别在哪的门禁配置。差别不在"agent 写的代码质量更差"——它可能比人写得更规整。差别在三处结构性事实：agent 的输入里可能混着不可信内容（PR 描述、issue 正文、被读进上下文的第三方文档），所以它的产出不能按"可信作者的产出"对待；它一晚上能开几十个 PR，人一晚上开不了，所以要有节流和批量回收；出事时要能按一次运行把它开过的全部 PR 一次性关掉，而这要求每个 PR 都带着可验证的来源标记。

```yaml
# ci/pr-gate.yaml —— agent 提交的 PR 与人提交的 PR 在门禁上的差别
# 同一个仓库两条门禁：human 与 agent。差别不在"agent 的代码质量更差"，
# 而在三处结构性事实——agent 的输入里可能有不可信内容、它一晚上能开几十个 PR、
# 出事时要能一次性回收它开过的全部 PR。这三条决定了下面多出来的那几道检查。
version: 2
owner: appsec-platform
applies_to: [group:product-services]

# ── 一、来源判定：先回答"这个 PR 是谁写的"，判不出就按 agent 处理 ──────────
provenance:
  order: [signed_trailer, bot_identity, label]     # 自上而下，第一个能判定的生效
  signed_trailer:
    field: "X-Agent-Run-Id"          # 由 agent 运行时写入 commit trailer 并签名
    verify_with: internal://agent-runtime/pubkeys
  bot_identity:
    actors: [svc-coding-agent]       # agent 用独立机器身份，不借开发者账号
  label:
    name: agent-authored
    trusted: false                   # 标签可被人手动加减，只作展示，不作判定依据
  on_conflict: treat_as_agent        # 判定信号互相矛盾时按更严的一侧走
  on_unknown: treat_as_agent         # 判不出来源一律按 agent，fail-close
  require_human_reviewer_identity: true   # 审批人必须是自然人账号，不接受机器身份审批

# ── 二、两条门禁 ──────────────────────────────────────────────────────────
gates:

  human:
    required_checks: [build, unit_test, sast_diff, license_check]
    required_approvals: 1
    dismiss_stale_approvals: true
    forbidden_paths: []              # 人改 CI 与锁文件走常规 CODEOWNERS 评审
    max_changed_files: 0             # 0 = 不限
    allow_self_approve: false

  agent:
    required_checks:                 # human 那五项之上多出来的四项
      - build
      - unit_test
      - sast_diff
      - license_check
      - secret_scan_full             # 全量扫而非只扫 diff：agent 可能把密钥写进它新建的文件
      - dependency_diff              # 依赖清单有无变化，见下面 dependency 段
      - prompt_injection_scan        # 扫 PR 描述与被读入的 issue/评论里的指令性内容
      - regression_test              # 重扫只证明"该漏洞消失"，证明不了"没引入回归"
    required_approvals: 2            # 一位代码 owner + 一位不在本次改动里的复核人
    approvers_must_include: [role:code_owner]
    allow_self_approve: false        # agent 不能批自己，也不能批另一个 agent 的 PR
    dismiss_stale_approvals: true
    require_linear_history: true     # 禁止 agent 用 merge commit 把历史搅乱
    max_changed_files: 40
    max_changed_lines: 800
    on_size_exceeded: split_required # 超限不是警告，是要求拆分后重开

    forbidden_paths:                 # 命中即阻断，不进入检查阶段
      # 改这里等于改门禁自己
      - ".github/workflows/**"
      - ".github/CODEOWNERS"
      - ".gitlab-ci.yml"
      - "Jenkinsfile"
      - "ci/pr-gate.yaml"
      - ".claude/**"                 # agent 的 hook 与权限配置
      - "coding-agent/permissions.yaml"
      # 依赖锁文件：一行改动可以换掉整棵依赖树，diff 看不出风险
      - "**/package-lock.json"
      - "**/yarn.lock"
      - "**/pnpm-lock.yaml"
      - "**/poetry.lock"
      - "**/Pipfile.lock"
      - "**/go.sum"
      - "**/Cargo.lock"
      # 权限与鉴权相关代码：错一行的后果与业务 bug 不是一个量级
      - "**/auth/**"
      - "**/authz/**"
      - "**/middleware/permission*"
      - "**/*_policy.rego"
      - "infra/iam/**"
      # 基础设施与密钥
      - "infra/**"
      - "**/.env"
      - "**/.env.*"
      - "**/*.pem"
    forbidden_path_action: block_and_close   # 直接关掉 PR，不留着让人"顺手批一下"
    forbidden_path_exception:
      allowed: true
      requires: [appsec_oncall_approval, written_reason, expires_at]
      max_ttl_hours: 24
      never:                          # 例外也不放开的三项
        - ".github/workflows/**"
        - "ci/pr-gate.yaml"
        - "coding-agent/permissions.yaml"

# ── 三、依赖变更：允许改清单，不允许改锁文件 ──────────────────────────────
dependency:
  manifest_paths: ["**/package.json", "**/pyproject.toml", "**/requirements*.txt",
                   "**/go.mod", "**/Cargo.toml"]
  agent_may_edit_manifest: true
  agent_may_edit_lockfile: false      # 锁文件由 CI 用固定工具链重新生成，不接受 agent 产出
  lockfile_regenerated_by: ci
  new_dependency_policy:
    require_human_approval: true
    checks: [license_allowlist, advisory_scan, maintainer_age_days, typosquat_distance]
    min_maintainer_age_days: 180
    on_new_transitive_only: warn      # 传递依赖变化只告警，否则升级一个补丁版就寸步难行

# ── 四、批量与回收：agent 的 PR 要能一次性收回 ────────────────────────────
throttle:
  max_open_prs_per_agent: 5
  max_prs_per_hour: 10
  on_exceeded: pause_agent_and_alert
recall:
  group_by: agent_run_id              # 出事时按 run_id 一次性关闭同一次运行开的全部 PR
  auto_close_on_agent_incident: true

# ── 五、留痕 ──────────────────────────────────────────────────────────────
audit:
  emit_on: [provenance_unknown, forbidden_path_hit, size_exceeded,
            exception_granted, agent_pr_merged]
  sink: siem://appsec/pr-gate
  record_fields: [timestamp, repo, pr_number, provenance, agent_run_id,
                  decision, deny_reason, approvers]
  drop_silently: never
  retention_days: 400
```

有代价的选择有两处。 一是 `provenance.on_unknown: treat_as_agent`。来源判不出来时按更严的一侧走，代价是误伤：一个开发者手工 cherry-pick 了 agent 的一个 commit，trailer 跟着过来了，他的 PR 就被当成 agent PR，要两个人批、还不许碰锁文件。买到的是这条门禁不会因为"标记丢了"而整条失效——而标记丢失恰恰是攻击者最省事的绕过方式。二是 `agent.forbidden_paths` 里的 `**/auth/**`、`**/authz/**` 这批权限相关代码。代价是 agent 在这些目录里真发现了漏洞也改不了，只能出一份分析报告等人来改，而这些目录往往正是最该被修的地方。买到的是：改错一行鉴权代码的后果与改错一行业务代码不在一个量级，而 agent 生成的补丁在这类代码上恰恰最容易"看起来对"——它能读懂函数签名，读不懂这个 `if` 背后三年前那次事故。

照抄时最容易改错的有三处。 第一处是 `provenance.label.trusted: false`。用标签判来源是最省事的做法，很多团队会把它改成 `true` 然后把 `signed_trailer` 那条删掉。改完之后，任何能改 PR 标签的人（在多数仓库配置里就是任何有写权限的人，也包括被劫持的 agent 自己）都能把一个 agent PR 摘掉标签，直接走 human 门禁——两个审批变一个、禁改路径检查整条跳过。标签是给人看的，判定要靠签名和机器身份。第二处是 `forbidden_path_action: block_and_close`。改成 `block` 只拦不关是很自然的想法，但一个被拦住却挂在那里的 PR 会成为常态化的例外申请入口——它每天出现在待办列表里，第五次看到时总会有人"顺手批一下"。关掉它意味着要重新开一个，而重新开一个的成本正好足以让人先想清楚为什么要改这个路径。第三处是 `dependency.new_dependency_policy.on_new_transitive_only: warn`。这条常被改成 `block`，理由听起来很正当（传递依赖也是攻击面）。改完之后升级一个补丁版本都会因为某个二级依赖跟着动了而被拦，两周内这条规则就会被整个关掉——包括它本该拦住的直接依赖那一半。门禁的杀伤力和它的存活率是一对反向指标，卡在直接依赖上是那个还能活下来的位置。

### 3.5 改动审计：门禁之外再查一遍

上面那份 YAML 是给平台的门禁读的。还需要一段能独立跑的脚本，理由有两个：门禁配置在托管平台上生效，而 agent 在本地或在自建 runner 上也会产出改动，那些路径上没有平台门禁；另一个是门禁配置本身会被改，一段读同一份配置、独立运行、结论进审计流的脚本，能让"门禁被改松了"这件事在下一次跑批时暴露出来。

下面这段做四件事：命中禁改路径、动了锁文件、新增了依赖、触及安全相关配置，再加一条 diff 规模上限。判据全部从 `pr-gate.yaml` 读，脚本里不写第二份清单。

```python
"""audit_agent_diff.py —— 审计一次编程智能体改动：禁改路径、新增依赖、安全配置、规模。
用法: git diff --unified=0 origin/main...HEAD | python3 audit_agent_diff.py ci/pr-gate.yaml
退出码三态：0 = 无发现可自动合入，1 = 有 BLOCK 须阻断，2 = 仅有 REVIEW 须人工批准后才合入。
二态（只有放行/阻断）是这类脚本最常见的设计缺陷：REVIEW 会被 CI 当成通过，
于是"新增依赖需人工批准"这条判定打印出来了、也没人拦，PR 照样自动合入。
判据全部读自 pr-gate.yaml，脚本不内置路径清单：两处各写一份，
结果是门禁改了、审计还按旧清单放行。
"""
import fnmatch, re, sys

import yaml

FILE_RE = re.compile(r"^\+\+\+ b/(.+)$")
SKIP_RE = re.compile(r"^(--- a/|@@ |diff |index |new file|deleted file|similarity)")  # 非内容行
LOCK_RE = re.compile(r"(package-lock\.json|\.lock|lock\.yaml|go\.sum)$")  # 锁文件
DEP_ADD_RE = re.compile(r'^\+\s*["\']?([A-Za-z0-9._@/-]+)["\']?\s*[:=><~^]')
SEC_CONF_RE = re.compile(r"(?i)verify\s*=\s*False|ssl_verify|check_hostname|cors|csrf|scope"
                         r"|permission|authoriz|authent|is_admin|secret|token|password|key")


def match_any(path, patterns):
    """路径是否命中任一 glob。fnmatch 不理解 ** 跨目录，先把 **/ 前缀展开成两种形态。"""
    for pat in patterns or []:
        if fnmatch.fnmatch(path, pat) or (
                pat.startswith("**/") and fnmatch.fnmatch(path, pat[3:])):
            return pat
    return None


def parse_diff(text):
    files, cur = {}, None   # {path: {"add": n, "del": n, "added": [加行原文]}}
    for line in text.splitlines():
        m = FILE_RE.match(line)
        if m:
            cur = m.group(1)
            files.setdefault(cur, {"add": 0, "del": 0, "added": []})
        elif SKIP_RE.match(line) or cur is None:
            continue
        elif line.startswith("+"):
            files[cur]["add"] += 1
            files[cur]["added"].append(line)
        elif line.startswith("-"):
            files[cur]["del"] += 1
    return files


def audit(files, gate, dep):
    """返回 [(severity, code, path, detail)]；出现一条 BLOCK 即阻断。"""
    out = []
    n_line = sum(f["add"] + f["del"] for f in files.values())
    for code, got, cap in (("SIZE_FILES", len(files), gate.get("max_changed_files")),
                           ("SIZE_LINES", n_line, gate.get("max_changed_lines"))):
        if cap and got > cap:                          # cap 为 0 或缺失表示不限
            out.append(("BLOCK", code, "-", "本次 %d，上限 %d" % (got, cap)))
    for path in sorted(files):
        hit = match_any(path, gate.get("forbidden_paths"))
        if hit:
            out.append(("BLOCK", "FORBIDDEN_PATH", path, "命中 %s" % hit))
        if LOCK_RE.search(path) and not dep.get("agent_may_edit_lockfile", False):
            out.append(("BLOCK", "LOCKFILE_EDIT", path, "锁文件须由 CI 重新生成"))
        if match_any(path, dep.get("manifest_paths")):
            for line in files[path]["added"]:
                m = DEP_ADD_RE.match(line)
                if m:
                    out.append(("REVIEW", "NEW_DEPENDENCY", path,
                                "新增依赖 %s，需人工批准" % m.group(1)))
        for line in files[path]["added"]:
            if SEC_CONF_RE.search(line):
                out.append(("REVIEW", "SECURITY_CONFIG", path,
                            "触及安全相关配置：%s" % line.strip()[:70]))
                break
    return out


def main(argv):
    if len(argv) != 2:
        sys.exit(__doc__)
    cfg = yaml.safe_load(open(argv[1], encoding="utf-8"))
    gate = (cfg.get("gates") or {}).get("agent")
    if not gate:
        sys.exit("配置里没有 gates.agent，拒绝放行")     # 缺配置一律不通过
    files = parse_diff(sys.stdin.read())
    if not files:
        sys.exit("未从 stdin 读到 diff，拒绝放行")
    findings = audit(files, gate, cfg.get("dependency") or {})
    for sev, code, path, detail in findings:
        print("[%s] %-16s %s  %s" % (sev, code, path, detail))
    print("文件 %d | 发现 %d 条" % (len(files), len(findings)))
    if any(f[0] == "BLOCK" for f in findings):
        return 1
    return 2 if findings else 0      # 有 REVIEW 无 BLOCK：不是放行，是转人工


if __name__ == "__main__":
    sys.exit(main(sys.argv))
```

退出码为什么是三态。 这段脚本产出两种严重度：`BLOCK` 是确定性判定（改了禁改路径、动了锁文件、超了规模上限），`REVIEW` 是"机器判不了、必须人看"（新增依赖、触及鉴权相关配置）。二态退出码只能表达前者，`REVIEW` 就只剩打印在日志里这一条出路——而 CI 日志没人逐行读，绿灯才是被读的那个信号。结果是 `pr-gate.yaml` 里明明写着 `new_dependency_policy.require_human_approval: true`，脚本也确实把这条依赖打印出来了，PR 还是自动合入了，因为退出码说"通过"。三态把这件事变成 CI 配置里必须显式回答的问题：`exit 2` 你是当失败处理（阻塞等人批），还是当成功处理（等于关掉这条检查）。两种选法都可以，但必须是被选的，不能是被默认掉的。对应到平台侧，`exit 2` 应该映射成"required check 未通过 + 加 `needs-human-review` 标签"，而不是映射成 warning 注解——注解不阻塞合并。

有代价的选择有两处。 一是判据从 YAML 读而不是写在脚本里。代价是脚本不能独立运行，必须带着那份配置一起分发，一个只想在本地跑一下的开发者会觉得多此一举。买到的是两处清单不会各自漂移——一份写在门禁里、一份写在脚本里，半年后它们必然不同，而不同的那部分就是审计放行、门禁拦截（或者反过来）的灰区。二是 `SECURITY_CONFIG` 每个文件只报第一条命中（那个 `break`）。代价是同一文件里的后续命中看不到，一次改了五处鉴权逻辑只会报一条。买到的是这条检查还有人看：它的判据是关键词正则，误报率天生不低，不加 `break` 的话一个改了 200 行的 PR 能刷出几十条同质告警，接下来的事情是有人把这条检查关掉。它的定位是"这个文件需要人多看一眼"的路标，不是漏洞清单。

照抄时最容易改错的有三处。 第一处是 `main()` 里 `if not gate: sys.exit(...)`。改成"没配 agent 门禁就按 human 处理"是很自然的写法，理由是"新仓库还没配"。改完之后，一个 `pr-gate.yaml` 缩进写错导致 `gates` 段整个丢失的仓库，会静默地一路放行——而缺配置和配置为空在 YAML 里长得一模一样。门禁类代码的默认行为必须是拒绝。第二处是 `match_any()` 里那个 `**/` 前缀的展开。`fnmatch` 不理解 `**` 跨目录语义，`**/poetry.lock` 匹配不到仓库根目录下的 `poetry.lock`——删掉那半行 `or` 条件，配置照样解析、脚本照样跑、也照样打印"发现 0 条"，只是根目录下的锁文件从此不再被拦。这是全段最不容易被测出来的一处，因为它只在特定路径深度上失效。第三处是输入格式。`parse_diff()` 认的是 `git diff` 的 unified 格式，靠 `+++ b/` 这行切文件。换成平台 API 返回的简化 diff、或 `git diff --stat`，这行的形态就变了，`FILE_RE` 一条都匹配不上——好在这个失败是响的，脚本会以"未从 stdin 读到 diff"退出而不是打印"发现 0 条"。真正会静默出错的是另一件事：不加 `--unified=0` 时，上下文行虽然不以 `+` 开头（前面有空格）因而不会被误计，但同一处改动会被多个 hunk 的上下文重复覆盖，`max_changed_lines` 那道规模闸门的口径会随 `-U` 的取值浮动。接入新数据源前先拿一个已知规模的 diff 对一遍数，别假设所有 diff 都长成 `git diff --unified=0` 的样子。

### 3.6 提示注入是首要风险

在所有针对编程智能体的攻击里，提示注入（对应 OWASP LLM Top 10 的 LLM01）是排在第一位的。它的形态很多——在 PR 的代码注释、字符串、甚至依赖包的 README 里埋入指令，诱导 agent 做出计划外的动作。

> 截至 2026.7 的实例：GMO Flatt Security 披露过针对 Claude Code GitHub Action 的供应链投毒路径；微软在 2026.6 发现过一条环境变量泄露的问题。两者均已修复。列出它们是为了说明这类攻击真实发生过，落地时必须把它当作首要风险对待，而非论证 agent 不能用。
> 来源：GMO Flatt Security 公开披露；微软 2026.6 安全公告。

需要划清的是：编程智能体自身的攻防，其防御深度属于第18章，本节点到即止，且分别指向具体小节——提示注入的完整防御（对应 LLM01）见 [18.3 LLM 威胁与防护](../第18章_AI系统安全/18.3_LLM威胁与防护.md)；供应链与第三方 skill 投毒（对应 LLM05）见 [18.3 LLM 威胁与防护](../第18章_AI系统安全/18.3_LLM威胁与防护.md)；工具滥用与 MCP 信任边界见 [18.2.7 Agentic AI 安全](../第18章_AI系统安全/18.2_AI安全架构设计与实施.md)。这里只强调一个落地前提：接入编程智能体时，上面这套护栏（Rule of Two、最小权限、人审 gate、把提示注入当首要风险）是硬性前置条件，不是可选项。

## 四、什么时候别用编程智能体

七个挂载点讲完之后，同样重要的是讲清编程智能体不该出现在哪里。

判断一个安全动作该不该请 agent，用一条简单的分界：能用确定性手段解决的，别请 agent。一条精确的 lint 规则、一个签名明确的 SAST 检查、一道基于固定条件的 CI 门禁——这些工作确定、可预测、成本近乎为零，用 agent 去做纯属浪费，还平白引入了 agent 判断的不确定性。检查"代码里有没有硬编码的密钥"这种有确定模式的事，一条正则加一个 pre-commit hook 就够了，不需要一个会推理的 agent。

agent 真正划算的，是那些确定性手段够不着的活——需要理解跨文件的调用上下文才能判断一个漏洞是否真的可达、需要因果推理才能把一份 CTI 报告翻译成检测规则、需要生成语义正确的修复而非机械替换。这三类活的共同特征，是它们没法被写成一条固定规则；这才是 agent 的用武之地。

与相邻三个领域的分工如下：

- 与 SDL（[第6章 应用安全架构](../../第02部分_技术架构与基础设施安全/第06章_应用安全架构/README.md)）的分工：SDL 提供安全开发生命周期的方法学骨架——威胁建模、安全需求、安全测试的完整流程；本节是把编程智能体这类新工具嵌进 SDL 各环节的落地样例。方法学在第6章，工具落地在本节。
- 与检测工程（[11.3 威胁检测工程](../../第04部分_安全运营与防御能力/第11章_安全运营/11.3_威胁检测工程.md)）的分工：编程智能体起草 Sigma/KQL 规则（1.4）的通用能力边界在本节；起草产物进入 Detection-as-Code 流水线后的投毒威胁建模、语义护栏与审批 gate 的具体实现，在 11.3.6。
- 与 Security for AI（[第18章 AI 系统安全](../第18章_AI系统安全/README.md)）的分工：本节讲编程智能体"做安全"的正面用途；它自身作为攻击面的防御深度，在第18章。正面用途在本节，防御深度在第18章。

把这三条分工摆清楚，才能避免一个常见的误区——把编程智能体当成一个包打天下的安全工具。它是研发流水线上一个有明确适用边界的新工具：在需要理解上下文、跨文件推理、生成修复的位置上，它能把安全动作前移到修复成本最低的地方；在能用确定性规则解决的位置上，它不该出现。

# 14.2　身份生命周期治理（JML）

身份生命周期自动化有一个残酷的政治现实：**它的价值几乎全在"转"和"离"，而组织的推动力几乎全在"入"。**

新员工第一天没有账号，会有人投诉。投诉会到达部门总监，总监会找 IT 总监，IT 总监会把它变成一个高优先级项目。整条链路上的每个人都能感受到痛。

离职员工第 400 天账号还在，没有人投诉。他自己不会说，他的经理已经忘了他，IT 的工单系统里这件事早就关闭了。**唯一会发现这件事的是攻击者和审计**，而这两者出现的时间都不可预测。转岗更隐蔽——员工带着旧权限干新活，业务照常运转，甚至更顺畅，因为他"什么都能查"。

这个不对称性决定了 JML 项目的落地顺序必须与直觉相反：**先做离职，再做入职，最后做转岗**。离职自动化是唯一一个业务部门不会反对的（没人会为一个已经走了的人争取权限），它能在最小阻力下建立起 HR 到目标系统的完整数据通路；这条通路建好以后，入职自动化是顺手的事。转岗放在最后，因为它需要前两者的数据质量作为前提，且它是唯一需要业务部门做出取舍的场景。

本节按这个顺序展开，并在 14.2.5 用最大篇幅处理离职撤销的时序问题——那是本节最有工程含量的部分，也是最容易做错的部分。

---

## 14.2.1 三类事件的不对称性

| 事件 | 触发源 | 时效要求 | 谁会发现失败 | 典型失败形态 |
|------|-------|---------|------------|------------|
| Joiner 入职 | HR 入职单 | 到岗前完成 | 员工与其经理，当天 | 账号有了但权限不全，靠工单补 |
| Mover 转岗 | HR 转岗单 | 生效日起 30 天内完成回收 | 没有人 | 只加不减，权限累积 |
| Leaver 离职 | HR 离职单 / 合同到期 | 分级，最快秒级 | 没有人（直到出事） | 账号禁用了，访问没断 |
| Leaver 非自愿离职 | HR 紧急通知 | 秒级，且需先于告知本人 | 安全团队 | 流程走不通，靠电话喊人 |
| 合同工到期 | 采购系统 / 无 | 到期日 | 没有人 | 无触发源，靠 90 天不活跃兜底 |

这张表里最要紧的是最后两行。**非自愿离职**是唯一一个撤销必须先于通知的场景——HR 与安全需要一个"静默撤销"的协同流程，通常是 HR 在会议开始前 5 分钟触发，安全侧在 60 秒内完成会话与特权撤销。这个流程必须提前演练，因为它第一次被用到时一定是在压力下。**合同工到期**则是最常见的黑洞：采购系统里有合同结束日，但那个字段从来没有被接到身份系统里。

---

## 14.2.2 Joiner：出生权限的边界

入职自动化的技术含量不高，难的是划定**出生权限（birthright entitlement）**的边界——哪些权限应当在入职时自动获得，哪些必须走申请。

一个可操作的判据：**出生权限 = 该人群 100% 需要 + 泄露后果可承受 + 不涉及职责分离约束**。三个条件缺一不可。邮箱、即时通讯、内网 Wi-Fi、考勤系统、内部知识库（公开区）通常满足；代码仓库读权限在工程组织里也常满足；而 CRM、ERP、数据平台几乎从不满足，因为它们的数据范围随岗位差异极大。

出生权限的定义维度建议控制在三个：**雇佣类型 × 岗位族 × 工作地**。加入第四个维度（如成本中心或职级）会让组合数迅速膨胀到无法维护。

```yaml
# 出生权限规则（示例）：三维度匹配，命中即授予
birthright_rules:
  - id: BR-ALL-BASE
    description: 全员基础包
    match:
      employment_type: ["employee", "contractor", "intern"]
      job_family: ["*"]
      work_country: ["*"]
    grants:
      - app: email
        entitlement: mailbox_standard
      - app: chat
        entitlement: member
      - app: intranet
        entitlement: reader
    revoke_on_leave: immediate

  - id: BR-ENG-REPO
    description: 工程岗代码仓库只读
    match:
      employment_type: ["employee"]
      job_family: ["ENG", "SRE", "DATA"]
      work_country: ["*"]
    grants:
      - app: source_control
        entitlement: org_member_read
    conditions:
      requires_training: ["secure-coding-101"]
      grace_period_days: 14
    revoke_on_leave: immediate

  - id: BR-CN-VPN
    description: 中国区办公网接入
    match:
      employment_type: ["employee", "contractor"]
      job_family: ["*"]
      work_country: ["CN"]
    grants:
      - app: vpn
        entitlement: corp_access
    conditions:
      requires_device_enrolled: true
    revoke_on_leave: immediate

policy:
  max_birthright_apps: 8
  review_cycle_months: 6
  # 超过 max_birthright_apps 需 CISO 例外审批：
  # 出生权限膨胀是最小权限失效的头号来源
  exception_approver: ciso
```

怎么读这段配置：`requires_training` 与 `grace_period_days` 是一组——培训未完成不阻断入职，但 14 天后自动回收，避免"先给了就永远给了"。`max_birthright_apps: 8` 是一条硬性护栏，它存在的理由见下面这个生产坑。

**生产坑：出生权限膨胀。** 权限申请流程越慢，业务越倾向于把应用塞进出生权限——"反正大家都要用，不如默认给"。某企业的出生权限清单在三年内从 6 个应用长到 31 个，其中包括一个能查询全量客户联系方式的报表系统。它的膨胀路径是完全合理的：每一次追加都有一个具体的、当时看起来正当的理由。防御手段是**给出生权限设一个数量上限并定期复检**，同时把申请流程做快，审批更严解决不了问题——申请一个应用如果 30 分钟能到手，没有人会去争取把它设成默认。

**Day-1 就绪的工程定义**：不是"账号已创建"，而是"员工用自己的凭据登录后，能完成岗位的第一个任务"。这意味着账号、密码首登、MFA 注册、设备绑定、基础权限五件事全部完成。建议以此定义度量，参考目标 > 98%（示例口径），并把未达标案例逐条归因——归因结果通常集中在两三个接口上。

## 14.2.3 SCIM 供给的工程现实

SCIM（RFC 7643/7644）[1][2] 是跨系统身份供给的事实标准，但**标准的存在不等于实现的一致**。真实项目中，SCIM 的工程量有一大半花在处理各家实现的偏差上。

先记住三条协议要点，它们决定了大部分设计：

**第一，停用用 PATCH 把 `active` 置为 false，不要用 DELETE。** DELETE 在多数 SaaS 中是硬删除，会带走该用户创建的内容、审计记录与共享关系。停用是可逆的，删除不可逆，而离职流程在真实企业里被撤回的频率比想象中高（返聘、误操作、法务保全要求）。

**第二，PATCH 的语义是部分更新，PUT 是整体替换。** 用 PUT 更新单个属性，会把目标端未提供的属性全部清空——这是导致"同步之后所有人的手机号没了"这类事故的经典原因。

**第三，供给必须幂等。** 网络重试、消息重复投递、人工重跑都会导致同一操作执行多次。以外部 ID（`externalId`）作为幂等键，先查后建，创建冲突（HTTP 409）视为成功而非失败。

下表是若干真实存在的实现偏差（依据主流 SaaS 的公开文档与实施经验归纳，具体行为随版本变化，落地前须逐项验证）：

| 偏差点 | 表现 | 应对 |
|-------|------|------|
| `userName` 唯一性范围 | 有的租户内唯一，有的全局唯一 | 用邮箱作 `userName` 之外，另存 `externalId` 做幂等键 |
| `active=false` 的语义 | 有的立即注销会话，有的仅阻止新登录 | 停用后必须另行调用会话撤销接口，见 14.2.5 |
| 组成员写入方式 | 有的改 `/Groups` 的 members，有的改 `/Users` 的 groups | 两种都实现，按目标系统能力选择 |
| 组成员 PATCH 粒度 | 有的只支持整组替换 | 大组（万人级）替换会超时，需分批或改用增量接口 |
| 属性大小写 | 有的区分大小写并因此重复建号 | 统一小写规范化后再发送 |
| 错误码语义 | 4xx 用于业务冲突，也用于限流 | 必须按响应体细分，不能只看状态码 |
| 限流 | 突发批量触发 429，且退避头缺失 | 客户端自带令牌桶，默认保守值 |

```python
"""SCIM 停用客户端：幂等、可重试、错误可分类。

刻意的设计选择：
1. 停用用 PATCH active=false，不用 DELETE（硬删除不可逆）。
2. 以 externalId 查找目标用户，而非邮箱（邮箱可变，见 14.1.3）。
3. 错误分三类：可重试（限流/5xx）、不可重试（4xx 业务错误）、需人工（未找到）。
4. 返回结构化结果，供上层编排器决定补偿动作。
"""
import time
from dataclasses import dataclass
from enum import Enum
from typing import Any, Dict, Optional

import requests


class ProvisionOutcome(Enum):
    SUCCESS = "success"
    ALREADY_INACTIVE = "already_inactive"
    NOT_FOUND = "not_found"
    RETRYABLE_ERROR = "retryable_error"
    PERMANENT_ERROR = "permanent_error"


@dataclass
class ProvisionResult:
    outcome: ProvisionOutcome
    target: str
    external_id: str
    detail: str = ""
    http_status: Optional[int] = None


RETRYABLE_STATUS = {429, 500, 502, 503, 504}


class ScimClient:
    def __init__(self, base_url: str, token: str, target_name: str,
                 timeout: int = 15, max_attempts: int = 4):
        self.base_url = base_url.rstrip("/")
        self.target_name = target_name
        self.timeout = timeout
        self.max_attempts = max_attempts
        self.session = requests.Session()
        self.session.headers.update({
            "Authorization": f"Bearer {token}",
            "Content-Type": "application/scim+json",
            "Accept": "application/scim+json",
        })

    def _request(self, method: str, path: str,
                 payload: Optional[Dict[str, Any]] = None) -> requests.Response:
        url = f"{self.base_url}{path}"
        last_exc = None
        for attempt in range(1, self.max_attempts + 1):
            try:
                resp = self.session.request(
                    method, url, json=payload, timeout=self.timeout
                )
            except requests.RequestException as exc:
                last_exc = exc
                time.sleep(min(2 ** attempt, 30))
                continue
            if resp.status_code in RETRYABLE_STATUS and attempt < self.max_attempts:
                # 优先遵守服务端退避指示，缺失时用指数退避
                wait = int(resp.headers.get("Retry-After", min(2 ** attempt, 30)))
                time.sleep(wait)
                continue
            return resp
        raise RuntimeError(f"SCIM request failed after retries: {last_exc}")

    def find_by_external_id(self, external_id: str) -> Optional[Dict[str, Any]]:
        # externalId 是幂等键：邮箱与 userName 都可能变化，externalId 不变
        safe = external_id.replace('"', '')
        path = f'/Users?filter=externalId eq "{safe}"'
        resp = self._request("GET", path)
        if resp.status_code != 200:
            return None
        resources = resp.json().get("Resources", [])
        return resources[0] if resources else None

    def deactivate(self, external_id: str) -> ProvisionResult:
        user = self.find_by_external_id(external_id)
        if user is None:
            # 找不到不等于成功：可能是从未供给，也可能是 filter 不被支持
            return ProvisionResult(
                ProvisionOutcome.NOT_FOUND, self.target_name, external_id,
                detail="user not found by externalId; manual check required",
            )
        if user.get("active") is False:
            return ProvisionResult(
                ProvisionOutcome.ALREADY_INACTIVE, self.target_name, external_id,
                detail="idempotent no-op",
            )

        payload = {
            "schemas": ["urn:ietf:params:scim:api:messages:2.0:PatchOp"],
            "Operations": [
                {"op": "replace", "path": "active", "value": False}
            ],
        }
        resp = self._request("PATCH", f"/Users/{user['id']}", payload)
        if resp.status_code in (200, 204):
            return ProvisionResult(
                ProvisionOutcome.SUCCESS, self.target_name, external_id,
                http_status=resp.status_code,
            )
        if resp.status_code in RETRYABLE_STATUS:
            return ProvisionResult(
                ProvisionOutcome.RETRYABLE_ERROR, self.target_name, external_id,
                detail=resp.text[:200], http_status=resp.status_code,
            )
        return ProvisionResult(
            ProvisionOutcome.PERMANENT_ERROR, self.target_name, external_id,
            detail=resp.text[:200], http_status=resp.status_code,
        )
```

怎么读这段代码：三个细节决定它在生产里能不能活下来。第一，`find_by_external_id` 返回 `None` 时的判定是 `NOT_FOUND` 而**不是** `SUCCESS`——把"找不到"当成"已经没有了"是危险的默认，因为很多 SaaS 的 SCIM 实现对 `filter` 支持不完整，查不到不代表用户不存在。第二，`ALREADY_INACTIVE` 是一个独立的成功态而非错误，这是幂等的具体体现：重复执行离职撤销必须安全。第三，`Retry-After` 头优先于本地退避——批量离职（如一次组织调整涉及 200 人）极易触发限流，忽略这个头会让整批任务在限流墙前空转。

**生产坑：供给失败的静默。** SCIM 连接器的失败通常表现为某个应用的同步任务在管理界面里显示"部分失败 3 条"，而这个界面没有人每天看。三个月后审计发现某人离职后在 CRM 里仍然活跃，追查回去是当初那 3 条中的一条。工程上的要求很简单但常被忽略：**任何一条离职撤销的失败都必须生成工单并有 SLA**，而不是记录在同步日志里。

**生产坑：SCIM 令牌本身是特权凭据。** 一个 SCIM Bearer Token 通常具备在目标 SaaS 中创建、修改、停用任意用户的能力——它是一个不受 MFA 保护、不过期、存在配置文件里的超级管理员。它必须按 14.8 的非人类身份规范治理：登记归属、设定有效期、轮换、监控异常调用量。

## 14.2.4 Mover：转岗是最难的一环

转岗处理有三种模型，它们的差异不在技术，而在于把风险留给谁。

| 模型 | 做法 | 优点 | 代价 | 适用 |
|------|------|------|------|------|
| 全撤重授 | 生效日撤销全部旧权限，按新岗位重新授予 | 权限最干净 | 业务中断风险最高；交接期无法完成 | 高敏感岗位调动（如财务与稽核之间） |
| 增量叠加 | 只加新权限，不动旧权限 | 零业务影响 | 权限累积的直接成因 | 不推荐，但这是多数企业的现状 |
| 时限并存 | 新权限立即授予，旧权限进入 N 天倒计时后自动回收 | 兼顾交接与回收 | 需要工程实现与倒计时可见性 | 推荐的默认模型 |

推荐的默认是**时限并存 + 强制回收窗口**：转岗生效日起，旧岗位权限被打上到期标记（默认 30 天，敏感权限 7 天，特权类 0 天即立即回收），到期自动回收，延期需要新旧两位经理共同批准且最多延一次。

关键设计在于**"哪些权限不进入宽限期"**。答案是三类：特权类（管理员、生产变更）、涉及职责分离约束的（新旧岗位组合会构成 SoD 冲突，见 14.4）、以及数据敏感级最高的。这三类必须在转岗生效日当天回收，因为它们正是转岗风险的实质——一个从付款岗调到采购岗的人，如果同时保有两边权限 30 天，他在这 30 天里可以完成一个完整的欺诈闭环。

```python
"""转岗权限差异计算：产出立即回收、宽限回收、新增授予三个清单。

规则优先级（从高到低）：
1. 新旧岗位组合触发 SoD 冲突 → 立即回收冲突侧
2. 权限被标记为 privileged → 立即回收
3. 新岗位仍需要 → 保留
4. 其余 → 进入宽限期，到期回收
"""
from dataclasses import dataclass
from datetime import date, timedelta
from typing import Dict, List, Set, Tuple


@dataclass(frozen=True)
class Entitlement:
    key: str
    app: str
    privileged: bool = False
    sensitivity: str = "internal"      # internal / confidential / restricted
    sod_group: str = ""                 # 空字符串表示不参与职责分离约束


GRACE_DAYS = {"restricted": 7, "confidential": 14, "internal": 30}


def compute_mover_actions(
    current: Set[Entitlement],
    target_role_entitlements: Set[Entitlement],
    sod_conflicts: Dict[str, Set[str]],
    effective_date: date,
) -> Dict[str, List[Tuple[str, str]]]:
    """返回 {'revoke_now': [...], 'revoke_scheduled': [...], 'grant': [...]}"""
    keep_keys = {e.key for e in target_role_entitlements}
    target_sod_groups = {e.sod_group for e in target_role_entitlements if e.sod_group}

    revoke_now: List[Tuple[str, str]] = []
    revoke_scheduled: List[Tuple[str, str]] = []

    for ent in current:
        if ent.key in keep_keys:
            continue

        conflicting = any(
            ent.sod_group and ent.sod_group in sod_conflicts.get(g, set())
            for g in target_sod_groups
        )
        if conflicting:
            revoke_now.append((ent.key, "sod_conflict_with_new_role"))
            continue
        if ent.privileged:
            revoke_now.append((ent.key, "privileged_no_grace"))
            continue

        days = GRACE_DAYS.get(ent.sensitivity, 30)
        due = effective_date + timedelta(days=days)
        revoke_scheduled.append((ent.key, due.isoformat()))

    grant = [
        (e.key, "target_role_birthright")
        for e in target_role_entitlements
        if e.key not in {c.key for c in current}
    ]
    return {
        "revoke_now": sorted(revoke_now),
        "revoke_scheduled": sorted(revoke_scheduled),
        "grant": sorted(grant),
    }


if __name__ == "__main__":
    cur = {
        Entitlement("AP-PAYMENT-EXECUTE", "erp", sod_group="payment",
                    sensitivity="restricted"),
        Entitlement("AP-INVOICE-VIEW", "erp", sensitivity="confidential"),
        Entitlement("CRM-READ-EAST", "crm"),
        Entitlement("PROD-DB-ADMIN", "dbops", privileged=True,
                    sensitivity="restricted"),
    }
    tgt = {
        Entitlement("PO-CREATE", "erp", sod_group="procurement",
                    sensitivity="restricted"),
        Entitlement("AP-INVOICE-VIEW", "erp", sensitivity="confidential"),
    }
    conflicts = {"procurement": {"payment"}, "payment": {"procurement"}}
    for bucket, items in compute_mover_actions(
        cur, tgt, conflicts, date(2026, 8, 1)
    ).items():
        print(bucket, items)
```

怎么读这段代码：`sod_conflicts` 是一张双向映射表，必须双向登记（`procurement→payment` 与 `payment→procurement` 都要有），否则冲突判定会依赖于转岗方向，出现"从 A 到 B 拦得住、从 B 到 A 拦不住"的不对称漏洞。`GRACE_DAYS` 按敏感级而非按应用设定，这样新增应用时不需要改代码。`revoke_scheduled` 返回的是到期日而非天数，因为倒计时必须相对于转岗生效日固定下来——用天数会导致每次重算时刷新，权限永远到不了期，这个 bug 我们真实遇到过，表现是"回收任务一直在跑但从来没回收成功"。

**生产坑：转岗当天全撤导致业务中断，然后整个机制被永久叫停。** 某企业上线转岗自动回收时选择了全撤重授，第一批 40 人中有 6 人在生效日当天无法完成手头工作，其中一位是正在处理季度关账的财务。事件升级到 CFO，结果是该机制被无限期暂停，两年内无人敢再提。这个教训的实质是：**权限治理机制的存续依赖于第一次上线的口碑**，宁可第一次做得保守（宽限期给到 45 天），也不要制造一个能被业务用来否定整个方向的事故。

### 权限累积的度量

要说服组织认真对待转岗，需要把权限累积量化。两个可操作的指标：

**岗位内权限离散度**：同一岗位代码下，员工持有权限集合的平均两两 Jaccard 距离。距离越大，说明同岗位的人权限差异越大，其中一部分就是历史累积。参考：距离 > 0.4 的岗位应列为重点治理对象（示例口径）。

**司龄-权限相关系数**：在同一岗位内，计算司龄与权限数量的相关系数。如果显著为正，说明权限只随时间增长而与职责无关——这是 permission creep 的直接证据，也是向管理层汇报时最有说服力的一张图。

## 14.2.5 Leaver：撤销时序，以及"禁用账号 ≠ 撤销访问"

这是本节最重要的部分。

先纠正一个几乎所有企业都存在的错误认知：**禁用 IdP 账号并不等于切断访问**。账号被禁用后，以下七类访问仍可能有效：

| 残留访问 | 为什么禁用无效 | 处置手段 |
|---------|--------------|---------|
| 已签发的会话 Cookie / 令牌 | 应用侧按令牌有效期校验，不回查 IdP | 显式调用会话撤销接口，并缩短令牌生命周期 |
| OAuth refresh token | 有效期可达数十天甚至无限，独立于账号状态 | 撤销该用户的全部授权同意与刷新令牌 |
| 应用本地账号 | 未接 SSO 的应用有独立用户表 | 纳入对账范围；无接口的走人工清单 |
| SSH 公钥 / 部署密钥 | 分布在服务器 `authorized_keys` 与代码平台 | 集中化密钥管理；离职触发全量清理 |
| 个人创建的 API 密钥 | 属于非人类身份，与账号解耦 | 密钥必须登记归属人，随人撤销（见 14.8） |
| 邮件转发规则 / 委派 | 规则在邮箱上，账号禁用后规则仍执行 | 离职流程强制检查并清除转发与委派 |
| 共享账号密码 | 他知道，且没变 | 离职触发共享账号密码轮换（见 14.6） |

（表中"处置手段"为通用做法，具体接口能力随平台而异。）

其中最容易被忽略的是**刷新令牌**。用户在钓鱼中被窃取的、或离职时留在个人设备上的刷新令牌，可以在账号禁用后继续换取新的访问令牌，直到刷新令牌本身过期或被显式撤销。在主流身份平台上，撤销刷新令牌是一个独立的 API 调用，不随账号禁用自动发生。这是 2020 年以来多起"已离职员工仍能访问邮箱"事件的技术根因。

### 分级撤销时序表

要求"离职即刻全部撤销"的方案会在第一次遇到法务取证或业务交接时被回滚。正确的做法是分级，并把每一级的时长与其业务理由绑定，这样在被质疑时可以逐条辩护。

| 时序档 | 动作 | 业务理由 |
|-------|------|---------|
| T+0（秒级，与 HR 事件同时） | 撤销所有活动会话与刷新令牌；禁用 VPN 与远程接入；回收全部特权与生产访问；禁用特权账号；吊销设备证书 | 这些是攻击面最大的通道，且不存在"最后再用一下"的合理场景 |
| T+15 分钟 | 禁用 IdP 主账号；移除全部 MFA 方法；停用门禁卡 | 留出的 15 分钟用于人工中止误触发（HR 误操作在真实环境中每年都会发生几次） |
| T+1 小时 | 停用已接 SSO 的 SaaS；停用未接 SSO 的重点应用（清单化）；轮换其知悉的共享账号密码 | 需要按目标系统串行执行，1 小时是可达的工程 SLA |
| T+当日下班前 | 清除邮件转发规则与邮箱委派；回收公司设备或远程锁定；撤销代码平台成员资格与个人访问令牌 | 需人工介入或依赖设备在线 |
| T+1 个工作日 | 邮箱转为"仅经理可读"的委派状态；转移文件与文档所有权 | 业务交接的最低成本方案，避免直接删除导致资料丢失 |
| T+7 天 | 完成非人类身份归属转移（他名下的服务账号、API 密钥、定时任务） | 需要接手人确认，7 天是现实的响应窗口 |
| T+30 天 | 邮箱归档、账号进入删除队列 | 与法务保全策略对齐 |
| T+法定保留期 | 保留身份记录与审计日志（不保留访问能力） | 合规与取证要求，通常 1～7 年不等 |

（时序为示例口径，需与法务、HR 共同确认后固化为制度。）

这张表有三处需要向业务解释的设计：

**为什么 T+0 不做全部撤销？** 因为 T+0 的动作必须是"不需要人工判断、不需要目标系统在线、失败可重试"的那一批。把邮箱委派放进 T+0 只会导致这一步经常失败，进而拖垮整个编排任务。

**为什么留 15 分钟窗口？** 因为 HR 误触发离职事件是真实存在的（选错人、日期填错、系统重复投递）。15 分钟窗口只覆盖"账号禁用"这类可逆动作，而不覆盖 T+0 的会话撤销——后者即使误触发，代价也只是让人重新登录一次。

**为什么邮箱要走委派而不是直接给经理转发？** 因为转发会让离职后的新邮件进入经理邮箱并混入其个人邮件，取证时无法区分；委派保持邮箱独立，访问有独立审计记录。这个细节在涉及劳动纠纷时会变得非常重要。

### 撤销编排器：部分失败是常态

撤销涉及十几个目标系统，其中总会有一两个当时不可用。编排器的核心设计不是"如何成功"，而是**"部分失败时如何不丢动作"**。

```python
"""离职撤销编排：分级执行、部分失败可续、全程可审计。

关键性质：
1. 每个动作是独立的、幂等的、可重放的工作单元。
2. 某一档内的失败不阻塞其他动作，但会阻止该档被标记为完成。
3. 不可重试的失败立即转人工工单，而不是静默丢弃。
4. 所有状态变更写审计事件，事件本身是撤销证据链。
"""
from dataclasses import dataclass, field
from datetime import datetime, timedelta, timezone
from enum import Enum
from typing import Callable, Dict, List


class Tier(Enum):
    T0_IMMEDIATE = 0
    T15_MINUTES = 1
    T1_HOUR = 2
    T_END_OF_DAY = 3
    T1_DAY = 4


TIER_DELAY = {
    Tier.T0_IMMEDIATE: timedelta(0),
    Tier.T15_MINUTES: timedelta(minutes=15),
    Tier.T1_HOUR: timedelta(hours=1),
    Tier.T_END_OF_DAY: timedelta(hours=8),
    Tier.T1_DAY: timedelta(days=1),
}


@dataclass
class RevokeAction:
    name: str
    tier: Tier
    handler: Callable[[str], bool]
    critical: bool = False          # critical 失败需立即升级告警
    attempts: int = 0
    max_attempts: int = 5
    state: str = "pending"          # pending / done / failed / escalated
    last_error: str = ""


@dataclass
class RevokeOrchestration:
    person_id: str
    triggered_at: datetime
    actions: List[RevokeAction] = field(default_factory=list)
    audit: List[Dict[str, str]] = field(default_factory=list)

    def _log(self, action: str, state: str, detail: str = "") -> None:
        self.audit.append({
            "ts": datetime.now(timezone.utc).isoformat(),
            "person_id": self.person_id,
            "action": action,
            "state": state,
            "detail": detail,
        })

    def due_actions(self, now: datetime) -> List[RevokeAction]:
        return [
            a for a in self.actions
            if a.state in ("pending", "failed")
            and now >= self.triggered_at + TIER_DELAY[a.tier]
        ]

    def run_once(self, now: datetime) -> Dict[str, int]:
        stats = {"done": 0, "failed": 0, "escalated": 0}
        for action in self.due_actions(now):
            action.attempts += 1
            try:
                ok = action.handler(self.person_id)
            except Exception as exc:            # 目标系统异常不应中断整体编排
                ok, err = False, f"{type(exc).__name__}: {exc}"
            else:
                err = "" if ok else "handler returned False"

            if ok:
                action.state = "done"
                stats["done"] += 1
                self._log(action.name, "done")
                continue

            action.last_error = err
            if action.attempts >= action.max_attempts:
                action.state = "escalated"
                stats["escalated"] += 1
                self._log(action.name, "escalated", err)
            else:
                action.state = "failed"
                stats["failed"] += 1
                self._log(action.name, "failed", err)
        return stats

    def tier_completed(self, tier: Tier) -> bool:
        return all(a.state == "done" for a in self.actions if a.tier == tier)

    def sla_breached(self, now: datetime) -> List[str]:
        """返回已超出本档时限却仍未完成的动作名，用于 SLA 看板。"""
        breached = []
        for a in self.actions:
            deadline = self.triggered_at + TIER_DELAY[a.tier] + timedelta(minutes=30)
            if a.state != "done" and now > deadline:
                breached.append(a.name)
        return breached
```

怎么读这段代码：`state` 里 `failed` 与 `escalated` 是两种不同的终态——`failed` 会在下一轮被重新拾起（因为 `due_actions` 同时选取 `pending` 与 `failed`），`escalated` 则退出自动重试并等待人工。这个区分很关键：无限重试会掩盖真实故障，而一次失败就转人工会淹没工单队列。`sla_breached` 单独提供而不是混在执行逻辑里，因为**SLA 是给管理层看的，执行状态是给工程看的**，两者的口径必须能分开解释。异常捕获使用 `except Exception` 并记录类型，是刻意的宽泛处理——一个目标系统的 SDK 抛出意外异常，不应该导致其余十几个撤销动作全部不执行。

## 14.2.6 中间态：休假、停职、调查中

生命周期不只有三个事件。中间态处理不好，会变成绕过撤销流程的后门。

| 状态 | 建议处理 | 争议点 |
|------|---------|-------|
| 短期休假（< 30 天） | 不做处理 | 无 |
| 长期休假 / 病假（> 30 天） | 保留账号，暂停特权与生产访问，MFA 保持 | 复岗时恢复权限的流程需存在，否则复岗当天等于重新入职 |
| 停职 / 待调查 | 立即执行 T+0 档全部动作，但不禁用主账号（避免打草惊蛇时机不当由调查方决定） | 由谁授权、如何保密，需与法务和 HR 预先约定 |
| 待离职（提出辞职到最后工作日） | 不降权，但提高监控等级（数据外发、批量下载） | 主动降权可能引发劳动争议，多数法务反对 |
| 竞业相关离职 | T+0 立即全撤，且先于告知 | 需 HR 与法务书面授权，流程必须提前演练 |

"待离职期间是否降权"是一个经常被争论的问题。本书的判断是：**默认不降权，改为提高监控**。理由有三：降权会被员工立即察觉并可能加速其行动；降权的范围很难界定，容易误伤正常交接；多数司法辖区下，仅因提出辞职就限制其履行职务的能力，可能带来劳动法风险。监控侧的做法参见 [10.4 内部风险与内部威胁防护](../../第03部分_数据安全与隐私/第10章_信息保护与内部风险/10.4_内部风险防护.md)，那里给出了离职窗口期的行为基线方法。

## 14.2.7 孤儿账号治理闭环

孤儿账号（无法关联到有效身份的账号）不能靠一次大扫除解决，因为它会持续再生。需要的是一个常设闭环。

```
      每日扫描目录与关键应用
                │
                ▼
      ┌─────────────────────┐
      │ 候选孤儿（无 person_id）│
      └──────────┬──────────┘
                 │ 自动归因：按创建者、OU、命名规则、最近登录源
                 ▼
      ┌─────────────────────┐        能归因
      │  归因引擎            │───────────────► 通知疑似责任人认领
      └──────────┬──────────┘                        │
                 │ 无法归因                            │ 14 天内
                 ▼                                    ▼
      ┌─────────────────────┐              ┌──────────────────┐
      │ 挂起：禁用 + 保留 30 天 │◄─────────────│ 未认领 / 认领被拒  │
      └──────────┬──────────┘              └──────────────────┘
                 │ 30 天无异议                        ▲
                 ▼                                    │ 认领成功
      ┌─────────────────────┐              ┌──────────────────┐
      │  删除并归档审计记录    │              │ 转为受管身份       │
      └─────────────────────┘              │ 补齐 owner/到期日  │
                                           └──────────────────┘
```

三条关键规则：

**认领必须带举证。** 只回复"这是我们在用的"不算认领，必须提供用途说明、责任人、预期到期日。没有到期日的认领一律驳回——**没有到期日的账号就是下一批孤儿**。

**禁用先于删除，且保留期不可跳过。** 禁用 30 天足以让任何真正在用的账号暴露出来（有人会来报障），比事前调研可靠得多，也比直接删除安全得多。

**认领不等于永久豁免。** 认领后的账号进入受管状态，纳入下一轮访问审阅与到期检查。见过的最糟糕情况是"认领"成为一个逃生通道：只要有人认领，账号就永远不再被扫描，两年后同一批账号又变成孤儿，且这次有了"曾被认领"的记录，更难删除。

## 14.2.8 失败叙事：那次被回滚的"一键全撤"

我们有一次把离职撤销做成了单一动作：HR 离职事件到达，编排器在 5 分钟内撤销该员工在所有系统中的一切访问，包括邮箱。技术上运行完美，第一个月处理了 60 多例，零失败。

第 37 天出问题。一位销售离职，其邮箱在 5 分钟内被禁用。三天后客户催问合同，业务找不到往来邮件；两周后该员工被指控带走客户资料，法务要求调取其离职前 90 天邮件作为证据——邮箱已按"离职后清理"策略进入删除队列，虽然最终从备份中恢复，但恢复过程耗时 11 天，且备份的完整性在后续程序中被对方质疑。

复盘时我们才意识到，"撤销访问"和"销毁数据"被我们混成了同一个动作。员工失去访问能力是安全要求，数据继续存在是业务与法务要求，二者在时间轴上必须分开。第二个错误是没有人在设计阶段把法务请到桌前——我们把这件事当成了纯技术编排。

改造后的方案就是 14.2.5 的分级时序表：**访问在秒级到小时级切断，数据在天级到月级处置，两条时间线独立，各有各的责任人**。附带的收获是，分级之后每一档都变得可辩护——当业务再来要求"能不能晚点禁用"，回答不再是"不行，流程如此"，而是"T+0 那一档不能动，因为那是攻击面；T+1 天那一档可以谈，我们看看你的交接需要多久"。**可谈判的控制比不可谈判的控制活得久。**

## 14.2.9 度量

| 指标 | 定义 | 参考目标 | 说明 |
|------|------|---------|------|
| Day-1 就绪率 | 到岗当日可完成首个任务的新员工比例 | > 98% | 唯一业务会主动关注的指标 |
| 离职 T+0 达成率 | 会话与特权在事件后 5 分钟内完成撤销的比例 | 100% | 未达成需逐例复盘 |
| 离职全链完成时长 P95 | 从 HR 事件到全部档位完成 | < 24 小时 | 长尾通常来自未接 SSO 的应用 |
| 转岗权限净变化 | 转岗后 60 天权限数相对转岗前的变化 | 中位数 ≤ 0 | 若持续为正，说明回收机制未生效 |
| 供给失败率 | 失败的供给动作 ÷ 总动作数 | < 0.5% 且全部有工单 | 关注绝对值而非仅看比率 |
| 孤儿账号存量 | 无法关联身份的启用账号数 | 持续下降 | 分母口径见 14.1.5 |
| 撤销闭环时长 | 从审阅或事件决定撤销到权限实际消失 | P95 < 48 小时 | 与 14.5 共用同一指标 |

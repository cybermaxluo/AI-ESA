# 14.6　特权访问管理（PAM）

一份让人安心的报表：特权账号纳管率 100%，1,287 个特权账号全部进入保险箱，密码 7～30 天自动轮换，所有 SSH 与 RDP 会话强制经过代理并全程录像，单月录制 3,400 余次会话。

同一个月的红队演练结论：从一台普通员工工作站出发，4 小时 20 分钟拿到域管理员权限，全程未接触 PAM 系统。路径是——工作站本地管理员密码全域复用（不在 PAM 纳管范围，因为"本地账号不算特权账号"），横向移动到一台运维工作站；该工作站上有一个配置管理工具的 API 令牌（不在 PAM 纳管范围，因为"那是自动化凭据"）；用它向数百台服务器下发命令；其中一台是备份服务器，备份服务账号在域中拥有高权限（不在 PAM 纳管范围，因为"服务账号由应用团队管理"）。

**报表没有说谎，它只是回答了一个错误的问题。** 分母是"我们已知的特权账号"，而攻击者用的是分母之外的东西。

这一节的核心判断有三条：**纳管率的分母通常是错的**（14.6.2）；**PAM 管得住入口，管不住入口之后**（14.6.6）；**零常驻权限比会话录制更能降低风险，但它需要先解决审批时延**（14.6.4、14.6.8）。

关于 PAM 的平台选型、部署拓扑与合规映射，[5.2.3](../../第02部分_技术架构与基础设施安全/第05章_云安全架构/5.2_云身份与访问管理.md) 与 [8.5](../../第03部分_数据安全与隐私/第08章_数据安全/8.5_数据访问控制.md) 已有覆盖，本节不重复，只处理它们没有展开的部分：特权的边界定义、零常驻权限的工程实现、以及破玻璃账号的设计。

## 14.6.1 先定义特权，再谈管理

"特权账号"这个词在多数企业的实际含义是"名字里有 admin 的账号"。这个定义会漏掉一半以上的实际特权。

可操作的判据是能力而非命名——满足以下任意一条即为特权：

1. **能授予或修改权限**（包括给自己）。
2. **能改变或删除审计记录**（包括关闭日志、修改保留策略）。
3. **能绕过访问控制读取全量数据**（备份、数据库超级用户、存储层直读）。
4. **能影响关键系统的可用性**（批量重启、删除资源、修改网络策略）。

按这个判据重新盘点，会浮现出大量**能力等价的"影子特权"**：

| 影子特权 | 为什么是特权 | 通常的归属 |
|---------|------------|----------|
| 服务台密码/MFA 重置权 | 可接管任意账号，等价于任意账号的权限 | IT 服务台，通常不纳管 |
| 应用管理员（可加应用凭据） | 可为高权限应用添加新凭据并以应用身份行动 | 应用团队 |
| 条件访问 / 认证策略管理员 | 可为自己开一个绕过所有认证要求的口子 | 身份团队 |
| 备份管理员 | 可读取全量数据，且可从备份恢复出凭据 | 基础设施团队 |
| 终端管理平台管理员 | 可向全部终端下发任意代码 | 终端团队 |
| CI/CD 流水线维护者 | 可修改构建产物并以部署身份访问生产 | 研发团队 |
| 虚拟化 / 云控制台管理员 | 可绕过操作系统层直接接管虚拟机 | 云平台团队 |
| 目录中的 ACL 特权（可改 DACL、可重置密码） | 无需组成员资格即可提权，见 14.7 | 无人负责 |

**判断：影子特权的数量通常超过命名特权。** 而它们的共同特征是"归属于某个业务团队，不被认为是安全问题"。把这张表在企业内填一遍，是启动 PAM 项目最有价值的第一步——它同时定义了范围和利益相关方。

## 14.6.2 纳管：分母、深度与闭环

### 分母怎么算

纳管率的分母必须是**持续发现的特权总量**，而不是台账上的已知数量。这意味着发现必须是一个常设的自动化任务，覆盖至少七类来源：

- 目录服务：高权限组成员、具备危险 ACL 的主体、`adminCount=1` 的残留对象（见 14.7）。
- 各类操作系统：本地管理员组成员、sudoers 配置、有 SSH 授权密钥的账号。
- 数据库：超级用户、具备 `GRANT` 能力的角色、直连的应用账号。
- 云平台：具备管理策略的用户与角色、可提权的策略组合（参见 5.2 的 CIEM 能力）。
- SaaS 应用：各应用的管理员角色成员。
- 网络与安全设备：本地管理账号、TACACS/RADIUS 外的后门账号。
- 自动化与流水线：配置管理工具、编排平台、构建系统的凭据。

发现结果与台账的差额，就是纳管率的真实缺口。**每次发现产出的新增项数量，本身就是一个健康指标**——如果每月都能发现几十个新的未纳管特权，说明创建入口没有被管住，需要回到源头治理（谁能创建特权账号、创建时是否强制登记）。

### 纳管深度：四档，不是一档

"纳管"不是二元状态。四档深度的成本与收益差异极大，应当按资产等级选择而非一刀切：

| 深度 | 含义 | 成本 | 适用 |
|------|------|------|------|
| D1 登记 | 台账中有记录、有责任人、有到期日 | 极低 | 全部特权的最低要求 |
| D2 凭据托管 | 密码/密钥存入保险箱并自动轮换，人工取用留痕 | 低 | 无法改造的遗留系统、网络设备 |
| D3 会话代理 | 访问必须经代理，全程录制，凭据不落到操作者手中 | 中 | 服务器、数据库、云控制台 |
| D4 零常驻权限 | 平时无权限，按需临时授予并自动回收 | 高 | Tier 0、生产变更、高价值数据 |

选择深度时有一条常被忽略的约束：**深度越高，对目标系统的兼容性要求越高**。D3 需要目标支持可代理的协议，D4 需要目标的授权模型支持动态授予与回收。一批老旧设备（工业控制终端、专用一体机、部分网络设备）永远只能停在 D2，这不是失败，而是应当被显式记录并接受的现状——把它们与"尚未纳管"混在一起统计，会让指标失去指导意义。

**判断：D1 的价值被严重低估。** 很多企业在 D3/D4 上投入巨大，却有几百个特权连"是谁的、还需不需要"都答不上来。先把 D1 做到 100% 覆盖（这只需要一张有强制字段的台账和一个发现任务），再逐级加深，比一开始就上 D3 更快见效。

### 纳管闭环

发现之后的处置必须有时限，否则发现清单会变成一份不断增长、无人处理的报表：

```yaml
# 特权发现与纳管闭环策略（示例）
privileged_discovery:
  scan_frequency_hours: 24
  sources: [directory, endpoints, databases, cloud, saas, network, cicd]
  classification_rules:
    - if: "member_of_group in ['Domain Admins','Enterprise Admins','Schema Admins']"
      tier: tier0
    - if: "can_reset_password_of_tier0 == true"
      tier: tier0        # 能力等价：能重置 Tier 0 密码的即为 Tier 0
    - if: "cloud_policy in ['AdministratorAccess','Owner']"
      tier: tier1
    - if: "is_local_admin == true and host_tier == 'tier1'"
      tier: tier1

  onboarding_sla_days:
    tier0: 3
    tier1: 14
    tier2: 30

  required_metadata:
    - owner_person_id
    - business_purpose
    - expires_on
    - approved_by
  reject_if_missing_metadata: true

  escalation:
    unmanaged_over_sla: notify_owner_and_ciso
    tier0_unmanaged_over_sla: block_account
    # tier0 超期直接禁用：这条需要高层背书，
    # 但它是唯一能让 Tier 0 纳管真正闭环的机制
```

怎么读这段策略：`can_reset_password_of_tier0` 这条规则实现了上一节的"能力等价"判据——它把服务台与目录 ACL 特权自动归入 Tier 0，而不依赖人工判断。`reject_if_missing_metadata: true` 意味着**没有责任人和到期日的特权账号无法完成纳管**，从而把元数据缺失变成一个必须解决的阻塞项而非可以拖延的待办。`tier0_unmanaged_over_sla: block_account` 是整份策略里唯一带强制力的一条，也是最需要事先取得管理层书面授权的一条。

## 14.6.3 组件与它们的局限

PAM 平台的四个核心组件在 5.2.3 与 8.5.5 已有描述，这里只补充实践中的局限，它们决定了架构上还需要补什么。

| 组件 | 解决什么 | 局限 |
|------|---------|------|
| 密码保险箱 | 凭据集中、轮换、取用留痕 | 轮换会打断依赖静态密码的应用；无法覆盖不支持密码修改的老旧设备 |
| 会话代理 | 凭据不落地、全程录制 | 只覆盖它支持的协议；进入目标机器后的行为不可见 |
| 凭据注入 | 操作者永不知晓密码 | 依赖客户端或浏览器插件，绕过路径多 |
| 应用密码管理（AAPM） | 应用不再硬编码密码 | 需改造应用；改造成本常导致长期例外 |
| 特权提升 | 用完即收 | 见 14.6.4 的时延与缓存问题 |

三个必须提前规划的工程约束：

**轮换与应用的冲突。** 密码轮换打断应用连接，是 PAM 项目最常见的生产事故。正确顺序是：先把应用改造为动态获取（AAPM 或 Vault，见 14.8），再开启轮换；而不是先开轮换再处理报障。对无法改造的应用，用"轮换时同步更新配置并重启"的编排任务，且必须在维护窗口内执行。

**会话代理的单点。** 所有特权访问都经过代理，代理故障即等于全部运维中断。需要多活部署、跨可用区、且**必须有一条不依赖 PAM 的应急访问路径**——这条路径就是破玻璃（14.6.7）。没有它，PAM 的可用性会成为业务连续性的最大单点。

**性能与体验。** 会话代理引入的延迟如果让工程师明显感到卡顿，绕过就会开始出现。上线前应实测交互延迟，超过 150 毫秒的额外往返会被明显感知（示例口径）。**体验问题在 PAM 项目中不是舒适度问题，是控制有效性问题。**

## 14.6.4 JIT 与零常驻权限：工程实现与它的坑

零常驻权限（Zero Standing Privilege，ZSP）的主张很简单：**平时没有人拥有特权，需要时临时产生、用完即消失**。它把攻击者可利用的窗口从"永远"压缩到"几小时"，是本节收益最大的控制。

三种实现方式，坑各不相同：

| 实现 | 做法 | 主要坑 |
|------|------|-------|
| 临时组成员 | 把用户临时加入特权组，到期移除 | 令牌与票据缓存导致变更不立即生效，见下 |
| 临时角色分配 | 云平台按需分配角色，带 TTL | 最终一致性延迟；跨账号/跨租户的传播时间不确定 |
| 即时账号创建 | 需要时创建一个一次性账号，用完删除 | 审计关联难（要能把一次性账号映射回自然人）；创建本身需要高权限 |

**最容易踩的坑：组成员变更不立即生效。** 在 Windows 域环境中，用户的组成员资格被写入 Kerberos 票据（TGT/PAC），把用户加入特权组后，其现有票据不包含新组，因此新权限**在重新登录或票据刷新前不会生效**；反过来更危险——**把用户移出特权组后，其手中已签发的票据仍然携带旧组信息，权限在票据有效期内继续可用**（默认可达 10 小时）。这意味着朴素实现的"到期移除"其实并没有到期，攻击窗口比设计的长得多。

对策有三层：授予后强制重新登录（解决生效问题）；回收时同时终止该用户的活动会话并使票据失效（解决回收问题）；把 JIT 授权时长设置为**明显短于票据生命周期**并配合会话终止，而不是依赖组变更本身。云平台上的对应问题是最终一致性——角色回收后短时间内旧凭据可能仍然有效，因此回收动作必须包含"撤销活动会话/令牌"这一步。

```python
"""JIT 特权提升服务：申请-审批-授予-到期回收，含幂等与回收补偿。

工程要点：
1. 授予与回收都是幂等的，可安全重放。
2. 回收失败进入补偿队列并升级，绝不静默失败——回收失败等于常驻权限。
3. 回收动作包含"终止活动会话"，否则票据/令牌缓存会让回收形同虚设。
4. 全流程写审计事件，审批理由与关联工单是合规证据。
"""
import uuid
from dataclasses import dataclass, field
from datetime import datetime, timedelta, timezone
from enum import Enum
from typing import Callable, Dict, List, Optional


class GrantState(Enum):
    REQUESTED = "requested"
    APPROVED = "approved"
    ACTIVE = "active"
    EXPIRED = "expired"
    REVOKE_FAILED = "revoke_failed"
    DENIED = "denied"


@dataclass
class JitPolicy:
    role: str
    max_duration_minutes: int
    require_approval: bool
    require_ticket: bool
    approver_group: str
    max_active_grants: int = 3          # 同一角色的并发授权上限
    forbid_self_approval: bool = True


@dataclass
class JitGrant:
    grant_id: str
    person_id: str
    role: str
    reason: str
    ticket_ref: Optional[str]
    requested_at: datetime
    duration_minutes: int
    state: GrantState = GrantState.REQUESTED
    approved_by: Optional[str] = None
    activated_at: Optional[datetime] = None
    expires_at: Optional[datetime] = None
    revoke_attempts: int = 0
    audit: List[Dict[str, str]] = field(default_factory=list)

    def log(self, event: str, detail: str = "") -> None:
        self.audit.append({
            "ts": datetime.now(timezone.utc).isoformat(),
            "event": event,
            "detail": detail,
        })


class JitService:
    def __init__(
        self,
        policies: Dict[str, JitPolicy],
        grant_fn: Callable[[str, str], bool],
        revoke_fn: Callable[[str, str], bool],
        kill_sessions_fn: Callable[[str], bool],
    ):
        self.policies = policies
        self.grant_fn = grant_fn
        self.revoke_fn = revoke_fn
        self.kill_sessions_fn = kill_sessions_fn
        self.grants: Dict[str, JitGrant] = {}

    def request(self, person_id: str, role: str, minutes: int,
                reason: str, ticket_ref: Optional[str] = None) -> JitGrant:
        policy = self.policies[role]
        if minutes > policy.max_duration_minutes:
            minutes = policy.max_duration_minutes
        if policy.require_ticket and not ticket_ref:
            raise ValueError("ticket reference required for this role")

        active = [
            g for g in self.grants.values()
            if g.role == role and g.state == GrantState.ACTIVE
        ]
        if len(active) >= policy.max_active_grants:
            raise RuntimeError("concurrent grant limit reached for role")

        grant = JitGrant(
            grant_id=str(uuid.uuid4()), person_id=person_id, role=role,
            reason=reason, ticket_ref=ticket_ref,
            requested_at=datetime.now(timezone.utc), duration_minutes=minutes,
        )
        grant.log("requested", f"role={role} minutes={minutes}")
        self.grants[grant.grant_id] = grant
        if not policy.require_approval:
            self.approve(grant.grant_id, approver="auto-policy")
        return grant

    def approve(self, grant_id: str, approver: str) -> JitGrant:
        grant = self.grants[grant_id]
        policy = self.policies[grant.role]
        if policy.forbid_self_approval and approver == grant.person_id:
            grant.state = GrantState.DENIED
            grant.log("denied", "self-approval forbidden")
            return grant
        if grant.state is not GrantState.REQUESTED:
            return grant                      # 幂等：重复审批不产生副作用

        grant.state = GrantState.APPROVED
        grant.approved_by = approver
        grant.log("approved", f"by={approver}")
        return self.activate(grant_id)

    def activate(self, grant_id: str) -> JitGrant:
        grant = self.grants[grant_id]
        if grant.state is GrantState.ACTIVE:
            return grant
        if not self.grant_fn(grant.person_id, grant.role):
            grant.log("activate_failed")
            raise RuntimeError("grant backend failed")
        now = datetime.now(timezone.utc)
        grant.state = GrantState.ACTIVE
        grant.activated_at = now
        grant.expires_at = now + timedelta(minutes=grant.duration_minutes)
        grant.log("activated", f"expires_at={grant.expires_at.isoformat()}")
        return grant

    def revoke(self, grant_id: str, reason: str = "expired") -> bool:
        """回收：先移除权限，再终止会话。两步都成功才算回收完成。"""
        grant = self.grants[grant_id]
        if grant.state in (GrantState.EXPIRED, GrantState.DENIED):
            return True                       # 幂等
        grant.revoke_attempts += 1
        removed = self.revoke_fn(grant.person_id, grant.role)
        # 关键：不终止会话，票据与令牌缓存会让权限在有效期内继续可用
        killed = self.kill_sessions_fn(grant.person_id)
        if removed and killed:
            grant.state = GrantState.EXPIRED
            grant.log("revoked", reason)
            return True
        grant.state = GrantState.REVOKE_FAILED
        grant.log("revoke_failed",
                  f"removed={removed} killed={killed} attempt={grant.revoke_attempts}")
        return False

    def sweep(self, now: Optional[datetime] = None) -> Dict[str, int]:
        """周期任务：回收到期授权，重试失败回收，并对超限失败升级。"""
        now = now or datetime.now(timezone.utc)
        stats = {"revoked": 0, "failed": 0, "escalated": 0}
        for grant in list(self.grants.values()):
            due = grant.expires_at is not None and now >= grant.expires_at
            if grant.state is GrantState.ACTIVE and due:
                stats["revoked" if self.revoke(grant.grant_id) else "failed"] += 1
            elif grant.state is GrantState.REVOKE_FAILED:
                if self.revoke(grant.grant_id, reason="retry"):
                    stats["revoked"] += 1
                elif grant.revoke_attempts >= 5:
                    grant.log("escalated", "revoke failed 5 times; manual action")
                    stats["escalated"] += 1
                else:
                    stats["failed"] += 1
        return stats
```

怎么读这段代码：`revoke` 要求 `removed` 与 `killed` 同时成功才置为 `EXPIRED`，这是本段最重要的设计——**只移除组成员而不终止会话的回收是假回收**。`REVOKE_FAILED` 是一个独立状态而不是简单的错误返回，因为它对应着一个真实的风险敞口（权限仍然存在），必须持续重试并在超限后人工介入。`max_active_grants` 限制同一角色的并发授权数，防止一次事故中攻击者用被盗账号批量申请。`forbid_self_approval` 看似基础，但在实现中经常被"临时放开以便应急"而永久失效，因此把它放在策略而非代码判断里，让它的关闭成为一个有记录的配置变更。

### 审批设计：不是所有申请都需要人

JIT 的审批环节最容易复制访问审阅的失败——审批人每天面对几十条申请，全部批准，于是 JIT 退化成"多点一次鼠标的常驻权限"。避免它需要三条设计：

**分层审批。** 按目标资产等级决定是否需要人：Tier 2 资产在工作时间内、有关联工单、时长不超过 2 小时的申请可自动批准；Tier 1 需一位审批人；Tier 0 需双人且不得同组。把大部分申请自动化掉，才能让人真正审视少数关键申请。

**审批要给依据。** 与 14.4.6 同理，申请里应带上：申请人近 30 天的同类申请次数、是否有关联工单及其内容摘要、申请的角色最近一次被谁使用、以及该申请是否偏离此人的历史模式。没有这些，审批人只能看到"某某申请 DBA-PROD 2 小时"，无从判断。

**审批也要被审阅。** 每月抽样复核 JIT 审批记录，重点看两类：批准了但会话中未执行任何操作的（说明申请是"以防万一"，应缩短时长或改为按需）、以及理由字段填写为"日常运维""处理问题"这类无信息内容的（说明理由字段没有起作用，需要改为选择具体场景）。

**生产坑：JIT 授权的"到期"没有真正到期。** 除了前面说的票据缓存问题，还有三处常见的静默失效：目标系统缓存了授权决策（应用侧的权限缓存 TTL 可能长达数小时）；用户在授权期内建立的长连接（数据库会话、SSH 会话）不会因权限回收而中断；以及授权期内用户为自己创建了其他访问路径（新增本地账号、写入授权密钥、注册新的服务凭据）。第三条最危险，因为它把一次限时授权变成了永久访问。对应的检查动作是：**回收后比对该主机/系统上的账号与凭据清单是否发生变化**，这项检查可以自动化，成本很低却能发现真正的问题。

### ZSP 成熟度阶梯

下表的 **M0–M4** 是成熟度刻度（M 取 Maturity，全书成熟度模型统一用它），描述的是特权授予方式随时间演进到了哪一步；它与本节前面按目标系统能力划分的纳管深度 D1–D4 是两条正交的轴，也与 17.1.2 的 AI 自主等级 L0–L5 没有任何换算关系。

| 阶段 | 状态 | 典型时长 |
|------|------|---------|
| M0 | 特权常驻，无时限 | 起点 |
| M1 | 特权常驻，但有台账与定期审阅 | 3～6 个月 |
| M2 | 特权带有效期，到期需续期 | 6～12 个月 |
| M3 | JIT：默认无权限，按需申请并自动回收 | 12～18 个月 |
| M4 | ZSP：连账号都是临时的，特权组常态为空 | 18 个月以上 |

多数企业在 M3 就能拿到绝大部分收益。M4 的边际收益递减而复杂度陡增（尤其是审计关联与应急场景），**不建议把 M4 作为普遍目标，只对 Tier 0 追求 M4**。

## 14.6.5 会话录制：它的真实用途

会话录制常被当作检测手段推销，但它在实践中的价值排序是：**威慑 > 取证 > 合规 >> 检测**。

原因很直接：没有人会看录像。一个月 3,400 次会话，即使每次只有 5 分钟，也是 280 小时的视频。除非发生事件或触发告警，否则录像只是躺在存储里。把录像当作主要检测手段的企业，通常在第一次事件调查时才发现两个问题：**检索不了**（只能按用户和时间找，无法按命令内容搜索），以及**没有覆盖**（真正出事的那条路径不走代理）。

因此录制方案的设计要点应当围绕它的真实用途：

- **结构化优先于视频。** 命令行文本、执行的 SQL、传输的文件名这些结构化数据，比视频有用得多——可检索、可告警、体积小两三个数量级。视频作为补充用于图形界面操作。
- **必须可检索。** 至少支持按命令关键字、按目标主机、按文件传输行为检索。不可检索的录像在取证时价值有限。
- **存储成本要提前算。** 以文本审计为主、视频按需保留的方案，成本可以控制在纯视频方案的很小一部分；若合规要求视频保留 5 年，需要在项目预算中单列并明确分层存储策略（热存 90 天、冷存其余）。

存储估算可以用一个简单模型先做量级判断（下列单价与体积均为示例口径，非行业基准，须以实测替换）：

| 录制形态 | 单会话体积（30 分钟） | 月增量（3,400 次会话） | 5 年留存（含压缩与冷存） |
|---------|-------------------|---------------------|---------------------|
| 纯文本命令审计 | 约 0.2 MB | 约 0.7 GB | 约 40 GB |
| 文本 + 元数据 + 关键帧截图 | 约 5 MB | 约 17 GB | 约 1 TB |
| 全程视频（图形会话） | 约 120 MB | 约 400 GB | 约 24 TB |

三档之间相差两个数量级，而它们在取证价值上的差距远没有这么大——**绝大多数事件调查依赖的是命令与文件传输记录，而不是画面**。因此推荐的默认策略是：命令与元数据全量长留、视频仅对图形会话录制且短期留存（如 90 天），超期后仅在有事件关联时导出归档。这个决定应当在项目立项时做出，因为它直接影响存储采购规模。
- **实时拦截要克制。** 对 `rm -rf /`、`DROP DATABASE`、`shutdown` 这类命令做实时阻断听起来很好，但误伤代价高且绕过容易（命令可以被拼接、编码、写进脚本）。更合适的定位是**告警而非阻断**，把阻断留给极少数不可逆操作。
- **合规与隐私。** 会话录制属于员工监控，在多数司法辖区需要事先告知、在部分辖区需要员工代表机构同意。这件事必须在项目启动阶段由法务与 HR 确认，而不是上线后补。录像的访问本身也应是受控且被审计的——**能随意调看他人会话录像的管理员，本身就是一个特权**。

## 14.6.6 堡垒机管得住入口，管不住入口之后

这是特权访问架构里最容易被忽略的边界。

会话代理（堡垒机）在用户与目标主机之间建立了一道关卡，但一旦会话建立，用户在目标主机内部的行为——本地提权、读取内存中的凭据、建立反向通道、修改本地账号——对堡垒机而言基本不可见（它看到的是终端输出流，而非系统调用）。更重要的是，**大量特权访问路径根本不经过堡垒机**：

| 绕过路径 | 说明 |
|---------|------|
| 云控制台与 API | 浏览器直接登录、CLI 直接调用，与 SSH/RDP 无关 |
| Kubernetes | `kubectl exec` 进入容器，走 API Server 而非堡垒机 |
| 数据库客户端 | 直连数据库端口，除非网络层强制阻断 |
| 配置管理与编排 | Ansible/Salt/编排平台以自己的凭据推送命令 |
| CI/CD 部署 | 流水线以部署身份变更生产 |
| 监控与备份 Agent | 常驻高权限，且可执行任意命令 |
| 厂商远程支持通道 | 供应商自带的远程接入工具 |

补位手段有三层：**网络层**强制目标系统只接受来自代理的管理流量（这一条能消灭大部分绕过路径，但需要与网络团队协作，见本部分网络与终端安全章）；**主机层**用 EDR 与系统审计（Linux 的 `auditd`/`sudo` 日志、Windows 的进程创建与特权使用事件）覆盖"入口之后"；**身份层**把上表中每一条路径的凭据都纳入 14.6.2 的发现范围，并按能力判据归类为特权。

**判断：如果只能做一件事，先做网络层强制。** 因为它把"绕过"从"可能"变成"不可能"，而其余两层都只是提高可见性。

主机层的"入口之后"可见性，需要明确采集哪些事件。下表是一份最小集合，它覆盖了特权会话建立后最值得关注的行为：

| 平台 | 事件 | 关注点 |
|------|------|-------|
| Windows | 4624（登录，含登录类型）/ 4625 | 类型 3 网络登录与类型 10 远程交互登录的来源是否为代理 |
| Windows | 4672 特殊权限分配给新登录 | 谁在何时获得了敏感权限，是特权使用的主索引 |
| Windows | 4688 进程创建（含命令行） | 必须开启命令行记录，否则该事件价值大减 |
| Windows | 4720/4728/4732 账号与组变更 | 会话中新建账号或自我提权 |
| Windows | 7045 服务安装 | 持久化的经典手法 |
| Linux | `auditd` execve 规则 | 记录执行的命令与参数 |
| Linux | `sudo` 日志与 `pam` 认证日志 | 提权行为与失败尝试 |
| Linux | `authorized_keys` 文件变更审计 | 会话中植入后门密钥 |
| Linux | 新增 setuid 文件、cron 变更 | 持久化 |

这份清单的意义不在于完整（完整清单见检测工程相关内容，[11.3](../../第04部分_安全运营与防御能力/第11章_安全运营/11.3_威胁检测工程.md) 有系统展开），而在于它划出了 PAM 与终端检测的责任边界：**PAM 负责"谁进来了、带着什么权限"，主机侧负责"进来之后做了什么"。** 两侧数据必须能通过会话标识或时间窗关联，否则调查时会卡在"这条 root 操作对应哪一次 JIT 授权"这个问题上——建议在 JIT 授权时把授权 ID 写入目标主机的一条审计标记事件，这是一个实现成本很低但调查时价值极高的小设计。

## 14.6.7 破玻璃账号：设计比使用更重要

破玻璃（break-glass）账号是当身份基础设施本身失效时的最后手段——IdP 宕机、条件访问策略配置错误把所有人锁在门外、PAM 平台不可用、联邦信任被破坏。**它是必需品**，因为没有它，一次策略误配就可能演变成持续数小时无人能修复的全局中断。

但它同时是一个天然的后门：不受条件访问约束、通常不启用常规 MFA、密码长期不变、知道的人不多因此也没人监督。设计不当时，它就是攻击者最想要的那把钥匙。

### 设计检查表

| 维度 | 建议 | 理由 |
|------|------|------|
| 数量 | 2～4 个 | 1 个是单点，多于 4 个无法有效监控 |
| 认证路径 | 彼此不同，且不依赖将要救援的组件 | 依赖 IdP 的破玻璃账号在 IdP 故障时无用 |
| 凭据形态 | 长随机密码（不少于 24 字符）；若必须有第二因素，用独立硬件密钥而非手机 App | 手机 App 依赖注册流程与网络 |
| 保管 | 密码分片保管，至少两人各持一部分；离线保存于保险柜 | 防止单人滥用 |
| 策略排除 | 从条件访问中排除，但这是唯一允许的排除项 | 见 14.3.6 |
| 监控 | 任何一次登录立即告警到多人（含 CISO），且告警链路不依赖被救援的系统 | 使用必然被发现 |
| 使用流程 | 双人在场、事前报备（紧急情况可事后 1 小时内补）、全程记录 | 可追责 |
| 事后动作 | 24 小时内轮换密码、复盘、更新演练记录 | 防止一次使用变成长期启用 |
| 演练 | 每季度一次，验证可登录、告警触发、事后轮换全流程 | 未演练的破玻璃在真正需要时通常不可用 |
| 有效性检查 | 每月自动校验账号未被禁用、未被策略覆盖、密码未过期 | 防止静默失效 |

### 什么情况才算"该用"

破玻璃滥用的根源，往往是没有人写清楚它的适用场景。一份明确的清单能消除大部分模糊地带：

| 场景 | 是否适用 | 说明 |
|------|---------|------|
| IdP 完全不可用，无人能登录 | 是 | 典型场景 |
| 条件访问策略误配导致全员被锁 | 是 | 且需要用它来回滚策略 |
| 最后一位全局管理员离职或账号损坏 | 是 | 需同时启动管理员补位流程 |
| 联邦信任被破坏或证书过期 | 是 | 通常伴随大范围认证失败 |
| PAM 平台故障，无法取用凭据 | 视情况 | 若目标系统仍可正常登录则不适用 |
| 需要执行一个审批很慢的变更 | 否 | 这是流程问题，走 14.6.8 的故障模式通道 |
| 值班人员手上没有权限 | 否 | 说明值班授权设计有缺陷，应修复根因 |
| 半夜没人审批 | 否 | 应通过预授权或自动审批规则解决 |

后三行是最常见的滥用理由，它们的共同点是：**问题的真实原因在别处，而破玻璃恰好是当下最省事的解法**。每一次以这类理由使用破玻璃，都应当在复盘中产出一条对应的流程改进项——否则同样的理由会在下个月再次出现。

**最常见的两种失效**：一是**静默失效**——某次策略调整不小心把破玻璃账号也纳入了 MFA 要求，而没有人测试过，直到真正需要时才发现登不进去；二是**滥用**——破玻璃账号因为"方便"（不受策略限制、不用等审批）被拿来做日常运维，几个月后它的密码被十几个人知道，成为一个完全不受控的超级账号。第一种靠每月自动检查，第二种靠告警加问责：**每一次使用都必须有人在 24 小时内解释为什么用它。**

### 检测规则

破玻璃账号的登录必须是高优先级告警，且规则要覆盖"登录成功"与"登录失败"两种情况——失败同样重要，它意味着有人在尝试。

```kusto
// 破玻璃账号任何认证活动均告警（Microsoft Sentinel / Entra ID 日志）
let BreakGlassUPNs = dynamic([
    "breakglass-01@example.com",
    "breakglass-02@example.com"
]);
union SigninLogs, AADNonInteractiveUserSignInLogs
| where TimeGenerated > ago(1h)
| where tolower(UserPrincipalName) in~ (BreakGlassUPNs)
| extend Outcome = iff(ResultType == "0", "Success", "Failure")
| project
    TimeGenerated,
    UserPrincipalName,
    Outcome,
    ResultType,
    ResultDescription,
    IPAddress,
    Location,
    AppDisplayName,
    ClientAppUsed,
    UserAgent,
    CorrelationId
| order by TimeGenerated desc
```

这条规则有三个细节值得注意：`union` 同时覆盖交互式与非交互式登录表——**只查 `SigninLogs` 会漏掉以刷新令牌形式发生的访问**；`in~` 是大小写不敏感匹配，避免因大小写差异漏报；不过滤 `ResultType`，因为失败尝试与成功登录同样需要告警。告警的送达链路要独立于企业邮件（邮件系统可能正是故障对象），建议同时走短信或独立的值班通知通道。

## 14.6.8 失败叙事：JIT 审批 15 分钟，然后在 P1 故障时被绕过

我们的第一版 JIT 设计得很规范：生产环境管理员权限全部取消常驻，需要时申请，审批人是值班主管，审批 SLA 15 分钟，授权时长 2 小时，到期自动回收。上线后的日常运行数据很漂亮——平均审批时长 6 分钟，日均申请 40 余次，常驻管理员数从 87 降到 0。

三个月后一次 P1 故障：核心支付链路中断，工程师需要立即登录数据库。他提交 JIT 申请，值班主管当时正在故障指挥电话会议里，没看到审批通知。工程师等了 4 分钟，然后做了任何一个处在他位置的人都会做的事——他找到了那个"以防万一"留下来的共享账号，密码写在一份运维手册里。故障在 11 分钟后恢复。

事后复盘时，没有人认为这位工程师做错了。业务中断每分钟的损失远大于流程合规的价值，而我们的流程在最需要它的时刻恰好是最慢的。真正的问题是**我们设计了一个只在平时可用的控制**。

改造的方案是引入一条**故障模式通道**，而非缩短 SLA（那只是把问题推给审批人）：

- 预先定义一组"故障模式角色"，权限范围明确且小于完整管理员（只覆盖故障处置需要的操作，例如重启服务、查看日志、执行只读诊断，不含删除与配置变更）。
- 当存在生效中的 P1 事件单时，该角色的申请**自动批准**，授权时长 60 分钟，可续期一次。
- 全程录制，事后 24 小时内由安全与业务共同复盘每一次故障模式授权，并检查其操作是否超出故障处置范围。
- 若无关联的 P1 事件单，故障模式通道不可用——这条约束把"绕过"变成了可审计的、有前置条件的正常路径。

改造后的数据：故障模式通道每月被使用 2～5 次，无一次被发现越界操作；共享账号被彻底删除；工程师的反馈从"这个流程碍事"变成"至少它不拦我"（示例口径）。

留下的判断是：**任何在紧急情况下比绕过它更慢的控制，最终都会被绕过**。设计特权控制时，必须同时设计紧急路径——不是留一个不受控的后门，而是让紧急路径本身成为受控路径中最快的那一条。这与 14.0.4 里"第三层流程健康度会静默摧毁第一、第二层"是同一个道理。

## 14.6.9 度量

| 指标 | 定义 | 参考目标（示例口径） |
|------|------|------------------|
| 特权发现覆盖率 | 已接入发现的来源类别 ÷ 应覆盖类别 | 100%（七类来源） |
| 新发现未纳管特权数 | 每月新发现且未在 SLA 内纳管的数量 | 趋势向下；Tier 0 为 0 |
| 常驻特权账号数 | 无时限的特权授权数 | Tier 0 为 0；整体持续下降 |
| JIT 覆盖率 | 经 JIT 产生的特权会话 ÷ 特权会话总数 | > 90% |
| JIT 审批时延 P95 | 申请到可用 | < 10 分钟；故障模式 < 1 分钟 |
| 回收失败存量 | 处于 REVOKE_FAILED 状态的授权 | 0，且任何一条超过 1 小时即告警 |
| 会话代理绕过率 | 未经代理的特权登录 ÷ 特权登录总数 | < 2%，且每例可解释 |
| 破玻璃使用次数 | 每季度使用次数 | 0～1；每次必有复盘记录 |
| 破玻璃可用性检查 | 每月自动校验通过率 | 100% |

其中"会话代理绕过率"需要独立数据源才能计算——不能只用 PAM 自己的日志（它只知道经过它的那些），必须从目标系统侧统计登录事件再做差集。**用被审计对象自己的日志来度量审计覆盖率，是身份度量里最常见的循环论证。**

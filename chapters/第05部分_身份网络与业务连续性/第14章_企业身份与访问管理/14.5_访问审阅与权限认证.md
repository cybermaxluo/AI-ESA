# 14.5　访问审阅与权限认证

一次真实的季度访问审阅数据：参与审阅人 312 位，待审条目 41,700 条，完成率 98.4%，按期完成的审阅人占 94%，撤销条目 712 条——**撤销率 1.7%**。报表交给审计，审计接受，控制被评为有效。

再看一组同一次审阅的行为数据：审阅人的中位单条决策时间是 2.4 秒；有 47 位审阅人在一次会话中连续批准超过 200 条且中途没有任何一次拒绝；最快的一位在 6 分钟内处理完 483 条。**2.4 秒不足以读完一条权限的名称，更不足以判断它是否必要。**

这两组数据描述的是同一件事：审阅确实"完成"了，但审阅这个动作没有发生。这就是橡皮图章（rubber-stamping）——一个在几乎所有企业都存在、在几乎所有审计报告里都被标记为"控制有效"的失败模式。

本节的核心主张是：**访问审阅是一场需要被设计的组织战役，而不是一个可以配置的系统功能。** 工具能把条目发出去、把结果收回来，但决定审阅有没有价值的是四件工具之外的事——审阅什么（范围）、谁来审（审阅人）、他看到什么（决策依据）、以及决定之后发生了什么（闭环）。

---

## 14.5.1 先分清三个目的

访问审阅通常被要求同时满足三个目的，而这三个目的的最优手段并不相同。混在一起做，结果是三个都做不好。

| 目的 | 想回答的问题 | 最优手段 | 混淆后的后果 |
|------|------------|---------|------------|
| 撤销多余权限 | 谁有不该有的权限 | 数据驱动的定向审阅（未使用、超同侪、高危） | 被淹没在全量条目里 |
| 发现异常与内鬼 | 有没有人的权限模式不正常 | 持续分析 + 例外调查，而非人工逐条 | 人眼不可能从四万条里发现异常 |
| 产生合规证据 | 我们是否按制度履行了复核 | 全量、留痕、可追溯 | 成为唯一目的后必然橡皮图章 |

**判断：如果一次审阅的唯一驱动力是合规，它必然退化为橡皮图章。** 因为在合规目的下，"完成"就是全部要求，而拒绝任何一条都会给审阅人带来额外工作（解释、沟通、可能的冲突）。理性的审阅人会选择全部批准，这个行为完全符合他被给定的激励。

改变的办法不是加强培训，而是改变激励与信息：让撤销变成低成本动作（撤错了可以自助恢复）、让批准变成需要理由的动作（高风险条目必须填写业务理由）、让审阅质量变得可观测（抽样复核并反馈给审阅人的上级）。

## 14.5.2 战役设计：六个必须提前定的参数

把一次审阅当作战役来设计，需要在启动前定下六个参数。这些参数一旦在启动后再改，整场战役的数据就无法与上一轮对比。

**参数一：范围切分。** 三种切法各有适用——按应用切（适合有明确应用负责人的场景，便于集中沟通）、按人群切（适合组织调整后的定向清理）、按风险切（只审高危权限，条目量最小、效率最高）。**不要一次性切全量**，尤其是第一次。第一次的目标是把流程跑通并建立口碑，不是覆盖率。

**参数二：审阅人。** 三种选择的失效模式在 14.4.6 已列出。审阅场景下还要加一条：**必须解决"审阅人已离职/已转岗"的情况**，否则会出现条目发给一个不再相关的人、他随手全批的局面。启动前用 HR 数据校验一次审阅人有效性，是成本极低但常被跳过的一步。

**参数三：时间窗。** 经验上 2 周优于 4 周（示例口径）。4 周的窗口会让所有人把它推到最后三天，届时决策质量与 2 周时无异，但项目周期翻倍。配套要有明确的提醒节奏（启动日、第 5 天、第 9 天、截止前 1 天）与升级路径（截止后未完成，上报其上级）。

**参数四：快照还是实时。** 审阅必须基于某个时点的权限快照，否则审阅期间的权限变更会导致"审阅了一个已经不存在的权限"或"新授的权限未被审阅"。快照必须留存，它是审计证据链的起点。同时要处理快照后的新增授权——建议在审阅期结束后自动纳入下一轮，而不是插入本轮。

**参数五：默认值。** 这是最重要的一个参数，见 14.5.3。

**参数六：撤销执行方式。** 决定"撤销决策产生后由谁执行、多久执行、失败怎么办"。这个参数必须在启动前定，因为它决定了审阅数据要携带哪些字段（目标系统、权限标识、执行接口）。见 14.5.5。

```yaml
# 访问审阅战役配置（示例）
campaign:
  id: AR-2026Q3-HIGHRISK
  name: "2026Q3 高危权限定向审阅"
  scope:
    mode: risk_based
    include_entitlements_tagged: ["privileged", "financial_impact", "restricted_data"]
    exclude_entitlements_tagged: ["birthright"]
    include_population: ["employee", "contractor"]
  reviewers:
    primary: application_business_owner
    fallback: line_manager
    validate_reviewer_active: true
    forbid_self_review: true
  schedule:
    snapshot_at: "2026-07-01T00:00:00Z"
    starts_at: "2026-07-06T00:00:00Z"
    ends_at: "2026-07-20T23:59:59Z"
    reminders_on_days: [1, 5, 9, 13]
    escalate_to_manager_after_days: 15
  decision:
    default_when_no_action: revoke
    require_justification_for: ["approve_privileged", "approve_sod_conflict"]
    allow_bulk_approve: false
    allow_bulk_revoke: true
  prefilter:
    hide_if_used_within_days: 30
    hide_if_peer_coverage_above: 0.85
    always_show_if_tagged: ["privileged", "sod_conflict"]
  quality_control:
    sample_rate_for_qa: 0.05
    rubber_stamp_flag_seconds: 5
    qa_reviewer_group: grp-iam-governance
```

怎么读这段配置：`default_when_no_action: revoke` 与 `allow_bulk_approve: false` / `allow_bulk_revoke: true` 是一组刻意的不对称设计——**让"收权"比"留权"更省力**。这是行为设计而非技术设计，效果远大于任何培训。`prefilter` 的三条规则把条目量压到可读范围：最近 30 天用过的隐藏（说明确实在用）、同岗位 85% 以上的人都有的隐藏（说明它本质上是出生权限，应走 14.4.1 重新分类而不是逐人审），但被标记为特权或存在 SoD 冲突的永远显示。`rubber_stamp_flag_seconds: 5` 是质量控制的输入，见下一节。

### 启动前的四项数据准备

一次审阅的质量上限，在启动之前就已经被数据质量决定了。以下四项缺任何一项，都建议推迟启动而不是硬上——硬上的结果是消耗掉一次组织耐心，却拿不到可用结论。

1. **权限有可读名称**：至少高危部分完成 14.4.1 的业务权限层建设。若审阅条目仍是 `SAP_R3_PRD_S_TCODE_FB60_ALL` 这样的字符串，后面所有设计都是徒劳。
2. **权限有负责人**：每个应用与每项高危权限都有明确的业务负责人，且该人在职。这是审阅人指派的前提。
3. **有使用数据**：能回答"这项权限最近一次被使用是什么时候"。没有使用数据，预过滤与决策辅助都无从谈起——而这两者正是把撤销率从 1.7% 拉到两位数的关键。多数应用不原生提供该数据，需要从登录日志、审计日志或数据库访问日志中构造，这项工作通常要提前两到三个月开始。
4. **身份数据可信**：审阅对象的人员状态、部门、经理关系来自权威源（14.1），而不是从目录里现拉。给一个已离职的人发审阅、把条目发给一个已转岗的经理，是审阅公信力最快的破坏方式。

### 条目卡片：审阅人真正看到的东西

审阅体验的全部，就是审阅人屏幕上那张卡片。它应当包含且仅包含以下字段——多了会被忽略，少了无法判断：

| 区域 | 字段 | 作用 |
|------|------|------|
| 是谁 | 姓名、岗位、部门、直属经理、入职/转岗日期 | 建立人的上下文 |
| 有什么 | 业务权限名称（一句话说明）、风险标签 | 让权限可理解 |
| 为什么有 | 授权来源（角色/直接授权/组继承）、授予时间、当初的申请理由 | 回答"这是谁给的" |
| 用没用 | 最近使用时间、近 90 天使用次数 | 最强的单一判断依据 |
| 别人有没有 | 同岗位覆盖率（如"该岗位 8% 的人拥有"） | 提供横向参照 |
| 有没有风险 | 是否构成 SoD 冲突、是否为特权 | 触发额外审视 |
| 怎么办 | 保留 / 撤销 / 转他人处理，高风险保留需填理由 | 决策动作 |

其中"同岗位覆盖率"这一项常被省略，但它的价值极高：**它把一个孤立判断变成了比较判断**。人很难回答"张伟是否需要这项权限"，却很容易回答"为什么只有张伟一个人有这项权限"。

## 14.5.3 审阅疲劳：量化它，然后设计对抗它

审阅疲劳不是一种态度，而是一个可以被测量的现象。四个可直接计算的指标：

- **单条决策时间中位数**：低于 5 秒基本可判定为未阅读。
- **最长连续同向决策**：连续 100 条以上全部批准，几乎必然是批量操作或无差别点击。
- **决策速率随进度的变化**：多数人在前 20 条认真、之后加速，速率曲线的斜率就是疲劳的直接证据。
- **条目量与批准率的相关性**：把审阅人按条目量分桶，如果条目量越大的桶批准率越高，说明疲劳在起作用——这条是向管理层解释"为什么必须减少条目量"最有力的证据。

```python
"""审阅质量分析：识别橡皮图章行为，产出抽样复核清单。

输入是审阅决策事件流（每条含审阅人、条目、决策、时间戳）。
输出三类信号：
1. reviewer_flags —— 疑似未阅读的审阅人及其证据
2. campaign_health —— 整场战役的质量指标
3. qa_sample —— 建议抽样复核的条目（优先抽疑似审阅人 + 高风险条目）
"""
import random
import statistics
from collections import defaultdict
from dataclasses import dataclass
from datetime import datetime
from typing import Dict, List, Optional


@dataclass
class ReviewDecision:
    reviewer_id: str
    item_id: str
    decision: str            # approve / revoke
    decided_at: datetime
    entitlement_risk: str    # low / medium / high
    justification: str = ""


FAST_DECISION_SECONDS = 5.0
LONG_STREAK_THRESHOLD = 100


def _intervals(events: List[ReviewDecision]) -> List[float]:
    ordered = sorted(events, key=lambda e: e.decided_at)
    return [
        (b.decided_at - a.decided_at).total_seconds()
        for a, b in zip(ordered, ordered[1:])
    ]


def _longest_streak(events: List[ReviewDecision], decision: str) -> int:
    ordered = sorted(events, key=lambda e: e.decided_at)
    best = cur = 0
    for e in ordered:
        cur = cur + 1 if e.decision == decision else 0
        best = max(best, cur)
    return best


def analyze_campaign(decisions: List[ReviewDecision],
                     qa_sample_rate: float = 0.05,
                     seed: Optional[int] = 42) -> Dict[str, object]:
    by_reviewer: Dict[str, List[ReviewDecision]] = defaultdict(list)
    for d in decisions:
        by_reviewer[d.reviewer_id].append(d)

    reviewer_flags = []
    for reviewer, events in by_reviewer.items():
        if len(events) < 10:
            continue
        gaps = _intervals(events)
        median_gap = statistics.median(gaps) if gaps else float("inf")
        approve_rate = sum(1 for e in events if e.decision == "approve") / len(events)
        streak = _longest_streak(events, "approve")

        reasons = []
        if median_gap < FAST_DECISION_SECONDS:
            reasons.append(f"median_gap={median_gap:.1f}s")
        if streak >= LONG_STREAK_THRESHOLD:
            reasons.append(f"approve_streak={streak}")
        if approve_rate == 1.0 and len(events) >= 50:
            reasons.append("approved_everything")
        # 高风险条目全部批准且无理由说明，是最强的单一信号
        high_risk = [e for e in events if e.entitlement_risk == "high"]
        if high_risk and all(
            e.decision == "approve" and not e.justification.strip() for e in high_risk
        ):
            reasons.append(f"high_risk_approved_without_justification={len(high_risk)}")

        if reasons:
            reviewer_flags.append({
                "reviewer_id": reviewer,
                "items": len(events),
                "approve_rate": round(approve_rate, 4),
                "median_gap_seconds": round(median_gap, 2),
                "reasons": reasons,
            })

    all_gaps = [g for ev in by_reviewer.values() for g in _intervals(ev)]
    total = len(decisions)
    revoked = sum(1 for d in decisions if d.decision == "revoke")

    rng = random.Random(seed)
    flagged_ids = {f["reviewer_id"] for f in reviewer_flags}
    # 抽样不是均匀抽：疑似审阅人与高风险条目权重更高
    weighted = [
        d for d in decisions
        if d.reviewer_id in flagged_ids or d.entitlement_risk == "high"
    ] or decisions
    sample_size = max(1, int(total * qa_sample_rate))
    qa_sample = rng.sample(weighted, min(sample_size, len(weighted)))

    return {
        "campaign_health": {
            "items": total,
            "revoke_rate": round(revoked / total, 4) if total else 0.0,
            "median_decision_gap_seconds": round(
                statistics.median(all_gaps), 2
            ) if all_gaps else None,
            "flagged_reviewers": len(reviewer_flags),
            "reviewers": len(by_reviewer),
        },
        "reviewer_flags": sorted(
            reviewer_flags, key=lambda f: -f["items"]
        ),
        "qa_sample": [d.item_id for d in qa_sample],
    }
```

怎么读这段代码：`median_gap` 用中位数而非均值，因为审阅行为通常是"几段密集点击 + 中间隔了半天"，均值会被长间隔拉高而失去判别力。`high_risk_approved_without_justification` 是四个信号中最应当重视的一个——它不依赖速度，只依赖"是否为高风险条目提供了理由"，因此不会误伤那些确实熟悉自己团队权限、能快速判断的优秀审阅人。`qa_sample` 采用加权抽样而非均匀抽样，是因为均匀抽样在 1.7% 撤销率的分布下几乎抽不到有价值的样本。

**治理五招**（按投入产出比排序）：

1. **预过滤**：把"最近用过""同岗位普遍拥有"的条目移出审阅范围。这一招通常能把条目量减少 60%～80%（示例口径），是收益最大的一步。
2. **决策辅助**：每条附上最近使用时间、同侪覆盖率、风险标签、是否存在 SoD 冲突。让审阅从"猜"变成"看数据"。
3. **默认撤销**：无操作即撤销。这一招争议最大、效果最强，建议先在高危范围内试点。
4. **微认证**：把年度全量拆成事件驱动的小批量，见 14.5.4。
5. **抽样问责**：5% 抽样复核，结果反馈给审阅人及其上级，并纳入管理报表。**审阅人知道存在复核，行为就会改变**，这与复核本身发现多少问题无关。

**生产坑：默认撤销上线的正确姿势。** 直接对全量启用默认撤销，会在截止日产生一次大规模权限清空，其后果与 14.4.8 那次"清零重授"类似。稳妥的做法是：第一轮仅对高危条目启用默认撤销、并把截止前 48 小时的未决条目单独提醒到审阅人及其上级；同时准备好自助恢复通道。跑通一轮之后再扩大范围。

## 14.5.4 微认证：把年度战役拆成日常动作

全量年审的问题不只是疲劳，还有时效——一个人在 2 月转岗，他多出来的权限要等到 11 月的年审才被看见，中间九个月完全裸奔。

微认证（micro-certification）是事件驱动的小批量审阅：**一次只审几条，只审与某个事件相关的那几条，发给最了解情况的那个人。**

| 触发事件 | 审阅范围 | 审阅人 | 时限 |
|---------|---------|-------|------|
| 转岗生效 | 旧岗位相关权限 | 新旧两位经理 | 5 个工作日 |
| 经理变更 | 该下属全部非出生权限 | 新经理 | 10 个工作日 |
| 权限异常增长（30 天内新增 > 阈值） | 新增部分 | 直属经理 + 应用负责人 | 3 个工作日 |
| 用户风险分升高 | 高危权限 | 安全团队 | 1 个工作日 |
| 应用敏感级提升 | 该应用全部授权 | 应用负责人 | 15 个工作日 |
| 外包合同续签 | 该外包全部权限 | 甲方担保人 | 与续签同步 |
| 特权权限授予满 90 天 | 该条权限 | 权限持有人的经理 | 5 个工作日 |

微认证的条目量通常是个位数，审阅人能真正读完，撤销率显著高于全量审阅（在实施场景中常见 8%～20%，而全量审阅普遍在 1%～3%，示例口径）。

外包与第三方人员需要一条独立的微认证轨道，原因在 14.1.1 已经说明——他们没有 HR 事件，因此不会被转岗、离职这类触发器覆盖。可行的替代触发器有三个：合同续签日（最可靠，因为采购必然会处理）、季度固定复核（由甲方担保人执行，条目量小）、以及"90 天无活动"信号。这条轨道的审阅人必须是甲方担保人而非供应商项目经理——**让供应商审阅自己人的权限，等于没有审阅**。

**判断：风险削减主要来自微认证，合规证据主要来自全量审阅。** 两者都需要，但不要指望后者产生前者的效果。一个务实的组合是：微认证覆盖高危与变更场景、常态运行；全量审阅每年一次、范围可以适度收窄（因为高危部分已由微认证持续覆盖），主要用于产生合规证据并发现微认证的盲区。

"每年一次"指的是全量战役的节奏，它不解除按数据分类设定的复核频率下限。[8.2](../../第03部分_数据安全与隐私/第08章_数据安全/8.2_数据分类与标记.md) 对访问 Restricted 数据的权限要求复核间隔不超过 90 天、Confidential 不超过 180 天，这两个数字应当由微认证轨道承担：把两类数据对应的权限打上标签，进入短周期与变更触发的微认证队列，而不是靠把全量战役加密到一季一次来满足——后者只会把撤销率压得更低。

### AI agent 身份怎么进审阅范围

现有的访问审阅围绕人设计：把条目发给主管，请他确认"这个人还需不需要这项权限"。AI agent 没有主管。14.8.2 的台账里有 `owner_person_id`，但那通常是把它搭起来的工程师，他能准确回答"它还在跑吗"，回答不了"业务上还需不需要它跑"。把 agent 条目直接塞进现有战役发给这位 owner，得到的会是 14.5.1 描述过的那种完成率很高的空转。

**谁来复核：业务责任人 + 平台责任人双签。** 两个角色回答不同的问题，缺任一方都会留下特定形态的残留：

| 复核人 | 回答的问题 | 单独复核时会漏掉什么 |
|-------|-----------|-------------------|
| 业务责任人 | 这个任务还要不要做？范围有没有变？产出还有人用吗？ | 工具集与凭据形态的漂移——他读不懂 `allowed_tools` |
| 平台责任人 | 工具集、数据范围、凭据形态是否仍与登记一致？委派人是否仍在职？ | 一个早已没有业务价值、技术上却一切正常的 agent |

沿用 14.4.6 的"双签但异步"：两人并行处理，任一方给出撤销即进入 14.5.5 的撤销闭环，恢复走申请流程留痕。

**复核什么：四项，权限只是其中一项。**

1. **工具授权与任务定义的双向差集。** 把 14.8.6 登记的 `allowed_tools` 与该 agent 过去 90 天真实调用过的工具集对比，两个方向都有信息：调用了但不在清单里，说明越界或清单已过期，这一条应当按事件处理而不进审阅队列；在清单里但一次没调用过，是可以直接收掉的部分。这张差集表是 agent 审阅唯一必须自动生成的材料，没有它，复核人只能凭印象。
2. **委派关系是否仍然成立。** `allowed_delegators` 里的人是否还在职、还在原岗位。委派人群体会随组织调整漂移，而这个漂移不触发任何 agent 侧的事件。
3. **它还在被使用吗。** 见下一段。
4. **数据范围是否漂移。** 与登记的 `data_scope` 比对。这一项与资产台账里"接入的数据源"字段是同一份事实，两边不一致时以实测的调用记录为准（见 15.11.5）。

**僵尸 agent 比僵尸账号隐蔽，因为它还在动。** 僵尸账号的特征是无活动，"90 天无登录"这类规则就能把它捞出来。僵尸 agent 相反：它仍在按定时任务运行，日志里活跃，费用持续发生，凭据也在正常轮换，所有面向"活动"的信号都是绿的——只是**它的输出已经没有人看了**。订阅它日报的那个团队解散了，它接的那条流程改用别的方式了，而没有人想起来去关掉它。

判定信号因此不能取自 agent 侧，要取自下游的消费侧。三个可采集的：产出被打开或下载的次数；它创建的工单被采纳的比例（直接关闭的不算）；它发出的告警被处置的比例。可操作的判定是：**连续两个复核周期"输出消费为零"即进入停用倒计时**，倒计时期间保留数据、只停调度，到期再撤凭据。停用比删除安全，因为总有一类 agent 的消费信号采不到（产出被人复制到别处使用），停调度会让这批使用者自己找上门来。

**频率：比人更频繁，且必须有事件驱动的那一半。**

| 触发方式 | 范围 | 复核人 | 周期或时限 |
|---------|------|-------|----------|
| 周期复核 | 可写、或数据范围含 Restricted 的 agent | 业务 + 平台双签 | 每季度 |
| 周期复核 | 只读且数据范围为 Internal 及以下 | 业务 + 平台双签 | 每半年 |
| 事件驱动 | 工具集变更、数据源新增 | 平台责任人，业务知会 | 3 个工作日 |
| 事件驱动 | 委派人离职或转岗 | 业务责任人 | 5 个工作日 |
| 事件驱动 | 输出消费连续两周期为零 | 业务责任人 | 5 个工作日 |
| 事件驱动 | 单次任务成本或调用量越过阈值 | 平台责任人 | 1 个工作日 |

（周期与时限为示例口径，应按本组织 agent 的变更频率校准。）这张表挂在 14.5.4 微认证的同一条轨道上，共用触发器与提醒机制；只有前两行进全量战役的范围。**agent 的条目量小、每条信息量大，是最适合微认证的一类对象**——一个 agent 的复核材料通常就是一页差集表加三个消费指标。

```yaml
# agent 审阅战役配置：14.5.2 campaign 结构的 agent 变体，只列差异字段
campaign:
  id: AR-2026Q3-AGENT
  name: "2026Q3 agent 身份复核"
  scope:
    mode: agent_identity
    include_agents_where:
      writable: true
      data_scope_max: restricted
    exclude_agents_where:
      lifecycle_state: retired
  reviewers:
    dual_sign: true
    business: agent_business_owner
    platform: agent_platform_owner
    forbid_same_person: true
  decision:
    default_when_no_action: suspend
    require_justification_for: ["keep_unused_tool", "keep_zero_consumption"]
  evidence_pack:
    tool_diff_days: 90
    delegator_status: true
    output_consumption: true
    cost_per_task_trend: true
    data_source_drift: true
  suspend_policy:
    grace_days: 14
    retain_data: true
    revoke_credential_after_grace: true
```

怎么读这段配置：`evidence_pack` 的五项是发出条件，任何一项生成失败该条目就不发出——宁可少发，也不要发一条复核人无从判断的条目，理由与 14.5.2 的四项数据准备相同。`default_when_no_action` 取 `suspend` 而非人的条目那种 `revoke`，因为停调度可逆且不破坏取证材料。

**这段配置里有代价的设计选择**：`suspend` 比 `revoke` 轻，代价是僵尸 agent 会在停用状态多活 14 天，而且 `suspend` 如果不带到期动作，会沉淀成一批"既没在跑也没被清理"的中间态。`revoke_credential_after_grace` 就是为这一点存在的，把它设成 `false` 等于把停用变成一个永久的待办。

**照抄时最容易改错的三处**：一是漏掉 `forbid_same_person`——小团队里业务与平台责任人常是同一个人，双签退化成单签，而报表上仍然显示"双签完成"；二是照抄 `tool_diff_days: 90`，季度性运行的 agent 需要长于其任务周期的窗口，否则季末才用的工具会被差集判成"从未调用"并被收掉；三是把 `output_consumption` 实现成"agent 有没有产出"，它要测的是"产出有没有被消费"，两者只差一个词，检出僵尸 agent 的能力差一个数量级。

**适用边界。** 这套做法要求 agent 已经有独立身份（14.8 的形态 (b) 或 (c)）。仍在借用人的凭据的 agent 进不了 agent 审阅范围——它的条目会以那个人的名义出现在普通审阅里，主管看到的是"这个人有一批他从没用过的权限"，处置方向从一开始就是错的。第二条边界：消费信号的采集依赖产出物有明确落点（工单、报表、告警队列）；产出直接进入另一个 agent 输入的场景下，消费信号退化成"下游 agent 是否还在跑"，需要沿链路一直追到有人的那一端。第三条边界是分工：这里复核的是 agent 的权限与存续，输出内容的质量与准确性属于另一条线（见 17.2.6），审阅流程判断不了它答得对不对。

**验证方法。** **双签有效性抽查**：从已完成的 agent 条目里抽 10%，核对两个签名是否来自不同自然人，以及平台侧签署人是否真能读懂工具清单——让他复述其中两个工具的作用就能判断。**僵尸检出验证**：挑三个已知长期无人使用的 agent（每个组织都有，问运维就知道），看它们是否被这一轮捞出来；捞不出来说明消费信号采错了地方。**差集材料的准确性核对**：随机取一条"清单里有但从未调用"的工具，到目标系统日志里反查 90 天确认确实没有调用记录。差集材料一旦被发现有假，复核人会立刻退回到全批准，而且不会告诉你。

**运行指标。** **agent 审阅覆盖率**（分母取 NHI 台账里的 agent 总数，不取审阅系统里已配置的数量，理由与 14.6.2 的纳管率分母相同）；**agent 条目撤销率**（预期显著高于人的全量审阅；首轮低于 5% 通常说明差集材料没做出来，此阈值为示例口径）；**僵尸 agent 检出数，以及停用后被申诉恢复的比例**（恢复比例长期为零说明停用判定过于保守，参照 14.5.8 申诉恢复率的自校准逻辑）；**双签合规率**（两位签署人为不同自然人的条目占比，目标 100%）；**从工具集变更到完成复核的时长 P95**（事件驱动那半边的时效）。

## 14.5.5 撤销闭环：决策不等于动作

审阅报表上的"已撤销 712 条"，与目标系统里真的少了 712 条权限，是两件事。二者之间有五个常见断链点：

| 断链点 | 表现 | 对策 |
|-------|------|------|
| 决策未转成工单 | 决策存在审阅系统里，无人执行 | 决策即自动创建执行任务，不依赖人工转派 |
| 目标系统无接口 | 只能人工登录后台删除 | 建立人工执行清单 + 完成举证（截图/导出）+ SLA |
| 执行失败无重试 | 接口报错后静默丢弃 | 参照 14.2.5 的编排器：失败可续、超限升级 |
| 撤销被业务打回 | 用户投诉后管理员手工恢复，无记录 | 恢复必须走申请流程并留痕，禁止直接改 |
| 撤销了角色但未撤销直接授权 | 用户仍有权限，来源不同 | 撤销前枚举全部授权来源，逐一处理 |

最后一条尤其隐蔽：同一项权限可能同时来自角色成员资格、直接授权、以及嵌套组继承。撤销其中一条来源后，用户依然拥有该权限，而审阅系统会显示"已撤销"。**审阅系统的"已撤销"应当以复核目标系统的实际状态为准，而不是以发出撤销指令为准。**

推荐的闭环状态机：

```
decided(revoke)
      │ 自动创建执行任务（含目标系统、权限标识、全部授权来源）
      ▼
   queued ──────► executing ──────► verified ──► closed
      │               │                 ▲
      │               │ 失败             │ 复核目标系统实际状态
      │               ▼                 │
      │           retrying ─────────────┘
      │               │ 超过重试上限
      │               ▼
      │           escalated ──► manual_task ──► evidence_attached ──► verified
      │
      └──► blocked（业务申诉中）──► reinstated（走申请流程，留痕）
                                └──► resumed（申诉驳回，回到 queued）
```

三条纪律：**`verified` 必须来自对目标系统的独立复核**，而不是执行接口返回成功；**`reinstated` 是一个需要审批的状态**，不能由管理员直接跳转；**`blocked` 有最长停留时间**（例如 10 个工作日），超时自动进入升级而非无限期挂起——见过的最糟糕情况是数百条撤销永久停留在申诉状态，报表上不算失败，实际上等于没撤。

配套的两个 SLA：撤销决策到 `verified` 的 P95 < 48 小时（有接口的系统）或 < 10 个工作日（人工执行）；`escalated` 状态的条目每周向 IAM 负责人汇总。

## 14.5.6 审计要的是证据链，不是结论

审计师不关心你的撤销率是多少，他关心的是能否复现整个过程。一条完整的证据链包含六个环节，缺一即为发现项：

1. **范围与依据**：本轮审阅覆盖了哪些人、哪些权限，依据哪条制度或控制要求（如 SOX 的用户访问复核控制）。
2. **快照**：审阅所依据的权限数据快照，含生成时间与来源系统，且此后不可修改。
3. **审阅人指派记录**：谁被指派审阅哪些条目，指派规则是什么，替代审阅人如何产生。
4. **决策记录**：每条的决策、决策人、决策时间，以及高风险条目的业务理由。
5. **执行证据**：撤销决策对应的执行结果与复核证据（接口返回、系统状态截图、导出清单）。
6. **例外与偏差**：未按期完成的条目及其处理、被申诉恢复的条目及其审批记录。

高频审计发现（可以直接拿去自查）：

- 审阅人对自己的权限做了审阅（自审），或审阅人是被审阅人的下属。
- 快照时间与审阅开始时间相差过大（例如 45 天），期间的变更未被覆盖。
- 撤销决策与目标系统状态不一致，抽查发现权限仍然存在。
- 高风险条目被批准但无业务理由记录。
- 审阅人已于审阅期间离职，其条目由他人代批但无授权记录。
- 上一轮的整改事项在本轮仍然存在，且无跟踪记录。

把这六条做成审阅系统的内置校验（启动前自动检查自审、审阅人在职、快照新鲜度），比事后应对审计便宜得多。一个附带收益是：这些校验的失败项本身就是一份高质量的整改清单——它们指向的通常不是审阅流程的问题，而是身份数据的问题（经理关系缺失、离职未同步、应用负责人未指定），修复它们会同时改善 14.1 与 14.2 的指标。

## 14.5.7 失败叙事：我们把默认值改了三次

第一版设计，我们把默认值设成"保留"——理由是"避免误伤业务"。结果是完成率 96%，撤销率 1.2%，其中大部分撤销来自三位特别认真的审阅人。审阅在事实上没有发生。

第二版，我们取消了默认值，要求逐条显式选择"保留"或"撤销"，并禁用了批量操作。理由是"强迫审阅人看每一条"。结果比第一版更糟：完成率从 96% 掉到 41%，大量审阅人在处理了几十条后放弃，截止日过后需要 IAM 团队逐个催办，催办本身消耗了两周人力。更糟的是产生了强烈的负面情绪——"安全部门又在给我们加活"，这句话在之后一年里被反复提起，直接影响了后续项目的配合度。

第三版才走对：**先做减法，再改默认值。** 具体是三件事叠加——预过滤把 41,700 条压到 6,800 条（隐藏最近用过的、同岗位普遍拥有的）；每条附上最近使用时间与同侪覆盖率；默认值改为"撤销"，但只对高危条目启用，且提供一键自助恢复。

第三版的结果：条目量下降 84%，完成率 97%，撤销率 11.4%，其中因误撤而自助恢复的比例是 6.8%（示例口径）。**6.8% 这个数字是整件事里最重要的一个**——它证明了默认撤销并没有造成大规模误伤，也让我们有底气把这套做法推广到更大范围。

复盘时的认识是：**我们前两次都在试图改变审阅人的行为，第三次才去改变审阅人面对的问题。** 一个人面对 300 条无法判断的条目时，无论用什么规则约束，他的最优策略都是走捷径；把 300 条变成 22 条并附上判断依据，他自然会认真读。这个道理在别处也成立，但在访问审阅上尤其明显，因为这里的"人"是几百位有本职工作的业务经理，你无法培训他们成为权限专家。

## 14.5.8 度量

| 指标 | 定义 | 参考目标（示例口径） | 说明 |
|------|------|------------------|------|
| 撤销率 | 撤销条目 ÷ 审阅条目 | 全量 > 5%；定向 > 10% | 长期低于 2% 即橡皮图章 |
| 撤销落地率 | verified 条目 ÷ 撤销决策条目 | 100% | 本节最重要的指标 |
| 撤销闭环时长 P95 | 决策到 verified | < 48 小时（有接口） | 与 14.2.9 同源 |
| 单条决策时间中位数 | 相邻决策时间间隔 | > 8 秒 | 低于 5 秒触发质量复核 |
| 被标记审阅人占比 | 触发橡皮图章信号的审阅人 ÷ 总审阅人 | < 10% | 逐轮下降说明治理生效 |
| 抽样复核错误率 | 复核认为决策不当的比例 | < 10% | 高于 20% 说明决策依据不足 |
| 微认证覆盖率 | 由事件触发审阅覆盖的高危权限 ÷ 高危权限总数 | > 90% | 决定风险时效 |
| 申诉恢复率 | 撤销后被恢复的条目 ÷ 撤销条目 | 5%～15% | 过低说明撤得太保守，过高说明预过滤不准 |

最后两条形成了一组自校准机制：**申诉恢复率过低说明审阅过于保守（撤销的都是显然该撤的），过高说明预过滤规则需要调整**。把它当作调参依据，而不是当作错误率来考核审阅人——把恢复率当错误率考核，会立刻把默认值推回"保留"。

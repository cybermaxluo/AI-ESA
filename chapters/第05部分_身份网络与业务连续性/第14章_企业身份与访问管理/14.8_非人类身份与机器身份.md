# 14.8　非人类身份与机器身份

2024 年 1 月，一家全球最大的软件企业披露：攻击者通过密码喷洒攻陷了一个"遗留的非生产测试租户账号"，该账号未启用多因素认证；随后攻击者利用该账号在租户中已有的一个 OAuth 应用，为自己创建了新的应用权限，最终以应用身份读取了包括高管在内的一批企业邮箱[1]。

这条攻击链里有三个非人类身份的典型问题，且它们都不是技术缺陷：**一个没有人记得的测试账号**（无所有者、无到期日、无生命周期）；**一个权限过宽的 OAuth 应用**（应用权限不受用户上下文约束，也不受条件访问策略保护）；**一次静默的凭据添加**（给应用加一个客户端密钥，是一个常规管理操作，没有人在看）。

同年披露的另一起大规模事件同样如此：某数据平台的多家客户环境被入侵，根因是这些环境中的账号使用了从信息窃取木马获取的凭据、且未启用多因素认证、也没有网络访问策略限制[2]。这里的"账号"大量是集成用的服务账号——它们天然无法完成交互式多因素认证，因此在几乎所有企业里都被默默地排除在认证加固之外。

**非人类身份（Non-Human Identity，NHI）是当前企业身份治理中最大的一块空白。** 各家厂商给出的机器身份与人类身份的数量比在 40:1 到 90:1 之间（厂商称，需自证；口径差异极大，有的把每个容器实例都算一个身份），但无论真实倍数是多少，结论是一致的：**企业投入了大量精力治理人的身份，而攻击者越来越多地使用不是人的身份。**

本节的核心判断：**NHI 缺的不是金库，是户主。** 大多数企业在讨论 NHI 时首先想到密钥管理平台，但密钥管理解决的是"凭据放哪、怎么轮换"，而 NHI 治理真正卡住的地方是"这个东西是谁的、还需不需要、能不能删"。没有户主，金库里装的只是一堆无人认领的钥匙。

## 14.8.1 类型学：它们从哪里来

| 类型 | 谁创建的 | 凭据形态 | 典型生命周期 | 治理缺口 |
|------|---------|---------|------------|---------|
| 目录服务账号 | 基础架构或应用团队 | 密码、Kerberos 密钥 | 无 | 密码永不过期，注册了 SPN，权限过宽 |
| 应用注册 / 服务主体 | 开发或管理员 | 客户端密钥、证书 | 密钥有效期，主体无 | 应用权限不受用户上下文与条件访问约束 |
| API 密钥 | 任何有权限的人 | 长期字符串 | 无 | 常绑定在个人账号上，人走了密钥还在 |
| OAuth 客户端与授权同意 | 用户或管理员 | 客户端凭据、刷新令牌 | 令牌有效期可能很长 | 用户可自助授权第三方应用读取自身数据 |
| CI/CD 令牌 | 研发 | 令牌、部署密钥 | 常设为永久 | 作用域过宽，泄露即等于生产访问 |
| 工作负载身份 | 平台自动签发 | 短期证书或令牌 | 分钟到小时 | 治理最好的一类，但 attestation 配置易错 |
| 设备与证书身份 | PKI | 证书 | 证书有效期 | 有效期以年计，吊销机制常年不运行 |
| AI agent 身份 | 业务或平台团队 | 令牌、密钥、委派凭据 | 无 | 多数直接复用人的凭据，见 14.8.6 |

数量爆炸的原因是**创建成本趋近于零而销毁成本不为零**：任何一个开发者用一条命令就能创建一个服务账号或一个 API 密钥，但要删除它，需要先确认没有人在用——而这个确认在缺少调用来源信息时无法完成。于是理性的选择永远是"先留着"。

一条可以立刻做的自查：**在你的环境里，创建一个具备生产数据读权限的服务账号，需要经过几个人？** 如果答案是"零"，那么 NHI 数量的增长速度就等于开发活动的速度。

### 它们无法做多因素认证，所以需要别的强度

人类身份的认证加固路线（14.3）在 NHI 上完全不适用——没有人可以按下硬件密钥，也没有手机可以接收推送。这导致一个普遍现象：**认证加固项目在推进时把 NHI"暂时排除"，而这个"暂时"从此没有结束**。前述两起公开事件的共同前提，正是这类被排除在外的账号。

替代的强度手段不是一个，而是一组，必须组合使用：

| 补偿手段 | 作用 | 落地要点 |
|---------|------|---------|
| 双向 TLS 或证书认证 | 用密码学材料替代口令 | 证书私钥的保护成为新的关键点 |
| 短期凭据 | 缩短泄露后的可用窗口 | 见 14.8.3 的动态凭据 |
| 来源约束 | 限定可发起调用的网络位置或工作负载身份 | 云平台的网络策略、条件访问的"工作负载身份"能力 |
| 调用行为基线 | 用规律性替代交互式验证 | 见 14.8.7 |
| 权限最小化与分离 | 降低单个凭据的价值 | 一个用途一个身份，禁止共用 |
| 禁止交互式登录 | 服务账号不应能用于人的登录 | 目录侧策略强制，且要覆盖远程桌面与远程管理 |

这些手段中没有任何一项能单独达到抗钓鱼 MFA 对人类身份的保护强度。**因此 NHI 治理的重点必须前移到"减少数量、缩短寿命、收窄权限"上**，而不是寄望于在认证环节补齐强度——认证强度补不齐，只能靠让每一个凭据都不值钱。

**判断：其中"一个用途一个身份"是收益最高也最常被违反的一条。** 共用凭据会让上面所有手段同时失效——来源无法约束（来源太多）、行为无法基线（模式混杂）、撤销无法执行（不知道会影响谁）。见过的极端案例是一个数据库账号被 20 多个服务共用，其中三个已经下线多年，而没有人敢动它。

## 14.8.2 先解决户主问题

治理 NHI 的第一步不是买平台，是让每一个 NHI 都有以下五项元数据，且**缺失即拒绝创建**：

| 字段 | 为什么必须 |
|------|----------|
| `owner_person_id`（人类责任人） | 撤销通知发给谁；离职时转移给谁 |
| `backup_owner_person_id` | 单点责任人离职会让 NHI 立刻变孤儿 |
| `purpose`（用途，自由文本但不可为空） | 三年后判断"还需不需要"的唯一依据 |
| `environment`（生产/预发/测试） | 决定控制强度；测试身份混进生产是常见事故 |
| `expires_on`（到期日） | 强制复核；无到期日的身份必然沉淀为孤儿 |

关键在于**把这五项做成创建时的强制项而不是事后补录**。事后补录的完成率在实践中很低，因为那时创建者已经拿到了想要的东西。

创建入口也必须收敛。理想状态是**所有 NHI 通过统一入口创建**（自助平台或基础设施即代码），云平台与目录中的直接创建权限收归少数人。这条在多数企业推不动，退一步的做法是"允许直接创建，但持续发现并强制补齐元数据，超期未补齐则禁用"——与 14.6.2 的纳管闭环同构。

**所有权转移必须与人的生命周期挂钩。** 14.2.5 的撤销时序表里，T+7 天那一档就是"完成非人类身份归属转移"。落地要点是：离职流程自动列出该人名下的全部 NHI，发给其经理，7 天内必须指定新责任人，逾期则该 NHI 进入禁用倒计时。这条规则第一次运行时会引发大量抱怨，因为它把长期无人管理的存量一次性暴露出来——这恰恰是它的价值。

## 14.8.3 Secrets 管理：从静态密钥到动态凭据

有了户主，才轮到金库。密钥管理的演进方向是明确的：**减少静态长期凭据的数量，直至为零。**

三个阶段：

**阶段一：集中化。** 把散落在配置文件、环境变量、代码仓库、运维文档里的密钥收进统一的密钥管理系统，应用改为启动时拉取。这一步的收益是可见性与可轮换性，代价是引入了新的依赖（密钥系统故障影响所有应用启动）。

**阶段二：动态化。** 不再存储长期凭据，而是由密钥系统按需向数据库、云平台申请一份短期凭据（租约模式），用完即撤销。这一步是质变——**泄露一份凭据的价值从"长期访问"降为"若干分钟的访问"**，同时每份凭据天然绑定到一次具体的申请，审计粒度大幅提升。

**阶段三：无密钥（secretless）。** 应用完全不接触凭据，由平台在连接建立时注入身份（见 14.8.4 的工作负载身份）。

```python
"""动态数据库凭据获取：租约模式的最小实现骨架。

要点：
1. 凭据按需申请、带 TTL、用完显式撤销，不落盘。
2. 续租失败必须导致连接被主动放弃，而不是继续使用过期凭据。
3. 申请与撤销都写审计，且携带调用方的工作负载身份，
   这样审计记录能回答"哪个服务在什么时候用了哪份凭据"。
"""
import threading
import time
from dataclasses import dataclass
from typing import Callable, Optional


@dataclass
class Lease:
    lease_id: str
    username: str
    password: str
    ttl_seconds: int
    issued_at: float

    def remaining(self) -> float:
        return self.ttl_seconds - (time.time() - self.issued_at)


class DynamicCredentialClient:
    def __init__(
        self,
        issue_fn: Callable[[str, str], Lease],
        renew_fn: Callable[[str], Optional[Lease]],
        revoke_fn: Callable[[str], bool],
        workload_identity: str,
        role: str,
        renew_threshold_ratio: float = 0.5,
    ):
        self.issue_fn = issue_fn
        self.renew_fn = renew_fn
        self.revoke_fn = revoke_fn
        self.workload_identity = workload_identity
        self.role = role
        self.renew_threshold_ratio = renew_threshold_ratio
        self._lease: Optional[Lease] = None
        self._lock = threading.Lock()

    def get(self) -> Lease:
        with self._lock:
            if self._lease is None:
                self._lease = self.issue_fn(self.workload_identity, self.role)
                return self._lease
            threshold = self._lease.ttl_seconds * self.renew_threshold_ratio
            if self._lease.remaining() > threshold:
                return self._lease
            renewed = self.renew_fn(self._lease.lease_id)
            if renewed is not None:
                self._lease = renewed
                return self._lease
            # 续租失败：主动撤销并重新申请，绝不继续使用即将过期的凭据
            self.revoke_fn(self._lease.lease_id)
            self._lease = self.issue_fn(self.workload_identity, self.role)
            return self._lease

    def close(self) -> None:
        with self._lock:
            if self._lease is not None:
                self.revoke_fn(self._lease.lease_id)
                self._lease = None
```

怎么读这段代码：`renew_threshold_ratio: 0.5` 意味着在租约过半时就尝试续租，而不是等到快过期——留出的余量用于吸收网络抖动与密钥系统的瞬时不可用。`close()` 显式撤销租约是很多实现遗漏的一步：不撤销的话，凭据会一直存活到 TTL 结束，一个频繁重启的服务会在数据库里堆积大量残留账号。**这个细节在实践中会以"数据库连接数莫名增长"的形式暴露出来，而排查方向通常一开始都跑偏了。**

### 目录服务账号：一条具体的迁移路径

在 AD 环境中，服务账号是 NHI 里存量最大、风险最集中的一类（它们通常密码永不过期、注册了服务主体名、权限过宽，直接对应 14.7.6 的 Kerberoasting 前置条件）。一条可执行的四步迁移路径：

1. **盘点与归类**：枚举所有注册了 SPN 的账号、所有密码永不过期的账号、所有在特权组中的服务账号。按"能否改造"分三类：可迁移到组托管服务账号（gMSA）、只能改强口令、必须保持现状（第三方产品限制）。
2. **优先处理交叉项**：既在特权组、又注册了 SPN、密码又永不过期的账号，是风险最高的组合，应当第一批处理，通常数量在个位数到几十之间。
3. **批量迁移到 gMSA**：适用于运行在 Windows 上、支持指定服务账号的服务。迁移后密码由系统管理并自动轮换，长度远超任何人工设定，离线破解不可行。
4. **剩余部分做补偿**：无法迁移的账号，采用 25 字符以上随机口令、仅 AES 加密、来源约束、以及针对性的行为监控。

这条路径的价值在于它把一个"清理不完的存量问题"转化成了"一次性的技术迁移 + 少量长期例外"。**关键是第 2 步——不要从数量最多的那一类开始，要从风险最集中的那一小撮开始。**

**生产坑：密钥管理平台自己成了单点。** 应用改为启动时从密钥系统拉取凭据后，密钥系统的可用性就等于全部应用的可用性。真实发生过的形态是：一次密钥系统的证书过期导致所有应用在重启后无法启动，而修复需要访问密钥系统本身。三条对策：应用侧缓存最近一次成功获取的凭据并在密钥系统不可用时继续使用（直到租约到期）；密钥系统自身的证书与凭据纳入独立的到期监控；以及**把"密钥系统不可用"纳入灾难恢复演练**——它现在是与目录服务同级的基础设施。

**生产坑：`secret zero` 被随手解决了。** 应用要从密钥系统取凭据，首先得有一个能向密钥系统证明身份的凭据，这就是所谓的 `secret zero` 问题。常见的错误解法是把这个引导凭据写进镜像或配置管理仓库——于是所有努力回到原点，因为拿到它就等于拿到了全部密钥。正确解法是用平台提供的身份证明（云实例元数据、容器编排平台的服务账号令牌、可信平台模块）来完成首次认证，即下一小节的工作负载身份。**如果你的密钥管理方案里 `secret zero` 是一个静态字符串，那么这套方案的实际强度就等于那个字符串的保护强度。**

### 关于轮换：不要把周期定成惩罚

静态密钥无法立刻消灭，因此轮换仍然必要。但轮换策略的设计有一个陷阱：**周期定得越激进，豁免就越多**。

一次真实的教训见 14.8.8。这里先给结论：轮换周期应当**按凭据类型与影响面分层**，而不是全局统一。可访问生产数据的凭据 90 天，普通集成凭据 180 天，已实现动态凭据的直接不适用。同时必须先具备两个前提——**轮换可自动化**（应用能在不重启的情况下感知新凭据）与**轮换可回滚**（新旧凭据有重叠有效期）。缺少这两个前提时，任何轮换要求最终都会变成一场关于豁免的谈判。

### Secrets 扫描：发现之后的问题更难

代码仓库、镜像、日志中的密钥扫描已是成熟能力，多数企业都在做。真正的困难在扫描之后：

- **不知道谁在用**：找到一个硬编码的数据库密码，但没人敢改，因为不知道还有哪些系统在用同一个。解法是先建立"凭据 → 调用来源"的可观测性（数据库连接的来源 IP 与应用标识），再动手。
- **历史提交里的密钥仍然有效**：从代码里删掉不等于撤销。**凡是进过版本库的密钥一律视为已泄露**，必须轮换而不是删除。
- **扫描结果的疲劳**：与 14.5 的审阅疲劳同构——每周几百条低质量告警会让人停止查看。必须按"是否真实有效"分级（尝试用它调用一次目标服务是最可靠的判定），只把有效凭据推给人处理。

## 14.8.4 工作负载身份：让凭据消失

工作负载身份（Workload Identity）的思想是：**不给工作负载发凭据，而是让平台证明它是谁。**

**SPIFFE / SPIRE** 是这一领域的开放标准与参考实现。核心概念三个：`trust domain`（信任域，一个组织的边界）、`SPIFFE ID`（形如 `spiffe://example.com/ns/payments/sa/api` 的身份标识）、`SVID`（该身份的可验证凭据，X.509 证书或 JWT 形式，有效期通常以分钟计）[4]。工作负载启动时，节点上的代理通过**证明（attestation）**——检查其所在节点的属性与工作负载的运行时特征（如容器编排平台中的命名空间与服务账号）——确认其身份，随后签发短期 SVID。

关键收益是：凭据从不长期存在、不需要分发、不需要轮换（因为生命周期本来就只有几分钟），且身份与部署位置绑定，被窃取后在别处无法使用。

```python
"""JWT-SVID 校验要点：受众、签发者、SPIFFE ID 白名单、有效期。

常见错误是只校验签名与有效期，而不校验 audience 与 SPIFFE ID，
这会让任何一个持有本信任域内合法 SVID 的工作负载都能访问本服务。
"""
from typing import Iterable, Set

import jwt          # PyJWT
from jwt import PyJWKClient


class SvidError(Exception):
    pass


def verify_jwt_svid(
    token: str,
    jwks_url: str,
    expected_audience: str,
    trust_domain: str,
    allowed_spiffe_ids: Set[str],
    leeway_seconds: int = 30,
) -> dict:
    signing_key = PyJWKClient(jwks_url).get_signing_key_from_jwt(token)
    claims = jwt.decode(
        token,
        signing_key.key,
        algorithms=["RS256", "ES256"],
        audience=expected_audience,      # 必校验：防止令牌被跨服务重放
        leeway=leeway_seconds,
        options={"require": ["exp", "aud", "sub"]},
    )

    subject = claims.get("sub", "")
    if not subject.startswith(f"spiffe://{trust_domain}/"):
        raise SvidError(f"SPIFFE ID not in trust domain: {subject}")
    # 白名单是精确匹配集合，不做前缀匹配：
    # 前缀匹配会让 /ns/payments-test 意外落入 /ns/payments 的授权范围
    if subject not in allowed_spiffe_ids:
        raise SvidError(f"SPIFFE ID not authorized for this service: {subject}")
    return claims


def authorized_callers(paths: Iterable[str], trust_domain: str) -> Set[str]:
    return {f"spiffe://{trust_domain}/{p.lstrip('/')}" for p in paths}
```

怎么读这段代码：`audience` 校验是最常被省略也最危险的一项——没有它，一个工作负载拿到的合法 SVID 可以被用于访问信任域内的任何服务。`allowed_spiffe_ids` 使用精确集合而非前缀匹配，理由与 14.3.2 的 origin 校验完全一致：前缀匹配在命名相近时会产生意外的授权扩展。

### OIDC 联邦：CI/CD 不再需要长期密钥

同一思想在云上的常见形态是 OIDC 联邦：CI/CD 平台为每次运行签发一个短期 OIDC 令牌，云平台配置对该签发者的信任并映射到具体角色，从此不再需要在流水线里存放长期访问密钥。

这里有一个高频且严重的配置错误——**信任条件里的主体（`sub`）声明使用了通配**：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:example-org/payments-service:environment:production"
        }
      }
    }
  ]
}
```

上面是正确写法：`sub` 用 `StringEquals` 精确绑定到具体仓库与具体环境。常见的错误写法是用 `StringLike` 配合 `repo:example-org/*:*`——它意味着**该组织下任意仓库的任意分支上的任意一次流水线运行，都能取得这个生产角色**。攻击者只需在该组织中拥有一个不起眼仓库的写权限（甚至提交一个 pull request 触发工作流），就能横向拿到生产权限[5]。

三条纪律：`aud` 必须校验；`sub` 必须精确到仓库与环境（或分支），禁止在仓库名位置使用通配；不同环境使用不同角色，不要用一个角色覆盖开发与生产。

## 14.8.5 CI/CD 凭据：流水线就是特权入口

流水线的权限往往超过任何一位工程师：它能读代码、写制品库、部署生产、访问密钥。因此它应当被当作 Tier 1 甚至 Tier 0 资产对待（见 14.7.2 的清单）。

需要落实的控制：

- **令牌最小作用域与短时效**：默认令牌通常权限过宽，应显式降权到本次任务所需，并限制有效期到任务时长。
- **环境保护与审批**：面向生产的部署作业应要求人工审批，且审批人不能是提交者本人。
- **分支与标签保护**：只有受保护分支上的运行才能取得生产凭据（对应上面的 `sub` 精确匹配）。
- **自托管执行器的隔离**：自托管执行器若在多个仓库间共享，一个仓库的恶意代码可以窃取另一个仓库遗留在机器上的凭据与缓存。生产用途的执行器应当一次性、隔离、不复用。
- **依赖与构建产物的完整性**：这部分属于供应链安全，见第7章。本节只强调其身份侧含义——**构建产物的签名密钥是 NHI，且是最高价值的那一类**。

## 14.8.6 AI agent 作为一等身份

企业开始部署能自主调用工具、访问系统、执行操作的 AI agent（相关架构与风险见[第17章](../../第06部分_AI驱动的安全创新/第17章_AI驱动网络安全/README.md)与[第18章](../../第06部分_AI驱动的安全创新/第18章_AI系统安全/README.md)）。从身份治理的角度，当前最普遍也最危险的做法是：**让 agent 复用某个人的凭据，或使用一个权限很大的通用服务账号。**

前者的后果是审计断链——日志里显示"张伟在凌晨 3 点导出了 12 万条客户记录"，而实际执行者是一个自动化流程；追责、取证、事件响应全部失去意义。后者的后果是权限无法收敛——一个服务账号服务于十几个 agent 场景，其权限是所有场景的并集，且无法针对单个场景撤销。

**判断：AI agent 必须是一等身份**，即拥有独立于人的身份标识与生命周期。五条要求：

1. **唯一身份**：每个 agent 实例（或每类 agent 的每个部署）拥有独立标识，可在日志中与人类身份区分开。
2. **可归属的委派链**：当 agent 代表某人执行操作时，凭据中必须同时携带 agent 身份与委托人身份（代表模式），使审计能回答"谁让它做的"。这在 OAuth 体系中对应"代表用户"的令牌形态，但**关键不是协议，而是日志里两个主体都在**。
3. **权限上界独立于委托人**：agent 的权限应是"委托人权限 ∩ agent 自身权限上界"，而不是简单继承委托人的全部权限。一个能读取用户全部邮件的助手，其风险远大于用户自己读邮件——因为它可以在几秒内读完全部并做出摘要与外发。
4. **可独立撤销**：能在不影响委托人正常工作的前提下，立即停用某个 agent 的全部访问。这要求 agent 的凭据独立签发、可单独吊销。
5. **行为可审计且可归因**：工具调用、参数、结果摘要必须留痕，且能与触发它的会话关联。

两个特有的风险需要单独设计：

**审批环节的机器化。** 当 agent 可以发起权限申请、而审批流又被另一个自动化环节处理时，人类审批就从流程中消失了。设计原则是：**涉及权限变更、资金、数据外发的动作，审批人必须是人，且审批界面要显示"这是由 agent 发起的"。**

**权限的隐式扩张。** agent 通过组合多个"低风险"工具达成高风险效果（读取工单系统 + 读取代码仓库 + 发送邮件 = 数据外发通道）。单个权限的授予审批看不出问题，组合才有问题。这本质上是 14.4.5 职责分离在 agent 场景的延伸——**应当为 agent 定义工具组合层面的约束，而不只是单个工具的授权**。

一个可以直接套用的 agent 身份登记结构（它同时满足 14.8.2 的五项元数据要求）：

```json
{
  "agent_id": "agent-svc-ticket-triage-prod-01",
  "display_name": "工单自动分诊 agent（生产）",
  "owner_person_id": "P-40b7c1de-2a55-4b83-91cc-7f6e2d0b8a31",
  "backup_owner_person_id": "P-9a1f0b32-88ce-4a17-b3d2-6e40c7215fa9",
  "purpose": "读取工单、按规则打标签与分派，不回复客户，不修改客户数据",
  "environment": "production",
  "expires_on": "2027-01-31",
  "identity": {
    "type": "workload",
    "spiffe_id": "spiffe://example.com/ns/itsm/sa/triage-agent",
    "credential": "short_lived_svid",
    "static_secrets": []
  },
  "delegation": {
    "mode": "on_behalf_of",
    "allowed_delegators": ["group:itsm-agents"],
    "effective_permission": "intersection_of_delegator_and_agent_ceiling"
  },
  "permission_ceiling": {
    "allowed_tools": ["ticket.read", "ticket.tag", "ticket.assign"],
    "denied_tools": ["ticket.reply", "customer.update", "email.send", "file.export"],
    "rate_limits": {"ticket.read": 2000, "ticket.assign": 200},
    "data_scope": "tenant:internal-it"
  },
  "human_approval_required_for": ["permission_change", "scope_expansion"],
  "audit": {
    "log_tool_calls": true,
    "log_parameters": true,
    "retain_days": 400
  }
}
```

怎么读这段登记：`denied_tools` 与 `allowed_tools` 同时存在不是冗余——显式拒绝列表用于表达"即使将来有人扩大了允许列表，这几项也不能给"，它是工具组合风险的第一道护栏（注意 `email.send` 与 `file.export` 被显式拒绝，正是为了切断上面说的数据外发通道）。`effective_permission` 声明了权限是委托人与 agent 上界的交集，而非继承。`rate_limits` 是 NHI 特有的控制项：agent 的破坏力主要来自速度，限速是最直接的减灾手段。

**推演**：agent 身份的标准化（身份格式、委派链表达、工具授权模型）在本书截稿时点仍在演进中，尚无被广泛采纳的统一规范。务实的做法是：先用现有机制（服务主体 + 代表模式 + 短期令牌）把上述五条要求实现出来，把 agent 纳入 NHI 台账并强制五项元数据，不必等待标准成熟——**等待的代价是这段时间里创建的 agent 全都成为无主身份**。

### 三种形态：借人的凭据、独立服务账号、可委派的短时凭据

上面五条要求描述的是终局。落地时先要回答一个更前置的问题：这个 agent 的凭据从哪来。现实中只有三种形态，代价各不相同。

**形态 (a)：借用配置者或某个业务用户的凭据。** 部署最快，因此也最普遍——不需要申请账号、不需要重新授权，把人的令牌或 API 密钥填进配置就能跑。除了前面说的审计断链，它还有三笔容易被漏掉的账：

- **凭据的生命周期挂在人身上。** 这个人离职时，14.2.5 的撤销时序会切断他的会话与刷新令牌，agent 随之停摆；而如果 agent 用的是他名下的长期 API 密钥，撤销时序里通常没有这一项，人走了密钥还在跑，且已经没有任何人为它负责。两种结局都不好，事先还无法预测会是哪一种。
- **权限继承的是这个人的全部，而不是 agent 需要的那部分。** 一个工作八年、转过三次岗的工程师，其权限集合远超任何单一 agent 的需要（14.0 的困境三给过这个累积过程）。更麻烦的是它是活的：这个人下次转岗新增的权限，agent 会在毫不知情的情况下一并获得。
- **为了让 agent 跑通，这个人自己的保护被拆掉了。** agent 无法完成交互式多因素认证，也过不了合规设备检查，于是常见的处置是把这个账号加进条件访问的排除列表、或为它开启旧协议认证。这条豁免落在一个真人账号上，从此这个人自己的登录也不再受保护——**用一个 agent 的可用性，换掉了一个人的认证强度**。这笔账在排除列表复核（14.3）里几乎从来对不上，因为那份列表只记录了"某某账号因业务原因豁免"。

**形态 (b)：独立服务账号。** 一个 agent 一个账号，日志里能把 agent 与人区分开，撤销也能单独执行。代价有两条：一是账号数量随 agent 场景线性增长，每一个都要走 14.8.2 的五项元数据与到期复核，治理成本是实打实的；二是**授权是静态的**——账号开通时按当时的任务范围定权限，而 agent 的任务在变（换了提示、加了工具、接了新数据源），权限却停在开通那一刻。两条压力叠加，结果是实践中最常见的一种妥协：按这个 agent 可能承担的最大任务集一次性开权限，之后再不调整。

**形态 (c)：可委派的短时凭据。** agent 代表某个人执行时，向身份提供方换取一份受限的短时凭据，凭据本身携带四项事实——谁批准了这次委派、代表谁执行、能调哪些工具与哪些数据范围、有效期多久。任务结束即失效，下一次任务重新签发。它同时解决了形态 (b) 的两个问题：权限随任务变化，审计链条上人与 agent 都在。

**判断：(c) 是方向，但它能否落地不取决于身份团队，取决于被访问系统。** 委派链只有在后端能解析它、并按"委派人权限 ∩ agent 上界"做交集判定时才有意义；后端只认一个主体标识的，拿到委派令牌也只会退化成形态 (b)。多数企业的内部系统属于后者，改造排期又不在身份团队手里。因此当前阶段务实的目标是 **(b) + 严格的最小权限 + 强审计**，并在新建的、后端可控的系统上直接按 (c) 设计。

**从 (a) 迁到 (b) 的五步。** 顺序不能换：

1. **先发现，再动手。** 找出哪些人的凭据正在被 agent 使用。三个可用信号：同一个用户主体在非交互式登录里出现高频固定间隔的调用；某人的 API 密钥来自数据中心网段，与其常用终端对不上；条件访问排除列表里那些理由写着"自动化需要"的账号。产出是一张"人的账号 → agent 用途"对照表，它通常比预期长。
2. **用实际调用定权限上界。** 取该 agent 过去 90 天真实调用过的接口与数据范围作为新服务账号的上界，不要让负责人自己申报——申报的结果总是"和原来一样"。
3. **先让工具透传调用方身份。** 如果 agent 经由一层工具或网关访问后端，而这层用自己的高权限身份去访问，那么换成服务账号并不会缩小实际能力，只是换了个名字。这一步最容易被跳过，跳过则整次迁移白做。
4. **并行运行，再撤旧凭据。** 新旧身份同时可用两周量级，对比两条链路的调用差集，差集为空再撤销旧凭据。
5. **豁免与旧凭据同日撤销。** 第 1 步里为 agent 开的条件访问排除与旧协议认证，必须在旧凭据撤销的同一天回收。分两次做，第二次一定会忘。

```yaml
# agent 身份形态迁移登记：一个 agent 一条，与 14.8.2 的 NHI 台账同一份数据
agent_identity_migration:
  agent_id: agent-svc-ticket-triage-prod-01
  current_form: borrowed_human_credential
  target_form: dedicated_service_account
  borrowed_from:
    person_id: P-40b7c1de-2a55-4b83-91cc-7f6e2d0b8a31
    inherited_permission_count: 217
    observed_permission_count: 9
    conditional_access_exemptions:
      - exclude_from_device_compliance
      - allow_legacy_auth
  migration_gate:
    tool_inventory_frozen: true
    ceiling_from_observed_not_declared: true
    caller_identity_propagated: true
    audit_fields_present: true
  cutover:
    dual_run_days: 14
    old_credential_revoke_on: "2026-09-15"
    exemption_rollback_on: "2026-09-15"

# 形态 (c) 的委派令牌声明模板：谁委派、代表谁、能做什么、多久有效
delegated_agent_token_claims:
  iss: "https://idp.example.com"
  sub: "spiffe://example.com/ns/itsm/sa/triage-agent"
  act:
    sub: "P-40b7c1de-2a55-4b83-91cc-7f6e2d0b8a31"
    auth_time: "2026-08-01T09:12:44Z"
  delegation_approved_by: "P-9a1f0b32-88ce-4a17-b3d2-6e40c7215fa9"
  task_id: "task-2026-08-01-7f3a91"
  scope:
    tools: ["ticket.read", "ticket.tag", "ticket.assign"]
    data_scope: "tenant:internal-it"
  exp_seconds: 900
  renewable: false
  effective_permission_rule: intersection_of_delegator_and_agent_ceiling
```

怎么读这段登记：`migration_gate` 的四项是切换闸门，任何一项为 `false` 就不允许撤旧凭据。做成闸门的理由是迁移压力总是来自"赶紧把新账号切上去"，而这四项里最容易被牺牲的就是 `caller_identity_propagated`。`sub` 始终是 agent 自身的身份、`act.sub` 才是它代表的人，两者分开是委派链能被审计的全部理由。

**这段配置里有代价的设计选择**：`ceiling_from_observed_not_declared` 要求用观测值定上界，代价是漏授权——过去 90 天没跑到的季度末任务会在切换后失败。因此 `dual_run_days` 必须覆盖一个完整业务周期，跨季度的 agent 应当把它调到 90 天以上，照抄 14 会踩在季末上。

**照抄时最容易改错的三处**：一是把 `exp_seconds` 从 900 调大以"减少换票开销"，短时凭据的全部价值来自它短，调到小时级就等于回到形态 (b)；二是把 `act` 写成 agent 自身而把 `sub` 写成人，这个方向一旦写反，日志里就只剩人、agent 再次隐形；三是把 `exemption_rollback_on` 留空或推后，这一项没有技术依赖，纯靠纪律，也因此是实践中最常漏的一项。

**适用边界。** 这三种形态只覆盖 agent 访问企业内部系统这一侧。agent 调用外部模型服务时用的是服务商签发的 API 密钥，那属于 14.8.3 的静态密钥问题，与委派链无关。第二条边界：形态 (c) 只在"agent 代表某个具体的人执行"时成立；无人触发的定时任务型 agent 没有委派人，它只能停在形态 (b)，其权限上界由业务责任人显式承担，不能借某个人的身份充数。第三条边界是规模——agent 数量在十个以内时形态 (b) 的账号治理成本可以忽略，这里讨论的取舍在几十个以上才成立。

**验证方法。** 三项实测，都能在一周内做完。**身份归属抽查**：从 agent 的调用日志里随机取 20 次调用，逐一回答"这次调用在被访问系统的日志里表现为哪个主体"，答案里出现真人主体的即为形态 (a) 存量。**继承落差测量**：对每个仍处于形态 (a) 的 agent，算出借用人的权限总数与该 agent 过去 90 天实际用到的权限数，比值即超授权倍数。**撤销演练**：挑一个非关键 agent 按预案撤销其凭据，测量从撤销到调用真正失败的时延，并观察是否连带影响了借用人本人的工作——形态 (a) 下这两件事一定绑在一起。

**运行指标。** agent 身份独立率已在 14.8.9 列出，这里补三项过程指标：**形态分布**（(a)/(b)/(c) 各占多少，按季度看迁移速度）；**超授权倍数**的中位数与最大值（形态 (a) 的存量风险大小）；**为 agent 开设的条件访问排除项数量及其平均存续时长**——这一项与 14.3 的排除列表复核共用同一份数据，两边口径必须一致，否则两个团队会各报各的数。

## 14.8.7 检测与撤销

NHI 的检测与人类身份有本质差异：**没有"异常登录地点"这种直觉信号**，因为服务账号本来就在数据中心里、本来就在凌晨运行、本来就没有设备。可用的信号是行为模式的稳定性——NHI 的行为通常极其规律，任何偏离都值得关注：

| 信号 | 说明 |
|------|------|
| 调用来源变化 | 服务账号突然从新的 IP 段、新的云区域、新的用户代理发起调用 |
| 调用类型扩展 | 一个只读账号突然开始调用写接口，或开始枚举资源 |
| 调用量突变 | 日常每小时数百次，突然出现批量导出 |
| 认证方式变化 | 一直用证书的账号突然用密码认证 |
| 凭据新增 | 为某个应用主体添加了新的客户端密钥或证书——这是攻击者建立持久化的常用手法[1] |
| 授权范围变化 | 应用被授予了新的高权限范围，尤其是无需用户交互的应用级权限 |
| 长期沉睡后激活 | 半年无活动的服务账号突然使用 |

其中"凭据新增"与"授权范围变化"两条最值得优先落地，因为它们对应的是攻击链中的持久化步骤，且日志字段明确、误报可控。具体的检测规则与响应动作见 14.10。

这些信号的共同前提是**存在可用的调用日志且日志中带有身份标识**。这一点在实践中常常不成立：很多内部服务的访问日志只记录来源 IP，不记录调用者身份；云平台的数据面操作日志默认可能不开启或不保留。因此 NHI 检测的第一项工程投入往往不是写规则，而是补日志——这与 [11.3](../../第04部分_安全运营与防御能力/第11章_安全运营/11.3_威胁检测工程.md) 强调的"数据源覆盖先于规则"是同一条原则。

**撤销的难点在于影响面未知。** 一个稳妥的撤销序列是：先降级（收缩权限范围而非直接禁用）→ 观察调用失败情况 → 确认影响面 → 完全撤销。对疑似泄露的凭据则相反，必须立即撤销并接受业务中断——这个判断的分界线应当事先写进预案，而不是在事件发生时临时讨论。

## 14.8.8 失败叙事：我们强推 90 天轮换，结果制造了一套豁免体系

我们曾把"所有静态凭据 90 天轮换"写进安全基线，并配了自动化检查与不合规通报。方向没错，执行方式错了。

第一个月，不合规项 1,100 余条。团队开始处理，很快发现三类无法在 90 天内解决的情况：老旧应用的凭据写在配置文件里，改一次要停机；某些第三方 SaaS 集成的密钥轮换需要对方配合，走工单要三周；还有一批凭据没人知道在哪用，改了就可能出事。

于是豁免流程启动了。第三个月，豁免申请 300 余条；第六个月，累计豁免 700 余条，其中大部分是"永久豁免"，理由写着"技术限制"。**到第九个月，基线的实际状态是：能轮换的都轮换了（它们本来风险就低，因为已经自动化），不能轮换的全部豁免（它们才是高风险的那批）。** 我们用九个月的时间，把一个安全要求变成了一份高风险资产清单——如果当初直接做一份清单，成本只有九个月里的百分之一。

复盘后的三点调整：

第一，**先做能力，再提要求。** 把"应用能否在不重启的情况下热加载凭据"作为前置改造项，改造完成的应用才纳入轮换要求。改造清单本身成为一条工程路线图，而不是一份不合规通报。

第二，**分层而非统一。** 按凭据的影响面（能访问什么数据、什么环境）设定不同周期，把有限的推动力用在最高风险的那几十条上。

第三，**把豁免变成有代价的选项。** 豁免必须有到期日、必须有补偿控制（如调用来源白名单、异常调用告警、更严格的监控）、必须每季度复核。**当豁免比整改更麻烦时，豁免数量会自然下降。**

这次经历留下的一般性判断：**任何合规式的安全要求，如果目标系统缺少达成它的能力，最终产出的不是合规，而是一套精心维护的例外体系**。而例外体系的危害不只是风险留存，还在于它消耗了组织对安全要求的信任——下一次提要求时，第一反应会是"又来了，先申请豁免吧"。

## 14.8.9 度量

| 指标 | 定义 | 参考目标（示例口径） |
|------|------|------------------|
| NHI 台账覆盖率 | 已登记且五项元数据齐全的 NHI ÷ 发现的 NHI 总数 | > 95% |
| 无主 NHI 数 | 责任人离职或字段为空的 NHI | 0 |
| 静态长期凭据数 | 无有效期或有效期 > 1 年的凭据 | 持续下降，生产环境趋近 0 |
| 动态凭据占比 | 通过租约模式签发的凭据 ÷ 凭据总数 | > 50%（第二阶段目标） |
| 工作负载身份覆盖率 | 使用短期平台身份的工作负载 ÷ 工作负载总数 | 新建 100% |
| CI/CD 长期密钥数 | 流水线中仍存在的长期云凭据 | 0 |
| 凭据新增事件闭环率 | 应用主体新增凭据后完成核实的比例 | 100% |
| 轮换豁免数与年龄 | 有效豁免条数、平均存续时长 | 逐季下降；无永久豁免 |
| agent 身份独立率 | 拥有独立身份的 agent ÷ agent 总数 | 100% |

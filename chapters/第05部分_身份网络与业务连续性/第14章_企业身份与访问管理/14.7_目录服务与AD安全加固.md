# 14.7　目录服务与 Active Directory 安全加固

一个成立于 1999 年的企业，它的 AD 域大概率也是 1999 年建的。二十多年里，这个域经历过三次并购、五任基础架构负责人、无数次"临时给一下权限"、至少两轮"我们要迁移到云"。今天它承载着单点登录、文件共享、打印、证书、组策略、以及某个没人敢碰的 ERP 的认证。**它无法被关停，无法被重建，也从来没有被完整地梳理过。**

这就是 AD 安全的真实起点。它的风险不在于软件老旧——微软对 AD 的安全更新从未中断；风险在于**它的设计前提是"域内互信"**：域内任意一台机器的账号可以读取整个目录结构，任意一个用户可以枚举所有用户、所有组、所有服务主体名，任意一个具备特定 ACL 的对象可以静默地重置管理员密码。这些不是漏洞，是设计。在 1999 年这是合理的设计，在攻击者已经默认存在于内网的 2026 年，它意味着**一次普通工作站的陷落，与一次域控陷落之间的距离，取决于配置而不是取决于架构**。

本书第12章（红队实践）已经详细讲过这条路怎么走——Kerberoasting、DCSync、Pass-the-Hash、Golden Ticket 在 [12.2](../../第04部分_安全运营与防御能力/第12章_红队实践/12.2_红队方法论.md) 与 [12.3](../../第04部分_安全运营与防御能力/第12章_红队实践/12.3_红队工具与技术.md) 都有完整的攻击侧描述。本节是它的镜像：**同样这些技术，防御侧要关掉什么、怎么验证关掉了、以及关掉之后怎么度量**。

一个提前给出的核心判断：**AD 加固的度量单位是攻击路径条数，不是配置项数量。** 你可以关闭 40 个配置项而攻击路径一条没少，也可以只做三件事（LAPS、分层登录限制、krbtgt 轮换）就砍掉一多半路径。区分二者的唯一方法是把攻击面画成图（14.7.7）。

## 14.7.1 为什么 AD 仍然是攻击面的中心

三个原因，一个比一个隐蔽。

**第一，它还在。** 即使企业的办公套件、协作、大部分业务系统都已上云，本地 AD 仍在为文件服务器、打印、传统应用、终端加域提供认证。"我们已经上云了"通常意味着"我们现在有两套身份系统"，而不是"我们不再有 AD"。

**第二，云的信任根往往仍在本地。** 混合身份架构下，云目录中的用户来自本地 AD 同步；如果使用密码哈希同步或直通认证，本地凭据的陷落等于云身份的陷落；如果使用联邦（AD FS），**本地的令牌签名密钥可以伪造任意用户的云端断言**——这正是 2020 年那次供应链攻击中使用的 Golden SAML 手法[1]，攻击者甚至不需要用户的密码，也不受云端 MFA 的约束（因为断言里可以声称 MFA 已完成）。

**第三，负责 AD 的人和负责安全的人通常不是同一批人。** AD 归基础架构团队，KPI 是可用性与用户体验；任何加固动作都可能影响某个说不清楚的老应用，因此默认答案是"再评估评估"。这个组织现实比任何技术问题都更能解释"为什么这些配置十年没改"。

一个可以立刻自查的问题：**你的云全局管理员账号，是从本地 AD 同步上去的吗？** 如果是，那么你的云环境的安全上限，等于你本地 AD 的安全水平。修复方法在 14.7.8。

## 14.7.2 分层管理模型：Tier 0/1/2

分层是 AD 安全的骨架，其他所有措施都挂在它上面。它的思想只有一句话：**高权限凭据不得出现在低信任的机器上。**

### 三层的定义

| 层 | 内容 | 陷落后果 |
|----|------|---------|
| Tier 0 | 对整个身份基础设施拥有直接或间接控制权的资产 | 全域沦陷，恢复需要森林级操作 |
| Tier 1 | 服务器与业务应用、其数据 | 业务数据泄露与中断 |
| Tier 2 | 用户工作站与终端设备 | 单点陷落，是攻击的常规起点 |

关键在 Tier 0 的清单——它比大多数人想象的长得多，而**遗漏一项就等于整个分层失效**：

| Tier 0 资产 | 为什么 |
|------------|-------|
| 域控制器、只读域控 | 显然 |
| `krbtgt` 账号 | 持有它即可伪造任意票据 |
| Domain Admins / Enterprise Admins / Schema Admins / Administrators / Backup Operators / Account Operators / Server Operators / Print Operators | 直接或可提升为域级控制 |
| 具备目录危险 ACL 的任意主体 | 无需组成员资格即可提权（见 14.7.6） |
| AD FS 服务器与其令牌签名密钥 | 可伪造云端断言 |
| 目录同步服务器与其服务账号 | 通常拥有目录写权限与密码哈希访问能力 |
| 企业 PKI（CA 服务器、模板管理权限） | 可签发任意身份的证书（见 ADCS 部分） |
| 终端管理与软件分发平台 | 可向所有终端（含 Tier 0 工作站）下发代码 |
| 备份系统与备份存储 | 备份中含域数据库，可离线提取全部哈希 |
| 虚拟化平台（承载 DC 的宿主与管理控制台） | 可直接读取 DC 内存或复制虚拟磁盘 |
| DNS（AD 集成区域）管理权限 | 可劫持认证流量 |
| 安全平台管理控制台（EDR、SIEM 的响应能力） | 可下发命令或关闭可见性 |
| 特权访问工作站（PAW）本身 | 管理入口 |

**发现方法**：不要靠人工回忆。用"谁能改变谁"的可达性分析（14.7.7）把间接控制关系算出来，通常会发现三到五个从未被认为是 Tier 0 的系统——最常见的是备份系统、终端管理平台和虚拟化控制台。

### 三条铁律

1. **凭据不下行**：Tier 0 凭据绝不在 Tier 1/2 机器上使用。一次在普通工作站上的域管理员登录，就把域管哈希留在了那台机器的内存里。
2. **管理不上行**：低层不能管理高层。Tier 2 的管理员不得对 Tier 1/0 的资产拥有任何管理权。
3. **登录受限**：用技术手段强制上述两条，而不是靠管理规定。

第三条是关键——前两条是原则，只有第三条是控制。执行手段有三个层次：

**登录权限矩阵（GPO 用户权限分配）**：通过"拒绝本地登录/拒绝通过远程桌面服务登录/拒绝从网络访问此计算机/拒绝作为批处理作业登录/拒绝作为服务登录"五组策略，构造一张互斥矩阵。

| 目标机器 | 拒绝登录的主体 |
|---------|--------------|
| Tier 2 工作站 | Tier 0 管理组、Tier 1 管理组 |
| Tier 1 服务器 | Tier 0 管理组、Tier 2 管理组 |
| Tier 0（DC 与 PAW） | Tier 1 管理组、Tier 2 管理组、所有普通用户 |

**认证策略与认证策略仓（Authentication Policies / Silos）**：比 GPO 更强的机制——它在 Kerberos 层面约束"这个账号只能从这些机器认证"。把 Tier 0 账号放入一个策略仓，限定其只能从 PAW 发起认证，即使凭据泄露，攻击者在其他机器上也无法使用。这需要域功能级别 Windows Server 2012 R2 及以上，且账号需在 Protected Users 组中获得最佳效果。

**特权访问工作站（PAW）**：管理 Tier 0 的操作必须在专用的、加固的、不用于收发邮件与上网的机器上进行。PAW 不是"装了很多安全软件的笔记本"，它的核心特征是**减少暴露面**：不上网、不收邮件、只允许运行管理工具、独立的更新与管理通道。

**生产坑：分层做了一半比不做更危险。** 常见形态是——建立了 Tier 0 组和 PAW，但域管理员日常仍用自己的普通账号处理邮件，需要时"提升"一下；或者 PAW 通过普通的终端管理平台管理（而那个平台是 Tier 2 可控的）。这两种情况下，分层只增加了操作复杂度，没有减少任何一条攻击路径。**验证分层是否真的成立，唯一可靠的方法是做一次路径分析，看是否还存在从 Tier 2 到 Tier 0 的边。**

## 14.7.3 ESAE / Red Forest 的现状：一个需要纠偏的"最佳实践"

很多企业的 AD 安全方案里仍然写着"建设 ESAE 红森林"。这条建议在今天需要被明确纠正。

ESAE（Enhanced Security Administrative Environment，俗称 Red Forest）是微软早年提出的架构：建立一个独立的、高度加固的管理森林，生产森林信任它，所有特权管理账号存放在管理森林中。它在设计上是有效的，但**微软已将 ESAE 从通用推荐中撤回**（微软文档明确写着 ESAE 已被现代特权访问策略取代、"不再是推荐架构"，但没有标注撤回年份；流传的"2021 年起"没有一手出处，做合规陈述时不要引用这个年份），理由是：绝大多数企业的实际风险来自尚未落实的基础控制（分层登录限制、LAPS、特权工作站、云端特权管理），而 ESAE 的建设成本极高、运维复杂，投入产出比在多数场景下不成立；取而代之的是**企业访问模型（Enterprise Access Model）**，其核心变化是把特权管理的控制平面上移到云身份平台（配合按需提权与特权工作站），而非再建一片本地森林[2]。

**判断：不要新建 ESAE。** 除非同时满足三个条件——存在极端保障需求（如与国家安全相关的隔离环境）、无法使用云身份服务、且已经完整落实了本节其余全部基础控制。这三个条件同时成立的企业极少。

已经建成 ESAE 的企业不必推倒重来，但应当重新评估它的边际价值：管理森林是否真的隔离（还是通过某个管理工具与生产森林互通）、它的运维是否已经沦为形式、以及它是否让基础控制（LAPS、分层、krbtgt 轮换）被推迟了。**见过的最糟情形是：企业花两年建了红森林，同时全域仍在使用同一个本地管理员密码。**

替代路径（按优先级）：

1. 落实分层登录限制与 PAW（14.7.2）——投入最小，砍掉的路径最多。
2. 部署 LAPS（14.7.4）——消灭横向移动的高速公路。
3. 把特权管理上移到云端的按需提权机制（配合 14.6 的 JIT），并确保云特权账号与本地 AD 解耦（14.7.8）。
4. 关闭 14.7.5、14.7.6 的具体攻击面。

## 14.7.4 LAPS：先修这一条高速公路

本地管理员密码复用是 AD 环境中最有效、也最常见的横向移动手段。攻击者在一台工作站上拿到本地管理员哈希后，可以直接用它认证到其他所有使用相同密码的机器——不需要域凭据，不触发域侧的登录异常，一台接一台。

Windows LAPS（Local Administrator Password Solution）解决这个问题：为每台机器生成随机的本地管理员密码，定期自动轮换，密码存储在目录中并按需授权读取。**自 2023 年起 Windows LAPS 已内置于 Windows 与 Windows Server（通过更新分发），取代了早期需单独安装的 Legacy LAPS**[3]。

### 关键决策点

| 决策 | 选项 | 建议 |
|------|------|------|
| 后端存储 | 本地 AD / 云目录 | 加域机器用 AD；纯云管理的设备用云目录；混合环境两者并存 |
| 密码加密 | Windows LAPS 支持在目录中加密存储 | 启用。Legacy LAPS 的密码属性为明文，仅靠 ACL 保护 |
| 密码复杂度与长度 | 可配置 | 不少于 20 字符，含全字符集 |
| 轮换周期 | 可配置 | 30 天以内；且**使用后立即轮换**（Windows LAPS 支持读取后自动轮换） |
| DSRM 账号 | 可纳入管理 | 纳入。目录服务恢复模式密码常年不变是一个被忽视的后门 |
| 读取授权 | 按 OU 委派 | 最小化；服务台只授予其负责的 OU |

### 部署检查表

1. 确认操作系统已具备 Windows LAPS 能力；混用环境需规划与 Legacy LAPS 的共存与迁移。
2. 更新 AD 架构（schema）以支持新属性，并按 OU 委派读取权限。
3. 通过组策略或终端管理平台下发策略：密码复杂度、长度、轮换周期、读取后轮换、加密主体。
4. **审计现有的读取权限**——这是最容易出问题的一步，见下面的生产坑。
5. 验证：随机抽取若干台机器，确认密码已写入目录、值互不相同、且在到期后确实变化。
6. 建立读取审计：谁在什么时候读了哪台机器的密码，必须可查。

```powershell
# 验证 LAPS 覆盖与密码新鲜度（示例，需按环境调整属性名与筛选范围）
# 1) 列出未纳入 LAPS 管理的计算机（无密码到期时间属性）
Get-ADComputer -Filter {Enabled -eq $true -and OperatingSystem -like "*Windows*"} `
  -Properties msLAPS-PasswordExpirationTime, OperatingSystem |
  Where-Object { -not $_."msLAPS-PasswordExpirationTime" } |
  Select-Object Name, OperatingSystem |
  Sort-Object Name

# 2) 列出密码已过期但未轮换的机器（通常是长期离线设备）
$now = (Get-Date).ToFileTimeUtc()
Get-ADComputer -Filter {Enabled -eq $true} -Properties msLAPS-PasswordExpirationTime |
  Where-Object { $_."msLAPS-PasswordExpirationTime" -and
                 [int64]$_."msLAPS-PasswordExpirationTime" -lt $now } |
  Select-Object Name

# 3) 审计谁被授予了读取密码的权限（重点排查继承而来的过宽授权）
$ou = "OU=Workstations,DC=corp,DC=example,DC=com"
(Get-Acl -Path "AD:$ou").Access |
  Where-Object { $_.ObjectType -ne [guid]::Empty -and
                 $_.ActiveDirectoryRights -match "ExtendedRight|ReadProperty" } |
  Select-Object IdentityReference, ActiveDirectoryRights, ObjectType, IsInherited |
  Sort-Object IdentityReference
```

**生产坑一：读取权限的意外扩散。** LAPS 密码的读取依赖目录 ACL。如果某个 OU 上曾经授予过"所有扩展权限（All Extended Rights）"给一个宽泛的组（例如服务台组，或某个历史遗留的委派），那么该组的所有成员都能读取该 OU 下所有机器的本地管理员密码——**攻击者攻陷一个服务台账号就等于拿到了半个企业的本地管理员权限**。部署 LAPS 前必须先做一次 ACL 审计，这一步比部署本身更重要。

**生产坑二：以为部署了就覆盖了。** 长期离线的设备（出差笔记本、备用机、实验室机器）不会轮换密码，它们保留着部署前的旧密码——而那个旧密码往往是全域复用的那一个。因此覆盖率必须按"密码在近 N 天内成功轮换过的机器数"来统计，而不是按"应用了策略的机器数"。

**生产坑三：服务器被排除在外。** 很多企业只在工作站部署 LAPS，理由是"服务器由专人管理"。但横向移动路径通常是工作站→服务器→域控，服务器的本地管理员密码复用同样致命。除域控外（域控没有本地管理员账号参与域认证的同类问题，但有 DSRM 密码），成员服务器应一并纳入。

## 14.7.5 GPO 基线：值得优先关闭的加固项

下表按"投入产出比"排序，前六项应当在任何 AD 加固项目的第一阶段完成。每一项都给出防御目标与验证方法。

| 加固项 | 防的是什么 | 验证方法 | 生产坑 |
|-------|-----------|---------|-------|
| 部署 LAPS（14.7.4） | 本地管理员密码复用横移 | 抽样比对多台机器密码不同 | 见上节三坑 |
| 分层登录限制（14.7.2） | 高权限凭据落到低信任机器 | 用 Tier 0 账号尝试登录 Tier 2 机器应失败 | 做一半等于没做 |
| 启用 SMB 签名（要求而非仅启用） | SMB 中继攻击 | 用抓包或配置查询确认 `RequireSecuritySignature` | 老旧存储设备可能不支持，需逐一测试 |
| 禁用 SMBv1 | 老旧协议漏洞与中继 | 查询可选功能状态 | 极老的打印机与扫描仪可能依赖 |
| LDAP 签名与通道绑定 | LDAP 中继获取目录写权限 | 先用审计模式统计不合规客户端[4] | 直接强制会打断老应用，必须先审计 |
| 域控上禁用 Print Spooler | 打印服务相关的强制认证与提权 | 服务状态查询 | 仅当 DC 确实不承担打印角色 |
| Protected Users 组 | 高权限账号的凭据缓存与弱加密 | 成员登录后确认不再使用 NTLM/RC4 | 组内账号不能用于服务、不能委派，加入前须确认 |
| 禁用 WDigest 明文缓存 | 内存中明文密码 | 注册表项校验 | 现代系统默认已禁用，但老镜像可能仍开启 |
| Credential Guard | LSASS 凭据窃取 | 系统信息中确认运行状态 | 与部分虚拟化/驱动不兼容，需兼容性测试 |
| `ms-DS-MachineAccountQuota` 设为 0 | 普通用户创建机器账号后滥用（RBCD 等） | 查询域对象属性 | 需要为合法的加域流程提供替代授权 |
| 清理 Pre-Windows 2000 Compatible Access 组 | 匿名/低权限枚举目录 | 检查组成员是否含 Authenticated Users / Anonymous | 极老的应用可能依赖 |
| 限制匿名枚举（RestrictAnonymous 系列） | 用户与共享枚举 | 用匿名会话尝试枚举应失败 | 部分文件共享场景受影响 |
| 禁用 LM 与 NTLMv1 | 弱哈希离线破解与中继 | 审计日志中统计使用情况 | 老设备（如某些一体机）可能仅支持 NTLMv1 |
| 限制本地账号的网络登录 | 本地管理员横移（与 LAPS 互补） | 用本地账号尝试网络认证应失败 | 部分运维脚本依赖本地账号 |
| PowerShell 脚本块日志与转录 | 攻击可见性 | 抽查日志中是否记录脚本内容 | 日志量大，需规划存储 |
| 清理 AdminSDHolder 遗留 | `adminCount=1` 但已不在特权组的对象权限异常 | 查询 `adminCount=1` 且不在任何特权组的账号 | 需人工确认后逐个处理 |
| 禁用无约束委派 | 票据窃取导致的域内提权 | 查询 `TrustedForDelegation` 为真的主机 | 老应用可能依赖，需改为约束委派 |
| DC 的 RDP 与管理入口限制 | 直接登录域控 | 尝试从非 PAW 发起 RDP 应被拒 | 需先建好 PAW |

### 域控本身：它不只是一台服务器

上表中的多数项面向全域，但域控还需要一组专属约束。它们不涉及复杂技术，却经常在"服务器就该统一管理"的惯性下被忽略：

- **域控上不安装任何其他角色与软件**。不做文件服务器、不做打印服务器、不装业务代理、不装非必要的监控与备份代理。每多一个组件，就多一条以 SYSTEM 权限运行的代码路径。
- **管理入口只允许来自 PAW**。域控的远程桌面与远程管理端口不应对普通网段开放，这需要网络层配合。
- **出站流量限制**。域控通常没有理由主动访问互联网。限制其出站不仅降低数据外带风险，也让 C2 通道更容易暴露。
- **虚拟化层的保护**。承载域控的虚拟化宿主与管理控制台属于 Tier 0——能复制虚拟磁盘或读取内存快照的人，等价于域管理员。虚拟域控的存储与快照必须加密并限制访问。
- **物理与备份介质**。域数据库文件（`ntds.dit`）加上系统密钥即可离线导出全部哈希，因此备份介质的保护等级必须与域控本身相同。这是备份系统被列为 Tier 0 的直接原因。
- **补丁节奏单列**。域控的补丁不应与普通服务器同批次，涉及认证协议的安全更新应有独立的加速通道与回退预案。
- **只读域控（RODC）的定位**。RODC 适用于物理安全无法保证的分支站点，但它不是"更安全的 DC"——凭据缓存策略配置不当仍会泄露账号哈希，且它默认可读取目录结构。把它当作降低分支风险的手段，不要当作加固手段。

**关于 NTLM 的分阶段收敛**：直接在域中禁用 NTLM 是本节最容易引发事故的操作。正确的路径是三步——第一步开启 NTLM 审计（记录但不阻断），持续 4～8 周覆盖月度与季度任务；第二步按审计结果逐个改造或加入例外白名单；第三步在特定范围（先域控、再服务器、最后全域）逐步阻断。14.7.10 记录了一次跳过第一步的后果。

## 14.7.6 攻击的防御侧收敛

这是本节的核心。下面按攻击技术组织，每一条给出**前置条件（攻击者需要什么）→ 收敛手段（拿掉哪个前置条件）→ 检测 → 验证**。防御的逻辑始终是拿掉前置条件，而不是试图识别攻击行为本身。

### Kerberoasting（T1558.003）

**前置条件**：任意有效域账号 + 存在注册了 SPN 的用户账号 + 该账号密码可离线破解（弱口令或 RC4 加密的票据）。

**收敛手段**（按有效性排序）：

1. **用组托管服务账号（gMSA）替代普通服务账号**。gMSA 的密码由系统管理、长度极高且自动轮换，离线破解在计算上不可行。这是根治手段。
2. 无法使用 gMSA 时，服务账号密码长度不少于 25 字符且随机生成——Kerberoasting 的价值完全来自离线破解的可行性。
3. **禁用 RC4，强制 AES**。RC4 加密的服务票据（事件 4769 中加密类型 `0x17`）是最易破解的形态；把服务账号的 `msDS-SupportedEncryptionTypes` 设为仅 AES，并在域级逐步淘汰 RC4。
4. **清理不必要的 SPN**，尤其是注册在**特权账号**上的 SPN——域管理员账号带 SPN 是最高危的组合，它把"破解一个服务账号口令"直接变成"拿到域管"。
5. 部署**蜜罐 SPN 账号**：创建一个名字诱人（如 `svc_sql_backup`）、密码极长、无任何实际权限、永不使用的账号并注册 SPN。任何针对它的服务票据请求都是高置信度的攻击信号，误报率接近零。

**检测**：

```yaml
title: Kerberoasting via RC4 Service Ticket Requests
id: 7c1a5b93-6f24-4d18-9a0c-3b8e2f5c7d41
status: experimental
description: 检测短时间内大量 RC4 加密的服务票据请求，或针对蜜罐 SPN 的任意请求
references:
  - https://attack.mitre.org/techniques/T1558/003/
logsource:
  product: windows
  service: security
detection:
  ticket_request:
    EventID: 4769
    TicketEncryptionType: '0x17'
    TicketOptions: '0x40810000'
  exclude_machine_accounts:
    ServiceName|endswith: '$'
  honeypot:
    EventID: 4769
    ServiceName: 'svc_sql_backup'
  timeframe: 10m
  condition: (ticket_request and not exclude_machine_accounts) or honeypot
falsepositives:
  - 仍在使用 RC4 的遗留应用
  - 漏洞扫描器与资产发现工具
level: high
tags:
  - attack.credential_access
  - attack.t1558.003
```

这条规则的两半有完全不同的性质：`ticket_request` 那一半依赖阈值与基线，误报取决于环境中还有多少 RC4 残留（这也解释了为什么"禁用 RC4"同时是加固手段和检测降噪手段）；`honeypot` 那一半不需要阈值也几乎不会误报，**是投入产出比最高的一条 AD 检测规则**。部署时把蜜罐账号的名称改成符合本企业命名习惯的形式，否则有经验的攻击者会识别出来。

**验证**：用红队工具请求一批服务票据，确认告警触发；查询域内是否仍存在带 SPN 的特权账号（应为零）。

### AS-REP Roasting（T1558.004）

**前置条件**：存在设置了"不要求 Kerberos 预身份验证"（`DONT_REQ_PREAUTH`）的账号。

**收敛**：把这个数字降到零，并把它纳入每日检查——这是一个"应当永远为零"的指标。极少数遗留应用会要求它，此时该账号必须使用极长随机密码并纳入监控。

### Pass-the-Hash / Pass-the-Ticket（T1550.002 / T1550.003）

**前置条件**：在攻击者可控的机器上存在可提取的凭据材料（NTLM 哈希、Kerberos 票据），且该凭据在别处仍然有效。

**收敛**：这是一组组合拳，单一措施都不足够。

1. **分层登录限制**（14.7.2）：让高价值凭据不出现在低信任机器上——这是最根本的一条。
2. **LAPS**（14.7.4）：让本地管理员哈希只对单台机器有效。
3. **Credential Guard**：把凭据隔离到虚拟化保护的容器中，使内存提取失效（需硬件支持与兼容性测试）。
4. **Protected Users 组**：组内成员不使用 NTLM、不缓存凭据、票据生命周期缩短。
5. **限制本地账号的网络登录**：即使拿到本地管理员哈希，也无法用它做远程认证。
6. **禁用 WDigest**：消除内存中的明文密码。

**验证**：在一台 Tier 2 机器上用域管理员账号登录（测试环境），确认该操作被策略拒绝；用已知哈希尝试对另一台机器做网络认证，确认失败。

### DCSync（T1003.006）

**前置条件**：某个主体拥有目录复制权限（`DS-Replication-Get-Changes` 与 `DS-Replication-Get-Changes-All`）。

**收敛**：**枚举并最小化拥有这两项权限的主体**。默认只有域控、域管理员组与少数同步服务账号应当拥有。实践中经常发现意外的持有者——历史遗留的同步账号、某个备份产品的服务账号、以及某次委派操作误授予的组。

```powershell
# 枚举域根上被授予复制权限的主体（DCSync 的前置条件）
$dn = (Get-ADDomain).DistinguishedName
$repl = @{
  "DS-Replication-Get-Changes"     = "1131f6aa-9c07-11d1-f79f-00c04fc2dcd2"
  "DS-Replication-Get-Changes-All" = "1131f6ad-9c07-11d1-f79f-00c04fc2dcd2"
}
(Get-Acl -Path "AD:$dn").Access |
  Where-Object { $_.ObjectType -in $repl.Values -and $_.AccessControlType -eq "Allow" } |
  Select-Object IdentityReference,
                @{n="Right";e={ ($repl.GetEnumerator() |
                    Where-Object { $_.Value -eq $PSItem.ObjectType }).Key }},
                IsInherited |
  Sort-Object IdentityReference
```

**检测**：11.3.8 已给出基于事件 4662 与上述两个 GUID 的 Sigma 规则，本节不重复。要补充的一点是：**检测规则的白名单必须按"已知同步账号 + 域控机器账号"精确构造，并且这份白名单本身要纳入变更审计**——攻击者若能悄悄把自己加进白名单，检测就失效了。

### Golden Ticket（T1558.001）与 krbtgt 轮换

**前置条件**：`krbtgt` 账号的密码哈希。

**收敛**：无法阻止拥有哈希者伪造票据，只能**让哈希失效**。`krbtgt` 密码需要**连续重置两次**才能真正使旧票据失效（AD 保留前一版本密码用于兼容），且两次之间必须留出足够间隔——至少大于最大票据生命周期（默认 10 小时）加上完整的域复制收敛时间，实践中建议间隔 24 小时以上并确认所有 DC 复制完成。

轮换时机：**定期**（建议不超过 180 天）+ **事件触发**（任何疑似域控陷落、任何 Tier 0 人员离职、任何域管理员账号疑似泄露）。

一个容易被忽略的点：**两次重置之间如果间隔太短，会导致大范围认证失败**（未刷新的票据同时失去两个版本的密码）；而如果只重置一次就宣告完成，攻击者手中的旧哈希仍然有效——这两种错误都很常见，前者制造事故，后者制造虚假的安全感。轮换必须走变更流程、在低峰期执行、并预先通知服务台。

### Silver Ticket 与 DCShadow

**Silver Ticket**（T1558.002）：用服务账号哈希伪造服务票据，不经过域控。收敛手段与 Kerberoasting 同源——gMSA、强密码、AES；此外在支持的服务上启用 PAC 验证可增加难度。

**DCShadow**：攻击者把自己注册为一个"域控"，从而推送任意目录变更且绕过常规审计。收敛手段是限制注册 DC 的能力（本质上是限制 Tier 0 权限），检测手段是监控配置分区中 `nTDSDSA` 对象的新增，以及非预期主机发起的复制请求。

### 基于委派的提权：RBCD 与无约束委派

**无约束委派**：被授予该属性的主机会缓存访问它的用户的 TGT，攻击者控制该主机后即可窃取。收敛：清查 `TrustedForDelegation` 为真的主机（域控除外），改造为约束委派或基于资源的约束委派。

**基于资源的约束委派（RBCD）滥用**：攻击者若能修改目标机器的 `msDS-AllowedToActOnBehalfOfOtherIdentity` 属性，即可以任意用户身份访问该机器。前置条件通常是"能创建机器账号"（默认 `ms-DS-MachineAccountQuota` 为 10）或"对目标对象有写权限"。收敛：把配额设为 0，并监控该属性的变更事件（目录服务对象修改事件 5136）。

### AD 证书服务（ADCS）：被低估的一整类路径

企业 PKI 常常不被视为身份基础设施，但一张能用于客户端认证的证书就等于一份身份凭据，且证书的有效期通常以年计——**它是比密码更持久的后门**。公开研究已系统梳理了模板与配置层面的多类提权路径[5]。

收敛的要点（不逐条罗列攻击编号，只给防御动作）：

1. **审计所有可用于客户端认证的证书模板**，重点检查三个组合：是否允许申请者自行指定主体备用名（SAN）、注册权限是否过宽（如 Domain Users 可申请）、是否要求管理员审批。这三者同时成立即为高危。
2. **关闭 CA 上的 `EDITF_ATTRIBUTESUBJECTALTNAME2` 标志**，它允许在任意模板上附加 SAN，影响面覆盖全部模板。
3. **保护 CA 服务器本身与其私钥**，按 Tier 0 管理；CA 管理员权限视同域管理员。
4. **加固证书注册的 Web 接口**：禁用不必要的 HTTP 注册端点，为必须保留的启用扩展保护（EPA）与 HTTPS，防止 NTLM 中继到注册接口。
5. **落实强证书映射**：证书与账号的映射必须是强绑定（含证书序列号或 SID 扩展），弱映射（仅凭主体名或邮箱匹配）允许攻击者用一张自签内容匹配的证书冒充他人。微软已通过 KB5014754 引入相关加固并进入完全强制阶段，环境中若存在依赖弱映射的老证书，需在此之前完成换发[6]。
6. **监控证书签发**：对可用于客户端认证的模板，签发事件应当可追溯到申请人与审批记录；异常签发（非常规时间、非常规申请者、SAN 与申请者不符）应告警。

**判断：ADCS 是当前 AD 攻击面中"存量最大、被治理最少"的一块。** 原因是它通常由另一个团队（PKI 或基础架构）管理，安全团队既不熟悉也没有权限，而它的配置往往在十年前完成后就再没动过。做一次全面的模板审计，通常能在一天内发现至少一条从普通用户到域管理员的路径。

## 14.7.7 AD 攻击面度量：以攻击路径为单位

现在回到本节开头的核心判断。要证明加固有效，需要能回答一个问题：**"从任意一台普通工作站到域管理员，现在还有多少条路径，最短几跳？"**

这需要把 AD 建成一张图：节点是用户、组、计算机、GPO、OU、证书模板；边是"谁能控制谁"的关系（组成员、ACL 写权限、密码重置权、本地管理员、会话中存在的凭据、GPO 链接、委派关系）。开源的图分析工具（BloodHound 及其数据采集器）已经把这套建模标准化，蓝队完全可以自行运行——它不是红队专属工具[7]。

### 指标集

| 指标 | 定义 | 目标（示例口径） |
|------|------|---------------|
| 到 DA 的攻击路径条数 | 从 Tier 2 起点可达域管理员的路径数 | 逐轮下降，最终趋近于 0 |
| 最短路径跳数 | 上述路径中的最小跳数 | ≥ 4（越大越好） |
| 高价值目标可达用户占比 | 能够（间接）控制 Tier 0 的普通用户比例 | < 1% |
| Tier 0 组成员数 | 各特权组成员总数 | 每个组个位数，且全部可解释 |
| krbtgt 密码年龄 | 距上次重置的天数 | < 180 天 |
| 带 SPN 的特权账号数 | 特权组成员中注册了 SPN 的账号 | 0 |
| `DONT_REQ_PREAUTH` 账号数 | 关闭预认证的账号 | 0 |
| 无约束委派主机数 | 域控之外的无约束委派主机 | 0 |
| 密码永不过期的特权账号数 | — | 0 |
| `adminCount=1` 孤儿数 | 标记为特权但已不在特权组的对象 | 0 |
| LAPS 有效覆盖率 | 近 30 天成功轮换过密码的机器 ÷ 应覆盖机器 | > 98% |
| Protected Users 覆盖率 | Tier 0 账号加入该组的比例 | 100% |
| 非 Tier 0 账号在 DC 上的登录次数 | 每周统计 | 0 |
| 复制权限持有者数 | 拥有 DCSync 所需权限的主体 | 仅 DC 与已登记的同步账号 |
| 高危 ACL 边数 | 图中"低权限可控制高权限"的边 | 逐轮下降 |

```python
"""AD 攻击面评分：从图数据计算路径类与配置类指标。

输入是一份已归一化的图导出（节点 + 边），例如从图分析工具导出的 JSON。
输出两类结果：
1. path_metrics —— 到高价值目标的路径条数与最短跳数
2. config_findings —— "应当为零"的配置类指标

设计取舍：路径枚举做深度上限与条数上限，避免在大型域中组合爆炸；
目的是趋势度量而非穷举证明。
"""
from collections import defaultdict, deque
from typing import Dict, Iterable, List, Set, Tuple

# 边类型 -> 是否构成"控制"关系（可用于提权）
CONTROL_EDGES = {
    "MemberOf", "AdminTo", "GenericAll", "GenericWrite", "WriteDacl",
    "WriteOwner", "Owns", "ForceChangePassword", "AllExtendedRights",
    "AddMember", "HasSession", "AllowedToDelegate", "AddKeyCredentialLink",
}


class AdGraph:
    def __init__(self) -> None:
        self.adj: Dict[str, Set[Tuple[str, str]]] = defaultdict(set)
        self.node_attrs: Dict[str, Dict[str, object]] = {}

    def add_node(self, node_id: str, **attrs) -> None:
        self.node_attrs.setdefault(node_id, {}).update(attrs)

    def add_edge(self, src: str, dst: str, edge_type: str) -> None:
        if edge_type in CONTROL_EDGES:
            self.adj[src].add((dst, edge_type))

    def shortest_paths(
        self, sources: Iterable[str], targets: Set[str],
        max_depth: int = 8, max_paths: int = 5000,
    ) -> Dict[str, object]:
        """广度优先枚举，返回路径条数、最短跳数与前若干条示例路径。"""
        found: List[List[str]] = []
        best_depth = None
        for src in sources:
            queue = deque([(src, [src], {src})])
            while queue and len(found) < max_paths:
                node, path, seen = queue.popleft()
                if len(path) - 1 >= max_depth:
                    continue
                for nxt, _etype in self.adj.get(node, ()):
                    if nxt in seen:
                        continue
                    new_path = path + [nxt]
                    if nxt in targets:
                        found.append(new_path)
                        depth = len(new_path) - 1
                        best_depth = depth if best_depth is None else min(
                            best_depth, depth
                        )
                        continue
                    queue.append((nxt, new_path, seen | {nxt}))
        return {
            "path_count": len(found),
            "shortest_hops": best_depth,
            "sample_paths": found[:10],
            "truncated": len(found) >= max_paths,
        }

    def zero_target_findings(self) -> Dict[str, List[str]]:
        """"应当为零"的配置类指标：任何非空结果都是待办项。"""
        out: Dict[str, List[str]] = defaultdict(list)
        for node, attrs in self.node_attrs.items():
            if attrs.get("unconstrained_delegation") and not attrs.get("is_dc"):
                out["unconstrained_delegation"].append(node)
            if attrs.get("dont_req_preauth"):
                out["dont_req_preauth"].append(node)
            if attrs.get("has_spn") and attrs.get("is_privileged"):
                out["privileged_account_with_spn"].append(node)
            if attrs.get("password_never_expires") and attrs.get("is_privileged"):
                out["privileged_password_never_expires"].append(node)
            if attrs.get("admin_count") and not attrs.get("in_privileged_group"):
                out["admincount_orphan"].append(node)
        return dict(out)


def score(graph: AdGraph, tier2_sources: Iterable[str],
          tier0_targets: Set[str]) -> Dict[str, object]:
    paths = graph.shortest_paths(tier2_sources, tier0_targets)
    findings = graph.zero_target_findings()
    zero_violations = sum(len(v) for v in findings.values())
    return {
        "path_count": paths["path_count"],
        "shortest_hops": paths["shortest_hops"],
        "zero_target_violations": zero_violations,
        "findings": findings,
        "sample_paths": paths["sample_paths"],
        "note": "path_count 用于趋势对比，不同采集范围之间不可直接比较",
    }
```

怎么读这段代码：`CONTROL_EDGES` 这个集合是全部分析的核心假设——它定义了"什么算控制关系"。其中 `ForceChangePassword`、`WriteDacl`、`AddKeyCredentialLink` 这几类经常被忽略，但它们提供的提权能力与直接的组成员资格等价，**遗漏它们会让攻击面报告显得比实际乐观得多**。`max_paths` 与 `max_depth` 的截断是刻意的：在大型域中路径数可能是天文数字，穷举没有意义，而趋势（这个月比上个月少了多少）才是有用的信息。最后那句 `note` 提醒了一个常见误用——采集范围变化会让路径数剧烈波动，跨期对比必须保证采集口径一致，否则"路径数下降 60%"可能只是因为这次少采了几台机器。

**运行节奏建议**：每月采集一次，每季度出一次趋势报告；每次加固动作前后各跑一次，用路径数的变化来证明该动作的价值——**这是向管理层证明 AD 加固投入产出比的最有效方式**，比"我们完成了 37 项配置加固"有说服力得多。

### 与红队/紫队的协同

图分析给出的是"理论上存在的路径"，它有两类误差：一是把实际不可用的边算了进来（例如某台机器上的会话早已结束），二是漏掉了图模型没有表达的路径（应用层漏洞、明文凭据文件、共享盘里的脚本）。因此攻击面度量必须与实际演练互相校准：

- 图分析先给出**候选路径清单**，紫队按清单逐条验证可达性，把不可达的边从模型中修正掉——这比让红队从零摸索高效得多。
- 红队演练发现的、图模型未预测到的路径，要反过来补进模型（通常意味着需要新增一类边或一类节点属性）。
- 每次加固后，选取被修复的那几条路径做定向复测，确认它们真的断了而不是换了一跳。

这套协同方式与 [12.5 紫队协作与检测能力建设](../../第04部分_安全运营与防御能力/第12章_红队实践/12.5_紫队协作与检测能力建设.md) 的方法论一致：**把攻击视角的产出转化为可持续度量的防御指标**，而不是让每次演练都从一份新报告开始。一个务实的节奏是每半年一次针对 AD 的定向演练，范围限定为"从标准工作站到 Tier 0"，输出只有两个数字——是否达成、用了多久。这两个数字比任何评分模型都更能说明问题。

## 14.7.8 混合身份的接缝：把云的控制平面解耦

如果本节只能记住一条建议，应当是这条：**云身份的特权账号必须是云原生账号，不得从本地 AD 同步。**

理由很直接。混合环境中存在几个"跨越边界"的组件，它们同时属于本地和云，因此它们的陷落会双向传导：

| 组件 | 风险 | 应对 |
|------|------|------|
| 目录同步服务器与其服务账号 | 拥有目录高权限与密码哈希访问能力，常驻本地网络 | 视同 Tier 0：专用服务器、限制登录、不装其他软件、账号纳入 PAM |
| 联邦服务（AD FS）令牌签名密钥 | 可伪造任意云身份的断言，绕过云端 MFA[1] | 优先迁移到云原生认证；仍需联邦的，密钥存 HSM、定期轮换、监控签名密钥导出行为 |
| 无缝单点登录的计算机账号 | 其密码若长期不轮换，可被用于伪造服务票据 | 纳入轮换计划（建议 30 天） |
| 从本地同步的云管理员账号 | 本地陷落直接等于云管理员陷落 | **改为云原生账号**，仅用于云端管理，配抗钓鱼认证器与 PAW |
| 密码哈希同步 | 本地哈希泄露可用于云端 | 与云端风险检测联动；特权账号不参与同步 |

"云管理员账号云原生化"这条建议的落地阻力通常来自便利性——管理员不想为云端维护第二套账号。但这正是要点：**第二套账号意味着两个独立的沦陷条件**。当本地 AD 被完全控制时，如果云端特权是独立的、用抗钓鱼认证器保护的、从 PAW 访问的，那么企业至少还保有云端的控制权与恢复能力；否则一次域控陷落就是全局归零。

同样的逻辑适用于**破玻璃账号**（14.6.7）：它必须是云原生的、不依赖本地 AD 的，否则本地故障时它同样不可用。

### 跨林信任的收敛

14.1.1 提到，并购期建立的林信任会在此后数年成为最大的攻击面。原因是**默认的双向林信任意味着两边的特权是等价的**：被并购方的域管理员可以在你的森林中获得等价权限，而你对他们的安全水平一无所知——而被并购公司的安全成熟度通常低于收购方，否则也不会是被收购的一方。

三项必须落实的收敛手段：

**SID 过滤（SID Filtering）**：默认情况下，跨信任传递的认证令牌中可以携带来自其他域的 SID（SID History 机制原本用于域迁移）。若不过滤，对方森林中的攻击者可以在令牌中注入你的域管理员 SID，从而直接获得你的域的最高权限。除非正在进行有明确期限的迁移，否则应当保持 SID 过滤启用，并在迁移完成后立即恢复。**"为了迁移方便临时关闭"是这类风险的最常见来源，而"临时"通常意味着永久。**

**选择性认证（Selective Authentication）**：默认的林信任下，对方森林的用户对本森林的资源具有"已认证用户"的身份，可以广泛访问。选择性认证把这个默认改成"逐资源显式授权"——对方主体必须被明确授予"允许身份验证"权限才能访问某台服务器。代价是配置工作量增加，收益是把信任的爆炸半径从"整个森林"缩小到"被明确列出的若干台机器"。**对并购与合作方场景，这应当是默认选择。**

**单向而非双向**：多数业务需求只需要单向信任（我们的用户访问对方资源，或反之），而工程上默认建成双向只是因为更省事。建立信任时应逐项论证方向的必要性。

此外要为每条信任设定**退出条件与复核周期**：这条信任是为什么建立的、什么条件下可以拆除、下次复核是什么时候。没有退出条件的信任会在原因消失后继续存在十年——而那时已无人知道它为什么在那里，因此也没有人敢拆。

## 14.7.9 恢复：备份不等于可恢复

AD 的灾难恢复与普通系统有本质差异：域控之间持续复制，因此**恢复不是"把某台机器还原"，而是"让整个森林回到一个一致且干净的状态"**。三个必须提前处理的问题：

**第一，恢复什么状态。** 如果攻击者已在域中植入持久化（新增特权账号、修改 ACL、植入 GPO、伪造证书），从被污染时点之后的备份恢复只会把后门一并恢复。因此需要保留足够久的备份（覆盖典型的驻留期），并具备"比对两个时点的目录差异"的能力。

**第二，恢复过程本身需要凭据。** 森林恢复需要目录服务恢复模式密码、备份介质访问权限、以及可用的管理终端。这些如果都依赖被攻陷的环境（比如密码存在域内的密码管理系统里），恢复就无从开始。**离线保存的恢复凭据是必需品**，且要定期验证其有效性。

**第三，只有演练能证明可恢复。** 森林恢复涉及数十个步骤，跨多个团队，且平时无人执行。没有演练过的恢复方案在真正需要时的成功率很低。建议至少每年一次在隔离环境中做完整演练，把耗时、卡点与所需凭据全部记录下来。

恢复完成后必须执行的动作包括：`krbtgt` 连续两次重置（14.7.6）、所有特权账号密码重置、所有服务账号轮换、证书吊销与重新签发评估、以及信任关系复核。业务连续性与灾难恢复的整体方法论见本部分的韧性相关章节，此处只强调 AD 的特殊性。

## 14.7.10 失败叙事：一刀切禁用 NTLM

我们曾经在一个季度加固计划里，把"域内禁用 NTLM"列为重点项。理由充分：NTLM 是中继攻击与哈希传递的基础，禁用它能一次性关掉一大类攻击。计划是在两个月内完成全域切换。

我们做了准备工作——发了通知、开了宣讲会、要求各应用团队自查是否依赖 NTLM。收到的回复是"我们的系统都用 Kerberos"。

切换在一个周六晚上执行。周一早上，故障开始出现：一台老的网络附加存储设备无法访问（它只支持 NTLM）；财务的一个报表工具连不上数据库（它用 IP 地址连接，而用 IP 而非主机名发起的连接会回落到 NTLM）；某个部门的扫描仪无法把文件存到共享目录；一个跨林信任的合作方系统认证失败。到周一中午，我们回滚了。

复盘中最重要的一个发现是：**各应用团队的"我们不用 NTLM"这个回答是真诚的，也是错误的**——他们不知道自己的系统在什么情况下会回落到 NTLM，因为这不是应用配置决定的，而是由连接方式、SPN 是否正确注册、DNS 解析结果等一系列因素在运行时决定的。**靠问是问不出来的，只能靠测。**

第二次尝试改成了三个阶段，用了七个月：

第一阶段（12 周），开启 NTLM 审计但不阻断，采集全域的 NTLM 使用记录。这一步的产出是一份清单：47 个仍在使用 NTLM 的来源，其中 31 个是可以修复的配置问题（缺 SPN、用 IP 连接、DNS 别名），11 个需要应用改造，5 个是无法改造的设备。**这份清单是靠 12 周的日志换来的，任何调查问卷都得不到它。**

第二阶段（16 周），逐个修复。可修复的配置问题优先，改造类的排入版本计划，无法改造的 5 台设备迁移到独立网段并单独授权。

第三阶段（4 周），分批阻断：先域控，观察一周；再服务器，观察两周；最后全域。整个过程只出现两起小范围故障，都在小时级内定位并解决。

这次失败留下的判断是：**任何影响认证路径的加固，必须先经历一个足够长的"审计但不阻断"阶段，且这个阶段的长度要覆盖业务的最长周期**（月结、季结、年度作业）。12 周不是拍脑袋定的，是因为要覆盖一个完整的季度末。更一般地说：**加固项目的时间成本主要花在"发现谁会受影响"上，而不是"执行变更"上**——低估前者是这类项目失败的主要原因。

## 14.7.11 落地顺序建议

把本节的内容压缩成一个可执行的顺序（假设从零开始，团队规模有限）：

| 阶段 | 动作 | 为什么在这个位置 |
|------|------|---------------|
| 第 1 月 | 建立攻击面基线（14.7.7）；枚举 Tier 0 资产；审计 DCSync 权限、SPN、无约束委派、`adminCount` 孤儿 | 先看清现状，且这一步不改变任何配置，零风险 |
| 第 2～3 月 | 关闭"应当为零"的项；清理特权组成员；`krbtgt` 首次轮换 | 见效快、风险低、不需要跨团队协作 |
| 第 3～5 月 | 部署 LAPS（含服务器）；启用 SMB 签名；关闭 DC 上的打印服务 | 砍掉横向移动主路径 |
| 第 4～8 月 | 分层登录限制 + PAW；Protected Users；ADCS 模板审计与加固 | 需跨团队协作，周期长 |
| 第 6～12 月 | LDAP 签名与 NTLM 收敛（审计先行，见 14.7.10） | 风险最高，必须最后做且要留足审计期 |
| 持续 | 每月攻击面度量；每季度趋势报告；每年恢复演练 | 让加固从项目变成运营 |

这张表隐含一条排序原则：**先做不需要别人同意的事，再做需要跨团队协作的事，最后做会影响业务的事**。第 1～3 月的动作全部在安全团队自己的权限范围内，它们产生的第一批数据（攻击路径条数、"应当为零"项的实际数量）正是后续争取资源与协作的筹码。跳过这一步直接去谈 NTLM 收敛，得到的通常是"等等看"。同样的道理也适用于向管理层要预算：一句"我们从普通工作站到域管理员有 1,400 条路径、最短 2 跳"，比一份包含 60 个配置项的加固方案更容易通过。

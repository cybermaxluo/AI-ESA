# 14.10　身份威胁检测与响应（ITDR）

一次事后调查的典型场景：所有日志都在。攻击者的每一步都被完整记录了——第 1 天的密码喷洒尝试在登录日志里，第 3 天的成功登录在登录日志里，第 3 天晚上给某个应用授予权限的操作在审计日志里，第 5 天用应用身份读取邮箱的调用在邮箱审计日志里。**没有任何一条日志缺失，也没有任何一条告警触发。**

原因不是数据不足，是缺少把它们连起来的东西：SIEM 里的这几条记录分属不同的表、不同的主体标识（一个是用户主体名，一个是对象 ID，一个是应用 ID）、不同的时间尺度（登录是秒级事件，权限授予是配置变更），而**判断"这次授权让谁获得了什么"，需要的不是日志，是权限图谱**。SIEM 天然不持有这个图谱。

这就是身份威胁检测与响应（ITDR）要补的位置。[11.3.8](../../第04部分_安全运营与防御能力/第11章_安全运营/11.3_威胁检测工程.md) 已经给出了 ITDR 的基础检测场景（凭据窃取类攻击、身份配置篡改）与规则示例，本节不重复，而是处理三件它没有展开的事：**ITDR 与 SIEM/UEBA 的运营分工**（14.10.1）、**身份侧特有的六类检测面**（14.10.4，含 AI agent 身份）、以及**身份响应动作的自动化边界**（14.10.5）。

一个提前给出的判断：**身份日志齐全不等于身份可见。** 衡量身份可见性的标准不是"采集了多少条日志"，而是能否在 5 分钟内回答这三个问题——这个账号现在有哪些权限？这些权限是什么时候、由谁授予的？如果它被攻陷，攻击者能到达哪里？

## 14.10.1 分工：ITDR 不是又一个 SIEM

| 能力 | 主要输入 | 判定依据 | 典型时间尺度 | 响应动作 | 通常归属 |
|------|---------|---------|------------|---------|---------|
| SIEM | 全域日志 | 规则与关联 | 秒到小时 | 告警、工单、编排 | SOC |
| UEBA | 行为序列 | 与个体/同侪基线的偏离 | 小时到天 | 风险分、调查线索 | SOC / 内部风险 |
| ISPM（姿态） | 配置与权限图谱 | 与安全基线的差距 | 天到周 | 整改工单 | 身份团队 |
| ITDR（检测响应） | 身份事件 + 权限图谱 + 姿态 | 身份语义（谁获得了什么能力） | 秒到小时 | 会话撤销、凭据吊销、授权回滚 | 身份团队 + SOC 共管 |

关键差异在"判定依据"那一列。SIEM 判断的是"这条事件像不像攻击"，ITDR 判断的是"这次变更让谁获得了什么能力"。同一条日志——"某管理员为某应用添加了一个客户端密钥"——在 SIEM 看来是一次常规管理操作（每天发生几十次），在 ITDR 看来需要先回答"这个应用有什么权限"，如果答案是"可读取全部邮箱"，那么这条日志的性质就完全不同。

**运营上的建议分工**：告警仍然进 SOC 的统一队列（不要建第二个告警池），但身份类告警的研判需要身份团队参与，且响应动作由身份团队执行——因为撤销会话、吊销应用凭据这类操作需要对业务影响有判断力。这与 [19.3 安全团队职能划分](../../第07部分_安全领导力与组织建设/第19章_安全领导力/19.3_安全团队职能划分.md) 中"专业能力驻留在专职团队、一线负责分诊"的原则一致。

## 14.10.2 两条腿：姿态与检测

只做检测不做姿态，等于一直在救火；只做姿态不做检测，等于装了锁但没装警报。两者的分工很清楚：

**姿态（ISPM）回答"存在什么可被利用的东西"**：常驻的高权限、未启用强认证的特权账号、拥有危险 ACL 的普通主体、权限过宽的应用、长期未使用的凭据、条件访问的排除项、跨租户的信任配置。这些都是静态的、可枚举的、可以按周巡检的。14.7.7 的攻击面度量就是姿态能力在 AD 上的具体形态。

**检测（ITDR）回答"有人正在利用它"**：异常授权、影子管理员的产生与使用、休眠账号激活、跨租户访问、认证方式被篡改。

一份可以直接用的姿态巡检清单（每周运行，任何一项非零都产生整改工单）：

| 姿态项 | 检查内容 | 目标 |
|-------|---------|------|
| 特权账号的认证强度 | 未注册抗钓鱼认证器的特权账号 | 0 |
| 常驻特权 | 无时限的高权限角色分配 | 0（见 14.6） |
| 条件访问排除 | 各策略排除项去重后的账号数与到期状态 | 见 14.3.10 |
| 高权限应用 | 拥有敏感应用级权限的应用及其最近使用时间 | 全部可解释，无 180 天未用 |
| 应用凭据 | 长期有效（> 1 年）或即将过期的应用凭据 | 无长期凭据 |
| 外部与跨租户 | 外部用户数、跨租户配置数、无活动的外部用户 | 全部有业务归属 |
| 目录危险 ACL | 低权限主体对特权对象的写权限、密码重置权、密钥凭据写权限 | 0（见 14.7.7） |
| 休眠账号 | 90 天无登录的启用账号 | 逐月下降 |
| 联邦与域配置 | 联邦域清单、签名证书有效期与轮换记录 | 全部在册且未过期 |
| 破玻璃账号 | 可用性自检结果 | 100% 通过（见 14.6.7） |

二者的联动是 ITDR 最有价值的部分：**姿态数据是检测规则的上下文**。同样一条"给应用添加凭据"的日志，如果姿态数据显示这个应用拥有高权限，告警级别应当直接升到最高；如果它是一个只读的内部工具，可以降级为记录。没有姿态数据的检测规则，只能靠阈值和名单，误报率高且容易被绕过。

## 14.10.3 数据源与它们的盲区

在写任何规则之前，先确认数据源存在、字段可用、延迟可接受。下表是身份检测的基础数据源清单（以主流云身份平台与 Windows 域为例，字段名以各平台当前文档为准，落地前须实测）：

| 数据源 | 关键内容 | 常见盲区 |
|-------|---------|---------|
| 交互式登录日志 | 用户登录、结果码、条件访问结论、认证方式、风险等级 | 只覆盖交互式登录 |
| 非交互式登录日志 | 客户端用刷新令牌换取访问令牌的记录 | 量极大，常被排除在采集之外——**而这正是令牌窃取后的活动所在** |
| 服务主体登录日志 | 应用以自身身份的认证 | 单独的表，容易被漏采 |
| 目录审计日志 | 角色分配、应用凭据、同意授权、域与联邦配置变更 | 变更详情藏在嵌套结构里，需要解析 |
| 邮箱/协作平台审计 | 邮件规则、委派、大量下载 | 默认可能未开启或保留期短 |
| Windows 安全日志 | 登录、组变更、目录对象修改、票据请求 | 采集范围常只覆盖域控，遗漏成员服务器 |
| 目录对象快照 | 权限图谱的来源 | 不是日志，需要独立的定期采集 |
| 身份平台的管理 API | 姿态数据（策略、排除项、应用权限） | 需要额外授权，且这个授权本身是特权 |

三个必须提前处理的工程问题：

**日志延迟。** 云身份平台的日志到达 SIEM 通常有分钟级延迟，某些类型可能更久。这意味着**基于身份日志的自动响应存在天然的时间差**——当你自动禁用账号时，攻击者可能已经完成了操作。设计自动响应时必须接受这一点，并把重点放在"缩小损失"而非"阻止发生"上。

**标识符不统一。** 同一个主体在不同日志里可能表现为用户主体名、对象 ID、应用 ID、SID、SAM 账号名。检测规则必须统一到一个稳定标识（通常是对象 ID 或 `person_id`），这需要在数据接入层做映射——**这项工作是 ITDR 落地成本的大头，且没有捷径**。

**非交互式登录的量。** 它可能是交互式登录的数十倍，全量采集成本高。折中做法是：全量采集特权账号与高价值应用的非交互式登录，其余做采样或只保留聚合。**不要因为量大就整体不采**——令牌窃取后的活动几乎全部表现为非交互式登录。

## 14.10.4 六类身份特有的检测面

以下六类是 11.3.8 未覆盖、且在近年公开事件中反复出现的场景。前五类的规则以 KQL 表达（面向云身份平台的日志表），字段名以平台文档为准；迁移到其他 SIEM 时逻辑不变。第六类是 agent 身份，它的数据源与前五类完全不同，单独说明。

### 一、异常授权：OAuth 同意与应用权限

攻击链的常见形态是：攻陷一个账号 → 注册或选中一个应用 → 为其授予高权限（尤其是不需要用户上下文的应用级权限）→ 以应用身份持久访问数据。这条路径的隐蔽性在于**它不再依赖被攻陷账号**——即使原账号被禁用、密码被重置，应用的访问依然有效。

```kusto
// 检测高权限的应用同意授权（委派与应用权限）
let HighRiskPermissions = dynamic([
    "Mail.Read", "Mail.ReadWrite", "Mail.Send",
    "Files.Read.All", "Files.ReadWrite.All",
    "Directory.Read.All", "Directory.ReadWrite.All",
    "Application.ReadWrite.All", "RoleManagement.ReadWrite.Directory",
    "User.Read.All", "Sites.FullControl.All"
]);
AuditLogs
| where TimeGenerated > ago(24h)
| where OperationName in (
    "Consent to application",
    "Add delegated permission grant",
    "Add app role assignment to service principal"
  )
| where Result == "success"
| extend Actor = tostring(InitiatedBy.user.userPrincipalName)
| extend ActorApp = tostring(InitiatedBy.app.displayName)
| mv-expand TargetResources
| extend TargetApp = tostring(TargetResources.displayName)
| mv-expand ModProp = TargetResources.modifiedProperties
| extend PropName = tostring(ModProp.displayName),
         NewValue = tostring(ModProp.newValue)
| where PropName in ("ConsentAction.Permissions", "AppRole.Value", "ConsentContext.IsAdminConsent")
| extend GrantedPerms = NewValue
| where GrantedPerms has_any (HighRiskPermissions)
| project TimeGenerated, OperationName, Actor, ActorApp, TargetApp,
          PropName, GrantedPerms, CorrelationId
| order by TimeGenerated desc
```

字段与逻辑说明：`InitiatedBy` 是一个嵌套结构，操作者可能是用户也可能是另一个应用，因此同时取 `user.userPrincipalName` 与 `app.displayName`——**由应用发起的授权变更尤其值得关注，它意味着自动化链路中存在提权能力**。`modifiedProperties` 需要两次展开才能拿到具体授予的权限字符串，这是这类规则最容易写错的地方（只看 `OperationName` 会漏掉"授予了什么"这个决定性信息）。误报主要来自 IT 团队的正常应用上线，抑制方法是维护一份"已批准应用 + 已批准权限"的白名单，并把白名单本身纳入变更审计。

配套的姿态检查同样重要：定期枚举租户内所有拥有高风险权限的应用，核对每一个的业务归属与最近使用时间——**存量里的高权限应用往往比新增的更危险，因为它们已经通过了"存在即合理"的时间考验**。

### 二、影子管理员

影子管理员指的是**没有管理员角色、但具备等价能力的主体**。它们不出现在"管理员组成员"这类报表里，因此在多数企业的特权盘点中完全隐形。典型来源：

- 能为高权限应用添加凭据的角色（获得凭据即可以该应用身份行动）。
- 能重置管理员密码的角色或 ACL（服务台类权限）。
- 能修改条件访问或认证方法策略的角色（可为自己开绕过通道）。
- 本地 AD 中对特权对象拥有写权限、密码重置权、或可添加密钥凭据的普通主体（见 14.7.6）。
- 能管理组成员资格的主体（可把自己加进特权组）。

检测分两部分。姿态侧靠图分析枚举（14.7.7 的可控关系边），检测侧则监控这些能力的实际使用：

```kusto
// 服务主体新增凭据：攻击者建立持久化的常用手法
AuditLogs
| where TimeGenerated > ago(24h)
| where OperationName in (
    "Add service principal credentials",
    "Update application – Certificates and secrets management",
    "Update service principal"
  )
| where Result == "success"
| extend Actor = tostring(InitiatedBy.user.userPrincipalName)
| mv-expand TargetResources
| extend TargetApp = tostring(TargetResources.displayName),
         TargetId  = tostring(TargetResources.id)
| mv-expand ModProp = TargetResources.modifiedProperties
| extend PropName = tostring(ModProp.displayName)
| where PropName in ("KeyDescription", "PasswordCredentials", "KeyCredentials")
| summarize Events = count(),
            Apps = make_set(TargetApp, 20),
            FirstSeen = min(TimeGenerated),
            LastSeen = max(TimeGenerated)
        by Actor, bin(TimeGenerated, 1h)
| where Events >= 1
| order by LastSeen desc
```

这条规则刻意不设高阈值（`Events >= 1`）：为应用添加凭据是低频操作，一次就值得看。降噪应当靠"排除已知的自动化发布流程"，而不是靠提高计数阈值——**用阈值给低频高危事件降噪，等于放弃这类检测**。

本地 AD 侧的对应检测是监控目录对象属性的写入，其中影子管理员最常用的一条是向目标账号写入密钥凭据属性（写入后即可用证书方式以该账号身份认证，无需知道其密码）：

```yaml
title: Shadow Credentials via msDS-KeyCredentialLink Modification
id: 5e8b3d17-40a2-4c96-b1de-7f0c9a2e6b83
status: experimental
description: 检测对 msDS-KeyCredentialLink 属性的写入，该操作可让攻击者以目标身份认证
references:
  - https://attack.mitre.org/techniques/T1098/
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 5136
    AttributeLDAPDisplayName: 'msDS-KeyCredentialLink'
    OperationType: '%%14674'
  filter_known_service:
    SubjectUserName:
      - 'svc_deviceregistration$'
  condition: selection and not filter_known_service
falsepositives:
  - 设备注册服务的正常写入
  - 基于证书的登录方案在首次注册时的写入
level: high
tags:
  - attack.persistence
  - attack.t1098
```

这条规则的前提是**目录服务对象修改审计已开启**（默认未开启，且需要在相应对象上配置系统访问控制项）。这一点值得单独强调：本节大量规则依赖的审计策略在默认配置下是关闭的，**"规则写好了却从来不触发"最常见的原因不是环境干净，而是日志根本没产生**。上线任何一条规则前，先用一次可控的操作验证事件确实出现在日志中。

### 三、休眠账号激活

长期无活动的账号突然登录，是一个强信号：它可能是被遗漏的离职账号被攻陷，也可能是攻击者启用了一个早已存在的后门账号。

```kusto
// 90 天无登录的账号突然成功登录
let LookbackDays = 90;
let DormantThreshold = 90d;
let RecentWindow = 1d;
let LastSeen =
    union SigninLogs, AADNonInteractiveUserSignInLogs
    | where TimeGenerated between (ago(LookbackDays * 1d) .. ago(RecentWindow))
    | where ResultType == "0"
    | summarize LastSuccess = max(TimeGenerated) by UserPrincipalName;
union SigninLogs, AADNonInteractiveUserSignInLogs
| where TimeGenerated > ago(RecentWindow)
| where ResultType == "0"
| summarize FirstNewSignin = min(TimeGenerated),
            IPs = make_set(IPAddress, 10),
            Apps = make_set(AppDisplayName, 10),
            Countries = make_set(tostring(LocationDetails.countryOrRegion), 5)
        by UserPrincipalName
| join kind=leftouter (LastSeen) on UserPrincipalName
| extend DormantDays = iff(isempty(LastSuccess), real(9999),
                           datetime_diff('day', FirstNewSignin, LastSuccess))
| where DormantDays >= 90
| project UserPrincipalName, FirstNewSignin, LastSuccess, DormantDays,
          IPs, Apps, Countries
| order by DormantDays desc
```

两个设计点：`union` 同时覆盖交互式与非交互式登录——只看交互式会漏掉以令牌形式发生的激活；`LastSuccess` 为空时赋一个极大值（表示"回溯窗口内从未成功登录"），否则 `leftouter` 连接产生的空值会让这些最可疑的账号被过滤掉。误报主要来自长假返岗、长期病假、以及季节性使用的账号，处置方式是与 14.2.6 的中间态数据做关联——**已知在休假状态的账号可以自动降级，而不是每次都人工判断**。

### 四、跨租户与外部身份滥用

企业间协作（外部用户、跨组织访问、合作方联邦）带来了一类新的攻击面：攻击者攻陷合作方的租户，然后借助已建立的信任关系访问你的资源。这类活动在日志中表现为"合法的外部用户正常访问"，很难与真实协作区分。

```kusto
// 外部/跨租户身份的敏感访问与授权活动
let AllowedPartnerTenants = dynamic([
    "11111111-1111-1111-1111-111111111111",
    "22222222-2222-2222-2222-222222222222"
]);
SigninLogs
| where TimeGenerated > ago(24h)
| where ResultType == "0"
| where UserType == "Guest" or HomeTenantId != ResourceTenantId
| extend PartnerTenant = tostring(HomeTenantId)
| extend UnknownPartner = iff(PartnerTenant in (AllowedPartnerTenants), false, true)
| summarize SignIns = count(),
            Apps = make_set(AppDisplayName, 15),
            IPs = dcount(IPAddress),
            Countries = make_set(tostring(LocationDetails.countryOrRegion), 5)
        by UserPrincipalName, PartnerTenant, UnknownPartner, bin(TimeGenerated, 1h)
| where UnknownPartner == true or SignIns > 50
| order by SignIns desc
```

这条规则同时覆盖两种情况：来自未登记合作租户的访问（`UnknownPartner`），以及来自已登记租户但活动量异常的访问。前者对应"信任关系被悄悄建立"，后者对应"合法信任被滥用"。**配套的姿态检查是定期枚举全部跨租户访问配置与外部用户清单，核对每一条是否仍有业务需要**——外部协作关系的清理，是身份治理中最少被执行的一项。

### 五、认证与联邦配置的篡改

最后补一类高危但低频的场景：域的认证方式变更、联邦配置修改、认证方法策略调整。这类操作正常情况下一年发生不了几次，一旦发生就意味着有人在改变整个租户的信任根（对应 14.7.1 提到的 Golden SAML 类风险）。

```kusto
// 认证与联邦配置变更：低频高危，全部告警
AuditLogs
| where TimeGenerated > ago(7d)
| where OperationName in (
    "Set domain authentication",
    "Set federation settings on domain",
    "Set DirSyncEnabled flag",
    "Update authentication methods policy",
    "Update conditional access policy",
    "Delete conditional access policy",
    "Add member to role"
  )
| extend Actor = tostring(InitiatedBy.user.userPrincipalName)
| mv-expand TargetResources
| project TimeGenerated, OperationName, Result, Actor,
          Target = tostring(TargetResources.displayName),
          TargetType = tostring(TargetResources.type),
          CorrelationId
| order by TimeGenerated desc
```

对这类规则，**不要做任何阈值抑制**，也不要因为"变更窗口内"就自动关闭告警——变更窗口正是攻击者最好的掩护。正确做法是把告警与变更管理系统做关联：有对应变更单的自动附上单号并降级为记录，没有的立即升级。

### 六、AI agent 身份：基线锚定任务定义，而非历史行为

前五类的检测对象是人或应用主体，规则可以建立在"与自身历史或同侪的偏离"之上。AI agent 不满足这个前提。它的正常行为是 7×24 运行、每分钟数十次调用、突发式批量读取、一次任务横跨工单系统与代码仓库与数据仓库。把人的基线规则原样套上去只有两种结果：阈值按人设，它天天在告警；阈值放宽到能容纳它的正常行为，它被攻陷后也不会告警。

历史基线在 agent 上还有两个更根本的失效点。**一是没有历史**：agent 上线第一天就以全速运行，学习期学到的是它的初始配置，而那个配置往往还没定型。**二是基线会整体平移且不留痕**：改一次提示词、换一个模型、加一个工具，行为分布立刻整体移动，而这次变更在登录日志、配置审计、变更管理里可能都没有对应记录。

**因此 agent 的检测必须锚定任务定义。** 任务定义就是 14.8.6 那份登记里的几项：允许的工具集、数据范围、典型的调用序列、单次任务的资源消耗区间。它是声明式的、可版本化的、变更时必须走复核的。以它为判据，agent 上线第一天就有可用的规则，改提示词导致的行为平移会立刻表现为"与声明不符"，而不会被静默地学进新基线。

| 信号 | 怎么算 | 为什么在 agent 上有效 |
|------|-------|-------------------|
| 工具组合偏离 | 本次任务实际调用的工具集合与序列，对照登记的 `allowed_tools` 与典型序列 | 单个工具都在授权内，组合才构成风险（14.8.6 的隐式扩张） |
| 单次任务资源消耗 | token 用量、调用次数、检索条数、执行时长，与该任务类型的声明区间比 | 数据在计费与网关侧本来就有，不需要标识符归一化 |
| 数据源越界 | 实际访问的数据源与登记的 `data_scope` 求差 | 任务范围是声明的，越界是确定性判定，不依赖阈值 |
| 任务内语义跳变 | 同一 `task_id` 内，越界检索紧跟一次外发类调用 | 提示注入劫持后的典型痕迹，机理见 18.3 |

第二行的要点是：**成本是一个被低估的检测信号**。一次任务的消耗突然放大一个数量级，原因只有几种——进了循环、在遍历远超预期的数据集、或被引导去做别的事，三种都要人看一眼；局限是它只对"消耗放大"型的攻击有效。

**被提示注入劫持后的痕迹长什么样。** 完整机理在 18.3，这里只给身份侧看得到的形态：任务前半段与登记的典型序列一致（读工单、查知识库），中段出现一次对与本任务无关的数据源的检索（用户目录、代码仓库、邮箱），紧接着是一次外发类调用（发邮件、调 webhook、写文件到共享位置）。检测锚点是 **`task_id` 内的序列跳变**——中段那次检索单独看完全合法，可疑之处在于它出现在这个任务里。这也是 `task_id` 必须贯穿一次任务全部工具调用的理由：没有它，这些调用在日志里就是一堆互不相关的合法操作。

```python
"""任务锚定的 agent 行为偏离评分：与声明的任务画像比对，不与历史基线比对。

输入是一次任务内按时序排列的工具调用，与该任务类型的声明画像。
data_scope 越界与"越界读取后外发"是确定性判定，命中即处置；
其余信号只用 score 排序。
"""
from dataclasses import dataclass
from typing import Dict, List, Sequence, Set


@dataclass
class TaskProfile:
    task_type: str
    allowed_tools: Set[str]
    exfil_tools: Set[str]      # 具备外发能力的工具，需人工标注
    data_scopes: Set[str]
    max_tool_calls: int
    max_cost_units: float


@dataclass
class ToolCall:
    task_id: str
    seq: int
    tool: str
    data_scope: str
    cost_units: float


DETERMINISTIC = ("data_scope_violation", "read_then_exfil")


def score_task(profile: TaskProfile, calls: Sequence[ToolCall]) -> Dict[str, object]:
    findings: List[Dict[str, object]] = []

    unauthorized = {c.tool for c in calls} - profile.allowed_tools
    if unauthorized:
        findings.append({"signal": "tool_not_in_profile",
                         "detail": sorted(unauthorized), "weight": 40})

    out_of_scope = {c.data_scope for c in calls} - profile.data_scopes
    if out_of_scope:
        findings.append({"signal": "data_scope_violation",
                         "detail": sorted(out_of_scope), "weight": 50})

    total_cost = sum(c.cost_units for c in calls)
    if total_cost > profile.max_cost_units:
        findings.append({"signal": "cost_blowout",
                         "detail": round(total_cost / profile.max_cost_units, 2),
                         "weight": 25})

    if len(calls) > profile.max_tool_calls:
        findings.append({"signal": "call_count_blowout",
                         "detail": len(calls), "weight": 15})

    ordered = sorted(calls, key=lambda c: c.seq)
    for prev, cur in zip(ordered, ordered[1:]):
        if (prev.data_scope not in profile.data_scopes
                and cur.tool in profile.exfil_tools):
            findings.append({"signal": "read_then_exfil",
                             "detail": f"{prev.tool}->{cur.tool}", "weight": 60})
            break

    return {
        "task_id": calls[0].task_id if calls else None,
        "task_type": profile.task_type,
        "score": sum(int(f["weight"]) for f in findings),
        "deterministic": [f["signal"] for f in findings
                          if f["signal"] in DETERMINISTIC],
        "findings": findings,
    }
```

怎么读这段代码：`deterministic` 与 `score` 分开返回是刻意的——越界与"读取后外发"命中即处置，不参与阈值比较；`score` 只用来给其余信号排序。序列判定只看相邻两步并在首次命中后 `break`，避免一次任务刷出几十条同类发现把队列淹掉。

**这段代码里有代价的设计选择**：`exfil_tools` 需要人工标注，标注口径直接决定检出能力——把"写文件到共享位置"漏标成非外发工具，这条规则就废掉一半。这是一次性工作，但必须由懂业务的人做，自动推断做不了。

**照抄时最容易改错的三处**：一是 `max_cost_units` 取全局值，agent 的任务类型之间消耗能差几个数量级，全局阈值必然要么全告警要么不告警，画像必须按 `task_type` 分开；二是把 `data_scope` 当扁平字符串做集合差，数据范围通常是层级的（`tenant:internal-it` 在 `tenant:*` 之下），不先做层级归一会把合法的下级范围判成越界；三是按入库时间取日志直接传进 `calls`，丢日志造成的 `seq` 缺号不会被发现，序列类信号静默漏检——判定前须先校验 `seq` 连续性。

**响应上有一处与人不同。** 人的账号出现可疑活动时，最有效的一步是问本人一句"这是你吗"。agent 没有本人可问，owner 也无法在几分钟内判断一次任务是否被劫持。因此 agent 类告警的默认动作应当是自动且可逆的三选一：暂停调度、降级到只读、吊销本次任务的委派令牌。三者都不影响别人工作，恢复成本很低，与 14.10.5 第一行同理。

**适用边界。** 任务锚定的前提是任务定义存在且被维护。没有 14.8.6 那份登记、或者登记从不更新的组织，这套检测起不来——它会退化成"每次改提示词都告警"，两周内被关掉。第二条边界：这里只覆盖 agent 经由受管工具层发出的调用；直连数据库或直接调外部 API 的部分看不到，只能靠 14.8.7 的 NHI 通用信号（调用来源变化、调用量突变）兜底，粒度粗得多。第三条边界是分工：这里检测身份与行为层面的偏离，模型输出内容本身的安全（越狱、有害内容）不在 ITDR 范围，见 18.3 与 18.7。

**验证方法。** **注入演练**：在测试环境给 agent 投喂一份带注入载荷的输入（一条工单正文、一个网页片段），载荷目标设成"读取一个任务范围外的数据源并外发"，看 `read_then_exfil` 是否命中、多久命中。这是唯一能证明规则真的接通了的办法。**画像漂移核对**：取过去 30 天全部任务用当前画像重跑，统计偏离率；偏离率突然升高通常意味着有人改了提示词或工具集而没更新登记，这一项既是规则自检，也是 14.5 那套复核的触发器。**成本信号可用性确认**：核实计费或网关侧的消耗数据能按 `task_id` 聚合——多数平台默认只按 API 密钥或按天聚合，这一点要在写规则之前确认。

**运行指标。** **`task_id` 贯通率**（全部工具调用带同一 `task_id` 的比例，低于 100% 时序列类信号按比例失效，这是本类检测最基础的一项）；**画像覆盖率**（有声明画像的任务类型 ÷ 任务类型总数）；**确定性信号的告警量与研判结论分布**（`data_scope_violation` 长期为零，先怀疑数据范围登记得太宽，理由与前面"规则从不触发通常是日志没产生"同源）；**从任务开始到偏离告警的时延 P95**（agent 的任务多在分钟级完成，超过任务时长的检测只剩取证价值）；**agent 类告警的自动可逆处置占比**。

## 14.10.5 响应：动作清单与自动化边界

身份侧的响应动作比网络或终端侧更"重"，因为它们直接影响人的工作能力。下表按影响面与可逆性排序：

| 动作 | 影响面 | 可逆性 | 建议自动化程度 |
|------|-------|-------|-------------|
| 撤销活动会话与刷新令牌 | 用户需重新登录 | 完全可逆 | **可全自动** |
| 要求下次登录强认证 | 一次额外验证 | 完全可逆 | **可全自动** |
| 吊销应用/服务主体的某个凭据 | 使用该凭据的集成中断 | 可逆（重新签发） | 半自动（准备好动作，人工确认） |
| 撤销某个应用的授权同意 | 该应用功能中断 | 可逆 | 半自动 |
| 重置密码 | 用户需走找回流程 | 可逆但有摩擦 | 半自动 |
| 移除并要求重新注册认证方法 | 用户需重新注册 | 可逆但摩擦大 | 人工 |
| 禁用账号 | 用户完全无法工作 | 可逆 | 人工（VIP 与关键岗位必须人工） |
| 隔离设备 | 设备无法访问企业资源 | 可逆 | 半自动 |
| 临时收紧条件访问策略 | 影响面可能极大 | 可逆但易出事故 | 人工，且需双人确认 |

**第一行是本表最重要的一条**：撤销会话与刷新令牌影响小、可逆、且直接切断令牌窃取类攻击的收益，是身份响应中性价比最高的动作，应当在检测到中高风险信号时无条件自动执行。很多企业把它和"禁用账号"放在同一个决策档位，因而迟迟不敢自动化——**这是把两个完全不同风险等级的动作混为一谈**。

自动化的三条边界：

1. **按人群分级。** VIP、高管、值班工程师、关键运维岗位的账号，任何"禁用"级动作都必须人工确认。这份名单要单独维护并定期复核。
2. **按可逆性分级。** 可逆动作可以自动，不可逆或高摩擦动作必须人工。
3. **有熔断。** 自动响应在单位时间内触发次数超过阈值时（例如 10 分钟内 20 次），自动暂停并告警——这既防止规则误配引发大规模误杀，也防止攻击者故意触发规则制造拒绝服务。

---

**生产坑：自动响应与日志延迟的竞态。** 检测规则在日志到达后触发，而日志有分钟级延迟；响应动作执行时，攻击者可能已经用同一份令牌完成了下一步操作，甚至已经建立了新的访问路径（新增应用凭据、新增认证方法）。因此**响应动作不能只针对触发告警的那条会话，必须针对该主体的全部有效凭据**：撤销全部会话与刷新令牌、枚举并核对其近期新增的认证方法与应用凭据。只撤销"那次登录"的响应，在真实攻击中几乎总是不够。

**生产坑：响应动作把证据也一起清掉了。** 移除认证方法、撤销同意授权、删除可疑应用，这些动作在阻断攻击的同时也删除了取证所需的配置状态。正确顺序是**先固定证据（导出当前配置与相关日志），再执行处置**；对不可逆的清理动作（删除应用、删除账号）尤其如此。这一条应当写进身份类事件的处置清单，因为在压力下人的本能是先删掉可疑的东西。

## 14.10.6 取证：身份事件要保全什么

身份类事件的调查与主机类不同，证据大多在云端且保留期有限。事件确认后应立即固定以下内容（与 [11.5 事件响应](../../第04部分_安全运营与防御能力/第11章_安全运营/11.5_事件响应.md) 的取证流程衔接）：

- 相关账号在事件窗口前后各 30 天的**交互式与非交互式登录记录**（含 IP、设备、认证方式、条件访问结论、关联标识）。
- **目录审计记录**：角色分配、应用凭据、同意授权、策略变更、组成员变更。
- **应用与服务主体的活动记录**，特别是被授予权限之后的调用。
- **邮箱与协作平台的配置**：转发规则、委派、共享链接、外发记录。
- **权限快照**：事件时点的权限图谱（若无历史快照，至少立即导出当前状态）。
- 认证方法的变更历史（何时注册了新认证器、由谁操作）。

时间线重建的三个坑：日志延迟导致事件顺序失真（应以事件本身携带的时间戳而非入库时间排序）；时区不统一（统一转为协调世界时再比对）；以及**非交互式登录常常是攻击活动的主体**，只用交互式登录构建时间线会得出"攻击者只登录了一次"的错误结论。

## 14.10.7 失败叙事：自动禁用误杀了一位高管

我们上线过一条自动响应规则：登录风险等级为高且来自新国家/地区时，自动禁用账号并通知 SOC。逻辑清晰，测试通过，上线后两周运行良好，拦下了三次真实的账号接管尝试。

第 15 天，一位业务负责人在飞机落地后登录，触发规则，账号被禁用。他当天有一场重要的客户会议，需要访问会议材料。恢复流程需要服务台核验身份，而服务台的核验流程（14.3.5 加固过的那套）要求经理确认——他的经理是 CEO，正在另一个时区的会议中。最终耗时约 3 小时才恢复。

事后追责的压力全部落在安全团队，而**这条规则本身是正确的**：那次登录确实符合高风险特征，只是恰好是真实用户。问题不在检测，在响应动作的选择。

改造后的做法：

1. **把默认动作从"禁用账号"改为"撤销会话 + 要求强认证"**。同样能阻断攻击者（他没有用户的认证器），而真实用户只需多做一次验证。这一条改动消除了绝大部分误杀成本。
2. **对 VIP 与关键岗位名单启用人工确认**，且该名单由 HR 数据自动维护而非人工整理（人工整理的名单三个月后必然过期）。
3. **建立 15 分钟内可达的恢复通道**：为高影响响应动作配备值班人员直通路径，绕开常规服务台排队——注意这条通道本身的核验强度不能降低，只是排队优先级提高。
4. **给自动响应加熔断**，见 14.10.5。

改造后的一年里，自动响应触发次数增加了（因为动作变轻了，可以更激进地触发），而误杀导致的业务影响降到接近零（示例口径）。

留下的判断是：**自动响应的设计重点不是"判断得多准"，而是"判断错了代价多小"。** 追求准确率会让规则越来越保守，最终变成只在证据确凿时才动作——而那时攻击往往已经完成。选择一个轻量、可逆、误伤成本低的动作，可以让你在证据不足时就敢于行动，这在时间就是一切的身份攻击面前，价值远大于把准确率从 90% 提到 95%。

## 14.10.8 度量

| 指标 | 定义 | 参考目标（示例口径） |
|------|------|------------------|
| 身份数据源覆盖率 | 已接入的关键数据源 ÷ 应接入总数 | 100%，且非交互式登录已覆盖特权账号 |
| 身份告警的平均研判时长 | 从告警到定性 | < 30 分钟 |
| 会话撤销自动化率 | 自动执行的会话撤销 ÷ 应执行总数 | > 90% |
| 高危配置变更的告警覆盖率 | 认证/联邦/角色变更中产生告警的比例 | 100% |
| 变更单关联率 | 高危变更告警中能关联到变更单的比例 | > 95%，缺口即为未授权变更嫌疑 |
| 自动响应误杀率 | 误伤真实用户的自动响应 ÷ 自动响应总数 | < 1%，且每例复盘 |
| 姿态问题平均修复时长 | 从 ISPM 发现到整改完成 | 高危 < 7 天 |
| 影子管理员存量 | 具备管理员等价能力但无管理员角色的主体数 | 逐月下降，且全部可解释 |

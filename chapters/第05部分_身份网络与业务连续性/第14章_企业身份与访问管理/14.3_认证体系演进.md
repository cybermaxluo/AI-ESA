# 14.3　认证体系演进：从 MFA 到无密码

2022 年 9 月，一家网约车公司披露了一次入侵：攻击者拿到一名承包商的凭据后，反复发起多因素认证推送，持续超过一小时；随后在即时通讯软件上冒充 IT 部门，告诉对方"要停止这些通知，请批准一次"。对方批准了。攻击者随即进入内网，在一个共享盘的 PowerShell 脚本里找到了特权访问管理系统的管理员凭据[1]。

这起事件里，MFA 是启用的、覆盖率是达标的、认证因素的数量是两个。失败的不是控制的存在与否，而是**控制的类型**——一个可以被"批准"的推送通知，它的安全性取决于人在疲劳状态下的判断力。

一年后，另一类攻击成为主流：中间人钓鱼（Adversary-in-the-Middle，AiTM）。攻击者部署一个反向代理，把受害者的每一次输入实时转发给真实登录页，把真实登录页的每一次响应实时回显给受害者。用户看到的是正常的登录流程——正确的界面、正确的 MFA 提示、成功的登录结果。攻击者拿到的是登录完成后的会话 Cookie。**在这个攻击面前，一次性口令、推送批准、短信验证码全部失效，因为它们都能被原样转发。**

所以本节的核心判断是：**认证器应当被分成两类而不是五档——抗钓鱼的和不抗钓鱼的。** 中间那些"比密码强一点"的方案，在当前的攻击经济下已经不构成有效防线。而更重要的一句话是：**一个账号的认证强度，等于它所有可用认证路径中最弱的那一条**，包括你已经忘记的那条备用路径，以及那条你从未把它当成认证路径的账号恢复流程。

---

## 14.3.1 抗钓鱼的定义：不是因素数量，是绑定机制

CISA 在 2022 年的指引中把 MFA 分为三档：抗钓鱼的（FIDO/WebAuthn 与基于 PKI 的智能卡）、应用推送与 OTP、以及短信/语音[2]。这个分档常被读成"强弱程度不同"，但真正的分界线是一个二元的机制问题：**认证器是否把请求的来源域（origin）纳入了签名范围**。

- **TOTP**：认证器（手机 App）不知道你在哪个网站输入这个六位数。它只与共享密钥和时间有关。攻击者的代理页面收到这六位数后转发给真站点，验证通过。
- **短信**：同上，且额外承担 SIM 卡劫持与运营商侧攻击风险。
- **推送批准**：认证器知道是哪个服务发起的请求，但不知道用户此刻正在与哪个页面交互。用户批准的是"某个登录请求"，而不是"我正在进行的这次登录"。
- **FIDO2/WebAuthn**：浏览器把当前页面的实际来源域传给认证器，认证器用与该域绑定的私钥签名。**攻击者的代理域名与真实域名不同，签名要么无法产生、要么无法通过验证**。这不依赖用户的判断力。

| 认证器类型 | 抗钓鱼（AiTM） | 抗 SIM 劫持 | 抗设备丢失 | 抗批准疲劳 | 部署成本 |
|-----------|--------------|-----------|-----------|-----------|---------|
| 密码 | 否 | 不适用 | 不适用 | 不适用 | 最低 |
| 短信 / 语音 OTP | 否 | 否 | 否 | 不适用 | 低 |
| TOTP App | 否 | 是 | 否 | 不适用 | 低 |
| 推送批准（无号码匹配） | 否 | 是 | 否 | 否 | 低 |
| 推送批准 + 号码匹配 + 上下文 | 否（仍可被代理） | 是 | 否 | 部分 | 低 |
| FIDO2 平台认证器（设备绑定） | 是 | 是 | 需备份策略 | 是 | 中 |
| FIDO2 硬件密钥 | 是 | 是 | 需备用密钥 | 是 | 中高 |
| 智能卡 / PIV | 是 | 是 | 需补发流程 | 是 | 高 |

（表中"抗钓鱼"一列是机制判定，不是概率评估。）

需要澄清一个常见误解：**号码匹配（number matching）不能把推送变成抗钓鱼的**。号码匹配解决的是"疲劳批准"——用户必须从登录界面读取两位数字并在手机上输入，无法闭眼点"允许"。但在 AiTM 场景中，攻击者的代理页面会把真实的两位数字显示给受害者，受害者输入后照样通过。号码匹配是必要的（主流平台已默认启用[3]），但它解决的是另一个问题。

## 14.3.2 WebAuthn 为什么抗钓鱼：机制拆解

```
      浏览器                    认证器                   服务端(RP)
        │                         │                         │
        │◄────────── challenge（一次性随机数） ─────────────┤
        │                         │                         │
        │ 取当前页面真实 origin     │                         │
        │ 计算 rpId 并校验其为      │                         │
        │ origin 的可注册后缀       │                         │
        │────► {challenge, rpId, origin} ──►│               │
        │                         │ 用与 rpId 绑定的私钥      │
        │                         │ 对 authData||H(clientData)│
        │                         │ 签名，signCount+1        │
        │◄──── {authData, clientDataJSON, signature} ──┤     │
        │                         │                         │
        ├──────────── 断言 ──────────────────────────────►│
        │                         │      服务端校验：        │
        │                         │  1. challenge 一次性且匹配│
        │                         │  2. origin 在白名单内     │
        │                         │  3. rpIdHash 匹配         │
        │                         │  4. UP/UV 标志位符合策略  │
        │                         │  5. 签名验证通过          │
        │                         │  6. signCount 未回退      │
```

攻击者的代理站点域名不是 `login.example.com`，浏览器会把真实的 origin 传给认证器，认证器要么找不到对应凭据（因为凭据是按 rpId 存储的），要么产生的签名在服务端校验 origin 时被拒绝。**这条防线不依赖用户识别域名的能力，这正是它的价值所在。**

服务端校验是容易写错的地方，下面这段代码把六项校验逐条落实。

```python
"""WebAuthn 断言（登录）服务端校验要点实现。

覆盖六项校验：challenge 一次性、origin 白名单、rpIdHash、标志位、
签名、signCount 回退检测；并额外给出企业场景关心的 BE/BS 标志判定。

依赖：cryptography。示例以 ES256（P-256 + SHA-256）为例。
"""
import hashlib
import json
import struct
from base64 import urlsafe_b64decode
from dataclasses import dataclass
from typing import Optional, Set

from cryptography.exceptions import InvalidSignature
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives.serialization import load_der_public_key

FLAG_UP = 0x01   # User Present：用户做了物理操作
FLAG_UV = 0x04   # User Verified：本地验证（PIN/生物特征）通过
FLAG_BE = 0x08   # Backup Eligible：该凭据可被同步（即 synced passkey）
FLAG_BS = 0x10   # Backup State：该凭据当前确已被备份


class WebAuthnError(Exception):
    pass


@dataclass
class StoredCredential:
    credential_id: bytes
    public_key_der: bytes
    sign_count: int
    aaguid: str
    require_uv: bool = True
    allow_synced: bool = False   # 高保障场景要求设备绑定，拒绝可同步凭据


def _b64url(data: str) -> bytes:
    return urlsafe_b64decode(data + "=" * (-len(data) % 4))


def verify_assertion(
    client_data_json: bytes,
    authenticator_data: bytes,
    signature: bytes,
    expected_challenge: bytes,
    allowed_origins: Set[str],
    rp_id: str,
    cred: StoredCredential,
) -> dict:
    # 1. clientData 基本校验
    client_data = json.loads(client_data_json.decode("utf-8"))
    if client_data.get("type") != "webauthn.get":
        raise WebAuthnError("unexpected clientData type")
    if _b64url(client_data["challenge"]) != expected_challenge:
        raise WebAuthnError("challenge mismatch")

    # 2. origin 必须精确匹配白名单，不做前缀或后缀匹配。
    #    这一条是抗钓鱼的落点：代理站点的 origin 不在白名单内。
    if client_data.get("origin") not in allowed_origins:
        raise WebAuthnError(f"origin not allowed: {client_data.get('origin')}")
    if client_data.get("crossOrigin") is True:
        raise WebAuthnError("cross-origin assertion rejected")

    # 3. rpIdHash 校验：authData 前 32 字节是 SHA-256(rpId)
    if len(authenticator_data) < 37:
        raise WebAuthnError("authenticator data too short")
    rp_id_hash = authenticator_data[:32]
    if rp_id_hash != hashlib.sha256(rp_id.encode("utf-8")).digest():
        raise WebAuthnError("rpIdHash mismatch")

    # 4. 标志位
    flags = authenticator_data[32]
    if not flags & FLAG_UP:
        raise WebAuthnError("user presence flag not set")
    if cred.require_uv and not flags & FLAG_UV:
        raise WebAuthnError("user verification required but not performed")
    is_synced = bool(flags & FLAG_BE)
    if is_synced and not cred.allow_synced:
        # 企业策略点：BE=1 意味着凭据可同步到个人云账户，
        # 私钥的实际保管方超出企业控制范围，高保障场景应拒绝
        raise WebAuthnError("synced credential not allowed for this resource")

    # 5. 签名验证：签名对象是 authData || SHA-256(clientDataJSON)
    signed_payload = authenticator_data + hashlib.sha256(client_data_json).digest()
    public_key = load_der_public_key(cred.public_key_der)
    if not isinstance(public_key, ec.EllipticCurvePublicKey):
        raise WebAuthnError("unsupported key type in this example")
    try:
        public_key.verify(signature, signed_payload, ec.ECDSA(hashes.SHA256()))
    except InvalidSignature as exc:
        raise WebAuthnError("signature verification failed") from exc

    # 6. signCount 回退检测：认证器每次断言递增计数器。
    #    新值 <= 旧值且二者都非零，提示凭据可能被克隆。
    new_count = struct.unpack(">I", authenticator_data[33:37])[0]
    cloned_suspected = False
    if new_count != 0 and cred.sign_count != 0 and new_count <= cred.sign_count:
        cloned_suspected = True

    return {
        "verified": True,
        "new_sign_count": new_count,
        "cloned_suspected": cloned_suspected,
        "user_verified": bool(flags & FLAG_UV),
        "backup_eligible": is_synced,
        "backup_state": bool(flags & FLAG_BS),
        "aaguid": cred.aaguid,
    }


def next_sign_count(cred: StoredCredential, result: dict) -> Optional[int]:
    """仅在计数器前进时更新存储值，避免回退写入掩盖克隆信号。"""
    if result["new_sign_count"] > cred.sign_count:
        return result["new_sign_count"]
    return None
```

怎么读这段代码：四个容易写错的点。第一，`origin` 必须**精确匹配**，不能用 `endswith` 这类后缀判断——`evil-login.example.com.attacker.io` 会通过后缀判断，这个错误在自研实现中出现过不止一次。第二，`challenge` 必须由服务端生成、一次性、有短过期时间，且校验后立即作废；把 challenge 存在客户端或允许复用，等于取消了防重放。第三，`signCount` 回退不应直接拒绝登录（部分平台认证器恒返回 0，某些实现存在计数器不同步），而应作为高置信度信号送去做风险决策——这是"检测而非阻断"更合适的少数场景之一。第四，`FLAG_BE` 的处理是企业场景独有的，下一小节展开。

## 14.3.3 Passkey 的企业落地：一个尚未解决的治理分歧

Passkey 是 FIDO 凭据的消费级包装，它带来了普及率，也带来了一个企业未准备好的问题：**私钥可能被同步到员工的个人云账户。**

两类 passkey 的差异在治理上是根本性的：

| 维度 | 设备绑定（device-bound） | 可同步（synced） |
|------|------------------------|-----------------|
| 私钥位置 | 单一硬件（安全芯片或独立密钥） | 同步到平台厂商的个人账户，跨设备可用 |
| 企业可见性 | 可通过 attestation 确认型号与批次 | attestation 常不可用或不携带设备信息 |
| 离职时的销毁 | 回收硬件即完成 | 无法销毁，只能在服务端删除该凭据 |
| 恢复体验 | 丢失即需补发 | 换机自动恢复，用户体验最好 |
| 适用 | Tier 0 管理员、特权账号、高敏感岗位 | 普通员工、外部用户、CIAM |

企业的真实矛盾在于：**同步 passkey 的用户体验优势巨大（换手机无需重新注册），但它把私钥的保管责任转移给了员工的个人云账户**，而那个账户的安全性（是否启用了强认证、是否与工作账号共用密码）企业既无法验证也无权干预。若该个人账户被接管，攻击者获得的是一个完全合法的、抗钓鱼的企业凭据。

务实的落地策略是**按资源分级而非按人群一刀切**：

1. 普通企业应用：接受同步 passkey，享受普及率收益。
2. 特权访问、生产变更、Tier 0 管理：要求 `BE=0`（设备绑定），并通过 AAGUID 白名单限定认证器型号。上面代码中的 `allow_synced` 就是这条策略的执行点。
3. 高保障场景额外要求 attestation 校验，确认认证器来自受信任的厂商批次。

**局限必须说清楚**：AAGUID 白名单与 attestation 在同步 passkey 场景下常常不可用——部分平台不返回可用的 attestation，或返回的 AAGUID 是通用值（厂商能力随版本变化，落地前须实测，属"需自证"事项）。因此"限定设备绑定"这条策略的实际执行力，取决于你的 IdP 与终端平台组合，而不是取决于规范本身。**推演**：企业级 passkey 的可管理性（凭据归属证明、批量吊销、设备绑定声明）大概率会在未来两年内成为 IdP 的差异化能力，但截至本书截稿时点，它仍是选型时需要逐项验证的空白区。

## 14.3.4 注册环节：整个体系的地基

一个反直觉的事实：**认证体系最脆弱的时刻是注册，不是登录。**

登录时用户已有强凭据，攻击者需要突破密码学。注册时用户还没有强凭据，系统必须用某种"更弱的东西"来确认这个人是谁——通常是一个密码，或者一封发到邮箱的链接，或者服务台的一通电话。攻击者只需要在真正的员工注册之前，抢先用泄露的密码登录并注册自己的认证器。这类"抢注"在入职季与大规模无密码迁移期高发，因为那时大量账号处于"有密码、无强认证器"的空窗状态。

可用的可信注册通道，按强度排序：

| 通道 | 做法 | 适用 | 风险 |
|------|------|------|------|
| 现场核验 | 入职当天线下核验证件后，由 IT 现场发放临时访问通行证（TAP）并当场完成注册 | 总部与大型办公点 | 无法覆盖远程入职 |
| 已有强认证器背书 | 用已注册的抗钓鱼认证器，添加第二个认证器 | 日常增补 | 首个认证器如何来仍需解决 |
| 经理带外确认 + 视频核验 | 视频中出示证件，经理确认，双人复核 | 远程入职 | 依赖人工，需防深度伪造 |
| 邮件链接 | 发注册链接到企业邮箱 | 不推荐单独使用 | 邮箱本身可能已被接管 |
| 服务台电话核验 | 靠"只有本人知道"的问题 | 不可接受 | 见 14.3.5 |

三条工程规则：

**临时访问通行证必须一次性、短时效、限用途。** 建议单次使用、有效期 60 分钟、仅可用于注册认证器而不能访问业务应用。签发本身要有审计记录和签发人。

**注册窗口要收紧。** 账号创建后到首个强认证器注册完成之间的时间窗，是抢注风险窗口。把它压到 24 小时以内，并对窗口内的异常登录（陌生地理位置、陌生设备）直接阻断而非仅记录。

**注册事件必须通知本人。** 任何新增认证器的操作，都要立即通过独立通道（企业邮箱 + 移动端推送 + 短信，至少两条）通知用户本人，通知内容包含时间、地点、设备。这条成本极低，却是发现抢注的主要手段。

## 14.3.5 账号恢复：整个体系最弱的一环

现在回到本节开头的核心判断：认证强度等于最弱可用路径的强度。对绝大多数企业而言，那条最弱路径就是**"我手机丢了"**。

一个典型的服务台社工攻击脚本是这样的（依据 CISA/FBI 通报的公开 TTP 归纳[4]）：

1. 从职业社交平台确认目标是 IT 或工程岗（这类人权限高，且服务台不会觉得可疑）。
2. 从公开泄露数据集中拿到工号、生日、入职年份、上级姓名。
3. 从企业官网、财报、招聘启事拼出内部术语与组织架构，让对话听起来像内部人。
4. 选周五下午或节假日前致电服务台（人手最少、最想快点下班的时段）。
5. 制造时间压力："我马上要开客户会，登不进去，能不能先帮我重置一下。"
6. 服务台核验三个"只有本人知道"的问题——全部答对，因为答案在第 2 步就拿到了。
7. 服务台重置 MFA，攻击者注册自己的认证器。

这个脚本的每一步都利用了流程本身的设计，没有任何技术漏洞。因此修复也必须在流程层：

**恢复流程的五条设计原则：**

1. **恢复的强度不得低于原认证。** 用一通电话恢复一个 FIDO2 凭据，等于把整个体系降级到电话核验。
2. **核验必须用服务台不掌握、攻击者也拿不到的信息**——不是生日和工号，而是带外因素：向注册在册的移动号码发起独立挑战、要求视频出示证件并与 HR 存档照片比对、由直属经理在独立系统中确认（且经理需完成自己的强认证）。
3. **设置恢复冷却期。** 高权限账号的恢复请求提交后强制等待（例如 4 小时），期间向本人的所有已知通道发送告警。绝大多数社工攻击经不起这个延迟——攻击者需要的是即时性。
4. **恢复后进入降级访问期。** 恢复完成后的 24 小时内，该账号不能访问特权资源、不能修改认证方法、不能批准他人请求。这条是纵深防御：即使恢复被骗过，攻击者也拿不到最有价值的东西。
5. **恢复必须是可检测事件。** 每一次恢复都要产生高优先级告警送到 SOC，含操作人、被恢复账号、渠道与耗时。见 14.10。

```yaml
# 账号恢复策略（示例）：按账号等级差异化，强度不低于原认证
account_recovery_policy:
  tiers:
    - name: tier0_admin
      applies_to: ["role:GlobalAdmin", "role:DomainAdmin", "group:Tier0"]
      allowed_channels: ["in_person_verified"]
      require_approvers: 2
      approver_constraints:
        must_be_phishing_resistant_authenticated: true
        must_not_be_same_team_as_requester: true
      cooldown_minutes: 240
      post_recovery_restriction_hours: 24
      notify: ["user_primary_email", "user_mobile", "manager", "soc"]

    - name: privileged_staff
      applies_to: ["group:Engineering", "group:Finance-AP", "group:HR-Core"]
      allowed_channels: ["in_person_verified", "video_id_check_with_manager"]
      require_approvers: 1
      cooldown_minutes: 60
      post_recovery_restriction_hours: 24
      notify: ["user_primary_email", "user_mobile", "manager", "soc"]

    - name: standard_staff
      applies_to: ["*"]
      allowed_channels:
        - "in_person_verified"
        - "video_id_check_with_manager"
        - "existing_strong_authenticator"
      require_approvers: 1
      cooldown_minutes: 30
      post_recovery_restriction_hours: 4
      notify: ["user_primary_email", "user_mobile", "manager"]

  forbidden_channels:
    - "knowledge_based_questions"
    - "sms_only_verification"
    - "email_link_only"

  helpdesk_controls:
    max_recoveries_per_agent_per_day: 5
    require_ticket_reference: true
    record_call: true
    random_qa_sample_rate: 0.1
```

怎么读这段配置：`forbidden_channels` 是整份策略里最重要的三行——把基于知识的问答（KBA）明确列为禁止渠道，是抵抗服务台社工的核心动作，而这恰恰是多数企业当前的默认做法。`max_recoveries_per_agent_per_day` 针对的是另一类风险：被收买或被冒充的服务台坐席；限流让批量滥用变得可见。`random_qa_sample_rate` 是治理闭环——10% 的通话抽检，既用于质量改进，也让坐席知道存在事后复核。

**生产坑：恢复流程的绕过路径通常在别处。** 你把服务台流程加固了，但用户还可以通过"自助密码重置门户"用短信验证码重置密码，然后用密码 + 短信登录，再自行添加新认证器——整个恢复流程被绕过了，而且全程自动化、无人工介入、无告警。**审视恢复能力时，要列举的是"所有能让一个没有认证器的人重新获得访问的路径"，而不是那条写在制度里的路径。** 这个清单通常比想象中长：自助门户、服务台、经理代提工单、目录管理员直接改属性、以及某个仍然存在的旧版认证接口。

## 14.3.6 条件访问策略工程

MFA 决定"用什么认证"，条件访问（Conditional Access，CA）决定"什么情况下需要认证什么、以及是否允许"。它是把认证从二元判断变成风险决策的地方。

策略设计建议按五个维度构造矩阵：**谁（人群/角色）× 访问什么（应用敏感度）× 从哪来（网络/地理）× 用什么设备（合规状态）× 当前风险（登录风险/用户风险）**。不要试图为每个组合写一条策略，而是先定义少数几条基线策略覆盖 90% 场景，再用例外策略处理剩余部分。

一套可参考的基线策略集（策略名建议采用 `CA<编号>-<人群>-<资源>-<控制>` 的命名规范，便于审计与变更追溯）：

| 编号 | 覆盖 | 控制 |
|------|------|------|
| CA001 | 全体用户，全部云应用 | 要求 MFA；阻断旧版认证协议 |
| CA002 | 管理员角色，全部应用 | 要求抗钓鱼认证器 + 合规设备；会话 4 小时 |
| CA003 | 全体用户，高敏感应用 | 要求合规设备 + 抗钓鱼认证器 |
| CA004 | 登录风险=高 | 阻断；风险=中则要求重新强认证 |
| CA005 | 非受管设备访问办公套件 | 仅浏览器访问、禁止下载、会话 1 小时 |
| CA006 | 来自不开展业务的国家/地区 | 阻断（配合明确的出差例外流程） |
| CA007 | 破玻璃账号 | 从所有策略中排除，但强制监控告警（见 14.6） |

```json
{
  "displayName": "CA002-Admins-AllApps-PhishingResistant",
  "state": "enabled",
  "conditions": {
    "users": {
      "includeRoles": [
        "Global Administrator",
        "Privileged Role Administrator",
        "Security Administrator",
        "Application Administrator"
      ],
      "excludeGroups": ["grp-breakglass-accounts"]
    },
    "applications": {
      "includeApplications": ["All"]
    },
    "clientAppTypes": ["all"],
    "locations": {
      "includeLocations": ["All"]
    }
  },
  "grantControls": {
    "operator": "AND",
    "builtInControls": ["compliantDevice"],
    "authenticationStrength": {
      "displayName": "Phishing-resistant MFA",
      "allowedCombinations": [
        "windowsHelloForBusiness",
        "fido2",
        "x509CertificateMultiFactor"
      ]
    }
  },
  "sessionControls": {
    "signInFrequency": {
      "value": 4,
      "type": "hours",
      "isEnabled": true
    },
    "persistentBrowser": {
      "mode": "never",
      "isEnabled": true
    }
  }
}
```

怎么读这段策略：`clientAppTypes` 设为 `all` 而非仅 `browser`，是为了覆盖非交互式与旧协议路径——**只覆盖浏览器登录的策略等于没有策略**，因为攻击者会选择走 IMAP、SMTP 或其他不支持现代认证的通道。`persistentBrowser: never` 阻止"保持登录状态"，这在管理员场景下必要，因为持久 Cookie 正是 AiTM 攻击的窃取目标。`excludeGroups` 指向破玻璃账号组，这是**唯一应当存在的排除项**——每增加一个排除，都是在这道防线上开一个洞。

**排除列表治理是条件访问最重要也最被忽视的运营工作。** 一条可执行的纪律：每个排除项必须有责任人、业务理由、到期日；到期自动失效而非自动续期；每季度产出排除项清单送安全委员会复核；排除项总数设上限并纳入度量。见过的失控形态是一个排除组里有 200 多个账号，最初的理由都已无人知晓，而其中包含若干高权限账号——这个组本身就是一条完整的绕过路径。

**上线纪律**：任何新策略先以"仅报告（report-only）"模式运行至少一周，用实际登录数据评估影响面，确认误伤规模后再切换为启用。同时必须先确保破玻璃账号已被排除并验证可用——把自己锁在门外是条件访问上线的经典事故，且它发生时你无法登录去修复它。

## 14.3.7 MFA 疲劳的检测与抑制

即使部署了号码匹配，推送类认证在过渡期仍会长期存在。三层处置：

**抑制**：限制单位时间内的推送次数（例如 10 分钟内最多 3 次），超限后自动锁定该账号的推送通道并要求走替代验证；连续拒绝达到阈值后自动触发密码重置流程（因为密码已经泄露是这类攻击的前提）。

**检测**：以下 Sigma 规则描述了核心特征——短时间内同一账号大量 MFA 挑战、其中多数被拒绝或超时，随后出现一次成功。

```yaml
title: MFA Fatigue Attack Pattern
id: 3f2c81e7-96b4-4a0d-8b7e-2c5f9a1d4e60
status: experimental
description: 短时间内同一用户产生大量 MFA 挑战且多数失败，随后出现成功登录
references:
  - https://attack.mitre.org/techniques/T1621/
logsource:
  product: azure
  service: signinlogs
detection:
  mfa_denied:
    ResultType:
      - '500121'
      - '50074'
  timeframe: 15m
  condition: mfa_denied | count() by UserPrincipalName > 8
falsepositives:
  - 用户更换手机后重复尝试
  - 推送通道故障导致的批量超时
level: high
tags:
  - attack.credential_access
  - attack.t1621
```

这条规则的关键在阈值与时间窗的组合：`8` 次 / `15` 分钟是一个折中（示例口径），过低会被换机、网络不稳等正常场景淹没。更可靠的做法是把它与"拒绝之后 30 分钟内出现成功登录且来源 IP 与历史不符"做关联，两个条件同时成立时才升级为高优先级事件——单看拒绝次数误报太多，单看成功登录又没有异常特征。

**响应**：用户拒绝一次 MFA 请求，本质上是在举报一次攻击。这个信号在多数企业被完全浪费。建议把"用户主动拒绝"作为一等事件：自动向用户发送确认（"刚才是你本人在登录吗"），回答"不是"则立即禁用会话、重置密码并转 SOC。这条链路的成本很低，但它把每一个员工变成了传感器。

## 14.3.8 无密码迁移的四个阶段

无密码不是一次切换，而是一条需要 12～24 个月的路径。四个阶段与各自的退出标准：

| 阶段 | 目标 | 退出标准 |
|------|------|---------|
| 一、并存 | 抗钓鱼认证器可选注册，密码仍可用 | 目标人群注册率 > 60%；服务台支持流程就绪 |
| 二、默认无密码 | 登录界面默认走无密码，密码作为备选 | 无密码登录占比 > 85%；恢复流程已加固（14.3.5） |
| 三、密码不可用 | 策略上禁止密码登录，密码仍存在于目录中 | 无密码登录占比 > 98%；例外人群方案落地 |
| 四、移除密码 | 账号无密码凭据 | 全部遗留协议下线；应急恢复不依赖密码 |

大部分企业会长期停在阶段二到三之间，卡点几乎总是同一批人群：

| 人群 | 困难 | 可行方案 |
|------|------|---------|
| 共享终端（车间、零售、医院） | 一台设备多人轮流使用，平台认证器绑定到设备 | 硬件密钥随人走；或 NFC 卡片 + PIN |
| 呼叫中心 | 禁带手机；换班频繁 | 硬件密钥挂工牌；工位不绑定 |
| 外包与合作方 | 设备不受管，硬件密钥采购与回收成本高 | 允许同步 passkey，但限制可访问资源范围 |
| 无智能手机人群 | 无平台认证器 | 硬件密钥；成本由 IT 承担而非部门 |
| 高管 | 抗拒流程变化，且是钓鱼首要目标 | 专人上门配置，配两把密钥，纳入 Tier 0 保护 |
| 遗留应用与协议 | 只支持用户名密码 | 前置代理或改造；无法改造的隔离并单独审计 |

**判断**：阶段三（禁用密码登录）才是收益拐点。停在阶段一、二只是增加了一条更安全的可选路径，攻击者仍然会走密码那条——**只要密码还能用，密码就是你的实际认证强度**。这是无密码项目最常被误解的地方：注册率的提升不等于风险的下降，只有关闭旧路径才等于风险下降。

## 14.3.9 失败叙事：我们先推 TOTP，两年后返工

2019 年前后，我们做了一次全员 MFA 推广，选择了 TOTP App。选型理由在当时非常充分：免费、无硬件采购、支持所有平台、用户熟悉度高，而硬件密钥当时单价不低且需要物流分发。项目做得很漂亮——8 个月覆盖 96% 账号，服务台工单增量可控，管理层认可。

两年后的一次演练，红队用一个反向代理钓鱼页面，在 3 天内拿到 27 个账号的有效会话，其中包括 2 个管理员账号。用户全部完成了 TOTP 验证，全部没有察觉。演练报告里最刺眼的一句话是：**"MFA 的部署没有改变这条攻击路径的成本。"**

复盘时有两个认识。

第一，我们当时把 MFA 当成了一个"是否部署"的二元问题，而没有把它当成"抵抗什么攻击"的问题。如果在 2019 年问一句"AiTM 代理钓鱼会不会成为主流"，答案在当时是不确定的；但如果问"TOTP 能不能抵抗 AiTM"，答案在当时就是明确的否。**我们回避了那个能问出正确答案的问题。**

第二，返工的代价远高于一开始就做对。第二次迁移面对的不是空白，而是一个已经运行两年、用户已经习惯、服务台已经建立流程、若干应用已经硬编码集成的 TOTP 体系。用户的普遍反应是"又要换"，这种情绪本身就是推广阻力，且它是我们自己制造的。最终第二次迁移用了 14 个月，比第一次更久。

留下的判断有两条。其一：**认证方案的选型标准应当是"能抵抗什么"，而不是"部署有多快"**；快速部署的价值会在两年内被攻击演进抵消，而迁移成本会随时间增长。其二：如果预算只够给一部分人配硬件密钥，正确的做法是"给高风险人群一个强方案，其余人排期"，而非"给所有人一个弱方案"——**部分覆盖的强控制，优于全面覆盖的弱控制**。

## 14.3.10 度量

| 指标 | 定义 | 参考目标 |
|------|------|---------|
| 抗钓鱼认证器覆盖率 | 已注册抗钓鱼认证器的账号 ÷ 总账号 | 特权账号 100%；全员 > 90% |
| 抗钓鱼登录占比 | 抗钓鱼方式完成的登录 ÷ 总登录数 | > 95%（这比覆盖率更真实） |
| 密码可用账号数 | 仍允许密码登录的账号数 | 持续下降，特权账号为 0 |
| 条件访问排除项数 | 各策略排除项去重后的账号数 | < 10 且全部有到期日 |
| 恢复事件量与耗时 | 每月账号恢复次数、平均处理时长 | 量应稳定；突增即异常 |
| 恢复后 24 小时内异常率 | 恢复账号在限制期内触发风险信号的比例 | 逐例复核 |
| MFA 拒绝事件闭环率 | 用户主动拒绝后完成核实的比例 | 100% |

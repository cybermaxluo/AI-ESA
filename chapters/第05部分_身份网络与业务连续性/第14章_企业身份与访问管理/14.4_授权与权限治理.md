# 14.4　授权与权限治理

"最小权限专项"在企业里有一条几乎固定的生命周期曲线。

第 1 个月，立项，管理层支持，全员通报。第 2 个月，盘点，导出全部权限数据，发现有 4.7 万条用户-权限关系，其中 1.9 万条从未被使用过。第 3 个月，制定清理计划，按应用分批。第 4 个月，第一批清理执行，收回 3000 条。第 5 个月，出现第一起业务投诉——某个季度末才运行的对账任务失败了，因为它的权限在"180 天未使用"规则下被回收。第 6 个月，清理暂停，改为"业务确认后再收"。第 7 个月，业务确认的回复率是 23%。第 8 个月，项目更名为"权限持续优化"，从专项变成日常。第 12 个月，没有人再提起它，而权限总数比启动时多了 6000 条。

这条曲线的每一步都是理性的，没有人做错事。它揭示的是**权限治理的收益与成本在时间上的错配**：清理的成本立刻发生（人力、业务中断风险、沟通摩擦），收益则是"某个不确定的未来不会发生某件不确定的坏事"。任何按季度考核的组织，都会自然地把这类工作排到后面。

所以本节的立场是：**不要做"最小权限运动"，要做能持续运行的权限工程**。运动会结束，工程不会。具体而言就是四件事——把权限变成可命名的对象（14.4.1）、把角色变成有人负责的资产（14.4.2、14.4.3）、把上下文约束交给 ABAC 做减法（14.4.4）、把职责分离与申请审批变成有信息支撑的日常流程（14.4.5、14.4.6）。

## 14.4.1 先解决命名问题：权限的三层模型

权限治理失败的第一个原因往往非常朴素：**没有人能读懂权限的名字**。

一条典型的权限记录长这样：`SAP_R3_PRD_S_TCODE_FB60_ALL`。审阅它的是一位销售总监。他不知道 FB60 是供应商发票录入事务码，不知道 `ALL` 指的是不受公司代码限制，也不知道这条权限与他团队某人的工作有没有关系。在这种信息条件下，唯一理性的选择就是点"批准"。

解决办法是引入中间层，把权限组织成三层：

| 层次 | 定义 | 命名对象 | 谁维护 | 举例 |
|------|------|---------|-------|------|
| 技术权限（Technical Entitlement） | 应用内的原子授权对象 | 系统生成 | 应用管理员 | `SAP_R3_PRD_S_TCODE_FB60_ALL` |
| 业务权限（Business Entitlement） | 一组技术权限的有业务含义的封装 | 人工命名 | 应用业务负责人 | "应付账款-发票录入（不含审批）" |
| 岗位角色（Job Role） | 一个岗位所需业务权限的集合 | 人工命名 | 岗位所属业务线 | "应付会计（华东）" |

这三层里，**中间层是全部治理能力的来源**。没有它，审阅、SoD 检测、角色工程、权限申请全部退化成对技术字符串的操作。有了它，审阅问题从"这条权限该不该保留"变成"这个人还需不需要录入供应商发票"——后者是业务人员真的能回答的问题。

建立中间层的成本很高（需要逐应用与业务方梳理），因此**不要试图一次覆盖所有应用**。可行的做法是按风险排序，只对前 20～30 个应用建立业务权限层，其余保持技术权限直连。判断依据是：该应用的权限是否会进入访问审阅、是否涉及 SoD、是否涉及敏感数据。

```yaml
# 权限目录条目（示例）：业务权限是治理的最小单位
entitlement:
  id: ENT-AP-INVOICE-ENTRY
  display_name: "应付账款-发票录入（不含审批）"
  description: "录入与修改供应商发票，不含放行与付款执行"
  application: sap_ecc_prd
  owner:
    business_owner: P-40b7c1de-2a55-4b83-91cc-7f6e2d0b8a31
    technical_owner: P-9a1f0b32-88ce-4a17-b3d2-6e40c7215fa9
  risk:
    sensitivity: confidential
    sod_group: ap_entry
    privileged: false
    financial_impact: true
  technical_entitlements:
    - SAP_R3_PRD_S_TCODE_FB60_ALL
    - SAP_R3_PRD_S_TCODE_FV60_ALL
    - SAP_R3_PRD_S_BKPF_BUK_1000
  grant_policy:
    default_ttl_days: 365
    requires_approval: ["line_manager", "business_owner"]
    auto_revoke_if_unused_days: 120
    review_frequency_months: 6
  evidence:
    control_ref: ["SOX-P2P-03"]
    last_reviewed: "2026-05-14"
```

怎么读这段目录：`sod_group` 是后面 14.4.5 做冲突检测的挂载点，必须在权限定义时就打上，事后补是最痛苦的工作。`default_ttl_days` 体现了一条重要主张——**授权默认应当有期限**，无期限授权应当是需要额外理由的例外，而不是默认。`auto_revoke_if_unused_days: 120` 与 `default_ttl_days: 365` 是两条独立的回收路径，前者针对"给了没用"，后者针对"用过但已不需要"。

## 14.4.2 角色工程：挖掘出来的角色需要有人认领

角色工程有两条路，实践中必须同时走。

**自上而下（top-down）**：从岗位职责出发，与业务共同定义"这个岗位应该有什么"。产出质量高、可解释、可辩护，但极慢——梳理一个业务线通常要数周，且业务方的耐心有限。

**自下而上（bottom-up，即角色挖掘 role mining）**：从现有的用户-权限矩阵出发，用算法找出高频共现的权限组合作为候选角色。产出快，覆盖广，但**产出的是数学结构而非业务概念**。

关于角色挖掘，需要说清楚它的真实效果。在典型实施场景中，挖掘能把 60%～75% 的用户-权限关系归入候选角色，剩余部分是长尾例外；而这些候选角色中，最终被业务认领并投入使用的通常只有三到五成（示例口径，非行业基准，且强依赖数据质量与业务配合度）。也就是说，**角色挖掘的实际净产出可能只覆盖三分之一到一半的权限关系**。

这不是算法不好，而是问题本身的性质：算法能告诉你"这 47 个人共同拥有这 12 项权限"，但不能告诉你这 12 项权限合起来叫什么、该由谁负责、以及未来新人是否也应该拥有它们。**候选角色如果没有业务负责人认领，它就只是又一个需要被审阅的对象，反而增加了治理负担。**

```python
"""角色挖掘：贪心集合覆盖 + 认领元数据占位。

方法说明：
- 输入是用户-权限二部图（user -> set(entitlement)）。
- 迭代地寻找"收益最大"的候选角色：收益 = 覆盖的用户-权限对数量，
  并对角色规模施加惩罚，避免产出巨型角色（巨型角色等于没分角色）。
- 输出候选角色 + 覆盖率 + 未覆盖残差，残差是必须人工处理的长尾。

刻意的取舍：不追求最优解（最小角色集是 NP-hard），
追求"可解释、可停止、可交给业务讨论"的近似解。
"""
from collections import Counter
from dataclasses import dataclass, field
from itertools import combinations
from typing import Dict, FrozenSet, List, Set, Tuple


@dataclass
class CandidateRole:
    entitlements: FrozenSet[str]
    members: Set[str]
    covered_pairs: int
    proposed_name: str = ""
    business_owner: str = ""      # 空 = 未认领，未认领角色不得上线
    status: str = "candidate"     # candidate / claimed / rejected

    def size(self) -> int:
        return len(self.entitlements)


def _frequent_entitlement_sets(
    assignments: Dict[str, Set[str]], min_members: int, max_size: int
) -> List[Tuple[FrozenSet[str], Set[str]]]:
    """枚举满足最小成员数的权限组合。max_size 控制组合爆炸。"""
    ent_users: Dict[str, Set[str]] = {}
    for user, ents in assignments.items():
        for e in ents:
            ent_users.setdefault(e, set()).add(user)

    frequent = {
        frozenset([e]): users
        for e, users in ent_users.items()
        if len(users) >= min_members
    }
    current = dict(frequent)
    for _ in range(max_size - 1):
        nxt: Dict[FrozenSet[str], Set[str]] = {}
        keys = list(current.keys())
        for a, b in combinations(keys, 2):
            merged = a | b
            if len(merged) > max_size or merged in nxt:
                continue
            users = current[a] & current[b]
            if len(users) >= min_members:
                nxt[merged] = users
        if not nxt:
            break
        frequent.update(nxt)
        current = nxt
    return sorted(frequent.items(), key=lambda kv: -len(kv[0]) * len(kv[1]))


def mine_roles(
    assignments: Dict[str, Set[str]],
    min_members: int = 5,
    max_role_size: int = 12,
    size_penalty: float = 0.15,
    max_roles: int = 50,
) -> Dict[str, object]:
    remaining = {u: set(ents) for u, ents in assignments.items()}
    total_pairs = sum(len(v) for v in remaining.values())
    roles: List[CandidateRole] = []

    while len(roles) < max_roles:
        candidates = _frequent_entitlement_sets(
            {u: v for u, v in remaining.items() if v}, min_members, max_role_size
        )
        best, best_gain = None, 0.0
        for ent_set, users in candidates:
            gain = len(ent_set) * len(users) * (1 - size_penalty * (len(ent_set) - 1))
            if gain > best_gain:
                best, best_gain = (ent_set, users), gain
        if best is None or best_gain <= 0:
            break

        ent_set, users = best
        covered = 0
        for u in users:
            covered += len(remaining[u] & ent_set)
            remaining[u] -= ent_set
        roles.append(CandidateRole(ent_set, set(users), covered))

    residual = {u: v for u, v in remaining.items() if v}
    covered_pairs = total_pairs - sum(len(v) for v in residual.values())
    return {
        "roles": roles,
        "coverage_ratio": round(covered_pairs / total_pairs, 4) if total_pairs else 0.0,
        "residual_users": len(residual),
        "residual_pairs": sum(len(v) for v in residual.values()),
        "top_residual_entitlements": Counter(
            e for ents in residual.values() for e in ents
        ).most_common(10),
    }


def unclaimed_roles(result: Dict[str, object]) -> List[CandidateRole]:
    """未认领的候选角色不得进入生产，此函数用于生成认领待办清单。"""
    return [r for r in result["roles"] if not r.business_owner]
```

怎么读这段代码：`size_penalty` 的存在是为了对抗一个典型的失败模式——不加惩罚时算法倾向于产出"包含 40 项权限、覆盖 200 人"的巨型角色，它的覆盖率指标很好看，业务含义等于零。`residual` 与 `top_residual_entitlements` 是本函数最有价值的输出：**残差里出现频率最高的权限，往往就是那些"人人都有一点、但每个人的组合都不同"的权限，它们通常是历史遗留或临时授予**，是清理的优先目标。`unclaimed_roles` 存在的唯一目的，是把"未认领"这个状态显式化——它是角色能否上线的门槛，不是可以稍后处理的元数据。

**工程建议**：把挖掘产出交给业务时，不要交角色列表，要交三样东西——候选角色的成员名单（业务方认人不认权限）、这个角色相对于岗位描述多出与缺少的部分、以及认领后需要承担的责任（每半年确认一次内容）。只交列表的结果通常是没有回音。

## 14.4.3 角色爆炸：症状、成因与止损

角色爆炸的典型体征是：角色数量接近甚至超过用户数量的一半，其中大量角色只有 1～2 个成员。此时角色层已经不再是抽象层，而变成了用户的另一种拼写方式，管理成本高于直接授权。

三个成因：

**组合维度失控。** 角色按"部门 × 职级 × 地域 × 法人实体"命名，四个维度各 10 个取值，理论上限就是一万个角色。解法是**角色分层**：基础角色（按岗位族）+ 叠加角色（按地域或数据范围），用叠加代替组合，把乘法变成加法。

**例外角色化。** 每出现一个特殊需求就新建一个角色（"应付会计-张伟专用"）。解法是明确禁止单人角色，特殊需求走直接授权 + 有效期，而不是污染角色体系。直接授权虽然"不优雅"，但它是可见的、可审计的、有期限的；伪装成角色的单人授权则会永久留存。

**只增不删。** 项目结束、系统下线、组织调整后，角色没有退场机制。解法是把"角色成员数为 0 超过 90 天"和"角色包含的权限已全部失效"作为自动废弃条件。

| 指标 | 定义 | 健康区间（示例口径） |
|------|------|-------------------|
| 角色/用户比 | 角色总数 ÷ 用户总数 | < 0.1 |
| 单人角色占比 | 成员数 ≤ 1 的角色 ÷ 角色总数 | < 5% |
| 空角色数 | 成员数为 0 的角色 | 0（超过 90 天自动废弃） |
| 角色覆盖率 | 通过角色获得的权限关系 ÷ 权限关系总数 | > 70% |
| 直接授权占比 | 未经角色的直接授权 ÷ 权限关系总数 | < 30% 且全部有期限 |

需要提醒的是，**角色覆盖率 100% 不是目标**。追求它会逼出大量单人角色和例外角色，反而制造爆炸。留出 20%～30% 的直接授权空间、并要求它们全部带期限，是更健康的稳态。

## 14.4.4 ABAC 的正确用法：只做减法，不做加法

RBAC 与 ABAC 的关系常被表述为"下一代替代上一代"，这在企业环境中是误导。它们解决的是不同的问题：**RBAC 回答"这个人属于哪一类"，ABAC 回答"此时此地这次访问是否符合约束"**。

ABAC 的代价集中在可解释性上，而可解释性直接决定治理能力：

- **"我为什么没有权限"难以回答。** RBAC 下的答案是"你不在这个角色里"；ABAC 下的答案可能是七个条件中的第四个在当前上下文求值为假，而这个上下文十分钟后又会变。没有决策日志的 ABAC 系统，服务台无法支持。
- **"谁有权访问这份数据"从查询变成了求解。** RBAC 下这是一次数据库查询；ABAC 下它需要对全体用户 × 全部上下文组合做求值，实际上无法穷举。而这个问题恰恰是审计与事件响应最常问的。
- **属性质量决定一切。** 授权依赖部门、职级、设备状态、位置等属性，任何一个属性源脏了或延迟了，都会静默地变成错误授权。见 14.1.2 的权威源矩阵。

因此本书给出的判断是：**在企业授权体系里，把 ABAC 用作约束层而非授予层——ABAC 只做减法，不做加法。**

具体地说，权限的"有无"由 RBAC 决定（可枚举、可审阅、可交给业务负责），而 ABAC 负责在此基础上收紧：必须是合规设备、必须在办公时间、必须已通过抗钓鱼认证、必须访问本人所属区域的数据。这样做的三个好处：**"谁有权限"这个问题仍然可以被回答**（答案是 RBAC 的集合，ABAC 只会让实际可访问范围更小）；审计证据链保持清晰；ABAC 策略出故障时，失效方向是"更严"而不是"更松"。

反过来，如果用 ABAC 做授予（例如"部门等于财务则自动获得财务系统访问"），那么一次属性同步错误就等于一次批量越权授权，而且没有任何授权记录可供审阅——因为权限从来没有被"授予"过，它是被计算出来的。

工程上必须配套两件事：

**决策日志记录每个条件的独立结果**，而不只是最终的允许/拒绝。这是 8.5.3 已经强调过的点，在企业规模下它的价值更大——服务台每天要处理数十起"我进不去"，没有条件级日志就只能靠工程师现场调试。

**提供反向查询能力**：给定一个资源，枚举出在"典型上下文"下可以访问它的主体集合。虽然无法穷举全部上下文，但用一组预定义的代表性上下文（办公网 + 合规设备 + 工作时间）做求值，足以回答审计的多数问题。这个能力必须在设计期就纳入，事后加极其困难。

下表是"RBAC 给有无、ABAC 给条件"的三个具体落点，可以直接作为设计模板：

| 场景 | RBAC 决定（可枚举、可审阅） | ABAC 收紧（不新增权限） |
|------|------------------------|----------------------|
| 财务系统付款查询 | 岗位角色"应付会计"包含查询权限 | 仅限本人所属公司代码；非合规设备只读且禁止导出 |
| 生产数据库访问 | 角色"DBA-生产"包含连接权限 | 仅在有关联变更单时放行；无单则拒绝并记录 |
| 客户数据平台 | 角色"客服专员"包含客户档案读取 | 单次会话查询量超阈值触发降级（脱敏返回）并告警 |

第二行是 ABAC 做减法最典型的用法：权限本身是常驻的（DBA 需要它才能工作），但**可用性被绑定到一个外部业务事实上**（有没有生效中的变更单）。这样既保留了"谁有权限"的可枚举性，又把实际可用窗口压缩到了业务需要的时刻——效果接近 14.6 的 JIT，但不需要改造授权体系。

决策日志的最小结构如下，关键是 `conditions` 数组必须逐条给出结果，而不是只给最终判定：

```json
{
  "decision_id": "dec-2026-07-31-0d4c1a9f",
  "timestamp": "2026-07-31T09:41:22Z",
  "subject": {
    "person_id": "P-8f3a91c2",
    "roles": ["DBA-PROD"],
    "auth_strength": "phishing_resistant",
    "device_compliant": true
  },
  "resource": {
    "id": "db-prod-billing",
    "sensitivity": "restricted"
  },
  "action": "connect",
  "effect": "deny",
  "conditions": [
    {"name": "role_grants_connect", "result": true, "source": "rbac"},
    {"name": "device_is_compliant", "result": true, "source": "mdm"},
    {"name": "auth_is_phishing_resistant", "result": true, "source": "idp"},
    {"name": "active_change_ticket_exists", "result": false, "source": "itsm"},
    {"name": "within_maintenance_window", "result": false, "source": "calendar"}
  ],
  "deny_reason": "active_change_ticket_exists=false",
  "policy_version": "authz-policy-2026.07.2"
}
```

怎么读这段日志：`deny_reason` 直接给出第一个失败条件的名字，服务台据此就能一句话答复用户（"你需要先开变更单"），无需工程介入；`policy_version` 让事后追溯成为可能——策略每天都在变，没有版本号的决策日志在三个月后毫无解释力；`source` 字段标明每个条件的属性来源，当授权出现异常时，它把排查范围从"整个授权系统"缩小到"某一个属性源"。

### agent 的授权：按工具授权，且不得超过委派人

人的授权模型建立在一个隐含前提上：岗位相对稳定，权限需求以月或年为尺度变化，因此"申请一次、长期持有、定期复核"是成立的。AI agent 不满足这个前提——它的权限需求随任务变化，尺度是分钟到小时，同一个 agent 今天在做工单分诊，下周接上一个新工具就在做变更影响分析。把 RBAC 原样搬过来，得到的是一种可以预先写出来的失败形态：**按这个 agent 可能承担的最大任务开一次权限，然后一直挂着**。

更麻烦的是 14.4.7 那条兜底规则在 agent 上失灵。"未使用即回收"之所以是唯一一条不需要业务判断就能执行的规则，是因为它依赖一个人类特性——人不会去碰自己用不到的权限。agent 会：它 7×24 运行、会遍历、会重试、会为了确认边界而试探性调用，几乎每一项授予过的权限都能在观测窗口里被触发至少一次。于是这条规则对 agent 身份永远回收不出东西，而报表上它仍然显示"已覆盖"。

三条可落地的做法。

**其一，按工具授权，不按资源授权。** agent 能触达的资源集合不可枚举——它会拼出你没设想过的查询组合与参数取值；而工具集合是可枚举、可命名、可交给业务负责人认领的，它是 14.4.1 业务权限层在 agent 场景的等价物。分工是：agent 的授权只决定"能调哪些工具"，工具内部再对具体资源做鉴权。

这条做法的代价必须写清楚：**工具层成了新的授权执行点**。如果工具用自己的高权限身份去访问后端（这是最常见的实现），工具层就变成一个混淆代理——agent 的实际能力等于工具的能力，按工具授权只是一层装饰。因此有一条配套的硬要求：工具必须把调用方身份（agent 身份与委派人身份两者）透传到后端，最终判定由后端做。

**其二，任务级的权限收窄。** 工具子集在任务开始时确定、任务结束即失效，这是 14.6 的 JIT 在 agent 上的形态，触发单位从"会话"换成"任务"。多数企业的授权平台短期内做不到按任务签发，但有一个今天就能做的最小版本：不改授权系统，只在 agent 运行时按任务类型加载工具子集，并把该子集与 `task_id` 一起写进日志。**能力收窄可以先于权限收窄落地**，前者是运行时的事，后者要等平台。

**其三，agent 不得拥有超过其委派人的权限——这必须是硬约束而不是建议。** 有效权限 = 委派人权限 ∩ agent 工具上界。放松它的后果是 agent 变成一条提权路径：一个只读用户通过调用一个具备写能力的 agent 完成了写操作，而这条路径不出现在任何权限报表里，因为该用户名下的权限一条没变。这类提权还顺带绕过职责分离——14.4.5 的冲突判定基于一个人持有的 `sod_group` 集合，agent 带来的能力不在这个集合里。**SoD 判定的输入必须是委派人自身的 group 集合，并上本次委派让他能间接触发的 group**，否则一级冲突可以被一个 agent 合法地绕开。

```python
"""agent 有效权限计算，以及把 agent 能力并入 SoD 判定。

两条规则：
1. 有效工具集 = 委派人可授出的工具 ∩ agent 工具上界 ∩ 本次任务声明的工具；
   三者取交集，任何一方收紧都立即生效，显式拒绝清单最后再减一次。
2. SoD 判定的输入是委派人自身的 sod_group 集合，并上"本次委派让他
   能间接触发的 sod_group"，结果交给 14.4.5 的 SodEngine 判定。
"""
from dataclasses import dataclass
from typing import Dict, FrozenSet, Set


@dataclass(frozen=True)
class AgentCeiling:
    agent_id: str
    allowed_tools: FrozenSet[str]
    denied_tools: FrozenSet[str]        # 显式拒绝优先于任何允许来源
    tool_sod_groups: Dict[str, str]     # 工具 -> 它等价于哪个 sod_group


def effective_tools(
    ceiling: AgentCeiling,
    delegator_tools: Set[str],
    task_declared_tools: Set[str],
) -> Set[str]:
    granted = (set(ceiling.allowed_tools)
               & set(delegator_tools)
               & set(task_declared_tools))
    return granted - set(ceiling.denied_tools)


def sod_groups_after_delegation(
    delegator_groups: Set[str],
    ceiling: AgentCeiling,
    delegator_tools: Set[str],
    task_declared_tools: Set[str],
) -> Set[str]:
    tools = effective_tools(ceiling, delegator_tools, task_declared_tools)
    reachable = {
        ceiling.tool_sod_groups[t] for t in tools if t in ceiling.tool_sod_groups
    }
    return set(delegator_groups) | reachable


if __name__ == "__main__":
    ceiling = AgentCeiling(
        agent_id="agent-svc-ap-assistant-prod-01",
        allowed_tools=frozenset({"invoice.read", "invoice.create", "payment.release"}),
        denied_tools=frozenset({"vendor.create"}),
        tool_sod_groups={
            "invoice.create": "ap_entry",
            "payment.release": "payment_release",
            "vendor.create": "vendor_master",
        },
    )
    delegator_tools = {"invoice.read", "invoice.create"}
    task_tools = {"invoice.read", "invoice.create", "payment.release"}
    # 委派人只有录入权限，agent 上界里却带着放行付款：交集把它挡在外面
    print(effective_tools(ceiling, delegator_tools, task_tools))
    print(sod_groups_after_delegation({"ap_entry"}, ceiling,
                                      delegator_tools, task_tools))
```

怎么读这段代码：三重交集里，`task_declared_tools` 是 agent 本次自己声明要用的工具，它只能收窄不能扩张——把它当成唯一输入就是把授权决定权交给了被授权方。`denied_tools` 在交集之后再减一次，不只在 `allowed_tools` 里过滤，这样无论工具从哪条来源进来都拦得住。

**这段代码里有代价的设计选择**：三重交集意味着委派人临时缺一项权限时，agent 会在任务半途静默地少做事情，表现出来是"结果不完整"，不报错。因此必须把"因交集为空被拒绝的调用"作为一类事件单独上报，否则这类收窄的副作用只会以业务抱怨的形式出现，且很难追到授权层。

**照抄时最容易改错的三处**：一是 `tool_sod_groups` 漏标——只要有一个高危工具没标 `sod_group`，SoD 判定在这个工具上就是盲的，而漏标不会报错，只会安静地少检出；二是把 `denied_tools` 的减法提前到交集之前，允许来源一多就会被绕过；三是把 `delegator_tools` 直接取成"该人所属角色的全部权限"，正确的取法是"该人可以授出的权限"，两者在存在不可再委派权限（如审批类）的场景下并不相同。

**适用边界。** 三条做法都以"存在一层可枚举的工具"为前提。agent 直接持数据库连接串、或直接调用后端 SDK 的架构里没有工具层，按工具授权无从谈起；这类 agent 只能退回到服务账号 + 资源级最小权限来治理（14.8 的形态 (b)），并把差距记进风险台账，不要在报表上把它算作已治理。第二条边界：交集规则要求"委派人权限"可查询，多数企业能查目录侧的角色，查不到应用内部的细粒度权限，因此交集在应用内部往往退化成"这个应用能不能用"这一档粒度。第三条边界是分工：这里只处理授权，agent 在授权范围之内被劫持后作恶属于检测问题（14.10）与提示注入防护（见 18.3），收窄权限只决定其能力上限。

**验证方法。** **提权路径实测**：取一个只读岗位的账号，让它通过每一个它能触发的 agent 尝试写操作，记录成功次数。这是"agent 是否已成为提权路径"的直接证据，问卷问不出来。**兜底规则失效验证**：对 agent 身份跑一遍 14.4.7 的"180 天未使用"规则，统计它回收出多少条；若接近零而该 agent 的工具清单明显偏宽，说明这条规则在 agent 上已经失效，需要换成任务定义比对（见 14.5）。**SoD 绕过验证**：取 14.4.5 矩阵里的全部一级冲突规则，逐条检查是否存在某个 agent，其工具集恰好补齐了冲突的另一半。

**运行指标。** **收窄比**：agent 工具上界条数 ÷ 委派人权限条数，越小越好，且应逐季下降。**因交集为空被拒绝的调用数**：收窄是否过紧的先行指标，突增通常指向上界定错，不要先按攻击处置。**工具的 `sod_group` 标注率**：未标注的工具即 SoD 盲区，目标 100%。**按任务加载工具子集的 agent 占比**：能力收窄的落地进度，它比"授权平台是否支持任务级签发"更早可测。

## 14.4.5 职责分离：矩阵要按流程写，不按应用写

职责分离（Segregation of Duties，SoD）的核心是防止单人完成一个完整的舞弊闭环。它的经典场景在财务（创建供应商 + 录入发票 + 审批付款），但在 IT 侧同样关键（编写代码 + 部署生产 + 审批变更；创建账号 + 授予权限 + 审阅权限）。

最常见的设计错误是**按应用编写 SoD 矩阵**。因为舞弊闭环通常跨应用：在采购系统建供应商，在 ERP 录发票，在网银执行付款。只在 ERP 内部检查冲突，会漏掉真正危险的组合。正确的做法是按业务流程建模：先画出流程的关键控制点，再把每个控制点映射到各系统的业务权限上。

冲突应当分三级处置，而不是一律禁止。三个档位直接用中文序数命名（一级 / 二级 / 三级），刻意不用字母记号：本书的裸 L0–L5 已被 17.1.2 的 AI 自主等级占用，而 SoD 禁止强度与自主性毫无关系，共用一套字母只会让人误以为两者能对齐。

| 等级 | 含义 | 处置 |
|------|------|------|
| 一级（绝对禁止） | 单人可完成完整资金或权限闭环 | 系统硬阻断，无例外；申请时即拒绝 |
| 二级（需补偿控制） | 存在风险但业务确有需要（如小型分支机构人手不足） | 允许，但强制补偿控制：事后复核、双人签核、专项监控、季度报告 |
| 三级（记录即可） | 理论冲突，实际风险低 | 记录并在审阅时提示，不阻断 |

二级的补偿控制必须是**可验证的具体动作**，而不是"加强管理"。例如"该用户执行的全部付款交易，由财务经理在次日通过对账报表逐笔复核，复核记录保存于 X 系统"——这样的描述才能在审计时作为证据。写成"通过管理手段控制风险"的补偿控制，等于没有控制。

```python
"""SoD 冲突检测：支持角色内冲突、跨角色组合冲突、以及跨应用流程级冲突。

设计要点：
1. 冲突定义在 sod_group 之间，而非具体权限之间——权限会变，流程不常变。
2. 同时检测"已生效的冲突"与"若批准该申请将产生的冲突"（预防优于事后）。
3. 已获批的例外（含补偿控制与到期日）参与判定，过期例外自动失效。
"""
from dataclasses import dataclass
from datetime import date
from typing import Dict, Iterable, List, Set, Tuple


@dataclass(frozen=True)
class SodRule:
    group_a: str
    group_b: str
    level: str          # 一级 / 二级 / 三级
    process: str        # 所属业务流程，用于报告归类
    description: str


@dataclass
class SodException:
    person_id: str
    group_a: str
    group_b: str
    approved_by: str
    compensating_control: str
    expires_on: date

    def covers(self, a: str, b: str, today: date) -> bool:
        if self.expires_on < today:
            return False
        return {a, b} == {self.group_a, self.group_b}


class SodEngine:
    def __init__(self, rules: Iterable[SodRule], exceptions: Iterable[SodException]):
        self.rules: Dict[Tuple[str, str], SodRule] = {}
        for r in rules:
            self.rules[tuple(sorted((r.group_a, r.group_b)))] = r
        self.exceptions = list(exceptions)

    def _violations(self, groups: Set[str], today: date) -> List[Dict[str, str]]:
        found = []
        ordered = sorted(groups)
        for i, ga in enumerate(ordered):
            for gb in ordered[i + 1:]:
                rule = self.rules.get((ga, gb))
                if rule is None:
                    continue
                found.append({
                    "group_a": ga,
                    "group_b": gb,
                    "level": rule.level,
                    "process": rule.process,
                    "description": rule.description,
                })
        return found

    def check_current(
        self, person_id: str, groups: Set[str], today: date
    ) -> List[Dict[str, str]]:
        result = []
        for v in self._violations(groups, today):
            covered = any(
                e.person_id == person_id and e.covers(v["group_a"], v["group_b"], today)
                for e in self.exceptions
            )
            v["status"] = "excepted" if covered else "open"
            result.append(v)
        return result

    def check_request(
        self, person_id: str, current_groups: Set[str],
        requested_groups: Set[str], today: date
    ) -> Dict[str, object]:
        """申请前置检查：返回是否应阻断，以及新产生的冲突。"""
        before = {
            (v["group_a"], v["group_b"]) for v in self._violations(current_groups, today)
        }
        after_all = self._violations(current_groups | requested_groups, today)
        new_conflicts = [
            v for v in after_all if (v["group_a"], v["group_b"]) not in before
        ]
        blocking = []
        for v in new_conflicts:
            covered = any(
                e.person_id == person_id and e.covers(v["group_a"], v["group_b"], today)
                for e in self.exceptions
            )
            if v["level"] == "一级" and not covered:
                blocking.append(v)
        return {
            "decision": "deny" if blocking else "allow",
            "blocking": blocking,
            "new_conflicts": new_conflicts,
        }


if __name__ == "__main__":
    rules = [
        SodRule("vendor_master", "ap_entry", "一级", "P2P",
                "同一人可新建供应商并录入其发票"),
        SodRule("ap_entry", "payment_release", "一级", "P2P",
                "同一人可录入发票并放行付款"),
        SodRule("code_commit", "prod_deploy", "二级", "SDLC",
                "开发者可自行部署生产，需事后复核"),
        SodRule("iam_grant", "iam_review", "一级", "IAM",
                "授权人不得审阅自己授出的权限"),
    ]
    engine = SodEngine(rules, exceptions=[])
    print(engine.check_request(
        "P-001", {"ap_entry"}, {"payment_release"}, date(2026, 7, 31)
    ))
```

怎么读这段代码：`check_request` 与 `check_current` 分离，对应两种完全不同的运营场景——前者是**预防**（申请时拦截，成本最低），后者是**检出**（存量清理，成本最高）。多数企业只做后者，于是永远在清理，因为入口是敞开的。`_violations` 用排序后的元组作为键，保证 `(a,b)` 与 `(b,a)` 命中同一条规则，这是很容易写错并导致单向漏检的地方（与 14.2.4 的转岗冲突判定同理）。例外的 `expires_on` 参与判定，意味着**过期例外自动恢复为冲突**，这是防止例外永久化的唯一有效手段。

**生产坑：矩阵有 200 条，执行的只有 8 条。** 原因通常是：矩阵由咨询顾问按行业模板交付，其中大量规则在本企业没有对应的权限映射（`sod_group` 从未被标注到实际权限上），于是这些规则永远不会命中。检验方法很简单——统计每条规则在过去 12 个月的命中次数，命中为 0 的规则要么是真的没有风险（应删除），要么是根本没接上（应修复）。**一条从未命中过的 SoD 规则不是"防患于未然"，它大概率是坏的。**

## 14.4.6 权限申请与审批：给审批人做出判断的依据

审批环节的真实状态是：**审批人普遍不理解他在批什么**。这不是态度问题，是信息问题。一个经理每周收到 20 个审批请求，每个请求只有申请人、权限代码和一句"工作需要"。他能做的只有批准。

要让审批产生价值，系统必须在请求里附上判断依据。四项信息，成本都不高：

1. **业务语言的权限说明**（来自 14.4.1 的业务权限层）与该权限的风险标签。
2. **同侪对比**：申请人所在岗位中，有多少比例的人拥有此权限。当答案是"该岗位 3% 的人拥有"时，审批人会认真看；当答案是"92% 的人拥有"时，说明它应该进出生权限而不是走审批。
3. **该申请会产生的 SoD 冲突**（来自 14.4.5 的前置检查），以及申请人现有的相关权限。
4. **建议期限**与到期后自动回收的说明——让审批人知道这不是永久决定，会显著提高拒绝意愿。

审批人的选择同样需要判断。三种模式各有失效场景：

| 审批人 | 优势 | 失效场景 |
|-------|------|---------|
| 直属经理 | 了解此人是否需要 | 不了解权限含义；与下属关系导致难以拒绝 |
| 应用负责人 | 了解权限含义 | 不了解申请人的业务背景；请求量大时橡皮图章 |
| 数据负责人 | 了解数据敏感性 | 通常不存在或不明确 |

推荐的组合是**双签但异步**：直属经理确认"这个人需要"，应用负责人确认"这个权限合适"，二者并行而非串行（串行会让时长翻倍，而时长直接导致绕过）。对低风险权限，应用负责人一侧可以配置为自动通过，把人的注意力留给高风险条目。

**自动审批的边界**：可以自动通过的是"该岗位 80% 以上的人已拥有、非特权、无 SoD 冲突、带默认期限"的申请。除此之外都应有人参与。把自动审批的范围写成规则并纳入定期复核，而不是靠工程师在代码里判断。

## 14.4.7 最小权限：从运动到工程

回到开头那条曲线。要让权限治理不半途而废，需要改变三个前提。

**第一，不做全量，做高危权限清单。** 全量清理的工作量与业务摩擦都是线性于权限总数的，而风险高度集中：能改生产、能动资金、能读客户数据、能授予权限的那几十项权限，承载了绝大部分实质风险。列出"高危权限 Top 50"，只治理它们，每季度复核一次——这是可以长期运行的节奏。

**第二，用消耗数据而不是猜测。** "未使用即回收"是唯一一条不需要业务判断就能执行的规则，因为它的依据是客观的。落地要点：观察期不少于 180 天（覆盖季度末与年度周期性任务）；对已知周期性任务显式豁免并登记；**回收后必须提供自助恢复**——这是降低阻力的关键设计，当用户知道"点一下就能拿回来"，反对声会显著下降，而实际恢复率通常很低（示例口径下不到 10%），这个数字本身就是最好的证据。

**第三，把回收做成自动的、无声的、默认的。** 权限带 TTL、到期自动失效、失效前 7 天通知、需要则续期。这样权限总量会自然收敛，不需要任何"专项运动"。运动式清理的本质，是在补偿平时缺少 TTL 机制所积累的债务。

一条容易被忽略的配套：**回收要与业务节奏错开**。不要在季度末、年末结账、大促期间执行批量回收。这不是技术要求，是政治要求——一次踩在关键业务窗口上的回收事故，足以让整个机制被叫停两年（14.2.4 给过一个类似的例子）。

## 14.4.8 失败叙事：一次"权限清零重授"

有一年我们决定用最彻底的方式解决权限累积：选定一个 800 人的事业部，在某个周末把所有非基础权限清零，然后按新定义的 24 个岗位角色重新授予，同时开通快速通道处理遗漏。

方案在纸面上无懈可击：一次性消除历史包袱，之后按角色维护即可。我们准备了回滚快照、加班值守、专线支持。

周一上午 9 点，快速通道收到 190 个请求；11 点，470 个；下午 2 点，超过 700 个——接近全员。事业部负责人在下午 3 点要求全量回滚，我们照做了，用时 40 分钟。

复盘发现三个错误，其中只有一个是技术性的。

**其一，我们把"岗位角色"建立在 HR 的岗位代码上，而 HR 岗位代码与实际工作内容的对应关系很弱。** 同一个岗位代码下的人，实际做的事差异极大——这个事业部有大量跨职能项目制工作，一个"业务分析师"可能在做数据、也可能在做流程。角色定义因此系统性地偏窄。

**其二，我们低估了长尾。** 24 个角色覆盖了大约 70% 的权限关系（与 14.4.2 说的挖掘覆盖率一致），剩下 30% 就是那 700 个请求。**70% 的覆盖率在报表上是不错的成绩，在切换当天是灾难**，因为剩下的 30% 会在同一时刻集中爆发。

**其三，我们没有做灰度。** 800 人一次切换，没有先做 30 人。而 30 人的试点会在半天内暴露出前两个问题，代价只有 1/25。

改造后的做法写在 14.4.7：不再追求"一次做对"，而是让权限自然收敛——高危权限重点治理，其余靠 TTL 与未使用回收慢慢消化。两年后回看，同一个事业部的人均权限数下降了约 35%（示例口径），过程中没有发生任何一起业务中断。**慢的方法之所以更快，是因为它不会被叫停。**

## 14.4.9 度量

| 指标 | 定义 | 参考目标（示例口径） |
|------|------|------------------|
| 高危权限持有人数 | Top 50 高危权限的持有人去重计数 | 每季度下降，且每人可解释 |
| 权限 TTL 覆盖率 | 带有效期的授权 ÷ 授权总数 | > 60%，特权类 100% |
| 未使用权限占比 | 180 天未使用的授权 ÷ 授权总数 | < 15% |
| SoD 规则命中率 | 过去 12 个月至少命中一次的规则占比 | > 70%（低于此说明矩阵未接通） |
| 一级冲突存量 | 未获例外的一级冲突数 | 0 |
| 例外过期未处理数 | 已过期但冲突仍存在的例外 | 0 |
| 申请到手时长 P50/P95 | 从提交到权限生效 | P50 < 4 小时，P95 < 2 天 |
| 审批拒绝率 | 被拒绝的申请 ÷ 总申请 | > 3%（长期为 0 说明审批无效） |

最后一条最容易被忽略：**审批拒绝率长期为 0，说明审批环节没有在做判断**。它不需要很高——拒绝率 3%～8% 通常意味着审批人确实在读内容。把这个指标放进管理报表，比任何培训都更能改变审批行为。

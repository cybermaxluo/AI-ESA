# 14.9　客户身份与访问管理（CIAM）

企业内部的身份系统，默认答案是"拒绝"——多一道验证、多一次审批、多一个策略，安全团队的直觉是收紧。面向客户的身份系统，默认答案是"别挡路"——注册流程每多一个字段，完成率就下降；登录每多一次验证，转化率就下降；密码策略每严格一档，找回请求就上升。

**这两套系统的目标函数方向相反。** 把企业 IAM 的思路直接搬到 CIAM 上，会做出一个安全但没人用的产品；把产品的思路直接搬到安全上，会做出一个好用但被凭据填充攻击洗一遍的系统。CIAM 的全部工程难度都来自这个张力。

因此本节的核心判断是：**CIAM 的安全投入应当按"欺诈损失 + 合规风险 + 信任成本"计价，而不是按控制项数量计价。** 一个能挡住 99% 攻击但让 3% 的真实用户流失的方案，在多数业务上是净亏损；而一个只挡住 80% 攻击、但对真实用户完全无感的方案可能是净收益。安全团队在 CIAM 场景中的价值，恰恰在于能把这笔账算清楚，而不是在于能列出更多控制。

---

## 14.9.1 与企业 IAM 的六个结构性差异

| 维度 | 企业 IAM | CIAM |
|------|---------|------|
| 规模 | 万级到十万级，增长可预测 | 百万到亿级，增长不可预测，峰值可达日常的数十倍 |
| 目标函数 | 控制优先，摩擦可接受 | 转化优先，摩擦即损失 |
| 身份来源 | HR 等权威源，身份真实性由入职流程保证 | 用户自称，真实性需要额外手段验证 |
| 账号恢复 | 有服务台、有经理、有线下核验 | 只有用户自己提供的联系方式，没有第二条可信通道 |
| 合规约束 | 劳动法、内控、审计 | 个人信息保护法规、同意管理、数据主体权利、未成年人保护 |
| 可用性要求 | 内部系统，故障影响办公 | 登录是全站入口，登录不可用等于业务全停 |

最后一条常被低估。企业 IdP 宕机 30 分钟是一次事故；电商登录服务宕机 30 分钟是一次财报事件。这意味着 CIAM 的架构决策（是否引入外部依赖、是否做同步的风险评估调用、限流阈值怎么定）必须以可用性为第一约束——**任何一个可能阻塞登录主链路的安全组件，都必须有降级路径**。

---

## 14.9.2 规模、成本与可用性

**计价模型影响架构。** 多数 CIAM 产品按月活跃用户计价，这带来一个反直觉的后果：**沉睡用户的清理会直接产生成本收益**。同时也带来一个风险——为了压低月活数而合并账号或延迟创建身份，可能损害安全边界。定价模型不应当反过来决定身份模型，但在实践中它经常会，这一点需要在选型时就识别出来。

**峰值容量按登录峰值而非注册峰值设计。** 大促、开学季、新品发布会带来数十倍的登录峰值，而登录链路上通常挂着风险评估、设备指纹、泄露口令比对等外部依赖。容量规划必须覆盖这些依赖，且每一个都要有超时与降级策略：**外部风险服务超时，应当放行并标记，而不是阻塞登录**（除非该服务本身就是主要的欺诈防线，那就要为它单独做容量保障）。

一份可执行的降级矩阵（阈值为示例口径，需按自身容量实测标定）：

| 组件 | 正常路径 | 降级触发 | 降级行为 | 事后动作 |
|------|---------|---------|---------|---------|
| 风险评分服务 | 同步调用，预算 150 ms | 超时或错误率 > 5% | 按中风险处理，记录降级标记 | 对降级期间的登录做事后批量复扫 |
| 泄露口令比对 | 注册/改密时同步调用 | 服务不可用 | 放行并标记（见 14.9.3 代码） | 后续在用户下次登录时补检 |
| 设备指纹 | 前端采集 | 采集失败 | 视为新设备，走中风险 | 无 |
| 短信通道 | 主通道 | 送达率骤降 | 自动切换备用通道，并优先引导邮箱或 Passkey | 复盘通道质量 |
| 身份数据库 | 主库读写 | 主库不可用 | 只读模式：允许已有会话继续，暂停注册与改密 | 按业务影响决定是否公告 |

这张矩阵的价值在于**它把"降级"从故障时的临场判断变成了预先的设计决策**。故障发生时没有时间讨论"要不要放行"，这个决定必须在设计评审时就做出并写下来。

**限流的误伤是真实成本。** 按 IP 限流会误伤共享出口的用户（企业网络、校园网、运营商 NAT），在移动网络环境下尤其严重。可行的做法是分层限流：按账号维度严格（保护单个账号不被爆破）、按 IP 维度宽松且带白名单、按设备指纹维度中等、并对触发限流的请求提供替代路径（人机验证）而不是直接拒绝。

## 14.9.3 账号接管：分层防护，而不是一道墙

针对 C 端的主要攻击是凭据填充（credential stuffing）与撞库：攻击者用其他网站泄露的账号密码组合批量尝试登录，单次成功率很低（公开估计约 0.1%，实测口径随撞库库源新鲜度与账密复用率大幅波动，见 [13.2.3](../../第04部分_安全运营与防御能力/第13章_业务风控与反欺诈/13.2_账号安全与反撞库.md)），但试的次数足够多就有收益，而且成本极低。

本小节给的是防护结构；这套结构在持续对抗下怎么运营——验证码与设备指纹的失效周期、检测与响应的时延约束、风控模型的线上衰减、人工审核环节的实际容量——见 [13.2 账号安全与反撞库](../../第04部分_安全运营与防御能力/第13章_业务风控与反欺诈/13.2_账号安全与反撞库.md)。

有效的防护是分层的，且每一层的设计原则都是"提高攻击者成本而不提高用户成本"：

| 层次 | 手段 | 对真实用户的影响 |
|------|------|---------------|
| 注册与改密时 | 比对已泄露口令库，拒绝已泄露口令 | 极小（只影响选了泄露口令的用户） |
| 登录前 | 按账号、IP、设备、指纹多维度限流 | 极小（正常用户不会触发） |
| 登录中 | 风险评分驱动的分层验证（step-up） | 仅高风险场景增加一步 |
| 登录后 | 异常行为监控（改绑手机、改密、批量下单） | 无感 |
| 全局 | 新设备登录通知、会话管理界面 | 无感，且提升信任感 |

**关于泄露口令比对**：直接把用户口令发给第三方服务是不可接受的。业界通行做法是 k-匿名（k-anonymity）查询——只发送口令哈希的前若干位，服务端返回该前缀下的全部哈希后缀，比对在本地完成，服务端无法得知具体查询的是哪一个口令。

```python
"""泄露口令检查（k-匿名模式）：只发送哈希前缀，本地完成比对。

安全性要点：
1. 明文口令与完整哈希都不离开本进程。
2. 前缀长度决定匿名集合大小，5 个十六进制字符对应约 10 万分之一的空间划分。
3. 服务不可用时必须 fail-open（放行）而不是 fail-close，
   否则一次第三方故障会让全站无法注册与改密。
"""
import hashlib
from typing import Optional

import requests

RANGE_API = "https://api.pwnedpasswords.com/range/{prefix}"
PREFIX_LEN = 5


def breach_count(password: str, timeout: float = 2.0) -> Optional[int]:
    """返回该口令在泄露库中出现的次数；服务不可用时返回 None。"""
    digest = hashlib.sha1(password.encode("utf-8")).hexdigest().upper()
    prefix, suffix = digest[:PREFIX_LEN], digest[PREFIX_LEN:]
    try:
        resp = requests.get(
            RANGE_API.format(prefix=prefix),
            timeout=timeout,
            headers={"Add-Padding": "true"},   # 响应填充，避免按长度侧信道推断
        )
        resp.raise_for_status()
    except requests.RequestException:
        return None                            # 调用方据此决定降级策略
    for line in resp.text.splitlines():
        found_suffix, _, count = line.partition(":")
        if found_suffix.strip() == suffix:
            return int(count)
    return 0


def evaluate_password(password: str, threshold: int = 1) -> dict:
    count = breach_count(password)
    if count is None:
        # 降级：不阻断用户，但记录并在后续风险评分中体现
        return {"decision": "allow", "degraded": True, "breach_count": None}
    if count >= threshold:
        return {
            "decision": "reject",
            "degraded": False,
            "breach_count": count,
            "message": "该密码已出现在公开泄露数据中，请更换",
        }
    return {"decision": "allow", "degraded": False, "breach_count": 0}
```

怎么读这段代码：`Add-Padding` 头要求服务端对响应做填充，防止观察者通过响应体长度推断被查询的前缀特征——这是一个容易被忽略但成本为零的细节。`breach_count` 返回 `None` 与返回 `0` 是两种不同的语义（服务不可用 vs 确认未泄露），把它们合并会导致故障期间所有口令都被判为"安全"，且没有任何记录。降级方向选择 `allow` 是刻意的：**在 CIAM 场景，一个安全增强组件的故障不应当导致主链路不可用**——这与企业内部系统的 fail-close 默认相反，是本节反复出现的取舍。

### 风险分层：把摩擦花在刀刃上

分层验证（step-up）的关键是**风险评分要用可靠且低成本的信号**。可用信号按性价比排序：设备是否见过（最强、最便宜）、IP 与常用地理位置的偏离、当前 IP 的历史恶意程度、登录速率与失败率、请求指纹的自动化特征、账号本身的价值（余额、等级、是否绑定支付方式）、以及本次操作的敏感度。

需要说清楚的是：**设备指纹不是身份，它是一个概率信号。** 它会因浏览器更新、隐私保护功能、清理数据而变化，因此"设备未见过"应当触发额外验证而不是拒绝；同时它也可以被伪造，所以不能用它来豁免验证——**指纹只应用于加严，不应用于放松**，这与 14.4.4 中 ABAC"只做减法"是同一条原则。

```json
{
  "policy_id": "ciam-risk-tiers-v3",
  "signals": {
    "known_device": {"weight": -30},
    "new_country": {"weight": 25},
    "impossible_travel": {"weight": 40},
    "ip_reputation_bad": {"weight": 35},
    "failed_attempts_last_hour_gt_5": {"weight": 20},
    "automation_fingerprint": {"weight": 30},
    "high_value_account": {"weight": 15},
    "sensitive_action": {"weight": 20}
  },
  "tiers": [
    {
      "name": "low",
      "max_score": 20,
      "action": "allow",
      "user_visible_friction": "none"
    },
    {
      "name": "medium",
      "max_score": 50,
      "action": "step_up",
      "allowed_methods": ["passkey", "push_with_number_matching", "otp_email"],
      "user_visible_friction": "one_extra_step"
    },
    {
      "name": "high",
      "max_score": 80,
      "action": "step_up_strict",
      "allowed_methods": ["passkey"],
      "notify_user": true,
      "user_visible_friction": "one_extra_step_plus_notification"
    },
    {
      "name": "critical",
      "max_score": 999,
      "action": "deny_and_review",
      "notify_user": true,
      "create_case": true
    }
  ],
  "degradation": {
    "on_scoring_service_unavailable": "treat_as_medium",
    "on_device_service_unavailable": "ignore_device_signals",
    "max_added_latency_ms": 250
  }
}
```

怎么读这段策略：`known_device` 的权重是负数，这是分层验证的核心机制——**用正向信号抵消风险，让绝大多数正常登录落进 `low` 档而完全无感**。`degradation` 段是 CIAM 特有的必需品：评分服务不可用时降级为 `medium`（要求一次额外验证）而不是 `deny`，也不是 `allow`；`max_added_latency_ms` 给整条风险评估链路设了预算，超时即按降级规则处理，防止安全组件把登录时延拖垮。`deny_and_review` 档配 `create_case`，意味着最高风险的拒绝必须有人复核——**没有复核出口的自动拒绝，会把真实用户永久挡在门外，而他们中的一部分会直接流失**。

**判断：不要用"锁定账号"作为主要防御手段。** 账号锁定会被攻击者用来对特定用户发起拒绝服务（故意输错密码把目标账号锁死），在 C 端场景这是真实发生的骚扰手法。更合适的做法是对来源限流、对高风险登录要求额外验证，把账号本身保持可用。

**生产坑：防护规则把攻击者训练得更聪明。** 上线新的风控规则后，拦截率通常会先升后降——攻击者会在几天内调整（换 IP 池、放慢速率、模拟真实浏览器、绕开被拦截的特征）。如果只看"拦截量"这一个指标，会误以为攻击减少了，实际上是攻击变得不可见了。有效的做法是同时跟踪三条曲线：拦截量、登录成功率的异常波动、以及确认的账号接管事件数。**当拦截量下降而接管事件数不变时，说明规则已经被绕过，而不是攻击停止了。**

**生产坑：验证码的成本被严重低估。** 人机验证会让相当比例的真实用户在完成前放弃（不同实现与人群差异极大），而自动化求解服务的成本对攻击者而言很低。把验证码作为默认的第一道防线，通常是在用较高的真实用户损失换取较低的攻击者成本增加。更合理的定位是把它放在风险分层的中高档，只对可疑流量出示。

## 14.9.4 认证方式：C 端的现实

**Passkey 在 C 端的价值高于企业端**：它同时提升安全性与体验（无需记密码、无需等验证码），这在 C 端是罕见的"双赢"。落地要点是渐进式引导——在用户成功登录后提示"下次可以用指纹直接登录"，而不是在注册流程中强制；同时必须保留至少一条备用路径，因为设备丢失、换机、跨平台的场景在 C 端远比企业端复杂。14.3.3 关于可同步凭据的治理顾虑在 C 端基本不适用：用户的凭据本来就由用户自己保管，同步反而降低了丢失风险。

**短信验证码需要重新评估。** 它的问题不只是安全性（SIM 卡劫持、中间人转发），还有成本与滥用：攻击者可以利用发送接口制造大量国际短信以套取分成（俗称短信泵送欺诈），单次攻击就可能产生可观的账单。控制手段包括按号码与 IP 限流、可疑目的地限制、异常增长告警，以及**尽快把主认证迁移到 Passkey，把短信降级为备用**。

**社交登录的两个坑**必须提前处理：

其一，**第三方返回的邮箱声明不一定经过验证**。如果系统按邮箱自动关联到已有账号，攻击者可以在一个允许自填邮箱的第三方平台上注册一个使用受害者邮箱的账号，然后用它登录并接管受害者账号。正确做法是：只信任明确标记为已验证的邮箱声明；不确定时走显式的账号关联流程（要求用户先用原方式登录再绑定）。

其二，**第三方 IdP 的可用性与政策不受你控制**。它可能变更接口、调整数据返回策略、区域性不可用，甚至关停。因此不应把社交身份作为唯一的身份锚点，注册时应引导用户补充一个自有的可验证联系方式。

## 14.9.5 注册、身份验证与最小化

注册流程的设计原则是**渐进式画像**：首次只要最少信息（一个可验证的联系方式 + 一种认证方式），其余信息在业务需要时再收集。这既提升转化，也天然符合数据最小化要求。

需要做实名或资质核验（KYC）的业务，要把握两条边界：

**收集的边界**：只收集当前业务环节法定必需的信息。一个常见错误是"先都收着，将来可能用得上"——收集了证件影像就必须为它建立与之匹配的存储、加密、访问控制与留存策略，这些成本往往超过它带来的收益。相关的数据保护要求见 [8.5 数据访问控制](../../第03部分_数据安全与隐私/第08章_数据安全/8.5_数据访问控制.md) 与 [8.7 数据安全监控与审计](../../第03部分_数据安全与隐私/第08章_数据安全/8.7_数据安全监控与审计.md)。

**留存的边界**：核验完成后，原始材料是否还需要保留？多数场景下保留"核验结果 + 核验时间 + 核验方式"即可，原始影像可以在核验完成后按策略删除。**每一份多留的证件影像，都是未来某次泄露事件的赔付基数。**

未成年人保护是一个独立的合规面：多数法域对儿童个人信息的处理有更严格要求（监护人同意、更小的收集范围、更强的默认隐私设置）。身份系统需要在数据模型上支持年龄标记与差异化策略，而不是在业务层临时判断。

## 14.9.6 同意与偏好：身份系统的合规接口

同意（consent）管理经常被当作一个前端弹窗问题，实际上它对身份系统有三项硬性要求：

1. **可举证**：每一次同意必须记录"谁、何时、通过什么界面、同意了哪个版本的条款、以什么方式表达"。条款更新后，旧同意是否仍然有效需要有明确规则。
2. **可撤回，且撤回要生效**：撤回同意后，依赖该同意的数据处理必须实际停止。这需要身份系统能把同意状态下发给下游消费方——**只在身份系统里改一个标志位，而下游数据管道照常运行，是最常见的合规缺口**。
3. **可响应数据主体请求**：访问、更正、删除、可携带四类请求都需要以身份为索引把数据聚合起来。这要求身份系统持有一份"该用户的数据分布在哪些系统"的映射。

一条同意记录的最小结构如下，它的每个字段都对应一个可能被监管问到的问题：

```json
{
  "consent_id": "cns-2026-07-31-9f3c21ab",
  "person_id": "C-77219ab4-0c31-4e29-9d55-3a1b6f2e8c40",
```

删除请求会与业务留存要求冲突：交易记录、发票、风控黑名单通常有法定保留期。可行的做法是**区分"身份删除"与"记录留存"**——删除可识别到自然人的标识与联系方式，保留脱敏后的交易记录，并在身份侧留下一条不可逆的删除标记（用于防止同一人重新注册后被误关联到旧数据）。这个方案需要法务确认，并且要在删除流程中留下可审计的证据。

## 14.9.7 B2B2C：当客户是一个组织

大量业务的真实结构不是"平台对个人"，而是"平台对企业，企业对个人"——经销商、代理商、企业采购方、机构客户。这时 CIAM 需要支持组织维度：

- **组织实体与成员关系**：用户属于哪个组织，一个用户可能属于多个组织并具有不同角色。
- **委托管理（delegated administration）**：组织的管理员可以自行邀请、移除成员并分配组织内角色，平台方不介入。这是规模化的关键——否则每一次成员变动都变成平台的工单。
- **权限边界**：组织管理员的权限上界必须由平台定义且不可突破，尤其要防止跨组织的数据可见性（一个多租户越权在 B2B 场景中的后果是客户之间的数据泄露）。
- **组织生命周期**：合同到期、组织注销时，成员访问如何处理——这是 14.2 的 JML 在客户侧的镜像，且同样容易被忽略。

还有一个容易被漏掉的场景：**同一个自然人同时是 C 端个人用户和某组织的成员**。此时"他是谁"有两个答案，而权限、数据可见性、合规义务都不同。身份模型必须支持"一个身份、多个上下文"，并在登录后让用户显式选择或按访问入口自动判定上下文——把两个上下文的权限合并成一个会话，是多租户越权的常见来源。

**判断：委托管理的默认权限要保守。** 组织管理员通常不是安全专业人员，给他们的默认能力应当只覆盖成员管理，涉及数据导出、接口凭据、审计日志访问的能力应当作为可选项由平台侧显式开通。

## 14.9.8 迁移：把老系统的用户接过来

CIAM 项目的多数工期花在迁移上。三种方案：

**方案一：批量迁移密码哈希。** 若旧系统的哈希算法与新系统兼容（或新系统支持多算法验证），可以直接导入哈希，用户无感。这是最理想的路径。

**方案二：延迟迁移（lazy migration）。** 导入哈希无法兼容时，新系统保留旧哈希并在用户首次登录时用旧算法验证，验证通过后立即用新算法重新计算并存储，同时废弃旧哈希。用户同样无感。需要设定一个截止日期，之后未登录的用户走密码重置。

**方案三：强制重置。** 所有用户必须重新设置密码。**这是最后手段**，见下一节。

延迟迁移的三个坑：旧哈希在迁移期内仍然存在，其保护等级必须与新系统一致（不能因为"临时的"就放松）；截止日的选择要覆盖低频用户（年度使用一次的用户很常见）；以及必须处理"旧系统在迁移期内仍在写入"的双写问题，否则会出现用户在旧系统改了密码、新系统仍用旧哈希的情况。

## 14.9.9 失败叙事：我们强制全员改密

一次安全事件后（并非本平台泄露，而是行业内另一家的泄露被证实与本平台存在大量重合用户），我们决定对全体用户强制密码重置。逻辑很清楚：这些用户很可能在两边用了同一个密码，不重置就等着被撞库。

执行方式是：下次登录时强制跳转到重置流程，必须完成才能继续。

结果分三部分。第一，重置完成率在两周内只有 34%——大量用户在跳转页面直接离开。第二，客服工单量增长了近四倍，主要是"收不到验证短信""邮箱是旧的登不上"这类问题，而这些用户中有相当比例最终没有回来。第三，也是最讽刺的：完成重置的用户里，有可观比例设置了与原密码高度相似的新密码（在允许的范围内做最小改动），撞库风险并未真正解除（以上均为示例口径）。

复盘的结论是：**我们把一个风险分层问题当成了全量问题处理。**

改造后的做法：

1. **只针对真正高风险的用户强制**——用 14.9.3 的泄露口令比对，找出当前口令确实出现在泄露库中的账号（这部分通常只占全部用户的很小比例），对他们强制重置；其余用户在下次登录时提示但不阻断。
2. **提供比"重置密码"更好的出口**——引导注册 Passkey，一步到位解决问题，且体验更好。愿意走这条路的用户比例远高于预期。
3. **把强制点放在风险时刻而非登录时刻**——在用户尝试进行敏感操作（改绑手机、提现、修改地址）时才要求提升认证，而不是在每次登录时设卡。

改造后的数据：受影响用户从全量降到不足 5%，高风险账号的处置完成率超过 80%，客服工单几乎没有增长（示例口径）。

留下的判断是：**在 C 端，任何面向全量用户的强制动作，都要先算清楚"这些人里有多少真的有风险"**。全量强制的成本是线性于用户数的，而收益只线性于高风险用户数——当高风险比例只有百分之几时，这笔账几乎不可能划算。这与企业内部形成鲜明对照：在企业内，全员强制的成本可以由行政力量吸收，而在 C 端，成本直接表现为流失。

## 14.9.10 度量

| 指标 | 定义 | 说明 |
|------|------|------|
| 注册转化率 | 完成注册 ÷ 开始注册 | 每次安全变更前后必须对比 |
| 登录成功率 | 成功登录 ÷ 登录尝试（剔除已识别的攻击流量） | 下降是最灵敏的误伤信号 |
| 凭据填充拦截率与误伤率 | 拦截的恶意尝试、被误拦的真实用户 | 两者必须同时汇报 |
| 账号接管事件数与损失 | 确认的 ATO 案例与直接损失金额 | 这是 CIAM 安全投入的主要计价依据 |
| 抗钓鱼认证器采用率 | 注册了 Passkey 的活跃用户占比 | C 端的核心演进指标 |
| 找回流程完成率 | 完成账号找回 ÷ 发起找回 | 过低说明恢复路径设计有问题 |
| 数据主体请求响应时长 | 从请求到完成 | 合规硬指标，通常有法定时限 |
| 登录链路可用性 | 登录服务的可用性与 P99 时延 | 与业务可用性同级 |

# 15.3　边界与流量防护

一次外部渗透测试的报告里有这样一句话：目标企业边界防火墙共 11,847 条策略，其中源或目的为 `any` 的 1,932 条，服务为 `any` 的 864 条，同时满足两者的 217 条。测试团队从互联网侧利用其中一条通往测试环境的规则进入，再沿着另一条为"数据迁移"开通的、三年前应当失效的规则到达生产数据库网段。

安全负责人的反应不是惊讶，而是无力：这些规则他们知道，也曾经想清理。上一次尝试是两年前，清理了 300 条之后，一条被删的规则导致某个季度结算作业失败，事故定级 P2，此后再无人敢碰规则库。

这是边界防护的真实困境。它不是"要不要买 NGFW"的问题——设备早就买了，能力早就有了；问题是**这套设备承载的策略集在持续腐化，而腐化的速度快于治理的速度**。本节讲的就是如何让治理速度追上腐化速度，以及边界上其余几类能力（IPS、抗 DDoS、反向代理与 WAF）各自的真实边界在哪里。

> 导读：15.3.1 界定 NGFW 的能力边界与部署位置，说明哪些事它做不了；15.3.2 剖析规则腐化的机理并给出可度量的腐化指标；15.3.3 是本节最实用的部分——规则治理工程的完整方法，包括不引发事故的清理流程；15.3.4 讲出向策略——边界上投入产出比最高却最少被做的控制；15.3.5 讲 IPS 调优，重点是"为什么全企业的 IPS 都开在检测模式"；15.3.6 讲 DDoS 分层防护与引流决策；15.3.7 划清反向代理、WAF、CDN、API 网关四者的职责边界；15.3.8 处理 TLS 解密这个绕不开的取舍。云上的 WAF 规则调优与云原生 DDoS 服务见 5.3.3 与 5.3.4，本节承担本地与混合边界。

## 15.3.1 NGFW 的能力边界与部署位置

### NGFW 到底比状态防火墙多了什么

下一代防火墙（Next-Generation Firewall, NGFW）相对传统状态检测防火墙，多出的核心能力是**应用识别**与**身份关联**：策略不再只写"允许 TCP/443 到某网段"，而可以写"允许财务组用户访问某几个 SaaS 应用"。附带的还有集成 IPS、URL 过滤、恶意文件检测、TLS 解密等模块。

防火墙规则集的设计、审阅与生命周期管理有成体系的公开指南可循[1]，但在实际企业里，绝大多数 NGFW 被当作贵一点的状态防火墙在用——买了应用识别，策略里全是端口；买了用户识别，从没接过身份源；买了 IPS 模块，开在检测模式从不阻断。这不完全是使用者的问题，每一项都有真实的落地阻力：

| 能力 | 落地阻力 | 现实处理 |
|------|---------|---------|
| 应用识别 | 应用签名对自研应用与私有协议无效；识别需要看到足够多的报文，前几个包可能已经放行 | 对外发布与出网方向用应用策略，内部东西向用端口策略 |
| 用户识别 | 需接入身份源并维护 IP 与用户的映射，NAT、共享终端、服务账号场景下映射失效 | 优先用于出网与远程接入方向，服务器区不依赖 |
| 集成 IPS | 误报影响业务，无人有把握开阻断 | 见 15.3.5 的分层调优方法 |
| TLS 解密 | 性能开销、证书信任链、隐私合规、应用兼容 | 见 15.3.8 的分级策略 |
| 恶意文件检测 | 加密流量下形同虚设；与终端侧能力重复 | 定位为纵深冗余而非主防线 |

一条务实的判断：**NGFW 的应用识别价值主要在出网方向**。出网方向的流量目标是互联网上的公共服务，签名库对它们的识别准确率高；而内部东西向流量大量是自研应用与私有协议，识别价值低、维护成本高。把有限的策略精力放在出网收敛上，回报显著高于试图对东西向做应用级策略（东西向应交给 15.2 的微隔离）。

### 部署位置决定了它能看见什么

同一台设备放在不同位置，作用完全不同：

```
部署位置                     看得见的流量              典型职责
─────────────────────────────────────────────────────────────────
互联网边界（南北向）          进出企业的全部流量        入向暴露控制、出向收敛
                                                      地理与信誉策略、IPS
DMZ 与内网之间               对外服务回连内部的流量     限制被攻陷的对外服务
                                                      横向进入内网（关键位置）
信任域之间（东西向）          跨域流量                  执行 15.1.3 的策略矩阵
数据中心互联                 机房之间                  防止一个机房沦陷波及另一个
分支到总部                   隧道内流量                分支侧策略一致性（见 15.1.6）
云与本地互联                 混合流量                  隧道两端策略对称性
```

其中**DMZ 与内网之间的那一道最容易被省略**。很多企业的架构是"互联网 → 防火墙 → DMZ → 内网"，但 DMZ 到内网这一跳要么没有独立策略，要么策略非常宽松（因为对外服务确实需要访问内部数据库、认证服务、消息队列）。攻击者攻陷一台对外 Web 服务器后，正是沿着这些宽松规则进入内网。这一道的策略应当是全网最严格的——精确到"哪台 DMZ 主机、用哪个进程、访问内网哪个 IP 的哪个端口"，且必须全量记录会话。

### 可用性约束反过来塑造安全策略

边界防火墙是全企业流量的必经之路，它的可用性等级与核心业务相同。这个事实对安全策略有两个不太被讨论的影响：

**影响一：所有会增加处理开销的功能都要做容量论证。** 开启 TLS 解密通常会让设备吞吐显著下降（下降幅度因型号与流量构成而异，厂商标称值往往基于理想流量模型，必须以本环境实测为准）；开启全量会话日志会增加日志系统压力；开启应用识别会增加单会话的处理延迟。这些功能一旦在容量不足时开启，表现出的不是"变慢"而是"随机丢包与会话中断"，排障极其困难，最终往往以关闭安全功能收场。**先扩容再开功能**，而不是开了功能等出问题再扩容。

**影响二：会话表与并发连接数是隐性瓶颈。** 防火墙的规格书上，吞吐量是最显眼的数字，但真实的瓶颈常常是并发会话数与新建会话速率。扫描行为、大量短连接的微服务架构、NAT 后的大量终端都会快速消耗会话表。会话表打满时，新连接直接失败，现象与"网络故障"完全一致。这项指标应当纳入日常监控并设置告警阈值（例如达到规格的 70%），而不是等到打满才发现。

**影响三：双机切换会话不同步。** 主备切换时若会话表未同步，所有长连接会中断。这对数据库连接池、文件传输、视频会议影响明显。选型与配置时需确认会话同步机制，并在维护窗口实际演练一次切换——很多企业的双机架构从部署之日起就没有真正切换过，直到某次硬件故障时才发现备机配置早已不同步。

## 15.3.2 规则腐化：机理与度量

### 腐化不是疏忽，是结构性必然

防火墙规则库的熵增有明确的机理，理解机理才知道该在哪里干预：

**机理一：新增有流程，删除没有流程。** 开通访问有申请单、有审批、有实施；关闭访问没有触发点——业务下线了不会有人通知网络团队去删规则，项目结束了不会有人回头收口。新增与删除的流程强度不对称，规则数量只能单调上升。

**机理二：规则的知识随人流失。** 规则的真实用途存在于实施者与申请者的记忆里，注释字段里通常只有一个工单号或一句"业务需求"。三年后两人都已换岗，这条规则就变成了一个不可解释的对象，而不可解释的对象没有人敢删。

**机理三：故障处置制造宽规则。** 深夜排障时，"先把这条改成 any 看看是不是防火墙的问题"是标准动作。问题解决后改回去这一步经常被遗忘，因为此时人已疲惫、故障已闭环、没有任何机制提醒。这类规则通常最宽、最危险，且最难被发现——因为它看起来和正常规则没有区别。

**机理四：合并与迁移带来批量污染。** 设备更换、厂商切换、数据中心迁移时，规则通常被整体导出导入。为了保证"迁移后业务不中断"，实施方会倾向于原样保留甚至适当放宽，于是上一代的所有历史债务被完整继承到新设备上，并获得了"这是新设备上的规则"这一层新鲜的伪装。

### 五种腐化形态与识别方法

| 形态 | 定义 | 识别方法 | 风险 |
|------|------|---------|------|
| 影子规则 | 被上方规则完全覆盖，永远不会命中 | 策略分析工具做包含关系计算 | 无直接风险，但掩盖真实策略、误导审计 |
| 冗余规则 | 与其他规则重复 | 同上 | 增加维护成本与出错概率 |
| 过宽规则 | 源、目的或服务为 any 或大网段 | 字段扫描 + 命中流量收敛分析 | **高**，是实际暴露面 |
| 僵死规则 | 长期零命中 | 命中计数 + 长周期观察 | 中，多为已下线业务的残留 |
| 到期规则 | 超过约定有效期 | 与工单系统对账 | 中至高，取决于当初为何开通 |

其中**过宽规则的识别不能只看字段**。一条"允许 10.0.0.0/8 访问某服务器 443 端口"的规则，看字段是过宽的，但如果实际命中流量只来自三个 /24 网段，它的收敛建议就非常明确。反之，一条看起来很精确的规则，如果目的是一个包含 200 台主机的对象组，它的实际暴露面可能比前者更大。**收敛分析必须结合命中流量做，纯静态分析只能产出一份没人会执行的清单**。

### 可度量的腐化指标

| 指标 | 计算方式 | 参考目标 | 说明 |
|------|---------|---------|------|
| 规则总数增长率 | 本季新增 - 本季删除 | 接近 0 | 净增长为正说明治理未追上腐化 |
| 过宽规则占比 | 含 any 或 /16 以上网段的规则 / 总数 | < 5% | 分入向与出向分别统计 |
| 无主规则占比 | 缺申请人/用途/有效期 | < 10% 且持续下降 | 治理成熟度的核心指标 |
| 90 天零命中占比 | 零命中规则 / 总数 | < 15% | 需排除已知周期性规则 |
| 影子规则数 | 策略分析工具输出 | 趋近 0 | 清理零风险，应优先做 |
| 平均规则年龄 | 所有规则创建至今天数的中位数 | 关注趋势 | 中位数持续上升说明只增不减 |

第一个指标是最有说服力的管理层汇报口径。**"我们本季度净删除了 400 条规则"比"我们新增了 3 条安全策略"更能说明治理在起作用**，而且它是一个不需要解释技术细节就能理解的数字。

## 15.3.3 规则治理工程：不引发事故的清理方法

### 清理项目的正确顺序

前述企业清理失败的根本原因是顺序错了——他们从"看起来最没用的规则"开始删，而这类规则反而最难判断。正确的顺序是按**风险从低到高**推进：

**第一批：影子规则与完全冗余规则（零风险）。** 这些规则永远不会命中，删除它们对流量没有任何影响。用策略分析工具（多数 NGFW 厂商自带，也有第三方策略管理平台）计算即可。这一批通常能删掉 10% 至 20% 的规则，且完全不需要业务确认——这是清理项目最好的开场，能立刻产出可见成果。

**第二批：明确到期与明确下线的规则。** 与工单系统、CMDB、资产系统对账：规则关联的目标主机已下线、关联的项目已关闭、规则标注的有效期已过。这一批需要核对但不需要业务判断。

**第三批：过宽规则的收敛（不删除，只收窄）。** 基于命中流量把 any 收敛到实际使用的范围。注意这一步是**收窄而非删除**，风险显著低于删除，且直接降低暴露面。收窄时应留出余量（例如实际来源是三个 /24，就写这三个 /24 而不是精确到 IP），避免因为轻微变化就报障。

**第四批：疑似僵死规则（需要业务确认与观察期）。** 这一批风险最高，必须走三步流程：切换为"允许但告警"→ 观察一个完整业务周期（建议 100 天以上，覆盖季度末）→ 零命中后删除。这与 15.2.6 的策略清理逻辑一致。

**永远不要在同一个变更窗口里删除超过一定数量的规则。** 一次删 300 条，出问题时无法快速定位是哪条。分批、每批带标记、可整批回滚，是这类项目的基本纪律。

### 命中数据的正确使用

下面这段代码演示如何把命中计数与业务周期结合，产出可执行的清理建议——而不是一份"90 天零命中"的裸清单。

```python
"""防火墙规则清理建议生成。

rules: 每条为 dict，字段
  rule_id, src, dst, svc, created_at(date), last_hit(date or None),
  hit_count_90d(int), owner(str or None), expires(date or None),
  tags(list[str])  # 例如 ['monthly-close', 'dr-drill']
today: date
"""
from datetime import date, timedelta

# 周期性标记：带这些标记的规则不能按"近 90 天零命中"判定为僵死
PERIODIC_TAGS = {"monthly-close", "quarter-end", "dr-drill", "annual-audit"}

OBSERVE_DAYS = 100          # 观察期需覆盖一个完整季度
NEW_RULE_GRACE_DAYS = 60    # 新规则尚未进入稳定期，暂不评估


def classify(rule, today):
    """返回 (处置动作, 优先级, 理由)。优先级 1 最高。"""
    age = (today - rule["created_at"]).days
    if age < NEW_RULE_GRACE_DAYS:
        return ("keep", 5, "新建规则，未到评估期")

    if rule.get("expires") and rule["expires"] < today:
        return ("remove_after_confirm", 1, "已过约定有效期")

    if rule["src"] == "any" and rule["svc"] == "any":
        return ("narrow_urgent", 1, "源与服务均为 any，暴露面最大")

    if rule["src"] == "any" or rule["dst"] == "any":
        return ("narrow", 2, "存在 any 字段，需按命中流量收敛")

    if set(rule.get("tags", [])) & PERIODIC_TAGS:
        # 周期性规则：只有跨越了完整周期仍零命中才可疑
        if rule["last_hit"] is None and age > 400:
            return ("observe", 3, "标记为周期性但一年以上无命中")
        return ("keep", 5, "周期性规则，短期零命中属正常")

    if rule["hit_count_90d"] == 0:
        if rule.get("owner"):
            return ("observe", 3, "90 天零命中，转告警模式观察")
        return ("observe", 2, "90 天零命中且无责任人")

    if not rule.get("owner"):
        return ("assign_owner", 4, "有流量但无责任人，需补登记")

    return ("keep", 5, "正常使用中")


def build_worklist(rules, today):
    buckets = {}
    for r in rules:
        action, prio, reason = classify(r, today)
        item = dict(r)
        item.update({"action": action, "priority": prio, "reason": reason})
        buckets.setdefault(action, []).append(item)
    for k in buckets:
        buckets[k].sort(key=lambda x: (x["priority"], x["rule_id"]))
    return buckets


def observation_end_date(start):
    """转入告警模式后，可执行删除的最早日期。"""
    return start + timedelta(days=OBSERVE_DAYS)
```

怎么读这段代码。三个判断值得强调：

第一，`PERIODIC_TAGS` 的存在把"零命中"从一个自动判决降级为一个需要上下文的信号。没有这层保护，季度末对账、灾备演练相关的规则会在每一轮清理中被反复误删——而这类规则的误删后果往往在数月后才暴露，且很难追溯到清理动作。**给规则打周期性标签这件事必须在清理项目启动前完成**，而不是在误删之后补。

第二，`NEW_RULE_GRACE_DAYS` 避免了对新规则的误判。刚开通的规则可能还没投入使用（业务尚未上线），此时的零命中不说明任何问题。

第三，无责任人的零命中规则优先级（2）高于有责任人的（3）。这是刻意的：有责任人意味着出问题时能快速找到人确认，风险可控；无责任人的规则一旦删错，恢复过程会非常痛苦。因此应当**优先处理无主规则，趁着还能追溯的时候把它们清掉或认领掉**。

### 让治理可持续的三个机制

清理是一次性项目，治理是持续机制。清理项目结束后如果没有以下三个机制，规则库会在 18 至 24 个月内回到原状：

1. **申请时必填四元组**：申请人、用途一句话、有效期（有硬上限）、关联工单。表单层面强制，不允许留空或填"长期"。
2. **规则退休与业务下线联动**：应用下线流程中增加"关联网络策略清理"检查项，由应用负责人确认。这是唯一能在源头阻断腐化的机制。
3. **季度自动对账**：规则库与工单系统、资产系统自动对账，输出异常清单并指派。自动化是关键——依赖人工发起的季度评审会在第三个季度失效。

### 策略即代码：把治理从人力密集变成流程内建

上述三个机制若靠人工执行，会在人员变动后失效。可持续的形态是把防火墙策略纳入版本控制与流水线，让治理规则变成提交时的自动检查：

```yaml
firewall_policy_lint:
  version: 3
  applies_to:
    - perimeter-cluster
    - dmz-internal
  hard_fail:
    - id: no-any-any
      description: 源与服务同时为 any 一律拒绝合入
      condition: src == "any" and service == "any"
    - id: metadata-required
      description: 必须填写申请人 用途 有效期 工单号
      required_fields: [requester, purpose, expires, ticket]
    - id: max-lifetime
      description: 有效期不得超过 365 天
      max_days: 365
    - id: no-inbound-to-critical-zone
      description: 禁止从互联网直接入向到关键控制域
      condition: src_zone == "internet" and dst_zone == "critical-control"
  warn_only:
    - id: broad-source
      description: 源网段大于 /16 需在评审中说明
      condition: src_prefix_len < 16
    - id: legacy-protocol
      description: 明文管理协议应改用加密替代
      protocols: [telnet, ftp, http-mgmt, snmpv1, snmpv2c]
  review_required:
    - id: cross-zone-new
      description: 新增跨信任域访问需安全会签
      condition: src_zone != dst_zone
      approvers: [infra-security]
```

这套检查的核心设计是把规则分成三档：`hard_fail` 直接拒绝合入（不给人工商量的余地），`warn_only` 提示但放行（避免过度阻碍），`review_required` 触发人工会签（对应 15.1.8 的高风险变更会签范围）。三档的比例决定了这套机制能否活下来——`hard_fail` 定得太宽，业务会绕过流水线直接上设备改配置；定得太窄，机制形同虚设。经验上 `hard_fail` 应当只包含那些"任何理由都不该例外"的项，其余一律走会签。

配套还需要一条纪律：**设备上的手工变更必须被检测出来**。策略即代码只约束流水线路径，绕过流水线直接在设备上改是常见做法（尤其在故障处置时）。检测手段是定期把设备实际配置拉回来与仓库比对，差异即告警（配置漂移检测见 15.10.4）。允许紧急手工变更，但要求 24 小时内补提交回仓库，超时告警升级。

## 15.3.4 出网策略：最被低估的边界控制

### 入向人人都做，出向几乎没人做

抽查任何一家企业的边界防火墙，入向策略通常写得很细（每个对外服务、每个端口、每个来源），出向策略往往只有一条：内网到 any，允许。这个不对称有一个朴素的理由——入向不放开业务就不通，出向不放开也不通，但放开出向没有人会抱怨，于是它一次性放到最宽就再也没动过。

而攻击链上有三个环节完全依赖出向：**载荷下载**（初始立足点拉取第二阶段工具）、**C2 回连**（受控主机与攻击者保持通信）、**数据外传**（把窃取的数据发出去）。出向策略是这三个环节共同的必经之路，也是投入产出比最高的单点控制。

### 分层收敛：从最容易的开始

出向收敛之所以推不动，通常是因为一开始就想做"全员按应用白名单"，这在办公终端上确实很难。分层做则容易得多：

| 对象 | 收敛难度 | 建议目标 | 说明 |
|------|---------|---------|------|
| 服务器（数据中心） | **低** | 默认拒绝，白名单放通 | 服务器的出网需求是有限且可枚举的：补丁源、时间源、厂商 API、日志上报 |
| 数据库、备份、管理系统 | **最低** | 完全禁止直接出网 | 这类系统没有任何直连互联网的合理需求 |
| 网络与安全设备管理面 | 最低 | 完全禁止 | 更新走内部镜像源 |
| 打印机、摄像头、楼宇设备 | 低 | 仅允许到厂商指定地址 | 这类设备被用作跳板与 DDoS 反射源的案例很多 |
| 办公终端 | **高** | 强制经代理，代理侧做分类过滤 | 直接在防火墙上做白名单不现实，见 15.7 |
| 开发与测试环境 | 中 | 允许到包管理源与代码托管，其余拒绝 | 开发方阻力大，但收益明确 |

**从服务器出网开始，是这项工作最正确的切入点。** 一台生产应用服务器需要连到互联网的目标通常不超过十几个，而它一旦被攻陷，就是数据外传的最短路径。相比办公终端，服务器出网收敛的业务阻力小一个数量级，安全收益却更高。

### 三个绕不开的工程细节

**细节一：白名单要用域名而不是 IP。** 补丁源、云服务 API、厂商更新通道的 IP 会持续变化，用 IP 写白名单意味着每隔几周就有业务报障。需要防火墙支持基于 FQDN 的策略，或者把这类流量统一引到代理上做域名级控制（见 15.7.4）。

**细节二：DNS 必须一并收敛。** 如果服务器可以直连任意 DNS 服务器，那么攻击者可以用 DNS 隧道绕过所有出向策略。出向收敛必须同时把 DNS 出向限制到企业解析器（DNS 隧道检测见 15.7.6）。

**细节三：例外必须走同一套治理。** 出向白名单会持续新增，若没有有效期与责任人，它会在两年内退化成另一个 any。用 15.3.3 的同一套四元组要求管理。

### 一个失败驱动的观察

一家企业在勒索软件事件后复盘，发现攻击者在加密数据之前的 11 天里，从一台被攻陷的文件服务器持续向外传输了大量数据。防火墙有完整的会话日志，日志里能清楚看到这台服务器与一个境外 IP 的长时间大流量连接——但没有任何策略阻止它，也没有任何告警规则关注"服务器主动向境外发起大流量出向连接"这件事。

这个案例的教训有两层：第一层是出向策略的缺失让数据外传畅通无阻；第二层更值得注意——**即使不阻断，仅仅对"服务器区的异常出向"建立一条告警规则，也能把发现时间从 11 天压缩到几小时**。出向策略的收益不只在阻断，还在于它把"什么是正常出向"定义了出来，从而让异常变得可检测（检测规则设计见 11.3）。

## 15.3.5 IPS 调优：从"全开检测"到"精准阻断"

### 为什么几乎所有企业的 IPS 都不阻断

入侵防御系统的默认状态是一个行业性尴尬：设备买了、签名更新了、日志有了，但策略是"检测不阻断"。原因很实在——一次误阻断造成的业务影响是立刻可见、可追责的，而一次漏拦造成的损失是延迟的、可归因于其他环节的。在这种收益结构下，没有人有动机去开阻断。

打破这个僵局的办法不是"全部开启阻断"，而是**按签名分层，让阻断决策在不同层上有不同的证据门槛**。四个档位直接以置信度含义命名——高置信档、上下文档、弱信号档、信息档——衡量的是"这条签名报出来时有多可信"，用中文而非 L1–L4 是为了不与 17.1.2 的 AI 自主等级 L0–L5 撞记号，两者之间也不存在任何对应：

| 层级 | 签名特征 | 处置 | 判据 |
|------|---------|------|------|
| 高置信档 | 特定 CVE 的确定性利用特征、已知恶意载荷、协议违规 | **直接阻断** | 误报率极低，且合法业务不会产生此类流量 |
| 上下文档 | 扫描、暴力破解、异常协议行为 | 阈值触发后阻断源 | 需要设置合理阈值与白名单 |
| 弱信号档 | 启发式、可疑但常见的模式 | 仅告警，送 SIEM | 单独看没有行动价值，需要与其他信号关联 |
| 信息档 | 协议统计、版本识别 | 不告警，仅留存 | 用于取证与资产发现 |

分层的实操做法是：**先把高置信档挑出来开阻断**。多数厂商的签名库自带置信度或严重性字段，加上"是否针对企业实际存在的技术栈"这个筛子，高置信档集合通常只有几百条，远小于全量签名库。这几百条开阻断的业务风险接近于零，但覆盖了利用已知漏洞的主要攻击面。

### 调优的具体动作

**动作一：按资产裁剪签名集。** 面向 Apache Struts 的签名对一个全是 .NET 的环境没有价值，只贡献噪声与性能开销。把签名集与资产实际技术栈对齐，能显著降低告警量。这需要资产系统提供软件清单（见 15.11），这是资产治理反哺检测能力的典型例子。

**动作二：区分方向。** 入向签名（外部攻击内部）与出向签名（内部主机的可疑外连）应当采用不同策略。**出向命中的价值远高于入向**——入向命中通常只说明"有人在扫我们"，出向命中往往意味着"内部已经有主机被控"。很多企业把两者混在一个告警队列里，高价值信号被淹没。

**动作三：处理 TLS 覆盖率问题。** 未解密的 TLS 流量里，IPS 只能看到握手信息（SNI、证书、JA3/JA4 指纹）。这意味着如果企业的出网流量 90% 是 TLS 且未解密，IPS 的实际检测覆盖率也就是那 10%。**汇报 IPS 有效性时必须同时给出可检测流量占比**，否则数字是误导性的（TLS 解密的取舍见 15.3.8）。

**动作四：建立误阻断的快速通道。** 开启阻断的前提是有一条比工单快得多的申诉路径——业务方报障后，值班人员应能在 15 分钟内定位到是哪条签名、并临时豁免。没有这条通道，第一次误阻断就会让整个阻断策略被撤回。

### 生产坑

**坑一：升级签名库后误报暴增。** 新签名未经本环境验证就直接生效。稳妥做法是新签名默认进入"仅告警"状态，观察一至两周后再按分层规则决定是否提升为阻断。这需要平台支持签名级的状态管理，选型时应确认。

**坑二：把 IPS 当成漏洞管理的替代品。** "IPS 已经能拦这个漏洞的利用，补丁可以晚点打"是一个危险的推理——IPS 拦的是已知利用方式，变体、加密通道、内部发起的利用都可能绕过。IPS 提供的是**修复窗口内的临时缓解**，不是修复的替代（漏洞管理见 11.8）。

**坑三：阻断源 IP 的连锁伤害。** 上下文档签名触发后阻断源 IP，在 NAT 环境下会误伤大量用户；在云环境下会阻断共享出口。阻断粒度应当尽量用会话或用户而非 IP，无法做到时需为已知的 NAT 出口与合作伙伴 IP 建立白名单。

## 15.3.6 DDoS 分层防护

### 三层能力与各自的适用区间

DDoS 防护是少数几个"能力必须提前采购、事到临头无法补救"的领域。三层能力的分工：

| 层级 | 承载位置 | 可处理量级 | 应对类型 | 起效时间 |
|------|---------|-----------|---------|---------|
| 本地清洗设备 | 企业出口内侧 | 受限于出口带宽 | 中小流量、应用层、协议异常 | 秒级，自动 |
| 运营商清洗 | 运营商骨干 | 大流量 | 容量耗尽型攻击 | 分钟级，需触发 |
| 云清洗中心 | 云服务商 | 极大流量 | 容量型 + 应用层 | 引流后生效 |

**本地设备的根本局限必须讲清楚**：当攻击流量超过企业互联网出口带宽时，链路在到达本地设备之前就已经被打满，设备再强也无济于事。这是很多企业在第一次遭遇大流量攻击时才发现的事实——买了昂贵的抗 D 设备，但出口只有 10 Gbps，攻击 50 Gbps，设备的仪表盘上一片红色而它什么也做不了。

因此**本地设备的定位应当是应用层与协议异常的精细处理，容量型攻击必须依赖上游**。两者不是替代关系。

### 引流决策：最需要提前排练的一件事

云清洗与运营商清洗都需要"引流"——把流量牵引到清洗中心，清洗后回注。引流的两种方式：

- **BGP 引流**：广播更精确的路由把流量吸引到清洗中心，适用于整段 IP 的防护，切换粒度粗（整个 /24），生效需要路由收敛时间。
- **DNS 引流**：修改域名解析指向清洗中心的 IP，粒度细（可以只切一个域名），但受 DNS 缓存与 TTL 影响，且对直接用 IP 访问的流量无效。

引流决策的现实困难在于**它需要在压力最大的时刻做一个影响面很大的决定**。可以提前准备的：

1. **把决策条件写成阈值而非判断题。** 例如"出口入向流量持续 5 分钟超过带宽的 70%，或核心业务可用性低于 95%"即触发引流，由值班人员执行而非等待管理层决策。
2. **把 TTL 提前调低。** 关键域名的 TTL 在平时就设为较低值（例如 300 秒），否则应急时改了解析也要等数小时才生效。这件事必须在攻击发生前做。
3. **每年至少演练一次引流与回切。** 演练要包含回切——很多企业演练过引流，从未演练过回切，结果攻击结束后长期跑在清洗链路上，多付费用且增加延迟。
4. **确认合约的触发流程与响应时限。** 服务商声称的响应时间（厂商称）需要通过演练验证，而不是相信合约文本。
5. **准备好业务侧的降级方案。** 攻击期间关闭非核心功能（推荐、搜索、上传）能显著降低源站压力，这需要业务方提前实现开关。

### 应用层攻击的处理边界

L7 攻击（HTTP Flood、慢速连接、针对昂贵接口的低频高消耗请求）不消耗带宽，靠流量阈值检测不出来。它们的处理位置在反向代理、WAF 或 CDN 层，手段是速率限制、挑战（JS 挑战/验证码）、以及最有效的一项——**把昂贵接口识别出来单独限流**。

同时需要区分**攻击型 L7 流量**与**业务型突发流量**。抢购、开售、热点事件带来的真实用户洪峰在流量特征上与 HTTP Flood 高度相似，而处置方式完全相反——前者要放行并扩容，后者要拦截。区分依据不在流量层面而在业务层面：真实用户会完成完整的业务链路（浏览、加购、下单），攻击流量往往只反复请求单一路径。因此**限流策略应当按业务链路的完成度而非单纯请求速率来设计**，这需要在网关层能识别会话与业务阶段，是网络防护与业务风控的交叉地带，需要两个团队共用同一份接口清单与阈值配置。

"昂贵接口"指单次请求消耗后端资源显著高于平均的接口：复杂查询、报表导出、模糊搜索、密码校验（因为哈希计算本身就是设计成慢的）。攻击者只需要几百个并发就能打垮它们。防护动作是在网关层为这类接口设置独立的、远低于普通接口的速率限制，并要求认证后才可访问。这项工作需要应用团队参与识别，是安全与研发协作的典型场景。

## 15.3.7 反向代理、WAF、CDN、API 网关的边界

这四类组件在边界上功能重叠，职责不清会导致两种失败：控制重复配置且互相冲突，或者所有人都以为别人做了而实际没人做。清晰的划分：

| 组件 | 核心职责 | 不应由它承担 | 失效表现 |
|------|---------|------------|---------|
| CDN | 缓存加速、吸收容量型攻击、隐藏源站 | 业务逻辑鉴权、精细访问控制 | 源站 IP 暴露导致被绕过直击 |
| 反向代理 | 流量入口收敛、TLS 终止、路由与灰度、隐藏内网拓扑 | 攻击特征检测 | 配置为直通，成为透明转发器 |
| WAF | 应用层攻击特征拦截、虚拟补丁 | 认证授权、业务风控 | 长期停在检测模式（见 5.3.4） |
| API 网关 | 认证、授权、配额与限流、协议转换 | 通用攻击特征检测 | 只做转发不做鉴权 |

四者的**正确串联顺序**是：CDN → 反向代理（TLS 终止）→ WAF → API 网关 → 应用。这个顺序的逻辑是"先便宜后昂贵"：CDN 用最低成本挡掉容量型流量与缓存命中的请求，反向代理终止 TLS 让后续组件能看到明文，WAF 用特征匹配挡掉通用攻击（开销中等），API 网关做认证与配额（需要查身份存储，开销较高），最后才轮到应用逻辑。任何顺序颠倒都会让昂贵的组件承受本该被前面挡掉的流量。

三个必须处理的边界问题：

**问题一：源站保护。** CDN 的所有价值在流量绕过它直击源站时归零。源站必须配置只接受来自 CDN 回源地址段的连接，并定期验证——这是一项会因为运维变更（新增一台源站、更换一个负载均衡）而反复失效的配置，需要纳入自动化核查。

**问题二：真实客户端 IP 的传递。** 经过多层代理后，应用看到的源 IP 是最后一跳代理的 IP。若依赖 `X-Forwarded-For` 又不做校验，攻击者可以伪造该头绕过基于 IP 的限制。正确做法是在最外层可信节点写入客户端 IP，中间各层只追加不信任外部传入值，应用侧只信任来自可信代理链的头部。

**问题三：谁负责证书。** 四层组件都可能持有证书，证书到期造成的可用性事故在这类架构里高频发生。证书应当集中管理、自动化续期、并对所有对外证书做统一到期监控——包括那些"临时"部署在测试域名上、后来接了生产流量的证书。

## 15.3.8 TLS 解密：一个必须显式做出的取舍

绝大多数出网与入向流量已经加密。不解密，边界上的 IPS、恶意文件检测、DLP、URL 分类都只能工作在元数据层面；解密，则要面对性能、隐私、合规与兼容四重成本。这个取舍无法回避，只能显式做出——解密设备本身会成为明文汇聚点与新的攻击目标，这一风险在公开的 TLS 检查风险管理指南中被单独强调[2]。

务实的做法是**分级解密**，而非全解或全不解：

| 流量类别 | 建议 | 理由 |
|---------|------|------|
| 员工出网到未分类/新注册域名 | 解密 | 风险最高，业务敏感度最低 |
| 员工出网到已知恶意/高风险类别 | 直接阻断，不必解密 | 无需检查内容 |
| 员工访问金融、医疗、政务、求职类站点 | **不解密** | 隐私与合规红线，多数法域下有明确限制 |
| 服务器出网 | 解密 | 服务器不产生个人隐私流量，且是 C2 回连的主要通道 |
| 对外发布服务的入向 | 在反向代理终止 | 本就需要终止才能做 WAF |
| 证书固定（pinning）的应用与移动端 | 加入豁免清单 | 强行解密会导致应用不可用 |

三条工程纪律：

**纪律一：豁免清单必须先建好。** 使用证书固定的应用（大量移动应用、部分桌面客户端、软件更新通道）在解密后会直接失败，且报错信息通常与网络无关，排障极其困难。解密上线前必须准备好豁免清单，并有一条快速添加的通道。

**纪律二：隐私与告知义务先于技术实施。** 对员工流量的解密属于监控行为，多数法域要求事先告知，部分法域要求员工代表机构参与决策。技术上线之前，法务与人力应当已经完成告知流程并留存证据。这条在跨法域运营的企业尤其重要，同一套技术配置在不同国家的合法性可能完全不同（相关的员工监控合规边界在 15.4.8 有更详细讨论）。

**纪律三：解密带来的日志本身是高敏数据。** 解密后的内容与元数据落到日志里，其敏感度远高于普通网络日志，访问控制与留存期限需要单独设计，不能沿用网络日志的默认策略。

## 15.3.9 验证与度量

### 验证方法

- **暴露面外部视角核对**：从互联网侧扫描企业所有对外 IP 与域名，与防火墙策略中"允许入向"的对象比对，输出"实际可达但策略中不该开放"与"策略开放但无对应服务"两份清单。后者是可以直接关闭的规则。
- **策略与实际配置比对**：设备上运行的配置与配置管理系统中的基线是否一致，检测手工变更（网络设备配置基线见 15.10.4）。
- **IPS 有效性抽样**：向受保护资产定向发送已知攻击特征流量，验证是否被阻断而不仅是告警，且验证时应覆盖 TLS 加密路径。
- **DDoS 引流演练**：每年至少一次完整的引流与回切演练，记录实际生效时间。
- **绕过路径搜索**：是否存在不经过边界防火墙的出网路径（分支直出、4G/5G 路由器、云上直连、办公 Wi-Fi 的旁路出口）。这类路径是边界防护的直接失效点。

### 运行关注指标

| 指标 | 定义 | 参考目标 |
|------|------|---------|
| 规则净增长 | 季度新增减删除 | ≤ 0 |
| 过宽规则占比 | 含 any/大网段规则占比 | < 5% |
| 无主规则占比 | 无责任人或用途 | < 10% |
| IPS 阻断模式签名占比 | 阻断态签名 / 已启用签名 | 逐季提升 |
| 可检测流量占比 | 经解密或明文流量 / 总流量 | 需明确披露，避免高估能力 |
| 对外暴露服务数 | 互联网可达的服务端口数 | 持续下降 |
| 引流演练达标 | 每年演练次数与实际生效时长 | ≥ 1 次，时长符合预案 |
| 证书到期事故数 | 因证书过期导致的可用性事件 | 0 |

### 常见误区

- **把设备能力等同于防护效果**。买了 NGFW 不等于有应用识别，开了 IPS 不等于会阻断，装了抗 D 设备不等于扛得住大流量。每一项都需要单独验证并披露实际覆盖率。
- **用规则数量衡量工作量**。规则越多不代表管得越细，多数情况下恰恰相反。管理层汇报应当用"净删除数"和"过宽规则占比"，而不是"本季度处理了多少条策略申请"。
- **忽略出向**。入向策略几乎所有企业都有，出向策略大量企业是 any。而 C2 回连、数据外传、恶意载荷下载全部走出向。
- **DDoS 只买不练**。合约签了、服务开了、从未演练，真到攻击时发现联系人换了、流程不清、TTL 太高。
- **把边界当成唯一防线**。本节所有能力的共同前提是流量确实经过它们。分支直出、移动办公、云上直连、员工手机热点这些路径完全不经过企业边界，边界再强也覆盖不到——这正是 15.7 的出网治理与 15.9 的 SASE 演进要解决的问题。

## 15.3.10 本节小结

边界防护的核心问题是策略腐化，不是能力缺失。规则库的熵增有明确机理——新增有流程而删除没有、知识随人流失、故障处置制造宽规则、迁移批量继承债务——干预点必须对准这四条，而不是每隔几年发起一次清理运动。

规则清理必须按风险从低到高分批推进：影子规则零风险先删，到期与下线规则对账即可，过宽规则收窄而非删除，疑似僵死规则走"转告警 → 观察一个完整业务周期 → 删除"的三步流程。给周期性规则打标签这件事必须在清理开始前完成，否则季度末作业会被反复误删。

IPS 的现实是几乎所有企业都开在检测模式，破局方法是按签名置信度分层，把几百条高置信签名先开成阻断，而不是纠结于全量开启。同时必须诚实披露可检测流量占比——未解密的 TLS 流量里，IPS 什么也看不见。

DDoS 防护中最需要提前做的不是采购而是演练：把引流触发条件写成阈值、把关键域名 TTL 提前调低、每年演练一次含回切的完整流程。本地设备无法应对超过出口带宽的攻击，这是物理事实而非产品选型问题。

最后，CDN、反向代理、WAF、API 网关的职责必须显式划分并按"先便宜后昂贵"的顺序串联，其中源站保护配置会随运维变更反复失效，需要纳入自动化核查。

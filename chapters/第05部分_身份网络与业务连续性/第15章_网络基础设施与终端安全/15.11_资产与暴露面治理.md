# 15.11　资产与暴露面治理

每一次事件复盘、每一次审计、每一次成熟度评估，结论里都会有那一条：资产清单不准确、不完整、不及时。企业于是采购新的资产管理平台、发起新的盘点项目、增加新的填报流程。两年后，同样的结论再次出现在报告里。

企业资产清点与软件资产清点被主流控制框架列为第 1、第 2 项控制，资产管理也是网络安全框架"识别"职能下的第一个类别[1][2]——它在所有清单里都排在最前面，却在所有企业里都做得最差。这个循环之所以反复，是因为**问题被反复诊断为技术问题，而它主要是组织问题**。资产不准的根源不在于没有发现工具——发现工具已经很成熟，扫描、代理、云 API 都能拿到数据；根源在于资产数据的准确性依赖于持续的人为动作（登记、更新、注销、认领），而这些动作没有任何一个人的利益与之绑定。

一个具体的表现：企业里几乎每个人都能说出"资产要准"，但如果问"某台服务器的资产记录写错了，谁会因此受到影响"，答案通常是"没有人"。数据质量的问题在这里就已经注定了。

本节讲的是怎么打破这个循环。它的核心不是介绍工具，而是三件事：**把资产数据从"靠人填"改成"靠系统推导"**（15.11.2、15.11.3）、**把资产归属做成一个有人负责且被考核的字段**（15.11.4）、以及**用数据质量指标持续暴露问题**（15.11.7）。这三件做到，资产管理才可能稳定；只上工具，两年后的报告会和今天一样。

> 导读：15.11.1 剖析资产不准的六个组织性根因；15.11.2 给出多源融合的架构；15.11.3 讲权威性与调和规则，这是融合能否可用的技术核心；15.11.4 处理资产归属——资产管理真正的难点；15.11.5 讲 SaaS 与影子 IT 发现，其中包括模型服务端点、向量库、MCP server、agent 运行时、AI 网关与推理 GPU 节点这批 2026 年增长最快的未纳管资产；15.11.6 讲 CAASM 与 EASM 的分工；15.11.7 给出资产数据质量的度量方法。本节是本章所有控制的共同前提——15.5 的终端覆盖率、15.6 的补丁分母、15.8 的准入白名单、15.2 的策略标签，全部依赖这里。

## 15.11.1 资产为什么永远不准：六个组织性根因

### 根因一：登记有流程，注销没有流程

新资产上线时会经过采购、部署、配置，这些环节自然产生记录。而资产下线时——服务器被回收、虚拟机被删除、SaaS 账号被停用、设备被员工带走——没有任何环节会主动触发资产记录的更新。**新增有推力，注销没有推力**，于是资产库只增不减，逐渐充满"僵尸记录"。

僵尸记录的危害不只是数字不准：它们会污染所有下游指标（合规率的分母被撑大）、消耗运营精力（每月排查早已不存在的失联设备）、并最终导致人们不再相信这份数据——**而不被信任的数据会加速腐化，因为没有人愿意维护一份已经没人看的清单**。

### 根因二：填报的人不是使用数据的人

资产登记通常由部署人员或申请人完成，而使用这份数据的是安全团队、审计团队、财务团队。填报者从填得准确中得不到任何好处，填得潦草也不承担任何后果。在这种激励结构下，字段被填成"待定""其他""见备注"是完全理性的行为。

**任何依赖"请大家认真填写"的资产数据都会在两年内失真**，这不是态度问题，是机制问题。

### 根因三：资产的定义本身不统一

"一台资产"到底指什么？一台物理服务器上跑了 30 台虚拟机，是 1 个资产还是 31 个？一个 Kubernetes 集群里有 2000 个短生命周期的 Pod，怎么算？一个 SaaS 应用算资产吗，它的 500 个用户账号算吗？一台员工笔记本重装系统后换了主机名，是同一个资产吗？

不同团队用不同的定义，于是同一个问题的答案在不同报表里不一致，而这种不一致会被解释为"数据不准"，进一步削弱信任。**统一资产模型是任何资产治理项目的第一步，且它是一个需要跨团队达成共识的决策，不是技术选型。**

### 根因四：变化速度超过登记速度

云环境里的资源可以在几秒内创建与销毁，容器的生命周期以分钟计。任何依赖人工登记或周期性扫描的机制，其时效性都跟不上。**这不是可以通过"提高扫描频率"解决的**——本质上需要把资产发现从"周期性拍照"改成"事件驱动"：资源创建时由平台自动推送记录，而不是等待下一次扫描。

### 根因五：边界之外的资产没有人负责

企业的资产越来越多地存在于自己的网络之外：SaaS 应用、云上的资源、开发者个人账号下的测试环境、市场部门注册的活动域名、合作伙伴托管的服务。这些资产的采购与管理不经过 IT，因此不在任何 IT 系统的视野里，但它们承载企业数据、使用企业品牌、一旦出事损失记在企业头上。

### 根因六：没有人因为资产不准而承担后果

这是前五个根因的总和，也是最根本的一条。资产数据不准，安全团队会抱怨，审计会记一笔，然后一切照旧。**只要没有任何角色的绩效与资产数据质量绑定，这件事就永远处于"重要但不紧急"的状态**，也就永远不会被真正解决。

这一条直接指向 15.11.4 的核心主张：资产治理的突破口不在工具，而在**把"归属"做成一个真实的、被考核的责任**。

### 一个失败驱动的观察

某企业在两年内先后启动过三个资产项目：第一次是采购资产管理平台并做全量盘点，交付了一份 14,000 条记录的清单；第二次是引入 CAASM 工具做多源集成；第三次是在一次审计发现问题后，组织各部门重新填报。

第三次填报结束后的抽查显示：责任人字段的填写率是 96%，而随机抽取 50 条记录逐个联系确认，**只有 19 人确认"这确实是我负责的"**——其余的要么已离职、要么表示"这个我不清楚，可能是隔壁团队的"、要么根本没有回复。

这个 96% 与 38% 的落差是整个资产治理领域的缩影：**填写率高不等于数据可用**。而更要紧的是三次项目的共同点——它们都在解决"怎么把数据收集上来"，没有一次在解决"为什么没有人在乎这份数据是否正确"。

第四次尝试他们换了做法：不再组织填报，而是把资产按各团队的云账号、代码仓库、部署流水线自动归集，生成候选归属并要求确认（超期默认接受），同时把"名下无主资产数"放进各技术团队的月度运营报表。六个月后，归属有效率从 38% 升到 81%（示例口径，非行业基准），而这一轮完全没有发起任何填报动作。

### 先统一资产模型

在开始集成之前必须先回答"什么算一个资产"，否则各方数据无法对齐。一个可用的模型分层：

| 层级 | 实体 | 是否单独计数 | 说明 |
|------|------|------------|------|
| 物理层 | 服务器、网络设备、终端、存储 | 是 | 有序列号，可物理定位 |
| 虚拟层 | 虚拟机、云实例 | 是 | 有实例 ID，生命周期独立 |
| 编排层 | 容器、Pod、函数 | **否，按工作负载聚合** | 单个实例生命周期太短，按 Deployment/服务聚合 |
| 服务层 | 应用、API、数据库实例 | 是 | 与业务归属直接对应 |
| 数据层 | 数据集、存储桶 | 是 | 需与数据分类分级结果关联 |
| 身份层 | 服务账号、密钥、证书 | 是 | 常被遗漏，但泄露后果严重 |
| 外部层 | 域名、公网 IP、SaaS 租户 | 是 | 边界外资产 |

**编排层"不单独计数"这条决定很关键。** 把每个 Pod 都当作一个资产，会让资产总数变成一个每分钟波动的无意义数字，也会淹没真正需要归属与治理的对象。正确的粒度是工作负载（一个部署单元），它有稳定的身份、有明确的归属、也是策略与责任的自然单位。

**身份层与外部层是两个最常被遗漏的层级。** 服务账号与 API 密钥不在任何"设备清单"里，域名与 SaaS 租户不在任何"IT 资产"里，而它们正是近年攻击的主要入口。资产模型如果只覆盖"能摸到的东西"，就会系统性地漏掉这两类。

## 15.11.2 多源融合：不要指望单一来源

### 每个数据源都只看得见一部分

没有任何单一系统能看到全部资产。可行的方案是把多个部分视图叠加起来，各自补上对方的盲区：

| 数据源 | 看得见 | 看不见 | 数据特征 |
|--------|-------|-------|---------|
| CMDB / 资产系统 | 已登记的、有流程的资产 | 未登记的一切 | 有业务属性（归属、用途），但时效差 |
| 云平台 API | 云上全部资源 | 本地资产 | 权威、实时、含标签 |
| 虚拟化平台 | 本地虚拟机 | 物理机、云 | 权威、实时 |
| EDR / 终端代理 | 装了代理的主机 | 装不了代理的设备 | 实时、含软件清单与进程 |
| UEM / 终端管理 | 已纳管终端 | 未纳管终端 | 含合规状态 |
| DHCP / DNS / ARP | 在网的一切（含未受管） | 静态 IP 且不解析的设备 | 覆盖广但信息浅 |
| 网络设备与准入 | 接在网上的设备与端口 | 不在企业网的设备 | 含物理位置线索（见 15.8.1） |
| 身份 / SSO 登录日志 | 被访问的应用与服务 | 不走 SSO 的系统 | **发现 SaaS 的最佳来源** |
| 采购与财务系统 | 花了钱买的东西 | 免费与试用的服务 | 权威但滞后 |
| 证书透明日志 | 申请了证书的域名 | 无证书的服务 | **发现影子域名的最佳来源** |
| 外部扫描 | 互联网可达的一切 | 内部资产 | **攻击者视角，见 15.11.6** |

**融合的价值不在于"合并成一份大清单"，而在于交叉比对产生的差异清单。** 真正有行动价值的输出是这些：

- 在 DHCP 里活跃但没有 EDR 的设备 → 终端防护缺口（见 15.5）
- 在云 API 里存在但不在 CMDB 里的资源 → 未登记资产
- 在 CMDB 里存在但所有数据源都看不到的记录 → 僵尸记录，应清理
- 在 SSO 日志里出现但不在采购记录里的应用 → 影子 IT（见 15.11.5）
- 在外部扫描里可达但不在任何清单里的服务 → **最高优先级的暴露面**
- 在证书透明日志里出现但不在域名台账里的域名 → 影子域名

**这些差异清单才是资产治理的实际产出**，而不是那份"资产总数 12,847"的数字。一个成熟的资产平台，其价值应该用"它每周产出多少条可行动的差异"来衡量。

### 融合的工程要点

**要点一：事件驱动优先于周期扫描。** 云资源创建、虚拟机创建、终端首次上线、域名注册——这些事件应当实时推送到资产平台，而不是等下一轮扫描。周期扫描作为兜底，用于发现事件通道遗漏的部分。

**要点二：保留来源与时间戳。** 每一个字段都应记录它来自哪个数据源、最后更新时间。没有这两项，冲突无法裁决，数据新鲜度无法度量。

**要点三：不要覆盖，要并存。** 当两个数据源对同一字段给出不同值时，不应让后写入的覆盖先写入的，而应两个值都保留、按权威规则计算出一个"当前有效值"、并把冲突本身作为一个可查询的对象。冲突数量是数据质量的直接指标（见 15.11.7）。

**要点四：身份关联是最难的部分。** 同一台设备在不同数据源里的标识不同——CMDB 用资产编号，EDR 用代理 ID，DHCP 用 MAC，云用实例 ID，SSO 用设备指纹。关联规则的质量决定了融合结果的可用性，这部分需要持续调优（见下节）。

**要点五：融合结果必须可解释。** 当有人质疑"为什么系统说这台机器归我"时，平台要能展示推导链条：来自哪个数据源、依据哪条规则、什么时候观测到的。不可解释的结论会被拒绝接受，而资产治理最需要的就是接受度。这一点在归属确认机制（见 15.11.4）中尤其重要——一个说不出理由的归属指派，收到的人第一反应就是否认。

## 15.11.3 权威性与调和规则

### 谁说了算：按字段而非按系统

常见的错误是宣布"CMDB 是唯一权威源"。这在实践中站不住——CMDB 对"这台机器的业务用途"是权威的，但对"它现在的 IP 是什么""它装了哪些软件""它最后一次上线是什么时候"完全不权威。

正确的做法是**按字段指定权威源**：

| 字段 | 权威源 | 理由 |
|------|-------|------|
| 存在性（这个资产是否存在） | 云 API / 虚拟化平台 / EDR 心跳 | 实时反映真实状态 |
| 网络地址 | DHCP / 云 API | 变化频繁，只有实时源可信 |
| 操作系统与版本 | EDR / UEM | 直接从系统读取 |
| 已安装软件 | EDR / 软件资产工具 | 同上 |
| 合规状态 | UEM / EDR | 同上 |
| 业务用途与分类 | CMDB / 应用目录 | 需要人的判断，无法自动推导 |
| **归属（责任人/团队）** | **CMDB + 组织系统，需强制维护** | 见 15.11.4 |
| 生命周期状态 | 采购 + 云 API + 心跳组合推导 | 单一来源都不够 |
| 物理位置 | 网络接入信息 + 资产系统 | 交换机端口能给出线索 |

### 调和规则的实现

下面这段代码演示多源记录的关联与调和，重点在于它把几个真实存在的难题显式处理了：标识关联的优先级、字段级权威、数据新鲜度衰减、以及冲突的保留。

```python
"""多源资产记录关联与调和。

records: 每条为某数据源上报的资产观测
  source, observed_at(datetime), identifiers(dict), attributes(dict)
identifiers 可能包含: asset_tag, serial, mac(list), instance_id,
  agent_id, hostname, cloud_arn
"""
from datetime import timedelta

# 标识的关联优先级：越靠前越可靠（唯一性强、不易变）
IDENTIFIER_PRIORITY = [
    "cloud_arn", "instance_id", "serial", "asset_tag", "agent_id", "mac",
]
# hostname 刻意不在列表中：主机名重复与复用极为常见，用它关联会造成错误合并

# 字段级权威：source 排在前面的优先
FIELD_AUTHORITY = {
    "existence": ["cloud_api", "hypervisor", "edr"],
    "ip_address": ["dhcp", "cloud_api", "edr"],
    "os_version": ["edr", "uem", "cmdb"],
    "installed_software": ["edr", "sam_tool"],
    "compliance_state": ["uem", "edr"],
    "business_purpose": ["cmdb", "app_catalog"],
    "owner_team": ["cmdb", "cloud_tag", "hr_system"],
}

# 各来源数据的有效期：超过则认为过期，不再参与权威裁决
SOURCE_TTL = {
    "dhcp": timedelta(days=2),
    "edr": timedelta(days=7),
    "uem": timedelta(days=7),
    "cloud_api": timedelta(days=1),
    "hypervisor": timedelta(days=1),
    "cmdb": timedelta(days=365),      # 业务属性变化慢，容忍旧数据
    "sam_tool": timedelta(days=30),
    "app_catalog": timedelta(days=365),
    "hr_system": timedelta(days=30),
    "cloud_tag": timedelta(days=1),
}


def correlate(records):
    """按标识优先级把观测记录分组为同一实体。"""
    groups = []
    index = {}

    def find_group(ids):
        for key in IDENTIFIER_PRIORITY:
            vals = ids.get(key)
            if not vals:
                continue
            for v in (vals if isinstance(vals, list) else [vals]):
                g = index.get((key, v))
                if g is not None:
                    return g
        return None

    for rec in records:
        gid = find_group(rec["identifiers"])
        if gid is None:
            gid = len(groups)
            groups.append([])
        groups[gid].append(rec)
        for key in IDENTIFIER_PRIORITY:
            vals = rec["identifiers"].get(key)
            if not vals:
                continue
            for v in (vals if isinstance(vals, list) else [vals]):
                index[(key, v)] = gid
    return groups


def reconcile(group, now):
    """对一组观测计算各字段的有效值，并保留冲突。"""
    resolved, conflicts, stale_sources = {}, [], set()

    fresh = []
    for rec in group:
        ttl = SOURCE_TTL.get(rec["source"], timedelta(days=30))
        if now - rec["observed_at"] > ttl:
            stale_sources.add(rec["source"])
        else:
            fresh.append(rec)

    all_fields = set()
    for rec in fresh:
        all_fields.update(rec["attributes"].keys())

    for field in all_fields:
        order = FIELD_AUTHORITY.get(field, [])
        candidates = [
            (r["source"], r["attributes"][field], r["observed_at"])
            for r in fresh if field in r["attributes"]
        ]
        distinct = {c[1] for c in candidates}
        if len(distinct) > 1:
            conflicts.append({"field": field, "values": sorted(
                [(c[0], str(c[1])) for c in candidates]
            )})

        def rank(item):
            src = item[0]
            pos = order.index(src) if src in order else len(order)
            return (pos, -item[2].timestamp())

        if candidates:
            resolved[field] = sorted(candidates, key=rank)[0][1]

    return {
        "attributes": resolved,
        "conflicts": conflicts,
        "stale_sources": sorted(stale_sources),
        "observed_by": sorted({r["source"] for r in fresh}),
    }


def lifecycle_state(entity, now, missing_days_threshold=30):
    """推导生命周期状态，而不是依赖人工维护的字段。"""
    seen = entity["observed_by"]
    live_sources = {"cloud_api", "hypervisor", "edr", "uem", "dhcp"}
    if seen and set(seen) & live_sources:
        return "active"
    if "cmdb" in seen or "app_catalog" in seen:
        return "record_only_investigate"
    return "unknown"
```

怎么读这段代码。四处设计值得说明：

第一，**`hostname` 被刻意排除在关联标识之外**，且代码里写了原因。主机名重复（不同环境用同一命名规则）与主机名复用（旧机器退役后新机器沿用名字）在企业里非常普遍，用它做关联会把两台不相干的机器合并成一个实体，产生极难排查的数据错误。这是资产融合中最常见的技术性错误。

第二，**`SOURCE_TTL` 让"数据新鲜度"参与裁决**。一份三个月前的 EDR 上报不应该覆盖今天的云 API 数据。同时注意 CMDB 的 TTL 被设为 365 天——因为它承载的是变化缓慢的业务属性，用同样严格的时效标准会把有用的信息全部判为过期。**不同来源的合理时效差异极大，用统一 TTL 是另一个常见错误。**

第三，**冲突被保留而不是被消解**。`conflicts` 列表让"哪些资产的哪些字段各系统说法不一"成为一个可查询、可度量的对象。这是数据质量治理的抓手——冲突数量下降说明各系统在收敛，冲突集中在某个字段说明那个字段的采集或流程有问题。

第四，`lifecycle_state` **从观测推导状态，而不是读取一个人工维护的字段**。一个只在 CMDB 里存在、所有实时数据源都看不到的记录，被标记为 `record_only_investigate` 而不是简单地当作"在用"或"已下线"——它需要人去确认到底是僵尸记录还是一台失联的真实资产。这个区分很重要：前者应删除，后者是风险。

## 15.11.4 资产归属：真正的难点

### 为什么归属比清单更难

发现资产是技术问题，已经基本解决。**确定"这个资产归谁管"是组织问题，远未解决**，而它恰恰是资产数据能否产生实际价值的关键——一个没有责任人的漏洞无法被修复，一台没有责任人的服务器无法被下线，一个没有责任人的域名无法被处置。

安全团队日常最大的时间消耗之一，就是"找人"：发现了一个问题，然后花两周时间在组织里追问这台机器是谁的。

归属难以确定的具体原因：

- **原始责任人已离职或转岗**，而资产记录里写的还是他的名字。
- **团队重组**，原来的团队不存在了，新团队不认为自己继承了这份责任。
- **共享资产**，一台数据库服务器服务于五个业务，谁是责任人？
- **平台化后责任分层**，基础设施团队管机器，应用团队管上面的服务，一个漏洞该找谁取决于漏洞在哪一层——而这需要判断。
- **填报时随手填了一个部门名**，而部门是一个太大的单位，找不到具体的人。

### 可操作的归属模型

**第一，归属必须落到一个"能被找到并且能做决定"的单位上。** 填部门名（"IT 部"）是无效的，因为部门不会做决定。有效的粒度是团队（有明确的负责人）或具体的人（并有一个备份联系人）。

**第二，区分两类归属，避免推诿。**

| 角色 | 职责 | 典型持有者 |
|------|------|-----------|
| 技术责任人 | 执行变更、打补丁、下线、修复配置 | 运维团队或平台团队 |
| 业务责任人 | 决定是否可以停机、是否可以下线、承担风险接受 | 应用负责人或业务方 |

很多推诿来自两者混淆：安全团队找到运维说"这台机器有高危漏洞请修"，运维说"我不能停业务"；找到业务方说"请安排停机"，业务方说"这是技术问题"。**明确两个角色并在资产记录里同时保存，是消除这类循环的必要条件。**

**第三，归属必须能自动推导与自动校验。** 完全依赖人工维护的归属字段必然腐化。可行的推导来源：

- 云资源的标签（在创建时由平台强制注入，见下文）
- 代码仓库与部署流水线的所有者（谁部署的，谁负责）
- 该资产上最频繁的运维操作者（从跳板机与登录日志推导）
- 关联应用在应用目录里的负责人
- 采购记录中的申请人所在团队

推导结果不必百分之百准确，它的作用是**把"完全空白"变成"有一个待确认的候选"**，这大幅降低了人工确认的成本。

**第四，在创建时强制，而不是在事后补。** 云上可以用策略强制资源必须带 owner 标签，否则创建失败或在宽限期后自动隔离；终端可以在首次注册时关联到使用人；应用上线检查项中包含责任人登记。**在创建时收集归属的成本接近于零，事后追溯的成本极高**——这是整个资产治理里投产比最高的一条规则。

### 让归属真正生效：考核

这是本节最核心也最容易被跳过的一步。上述所有机制，如果没有一个让人在意的后果，仍然会腐化。可行的考核设计：

**其一，把"无主资产数"作为团队级指标公开。** 按团队统计其名下资产的完整性（有无归属、归属是否有效、字段是否完整），在管理层的定期报告中呈现。公开可见本身就是有效的驱动力。

**其二，把归属确认作为一个有截止日期的任务。** 系统自动推导出候选归属后，向候选责任人发出确认请求：确认接受、或指向正确的人。**超期未响应的默认接受**——这个默认值是机制起作用的关键，否则所有人都会选择不响应。

**其三，把后果与归属绑定。** 无主资产在超过宽限期后进入受限状态（网络隔离、禁止出网、禁止新建同类资源）。这听起来严厉，但它是唯一能让归属确认从"低优先级的骚扰"变成"必须处理的事"的机制。实施时需要分级——先从新建资产开始强制，存量资产给较长的过渡期。

**其四，把资产数据质量纳入 IT 与平台团队的运营指标**，与可用性、变更成功率并列。安全团队无法独自解决这个问题，必须让持有资产的团队自己在意。

**其五，给正确的行为提供便利而不只是给错误的行为施加成本。** 确认归属应当是一次点击，而不是登录另一个系统填一张表；转移归属应当有明确的交接流程，而不是让人不敢接手；批量认领（"这个网段的机器都是我们的"）应当被支持。**如果确认归属本身很麻烦，任何考核都只会催生敷衍**——填一个部门名交差比认真确认省事得多。

**一个现实的提醒：** 上述第三条在多数企业会遇到强烈阻力，因为它把一个"数据质量问题"升级成了"可能影响业务的动作"。较稳的推进方式是先在低风险范围试点（例如非生产环境、新建资源），用数据证明它有效且没有造成事故，再逐步扩大。

## 15.11.5 SaaS 与影子 IT 发现

### 发现渠道

企业实际使用的 SaaS 数量通常远超 IT 知道的数量。有效的发现渠道，按信噪比排序：

1. **身份提供方的登录日志。** 走 SSO 的应用一目了然，这是最干净的来源。但它看不到不走 SSO 的应用——而风险更高的往往就是那一批。
2. **出网代理与 DNS 日志。** 访问了哪些 SaaS 域名，能覆盖不走 SSO 的应用（见 15.7）。噪声较大，需要与已知 SaaS 域名库比对。
3. **财务与报销记录。** 员工用个人信用卡订阅后报销，是影子 IT 的经典路径。这条渠道能发现技术手段看不到的服务，且自带业务上下文（谁买的、多少钱、什么用途）。
4. **邮件与账号注册。** 用企业邮箱注册的第三方服务会产生欢迎邮件、验证邮件。这条渠道有效但涉及邮件内容分析，需要注意合规边界（见 15.4.8）。
5. **CASB 或 SSE 平台的应用发现。** 集成度最高，但覆盖依赖流量经过它（见 15.9）。
6. **OAuth 授权记录。** 用户把企业身份授权给第三方应用（"用企业账号登录某工具"），这类授权在身份平台里有记录，且**风险等级高**——被授权的应用可能获得读取邮件、文件的权限。

**第六条最容易被忽略但风险最高。** 一个用户点击"允许"授予了某个第三方应用读取全部邮件的权限，这在技术上不产生任何网络流量异常，也不会出现在采购记录里，却把企业数据交给了一个未经评估的第三方。定期审查 OAuth 授权、限制可授权的权限范围、要求高权限授权走管理员审批，是必要的控制。

### SaaS 资产的特殊性

SaaS 不同于设备资产，它的"资产"其实是三层，每层都需要单独治理：

| 层次 | 对象 | 关键风险 | 治理动作 |
|------|------|---------|---------|
| 租户层 | 企业在该 SaaS 的账户 | 管理员账号被盗即全租户失守 | 纳入 SSO、强制多因素、限制管理员数量 |
| 账号层 | 该 SaaS 中的用户账号 | 离职后账号未清理 | 与身份系统联动的自动开通与回收 |
| 数据层 | 存放在该 SaaS 中的企业数据 | 数据外泄、过度共享 | 分类、共享策略、导出控制 |

**账号层的失效最普遍：** 员工离职后，企业目录里的账号被禁用了，但那些不走 SSO 的 SaaS 里的账号仍然有效。这类"离职后仍可访问"的情况在审计中几乎必然被发现。修复的根本手段是把所有 SaaS 纳入 SSO——这不只是登录便利问题，而是账号生命周期能否被统一控制的问题。对确实无法接入 SSO 的服务，必须在离职清单里逐项手工处理，且这份清单需要随 SaaS 采购持续更新。

**租户层容易被完全忽略：** 谁是这个 SaaS 的企业管理员？如果那个人离职了怎么办？如果他是唯一的管理员呢？这类"单点管理员"问题在小型 SaaS 上非常常见，且在需要紧急处置时（例如要立刻撤销某人的访问）会造成严重延误。资产记录里应当为每个 SaaS 租户登记至少两名管理员。

### 发现之后做什么

发现清单本身没有价值，处置才有。一个可操作的分诊：

| 情形 | 处置 |
|------|------|
| 已在采购与安全评估范围内 | 无动作，标记为已知 |
| 未评估但业务确有需求且低风险 | 补做评估、纳入 SSO、登记归属 |
| 未评估且处理敏感数据 | **优先处理**：评估或迁移到已批准的替代方案 |
| 免费版被广泛使用 | 通常意味着真实需求，考虑正式采购企业版（能获得管理与审计能力） |
| 已停用但账号仍在 | 清理账号，尤其是有企业数据的 |
| 明确不应使用 | 阻断访问并沟通替代方案 |

**"免费版被广泛使用"这一行值得强调。** 它通常不是违规，而是一个需求信号——员工用免费版说明这个工具确实有用而正规渠道没有提供。此时正确的动作是把它正规化（采购企业版、纳入 SSO、获得审计能力），而不是简单封禁。封禁会把使用转入更隐蔽的渠道，风险反而上升。

### AI 资产：算法团队自建的那一批

影子 IT 的主角在过去两年换了一批。上面讨论的 SaaS 仍然存在，但企业里未纳管资产增长最快的一类，是算法与业务团队自建的 AI 基础设施：模型服务端点（自托管推理服务，或对外部模型 API 的内部封装层）、向量库、MCP server、agent 运行时、AI 网关，以及承载它们的推理 GPU 节点。

它们不进台账的原因与 SaaS 不同，值得单列：算力常常来自研发预算或云上配额，不经过 IT 采购；不少服务从实验环境直接转正，没走过发布流程；部署位置在研发网段或团队自有的云账号里，不在常规扫描范围；写它的人可能已经换了项目，而这类服务又不像业务系统那样有一个明确的应用负责人。四条叠加的结果是，它们承载着企业最敏感的一批文档与数据，却正好落在 15.11.1 六个根因的中心。

处置原则只有一条：**进同一本台账，走同一套归属与考核机制。** 为 AI 资产另开一套登记系统的结果是两本账都不准——按 15.11.2 的融合逻辑，同一个实体被拆到两个系统里，交叉比对就失效了。

**发现渠道。** 按覆盖面与信噪比排序，与上面 SaaS 的六条渠道并行使用：

| 渠道 | 能发现什么 | 局限 |
|------|-----------|------|
| 云平台 API 按资源类型枚举 | GPU 实例规格、托管推理服务、托管向量库服务 | 只覆盖已纳管的云账号 |
| K8s 集群与内部服务注册表 | 带 GPU 资源请求的工作负载、指向推理端口的 Service 与 Ingress | 集群本身须在纳管范围内 |
| 出网流量与 DNS 日志 | 调用外部模型 API 的源主机，自建服务与办公终端都能覆盖 | 需先把模型 API 域名整理成独立分类（见 15.7.4） |
| GPU 节点的进程特征 | 推理框架的服务进程与监听端口、长期非零的显存占用 | 依赖 EDR 已覆盖那批机器 |
| 代码仓库与依赖清单 | 模型 SDK、向量库客户端、MCP 相关依赖 | 能发现尚未上线的部分，比流量发现早一个周期 |
| 模型服务商账户下发的 API Key | 每个 key 的调用来源 IP 与调用量 | 只覆盖走企业账户的部分 |
| 采购与云账单 | 外部模型 API 的费用科目、GPU 资源支出 | 权威但滞后一个账期 |

前两条覆盖面最大，其余几条补它们的盲区。算力全部在一个受管集群里的组织，第二条基本够用；多云加大量团队自有云账号的组织，第一条与第七条不可省。

**纳管字段。** 在 15.11.1 资产模型的通用字段之外，AI 资产还要额外登记这几项。缺任何一项，后续的风险判断都会落空：

| 字段 | 为什么必须有 |
|------|------------|
| 资产类型 | 模型服务端点 / 向量库 / MCP server / agent 运行时 / AI 网关 / 训练或推理节点。类型决定套哪套控制 |
| 基础模型与来源 | 用的哪个模型、自托管还是调外部 API、哪个服务商、哪个版本。这是供应链与合规判断的输入（见 18.2.4） |
| 接入的数据源 | 这个服务能读到哪些库、哪些文档集、哪些内部 API。**AI 资产最关键的字段，传统台账里没有对应项** |
| 可触发的动作 | agent 与 MCP server 能调什么工具、能不能写数据、能不能调用外部系统。对应 17.1.2 的自主等级判定 |
| 对外暴露状况 | 有无公网入口、是否经统一网关、认证方式 |
| 数据出境 | 请求内容是否离开企业网络、去了哪里、留存多久 |
| 处理的数据分类 | 按 8.2.1 的四级标注，它决定这个服务能接哪些数据源 |
| 技术与业务责任人 | 与 15.11.4 一致，两类分开登记 |

**与传统资产的四条关键差异。**

**差异一：暴露面按数据集算，不按主机算。** 一台 Web 服务器被攻陷，攻击者拿到的是这台机器上的数据与它持有的凭证；**一个向量库被读走，等于它索引的全部文档被读走**。而那些文档的原始副本可能分散在多个做了分类分级、加密与访问审计的系统里，做索引这一步把它们汇到了一处，且这一处的保护强度通常低于原始系统。因此 AI 资产的影响面评估必须挂在"接入的数据源"这个字段上，沿用主机重要性打分会系统性低估。

**差异二：能力会在资产本身不变的情况下改变。** 一个 agent 挂上一个新的 MCP server，它能做的事就变了，而主机、镜像、端口、进程全都没变。配置漂移检测与端口扫描看不到这类变化。台账里"可触发的动作"与"接入的数据源"两个字段因此必须受变更管控；登记时填一次就不再看，等于没有这两个字段。

**差异三：生命周期短且反复重建。** 实验用的推理端点开一天就关，但它在开着的那一天可能已经被互联网扫描器收录。周期性扫描的间隔在这里不适用，必须走 15.11.2 要点一的事件驱动路径，把云资源创建与集群工作负载创建事件实时推过来。

**差异四：实际控制人不在 IT。** 传统资产的责任人在 IT 与运维，AI 资产的实际控制人在算法与业务团队，他们通常不在安全流程的收件人列表里，也不熟悉资产登记这套语言。归属确认的通道要为这批人单独建，材料按他们的工作方式写（见 15.11.4）。

**适用边界。** 这套做法的前提是已经有一个可用的统一台账。如果 CMDB 本身是空的或全靠人工填报，先解决那个问题，AI 资产只会让它更乱。第二条边界：员工在个人设备、个人账号上使用外部模型服务不属于资产问题，对应的控制是数据分类与出网治理（见 15.7.4），而那条控制也有自己的局限。第三条边界是分工：本节讨论的是发现与登记，AI 系统本身的安全设计（模型注册表、推理侧隔离、MCP 信任边界）在 18.2 展开——台账负责回答"有什么、归谁、接了什么数据"，加固方案不在这里。

**验证方法。** 反向抽查测完整性：从出网日志里取出解析过模型 API 域名的源 IP、从云 API 取出全部 GPU 实例，逐一到台账里查，查不到的即为缺口。正向抽查测时效性：从台账随机取 AI 资产记录，联系登记的责任人确认"接入的数据源"字段与现状是否一致——这一项比责任人确认更难通过，因为数据源的变化频率远高于人员变化。外部视角核对：用 15.11.6 的 EASM 结果过一遍，看有无对外可达的推理端点或向量库端口不在台账里。最后做一次登记时延演练：让一个团队按正常流程新上线一个推理端点，测量它从上线到出现在台账里用了多久。

**运行指标。** AI 资产台账覆盖率（三条主要发现渠道的并集中已登记的比例，分母必须来自发现渠道而非台账自身）；"接入的数据源"字段的填写率与有效率，两者的落差参照 15.11.4 里归属完整率与有效率的经验；对外暴露的 AI 资产数，以及其中未经统一网关的数量；新建 AI 资产的登记时延分布（用分布，不用平均值）；无主 AI 资产数。

## 15.11.6 CAASM 与 EASM：内外两个视角

### 两者的分工

- **CAASM（网络资产攻击面管理）**：从内部视角出发，通过集成各系统 API 建立统一资产视图，回答"我有什么、状态如何、缺什么"[3]。它是 15.11.2 多源融合的产品化形态。
- **EASM（外部攻击面管理）**：从**攻击者视角**出发，通过互联网扫描、证书透明日志、域名与 IP 归属数据、公开信息发现企业暴露在外的资产，回答"从外面能看到我什么"。

**两者的差异不是技术，而是视角，且这个视角差异会产生完全不同的发现。** 内部视角看不到的东西往往最危险：一台由某个团队在自己的云账号里开的测试服务器、一个市场活动用的、外包公司搭的站点、一个被遗忘的旧域名指向了一个已被他人接管的 IP。

### EASM 的典型发现

按危险程度排序的常见发现：

1. **未登记的对外服务。** 尤其是管理界面、测试环境、以及本应内网访问的系统被意外暴露。
2. **子域名接管风险。** DNS 记录指向一个已经不再属于你的资源（例如已删除的云存储桶、已过期的第三方服务），攻击者可以注册同名资源从而控制你的子域名。这类问题极其常见且危害大（可用于钓鱼、绕过同源限制、获取 Cookie）。
3. **过期或错配的证书。** 包括已过期、域名不匹配、使用弱算法的证书。
4. **暴露的开发与测试资产。** 测试环境往往配置薄弱、数据却是生产副本。
5. **凭证与密钥泄露。** 出现在公开代码仓库、公开文档、公开构建日志中的密钥。
6. **信息泄露。** 目录列表、错误页暴露的内部路径与版本信息、公开的内部文档。

### 子域名接管：一个值得单独展开的问题

子域名接管在上述清单里排第二，因为它同时具备"极易发生"与"后果严重"两个特征，而多数企业完全没有针对它的检测。

**发生机制**：企业为某个用途创建了 `promo.example.com`，用 CNAME 指向某个云服务或第三方平台的资源。活动结束后，那个云资源或第三方账号被删除，但 DNS 记录忘了删。此时任何人都可以去那个平台注册同名资源，从而**合法地控制 `promo.example.com` 的内容**。

**为什么后果严重**：接管者拿到的是一个属于你的、带着你品牌的、可以申请有效证书的域名，不是什么陌生域名。它可以用于高可信度的钓鱼、可以获取限定在父域下的 Cookie、可以绕过某些基于域名的信任判断。

**检测方式**：定期遍历企业全部 DNS 记录，对每一条 CNAME 与别名记录检查目标是否仍然存在且仍归属于本企业。这项检查完全可以自动化，且成本很低——**它是资产治理中投产比最高的单项自动化之一**。

**预防机制**：把"删除资源前先删除指向它的 DNS 记录"写进下线流程；对 DNS 记录也施加归属与到期管理（与 15.3.3 的规则治理同一套逻辑）；以及在域名台账中记录每条记录的用途与创建原因。

### 落地要点

**其一，先解决"什么算我的"这个前置问题。** EASM 工具依赖你提供种子（域名、IP 段、组织名），种子不全则结果不全，种子过宽则产生大量不属于你的噪声。种子清单本身需要维护，且它与 15.4.3 的域名盘点是同一份数据。

**其二，输出必须能路由到人。** EASM 的发现如果不能关联到责任团队，它就只是一份不断增长的清单。这再次回到 15.11.4——**没有归属，暴露面管理无法闭环**。

**其三，与漏洞管理流程合并而不是并行。** EASM 发现的问题应当进入同一套 SLA 与工单体系（见 11.8），而不是形成第二条独立的处置流程。两条流程并存必然导致其中一条被忽略。

**其四，扫描频率与变更速度匹配。** 每季度扫一次的 EASM 无法发现存在两周的临时暴露，而临时暴露正是常见形态。至少每周一次，关键资产每日一次。

**其五，把红队的发现回流。** 红队在信息收集阶段找到的资产，往往是 EASM 工具遗漏的（见 12.2）。把红队的资产发现结果作为 EASM 种子与规则的输入，能持续改善覆盖。

## 15.11.7 资产数据质量的度量

### 不要度量"资产总数"

资产总数是一个几乎没有信息量的指标——它既不能说明覆盖是否完整，也不能说明数据是否可用。有价值的是下面这几类：

**覆盖类：**

| 指标 | 定义 | 说明 |
|------|------|------|
| 多源交叉覆盖率 | 至少被两个独立数据源观测到的资产占比 | 单源可见的资产可能是数据错误 |
| 未纳管发现数 | 网络可见但不在任何管理平台的设备数 | 直接对应终端与准入的缺口 |
| 外部暴露未登记数 | EASM 发现但不在资产库的服务 | 最高优先级 |

**质量类：**

| 指标 | 定义 | 说明 |
|------|------|------|
| 归属完整率 | 有有效技术与业务责任人的资产占比 | **最重要的单一指标** |
| 归属有效率 | 责任人仍在职且在相关岗位的占比 | 完整不等于有效 |
| 字段冲突数 | 多源对同一字段给出不同值的数量 | 反映采集与流程问题 |
| 数据新鲜度 | 各字段最后更新时间的分布 | 用分布而非平均值 |
| 僵尸记录数 | 仅存在于记录中、所有实时源均不可见 | 应定期清理 |

**流程类：**

| 指标 | 定义 | 说明 |
|------|------|------|
| 新建资产带归属率 | 创建时即有归属的资产占比 | 前置控制的有效性 |
| 归属确认响应时长 | 从发出确认请求到响应 | 反映机制是否被认真对待 |
| 下线登记及时率 | 资产实际消失到记录更新的时长 | 对应根因一 |

**"归属完整率"应当被当作资产治理的头号指标**，理由在 15.11.4 已述：没有归属，所有其他数据都无法转化为行动。

### 让指标驱动行动

指标本身不产生改变，指标的呈现方式才产生改变。两条实践：

**其一，按团队而非按全局呈现。** "全公司归属完整率 73%"没有任何人会为它负责；"你的团队名下有 47 个无主资产，全公司排名第 3"则会立刻产生动作。资产数据质量的所有指标都应当能按持有团队拆解，这是让它进入各团队视野的唯一方式。

**其二，把指标与具体清单绑定。** 每一个指标数字旁边应当有一个可点开的清单，列出构成这个数字的具体资产。只给数字不给清单，接收者无法行动，指标就退化成了汇报素材。

### 一个诚实性检查

资产指标最容易被粉饰。三个提问可以快速识别口径问题：

1. **分母是什么？** 如果"资产覆盖率"的分母是资产库里的记录数，那它天然接近 100%，毫无意义。有效的分母必须来自资产库之外（例如网络上实际观测到的设备数）。
2. **失联与豁免怎么算？** 它们应当留在分母里并单独列出，而不是被移除。
3. **"有归属"的判定标准是什么？** 字段非空不等于有归属。填了一个已离职员工的名字、填了"IT 部"、填了"待定"，都应当判为无效。

## 15.11.8 验证、常见误区与本节小结

### 验证方法

- **反向抽查**：随机抽取若干条资产记录，实地或通过多源验证其真实存在与属性准确性；再从网络实际观测中随机抽取若干设备，检查它们是否在资产库中。**两个方向都要做**，只做前者会漏掉最重要的一类问题（存在但未登记）。
- **归属可达性测试**：随机抽取资产，尝试按记录中的责任人联系并请其确认。实测的响应率通常远低于"归属完整率"所暗示的水平。
- **外部视角核对**：用 EASM 结果与内部资产库比对，输出双向差异。
- **事件回溯测试**：拿一个历史事件，检验当时的资产数据能否支持定位（这台机器是谁的、上面跑什么、谁能授权处置）。
- **数据源健康检查**：确认每个数据源的采集仍在正常工作——采集中断往往是静默的，只有在数据"变好看"（未纳管数量突然下降）时才可能被注意到。**指标突然变好，通常是采集坏了。**

### 常见误区

- **把资产治理当作工具采购**。工具能发现资产，但无法建立归属、无法制造后果，而这两项才是根因。
- **宣布单一权威源**。权威性应当按字段而非按系统划分。
- **用主机名做关联**。重复与复用极为普遍，会造成错误合并。
- **依赖人工填报**。填报者与数据使用者分离，激励结构决定了数据必然失真。
- **度量资产总数**。它不反映覆盖也不反映质量。
- **归属只填部门**。部门不做决定，找不到人。
- **发现清单不路由到人**。无论 CAASM 还是 EASM，不能关联到责任团队的发现都无法闭环。
- **封禁影子 IT 而不解决需求**。会把使用转入更隐蔽的渠道。
- **为 AI 资产另开一套台账**。同一个实体拆到两个系统里，交叉比对失效，结果是两本都不准（见 15.11.5）。
- **按主机重要性评估 AI 资产的影响面**。一个向量库被读走等于它索引的全部文档被读走，影响面要挂在"接入的数据源"字段上。

### 本节小结

资产永远不准的根因是组织性的：注销没有流程、填报者不是数据使用者、资产定义不统一、变化快于登记、边界外资产无人负责，以及最根本的一条——**没有人因为资产不准而承担后果**。因此单纯采购工具或发起盘点项目，两年后会得到同样的结论。

技术上的正确路径是多源融合：没有任何单一数据源能看到全部资产，而融合的价值不在于合并成一份大清单，**而在于交叉比对产生的差异清单**——在网但无代理的设备、云上有而 CMDB 没有的资源、外部可达但内部无记录的服务。一个资产平台的价值应当用"每周产出多少条可行动的差异"来衡量。

融合的技术核心是按字段而非按系统指定权威源、让数据新鲜度参与裁决、保留冲突而非消解冲突、以及避免用主机名做实体关联（这是最常见的技术性错误）。生命周期状态应当从观测推导，而不是读取一个人工维护的字段。

而资产管理真正的难点是归属。它的解法有四条：落到能做决定的单位（团队或人，不是部门）、区分技术责任人与业务责任人以消除推诿、尽可能自动推导以降低确认成本、以及**在创建时强制收集**——这是整个资产治理里投产比最高的一条规则。

影子 IT 的主角在过去两年换了一批：算法与业务团队自建的模型服务端点、向量库、MCP server、agent 运行时、AI 网关与推理 GPU 节点，大多不经 IT 采购、不走发布流程、不在扫描范围。它们必须进同一本台账，并额外登记四个传统台账里没有的字段——基础模型与来源、接入的数据源、可触发的动作、数据出境情况。与传统资产的差异有四条：暴露面按数据集算而非按主机算（一个向量库被读走等于它索引的全部文档被读走）、能力会在主机与端口都不变的情况下随挂载的工具改变、生命周期短到周期性扫描抓不住、实际控制人不在 IT 因而需要单独的归属确认通道。

最后，让归属真正生效需要后果：把无主资产数作为团队级公开指标、把归属确认做成超期默认接受的任务、把资产数据质量纳入持有团队的运营指标，并在充分试点后对长期无主的资产施加受限状态。没有这一层，前面所有机制都会在两年内回到原点。

# 15.5　终端安全管理

一家企业在勒索软件事件的复盘会上给出了这样一组数字：EDR 覆盖率 98.2%，终端合规率 96%，反病毒引擎全部为最新版本。攻击的完整路径是：一名财务人员打开了一个 ISO 附件，里面的快捷方式启动了一个签名合法的远程管理工具；攻击者用这个工具在终端上运行了一个凭证抓取程序；由于该员工是本机管理员，程序顺利执行；获取的域账号在另外三台机器上复用成功，两小时后攻击者拿到了域管理员权限。

EDR 在这条路径上产生了 11 条告警。全部是"中等"级别，全部处于"仅检测"状态，全部没有阻断。原因是三年前部署时，为了避免影响业务，团队把所有阻断策略关掉了，计划"稳定后再逐步开启"。此后经历了两次团队交接，没有人记得这件事。

这是终端安全最典型的失效方式：**能力都在，配置全是默认或最保守的那一档**。全书其他章节大量引用 EDR 作为数据源与响应执行点，但很少有人讲清楚 EDR 本身该怎么配。本节要补的就是这一块：EDR 与 EPP 的实际分工、策略从检测到阻断的推进路径、防篡改、应用控制、本地管理员治理、外设管控、全盘加密，以及 Windows 之外的 macOS 与 Linux 该怎么办。

> 导读：15.5.1 厘清 EPP 与 EDR 的分工，说明"买了 EDR 就可以不要 EPP"是个误解，并界定 AI 生成载荷改变了检出能力的哪一段；15.5.2 讲选型中必须实测的项，含控制台 AI 助手这一新增攻击面的采购要求；15.5.3 是本节最实用的部分——策略调优与排除项治理；15.5.4 讲防篡改；15.5.5 讲应用控制与白名单的分阶段落地；15.5.6 处理本地管理员权限治理，这是终端安全里投产比最高的单项；15.5.7 讲终端凭证保护；15.5.8 讲浏览器与扩展治理；15.5.9 讲外设与 USB 管控；15.5.10 讲全盘加密与密钥托管；15.5.11 讲基线与合规；15.5.12 处理 macOS 与 Linux 的差异；15.5.13 讲服务器终端的特殊性；15.5.14 讲终端侧的响应准备。移动设备与 BYOD 的策略选择见 10.5，本节聚焦受管的 PC 与服务器。

## 15.5.1 EPP 与 EDR：分工与常见误解

### 两者解决的不是同一个问题

| 维度 | EPP（端点保护平台） | EDR（端点检测与响应） |
|------|-------------------|---------------------|
| 目标 | **阻止**已知与可归类的恶意行为 | **发现并处置**已经发生的可疑活动 |
| 判定方式 | 签名、静态特征、行为规则、机器学习分类 | 行为遥测 + 关联分析 + 人工研判 |
| 决策时机 | 执行前或执行瞬间，自动 | 执行后，通常需要人参与 |
| 失败形态 | 漏杀（未识别）或误杀（业务受损） | 告警产生但无人处置 |
| 成功前提 | 策略开在阻断档 | 有人看告警、有响应流程 |

**最常见的误解是"有了 EDR 就不需要 EPP"。** 实际上两者的失败模式互补：EPP 拦不住的（无文件攻击、合法工具滥用、零日）恰恰是 EDR 擅长发现的；而 EDR 发现之后需要人来处置，这条链路在夜间、周末、人手不足时会断裂——此时唯一还在工作的就是 EPP 的自动阻断。

现代产品通常把两者打包在同一个代理里，这掩盖了一个重要事实：**它们是两组独立的策略，需要分别配置、分别验证**。很多企业的"EDR 上线"实际只是装了代理并开了遥测，而阻断类策略仍是关闭状态——这正是本节开头案例的成因。

### 三层能力，三种运营要求

把终端防护拆成三层，可以更清楚地看出各自需要什么才能生效：

```
第一层：自动阻断（无需人参与）
  ·反恶意软件引擎、行为阻断、攻击面削减规则
  ·要求：策略开在阻断档 + 例外治理
  ·失效表现：全部开在"仅检测"

第二层：检测与告警（需要人参与）
  ·行为遥测、关联分析、威胁狩猎
  ·要求：告警接入 SOC + 处置流程 + 分诊容量
  ·失效表现：告警堆积无人看（见 11.7）

第三层：执行控制（改变可执行的边界）
  ·应用控制/白名单、本地管理员收敛、外设管控、脚本引擎限制
  ·要求：跨团队推动 + 例外流程 + 长期运营
  ·失效表现：从未启动，或只在少数机器上试点
```

三层的投入产出比从下往上递增而落地难度也递增。**第三层是收益最高的，因为它改变的是攻击者能做什么，而不是他做了之后能不能被发现**——但它也是唯一需要与业务和 IT 深度协作的一层，所以在大多数企业里是空白（见 15.5.5 与 15.5.6）。

### AI 生成载荷：EDR 的能力边界在哪一段变了

2024 年之后，攻击侧把大模型接进了载荷制备环节：批量产出同一功能的多种变形实现、按目标环境的系统版本与已装软件定制 loader、把回连流量包装成贴合目标企业日常业务的形态。防守侧要先把这件事的性质说准，否则会做错反应。

**这里新增的不是攻击技术，是产量。** 多态引擎、加壳、代码混淆、按目标定制的免杀，这些手法在 2010 年前就已成熟，只是每做一份都要人工调试，一个熟练的人一天做不了几份，于是同一份样本必须复用到大量目标上。大模型把这道工序的人力成本压到接近零，"每个目标一份独立样本"从奢侈品变成默认做法。攻击手法本身没有变，变的是检出率曲线的形状：以样本哈希、静态特征、已知家族聚类为判据的那部分能力，随着"每份样本只用一次"而持续贬值；以执行链、API 调用序列、注入手法、内存中的代码形态为判据的那部分，因为 TTP 层面的演化速度远慢于载荷层面，相对价值上升。

对终端策略的三条直接影响：

- **样本级检出率不能再作为选型与汇报的主指标。** 一份"对 1000 个样本检出 99% 以上"的测试结果，其信息量取决于这 1000 个样本代表多少种技术。若它们是同一家族的 1000 个变体，这个数字说明不了什么。
- **EPP 的静态判定层贬值最快，15.5.3 里 B 档那批攻击面削减规则贬值最慢。** "禁止 Office 应用创建子进程""禁止脚本引擎执行下载内容"这类规则约束的是行为路径，与载荷长什么样无关。把 B 档的推进优先级排到静态引擎调优之前，是这条趋势下最直接的策略调整。
- **内存扫描与执行后的行为检测要逐项确认是否开启。** 部分产品把这两项做成可选功能且默认关闭，理由是性能开销，而它们正是这条趋势下相对价值最高的两项。开启前按 15.5.2 的第二项实测开销。

连带影响还有一处在情报侧：以文件哈希为主的失陷指标有效期显著缩短，一份上周有效的哈希清单这周可能一条都命中不上；而基础设施类指标——域名、IP、证书指纹、TLS 客户端指纹——因为攻击者的服务器复用成本没有同步下降，衰减慢得多。终端与网络两侧的情报订阅权重应当据此调整，DNS 与出网日志的相对价值随之上升（见 15.7.1）。

需要避开的一种应对方式是：检出率下滑之后去调高静态引擎的启发式强度。这条路在多数环境里走不通——启发式强度与误报量近似同步上升，而误报的标准处理动作是加排除项，最终结果是排除项数量增长、其中一部分指向用户可写目录，等于把 15.5.3 里最危险的那类配置又扩大了一轮。补法在行为层与执行层，静态判定的阈值上补不出来。

**适用边界。** 这条判断只覆盖"载荷制备与执行"这一环，对初始访问方式、提权路径、横向移动手法都不成立——攻击者仍然要通过钓鱼或暴露服务进来，仍然要拿到凭证才能走远。因此 15.5.5 的应用控制与 15.5.6 的本地管理员治理不受这条趋势影响：应用控制只判断程序在不在允许清单里，不判断它像不像恶意软件，载荷变形多少次都不改变这个判定结果，它在这条趋势下的相对价值反而上升。第二条边界是前提性的：如果终端策略还停在全部仅检测的状态（本节开头的案例），讨论检出率曲线没有意义，先把 A 档打开。第三条边界在研发终端上：那里自编译二进制大量出现，行为基线本身噪声高，"行为检测价值上升"的结论要打折扣，缺口靠 15.5.5 的分层控制补，调检测阈值补不上。

**验证方法。** 把检出率回归的测试单位从"样本"换成"同一 TTP 的 N 个变体"：

1. 选一组与本企业相关的 ATT&CK 技术（凭证转储、进程注入、计划任务持久化、防护停用这几类是合适的起点），用 Atomic Red Team 的现成用例建立基线覆盖。
2. 对每个技术准备 N 个实现变体：换实现语言、换调用的 API 路径、换加载方式、换字符串与编码处理。造变体不必依赖大模型，改编译选项与调用路径人工也能造出十几个，用大模型只是让 N 更大、迭代更快。
3. 在与生产同策略的隔离终端上逐个执行，记录三件事：是否检出、被哪一层检出（静态引擎 / 行为规则 / 内存扫描）、是阻断还是仅告警。这台终端的策略必须与生产完全一致，包括排除项——用一台"干净配置"的机器测出来的数字没有参考价值。
4. 每次代理版本升级、每次策略档位调整后重跑同一组变体，形成时间序列。

两条操作纪律：自研变体只在隔离环境生成与执行，不上传任何公共沙箱或多引擎扫描平台，否则等于把自己的测试集交出去；测试主机与测试账号要在资产库里单独标注，避免测试告警混进正式的事件统计。

**运行指标。** 按 ATT&CK 技术分别统计，不做全局平均：

| 指标 | 定义 | 说明 |
|------|------|------|
| TTP 变体检出率 | 该技术被检出的变体数 / 变体总数 | 按技术分别列；低于半数的技术列入检测补齐队列 |
| 变体阻断率 | 被阻断的变体数 / 变体总数 | 与检出率的差额就是"要靠人处置"的那部分 |
| 检出层次分布 | 静态 / 行为 / 内存三层各自的命中占比 | 静态占比逐季下降，是这条趋势在本环境已经发生的直接证据 |
| 版本间检出率变化 | 同一组变体在两次回归之间的检出率差 | 升级带来的能力变化，正负都记 |
| 回归覆盖的技术数 | 已建变体集的 ATT&CK 技术数量 | 逐季扩充，不追求一次覆盖全部 |

回归结果有两种用法，都要用上。横向看：哪些技术的变体检出率明显低于其余，这批技术进检测工程的补齐队列（见 11.3）。纵向看：同一技术在几个季度之间的曲线，若某条技术的检出率在没有做过任何策略调整的情况下持续走低，说明它的检测依赖静态判据，需要改写成行为判据。第二种用法更重要，它是"静态判定层正在贬值"这件事在本环境里唯一可信的证据来源；外部报告写得再多，也代替不了自己这条曲线。

厂商公开的检出率数据在这套口径下不可直接比较——各家的测试集、配置档位、样本时效都不同，需在自己环境按上述方法验证。

## 15.5.2 选型：需要实测而非听介绍的几件事

各家产品的检出率宣传（厂商称）在真实环境中的可比性很差，测试集、配置档位、样本时效都不同。POC 阶段真正值得投入时间实测的是下面几项：

**一、Windows 之外的覆盖能力。** 多数产品在 Windows 上能力最强，macOS 与 Linux 上的功能集常常显著缩水（少了应用控制、少了设备管控、遥测字段更少）。**必须按操作系统分别评估功能矩阵**，而不是接受一句"全平台支持"。若企业研发团队大量使用 macOS、生产环境大量是 Linux，这项差异会直接决定实际防护水位（见 15.5.12）。

**二、性能开销的真实数值。** 在真实业务负载下测量：编译构建耗时变化、数据库压测的吞吐变化、终端开机与登录耗时变化。研发团队对构建变慢极其敏感，这是 EDR 在研发机上被要求豁免的头号原因——提前测出数字并优化配置，比事后争论有效得多。

**三、离线与断网时的行为。** 终端离开企业网络、代理无法回连管理平台时，本地策略是否仍然生效、遥测能否缓存、多久后本地缓存的策略会过期。远程办公场景下这是常态而非例外。

**四、卸载与篡改的实际难度。** 用本地管理员权限尝试停止服务、删除文件、修改注册表、安全模式启动后卸载。这些是攻击者的标准动作，也是选型时最少被测试的（见 15.5.4）。

**五、隔离（containment）的粒度与恢复。** 网络隔离一台机器后，还能不能远程管理它、能不能采集证据、能不能让用户看到提示、解除隔离要多久。事件响应中这几分钟直接影响处置效果（见 11.5）。

**六、与现有工具的冲突。** 同一台机器上并存两个终端防护代理，是性能与稳定性事故的经典来源。若企业正在从旧产品迁移到新产品，必须验证共存期的行为，并规划好卸载旧代理的顺序与回退方案。同样需要验证的还有：与备份代理、虚拟化工具、数据库客户端、开发工具链、以及某些行业专用软件的兼容性。这类问题在 POC 的小范围试用中往往不会暴露，需要专门覆盖典型岗位的完整软件栈。

**七、数据留存与查询性能。** 遥测数据保留多久、查询 30 天前的进程树需要多长时间、导出原始数据是否受限。事件调查往往需要回溯数周，若产品默认只存 7 天，调查会在最关键的地方断掉。

### 控制台里的 AI 助手是一个新增的攻击面

2024 年之后，主流终端防护控制台陆续加入自然语言查询、告警摘要、处置建议、剧本自动生成这几类能力。采购时它们被算作运营效率的改进，而在威胁建模上它们是一个新的输入面：**这些 AI 组件读取的遥测字段，有相当一部分由被攻陷主机上的攻击者直接写入**。

可被攻击者控制的输入至少有这几类，它们都会原样进入告警记录，也就都会进入 AI 助手的上下文：

- **进程命令行**。攻击者完全控制自己启动的进程带什么参数，把几百字的指令文本塞进命令行毫无难度。
- **文件名与路径**。同理，且文件名出现在几乎每一条文件类告警里。
- **脚本内容与注册表键值**。脚本类告警通常带上脚本片段，长度足以承载一段完整指令。
- **网络遥测字段**。请求头、DNS 查询串、TLS SNI 里的内容同样由对端决定。
- **富化数据**。外部威胁情报的描述字段、开源情报摘要若被拼进上下文，来源同样不可信。

按 AI 组件被授予的权限，后果分三档：

| AI 组件的权限 | 提示注入的后果 |
|-------------|--------------|
| 只生成摘要与解释 | 误导分析师。把一次批量加密行为总结成"备份任务"，把已攻陷主机描述为"已确认误报" |
| 自然语言转查询 | 证据检索被引偏。查询被诱导到错误的时间窗或错误的主机范围，分析师看到的是一片干净 |
| 可触发处置动作 | **一条新的拒绝服务通道**。攻击者在一台无关紧要的机器上构造命令行，诱导助手隔离核心业务主机、终止关键进程、把常用二进制加入黑名单 |

第三行是采购与配置的重点。一个能触发"隔离主机"的 AI 助手，其可用性风险与它带来的效率收益不在同一个量级——攻击者不需要绕过任何检测，只需要让告警产生。这两类风险在 18.3 里分别对应提示词注入与过度代理权限两个条目，通用防护在那里给出，本节只补终端场景的落地要求。

三档之间的差别只在权限，注入路径完全相同，因此"我们只用摘要功能"不构成豁免理由——功能开关会随版本升级变化，一次控制台升级就可能把处置建议默认打开。升级后重新确认 AI 相关功能的开关状态，要写进升级检查清单。

**采购阶段必须写进要求的六条：**

1. **上下文字段可披露。** 要求厂商说明 AI 组件的上下文里放了哪些遥测字段、这些字段进入模型前做了什么处理（截断、转义、结构化包装）。答不上来的按"全部原始字段直接入上下文"处理。
2. **AI 功能可整体关闭，也可按角色关闭。** 关闭后不得影响查询、策略下发、隔离等基础功能。这一条要落在合同上，"深度集成、无法单独关闭"是不可接受的答复。
3. **建议与执行分离。** AI 只产出建议，执行由人显式确认，确认界面必须展示将要执行的具体动作与受影响主机清单。用 17.1.2 的自主等级标尺讲，终端控制台的 AI 助手在生产环境的上限是 L2（AI 把材料查齐，人做决定），默认把 L3 及以上打开的产品在采购阶段就要求关掉。
4. **权限继承发起人。** 助手执行查询时用提问者的权限，不用统一的高权服务账号。否则一线分析师可以借助手读到权限之外的数据，这在做了数据分域的组织里是硬性合规问题。
5. **交互全量审计且不可删改。** 每一次提问、生成的查询语句、给出的建议、人做了什么确认，都要落审计日志，且控制台管理员不能删改（管理平台自身的安全见 15.5.15 自评清单的第九项）。
6. **推理位置与数据流向可说明。** 模型是本地推理还是调外部 API；调外部时，遥测数据出境的路径、留存时长、是否用于训练。这一项与 15.7.4 讨论的模型 API 出网是同一个问题在采购侧的对应面。

**配置阶段的三条：** 关闭全部自动处置，或把自动处置收窄到明确列举的低风险动作（例如终止指定哈希的进程），隔离主机、批量删文件、下发策略一律不在其中；对隔离类动作设单次影响上限并要求二次确认；把助手行为本身纳入监控——短时间内异常密集的隔离建议、查询范围突然扩到全网，这两个信号要产生告警。

**一个容易被漏掉的延伸面。** 把终端告警接进企业自建的安全智能体（见 17.2）时，上面这条注入路径会被原样继承，而自建侧的权限通常比厂商控制台更大——它往往同时握着 SIEM 查询、工单、隔离与封禁这几套工具。在厂商控制台上做的动作限制不会自动出现在自建智能体上，两边各配一遍是必要的。

**适用边界。** 这条只在"AI 组件能读到攻击者可控字段"时成立。只做产品文档问答的助手不接触遥测，不构成这条路径——但要实测确认，多数产品的同一个对话框既回答文档问题也查遥测，销售口径里的"知识库助手"未必真的隔离。完全离线、只有平台管理员可用的场景风险也低。还有一条更要紧的边界：提示注入没有可以宣告完成的修复，输入过滤能降低命中率但不能归零（依据见 18.3 对应条目的适用边界）。因此控制重心放在限制 AI 组件能触发什么动作，而不是设法让它不被注入。

**验证方法。** 在隔离的测试租户里逐个通道做注入测试，每条通道各造一个用例：用带指令文本的进程命令行触发一条告警，观察助手的摘要与建议是否被影响；用文件名承载指令重复一次；用脚本内容重复一次；若接入了外部情报富化，在测试情报源的描述字段里重复一次。另外三项：用只读账号通过助手提问需要更高权限的数据，验证权限继承；关闭 AI 功能后跑一遍日常运营动作，验证基础功能不受影响；做一次完整交互后检查审计日志能否还原全过程。这七个用例应当与前面七项实测一起放进 POC 清单，上线之后再补的成本高得多。

**运行指标。** AI 助手在生产环境可直接触发的动作类型数（目标 0）；注入测试用例在本环境的通过率，每次控制台版本升级后重跑；助手交互的审计覆盖率（目标 100%）；经助手发起的高影响动作数及其中人工确认的比例；助手使用统一服务账号发起的查询数（目标 0）。这几项不产生日常噪声，季度盘点一次即可。

## 15.5.3 策略调优：从"仅检测"到"阻断"

### 分档推进，而不是一次性开关

把全部策略从检测切到阻断会造成大面积业务中断，而永远不切则等于没有防护。可行的路径是**按策略类别分档，每档有不同的证据门槛与推进节奏**：

| 档位 | 策略类别 | 推进节奏 | 判据 |
|------|---------|---------|------|
| A 立即阻断 | 已知恶意文件、勒索行为特征、凭证转储、引导区篡改 | 部署即开启 | 合法业务不会产生此类行为 |
| B 观察后阻断 | 攻击面削减类（宏创建子进程、脚本执行下载内容、办公软件创建可执行文件） | 检测 4-8 周后逐条开启 | 需要按规则逐条评估误报 |
| C 需要定制 | 可疑工具使用（远程管理工具、系统管理工具、渗透测试工具） | 白名单化后开启 | IT 运维本身在用，需先确定合法使用者 |
| D 仅检测 | 弱信号、启发式、需要上下文的行为 | 长期保持检测 | 单独看无行动价值，送 SOC 关联 |

**A 档必须在部署第一天就开启。** 它的误报风险接近于零，而这一档覆盖的正是损失最大的行为。把 A 档也关掉"等稳定"是完全没有道理的保守，也是本节开头案例的直接成因。

**B 档是收益最大的一档，也是最需要耐心的。** 攻击面削减类规则（例如"禁止 Office 应用创建子进程""禁止脚本引擎执行从互联网下载的内容""禁止从 USB 运行未签名的可执行文件"）几乎覆盖了主流投递链的每一环。它们的误报来自企业里那些"用 Office 宏做自动化""用脚本调用外部程序"的历史遗留，需要逐条识别并处理——处理方式优先是改造那个业务流程，其次才是加例外。

**C 档的关键是先确定"谁在合法地使用"。** 远程管理工具是 IT 支持团队的日常工具，也是攻击者最爱的落地工具。正确做法不是禁用，而是限定：只允许特定的一款工具、只允许从特定管理终端发起、只允许特定账号使用，其余全部阻断。这需要 IT 团队先完成工具收敛，是一项跨团队工作。

### 把档位写成配置，而不是留在会议纪要里

分档只有落成可版本化的配置，才不会在人员交接后失传。下面是一份终端策略基线的组织形态，重点在于它显式记录了**每一条策略当前处于哪一档、为什么、什么条件下会推进到下一档**：

```yaml
endpoint_policy_baseline:
  version: 12
  effective_from: 2026-05-01
  owner: endpoint-security
  scope: corporate-windows-workstation

  tier_a_block_now:
    - id: ransomware-behavior
      state: block
      note: 加密类批量文件改写行为, 部署第一天即启用
    - id: credential-dump
      state: block
      note: 认证进程内存读取, 合法业务不产生
    - id: boot-record-tamper
      state: block
    - id: known-malware
      state: block

  tier_b_observe_then_block:
    - id: office-child-process
      state: block
      observed_since: 2026-01-15
      promoted_on: 2026-03-20
      exceptions_count: 2
    - id: script-launch-downloaded-content
      state: block
      observed_since: 2026-01-15
      promoted_on: 2026-03-20
      exceptions_count: 0
    - id: office-create-executable
      state: audit
      observed_since: 2026-03-01
      blocking_issue: 财务部报表工具会生成临时可执行文件, 改造中
      target_promote: 2026-08-01
    - id: exec-from-removable
      state: block
      observed_since: 2026-02-01
      promoted_on: 2026-04-10

  tier_c_allowlist_required:
    - id: remote-admin-tools
      state: block
      allowed_tools:
        - name: 企业标准远程支持工具
          allowed_source_hosts: mgmt-jump-hosts
          allowed_accounts: it-support-group
      note: 其余同类工具一律阻断, IT 工具收敛已于 2026-02 完成

  tier_d_detect_only:
    - id: suspicious-parent-child
      state: audit
      route_to: siem
    - id: rare-signed-binary
      state: audit
      route_to: siem

  exclusions:
    - path_or_hash: sha256:PLACEHOLDER_HASH_OF_LEGACY_REPORT_TOOL
      scope: finance-workstations
      reason: 遗留报表工具误报, 已确认无害
      owner: finance-it
      ticket: EXC-2026-0442
      expires: 2026-11-30
      review_note: 供应商已承诺 Q3 发布签名版本, 届时移除本例外
```

这份配置最有价值的是三个字段。`blocking_issue` 显式记录了"这条为什么还没开到阻断"——没有它，一条停在 audit 的策略过几个月就变成了默认状态，没有人记得它本来是要推进的。`target_promote` 给这个停滞加了一个日期，到期未推进就会被季度复核抓出来。`review_note` 让例外带上了退出条件，而不是无限期存在。

配套的运营纪律是：**每季度复核一次，输出"仍处于 audit 状态且已超过目标日期"的清单**，并在管理层报告中呈现。把停滞变成可见的数字，是唯一能让 B 档持续推进的机制。

### 排除项治理：最容易腐化的地方

排除项（exclusion）是终端防护体系里最危险的配置——它在扫描与检测中开出一个洞，而这个洞不产生任何日志、不引发任何告警、也几乎不会被复查。攻击者深知这一点，专门把载荷放在常见的排除路径下。

排除项的典型来源与风险：

| 来源 | 典型形态 | 风险 |
|------|---------|------|
| 厂商推荐配置 | 数据库、虚拟化平台、备份软件的官方排除清单 | 中，通常合理但需按实际路径收窄 |
| 性能问题临时处理 | 排除整个 `D:\` 或整个开发目录 | **极高**，范围过大且无到期日 |
| 误报处理 | 排除某个业务程序 | 中，应用哈希或签名而非路径 |
| 历史遗留 | 早已不存在的软件的排除项 | 中，无用但可能被利用 |

四条治理纪律：

1. **排除项必须用最精确的维度。** 优先级：文件哈希 > 数字签名 > 完整路径 + 进程 > 目录 > 扩展名 > 整盘。绝对禁止排除整个盘符或用户可写的宽泛目录（例如 `C:\Users\*\Downloads`）。
2. **排除项必须有责任人、理由与到期日**，与防火墙规则同一套治理逻辑（见 15.3.3）。
3. **定期审计排除路径是否可被普通用户写入。** 一个被排除的目录如果普通用户能往里写文件，它就是一个完美的载荷投放点。这项检查可以完全自动化，且几乎总能查出问题。
4. **排除项变更纳入变更管理并留痕。** 攻击者拿到管理平台权限后添加排除项，是真实发生过的攻击手法——管理平台的配置变更本身必须被审计并告警。

### 一个容易被忽略的问题：告警去了哪里

策略调优的另一半是告警链路。常见的断裂点：产品控制台里有告警，但没有接入 SIEM；接入了 SIEM，但没有对应的处置剧本；有剧本，但夜间无人值守；有值守，但告警量超出分诊容量。

一个可操作的自检是**端到端时延实测**：在一台终端上执行一个已知会触发高危告警的行为（例如用测试工具模拟凭证转储），记录从行为发生到有人开始处置的时间。这个数字比任何覆盖率指标都更能反映终端防护的真实状态（检测工程与告警设计见 11.3、11.7）。

## 15.5.4 防篡改：让代理无法被关掉

攻击者拿到本地管理员权限后的第一个动作，往往是尝试停用终端防护。若代理可以被关掉，前面所有策略配置都失去意义。

### 需要逐项确认的防护面

- **服务与进程保护**：本地管理员能否停止服务、结束进程、挂起线程。
- **文件与注册表保护**：能否删除或替换代理文件、修改配置注册表项。
- **卸载保护**：卸载是否需要一个只有管理平台才有的令牌或密码。这个密码不能是全企业统一且长期不变的——一旦泄露即全线失效，应支持按设备生成或定期轮换。
- **安全模式启动**：进入安全模式后代理是否仍加载。这是绕过终端防护的经典手法，很多产品在安全模式下默认不启动。
- **驱动加载顺序与早期启动**：代理是否在早期启动阶段就获得保护，避免被启动前加载的组件干扰。
- **管理平台侧的策略强制**：即使本地被修改，下一次心跳能否被检测并自动修复。
- **卸载与停用的告警**：任何停用、卸载、篡改尝试是否产生高优先级告警。**这条比阻止本身更重要**——阻止可能被绕过，但告警让你知道有人在尝试。

### 生产坑

**坑一：为了运维方便把防篡改关掉。** IT 团队在批量重装、迁移、排障时会觉得防篡改碍事，于是申请关闭"临时使用"。可行的替代是提供一个受控的临时禁用机制：需要管理平台授权、限定单台设备、限定时长、自动恢复、全程留痕。

**坑二：卸载密码写在部署脚本里。** 部署脚本往往存放在共享目录或代码仓库中，普通用户可读。这等于把防篡改的钥匙公开。密码应通过管理平台下发或使用一次性令牌。

**坑三：只保护了终端代理，没保护管理平台。** 管理平台是终端防护的"上帝视角"——它能推送策略、执行脚本、卸载代理。攻击者拿到平台管理员权限，可以一次性关掉全公司的防护，甚至用它分发勒索载荷。因此管理平台必须被当作最高信任域资产对待（见 15.1.3）：强制多因素认证、限定管理终端来源、所有配置变更审计并告警、管理员账号与日常办公账号分离。

## 15.5.5 应用控制与白名单

### 为什么它是收益最高、也最少被做的控制

应用控制（application control，也称白名单）改变的是攻击的可能性空间：不在允许列表中的程序根本无法执行，无论它是恶意软件、被滥用的合法工具，还是攻击者自带的载荷。它不依赖检测——因此不受免杀、混淆、零日的影响。规划、部署与运维的通用方法（包括规则判据选择与分阶段推进）可参照公开的应用白名单指南[1]。

它极少被完整落地的原因也很直接：**企业里到底有多少程序在运行，没有人知道**。研发机上有大量自编译的二进制，业务部门有各种小工具，历史遗留系统依赖着早已无人维护的组件。一份完整的允许清单看起来是不可能完成的任务。

破解这个困境的关键认知是：**不必对所有终端做同样强度的应用控制。** 按岗位与风险分层，能让这项工作从"不可能"变成"分批可完成"。

### 分层落地路径

下表的五个档位按管控强度从松到紧排列，用"第一档"至"第五档"称呼，量的是**允许什么程序在终端上跑**这一件事。这里刻意不用 L1–L5 之类的字母记号：本书的裸 L 记号只留给 17.1.2 的 AI 自主等级，管控强度与自主性风马牛不相及，套同一套记号只会平添误读。

| 层级 | 适用对象 | 控制强度 | 落地难度 |
|------|---------|---------|---------|
| 第一档 阻断高风险位置 | 全员 | 禁止从临时目录、下载目录、USB、邮件附件目录执行 | **低**，收益立现 |
| 第二档 阻断未签名 | 全员（研发除外） | 只允许有有效数字签名的可执行文件 | 中，需处理内部自研程序 |
| 第三档 受管安装源 | 标准办公岗位 | 只允许由受信任的安装程序（UEM、软件分发系统）部署的程序运行 | 中高，需先统一软件分发 |
| 第四档 严格白名单 | 高价值岗位（财务、高管助理、运维） | 显式允许清单，其余全拒 | 高，但对象数量少 |
| 第五档 服务器白名单 | 生产服务器 | 显式允许清单 | **中**，服务器软件变化远少于 PC |

**第一档是所有企业都应该立刻做的。** "禁止从用户可写的临时目录执行可执行文件"这一条规则，覆盖了绝大多数邮件与浏览器投递的初始载荷执行路径，而合法软件几乎不从这些位置运行。它的实施成本极低，误报可控，是应用控制的正确起点。**不要从第四档开始试点**——那会立刻遇到最难的问题，然后项目停摆。

**第五档常被忽略但难度低于第二、第三档。** 生产服务器上运行的程序集合稳定、变化受控、有明确的变更流程，做白名单比办公终端容易得多，而服务器被攻陷的损失更大。很多企业的顺序反了。

### 规则的形态：越靠"身份"越省事

应用控制规则可以基于不同的判据，维护成本差异极大：

| 判据 | 维护成本 | 稳定性 | 适用 |
|------|---------|-------|------|
| 文件哈希 | **最高**，每次更新都要改 | 最精确 | 极少数关键程序 |
| 数字签名（发布者） | **最低** | 软件更新不影响 | 主力手段 |
| 签名 + 产品名 + 版本下限 | 低 | 可拒绝旧版本 | 需要强制版本时 |
| 文件路径 | 低但**不安全** | 路径可被写入即失效 | 仅用于系统只读目录 |
| 受管安装源 | 低 | 与分发通道绑定 | 大规模部署的关键 |

**主力应当是"数字签名 + 受管安装源"这一组合。** 基于哈希的规则在理论上最严格，但一个每月更新的浏览器意味着每月都要改规则，这种维护量会让规则集在半年内失控并最终被放弃。基于路径的规则则有一个致命问题：如果那个路径普通用户可写，攻击者只要把载荷放进去就绕过了——**因此路径规则只能用于用户无写权限的系统目录，且必须定期核验目录权限**。

一份典型的分层规则集在结构上大致是：允许操作系统厂商签名的程序；允许企业内部代码签名证书签名的程序；允许由企业软件分发系统安装的程序；允许一批经过审核的第三方发布者；显式拒绝一批已知被滥用的合法工具（即便它们有有效签名）；其余全部拒绝。**最后那条"显式拒绝有效签名的滥用工具"很关键**——攻击者大量使用带有合法签名的系统管理工具、远程控制工具、驱动加载工具，只按签名放行会把它们全放进来。

### 工程要点

**要点一：先用审计模式跑足够长。** 与微隔离的学习期同理，审计模式需要覆盖完整的业务周期——月末结算、季度报表、年度审计期间会出现平时不运行的程序（见 15.2.3）。

**要点二：用"受管安装源"概念降低维护量。** 现代应用控制机制支持把某个安装程序（例如企业的软件分发客户端）标记为受信任来源，由它安装的程序自动获得允许。这把维护工作从"逐个程序加白"变成"管好分发通道"，是第三档可行的关键。

**要点三：处理好脚本与解释器。** 只控制可执行文件而不控制脚本引擎，等于留了一扇大门。PowerShell、Windows Script Host、宏、Python、Node 都可以执行任意逻辑。对应措施包括：脚本引擎的受限模式、脚本签名要求、关闭不必要的解释器、以及对脚本引擎的行为做重点监控。

**要点四：例外流程必须比绕过更省事。** 若加白一个程序需要三天审批，员工会想办法绕过（改名、放到已允许的目录、用便携版）。目标应当是常见场景当天完成，且有自助提交入口。

**要点五：与研发环境的边界要提前谈好。** 研发机上强制签名或白名单几乎必然失败——研发工作本身就是不断产生新的未签名二进制。可行的替代是：研发机使用独立的、更严格的网络与数据访问策略（把风险控制在爆炸半径上），同时在研发机上保持完整的 EDR 遥测与阻断能力。用网络与权限的收紧，换执行控制的放宽。

## 15.5.6 本地管理员权限治理

### 单项投产比最高的终端控制

回到开头的案例：如果那名财务人员不是本机管理员，凭证抓取程序无法运行，攻击链在第三步就断了。本地管理员权限的收敛是终端安全里**投入最小、效果最直接**的一项工作——它不需要采购，主要成本是处理"用户需要装软件"这一类日常需求。

它长期做不掉的原因通常有三个：历史上镜像里就把用户加成了管理员；IT 支持流程依赖用户自己能装软件；某些业务软件确实要求管理员权限运行。这三个都有解法。

### 三种常见的反对意见与回应

**"我们是研发公司，工程师必须有管理员权限。"** 部分成立，但需要拆开看：工程师需要的通常是安装开发工具、运行容器、调试驱动，其中多数可以通过预装工具链、容器化开发环境、以及针对性的按需提权解决。真正需要长期管理员权限的岗位往往远少于声称的数量。可行的折中是：研发机保留管理员权限，但把研发机放进独立的网络与数据访问域，并保持完整的 EDR 阻断能力——用爆炸半径换执行自由。

**"收权会大幅增加 IT 工单量。"** 短期成立。可量化的应对是：先统计当前提权动作的分布（见下文代码），把占比最高的几类做成自助方案，再开始收权。做好配套的企业，收权后的工单增量通常远低于预期；不做配套直接收权的，工单会在两周内压垮支持团队并迫使项目回退。

**"高管要求保留权限。"** 这是最难的一类，因为它不是技术问题。有效的回应是把风险具体化：高管终端是社工攻击的首要目标，且其账号往往有更广的数据访问权；同时提供高优先级的支持通道作为补偿（专人响应、优先处理），让"没有管理员权限"不等于"办事变慢"。这类特例最好由 CISO 与高管本人直接沟通，而不是由 IT 支持人员去说服。

### 落地路径

**第一步：搞清楚现状。** 统计有多少终端的日常用户是本机管理员、这些账号里有多少是域账号被加进本地管理员组、有多少是共享的本地账号。这个数字通常远超预期。

**第二步：先处理最容易的群体。** 新入职员工与新装机器直接不给管理员权限——从增量开始，避免与存量的历史习惯正面冲突。同时选一两个配合度高的部门做试点。

**第三步：为常见需求提供替代方案。** 收权之所以引发抵抗，是因为它挡住了真实需求。需要同时提供：

- **自助软件门户**：常用软件预先打包，用户自助安装，无需管理员权限。这是最重要的配套，没有它收权必然失败。
- **按需提权**：对确需管理员权限的操作，提供限时提权机制（申请、审批或自动策略、限时、留痕）。
- **应用级提权**：某些老旧软件要求管理员权限才能运行，可以针对该程序单独授权，而不是把用户整体提为管理员。
- **驱动与打印机安装**：这是最常见的提权理由，现代操作系统与管理平台都提供了不需要管理员权限的部署方式，应提前配置好。

**第四步：处理本地管理员账号本身。** 即使日常用户不是管理员，机器上仍有内置管理员账号。三条要求：**每台设备的本地管理员密码必须唯一**（共享密码意味着一台被攻破全部沦陷，这是横向移动的经典路径）；密码定期自动轮换；取用密码的动作被审计。Windows 环境可用系统内置的本地管理员密码解决方案实现，macOS 与 Linux 也有对应的管理平台能力。

### 用数据说服而非用原则说服

收权项目最常见的卡点是"业务方说需要"。与其争论原则，不如用数据把讨论收敛到具体场景。下面这段代码演示如何从终端遥测中提取"用户实际使用管理员权限做了什么"，从而把一个笼统的需求拆成可逐条解决的清单。

```python
"""本地管理员权限使用分析：把"我需要管理员权限"拆解为具体动作。

events: 提权事件记录，字段
  host, user, timestamp, action_type, target, source(agent|uem|manual)
action_type 取值示例：
  install_software / driver_install / service_control /
  registry_write_hklm / network_config / printer_install / unknown
"""
from collections import Counter, defaultdict

# 已有替代方案的动作类型 -> 替代方案标识
HAS_ALTERNATIVE = {
    "install_software": "self-service-portal",
    "printer_install": "managed-printer-deploy",
    "driver_install": "uem-driver-package",
    "network_config": "uem-network-profile",
}

# 这些动作即使有需求也不应下放到普通用户
NEVER_DELEGATE = {"service_control", "registry_write_hklm"}


def analyse(events):
    per_user = defaultdict(Counter)
    for e in events:
        per_user[e["user"]][e["action_type"]] += 1

    findings = []
    for user, counter in per_user.items():
        total = sum(counter.values())
        covered = sum(c for a, c in counter.items() if a in HAS_ALTERNATIVE)
        blocked = sum(c for a, c in counter.items() if a in NEVER_DELEGATE)
        unknown = counter.get("unknown", 0)

        if total == covered:
            verdict = "可直接收权：全部动作已有自助替代方案"
        elif blocked > 0:
            verdict = "需单独评估：存在不应下放的高风险动作"
        elif unknown > total * 0.2:
            verdict = "需补充采集：未识别动作占比过高"
        else:
            verdict = "可收权并配置按需提权：少量特殊动作"

        findings.append({
            "user": user,
            "total_actions": total,
            "covered_by_alternative": covered,
            "must_not_delegate": blocked,
            "unknown": unknown,
            "verdict": verdict,
            "top_actions": counter.most_common(3),
        })

    findings.sort(key=lambda x: (-x["must_not_delegate"], -x["total_actions"]))
    return findings


def rollout_waves(findings):
    """按可收权难度分批，先做零阻力的一批以积累经验与信任。"""
    waves = {"wave1_no_friction": [], "wave2_needs_jit": [], "wave3_case_by_case": []}
    for f in findings:
        if f["verdict"].startswith("可直接收权"):
            waves["wave1_no_friction"].append(f["user"])
        elif f["verdict"].startswith("可收权并配置按需提权"):
            waves["wave2_needs_jit"].append(f["user"])
        else:
            waves["wave3_case_by_case"].append(f["user"])
    return waves
```

怎么读这段代码。核心思路是**把"需不需要管理员权限"这个二元问题，换成"这些具体动作各自有没有替代方案"**。经验上，大多数用户的提权动作集中在装软件与装打印机这两类，而这两类都有成熟的免提权替代方案——把这部分识别出来，`wave1` 往往能覆盖相当大比例的用户，且这批用户收权后不会产生任何投诉，这为后续更难的批次积累了内部信任。

`unknown` 占比的检查是一个诚实性设计：如果超过两成的动作无法归类，说明遥测采集不足，此时的分析结论不可信，应先补数据而不是硬推。这比给出一个看起来完整但实际站不住的清单更负责任。

`NEVER_DELEGATE` 集合体现了一条边界：服务控制与系统级注册表写入即使有业务需求也不应通过永久权限满足，只能走按需提权并留痕——因为停用安全代理、建立持久化都要经过这两类动作。

### 需要提前说明的两件事

**第一，UAC 提示不是安全边界。** 一个被加入本地管理员组的用户，其运行的程序可以通过多种方式绕过 UAC 提示获得完整权限——这一点微软官方文档已明确说明。因此"用户是管理员但有 UAC 保护"并不构成防护，唯一有效的是**不给管理员权限**。

**第二，收权不解决所有问题，但改变攻击成本。** 非管理员用户仍可能被窃取当前用户凭证、仍可能在用户上下文中运行恶意程序、仍可能访问其有权访问的数据。收权阻断的是提权、驱动加载、防护软件停用、以及大部分凭证转储手法——它把攻击者从"立刻拿到机器完全控制权"变成"需要额外找一个提权漏洞"，这个额外步骤本身就是检测机会。

## 15.5.7 终端凭证保护

### 攻击者要的从来不是这台机器

绝大多数终端沦陷不是目标本身，而是**取凭证的手段**。一台办公终端上可能存在的凭证包括：当前登录用户的凭证材料、缓存的域凭证、浏览器保存的密码与会话 Cookie、各类客户端保存的令牌、脚本与配置文件里的明文口令、以及最有价值的——本地管理员口令（若全企业相同）。

因此终端防护中有一组专门针对凭证的控制，它们的共同特点是**成本低、对用户几乎无感、但直接抬高攻击成本**：

| 控制 | 作用 | 落地注意 |
|------|------|---------|
| 凭证隔离机制（虚拟化保护） | 让凭证材料无法被普通内存读取手法获取 | 需要硬件支持，老旧设备可能不满足；与部分虚拟化软件冲突 |
| 认证子系统保护 | 阻止未签名代码注入认证进程 | 部分老旧安全软件会因此无法工作，需先兼容性验证 |
| 限制缓存的域凭证数量 | 减少离线可破解的凭证 | 设为 0 会导致断网无法登录，通常设 1 至 2 |
| 禁用旧版认证协议与明文协议 | 消除可被降级利用的路径 | 需先排查依赖旧协议的老系统 |
| 特权账号限制登录范围 | 域管理员不得登录普通终端 | **最重要的一条**，见下文 |
| 浏览器凭证同步策略 | 禁止企业账号同步到个人浏览器配置 | 需与浏览器管理策略配合（见 15.5.8） |

### 分层管理：这是终端与身份的交界

"域管理员不得登录普通终端"这条规则的重要性怎么强调都不为过。它的逻辑是：一旦高权限账号在一台低安全等级的机器上登录，它的凭证材料就出现在那台机器的内存里，那台机器一旦被攻陷，攻击者直接获得高权限。这条路径是绝大多数域接管事件的核心环节。

对应的实践是把账号与设备分层：最高权限账号只能在专用管理终端上使用，中间层管理账号只能登录服务器，普通账号只能登录办公终端；跨层登录在策略上被拒绝，且尝试跨层登录本身就是高优先级告警。这项工作需要身份团队与终端团队协同——终端侧负责限制登录，身份侧负责账号分层，任何一侧单独做都不完整。

**一个常见的实施顺序错误**是先建了专用管理终端，却没有在普通终端上拒绝高权限账号登录。结果是管理员在方便的时候还是用自己的办公机操作，专用终端沦为摆设。**拒绝登录的策略必须与专用终端同时上线**，否则新流程不会被采纳。

## 15.5.8 浏览器与扩展治理

### 浏览器已经是最重要的应用运行环境

企业业务大量迁到 SaaS 之后，员工日常接触数据的界面主要是浏览器。这带来两个后果：**凭证钓鱼的落地点在浏览器**，**数据外带的通道也在浏览器**。而在很多企业里，浏览器是完全不受管的——用户自己下载安装、自己登录个人账号同步、自己装任意扩展。

浏览器管控的三个层次：

**层次一：受管配置。** 通过企业策略统一下发浏览器配置，包括：禁止使用个人账号同步企业配置、强制安全更新、禁用不安全的旧协议与内容、配置企业根证书、设置默认搜索与主页、开启安全浏览功能。这一层成本低、几乎无感，应作为标配。

**层次二：扩展治理。** 浏览器扩展是一个被严重低估的攻击面——它可以读取所有页面内容、拦截表单输入、访问 Cookie。一个被收购或被劫持的合法扩展，等于在每个安装它的员工浏览器里植入了监听器。可行的策略是**从"允许任意扩展"改为"允许清单"**：预先审核并允许一批常用扩展，其余需申请。审核要点包括：开发者身份、权限申请范围（要求"读取和更改所有网站上的数据"的扩展需要特别审慎）、更新历史、是否发生过所有权变更。

**层次三：企业浏览器或浏览器隔离。** 对高风险场景（访问未分类站点、承包商访问、高敏数据操作），可以使用具备额外管控能力的企业浏览器，或远程浏览器隔离（页面在远端渲染，本地只接收画面）。后者能有效阻断浏览器漏洞利用与恶意下载，代价是体验与成本。

### 与其他控制的关系

浏览器治理与 15.7 的 Web 访问控制是互补的：**SWG 管的是"能访问哪些站点"，浏览器管控管的是"在浏览器内部能做什么"**。加密流量比例上升后，网络侧能看到的信息越来越少，而浏览器侧能拿到的是明文——这使得浏览器成为越来越重要的策略执行点。同时它也是数据防护的关键位置：复制粘贴、打印、下载、截屏的控制在浏览器层比在网络层更精确（相关策略见 10.3）。

**一条容易被忽略的检查**：企业里有多少台终端安装了两个以上的浏览器？非主力浏览器往往完全不受管理策略覆盖——策略只下发给了主力浏览器，而员工用另一个浏览器就绕过了全部控制。这项检查通常能查出可观的缺口。

## 15.5.9 外设与 USB 管控

### 分级而非一刀切

"禁用 USB"在多数企业行不通——键鼠、加密狗、会议设备、生产设备、办公场景的合法需求真实存在。可行的是按设备类别与场景分级：

| 设备类别 | 建议策略 | 说明 |
|---------|---------|------|
| 大容量存储（U 盘、移动硬盘） | 默认只读或禁止；按需授权 | 数据外带与载荷投递的主要通道 |
| 手机与相机（MTP/PTP） | 默认禁止数据传输，允许充电 | 常被用作绕过存储管控的手段 |
| 键盘鼠标（HID） | 允许，但对"新出现的键盘"告警 | 应对伪装成键盘的攻击设备 |
| 网络适配器（USB 网卡） | 默认禁止 | 可用于绕过网络管控、建立旁路通道 |
| 光驱与虚拟光驱 | 禁止挂载可执行内容 | ISO 挂载是常见投递手段 |
| 打印与扫描 | 允许 | 低风险 |
| 无线接口（蓝牙、外接 Wi-Fi） | 按岗位限制 | 数据外带的隐蔽通道 |

**HID 一行值得强调。** 伪装成键盘的攻击设备（插入后自动"打字"执行命令）无法通过存储管控拦截，因为它根本不是存储设备。对应的控制是：对新连接的键盘类设备产生告警或要求确认，并在高敏岗位上限制 HID 设备的即插即用。这项控制成本低，但覆盖了一类完全绕过存储策略的攻击。

### 一个失败驱动的细节

一家制造企业禁用了所有 U 盘存储，执行了两年，自认为数据外带风险已被消除。一次内部调查发现，生产部门为了在车间与办公室之间传数据，普遍使用手机通过 USB 连接电脑传文件——设备类别是 MTP 而非大容量存储，完全不在管控策略覆盖范围内。更进一步的检查还发现，部分工位使用了 USB 转以太网适配器接入了一条未受管的网络。

这个案例说明两件事。第一，**USB 管控必须按设备类别全面覆盖，只堵存储类等于没堵**。第二，也是更根本的：**当合法需求没有被满足时，用户一定会找到绕过方式，而绕过方式往往比原方式风险更高**。这家企业后来的解决办法不是继续加码禁止，而是在车间部署了受管的文件交换终端，同时把 MTP 与 USB 网卡纳入管控——先给出路，再收口子。

### 实施机制与三个细节

设备管控的实现有两条路径：**操作系统层的设备安装限制**（按设备类别标识或硬件 ID 决定是否允许驱动安装，粒度粗但可靠）与**终端防护代理的设备控制模块**（可按厂商、型号、序列号做精细策略，并能与内容检测联动）。多数企业两者并用：前者做兜底，后者做精细例外与审计。

三个容易踩的细节：

**细节一：策略生效时机。** 设备安装限制通常只在设备"首次安装驱动"时生效，对已经装过驱动的设备可能不起作用。上线时需要一并清理已安装的设备记录，否则老设备照常可用，而你以为策略生效了。

**细节二：白名单粒度选序列号还是型号。** 按型号放行意味着任何同型号设备都能用（包括员工自己买的同款）；按序列号放行最精确但维护量大。折中做法是企业统一采购一批加密 U 盘，按型号 + 加密状态放行，既可管理又不必逐个登记。

**细节三：告警要能定位到人。** "某终端接入了未授权存储设备"这条告警若不能关联到使用人与设备信息，处置价值有限。日志应包含设备厂商、型号、序列号、接入时间、以及随后的文件操作，这样才能判断是误接还是有意为之。

### 与 DLP 的分工

外设管控与数据丢失防护（DLP）在 USB 场景上重叠，需要分清职责：**外设管控回答"这个设备能不能用"，DLP 回答"这些数据能不能出去"**。两者应当配合：外设管控做粗粒度的设备准入（例如只允许企业配发的加密 U 盘），DLP 做内容级判断（例如允许写入但敏感文件需要加密或阻止）。只做其中一个都有明显缺口——只做设备管控，用户可以往允许的设备里拷任何东西；只做内容检测，用户可以用未受管的设备绕过（DLP 策略设计见 10.3）。

### 落地经验

- **强制加密写入是最平衡的策略**：允许使用 U 盘，但写入的数据自动加密，只有企业设备能读。既保留了便利，又解决了 U 盘丢失导致的数据泄露。
- **例外要有到期日**：出差、现场支持、与外部交换数据的临时需求应当限时授权而非永久开放。
- **告警比阻断更早可用**：在还没准备好阻断时，先把"大容量存储设备接入"做成日志与告警，能立刻获得可见性，也为后续策略提供数据基础。
- **别忘了服务器与生产设备**：生产环境的服务器、工控终端、自助终端上的 USB 口往往完全不受管，而它们的物理接触门槛可能比办公区更低。

## 15.5.10 全盘加密与密钥托管

### 加密本身不难，难的是运营

全盘加密的技术方案在主流平台上都已成熟并内置，选型与部署考量（全盘加密、卷加密、文件加密的适用差异与密钥管理要求）有公开指南可循[4]。真正会出问题的是运营环节：

**问题一：覆盖率的统计口径。** "加密率 99%"这个数字需要追问：分母是什么？失联超过 30 天的设备算不算在内？加密进行中的算不算已加密？只加密了系统盘、数据盘未加密的算不算？口径不清的覆盖率是最常见的自欺来源（口径问题在 15.6 与 15.11 会反复出现）。

**问题二：恢复密钥的托管与取用。** 恢复密钥必须集中托管（通常在身份目录或管理平台中），否则用户忘记密码或设备故障时数据直接丢失。同时托管本身引入新风险：**谁能查看恢复密钥**。这个权限应当受严格限制并全程审计——能读取全公司恢复密钥的账号，其权限等同于能读取全公司终端数据。

**问题三：加密状态与合规的脱节。** 设备"启用了加密"不等于"当前处于加密保护状态"。休眠与睡眠状态下密钥可能仍在内存中；未设置开机前认证时，攻击者拿到设备可以直接启动到登录界面并尝试其他攻击面。对高敏岗位应要求开机前认证并禁用睡眠时保留密钥。

**问题四：设备退役时的处理。** 加密最有价值的场景之一是设备退役——只要密钥被销毁，磁盘内容即不可读，无需物理销毁。但这要求退役流程中明确执行密钥销毁并留证，而多数企业的退役流程只有"擦除"这一步，且擦除是否成功无人验证。

### 加密之外还要考虑的两件事

**第一，加密保护不了正在运行的系统。** 全盘加密只在设备关机或处于休眠且密钥已卸载时才真正提供保护。一台正常运行、已登录的笔记本被拿走，加密不提供任何帮助。因此加密需要与自动锁屏、休眠策略、以及丢失后的远程擦除配合。对高敏岗位应缩短锁屏时间并要求合盖即休眠。

**第二，加密与备份、取证、恢复的交互。** 加密会影响：磁盘级备份的可用性（备份的是密文，恢复需要密钥）、故障硬盘的数据救援（往往变成不可能）、以及事件调查中的取证获取（需要密钥或在系统运行时采集）。这些流程都需要在启用加密时同步调整，而不是等到第一次数据恢复失败时才发现。取证团队应当有明确的、经过审批的密钥获取路径。

### 落地检查清单

- 全部受管终端（含服务器本地盘、外接工作盘）启用加密
- 恢复密钥 100% 成功托管（**这项要单独度量**，托管失败的设备是定时炸弹）
- 恢复密钥取用有审批与审计
- 高敏岗位启用开机前认证
- 退役流程包含密钥销毁并留证
- 定期抽查：随机取几台设备验证加密状态与密钥可用性

## 15.5.11 终端基线与合规

### 基线的三个层次

- **配置基线**：操作系统与常用软件的安全配置项（来自 CIS Benchmark[2]、厂商加固指南、DISA STIG[3] 等）。数量大、需要裁剪。
- **能力基线**：必须安装并正常运行的安全组件（EDR、加密、UEM 代理、日志采集）。数量少、最关键。
- **状态基线**：当前必须满足的运行状态（补丁在 SLA 内、无高危漏洞、防篡改开启、无未授权本地管理员）。

多数企业把大量精力花在第一层的条目数上（"我们实施了 300 项 CIS 配置"），而第二层与第三层的缺口才是事件中真正被利用的。**能力基线应当是硬门禁：不满足就不允许访问企业资源**，这需要与条件访问集成（见 10.5.2）。

### 一份可直接用的高价值配置清单

与其从数百条基准里挑，不如先把下面这些"高价值、低争议"的配置做掉。它们的共同特征是：直接对应真实攻击路径、对业务影响小、且大多可以一次性配置后长期不变。

| 配置项 | 阻断的攻击环节 | 典型阻力 |
|--------|--------------|---------|
| 禁用宏（来自互联网的文档） | 邮件投递的第一跳 | 低，主流平台已默认 |
| 禁止挂载来自互联网的光盘镜像 | 绕过下载标记的投递手法 | 低 |
| 脚本引擎受限模式 + 脚本块日志 | 无文件攻击与横向移动 | 中，需处理运维脚本 |
| 禁用旧版脚本宿主与旧协议 | 降级利用与遗留攻击面 | 中，需排查老系统依赖 |
| 关闭自动播放与自动运行 | 外设投递 | 低 |
| 禁止普通用户安装驱动 | 恶意驱动加载与防护绕过 | 中，需打印机等场景配套 |
| 限制远程管理服务的入向 | 横向移动的主要通道 | 中，需与运维协调 |
| 主机防火墙默认拒绝入向 | 终端之间的横向移动 | **低，但极少被做** |
| 禁止本地账号远程登录 | 本地管理员口令复用的横向路径 | 低 |
| 强制安全启动与固件密码 | 引导阶段的篡改与绕过 | 中，老设备可能不支持 |

**"主机防火墙默认拒绝入向"是这一组里性价比最高的一条。** 办公终端之间几乎没有任何需要互相连接的合法业务，而终端到终端的横向移动却是勒索软件扩散的主要方式。在终端上开启主机防火墙并默认拒绝入向连接（只放行远程支持工具所需的特定来源），成本几乎为零，效果相当于给每台终端做了微隔离。这条控制在实践中被忽略的比例高得惊人——它不需要任何采购，却常年不做。

### 裁剪：不要全量照搬

行业基准包含数百项配置，全量实施会产生大量业务影响与运维负担，且其中相当一部分对当代威胁的边际价值很低。裁剪的方法：

1. 按"该配置阻断的攻击路径在本企业是否真实存在"筛选，而非按条目数量追求覆盖率。
2. 保留所有与凭证保护、远程执行、脚本引擎、旧协议禁用相关的项——这几类对攻击链的影响最直接。
3. 对影响业务的项做记录并说明理由，形成本企业的基线版本，而不是每次审计都重新解释一遍。
4. 基线版本化管理，每次操作系统大版本更新后复核。

### 合规率的诚实统计

终端合规率是最容易被粉饰的指标，几种常见的失真：

- **分母排除失联设备**。三个月没上线的设备不算不合规，只算"离线"——而它可能正被攻击者控制着。正确做法是失联设备单列并计入风险，而不是移出分母。
- **只统计在线设备的瞬时状态**。应统计一段时间内的持续合规，而不是某一刻的快照。
- **把"策略已下发"当作"策略已生效"**。管理平台显示已推送，不代表终端实际应用成功。需要从终端侧回读实际状态。
- **豁免设备不计入**。长期豁免的设备（老旧系统、专用设备）应当在报表中显式呈现，而不是消失。

## 15.5.12 macOS 与 Linux：不能用 Windows 的方式管

### macOS 的关键差异

**权限模型不同。** macOS 的隐私保护机制（对摄像头、麦克风、屏幕录制、文件目录、完全磁盘访问的授权）要求用户显式同意，这意味着**安全代理的部署必须通过管理平台预先授权**，否则会弹出一堆用户看不懂的提示，而用户拒绝之后代理就是残废的。这是 macOS 部署中最常见的失败——代理"装上了"但没有完全磁盘访问权限，实际什么也看不到。

**内核扩展已被淘汰。** 现代 macOS 上安全产品必须使用系统提供的端点安全框架，能力边界由系统定义。这带来的实际后果是各厂商在 macOS 上的能力趋同且弱于 Windows，选型时不要期待对等的功能。

**系统完整性保护带来的约束。** 系统目录不可写、部分操作即使 root 也不被允许，这提升了安全性，但也意味着一些 Windows 上的检测手法在 macOS 上无法实现。

**管理通道不同。** macOS 的管理依赖设备管理协议与自动注册机制，与 Windows 的域管理是完全不同的体系。企业若把 macOS 简单纳入 Windows 的管理框架，会发现大量策略根本不生效（统一终端管理见 15.6.1）。

**常被忽略的一点：macOS 用户通常是本机管理员。** 研发与设计岗位大量使用 macOS，且默认账号就是管理员。15.5.6 的收权工作在 macOS 上同样重要，且需要配套的按需提权工具。

### Linux 服务器的关键差异

**代理的兼容性风险更高。** 内核模块式的代理与内核版本强相关，升级内核可能导致节点无法启动——这是真实发生过的生产事故。基于 eBPF 的方案兼容性更好，但对内核版本有下限要求，老旧发行版可能不支持。**部署前必须在与生产完全一致的内核版本上验证**，且升级代理要走灰度。

**性能敏感度更高。** 数据库、消息队列、高并发服务对额外的系统调用开销敏感。需要在压测环境实测，并对高负载节点单独调优（例如降低采集频率、缩减采集范围）。

**容器场景需要单独设计。** 主机上的代理能否看到容器内的进程、能否关联到容器与镜像身份、是否与容器运行时冲突，这些都需要验证。容器工作负载的运行时保护有专门的方案（见 5.4）。

**基线与合规工具链不同。** Linux 的配置基线通常通过配置管理工具（Ansible、Puppet、Chef）或不可变镜像实现，而不是通过终端管理平台推送策略。这意味着 Linux 的合规状态数据往往不在终端管理平台里，需要单独接入统一视图。

### 三个平台的能力落差需要被显式承认

一份诚实的能力矩阵通常长这样（具体取决于产品，需要以本企业实测为准）：

| 能力 | Windows | macOS | Linux 服务器 |
|------|---------|-------|------------|
| 行为遥测与检测 | 完整 | 中等（受框架限制） | 中等（取决于采集机制） |
| 自动阻断 | 完整 | 中等 | 有限，常因怕影响业务而不开 |
| 应用控制 | 内置机制成熟 | 有限（依赖签名与公证机制） | 需自建（不可变镜像更实际） |
| 外设管控 | 完整 | 有限 | 基本不涉及 |
| 全盘加密与密钥托管 | 成熟 | 成熟 | 需自行设计（服务器场景不同） |
| 本地管理员治理 | 有成熟方案 | 需第三方或自建 | 由账号与 sudo 策略承担 |
| 隔离与远程取证 | 完整 | 中等 | 有限 |

**把这张表放进管理层汇报，比一个"终端防护覆盖率 98%"的数字诚实得多**。它同时也回答了一个常见质疑："既然我们买了同一个产品，为什么 macOS 上还是出了问题"——因为产品在不同平台上根本不是同一套能力。

对能力落差的补偿手段，通常不是继续在终端上加码，而是**用其他层的控制补齐**：macOS 与 Linux 上做不到的执行控制，用更严格的网络分段、更强的身份与特权访问控制、更完善的日志采集来部分弥补。这是纵深防御的实际含义——知道哪一层弱，然后在别处补上，而不是每一层都追求最强。

### 一条通用建议

不要用一套指标衡量三个平台。**分平台统计覆盖率、合规率与能力状态**，并在报表中显式呈现各平台的能力差异。把 macOS 与 Linux 混入总体覆盖率，会掩盖这两个平台上的真实缺口——而攻击者非常清楚哪个平台防护更弱。

## 15.5.13 服务器终端的特殊性

服务器与办公终端共用一套代理，但运营方式应当不同：

| 维度 | 办公终端 | 服务器 |
|------|---------|--------|
| 变更频率 | 高（用户自主行为多） | 低（受变更流程约束） |
| 白名单可行性 | 中 | **高**，应优先做 |
| 阻断策略风险 | 影响单个用户 | 可能影响整个业务 |
| 例外来源 | 用户需求 | 应用兼容性、性能 |
| 响应时的隔离 | 可直接隔离 | 需评估业务影响，通常先隔离流量不停机 |
| 本地管理员 | 应收敛到零 | 由运维账号体系管理，走特权访问流程 |

三条服务器专属的建议：

**其一，服务器上的阻断策略要比办公终端更保守地上线，但最终应当更严格。** 上线过程需要灰度与变更窗口，但因为服务器软件集合稳定，最终能达到的策略强度反而高于办公终端。

**其二，服务器的"用户"是运维人员，控制点在特权访问而非终端本身。** 服务器上的可疑行为大多来自运维操作或被盗用的运维凭证，因此终端检测需要与跳板机、特权访问日志关联才有判断力（见 15.10.3）。

**其三，别忘了那些"不是服务器的服务器"。** 生产环境里总有一些工控机、自助终端、数字标牌、会议室主机、打印服务器——它们运行着老旧操作系统、无人负责、常年不重启、也没装任何代理。这类资产是终端防护最大的盲区，处理办法通常不是给它们装代理（往往装不上），而是把它们隔离并包围（见 15.2.1 的约束一）。

### 服务器上的两类特殊工作负载

**其四，虚拟化宿主机与超融合节点。** 这类节点承载着几十上百台虚拟机，被攻陷的影响面远大于单台服务器，但它们往往因为"厂商不支持装第三方代理"或"怕影响性能"而完全裸奔。可行的替代控制是：把管理面严格隔离到带外管理网（见 15.10.2）、管理账号走特权访问流程、配置基线固化并检测漂移、以及把宿主机的日志接入监控。**不能装代理不等于不能防护**，但需要显式列出替代控制，而不是默认它安全。

**其五，构建与制品服务器。** CI/CD 节点是攻击者的高价值目标——攻陷它可以把恶意代码注入所有下游产物。这类服务器的特点是天然要执行大量未知代码（这正是它的工作），因此应用控制在这里不适用。替代思路是：把构建过程放在一次性的、每次重建的环境里（构建完即销毁），限制构建节点的网络出向与凭证访问范围，并对制品做签名与验证（供应链侧的完整控制见第 7 章相关内容）。

### 服务器防护常见的三个自欺

**自欺一：把"服务器在机房里"当作安全边界。** 服务器的攻击面主要来自网络与凭证，物理位置几乎不提供保护。这个观念会导致服务器上的终端防护长期被视为可选项。

**自欺二：用补丁合规率代替终端防护。** 打了补丁只解决已知漏洞，解决不了凭证窃取、合法工具滥用、配置错误被利用。两者是不同维度的控制。

**自欺三：认为服务器"没人用所以不会中招"。** 服务器上的初始立足点大多来自暴露的服务、被盗的运维凭证，或从办公终端横向移动过来，很少由用户操作产生。没有交互式用户反而意味着任何交互式登录都值得怀疑——这实际上是一个很好的检测机会，前提是有人在看。

## 15.5.14 终端侧的响应准备

终端防护的最后一环是"出事之后能做什么"。很多企业在事件中发现：能看到告警，却无法在几分钟内隔离机器、无法采集内存、无法确认同批感染范围。这些能力必须提前准备并演练，事到临头才配置一定来不及。

### 需要提前具备的六项能力

| 能力 | 提前准备的内容 | 常见缺口 |
|------|--------------|---------|
| 网络隔离 | 权限授予到值班人员；隔离后仍可远程取证 | 只有管理员能操作，夜间无人 |
| 批量查询 | 能在全网快速搜索指定文件哈希、进程、注册表项、网络连接 | 查询超时或数据已过留存期 |
| 远程取证采集 | 内存与关键工件的采集脚本已就绪并测试过 | 需要临时写脚本，耗时数小时 |
| 远程执行 | 可批量执行处置动作，且该能力本身受严格授权与审计 | 权限过宽（能力越强越怕滥用） |
| 用户通知 | 隔离时向用户展示明确说明与联系方式 | 用户以为是网络故障，自行重装 |
| 回滚与重建 | 标准重装镜像、数据恢复流程、恢复后的加固基线 | 重建后的机器沿用旧配置，重复被打 |

**"隔离后仍可远程取证"这一条最容易被忽视。** 有些产品的隔离是彻底断网，包括与管理平台的通信——这样一来机器虽然安全了，但你也无法再从它身上取任何证据，只能派人到现场。正确的隔离应当保留与管理平台的通道，阻断其余全部流量。选型时需要实测这一点。

**"用户通知"是一个被低估的环节。** 一台被静默隔离的机器，用户的第一反应是找 IT 报网络故障，第二反应是自己重启、重装、或者换一台机器继续工作——每一个动作都在破坏证据或扩大影响。隔离时在屏幕上显示明确说明（发生了什么、请不要关机、请联系谁），能显著改善后续处置质量。

### 与整体响应流程的衔接

终端侧的这些动作只是响应流程的一部分，需要与事件分级、通报、取证保全、恢复验证等环节衔接（完整流程见 11.5）。这里要强调的是一条容易被跳过的准备工作：**演练**。把上述六项能力串起来做一次桌面推演加实机演练，通常会暴露出三到五个此前完全没意识到的断点——权限不在值班人员手上、脚本在最新系统版本上跑不通、采集出的数据没有地方存、隔离解除需要走一个两天的审批。这些断点在真实事件中每一个都会造成小时级的延误。

## 15.5.15 验证与度量

### 验证方法

- **策略生效验证而非配置检查。** 在真实终端上执行受控的测试行为（模拟凭证访问、模拟从临时目录执行、模拟外设写入），验证是否真的被阻断。控制台显示"策略已应用"不等于策略生效。
- **防篡改实测。** 用本地管理员权限尝试停用代理、安全模式启动后卸载、删除关键文件，验证阻止与告警。
- **覆盖率交叉核对。** 用资产系统、身份日志、网络接入记录、UEM 数据交叉比对终端防护覆盖率，找出"在网但无代理"的设备（多源融合方法见 15.11.2）。
- **端到端响应时延实测。** 从触发高危行为到有人开始处置的实际耗时。
- **红队验证执行控制。** 让红队尝试在受控终端上落地并执行任意程序，验证应用控制的实际强度（见 12.2）。

### 运行关注指标

| 指标 | 定义 | 参考目标 | 说明 |
|------|------|---------|------|
| 代理覆盖率 | 有代理且健康 / 应装设备总数 | ≥ 98% | **分平台统计**，分母含失联设备 |
| 代理健康率 | 心跳正常且策略最新 | ≥ 98% | 装了但不健康与没装等价 |
| A 档策略开启率 | 高置信阻断策略处于阻断态 | 100% | 低于 100% 需逐项说明 |
| B 档策略开启率 | 攻击面削减类处于阻断态 | 逐季提升 | 按规则逐条统计更有意义 |
| 排除项数量与宽度 | 排除项总数、其中宽泛排除数 | 持续下降 | 宽泛排除应趋近 0 |
| 本地管理员比例 | 日常用户为本机管理员的终端占比 | < 5% | 终端安全最有价值的单一指标 |
| 应用控制覆盖率 | 处于强制模式的终端占比 | 分层统计 | 第一档应接近 100% |
| 加密与密钥托管率 | 已加密且密钥托管成功 | 100% | 托管失败要单独列 |
| 高危告警处置时延 | 从产生到开始处置 | 目标依 SLA | 反映链路是否真的闭环 |
| 失联设备数与时长 | 超过阈值未上线的设备 | 持续下降 | 不得移出分母 |

**本地管理员比例是这张表里最值得优先改善的一项。** 它不需要采购、不依赖厂商、效果直接作用于攻击链的关键环节，且它的改善会同时提升其他所有控制的有效性——因为大部分终端防护的绕过手法都以本地管理员权限为前提。

### 一个可用的自评问题清单

在没有条件做完整评估时，下面九个问题能快速定位终端防护的真实水位。每个问题都可以在半天内查清，且答案没有含糊空间：

1. 高置信阻断策略（勒索行为、凭证转储）现在是阻断还是仅检测？
2. 攻击面削减类规则里，有几条处于阻断状态？
3. 排除项总共多少条，其中有几条指向普通用户可写的目录？
4. 日常用户是本机管理员的终端占比是多少？
5. 全部终端的本地管理员密码是否唯一且定期轮换？
6. 从触发一条高危告警到有人开始处置，实测耗时是多少？
7. macOS 终端上的代理是否拿到了完全磁盘访问权限？
8. 失联超过 30 天的终端有多少台，它们在合规率的分母里吗？
9. 管理平台的管理员账号有多少个，是否与日常办公账号分离？

这九个问题中若有三个以上答不上来或答案不理想，那么无论覆盖率数字多好看，终端防护的实际水位都值得重新评估。

### 常见误区

- **把覆盖率当作防护水位**。98% 覆盖率 + 全部策略仅检测，等于 0 防护。
- **只看 Windows**。macOS 与 Linux 的能力缺口被总体指标掩盖。
- **排除项无治理**。它是唯一不产生日志的安全洞，且攻击者主动寻找。
- **忽略管理平台自身的安全**。它是能一键关掉全公司防护的系统。
- **把执行控制无限期推迟**。应用控制与本地管理员收敛难度高，但它们是唯一能改变"攻击者能做什么"的控制，其余都只是改变"能不能被发现"。
- **继续用样本级检出率评估防护水位**。AI 把"每个目标一份独立样本"的成本压到接近零之后，这个数字对静态判定层已经失去参考意义，回归口径要换成同一 TTP 的 N 个变体检出率（见 15.5.1）。
- **默认打开控制台的 AI 自动处置**。告警字段由攻陷主机上的攻击者写入，一个能触发隔离主机的 AI 助手就是一条可被远程触发的拒绝服务通道（见 15.5.2）。

### 一条关于推进节奏的建议

上表中的多数指标不会在一个季度内显著改善，这会造成汇报上的困难——终端安全的改进是缓慢且不性感的。一个有效的做法是**把长期指标与短期里程碑分开呈现**：长期看本地管理员比例、应用控制覆盖率这类结构性指标；短期看"本季度把 3 条 B 档策略推进到阻断""本季度清理了 40 条宽泛排除项""本季度 wave1 的 800 名用户完成收权"这类可交付的动作。前者说明方向，后者证明在动。

同样重要的是**不要在同一个季度同时推进多项对用户有感的变更**。收本地管理员权限、上应用控制、收紧 USB 三件事若同时落地，用户感受到的是"IT 突然把一切都锁死了"，反弹会集中爆发并可能导致全部回退。分季度推进、每次只动一项、每项都配好替代方案，是这类工作能走完的现实节奏。

## 15.5.16 本节小结

终端防护的典型失效不是能力缺失，而是**能力全部处于最保守的默认档位**。EDR 与 EPP 是两组独立策略而非一个产品，前者发现、后者阻断，且后者在无人值守时是唯一还在工作的一层。策略推进应当分档：高置信阻断项部署第一天就开，攻击面削减类观察数周后逐条开，可疑工具类先做白名单化，弱信号长期保持检测。

排除项是终端体系里最危险的配置——它不产生日志、不引发告警、几乎从不被复查，而攻击者专门寻找它。治理纪律与防火墙规则相同：最精确的维度、责任人、到期日、可被普通用户写入的排除路径必须清零。

三层能力中，第三层（执行控制）收益最高也最少被做。其中**本地管理员权限收敛是整章投产比最高的单项**：不需要采购，主要成本是提供自助软件门户与按需提权这两个配套，而它直接切断了凭证转储、驱动加载、防护停用等一大类攻击手法。应用控制应从第一档（禁止从临时与下载目录执行）开始而不是从严格白名单开始，服务器白名单比办公终端容易且价值更高，很多企业的顺序反了。

macOS 与 Linux 不能用 Windows 的方式管：macOS 的隐私授权必须通过管理平台预先下发，否则代理形同虚设；Linux 的内核兼容性是真实的生产风险，必须在一致的内核版本上验证并灰度。分平台统计指标，不要让总体数字掩盖单平台的缺口。

凭证保护是终端与身份的交界，其中"高权限账号不得登录普通终端"这条规则的价值远超其实施成本——绝大多数域接管事件都经过这一环。浏览器则已经是最重要的应用运行环境与数据出口，而它在多数企业里完全不受管；扩展治理与受管配置是低成本高回报的补课项。

攻击侧接入大模型之后，需要调整的是评估口径而不是控制清单。载荷可以按目标批量变形，静态特征与已知家族聚类这一层持续贬值，行为规则与内存扫描的相对价值上升，而应用控制这类不看载荷长相的执行控制完全不受影响，相对价值反而更高。落到日常动作上有两条：把检出率回归的单位从"样本"换成"同一 TTP 的 N 个变体"，把 B 档攻击面削减规则的推进排到静态引擎调优之前。

与此同时，终端防护产品自己引入的 AI 组件是一个需要单独建模的新攻击面。控制台的自然语言查询与处置建议读取的是进程命令行、文件名、脚本内容这些由攻陷主机上的攻击者写入的字段，一个能触发"隔离主机"的助手就构成一条远程可触发的拒绝服务通道。采购阶段就要把六条要求写进合同：上下文字段可披露、AI 功能可整体与按角色关闭、建议与执行分离、权限继承发起人、交互全量审计不可删改、推理位置与数据流向可说明。

最后，管理平台本身是最高信任域资产。一个能推送策略、执行脚本、卸载代理的系统被攻陷，等于全公司终端防护被一键清零。同样地，隔离、批量查询、远程取证这些响应能力必须提前授权到值班人员并演练——事件发生时才发现权限不在手上，是最常见也最昂贵的准备不足。

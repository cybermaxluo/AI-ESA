# 15.10　混合与本地数据中心安全

一次红队演练的报告里，最短的一条攻击链只有三步：从办公网扫描发现一台服务器的管理控制器暴露在办公网可达的网段上；用厂商默认口令登录成功；通过管理控制器挂载虚拟光驱，引导一个临时系统，读取了该服务器的全部磁盘内容——**整个过程没有触碰操作系统，因此服务器上的所有终端防护、所有审计日志都没有产生任何记录**。

这台服务器承载的是一个核心数据库。它的操作系统打满了补丁、装了 EDR、配置了微隔离策略。而这些全部被绕过了，因为攻击者走的是另一条路：那块独立于操作系统运行、拥有完全硬件控制权、口令还是出厂默认值的管理控制器。

本地数据中心的安全有一个共同的失效模式：**注意力全部集中在操作系统与应用层，而承载它们的基础设施——管理控制器、交换机、机柜、固件——处于一种"没有人认为它是自己责任"的状态。** 它们不在补丁流程里、不在资产系统里、不在监控里，甚至不在网络拓扑图上。

云的兴起让这块的关注度进一步下降——预算与人才都在往云上走，而本地数据中心仍然承载着大量最关键的系统，且往往还要再运行五到十年。本节讲的就是这块"没人管的地方"该怎么管。

> 导读：15.10.1 讲机房逻辑分区与流量矩阵；15.10.2 是本节最重要的部分——带外管理网的设计与隔离；15.10.3 讲跳板机；15.10.4 讲网络设备加固与配置漂移检测；15.10.5 讲固件与设备生命周期；15.10.6 处理混合互联，即本地与云之间那条最容易两端不对称的链路；15.10.7 给出物理与环境安全的最小集。云侧的对应内容见 5.3 与 5.4。

## 15.10.1 机房逻辑分区与流量矩阵

### 分区的第一原则：管理面与业务面分离

数据中心的分区设计中，最重要的一条不是把业务系统分成几个区，而是**把"管理"与"业务"这两个平面彻底分开**。

一台服务器上有两类流量：业务流量（应用之间、应用与数据库之间）和管理流量（运维登录、配置下发、监控采集、备份传输）。它们的风险特征完全不同——管理流量的权限高、来源少、模式稳定；业务流量的权限低、来源多、模式复杂。把它们混在同一张网上，意味着任何一台被攻陷的业务服务器都能直接尝试访问所有设备的管理接口。

一个可操作的分区结构：

| 平面 | 承载 | 可达性要求 |
|------|------|-----------|
| 业务面 | 应用间流量、对外服务 | 按 15.2 的微隔离策略 |
| 存储面 | 存储网络、备份流量 | 与业务面隔离；备份目标不可被业务系统删除 |
| 管理面（带内） | 操作系统层的运维访问、配置管理、监控代理 | 仅来自跳板机与管理系统 |
| 管理面（带外） | 服务器管理控制器、交换机控制台、PDU、机房环境设备 | **完全独立，见 15.10.2** |
| 互联面 | 与云、与分支、与合作伙伴的链路 | 两端策略对称，见 15.10.6 |

### 流量矩阵：把"应该怎样"写下来

分区之后需要一张流量矩阵，明确每两个区之间允许什么。这张矩阵是 15.1.3 跨域策略矩阵在数据中心内部的细化，几个必须明确的格子：

- **业务面到管理面：一律拒绝。** 应用服务器没有任何理由访问交换机的管理接口或另一台服务器的管理控制器。
- **管理面到业务面：仅特定协议、仅从跳板机发起。** 运维需要登录服务器，但这条路径应当收敛到跳板机。
- **备份目标到任何地方：只接受写入，不主动发起。** 备份存储被攻陷或被用作跳板的路径由此切断。
- **存储面到互联网：完全禁止。** 存储设备的管理界面从不需要出网。
- **管理面到互联网：仅经代理访问厂商更新源。** 直连出网是一条常被忽略的通道。

**这张矩阵最容易被违反的地方是监控系统。** 监控需要访问所有区域的所有设备，于是它常常被配置成"能访问一切"，成为一个横跨所有分区的通道。正确处理是把监控拆成采集端与分析端：采集端部署在各区内、只做本区采集、单向把数据推送到分析端；分析端不主动连接任何被监控对象。这个改造有一定成本，但它消除了一个天然的跨区通道。

## 15.10.2 带外管理网：本节最重要的一件事

### 什么是带外，为什么必须独立

带外管理（Out-of-Band, OOB）指的是不依赖业务网络、不依赖操作系统就能访问设备的管理通道，包括：

- 服务器的管理控制器（各厂商名称不同，功能类似：独立处理器、独立网口、独立供电、可远程开关机、可挂载虚拟介质、可看到控制台画面）
- 网络设备的控制台口与专用管理口
- 存储设备、机架式 PDU、UPS、精密空调、门禁与环境监控
- 终端服务器（把多台设备的串口集中起来的设备）

**这类接口的权限高于操作系统。** 主流管理控制器普遍实现 IPMI 与 Redfish 两类接口规范[1][2]，其中 IPMI 的多项协议级弱点（如 RAKP 认证响应可离线破解）已被公开记录多年、且无法通过打补丁消除，只能靠网络隔离规避[3]。拿到服务器管理控制器就等于拿到了那台服务器的物理访问权——可以关机、可以从任意介质引导、可以读取磁盘、可以在操作系统完全无感知的情况下操作。因此它们的暴露等价于机房大门敞开。

### 设计要求

**要求一：物理或逻辑上完全独立的网络。** 带外管理网不应与业务网、办公网有任何路由可达。理想是独立的交换设备与布线；退而求其次是独立的 VLAN 且严格的策略隔离，但要注意——**仅靠 VLAN 隔离的带外网，其安全性取决于交换机配置不出错，而这类配置在多年运维中一定会出错**。对承载关键系统的机房，独立物理网络是值得的投资。

**要求二：唯一入口是跳板机。** 运维人员不能从办公终端直接访问带外网，必须经过跳板机（见 15.10.3）。带外网内部不应有到互联网的路由。

**要求三：默认口令必须全部更换，且每台唯一。** 管理控制器的默认口令是公开信息，且很多设备出厂时启用了默认账号。这项工作枯燥但必须做完——**做完 90% 等于没做**，攻击者只需要找到那 10%。口令应纳入特权凭证管理并定期轮换。

**要求四：启用并强制认证与加密。** 关闭不安全的旧管理协议，启用集中认证（把管理控制器接入企业认证体系而不是本地账号），启用会话加密，禁用不需要的服务。

**要求五：固件必须更新。** 管理控制器的固件漏洞可能允许未认证的远程代码执行，而它的权限高于操作系统；平台固件的保护、检测与恢复要求可参照平台固件韧性指南[4]。这类固件的更新极少被纳入补丁流程（见 15.6.5），是本地数据中心最大的单点缺口之一。

**要求六：应急可达性。** 带外网的价值之一是"业务网全挂时还能进去处理"。因此它需要有独立于业务网的接入方式——独立的互联网链路、独立的运营商、甚至蜂窝网络备份。同时这条应急通道本身必须强认证并全程审计，否则它就是一个后门。

### 分阶段落地：从零到有

多数企业不是"没有带外网"，而是"有一张名义上的管理 VLAN，实际上什么都能到"。从这个状态出发的推进路径：

**阶段一（1-2 个月）：摸清现状并止血。** 扫描全部管理接口，确认它们当前从哪些网段可达；立刻修改所有默认凭证；关闭管理接口上的不安全协议。这三件事不需要改动网络结构，可以立刻做，且能消除最大的一部分风险。

**阶段二（3-6 个月）：收敛可达性。** 在现有网络上加策略，把管理接口的可达来源收敛到跳板机与管理系统。此阶段需要先摸清"谁在合法地访问这些接口"（监控系统、备份系统、自动化工具），避免一刀切造成运维中断——方法与 15.2.4 的学习期一致。

**阶段三（6-18 个月）：结构性隔离。** 新建或改造为独立的带外网络，把管理接口迁入。这一步涉及布线与设备采购，通常与机房改造或设备更新周期结合进行，单独立项难度大。

**阶段四（持续）：纳入运营。** 固件补丁、凭证轮换、日志监控、新设备接入流程、定期可达性验证。

**这条路径的关键在于阶段一与阶段二不依赖阶段三。** 很多企业因为"没有预算做独立带外网"而什么都不做，实际上前两个阶段已经能消除大部分实际风险，且几乎不需要预算。

### 一份自查清单

| 检查项 | 通过标准 |
|--------|---------|
| 带外网与业务网的路由可达性 | 从任意业务服务器无法 ping 通任何管理控制器 |
| 带外网与办公网的路由可达性 | 从任意办公终端无法直接访问，必须经跳板机 |
| 默认口令 | 全量扫描确认无默认凭证，覆盖率 100% |
| 认证方式 | 接入企业认证体系，启用多因素 |
| 管理控制器固件版本 | 无已知高危漏洞，纳入补丁 SLA |
| 出网可达性 | 带外网无法直连互联网 |
| 日志 | 管理控制器的登录与操作日志接入监控 |
| 应急通道 | 存在、可用、每年演练、全程审计 |
| 未接入设备发现 | 定期扫描带外网段，发现未登记的设备 |

**第一项与第三项若不通过，本节其他内容的优先级都要往后排。** 这两项是本地数据中心安全的地基。

## 15.10.3 跳板机与特权访问路径

### 跳板机不只是"一台中转的机器"

很多企业有跳板机，但它只是一台运维习惯性登录的服务器——从办公终端 SSH 到跳板机，再从跳板机 SSH 到目标。这种形态提供的安全价值很有限，因为攻击者攻陷办公终端后可以完全复现同样的路径。

一个真正起作用的跳板体系需要满足：

**其一，跳板机是唯一路径，且这一点被网络策略强制。** 目标设备的管理端口只接受来自跳板机的连接，其他来源一律拒绝。若不做这条强制，跳板机就只是一个可选的便利工具。

**其二，进入跳板机需要强认证与二次授权。** 多因素认证是底线；对高权限操作还应有申请与审批（即时授权），而不是长期持有。

**其三，凭证不落在运维人员手上。** 由跳板体系代为注入目标凭证，运维人员不知道目标设备的实际口令。这样即使运维人员的终端被攻陷，攻击者也拿不到目标凭证。

**其四，全程会话记录。** 记录内容包括命令、输出、以及图形会话的画面。记录本身必须存放在运维人员无法删改的位置。

**其五，跳板机自身受到最高等级的保护。** 它是整个体系的咽喉——最严格的补丁、最小的软件集、应用控制白名单（见 15.5.5）、无互联网访问、独立的账号体系。

**其六，运维人员使用专用终端。** 这一条最常被省略，也最关键：如果运维人员用日常收邮件、上网的那台笔记本登录跳板机，那么跳板机的所有保护都建立在一台高风险终端之上。专用管理终端（不收邮件、不上网、只用于管理任务）是特权访问的完整闭环，与 15.5.7 的账号分层要求一起构成完整设计。

### 生产坑

**坑一：跳板机成为可用性单点。** 跳板机故障时运维完全无法工作，这会催生"应急直连路径"，而应急路径一旦存在就会被日常使用。正确做法是跳板机集群化，并把应急路径设计成需要多人授权、限时、全程记录的形式。

**坑二：会话记录无人看且从未验证。** 记录的价值在事后调查，但如果从未验证过记录是否完整可读，事到临头才发现格式损坏或存储已满。应定期抽查回放。

**坑三：自动化绕过跳板。** 配置管理工具、监控系统、CI/CD 流水线也需要访问设备，它们通常直连而不走跳板。这些自动化通道的凭证往往权限极高且长期有效，是被忽视的高价值目标。它们应当有独立的、同等严格的凭证管理与审计，而不是因为"不是人在操作"就被排除在特权访问体系之外。

## 15.10.4 网络设备加固与配置基线

### 加固清单

网络设备（交换机、路由器、防火墙、负载均衡器、无线控制器）的加固项相对固定，可以做成检查清单并自动化核查：

| 类别 | 具体项 |
|------|--------|
| 管理访问 | 禁用明文管理协议；仅从管理网可达；启用集中认证与授权；管理会话超时；限制并发会话 |
| 账号 | 消除本地共享账号；本地应急账号唯一且纳入凭证管理；禁用默认账号 |
| 协议与服务 | 关闭不使用的服务与发现协议（尤其在面向不可信网络的接口上）；禁用不安全的旧版协议 |
| 日志与时间 | 日志外送到集中平台；启用时间同步并对时间源做认证；日志包含配置变更 |
| 控制平面保护 | 限制到设备自身的流量速率，防止控制平面被打满 |
| 路由与二层保护 | 路由协议认证；防止未授权设备成为二层根桥；限制端口的地址学习数量；防止未授权的地址分配服务 |
| 配置管理 | 配置定期自动备份；备份存储受保护；变更留痕 |

**"日志外送"这一项容易被低估。** 网络设备的本地日志空间很小，会快速覆盖；而攻击者修改设备配置后，本地日志可能在几小时内就被冲掉。外送到集中平台是唯一能保留证据的方式，且它同时解决了"设备被重置后日志全丢"的问题。

### 配置漂移检测

设备配置会因为故障处置、临时需求、人员操作习惯而持续偏离基线，且这些偏离没有任何机制会自动暴露。配置漂移检测的做法：

1. **定义黄金配置（golden config）。** 按设备角色（接入交换机、汇聚交换机、边界防火墙）定义标准配置模板与必须包含的加固项。
2. **定期拉取实际配置并比对。** 频率至少每日一次。比对结果分三类：与模板不一致的差异、缺失的必需项、以及新增的未知配置。
3. **差异分级处置。** 涉及安全项的差异（认证配置被改、日志外送被关、访问控制列表被放宽）应当立即告警；无害的差异（接口描述、注释）可以只记录。
4. **允许受控偏离但要记录。** 某些设备确实需要特殊配置，这类偏离应当在基线里显式声明为例外，而不是让它每天产生一条告警直到被忽略。

**配置漂移检测最重要的产出不是"发现了不合规"，而是"发现了未经变更流程的修改"。** 一条在变更窗口之外出现的配置改动，无论内容是什么，都值得追问——它可能是运维的临时操作，也可能是攻击者留下的后门（例如新增一个本地账号、放宽一条访问控制列表、增加一条策略路由把流量镜像出去）。这类改动在传统的合规检查里根本不会被注意，而在漂移检测里一目了然。

### 基线与漂移的可执行形态

黄金配置与漂移规则应当写成结构化配置，让检查完全自动化：

```yaml
network_baseline:
  version: 14
  owner: network-engineering
  applies_to_role: access-switch

  required:
    - id: mgmt-plane-acl
      description: 管理访问仅允许来自管理网与跳板机
      severity: critical
    - id: no-cleartext-mgmt
      description: 明文管理协议全部禁用
      severity: critical
    - id: central-aaa
      description: 启用集中认证与命令授权
      severity: critical
    - id: syslog-export
      description: 日志外送到集中平台且目标正确
      severity: critical
    - id: ntp-authenticated
      description: 时间同步指向企业时间源并启用认证
      severity: high
    - id: control-plane-policing
      description: 控制平面限速已启用
      severity: high
    - id: unused-ports-shutdown
      description: 未使用端口处于关闭或隔离状态
      severity: high
    - id: port-security-limits
      description: 接入端口限制地址学习数量
      severity: medium

  forbidden:
    - id: local-shared-account
      description: 除受控应急账号外不得存在本地账号
      severity: critical
    - id: any-any-acl-on-mgmt
      description: 管理接口上不得存在放行全部来源的规则
      severity: critical
    - id: discovery-proto-on-edge
      description: 面向不可信网络的接口不得启用邻居发现协议
      severity: medium

  drift_rules:
    change_window:
      weekdays: [tue, thu]
      start_local: "22:00"
      end_local: "02:00"
    outside_window_action: alert_high
    inside_window_action: record_and_diff
    auto_revert:
      enabled: false
      note: 自动回滚风险高, 当前仅告警并要求 24 小时内补录变更单

  sanctioned_deviations:
    - device: sw-lab-07
      rule_id: unused-ports-shutdown
      reason: 实验室环境需要随时插拔设备
      owner: rd-infra
      expires: 2026-12-31
```

三处设计值得说明。`severity` 让漂移告警可以分级路由——critical 项的偏离应当立即通知值班，medium 项进入周报即可。没有分级，告警会因为噪声过多而整体失效。

`drift_rules` 里区分了**变更窗口内与窗口外**的处置：窗口内的改动记录并生成差异供事后核对，窗口外的改动直接高优先级告警。这条区分是把漂移检测从"合规工具"变成"检测工具"的关键——攻击者不会在你的变更窗口里操作。

`auto_revert.enabled: false` 是一个刻意保守的默认值。自动回滚配置听起来很美，但它可能在故障处置过程中把工程师刚做的紧急变更改回去，造成更大的问题。较稳的路径是先只做告警，运行半年积累信心后，再对少数几类明确无害的项（例如"日志外送目标被改"）启用自动回滚。

### 与策略即代码的衔接

配置基线与 15.3.3 的防火墙策略即代码是同一套工程思路的两个应用面：**把期望状态写成代码、放进版本库、自动比对实际状态、差异即告警**。成熟的做法是把两者合并到同一条流水线里，让网络设备的全部配置（包括安全策略）都通过代码变更产生，手工变更被检测并要求补录。

## 15.10.5 固件与设备生命周期

### 生命周期是一个安全问题

网络设备与服务器硬件都有明确的厂商生命周期：停止销售、停止软件维护、停止支持。**一旦过了停止软件维护的时间点，这台设备的新漏洞将永远不会被修复。** 它会在网络里继续工作很多年，而它的漏洞是永久性的。

这件事之所以长期被忽略，是因为它跨越了两个部门的边界：设备更换是基础设施与采购的预算问题，而漏洞管理是安全的责任，两边都不觉得"到期设备"是自己的议题。

可操作的做法：

1. **建立设备生命周期台账。** 每台设备记录型号、采购时间、厂商公布的各阶段生命周期日期。这份数据可以从厂商公开信息获取并与资产系统关联（见 15.11.2）。
2. **提前 18 个月预警。** 停止软件维护日期前 18 个月进入预警，给采购与预算流程留出时间。到期前才发现，只能选择"带病运行"或"紧急采购"，两者都不好。
3. **对已过期设备强制补偿控制。** 无法及时更换时，必须有明确的补偿措施：更严格的网络隔离、禁止管理面暴露、加强监控、以及记录风险接受。
4. **把生命周期纳入采购决策。** 采购时评估厂商的支持周期承诺，而不只看价格与性能。一台便宜但支持周期只有三年的设备，总体成本可能更高。

### 固件更新的现实困难

固件更新在本地数据中心的执行率极低，原因很实在：需要重启、可能变砖、不同型号流程不同、且"它现在跑得好好的"。

几条能提高执行率的做法：

- **与硬件维护窗口绑定。** 不要单独发起固件更新，而是在已有的机房维护窗口中一并完成。
- **优先处理管理控制器与网络设备。** 它们的固件漏洞影响最大（权限高于操作系统、位于流量必经路径），应当优先于普通外设固件。
- **先在同型号的非生产设备上验证。** 保留少量同型号设备用于验证，能显著降低生产更新的风险。
- **把固件版本纳入配置基线核查。** 让"固件版本低于基线"成为一条自动产生的不合规项，而不是需要人主动想起来去看的事。

## 15.10.6 混合互联：最容易两端不对称的地方

### 三类互联与各自的风险

| 类型 | 典型用途 | 主要风险 |
|------|---------|---------|
| 专线 / 云直连 | 本地与云之间的稳定连接 | 两端策略不对称；路由泄露；带宽成为单点 |
| IPsec 隧道 | 分支互联、备份链路、与合作伙伴互联 | 配置老化；加密套件过时；对端变更无通知 |
| SD-WAN 覆盖网 | 多分支的统一互联 | 控制器成为高价值目标；策略在覆盖层与底层不一致 |

### 两端不对称：最常见的失效

混合互联的典型故障模式不是"连不通"，而是**两端的安全策略不一致，形成单向的宽松路径**。常见形态：

- 云端的安全组收紧到只允许特定源，本地端的防火墙仍是"允许整个云网段"。
- 本地端做了细粒度的访问控制，云端为了方便开了整个 VPC 互通。
- 一端做了流量记录，另一端没有，导致事件调查时只有半边数据。
- 一端的策略经过评审，另一端由另一个团队"临时"配置且从未评审。

根因是 15.1.7 讲的责任边界问题：**链路的两端分属不同团队，各自只对自己那半边负责，而没有人对"这条链路整体"负责。**

这里需要和 5.9.5 的责任共担模型对接一下。责任共担模型划的是企业与云服务商之间那条线——云侧哪些归服务商、哪些归客户，见 [5.9](../../第02部分_技术架构与基础设施安全/第05章_云安全架构/5.9_多云治理.md)。它划完之后，云端安全组归属清楚了，本地端防火墙归属也清楚了，唯独中间这条链路的**整体**没有归属：模型处理的是企业与服务商之间的纵向边界，而混合互联的缺口出在企业内部的横向边界上——同属客户责任范围的两端，分别由云平台团队和网络团队配置，两边都合规，合起来仍然可以是不对称的。本节处理的正是这一段。

对策是把每一条跨界链路作为一个独立的受管对象：有唯一的责任人（这个责任人要同时对两端负责，而不是两端各有一个）、有两端配置的联合评审、有定期的一致性核查（自动比对两端的允许策略是否对称）、有明确的到期与复核周期。

### 一致性核查的可执行形态

两端策略对称性的核查可以自动化，核心是把两端的策略归一化到同一个模型再比对：

```python
"""混合互联链路两端策略对称性核查。

local_rules / cloud_rules: 已从各自设备/云 API 拉取并归一化的规则
  每条为 dict: src, dst, proto, ports(set), action
链路声明 link_spec 定义这条链路"应该"承载什么:
  allowed_flows: 明确批准的流量清单
"""
import ipaddress


def _net(x):
    return ipaddress.ip_network(x, strict=False)


def covers(rule, flow):
    """规则是否覆盖某条声明的流量。"""
    if rule["action"] != "allow":
        return False
    if not _net(flow["src"]).subnet_of(_net(rule["src"])):
        return False
    if not _net(flow["dst"]).subnet_of(_net(rule["dst"])):
        return False
    if rule["proto"] not in (flow["proto"], "any"):
        return False
    return rule["ports"] == "any" or set(flow["ports"]) <= set(rule["ports"])


def extra_reach(rules, allowed_flows):
    """找出规则允许但未在声明清单中的通行范围。"""
    surplus = []
    for r in rules:
        if r["action"] != "allow":
            continue
        justified = any(covers(r, f) for f in allowed_flows)
        if not justified:
            surplus.append(r)
    return surplus


def audit_link(link_spec, local_rules, cloud_rules):
    flows = link_spec["allowed_flows"]

    local_gap = [f for f in flows if not any(covers(r, f) for r in local_rules)]
    cloud_gap = [f for f in flows if not any(covers(r, f) for r in cloud_rules)]

    findings = {
        "link": link_spec["name"],
        "owner": link_spec["owner"],
        "flows_missing_local": local_gap,
        "flows_missing_cloud": cloud_gap,
        "local_surplus": extra_reach(local_rules, flows),
        "cloud_surplus": extra_reach(cloud_rules, flows),
    }
    findings["asymmetric"] = bool(
        findings["local_surplus"] or findings["cloud_surplus"]
        or local_gap or cloud_gap
    )
    return findings
```

怎么读这段代码。它比对的不是"两端规则是否字面相同"——那不可能相同，因为两端用的是不同的策略模型（本地是防火墙规则，云上是安全组）。它比对的是**两端相对于同一份"应该承载什么"的声明各自偏离了多少**。

`extra_reach` 是这段代码的核心产出：**规则允许但声明清单里没有的通行范围**。这正是不对称的实际表现——一端严格按清单配置，另一端放行了整个网段，那么另一端就会产出大量 surplus 项。把这个清单交给链路责任人，比给他两份格式不同的规则导出有用得多。

前提条件是 `link_spec` 必须存在，也就是**每条跨界链路都要有一份声明它应该承载什么流量的文档**。多数企业没有这份东西，而这恰恰是问题的根源：没有"应该是什么"，就无法判断"实际是什么"是否正确。建立这份声明的过程本身，通常就会发现若干条谁也说不清用途的通路。

### 其他工程细节

**地址规划冲突。** 本地网段与云上网段重叠是并购与快速上云的常见后果，处理方式通常是网络地址转换，而这会导致日志中的地址无法直接关联到实际主机，给事件调查带来困难。因此若使用了地址转换，转换关系必须被记录并可查询。

**路由泄露。** 一端的路由被意外通告到另一端，导致流量走了非预期的路径（例如云上流量经本地出网，或者本地流量经云出网），从而绕过了原本设计的检查点。这类问题很难通过配置审计发现，需要通过实际的路径追踪来验证。

**加密与完整性。** 专线通常被认为"物理上安全"因而不加密，但专线中间经过运营商网络，且专线本身不提供任何身份保证。对承载敏感数据的链路，应当在专线之上再叠加加密。

**带宽与降级。** 互联链路是单点时，其中断会导致混合架构的一半不可用。需要明确降级预案：链路中断时哪些业务受影响、是否有备份路径、备份路径的容量与安全策略是否一致（**备份路径的策略常常比主路径宽松，这是一个隐蔽的缺口**）。

## 15.10.7 物理与环境安全的最小集

物理安全不是本书的重点，但有几项与网络安全直接相关的最小要求：

- **机柜上锁，控制台口不可自由接触。** 一个可物理接触的控制台口通常意味着可以通过密码恢复流程获得设备完全控制权。
- **未使用的机房网口关闭。** 与 15.8.6 的办公区要求一致。
- **访问记录与陪同制度。** 第三方维护人员进入机房应当有记录与陪同，且其操作范围明确。
- **设备离场管控。** 硬盘、设备的离场必须有流程与记录，报废设备的介质必须销毁或经确认的擦除（与 15.5.8 的密钥销毁配合）。
- **环境监控设备的网络归属。** 温湿度、漏水、门禁这类设备往往接在带外网或另一个"谁也说不清"的网段上，需要明确归属并纳入准入与隔离策略（见 15.8.1）。

## 15.10.8 验证与度量

### 验证方法

- **管理面可达性测试**：从业务服务器、办公终端尝试访问各类管理接口，验证均被阻断。这是本节最重要的单项验证。
- **默认凭证扫描**：对全部管理控制器、网络设备、存储设备做默认凭证核查，输出覆盖率而非仅列出发现项。
- **配置漂移比对**：每日自动比对，重点关注变更窗口之外的改动。
- **跳板机绕过测试**：尝试从非跳板来源访问受保护设备的管理端口。
- **互联链路策略对称性核查**：自动比对两端的允许策略，输出不对称项。
- **应急通道演练**：模拟业务网完全不可用，验证带外应急通道可用（含认证与审计）。

### 运行关注指标

| 指标 | 定义 | 参考目标 | 说明 |
|------|------|---------|------|
| 管理面隔离达标率 | 通过可达性测试的管理接口占比 | 100% | 未达标项应视为高危 |
| 默认凭证清零率 | 已更换默认凭证的设备占比 | 100% | 90% 与 0% 差别不大 |
| 管理控制器固件合规率 | 无已知高危漏洞的比例 | ≥ 95% | 单独统计，不混入服务器补丁 |
| 配置漂移项数与年龄 | 与基线不一致的配置项 | 持续下降 | 关注变更窗口外的改动 |
| 生命周期到期设备数 | 已过或 18 个月内将过维护期的设备 | 有替换计划覆盖 | 无计划的应进入风险登记 |
| 跳板机覆盖率 | 强制经跳板机访问的设备占比 | ≥ 95% | 剩余部分需说明 |
| 自动化直连通道数 | 绕过跳板的自动化访问路径 | 已登记且受控 | 数量不必为零但必须已知 |
| 互联链路不对称项 | 两端策略不一致的条目 | 0 | 每条都应有责任人 |

### 一个失败驱动的观察

某企业每年做外部渗透测试，报告年年是"边界防护良好，未发现可利用的外部入口"。第四年他们把范围扩大到了内部——测试人员被给予一台普通办公终端的访问权，模拟"钓鱼成功后"的场景。结果是 4 小时内取得了全部核心系统的控制权，路径与本节开头几乎一样：办公网可达管理控制器网段，其中 27 台设备使用默认凭证。

复盘中最值得注意的不是这个结果，而是团队的反应："我们知道管理网没隔离，但一直没人把它当成一个必须解决的问题。" 追问下去，原因是**这件事没有出现在任何一份报告里**——外部渗透测试打不到它（它不对外），合规检查不查它（检查项里没有），漏洞扫描扫不到它（扫描范围是业务网段），资产系统里没有它（管理控制器不是"一台服务器"）。

一个风险要被处理，首先要被看见。**本地数据中心的很多风险之所以长期存在，是因为现有的所有检查机制都正好覆盖不到它们，与修复难度无关。** 这也是为什么本节的验证方法里，第一项是"管理面可达性测试"——它是专门为了让这类风险显形而设计的，而不是常规检查的副产品。

### 常见误区

- **认为"在机房里"就是安全的**。物理位置不提供任何网络层保护，而管理接口的暴露完全绕过操作系统层的所有防护。
- **带外管理网只做 VLAN 隔离然后不再核查**。多年运维中的配置变更一定会打破隔离，必须持续验证而非一次配置。
- **默认凭证清理做到 90% 就停下**。攻击者只需要剩下的那 10%。
- **跳板机不强制**。不做网络层强制的跳板机只是一个可选的便利工具。
- **自动化通道被排除在特权访问体系外**。它们的凭证权限最高、有效期最长、审计最少。
- **忽略设备生命周期**。过了维护期的设备，其新漏洞将永远不会被修复。
- **互联链路只管自己那一端**。两端不对称是混合架构最常见的实际缺口。

---

## 15.10.9 本节小结

本地数据中心的失效模式高度一致：注意力集中在操作系统与应用层，而管理控制器、网络设备、固件、机柜这些承载它们的基础设施处于无人认领的状态。开头那条只有三步的攻击链之所以成立，正是因为管理控制器的权限高于操作系统，却不在任何安全流程里。

**带外管理网的隔离与默认凭证清零是这一节的地基，其他所有工作都应排在它们之后。** 隔离必须持续验证而非一次配置——多年运维中的配置变更一定会打破它；凭证清理必须做到 100%，因为做到 90% 与没做的差别很小。

跳板机要真正起作用，取决于三件事：网络层强制它是唯一路径、凭证不落在运维人员手上、以及运维人员使用专用管理终端。第三项最常被省略，而它决定了整套特权访问体系是否建立在一台高风险终端之上。同时，配置管理工具、监控系统、流水线这些自动化通道不能因为"不是人在操作"就被排除在特权访问体系之外——它们的凭证往往权限最高、有效期最长。

配置漂移检测的核心价值不在于发现不合规，而在于**发现变更窗口之外的修改**——那可能是攻击者留下的后门，而这类改动在传统合规检查中完全不会被注意。它与防火墙策略即代码是同一套工程思路，应当合并到同一条流水线。

设备生命周期是一个跨越采购与安全两个部门边界、因而长期无人认领的安全问题：过了维护期的设备，其新漏洞将永远不会被修复。提前 18 个月预警是给预算流程留出时间的现实做法。

最后是混合互联：它的典型失效不是连不通，而是两端策略不对称形成单向宽松路径，根因是链路两端分属不同团队而没有人对整条链路负责。把每条跨界链路作为一个独立的受管对象、指定唯一责任人、定期自动核查两端对称性，是唯一可靠的解法。

# 15.7　DNS 与出网治理

一次事件响应中，安全团队拿到了一份来自外部机构的通报：某个境外域名与本企业的网络存在通信，该域名被关联到一个已知的攻击组织。通报里给出的是域名，不是 IP。

团队要回答的第一个问题是"哪台机器在解析这个域名"。这个问题他们答不出来。企业的 DNS 服务器上没有开启查询日志——理由是"日志量太大、占磁盘、没人看"；终端上没有采集 DNS 事件；边界防火墙记录了会话，但记录的是目的 IP，而那个域名解析到的是一个大型 CDN 的共享 IP，与成百上千个正常网站共用。

最终的定位方式是在全网部署临时的 DNS 采集，等待攻击者的下一次回连。这个过程花了 9 天。

DNS 日志是安全运营中**成本最低、价值最高、却最常缺失**的一类数据。它记录了每一台设备试图访问的每一个名字，而恶意软件、C2 通信、数据外传、钓鱼点击、影子 IT 使用几乎都会先经过一次域名解析。本节讲的是如何把这条通道管起来——既拿到可见性，也拿到控制力——以及在加密 DNS 普及之后，这件事变得更难了。

> 导读：15.7.1 讲企业 DNS 架构与日志采集的工程细节；15.7.2 讲保护性 DNS 与过滤策略；15.7.3 处理 DoH/DoT 带来的可见性丢失与可行应对，这是近年最实际的新问题；15.7.4 讲出网代理与白名单（含模型 API 出网这条 DLP 覆盖不到的通道），与 15.3.4 的防火墙侧出向策略互补；15.7.5 界定 SWG 的能力与边界；15.7.6 讲 DNS 隧道与 DNS 滥用的检测。云上的出网控制见 5.3，远程用户的出网走 SASE 路径见 15.9。

## 15.7.1 企业 DNS 架构与日志

### 一个能被治理的 DNS 架构长什么样

**核心原则是：企业内所有设备的所有 DNS 查询，都必须经过企业可控的解析器。** 这一条听起来理所当然，实际上在多数企业里并不成立——终端可以手工改 DNS、可以用浏览器内置的加密 DNS、可以用移动热点、访客与 IoT 网段可能直接指向公共解析器。

可治理的架构包含四层：

```
终端与服务器
   │  (强制指向内部解析器；禁止直连外部 53/853/DoH)
   ▼
内部递归解析器（企业自建或托管）
   │  ·内部域权威解析（split-horizon）
   │  ·查询日志记录 ← 可见性的来源
   │  ·响应策略（阻断/重定向/sinkhole）← 控制力的来源
   ▼
上游保护性 DNS 服务
   │  ·威胁情报驱动的域名过滤
   │  ·分类过滤（内容类别）
   ▼
互联网权威 DNS
```

这个结构里，**内部递归解析器是不可让渡的控制点**。即使采购了外部的保护性 DNS 服务，也应当保留内部解析器这一层，原因有三：它提供内部域名解析（外部服务做不到）、它是日志的可靠来源（外部服务的日志按客户端 IP 聚合，经过 NAT 后无法定位到具体设备）、以及它是应急阻断的执行点（发现新的恶意域名时能立刻生效，不必等待外部服务更新）。

### 日志采集：两个位置，各有取舍

| 采集位置 | 优点 | 局限 |
|---------|------|------|
| 解析器侧 | 覆盖所有使用该解析器的设备；部署简单 | 经过 NAT 或本地缓存后难以定位到设备与进程；**看不到被缓存的重复查询** |
| 终端侧 | 能关联到具体进程与用户；不受缓存影响 | 需要终端代理支持；覆盖率受限于代理部署 |

**两者应当并存而非二选一。** 解析器日志给出全局视图与总量，终端日志给出归因能力。事件调查中最有价值的一条记录是"哪台机器上的哪个进程解析了这个域名"，这只有终端侧能提供。

关于"日志量太大"这个常见的反对理由，几条实用的应对：

- **先采集再考虑降本，而不是相反。** 缺失的 DNS 日志在事件中造成的损失，远高于存储成本。
- **分层留存**：全量原始日志短期留存（例如 30 天）满足调查需要，聚合后的摘要（每设备每域名每天的查询计数）长期留存（例如 13 个月）满足回溯需要。摘要数据的体积通常只有原始日志的很小一部分，却能回答"过去一年有没有设备访问过这个域名"这个最常被问的问题。
- **过滤高频噪声**：内部域名、已知的遥测与更新域名可以按比例采样而非全量记录。但要小心——**不要把"未分类域名"过滤掉**，那恰恰是最值得看的部分。

### DNS 基础设施本身的安全

治理 DNS 的同时不能忘记 DNS 服务本身也是一项关键基础设施，它的失效会造成全面业务中断，它被劫持则等同于全面中间人。四项基本要求：

- **解析器不对互联网开放递归。** 开放递归解析器会被用于放大攻击，也会成为外部投毒的入口。这是一项基础配置，但在企业里仍能查出遗漏。
- **权威 DNS 与递归解析分离。** 两者混在同一台服务器上，会让权威服务的漏洞影响到内部解析，反之亦然。
- **域名注册账户的保护等级。** 域名被劫持的后果是全部服务被接管，而攻击点往往不是技术层面，而是注册商账户被盗。注册账户应启用强认证、启用注册商锁定、且与关键控制域同等对待（见 15.1.3）。
- **变更审计。** 谁在什么时候改了哪条记录，必须可追溯。DNS 记录的意外修改是一类高频事故来源，恶意修改则极难被发现。

### 内部域名的暴露问题

一个容易被忽略的风险：内部域名信息通过 DNS 泄露到外部。常见形态包括内部主机名出现在公共证书透明日志中、内部域名的查询被发往外部解析器、以及在公共 DNS 上为内部资产配置了 A 记录（"反正它在内网，指到内网 IP 也无所谓"——这等于把内网拓扑公开了）。

对策是：内部命名与外部命名分离（内部使用独立的域或子域，不在公共 DNS 上解析）、终端强制使用内部解析器（避免内部查询外泄）、以及定期检查公共 DNS 与证书透明日志中是否出现了不该出现的内部名称（这项检查同时是暴露面管理的输入，见 15.11.6）。

## 15.7.2 保护性 DNS：低成本的高价值控制

### 它能挡住什么

保护性 DNS（Protective DNS, PDNS）的原理很简单：在解析阶段判断域名是否可疑，可疑则拒绝解析或重定向到一个可控的页面；选型时应关注的能力项与部署方式，可参照公开的 PDNS 选型指南[4]。它的价值在于位置——**几乎所有网络行为都从域名解析开始**，因此这是一个能在攻击链极早期介入的通用控制点，且不需要看到流量内容，因此不受加密影响。

它能有效覆盖的场景：

- 恶意软件的 C2 回连（大量使用域名而非硬编码 IP，因为域名便于切换）
- 钓鱼页面访问（用户点击链接后的第一步）
- 已知恶意载荷托管站点的下载
- 部分数据外传通道
- 加密货币挖矿与其他非业务用途

它挡不住的：直接使用 IP 通信（不经过 DNS）、已经建立的连接、使用自定义解析通道的恶意软件、以及攻击者控制的合法平台（例如利用云存储或代码托管平台作为 C2 通道——这些域名无法被阻断）。

### 过滤策略的分层

| 类别 | 处置 | 说明 |
|------|------|------|
| 已知恶意（情报驱动） | 阻断 + 告警 | 高置信度，误报低 |
| 新注册域名 | **阻断或降级**（例如注册 30 天内） | 攻击基础设施的高度集中区，业务影响需评估 |
| 动态 DNS 与免费子域服务 | 阻断（保留例外） | 常见的临时 C2 载体 |
| 无内容分类的未知域名 | 记录 + 可选阻断 | 需谨慎，误报影响面大 |
| 高风险内容类别 | 按策略阻断 | 与内容过滤策略一致 |
| 已知安全的高频域名 | 直接放行（不查情报） | 降低延迟与查询量 |

**新注册域名这一行的收益最高。** 攻击基础设施高度集中在新注册域名上——钓鱼站点、C2 域名往往在使用前几天甚至几小时才注册。对"注册时间少于 N 天"的域名施加阻断或额外审查，是一项性价比很高的控制。它的业务影响是真实的（市场活动可能启用新域名、合作伙伴可能刚建站），因此需要一条快速的放行通道，以及一个明确的责任人。多数企业选择 7 至 30 天的阈值，并对市场与采购部门提前沟通。

### 阻断页面的设计

被阻断时用户看到什么，直接影响这项控制的可持续性。三条要求：

1. **明确告知这是企业策略而非网络故障。** 否则用户会报障"上不了网"，产生大量无效工单，且可能自行更改 DNS 设置绕过。
2. **给出申诉入口。** 误分类是必然的，没有申诉通道会导致业务方施压整体放宽策略。
3. **不要显示过多技术细节。** 阻断页面若显示被阻断的完整 URL 与判定理由，在某些场景下会泄露信息。

同时需要注意：**阻断页面只在 HTTP/HTTPS 场景下可见**。非浏览器的程序（恶意软件、后台服务）遇到的是解析失败，它们不会看到任何页面。因此阻断日志与告警才是这项控制的主要产出，页面只是给人看的。

## 15.7.3 加密 DNS：可见性正在丢失

### 问题的实质

DoH（DNS over HTTPS）[1]与 DoT（DNS over TLS）[2]把 DNS 查询加密。从隐私角度这是进步，从企业可见性角度这是一个直接的能力损失：**如果终端绕过企业解析器直接向外部加密 DNS 服务查询，企业既看不到查询，也无法施加任何过滤**。

问题的严重性来自两点。第一，DoH 走 443 端口，与普通 HTTPS 流量在网络层无法区分——不能像 DoT（853 端口）那样简单地按端口阻断。第二，**它可能被默认启用**：部分浏览器与操作系统在特定条件下会自动升级到加密 DNS（DNS-over-TLS 的"机会性"与"严格"两种使用模式见 RFC 8310[3]），而用户完全不知情，企业也不会收到通知。

更进一步，加密客户端握手（ECH）等机制会继续压缩网络侧的可见信息——过去还能从 TLS 握手的服务器名称指示中看到访问目标，这一信息也在逐步被加密。**这条趋势是确定的：网络侧的明文可见性会持续下降，控制点必须向终端侧与身份侧迁移。**

### 可行的应对组合

没有单一手段能解决，需要组合使用：

**手段一：通过管理策略显式关闭浏览器与操作系统的加密 DNS。** 主流浏览器与操作系统都提供了企业策略开关，可以强制关闭或强制指定使用企业自己的加密解析器。这是**最有效、最应该优先做**的一步，成本几乎为零，但需要覆盖到所有浏览器（包括非主力浏览器，见 15.5.8）与所有操作系统。

**手段二：阻断已知的公共加密 DNS 端点。** 维护一份公共 DoH/DoT 服务的域名与 IP 列表，在防火墙与解析器上阻断。这份列表需要持续更新，且无法穷尽——它是一层减损措施而非根治。DoT 因为使用固定端口，阻断相对容易；DoH 需要按目标地址阻断。

**手段三：利用探测机制。** 部分浏览器实现了一个"探测域名"机制：启动时查询一个特定域名，若企业解析器对该域名返回不存在，浏览器就不会自动启用 DoH。在企业解析器上为这类探测域名配置相应响应，可以阻止自动启用行为。这个手段依赖具体实现，需要针对企业环境中实际使用的浏览器版本核实当期行为。

**手段四：把控制点搬到终端。** 终端代理可以在系统调用层面看到域名解析请求，无论后续用什么协议传输。这是**长期唯一可靠的方案**——它不依赖网络位置、不受加密影响、且能关联到进程。这也是终端安全能力与网络安全能力融合的一个具体体现（终端遥测见 15.5）。

**手段五：转向"自己提供加密 DNS"。** 与其对抗加密，不如自己成为加密解析器的提供方——企业部署自己的 DoH 端点并通过策略强制终端使用。这样既保留了传输加密的隐私收益，又保留了企业的可见性与控制力。这是较为成熟的组织正在走的方向。

### 一条需要说清楚的边界

对员工设备上的加密 DNS 施加管控，本质上是限制一项隐私增强技术。在受管的企业设备上，这通常是可接受的（设备归企业所有、用于工作目的、且已告知）。但在 BYOD 场景下，这条界限要谨慎——把管控延伸到个人设备的全部网络行为，会触碰隐私边界并引发合规问题（设备策略选择见 10.5.1）。可行的做法是在 BYOD 上只对企业应用容器内的流量施加控制，而不接管整机 DNS。

## 15.7.4 出网代理与白名单

### 代理的价值：从"IP 到 IP"变成"人到域名"

防火墙的出向策略基于 IP 与端口（见 15.3.4），而现代互联网的目标是域名且 IP 高度共享（CDN、云平台）。这使得纯防火墙的出向控制要么过宽（放行整个云平台的 IP 段）要么过于脆弱（IP 变了就断）。

出网代理解决的正是这个问题：它工作在应用层，能看到目标域名（即使流量加密，也能从连接请求中获得目标主机名），能关联到用户身份，能施加分类过滤，且能产生带用户维度的访问日志。

因此一个成熟的出网架构通常是：**服务器区用防火墙做严格的域名白名单，办公终端强制经代理，两者的日志汇入同一分析平台**。

### 服务器出网白名单的落地

服务器的出网需求有限且可枚举，是最应该做白名单的对象（见 15.3.4）。落地时的几个细节：

- **分类建立模板。** 按服务器角色建立出网模板：应用服务器（内部仓库、时间源、日志上报）、构建节点（包管理源、代码托管）、数据库（几乎不需要出网）、管理节点（厂商更新源）。用模板而非逐台配置。
- **优先走内部镜像源。** 把操作系统更新源、语言包管理源、容器镜像源在内部做镜像，服务器只连内部镜像，出网需求直接归零。这是最彻底的方案，且顺带提升了稳定性与速度。
- **需要出网的走统一代理。** 剩余的出网需求（调用第三方 API、上报数据）统一经过一个代理，在代理上做域名白名单与日志记录，而不是在每台服务器上各自开放。
- **禁止服务器使用外部 DNS。** 与上文一致，否则白名单可被 DNS 隧道绕过。

### 办公终端的分类过滤

办公终端做白名单不现实，实际策略是"黑名单 + 分类过滤 + 未知域名策略"：

- 恶意与高风险类别：阻断。
- 与工作无关且高风险的类别（例如非法内容、恶意软件分发类）：阻断。
- 与工作无关但低风险的类别：按企业文化决定，可以只记录不阻断。**过度限制会损害信任且推动员工使用个人设备处理工作，反而增加风险。**
- 未分类域名：这是策略设计的难点。全部阻断会造成大量误伤（新网站、小众站点、内部工具），全部放行则留下最大的缺口。折中做法是对未分类域名施加额外措施——例如仅允许浏览器访问、阻断文件下载、或结合新注册域名判断做差异化处理。

### 一个失败驱动的观察

某企业为服务器区建立了严格的出网白名单，只允许访问内部镜像源与三个第三方 API 域名。上线半年后的一次红队演练中，红队在一台应用服务器上落地后，发现出网确实被封死——直到他们尝试了 DNS。服务器的 DNS 配置指向内部解析器，而内部解析器会向互联网递归查询，于是红队用 DNS 隧道建立了一条速率很低但完全可用的通道，持续了整个演练期间未被发现。

复盘暴露的两个问题：第一，**出网白名单只覆盖了 TCP/UDP 的直接连接，没有把 DNS 视为一条出网通道**；第二，内部解析器上没有针对服务器区的查询做任何限制或异常检测——服务器解析大量随机子域这件事，在日志里清清楚楚，但没有任何规则在看它。

这个案例说明出网治理必须把 DNS 当作一等公民：**任何声称"完全封闭出网"的环境，如果 DNS 还能递归到互联网，就没有真正封闭**。对确实需要完全隔离的环境，正确做法是让内部解析器只对内部域做权威解析、对外部域一律返回失败，或者只允许解析一份明确的域名白名单。

### 未分类域名的处理：一个具体建议

前文提到未分类域名是策略难点。一个在实践中较为平衡的处理是**按"访问方式 + 域名年龄"做二维差异化**：

| 情形 | 处置 |
|------|------|
| 浏览器访问 + 域名年龄 > 90 天 | 放行，记录 |
| 浏览器访问 + 域名年龄 < 90 天 | 放行但阻断下载，显示提示 |
| 非浏览器程序访问 + 任意年龄 | **阻断并告警** |
| 服务器发起的访问 | 阻断（服务器应走白名单） |

第三行是这张表的核心价值：一个未分类域名被浏览器访问，很可能是员工在正常上网；但被一个后台进程访问，几乎没有正当理由——**这是一条信噪比极高的规则**，而它需要的信息（发起进程）只有终端侧能提供，这再次说明了终端与网络数据结合的价值。

### 模型 API 出网：一条 DLP 覆盖不到的通道

员工把文档粘进外部模型的网页版、自建服务把业务数据拼进提示词后调外部模型 API——这两件事在出网视角下属于同一类流量，而现有的数据外传检测对它基本无效。三条原因同时成立：

- **内容在 TLS 里。** 不做解密就看不到提示词，而模型 API 调用大量来自服务器区，那里通常不解密（见 15.3.8 的取舍）。
- **目的地是合法的商业域名。** 主流模型服务商的域名在各家分类库里普遍归入"IT 与技术"或"生产力工具"，默认放行，且证书、注册信息、信誉分全部正常。
- **流量模式与正常 API 调用没有区别。** 周期性 POST、JSON 载荷、单次几 KB 到几百 KB。传统外传检测依赖的三类特征——大体积上传、异常时段、低信誉目的地——一条都不满足。

结果是：一条能把任意内容送出企业的通道，在出网日志里看起来只是一次普通的第三方 API 调用。

**分层做法。** 四层从可见性递进到控制力，前两层是必做项，后两层按组织情况裁剪。

**第一层：把模型 API 域名清单化。** 在代理与 DNS 平台上建一个独立的自定义分类，把主流模型服务商的三类域名分开登记：API 端点（自建服务在用）、网页版域名（员工浏览器在用）、SDK 与包下载域名（构建节点在用）。这一层不做任何阻断，先解决"谁在调、调多少、从哪些主机调"。成本是加一个分类，一两天可完成，而它产出的第一份清单通常会直接暴露若干未申报的自建服务——正是 15.11.5 要找的那批资产。

**第二层：自建服务强制经 AI 网关代收。** 服务器区本来就走出网白名单，把模型 API 域名从白名单里去掉、只保留内部 AI 网关地址，服务改为调网关。**这一层是整套控制里唯一能看到内容的一环**：网关把加密流量落成可检查的明文，从而能记录调用方身份、按数据分类拦截、对提示与响应做留存审计。网关架构见 17.2.3 与 18.2.5，本节只负责把流量逼进去。

**第三层：办公终端按数据分类决定放行范围。** 终端上做白名单不现实（同本节前文的判断），可执行的做法是：企业采购、走企业账号、签了数据处理协议的模型服务放行；其余服务的网页版按可处理的数据范围区分——允许承载 Internal 及以下的，控制点放在浏览器侧的上传与粘贴限制上（见 15.5.8），指望网关做内容检测在这里行不通；Restricted 与 Confidential 数据的来源系统，则不允许与外部模型网页版共用同一个浏览器配置文件。

**第四层：非浏览器进程访问模型 API 域名一律阻断并告警。** 这条直接复用上面那张未分类域名表第三行的逻辑：办公终端上有后台进程在调模型 API，要么是没申报的自建工具，要么是数据外带，两种情况都需要人看一眼。信噪比高，误报可控。

**适用边界，也是这条控制最需要说清楚的部分。** 出网治理覆盖的对象只有两类：公司网络内的自建服务，以及受管的办公终端。它挡不住的至少有下面几项：

- **个人设备与个人账号完全绕过。** 员工用手机拍下屏幕上的代码、在家用个人账号处理工作内容、把文档转到私人邮箱再上传——网络侧一条都拦不到。这部分只能靠数据分类、终端侧的复制与截屏控制、以及制度与培训，三者的强度都低于网络控制。把出网治理当作数据外带的完整答案，会产生虚假的安全感。
- **域名清单会过期。** 模型服务商增加端点、更换 CDN、上新产品线的节奏快于传统 SaaS，清单滞后期内就是漏的。把清单维护挂到具体的人与具体的周期上，否则它半年后不准。
- **网关代收只对能改代码的自建服务成立。** 买来的第三方软件内嵌模型调用、SaaS 产品在自己后端调模型，企业侧改不了，只能在采购与续约环节要求供应商披露（这与 15.5.2 里对终端防护内置 AI 组件的要求是同一件事的两个场景）。
- **调用方不止服务器与浏览器两类。** IDE 里的编码助手、桌面客户端、命令行工具都会从办公终端直接出网，它们既不受服务器区白名单管辖，也不走浏览器。第四层"非浏览器进程一律阻断"在这里会误伤真实需求，因此必须同步给出受支持的替代路径（企业采购的编码助手，或经内部网关的端点），否则这条规则会在两周内被要求整体关掉。
- **全面封禁会把使用推到看不见的地方。** 与本节前文对办公终端过度限制的判断一致：先把企业采购的服务做到可用、够快、够用，再收紧其余；顺序反过来会同时损失可见性与信任。

**一个反复出现的失败形态：** AI 网关上线了，但服务器区白名单里原来那几个模型 API 域名没有删。开发者手上的旧配置继续走直连，网关侧的调用量看起来一切正常，实际经过率可能只有一半。上线检查清单上必须有"旧路径已关闭"这一项，且用下面第 3 条验证方法实测，不看配置文件。

**验证方法。**

1. 从代理与 DNS 日志按模型 API 域名分类做一次全量拉取，列出源主机与调用量，与 15.11.5 的资产台账比对。第一次做通常会发现相当数量的未申报服务，这批数据同时是资产治理的输入。
2. 在受管终端上用非浏览器进程（命令行工具、脚本）访问模型 API 域名，验证是否被阻断并产生告警。
3. 在服务器区找一台已改为走网关的服务，验证它直连模型 API 域名会被拒绝。这一步测的是白名单有没有真的收紧，而不是网关有没有在跑。
4. 用一份带标记的测试数据（不含真实敏感内容）经网关发出，验证按数据分类的拦截规则生效，并确认审计日志里能检索到这次调用。
5. 统计模型 API 出网中经网关的比例。与 15.7.5 对 SWG 的判断一致，覆盖率比检测能力更值得先解决。

**运行指标。** 模型 API 出网的网关经过率（网关侧调用量 / 代理与 DNS 观测到的全部模型 API 会话数，分母不能取自网关自身）；直连模型 API 的服务器数（目标 0）；非浏览器进程访问模型 API 域名的阻断数，及其中确认为未申报工具的比例；域名清单更新时延（新端点出现到进入清单的天数）；经网关调用中按数据分类被拦截的比例与对应的申诉率——申诉率持续偏高说明分类规则过严，而过严会把使用推向个人设备，等于把这条通道变回不可见。

**不要把阻断量当成效指标。** 阻断量上升可能只是域名清单变全了，与实际风险变化无关。

## 15.7.5 SWG：能力与边界

安全 Web 网关（SWG）是出网治理的集成形态，通常包含 URL 过滤、恶意内容检测、文件下载控制、以及一定程度的数据外传控制。它可以部署为本地设备或云服务（后者是 SASE/SSE 的组成部分，见 15.9.3）。

需要清楚它的三条边界：

**边界一：只覆盖经过它的流量。** 非 HTTP/HTTPS 协议、直接 IP 通信、以及绕过代理的路径（分支直出、移动网络、个人热点）都不在它的覆盖内。**评估 SWG 有效性的第一个问题永远是"实际有多少比例的出网流量经过了它"**，而不是它的检测能力有多强。

**边界二：深度检测依赖 TLS 解密。** 不解密的情况下，SWG 能看到的只有目标域名与流量特征，无法检测下载的文件内容或页面内的恶意脚本。这把 15.3.8 的取舍问题原样搬了过来。

**边界三：与浏览器侧控制重叠但不等价。** 数据外传的控制（复制粘贴、上传、打印）在浏览器侧比在网关侧更精确，而恶意内容检测在网关侧更集中。两者应当分工而非互相替代（见 15.5.8）。

一条实用建议：**先解决覆盖率，再优化检测能力。** 一个覆盖 95% 出网流量、只做基础分类过滤的 SWG，其实际防护效果显著优于一个功能强大但只覆盖 60% 流量的方案。而覆盖率的提升往往不是产品问题，是网络路径与终端配置问题。

## 15.7.6 DNS 隧道与 DNS 滥用检测

### 攻击者为什么用 DNS

DNS 在几乎所有网络中都是被允许的——即便出网被严格限制，DNS 通常仍能出去（否则什么都不能用）。这使它成为最后一条可用的通道，被用于：C2 通信（把命令编码在 DNS 查询与响应中）、数据外传（把数据分块编码到子域名里）、以及可用性验证（确认某台机器是否能出网）。

### 可检测的特征

DNS 隧道无法完全隐藏，它必然产生一些统计上的异常：

| 特征 | 说明 | 误报来源 |
|------|------|---------|
| 同一父域下的唯一子域数量极多 | 每次通信都是一个新子域 | CDN、遥测服务、反垃圾邮件服务 |
| 子域名长度异常且随机性高 | 编码后的数据 | 部分正常服务也用长随机子域 |
| TXT/NULL 等非常见记录类型占比高 | 用于携带更多数据 | 邮件认证、域名验证服务 |
| 单设备 DNS 查询量远超基线 | 隧道需要大量查询 | 配置错误、缓存失效 |
| 查询目标域名年轻且解析结果稳定 | 攻击者自建的权威服务器 | 新上线的正常服务 |
| 查询与响应的时间模式规律 | 心跳式通信 | 正常的轮询服务 |

**单一特征都有大量误报，必须组合。** 一条实用的组合逻辑是：同一父域 + 唯一子域数超过阈值 + 子域平均长度超过阈值 + 该父域不在已知服务白名单中。这与 11.3 中 DGA 检测的思路一致——用行为特征而非指标列表，并用白名单兜底误报。

### 一段可读的检测逻辑

下面这段代码把上表的多个特征组合成一个可解释的评分，重点在于**它把每一条判据的贡献显式化**，从而让分析师能理解"这条告警为什么产生"，而不是面对一个黑盒分数。

```python
"""DNS 隧道与 DNS 滥用的组合式检测。

queries: 一段时间窗口内的查询记录
  client, qname(完整域名), qtype, ts, resp_size
需要外部输入：
  known_service_domains  已知会使用长随机子域的合法服务（CDN/遥测/反垃圾）
  baseline_qps           每客户端的历史查询速率基线
"""
import math
from collections import defaultdict

TUNNEL_SUSPECT_QTYPES = {"TXT", "NULL", "CNAME", "MX"}
MIN_UNIQUE_SUBDOMAINS = 50      # 单一父域下的唯一子域数阈值
MIN_AVG_SUBDOMAIN_LEN = 25      # 子域平均长度阈值
SCORE_ALERT_THRESHOLD = 60


def shannon_entropy(text):
    if not text:
        return 0.0
    freq = defaultdict(int)
    for ch in text:
        freq[ch] += 1
    n = len(text)
    return -sum((c / n) * math.log2(c / n) for c in freq.values())


def split_domain(qname, public_suffix_depth=2):
    """粗略切分父域与子域；生产中应使用公共后缀列表精确切分。"""
    labels = qname.rstrip(".").split(".")
    if len(labels) <= public_suffix_depth:
        return qname, ""
    parent = ".".join(labels[-public_suffix_depth:])
    sub = ".".join(labels[:-public_suffix_depth])
    return parent, sub


def score_pair(records, parent, known_service_domains, baseline_qps):
    """对 (客户端, 父域) 这一对计算可疑度评分与理由。"""
    subs = [r["sub"] for r in records if r["sub"]]
    if not subs:
        return 0, []

    unique_subs = set(subs)
    avg_len = sum(len(x) for x in unique_subs) / len(unique_subs)
    avg_entropy = sum(shannon_entropy(x) for x in unique_subs) / len(unique_subs)
    suspect_type_ratio = sum(
        1 for r in records if r["qtype"] in TUNNEL_SUSPECT_QTYPES
    ) / len(records)

    score, reasons = 0, []
    if parent in known_service_domains:
        return 0, ["父域在已知服务白名单中"]

    if len(unique_subs) >= MIN_UNIQUE_SUBDOMAINS:
        score += 25
        reasons.append("唯一子域数 %d 超过阈值" % len(unique_subs))
    if avg_len >= MIN_AVG_SUBDOMAIN_LEN:
        score += 20
        reasons.append("子域平均长度 %.1f 偏长" % avg_len)
    if avg_entropy >= 3.6:
        score += 20
        reasons.append("子域随机性偏高 熵值 %.2f" % avg_entropy)
    if suspect_type_ratio >= 0.3:
        score += 20
        reasons.append("可疑记录类型占比 %.0f%%" % (suspect_type_ratio * 100))

    client = records[0]["client"]
    base = baseline_qps.get(client)
    if base and len(records) > base * 5:
        score += 15
        reasons.append("查询量为该客户端基线的 5 倍以上")

    return score, reasons


def detect(queries, known_service_domains, baseline_qps):
    grouped = defaultdict(list)
    for q in queries:
        parent, sub = split_domain(q["qname"])
        grouped[(q["client"], parent)].append({
            "client": q["client"], "sub": sub,
            "qtype": q["qtype"], "ts": q["ts"],
        })

    alerts = []
    for (client, parent), records in grouped.items():
        score, reasons = score_pair(
            records, parent, known_service_domains, baseline_qps
        )
        if score >= SCORE_ALERT_THRESHOLD:
            alerts.append({
                "client": client, "parent_domain": parent,
                "score": score, "reasons": reasons,
                "query_count": len(records),
            })
    alerts.sort(key=lambda a: -a["score"])
    return alerts
```

怎么读这段代码。三处判断值得注意：

第一，**白名单检查放在最前面并直接返回 0**。这不是优化，而是必要的设计——CDN 与遥测服务在所有统计特征上都与隧道高度相似，若不先排除，告警队列会被它们完全占据，检测能力实际归零。白名单的维护是这类检测的持续成本，必须在上线前就规划好由谁维护、多久更新。

第二，**评分需要多条判据共同达标才会触发**（阈值 60 意味着至少需要三项特征命中）。任何单条特征单独使用都会产生大量误报：唯一子域多的可能是 CDN，子域长的可能是某些云服务的资源标识，TXT 查询多的可能是邮件认证相关服务。

第三，`reasons` 列表是这段代码最重要的产出。**一条不能解释自己为什么触发的告警，分析师无法在几分钟内判断真伪，最终会被忽略**——这是告警设计的通用原则（见 11.3）。把判据与数值一起输出，让研判从"重新调查一遍"变成"核对几个数字"。

`split_domain` 的简化实现是一个刻意留下的提示：生产环境必须使用公共后缀列表来正确切分父域，否则形如 `xxx.example.co.uk` 的域名会被错误切分，导致同一父域下的查询被拆散、特征被稀释而漏检。这类"看起来无关紧要的实现细节"往往是检测规则在生产中失效的真实原因。

### 工程上的注意点

- **检测的前提是有日志。** 本节开头的困境在这里再次出现：没有 DNS 查询日志，以上所有检测都无从谈起。
- **白名单是必需品而非补丁。** CDN、安全服务、遥测平台大量使用长随机子域，若不维护白名单，告警会被它们淹没。白名单需要随服务变化持续更新。
- **响应记录同样重要。** 只记录查询不记录响应，会丢失"域名解析到了哪里"这一关键信息，也无法检测通过响应下发数据的方向。
- **阻断隧道的直接手段是限制查询速率与记录类型。** 对非基础设施类客户端限制 TXT/NULL 记录查询、对单设备的查询速率设上限，能显著提高隧道的成本，代价是可能影响某些正常服务，需要先观察后启用。

## 15.7.7 验证与度量

### 验证方法

- **旁路测试**：在终端上手工设置外部 DNS、启用浏览器加密 DNS、使用移动热点，验证是否被阻断或被检测到。这是最直接的有效性验证。
- **阻断有效性抽检**：用测试域名验证保护性 DNS 的阻断确实生效，并检查是否产生了对应日志与告警。
- **日志完整性核对**：从终端发起已知的域名查询，验证解析器日志与终端日志中都能找到该记录，并能关联到设备与进程。
- **覆盖率测算**：对比"经过企业解析器的查询量"与"终端侧观测到的解析请求总量"，差值即为绕过量。
- **隧道模拟**：用受控的隧道工具产生流量，验证检测规则能否发现。

### 运行关注指标

| 指标 | 定义 | 参考目标 | 说明 |
|------|------|---------|------|
| DNS 日志覆盖率 | 有日志的查询 / 估算总查询量 | ≥ 95% | 差值即绕过量 |
| 绕过企业解析器的设备数 | 检测到使用外部 DNS 的设备 | 趋近 0 | 需终端侧或网络侧检测 |
| 加密 DNS 策略覆盖率 | 已通过策略关闭或指向企业端点的终端占比 | 100% | 分浏览器与操作系统统计 |
| 出网经代理比例 | 经过代理的出网流量占比 | ≥ 95% | SWG 有效性的前提 |
| 服务器直连互联网数 | 未经代理直接出网的服务器 | 趋近 0 | 高价值指标 |
| 保护性 DNS 阻断量与构成 | 按类别统计的阻断次数 | 持续监控 | 突增通常意味着事件 |
| 新注册域名阻断误报率 | 因误阻断产生的申诉 / 阻断总数 | < 2% | 高于此值需调整阈值 |
| 未分类域名访问量 | 无分类域名的访问占比 | 关注趋势 | 高值说明分类库不适配本企业 |

**"绕过企业解析器的设备数"是这张表里最应该优先建立的指标**。它直接反映了本节所有控制的实际覆盖面——一台绕过解析器的设备，同时逃脱了保护性 DNS、DNS 日志、以及基于 DNS 的所有检测。

### 常见误区

- **不开 DNS 日志**。以"日志量太大"为由不采集，是事件调查中最常见的致命缺口。分层留存可以解决成本问题。
- **只在解析器采集，不在终端采集**。缺少进程与用户归因，日志的调查价值大打折扣。
- **忽略加密 DNS**。默认启用的加密 DNS 会静默瓦解整套 DNS 治理，而它不会发出任何通知。
- **只做阻断不做告警**。被阻断的恶意域名解析是一条高价值的检测信号——它说明某台设备上有东西在尝试连接恶意基础设施，即使这次被挡住了，问题仍然存在，必须去看那台机器。
- **把 SWG 的检测能力当作防护水位**，而忽略它的实际流量覆盖率。
- **把模型 API 域名和普通生产力工具放在同一个分类里**。它默认放行、流量特征正常、内容在 TLS 里，等于一条不受 DLP 覆盖的出网通道（见 15.7.4）。
- **把模型 API 出网治理当作数据外带的完整答案**。个人手机与个人账号绕过全部网络控制，这条控制的范围只有公司网络内的自建服务与受管办公终端。

## 15.7.8 本节小结

DNS 是安全运营中投产比最高的数据源之一：它记录了每台设备试图访问的每一个名字，覆盖了 C2 回连、钓鱼点击、数据外传、影子 IT 使用的共同起点，而采集它几乎不需要新增设备。以"日志量太大"为由不采集，是事件调查中最常见也最昂贵的缺口——分层留存（原始日志短期、聚合摘要长期）能以很小的成本保留回溯能力。

架构上有一条不可让渡的原则：企业内所有设备的所有 DNS 查询必须经过企业可控的解析器。内部递归解析器即使在采购了外部保护性 DNS 服务之后也必须保留，因为它是内部域解析、设备级归因与应急阻断这三项能力的唯一来源。

保护性 DNS 的价值在于它介入的位置极早且不受流量加密影响。策略上，"新注册域名阻断"是性价比最高的单条规则，但必须配一条快速放行通道。同时要记住：**被阻断的恶意解析是高价值告警**，只挡不看等于浪费了这项控制一半的价值。

加密 DNS 是近年最实质的新挑战，且它可能在无人察觉时默认启用。应对必须是组合式的：通过管理策略显式关闭或指向企业端点（成本最低、优先做）、阻断已知公共端点、利用浏览器的探测机制、把控制点搬到终端、以及自建加密解析端点。更根本的判断是：**网络侧的明文可见性会持续下降，控制点必须向终端与身份迁移**——这个趋势会影响本章多个小节的长期技术选型。

出网清单里 2024 年之后需要单列的一类是外部模型 API。它的内容在 TLS 里、目的地是信誉正常的商业域名、流量形态与普通第三方 API 调用没有区别，传统外传检测依赖的三类特征一条都不满足。可落地的分层是：先把这批域名做成独立分类拿到可见性，再把服务器区的出网白名单收到只剩内部 AI 网关、由网关代收，办公终端按数据分类决定放行范围，非浏览器进程访问一律阻断告警。同时要说清楚它的范围——个人手机与个人账号绕过全部网络控制，出网治理解决的只有公司网络内的自建服务与受管办公终端两类，把它当作数据外带的完整控制会产生虚假的安全感。

最后，评估任何出网控制（SWG、代理、过滤）的第一个问题永远是覆盖率而非检测能力。一个覆盖 95% 流量的基础方案，实际效果优于覆盖 60% 流量的强大方案，而覆盖率的提升通常是网络路径与终端配置问题，不是产品问题。

# 15.2　网络分段与微隔离工程

一家大型零售企业在 2023 年启动微隔离项目，采购了主机代理式微隔离平台，预算 18 个月、覆盖 6,000 台服务器。项目第 4 个月完成代理部署与流量学习，产出了一张漂亮的应用依赖图，管理层在季度会上看到了它；第 9 个月做完前两个应用组的策略并进入强制模式；第 14 个月，一次策略变更导致订单系统夜间批处理中断 40 分钟；第 15 个月起，所有新增策略必须经过变更委员会评审；第 18 个月项目验收，实际处于强制模式的工作负载 213 台，占比 3.6%（示例口径，非行业基准）。此后两年，平台每年续费，覆盖率再未提高。

这不是个别失败。微隔离是企业安全里立项通过率高、完整交付率低的典型品类——它的困难不在技术，而在于**项目的成本与收益在时间上严重错配**：成本在前（部署、学习、建模、协调），收益在后（只有进入强制模式才产生防护价值），而中间横亘着一段没有任何安全收益、却持续消耗组织信用的漫长爬坡。多数项目死在这段爬坡上。

> 导读：15.2.1 梳理从物理隔离到身份感知的六类分段技术，给出选型判据；15.2.2 是本节的核心——分段的**实施成本曲线**，解释为什么覆盖率从 60% 到 90% 的代价可能超过从 0 到 60%；15.2.3 讲东西向流量可视化，这是所有分段工作的前置条件；15.2.4 给出从学习模式到强制模式的五阶段落地路径与具体策略形态；15.2.5 讲标签体系——微隔离真正的地基；15.2.6 处理策略生命周期与漂移；15.2.7 直面微隔离项目烂尾的六个根因，其中五个是组织性的；15.2.8 讲验证。云上的安全组与 NetworkPolicy 实现见 5.3.2，本节承担本地与混合环境，两者的策略语义可以统一但工具链不同。

## 15.2.1 分段技术谱系与选型

### 六类技术，六种代价

"网络分段"是一个被过度笼统使用的词。下表把常见技术按**策略绑定对象**排列——这是比"粒度"更有解释力的维度，因为策略绑定什么，就决定了它在什么情况下会失效。

| 技术 | 策略绑定对象 | 生效位置 | 同网段内流量 | 主要失效方式 | 典型单位成本 |
|------|------------|---------|------------|------------|------------|
| 物理隔离 | 线缆与设备 | 物理层 | 完全隔离 | 被"临时"跳线或双网卡打通 | 最高，需独立设备与布线 |
| VLAN + ACL | 端口与网段 | 交换机/三层设备 | **不受控** | 同 VLAN 内横向不受任何约束 | 低，复用现有设备 |
| 子网 + 区域防火墙 | IP 地址与网段 | 防火墙 | **不受控** | IP 变动导致策略漂移；东西向吞吐瓶颈 | 中，需防火墙容量 |
| 虚拟化分布式防火墙 | 虚拟机对象与标签 | 宿主机内核 | 受控 | 覆盖不到物理机与非该平台工作负载 | 中，绑定虚拟化平台 |
| 主机代理式微隔离 | 工作负载标签与进程 | 主机内核/防火墙 | 受控 | 代理兼容性、覆盖率、性能 | 中高，按工作负载订阅 |
| 身份感知代理 | 用户与应用身份 | 代理/网关 | 受控 | 仅覆盖经过代理的协议 | 中高，按用户订阅 |

表中最关键的一列是"同网段内流量"。虚拟化环境下的网络分段、路径冗余、防火墙流量控制与虚拟机流量监控四项配置要点，可参照虚拟网络配置指南[1]；而把策略绑定到工作负载身份而非网络位置，则是零信任架构中"资源级细粒度授权"的直接落地形态[2]。VLAN 与子网这两种最普及的分段技术，对同一广播域内主机之间的通信**没有任何约束能力**——而这恰恰是横向移动最常用的路径。这解释了一个反复出现的复盘结论："我们做了分段，但攻击者从一台 Web 服务器直接打到了同一区里的另外 30 台，因为它们在同一个 VLAN。"分区之内是一片开阔地，这是传统分段的结构性缺口，也是微隔离存在的全部理由。

### 选型决策树

选型不应从"哪个更先进"出发，而应从"要拦住哪条路径"出发：

```
要控制的横向路径是什么？
│
├─ 跨信任域（办公→生产、生产→数据）
│   └─ 子网 + 区域防火墙 已足够，先把这层做扎实
│      └─ 若防火墙东西向吞吐不足 → 考虑虚拟化分布式防火墙分担
│
├─ 同一区内、同一 VLAN 内的服务器之间
│   ├─ 工作负载全部在单一虚拟化平台 → 虚拟化分布式防火墙（无需装代理）
│   ├─ 工作负载跨物理机/多平台/多云 → 主机代理式微隔离
│   └─ 只需保护少数几个关键系统 → 目标系统主机防火墙 + 集中配置管理
│
├─ 终端到终端（办公网内横向）
│   └─ 交换机端口隔离 / 无线客户端隔离 + 终端主机防火墙（见 15.5、15.8）
│
└─ 人到应用（管理访问、运维访问）
    └─ 身份感知代理 / 跳板机 / ZTNA（见 15.9、15.10.3）
```

这棵决策树的第一个分叉最重要：**不要在跨域隔离还没做好的时候去做工作负载级微隔离**。很多项目的顺序反了——花两年做同区内的精细策略，而办公网到数据库的直连路径一直开着。收益排序应该严格按"该路径被实际利用的概率 × 被利用后的损失"来排，跨域路径几乎总是排在前面，而它用现有防火墙就能做，成本低一个数量级。

### 三条容易被忽略的技术约束

**约束一：微隔离代理不是万能覆盖。** 老旧操作系统（已停止支持的 Windows Server 版本、特定内核版本的 Linux）、网络设备、存储阵列、打印服务器、专有设备（如医疗影像工作站、生产线控制终端）通常装不了代理。这些正是最脆弱的资产。对它们只能退回网络层手段：把它们收敛到独立网段，用防火墙包围。**微隔离项目必须在启动时就统计"装不了代理的资产比例"**，这个数字直接决定项目上限。

**约束二：策略与流量不在同一个平面。** 主机代理执行的是本机策略，它看不到"对端是否也装了代理"。当 A 装了代理、B 没装时，A 到 B 的策略只有出向一半生效。这会导致学习期数据不完整、强制期出现单边阻断的诡异现象。工程上必须维护一份"代理覆盖地图"，并把未覆盖资产标记为策略盲区，而不是当作"没有流量"。

**约束三之前，先用满已有设备。** 在采购任何新平台之前，现有交换机上通常还有两项被闲置的能力值得先用：**私有 VLAN（PVLAN）** 可以在不改变 IP 规划的前提下，让同一网段内的端口互相隔离而仍能访问网关，非常适合 DMZ、打印机网段、IoT 网段这类"成员之间本就不该通信"的场景；**端口保护/客户端隔离** 在接入交换机与无线控制器上可以直接切断终端之间的二层可达性。这两项配置的成本近乎为零，覆盖的却是横向移动最常用的路径之一。跳过它们直接上微隔离平台，是很多项目在成本论证上站不住脚的原因。

需要注意 PVLAN 的两个限制：跨交换机使用时需要在中继链路上正确配置，配置不当会造成隔离失效且难以察觉；它无法表达"A 可以访问 B、但 B 不能访问 A"这类有方向的策略，只能做全隔离或全互通。因此 PVLAN 是低成本的粗粒度补丁，不是微隔离的替代品。

**约束三：容器与短生命周期工作负载需要另一套语义。** 一个 Pod 的生命周期可能是几分钟，基于 IP 的策略完全无法跟上。容器环境应使用 NetworkPolicy 或 Service Mesh（见 5.3.2），把它硬塞进主机代理体系通常得不偿失。混合环境的正确做法是两套体系并存，在边界处做策略语义的映射，而不是强求单一平台覆盖一切。

## 15.2.2 实施成本曲线

### 为什么后 30% 比前 60% 更贵

分段项目最常见的规划错误是把成本按覆盖率线性外推："前三个月覆盖了 20%，那一年半就能全覆盖。"实际曲线远非线性：

```
实施成本（累计人月）
  ▲
  │                                                   ┌── 最后 5%：
  │                                                 ╱   多为无主/老旧/
  │                                              ╱      特殊资产，常
  │                                          ╱          需改造或豁免
  │                                      ╱
  │                              ╱ ─────  第三段：长尾
  │                      ╱                （复杂依赖、跨团队协调）
  │            ╱ ──────  第二段：爬坡
  │      ╱               （策略建模与业务确认成为瓶颈）
  │  ╱ ─  第一段：铺开
  │╱     （部署代理、采集流量，技术工作为主）
  └──────────────────────────────────────────────────────▶
   0%        40%        70%        90%      95%    覆盖率(进入强制模式的工作负载占比)
```

三段的性质完全不同，投入的也不是同一种资源：

**第一段（0%–40%，技术工作主导）。** 部署代理、接入流量、完成标签化。这一段快、可预测、可由基础设施团队独立完成，容易在项目早期营造"进展顺利"的假象。首批进入强制模式的通常是那些依赖关系简单、有明确 owner、团队配合意愿高的系统——它们不代表剩下的部分。

**第二段（40%–70%，业务协调主导）。** 瓶颈从工具切换到人。每一个应用组进入强制模式，都需要：找到应用负责人、解释影响、确认依赖清单、约定回退方案、安排变更窗口、观察一段时间。一个中等复杂度应用的策略确认往往需要 2 至 4 周日历时间，而其中的实际工作量可能只有几天——**日历时间被排队、等待与协调消耗**。这一段的成本与工作负载数量弱相关，与**应用数量和团队数量强相关**。

**第三段（70%–95%，长尾与例外）。** 剩下的是最难啃的：共享服务（DNS、AD、监控、备份代理，几乎与所有系统通信）、跨团队的复杂依赖、无人认领的历史系统、装不了代理的设备。这一段常见的现象是每推进一个百分点都需要一次专项协调，而且随时可能因为一次生产影响被整体叫停。

**最后 5% 通常不应该用同一种手段强攻，但这句话很容易被读成"最后 5% 可以不管"，那是错的**，而且错得很危险。回头看上一段列的长尾构成：DNS、AD、监控、备份代理——这些恰恰是攻击者横向移动时最想要的目标，也是勒索软件必先摧毁的对象。按资产数量算，它们是 5%；按被打穿之后的后果算，它们可能是这个网络里最重要的 5%。用"占比小"作为放弃的理由，等于用错了度量单位。

正确的做法是换手段而不是降标准：把这批系统收敛进一个受严格包围的隔离网段，入口出口都走可审计的网关，用网络层的强制手段替代主机代理的强制模式，并对它们单独提高检测覆盖（这里恰恰是最该部署高保真检测的地方）。**判断哪些可以停在这一档，用的是风险而不是数量**——问的是"这台系统被拿下之后攻击者能做什么"，而不是"还剩几台没装上"。真正可以停的是那些低价值、低连通、随时可以整体断网的历史遗留系统；共享服务不在此列。

至于覆盖率数字本身：追求 100% 的代理覆盖率确实是项目烂尾的常见诱因——它把一个已经产生了主要价值的项目变成"永远没完成"的项目，进而失去管理层支持。解法是把度量口径从"代理覆盖率"改成"关键路径被强制管控的比例"，让那些用网络层兜底的系统以另一种形式计入完成，而不是永远挂在分母里当作欠账。

### 成本构成的实际分布

下表是一个 5,000 工作负载规模项目的成本构成参考（示例口径，非行业基准，用于结构而非绝对值）：

| 成本项 | 占比 | 说明 |
|--------|------|------|
| 软件订阅 | 25% | 按工作负载或 CPU 计费，是唯一容易估算的部分 |
| 部署与集成 | 10% | 代理下发、与 CMDB/UEM 集成、日志接入 |
| 流量分析与建模 | 15% | 依赖图构建、标签体系设计、策略生成 |
| **业务协调与确认** | **30%** | 与应用团队沟通、依赖确认、变更窗口协调 |
| 变更与回退处置 | 10% | 灰度、观察、异常处置 |
| 持续运营 | 10% | 新增工作负载纳管、策略变更、漂移修复（首年） |

采购谈判几乎全部围绕第一行展开，而项目失败几乎全部发生在第四行。**规划时如果没有为"业务协调"配置专门的人力（而不是让工程师兼任），项目在第二段必然停滞**。这个角色需要的能力是关系管理与流程推动，而非网络技术——这是很多安全团队没有的技能组合，也是最值得从项目一开始就明确的资源。

### 三个可以显著压低成本的杠杆

1. **先做"出向收敛"而非"入向精细化"。** 对绝大多数服务器而言，限制它能主动连出去的目标（尤其是禁止直连互联网、禁止访问其他区），比精细定义谁能连它更容易达成共识，且对阻断 C2 回连与横向探测的效果立竿见影。出向策略的业务确认成本远低于入向。
2. **按"策略模板"而非按"应用"建模。** 同类系统（例如所有 Web 前端、所有 MySQL 实例）共享一套策略模板，通过标签匹配自动应用。这把工作量从"应用数量"降到"模板数量"，是第二段提速的关键手段。模板数量通常在 15 至 40 个之间就能覆盖大部分工作负载。
3. **把共享服务先做成"全局允许"的白名单。** DNS、AD、NTP、监控、备份、补丁源这些与所有系统通信的服务，单独定义一组全局策略，让每个应用组的建模只需处理业务依赖。不这么做的话，每个应用组都要重新发现同一批共享依赖，重复劳动惊人。

### 被低估的一项收益：合规范围收敛

分段项目的商业论证通常只写"降低横向移动风险"，这个论点在预算评审中很难赢——它无法量化。一个更有说服力的论点是**合规范围收敛**：受监管数据所在的环境范围越小，需要接受审计、需要满足全套控制要求的系统就越少。

以支付卡数据环境为例，PCI DSS v4.0.1 明确允许通过网络分段把不处理、不存储、不传输持卡人数据且无法影响该环境安全的系统排除在评估范围之外（分段有效性需通过渗透测试验证，见 Req 11.4.5）。这带来的直接节省是可计算的：范围内系统数量减少，意味着更少的漏洞扫描、更少的日志留存、更少的访问审查、更短的审计周期。

把这个论点写进商业论证时，需要注意三点：其一，分段必须是**强制生效**的，模拟模式不算数，审计会要求证据；其二，**分段有效性需要独立测试**，且测试范围要覆盖所有进入范围边界的路径，包括管理面；其三，范围收敛的收益属于合规与审计预算，需要在立项阶段就把这部分利益相关方拉进来，否则收益记在别人账上，你的项目仍然要不到钱。

同样的逻辑适用于个人数据的分域治理与跨境数据的隔离要求——数据侧的分类分级一旦确定，网络侧的分区就有了明确的划分依据。分段是少数几个能同时服务安全与合规两条线的基础能力，善用这一点能显著改善项目的资源处境。

## 15.2.3 东西向流量可视化：先看见，再隔离

### 数据源与各自的盲区

任何分段工作的第一步都是搞清楚"现在谁在跟谁说话"。可用数据源及其固有盲区：

| 数据源 | 覆盖 | 盲区 | 获取成本 |
|--------|------|------|---------|
| 防火墙会话日志 | 跨区流量 | 看不到同区、同网段流量 | 低，已有 |
| 交换机 NetFlow/sFlow | 经过该设备的流量 | 采样率损失、看不到同宿主机流量 | 低至中 |
| 虚拟化平台流表 | 虚拟机之间 | 覆盖不到物理机 | 中 |
| 主机代理遥测 | 本机全部连接 + **进程与用户** | 仅覆盖装了代理的主机 | 中高 |
| 云流日志 | 云内 | 与本地数据模型不一致，需归一化 | 低（见 5.3） |

主机代理遥测的独特价值在于**它带进程信息**。"10.20.1.5 连了 10.20.1.9 的 3306 端口"这条记录无法用于建模，因为你不知道这次连接是应用发起的、是运维手工查询、还是备份脚本。而"`/usr/sbin/mysqld` 被 `/opt/app/bin/api-server` 连接"是可以直接转成策略的。**没有进程维度的流量数据，策略建模的准确率会显著下降**，这是主机代理方案相对纯网络方案的核心优势，也值得为之付出部署代价。

### 从流量到策略候选

下面这段代码演示流量记录到策略候选的转化逻辑。它的价值不在于代码本身（每家平台都有内置能力），而在于**它把建模中的几个关键判断显式化了**：多长的观察窗口才算充分、多低的频次算噪声、哪些目标应当归入共享服务而不进入应用策略。

```python
"""东西向流量记录 -> 微隔离策略候选。

输入 flows: 每条为 dict, 字段包含
  src_wl, dst_wl : 工作负载标识（非 IP，已通过资产系统解析）
  dst_port, proto, dst_process : 目标端口/协议/进程
  day            : 观察到的日期（用于判断覆盖天数）
"""
from collections import defaultdict

# 共享服务：与几乎所有工作负载通信，单独成组，不进入应用策略
SHARED_SERVICE_PORTS = {53, 88, 123, 389, 445, 464, 636, 3268}

# 阈值取值依据见正文：观察窗口需覆盖月末批处理
MIN_OBSERVED_DAYS = 35     # 至少跨越一个完整月度周期
MIN_FLOW_COUNT = 3         # 低于此值视为噪声或一次性运维行为
RARE_BUT_KEEP_DAYS = 28    # 罕见但周期性（如月结）仍需保留


def build_policy_candidates(flows):
    agg = defaultdict(lambda: {"count": 0, "days": set(), "processes": set()})
    for f in flows:
        key = (f["src_wl"], f["dst_wl"], f["proto"], f["dst_port"])
        rec = agg[key]
        rec["count"] += 1
        rec["days"].add(f["day"])
        if f.get("dst_process"):
            rec["processes"].add(f["dst_process"])

    candidates, review_queue, shared = [], [], []
    for (src, dst, proto, port), rec in agg.items():
        span = len(rec["days"])
        item = {
            "src": src, "dst": dst, "proto": proto, "port": port,
            "flow_count": rec["count"], "observed_days": span,
            "dst_processes": sorted(rec["processes"]),
        }
        if port in SHARED_SERVICE_PORTS:
            shared.append(item)
        elif rec["count"] >= MIN_FLOW_COUNT and span >= 5:
            candidates.append(item)
        elif span >= 1 and rec["count"] >= 1:
            # 低频不等于不需要：月结、季度对账、灾备演练都在这里
            item["reason"] = "low_frequency_manual_review"
            review_queue.append(item)
    return {
        "auto_candidates": candidates,
        "manual_review": review_queue,
        "shared_services": shared,
    }


def observation_window_sufficient(flows):
    """观察窗口是否足以覆盖周期性业务。不足时不应进入强制模式。"""
    days = {f["day"] for f in flows}
    return len(days) >= MIN_OBSERVED_DAYS
```

怎么读这段代码。三个判断决定了它的行为：

第一，`MIN_OBSERVED_DAYS = 35`。观察窗口必须**跨越一个完整的月度业务周期**。绝大多数分段事故发生在月末、季末或年度结算日——那些一个月只跑一次的批处理、对账任务、报表生成，在 2 周的学习期里完全不会出现。35 天是覆盖"一个自然月 + 缓冲"的最小值；若业务有季度性作业，学习期还需相应延长，或至少在强制模式的第一个季度末安排额外观察。

第二，`review_queue` 不是丢弃队列，而是**必须人工看的队列**。项目中最危险的做法是把低频流量当噪声直接过滤掉——它们往往是最容易漏、后果最严重的一类。正确处理是把它们单独列出，逐条问业务方"这是什么"，而不是让阈值替你做决定。

第三，共享服务被单独抽出。若不这么做，每个应用组的候选策略里都会塞满到 DNS、AD、NTP 的条目，既淹没真正的业务依赖，又造成大量重复。共享服务应当作为一组全局策略统一定义与评审。

### 依赖图的正确读法

流量可视化平台生成的依赖图很容易被误用。三条使用纪律：

- **依赖图显示的是"发生过什么"，不是"应该发生什么"。** 图上一条连线可能正是攻击者留下的横向路径，或是一次不该存在的运维直连。把依赖图直接转成允许策略，等于把当前的错误配置固化成基线。每个应用组的首次建模都应当包含一次"这些连接里有没有本来就不该有的"的清理。
- **不要在图上追求视觉整洁。** 真实的依赖图是乱的，尤其是有共享服务和监控代理时。整洁的图通常意味着数据不全。
- **关注"意外的对称性"**。若 A→B 与 B→A 双向都有大量连接，通常意味着两者之间存在未文档化的耦合，或者是同一个集群的成员通信。这类关系在策略建模时最容易出错。

## 15.2.4 从学习模式到强制模式

### 五阶段路径

从"看得见"到"拦得住"是分段项目的价值分水岭。可执行的五阶段路径如下，每阶段有明确的进入条件与退出条件：

| 阶段 | 动作 | 进入条件 | 退出条件（可进下一阶段） |
|------|------|---------|----------------------|
| 1 观察 | 部署代理，仅采集不阻断 | 代理覆盖率 ≥ 90%，资产标签完成 | 观察窗口 ≥ 35 天，依赖图稳定 |
| 2 建模 | 生成策略候选，业务确认 | 依赖图可用 | 应用负责人书面确认依赖清单 |
| 3 试运行 | 策略生效但仅告警（模拟阻断） | 策略集完成 | 连续 14 天"若阻断则命中"事件 = 0 |
| 4 灰度强制 | 在部分实例上真实阻断 | 试运行零命中 | 灰度实例运行 14 天无业务影响 |
| 5 全量强制 | 全部实例真实阻断 | 灰度通过 | 纳入日常运营，进入变更流程 |

阶段 3 的"模拟阻断"是这条路径上最重要、也最常被跳过的一环。它的作用是回答一个具体问题：**如果现在打开阻断，会拦住什么。** 直接从"仅采集"跳到"真实阻断"，等于用生产业务来做这次测试。工程上，模拟阻断产生的每一条"本应阻断"事件都必须被清零——不是靠加白名单清零，而是逐条判断"这是遗漏的合法依赖（补策略）还是本就不该有的连接（该阻断）"。

阶段 4 的灰度粒度也有讲究。**灰度应当按实例而非按策略**：同一策略集在 20% 的实例上真实生效，其余实例保持模拟。这样一旦出问题，受影响的是一部分实例而非整个应用，且负载均衡可以自动摘除。反过来（按策略灰度，即先开一部分规则）会导致所有实例都处于一个"策略不完整"的状态，反而更危险。

### 策略的具体形态

策略应当写成声明式、可版本化的形式，与工作负载标签绑定而非与 IP 绑定：

```yaml
policy_set: payment-core
version: 7
owner: payments-platform-team
security_reviewer: infra-security
mode: enforce          # observe | simulate | enforce
scope:
  match_labels:
    app: payment-core
    env: prod
default_action: deny

ingress:
  - name: from-api-gateway
    from:
      match_labels:
        app: api-gateway
        env: prod
    ports:
      - proto: tcp
        port: 8443
    process: /opt/payment/bin/paysvc
    justification: 支付下单主链路
    ticket: CHG-2026-3312
    expires: 2027-03-31

  - name: from-reconcile-batch
    from:
      match_labels:
        app: reconcile-batch
        env: prod
    ports:
      - proto: tcp
        port: 8443
    schedule_hint: monthly-close
    justification: 月末对账批处理, 仅每月 1 号至 3 号活跃
    ticket: CHG-2026-3318
    expires: 2027-03-31

egress:
  - name: to-payment-db
    to:
      match_labels:
        app: payment-db
        env: prod
    ports:
      - proto: tcp
        port: 5432
    justification: 主库读写
    ticket: CHG-2026-3312
    expires: 2027-03-31

  - name: to-shared-services
    to:
      policy_group: shared-services-baseline
    justification: DNS/AD/NTP/监控/备份, 由全局基线维护
    ticket: BASELINE

  - name: to-external-acquirer
    to:
      fqdn:
        - acquirer-a.example.net
        - acquirer-b.example.net
    ports:
      - proto: tcp
        port: 443
    justification: 收单机构接口, 出向仅限这两个域名
    ticket: CHG-2026-3401
    expires: 2026-12-31

exceptions:
  - name: legacy-fileshare-temp
    to:
      match_labels:
        app: legacy-fileshare
    ports:
      - proto: tcp
        port: 445
    justification: 遗留报表导出, 待改造为对象存储
    ticket: EXC-2026-0091
    expires: 2026-09-30
    risk_accepted_by: payments-director
```

这份策略里有五个值得照抄的设计：

**`mode` 与策略同版本管理。** 从 simulate 到 enforce 是一次可追踪、可回滚的版本变更，而不是控制台上的一个开关。事故复盘时能准确回答"什么时候、由谁、把哪个策略集切到了强制"。

**`schedule_hint: monthly-close`。** 这条注记提醒运维：这条规则的流量一个月只出现三天，因此"最近 30 天无命中"不能作为删除它的依据。缺少这类注记，规则清理工作会周期性地误删月度作业依赖，这是清理项目里最常见的自伤。

**`process` 字段。** 把策略收紧到进程级别，意味着即使攻击者在同一台机器上获得了执行权限，用其他程序发起的连接也不被允许。这是主机代理相对网络设备的核心能力，不用等于白买。

**`expires` 与 `exceptions` 分区。** 例外要放进独立区块，带风险接受人与到期日，不能只在策略里多加一条。这让"这个系统当前有几个安全例外"成为一个可查询的数字，而不是散落在几百条规则里的隐性债务。

**出向的 `fqdn` 而非 IP。** 对外部接口的出向策略应基于域名，因为对方 IP 会变。这要求代理支持域名解析跟踪，选型时应确认。

## 15.2.5 标签体系：微隔离真正的基础设施

### 策略写不出来，通常是因为标签不存在

微隔离平台的策略语言都很像——匹配标签、指定端口、允许或拒绝。真正决定项目能否推进的，是**标签本身是否可靠、是否完整、是否有人维护**。策略引用了 `app: payment-core`，而资产系统里有 40% 的服务器这个字段为空，那么这套策略从第一天起就只能覆盖 60% 的对象。

标签体系设计有几条硬经验：

**维度要少而正交。** 四到五个维度足够表达绝大多数策略需求，超过这个数量会迅速失控：

| 维度 | 取值示例 | 用途 | 来源 |
|------|---------|------|------|
| `env` | prod / staging / dev / dr | 环境隔离，最刚性的一刀 | 资产系统或云标签 |
| `app` | payment-core / order-api | 应用归属，策略集的主键 | CMDB 应用目录 |
| `tier` | web / app / db / cache / batch | 层级，用于生成模板化策略 | 部署系统或人工确认 |
| `zone` | 关键控制 / 高敏数据 / 业务生产 | 信任域，对齐 15.1.3 的矩阵 | 由 app + tier 推导 |
| `owner` | 团队标识 | 策略审批与故障联系 | HR/组织系统 |

`zone` 应当由前几个维度**推导**而非手工填写——手工填写的分类字段在半年内一定会失真。推导规则本身写成代码并版本化，这样"这台机器为什么被划进高敏数据域"是可解释、可审计的。

**标签必须有唯一权威源。** 微隔离平台自己也能打标签，这是个陷阱：一旦平台内标签与资产系统标签并存，两者必然分叉，而故障时没人知道该信哪个。正确做法是平台标签**只读同步**自权威源（资产系统），平台内不允许手工改标签；需要改就去改源头。这条纪律会带来短期不便（改个标签要走资产系统流程），但它是长期可维护的唯一路径，也直接对应 15.11 的多源融合与权威性规则。

**未打标签的对象需要显式策略。** 无标签工作负载是真实存在且长期存在的（新上线、迁移中、临时环境）。必须为它们定义一个明确的"未分类"策略：允许基础网络服务与出网、禁止访问任何生产资产、并在超过宽限期后升级告警。把未分类对象直接归入默认允许或默认拒绝都会出问题——前者是缺口，后者是持续的业务噪声。

### 与资产系统的耦合方向

一个常见的项目顺序错误是"先上微隔离，顺便把资产数据理清楚"。实际发生的是：微隔离项目被资产数据质量拖垮，而资产数据并没有因此变好，因为微隔离项目没有权限也没有动力去改造资产流程。

更可行的顺序是**先做窄而准的资产切片**：不追求全量资产准确，只保证进入本期微隔离范围的那几百台服务器的 `env`/`app`/`owner` 三个字段准确且有人维护。这份切片随项目推进逐步扩大，同时把维护流程沉淀回资产系统。这样两个项目互为拉动而非互相拖累（资产治理的完整方法见 15.11）。

### 回退机制的工程细节

"能回退"这句话在方案文档里很容易写，在凌晨两点很难做到。可用的回退机制需要满足四个条件：

**条件一：回退的粒度是策略集，不是整个平台。** 全平台切回观察模式意味着所有已完成的工作瞬间失效，且再切回来需要重新走审批——因此没人敢用，遇事只能硬扛。正确的粒度是"把 `payment-core` 这一个策略集切回 simulate"，影响面可控，操作可逆。

**条件二：回退操作不需要安全团队在场。** 应用值班人员应当有权在业务受影响时自行执行回退，事后补报。把回退权限锁在安全团队手里，等于把恢复时间与安全团队的响应速度绑定——这在深夜和节假日是不可接受的。授权的代价是可能出现"一有风吹草动就回退"，这可以用事后复核约束，但不应用事前审批约束。

**条件三：回退动作有明确的执行时限承诺。** 从决定回退到策略实际失效需要多久，取决于平台的策略下发机制。有些平台的下发是分钟级的批量同步，这意味着"60 秒内回退"根本做不到。**这个数字必须在选型阶段实测，而不是相信文档**。实测方法很简单：在测试环境把一条阻断策略切回观察，用持续发包验证从操作到实际放行的时间。

**条件四：回退后有强制的复盘与再进入流程。** 回退容易导致策略集长期滞留在 simulate 模式（见 15.2.6 的健康检查项）。每次回退应自动创建一张任务单，要求在约定期限内完成根因分析并重新进入强制，否则升级到管理层。没有这一环，回退机制会变成事实上的放弃机制。

## 15.2.6 策略生命周期与漂移治理

策略上线不是终点。分段体系的衰减有三个来源，需要分别处置：

**来源一：新工作负载未纳管。** 新上线的服务器如果没有正确打标签，会落入默认策略——如果默认是允许，就是一个持续扩大的缺口；如果默认是拒绝，业务会立刻报障并被临时加白。两种结局都不好。正确做法是把"标签"变成上线流程的必填项，由自动化平台在创建时注入，并对无标签工作负载设置**限时宽限期 + 强提醒**，而非直接放行或直接阻断。

**来源二：标签漂移。** 工作负载的标签（env、app、tier）来自 CMDB 或云标签，而这些源本身在变。一个从 `env: staging` 改成 `env: prod` 的实例会瞬间落入完全不同的策略集。必须监控标签变更事件，并对导致策略集切换的变更发出告警。

**来源三：例外沉积。** 每次故障处置都会产生"先加个规则让它通"，而这些规则的清理依赖于人的自觉。唯一有效的机制是**到期即失效**：例外规则带硬性到期日，到期自动失效并通知，需要续期则重新走审批。把默认值设成"到期删除"而不是"到期提醒"，是这套机制起作用的关键。

一份可用的季度策略健康检查清单：

- 过去 90 天零命中的允许规则清单（**排除**带 `schedule_hint` 注记的周期性规则）
- 无 owner 或 owner 已离职的策略集
- 处于 simulate 模式超过 90 天的策略集（说明推进停滞）
- 已过期但仍生效的例外
- 覆盖范围为空的策略集（标签变更后再无匹配对象，属于死策略）
- 与跨域策略矩阵（见 15.1.3）冲突的规则

这份清单里最容易出问题的是第一项。"零命中即删除"听起来天经地义，但它是规则清理项目里最常见的自伤来源——月度批处理、季度审计导出、灾备切换演练、年度结算，这些流量在 90 天窗口里可能只出现一两次甚至一次都没有。因此清理的正确姿势是**三步走**：先把候选规则切成"仅告警"（真删之前先观察它会不会被命中），观察一个完整业务周期（建议 100 天以上，覆盖季度末），确认零命中后再删除。这个流程慢，但它把"清理引发的生产事故"这个类别基本消除掉了。同样的三步走逻辑在防火墙规则治理中同样适用（见 15.3.3）。

## 15.2.7 微隔离项目为什么大量烂尾

六个根因，其中五个与技术无关。

**根因一：价值兑现太晚，管理层耐心先耗尽。** 项目前 6 至 9 个月只产出"可见性"，而可见性无法回答"我们更安全了吗"。对策是**在早期就交付可强制的窄切片**——例如第 8 周就对"禁止服务器直连互联网"和"禁止办公网直连数据库端口"这两条全局策略进入强制模式。这两条不需要应用依赖建模，风险低、收益立现，能为后续爬坡争取信用。

**根因二：把覆盖率当唯一 KPI。** 一旦考核覆盖率，团队会优先做最容易的部分，并把最有价值但最难的关键系统留到最后（而最后往往不会到来）。更好的指标是"**关键信任域间路径的阻断率**"与"**关键系统进入强制模式的比例**"，让考核指向价值而非数量。

**根因三：一次生产事故导致整体刹车。** 一次因策略导致的业务中断，往往触发"所有策略变更需委员会审批"的过度反应，此后推进速度下降一个数量级。预防手段是**在第一次事故发生前就建好回退机制**：单个策略集能在 60 秒内切回 simulate 模式、有明确的一键回退操作、有值班人员随时可执行。有可靠回退的项目，事故后恢复推进；没有的，事故后停摆。

**根因四：应用团队没有动机。** 对应用负责人而言，配合微隔离建模意味着额外工作与潜在故障风险，收益却记在安全团队账上。有效的做法有三种：把配合度纳入应用团队的运维评分；把微隔离策略作为应用上线检查项的一部分（新应用比老应用容易得多）；用故障数据说话——展示同类企业中未隔离系统在事件中的实际损失。

**根因五：策略建模由安全团队独自完成。** 安全团队不了解业务依赖，做出的策略必然有遗漏，遗漏导致故障，故障导致不信任。正确的分工是：安全团队提供候选策略与工具，**应用团队确认并签字**，签字这一步不能省——它把责任明确到了最了解系统的人身上，也是后续出问题时能快速定位的依据。

**根因六（唯一的技术根因）：代理覆盖不全导致的策略盲区。** 前文已述，装不了代理的资产比例决定项目上限。这个数字必须在立项时算清楚，并在方案里明确这部分用什么手段兜底。把它留到实施中期才发现，会直接动摇整个方案的可行性论证。

### 如何救活一个已经停滞的项目

多数企业面对的不是"要不要启动微隔离"，而是"手上这个停在 5% 的项目怎么办"。三种可选路径，按现实性排序：

**路径一：重新定义范围，把项目从"全覆盖"改为"关键系统覆盖"。** 公开宣布放弃全量目标，把范围收缩到关键控制域与高敏数据域的几百台工作负载，重新排期。这是最有效的止损——它把一个注定失败的承诺换成一个能完成的承诺，同时保住了大部分实际风险收益。代价是需要向管理层解释目标变更，这需要提前准备好"为什么原目标不合理"的数据（成本曲线、协调工时统计、装不了代理的资产比例）。

**路径二：降级技术手段，用网络层补位。** 如果代理覆盖或组织协调确实推不动，把目标从"工作负载级隔离"降到"更细的网络分区"——把关键系统迁入独立网段，用现有防火墙包围。安全收益低于微隔离，但可交付性高得多。已购买的微隔离平台可以保留作为可视化工具使用，这仍然有价值。

**路径三：以出向策略为唯一目标重启。** 放弃入向精细化，只做一件事：所有服务器禁止直连互联网、禁止访问办公网段、只允许出向到明确列出的目标。这套策略不需要应用依赖建模，可以在数周内覆盖数千台机器，且对 C2 回连和数据外传有直接的阻断效果。它常常是投入产出比最高的单项动作。

三条路径的共同点是**都以缩小承诺换取真实交付**。继续维持原计划、期待"下个季度加大投入"是最糟的选择——它会持续消耗组织信用，直到平台在某次预算削减中被整体砍掉，此前所有投入归零。

### 一个反面时间线

回到本节开头的零售企业案例。复盘发现四个可以更早介入的节点：第 4 个月产出依赖图时，没有同步交付任何强制策略（根因一）；第 9 个月只完成两个应用组，此时已经能看出爬坡速度远低于计划，但项目计划未做调整（根因二）；第 14 个月的中断事故没有可用回退，处置耗时 40 分钟（根因三）；事故后引入的变更委员会把单条策略的上线周期从 3 天拉长到 3 周（根因三的连锁反应）。四个节点中，只有第三个是技术问题，而它反而是最容易在方案设计阶段解决的。

### 分段的第二重收益：高置信度检测信号

分段体系一旦进入强制模式，会持续产出一类质量极高的检测信号——**被拒绝的连接**。它的价值在于信噪比：一台服务器按策略只应与三个目标通信，那么它尝试连接第四个目标这件事本身就是异常，不需要任何威胁情报或行为基线来佐证。

这类信号的三种典型形态：

- **横向扫描**：单一源在短时间内触发多条不同目标的拒绝记录，几乎必然是探测行为（无论是攻击者还是未申报的扫描器）。
- **出向异常**：服务器尝试直连互联网或访问未在策略中的域名，是 C2 回连与数据外传的直接指示。
- **进程不匹配**：连接目标在策略允许范围内，但发起进程不是策略指定的进程——这是攻击者在已沦陷主机上复用合法路径的典型特征，纯网络设备完全看不到。

工程上需要注意的是**不要把所有拒绝日志一股脑送进 SIEM**。强制模式初期的拒绝量主要来自策略遗漏，噪声极大；应当先在平台侧按"源工作负载 + 目标 + 端口"聚合，只把首次出现的新组合与短时高频组合送出。等策略稳定后（拒绝量回落到基线），再放宽送出条件。这条与检测工程的告警设计原则一致（见 11.3），也是让分段投入在防护之外多产出一份运营价值的关键（监控接入见 11.7）。

## 15.2.8 验证与度量

### 验证方法

- **可达性矩阵测试。** 用自动化脚本从每个信任域内的探针主机，向其他域的典型端口发起连接，生成实际可达矩阵，与 15.1.3 的策略矩阵比对。这项测试应当定期自动执行（例如每周），并把差异作为告警而非报告。
- **同网段横向测试。** 专门验证"同 VLAN 内两台服务器之间"的可达性，这是传统分段的盲区，也是微隔离价值的直接证明。测试应覆盖 SMB、RDP、SSH、WinRM、数据库端口等常见横向协议。
- **红队路径复用。** 要求红队报告标注每次横向移动是否穿过了微隔离策略、如果穿过了原因是什么（策略缺失、策略过宽、走了未覆盖的资产、使用了被允许的合法路径）。这四种原因对应四种完全不同的改进动作（见 12.2）。
- **策略与实际配置比对。** 声明的策略集与代理上实际生效的规则是否一致。代理离线、策略下发失败、本地防火墙被手工修改都会造成落差，而控制台上仍显示"已下发"。

### 运行关注指标

| 指标 | 定义 | 参考目标 | 说明 |
|------|------|---------|------|
| 强制模式覆盖率 | enforce 模式工作负载 / 应纳管总数 | 逐季提升，不设 100% | 分关键系统与一般系统分别统计 |
| 关键系统强制率 | 关键控制域与高敏数据域中 enforce 比例 | ≥ 90% | 比总覆盖率更有价值 |
| 代理覆盖率 | 已装代理主机 / 可装代理主机 | ≥ 95% | 分母需剔除技术上不可装的 |
| 策略盲区资产数 | 装不了代理且未被网络层包围的资产 | 趋近 0 | 必须有兜底方案 |
| 模拟阻断命中数 | simulate 模式下"本应阻断"事件数 | 进入 enforce 前为 0 | 非零即不可进入强制 |
| 例外数量与平均存续时长 | 生效中的 exceptions | 数量下降，时长 < 90 天 | 反映治理纪律 |
| 阻断事件中的真实告警比 | 被阻断连接中判定为异常的比例 | 持续监控 | 全为误配说明策略过严，全无异常说明策略过松 |
| 策略变更平均周期 | 从申请到生效 | < 5 个工作日 | 超过此值业务方会寻找绕行路径 |

最后一个指标常被忽视但极其重要：**策略变更周期一旦超过业务的忍耐阈值，绕行就会出现**——业务方会申请"临时全通"，或干脆把新服务部署到还没纳管的网段。分段体系的可持续性，取决于它是否比绕过它更省事。

### 常见误区

- **把依赖图当成交付物**。可视化本身不产生任何防护效果，它只是建模的输入。项目汇报里若连续两个季度的主要成果都是"完善了依赖图"，说明项目已经停在第一段。
- **用平台内标签替代资产系统标签**。短期方便，长期分叉，故障时无法判断以哪份为准（见 15.2.5）。
- **把学习期定为两周**。两周覆盖不到任何月度周期性作业，是月末生产事故的直接原因（见 15.2.3 的 35 天阈值）。
- **强制模式与业务高峰期重叠**。切换强制的时间窗口应避开结算日、大促、财报季，这一点在项目排期时几乎总被忽略，而它决定了第一次事故的严重程度。
- **只做入向不做出向**。入向策略防的是"别人来打我"，出向策略防的是"我已经被打穿之后往外连"。后者在勒索软件与数据外传场景中的价值更高，成本却更低。

## 15.2.9 本节小结

网络分段的技术选择应从"要拦住哪条横向路径"倒推，而不是从产品能力出发。跨信任域的隔离用现有防火墙就能做且收益最高，应当先于工作负载级微隔离；同一 VLAN 内的横向移动是传统分段的结构性盲区，也是微隔离唯一不可替代的价值所在。

实施成本曲线是本节最需要带走的一张图：0% 到 40% 是技术工作，40% 到 70% 的瓶颈是业务协调，70% 以上是长尾与例外，而最后 5% 通常应当用网络层手段兜底而非强攻。规划时若按线性外推，项目在第二段必然失控。

从学习到强制的五阶段路径中，"模拟阻断"是不可跳过的一环，"按实例灰度"优于"按策略灰度"，"可在 60 秒内回退"是项目能否在第一次事故后存活的决定因素。

微隔离烂尾的六个根因里有五个是组织性的——价值兑现太晚、KPI 指向数量、事故后过度反应、应用团队缺乏动机、安全团队独自建模。这意味着技术选型做得再好，若没有相应的组织安排，项目仍会停在 3.6% 的覆盖率上。

三条可以带走的操作建议：**第一，把"禁止服务器直连互联网"和"办公网不可直达数据库端口"这两条全局策略提前到项目第 8 周交付**，它们不需要依赖建模，却能立刻产生可演示的防护价值，为后续爬坡换来组织信用。**第二，把标签体系作为独立的、有专人负责的基础设施来建设**，而不是微隔离项目的副产品——策略写不出来通常不是策略语言的问题，是标签不存在的问题。**第三，在选型阶段实测回退时延**，因为项目能否在第一次生产事故后存活，取决于那一晚能不能在几分钟内让业务恢复。

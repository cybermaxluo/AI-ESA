# 3.4　关键场景 Playbook

> 导读：Playbook 是 BISO 体系从"人治"走向"规则治"的核心工具——将依赖个人经验的判断，转化为可复制、可审计的标准流程。本节提供七类场景的完整操作指南：3.4.2 产品上线安全评审（最高频场景，含 AI 辅助初审与分流）、3.4.3 营销活动风险评估、3.4.4 供应商接入 TPRM（全生命周期）、3.4.5 新兴技术评估（以 AI/ML 为核心展开，含用 AI 辅助完成评估）、3.4.6 并购安全尽调、3.4.7 GSBP-BISO 与安全中心协作场景（含事件响应、例外管理、合规审计、威胁情报四个子场景）、3.4.8 组织 AI 资产治理（影子 AI 发现与 Agent 登记）。3.4.2 与 3.4.5 中，AI 均只承担初审与出草稿，风险分级、检查项勾选与放行决策的责任仍在人。Playbook 生命周期管理见 3.4.9；伙伴关系生命周期中各场景的触发时机见 [3.3](3.3_业务安全伙伴关系生命周期.md)。

## 3.4.1 Playbook 设计原则与结构

### 标准化服务的核心工具

Playbook（标准作业程序）是 GSBP/BISO 团队实现服务标准化的关键工具。其核心价值体现在三个层面：服务一致性确保无论哪位 GSBP 执行，输出质量保持一致；知识复用将最佳实践沉淀为可重复使用的流程；新人支持缩短培养周期，使新加入的 GSBP 能够快速上手。

缺乏标准化 Playbook 的团队往往面临服务质量不一致的困境。当同一类型的产品上线评审由不同 GSBP 执行时，评审范围、检查深度、输出格式可能完全不同。这种不一致性会导致业务方困惑——他们无法预期评审内容和时间周期，也难以提前准备所需材料。Playbook 的存在，让业务方能够明确知道评审流程包含哪些步骤、需要准备什么文档、整个周期需要多长时间。

![Playbook 框架](../../../assets/images/chapter_03/05_Playbook_Framework_v6.png)

适用边界：Playbook 适用于高频、可标准化的场景，如产品上线评审、供应商接入评估、营销活动风险评估等。对于低频或高度定制化的场景（如重大并购、监管专项检查），Playbook 提供框架性指导，但具体执行需要根据实际情况调整。

关键约束：Playbook 设计需要在标准化与灵活性之间取得平衡。过于详细的 Playbook 会导致使用率下降，GSBP 倾向于"自己发挥"而非查阅冗长文档。建议采用"核心流程 + 扩展指南"的分层结构：核心流程精简覆盖大多数常见场景，扩展指南针对边缘情况提供深度指引。

常见误区：过度标准化（试图将所有细节写入 Playbook，文档臃肿难以维护）；缺乏版本管理（Playbook 长期不更新，与实际执行流程脱节，GSBP 逐渐弃用）。

验证方法：定期抽查 Playbook 执行记录，对比不同 GSBP 处理同类场景的输出质量差异；通过 VOC 调研收集业务方对服务一致性的反馈。

运行指标：Playbook 执行率（按 Playbook 执行的项目占比）、输出质量差异率（同类项目输出质量的标准差）、业务满意度中"服务一致性"分项得分。

### 标准 Playbook 结构

一个完整的 Playbook 应包含以下核心章节：

场景定义：明确 Playbook 的适用范围、触发条件和排除场景。场景定义的清晰程度直接影响 GSBP 的判断效率——当新需求到达时，GSBP 应能快速判断是否适用本 Playbook，以及适用哪个风险等级的评审流程。

角色与职责：通过 RACI 矩阵明确各角色的责任分工。R = Responsible（执行者），A = Accountable（最终负责人），C = Consulted（需要咨询的专家），I = Informed（需要知情的利益相关方）。避免职责模糊导致的推诿或遗漏。

前置条件：列明执行 Playbook 所需的输入材料、工具准备和人员准备。前置条件不满足时，GSBP 应要求业务方补齐材料，而非在评审过程中反复沟通——后者浪费双方时间，而且往往让 GSBP 看起来像是在刁难业务。

执行步骤：按阶段拆分的详细步骤，包含任务描述、负责人、时间要求、产出物和检查点。步骤描述应具体到可操作层面，避免"进行安全评估"这类模糊表述。

质量检查：关键检查点（必须满足的条件）、审批决策点（Go/No-Go 决策）、例外处理（无法满足时的处理流程）。

产出与交付：交付物清单、交付标准、存储位置。明确的交付标准便于业务方验收，也便于后续审计追溯。

成功指标：时间指标（SLA 达成情况）、质量指标（错误率、返工率）、满意度指标（业务方反馈）。这些指标是 Playbook 优化的数据来源，没有这些数据，优化只能靠主观感受。

常见风险与应对：识别执行过程中可能遇到的风险，预设应对措施。这部分内容来源于历史执行经验的沉淀，应随每次复盘持续更新。

## 3.4.2 Playbook 1：产品上线安全评审

### 场景定义

场景描述：新产品、功能或服务上线前，进行全面的安全风险评估与控制验证，确保符合安全与合规要求。

适用范围：

- 面向用户的新产品或重大功能更新
- 涉及用户数据处理的系统变更
- 跨境业务或进入新市场的产品
- 第三方集成或 API 对外开放

触发条件：

- 产品进入 UAT（用户验收测试）阶段
- 计划上线日期前 10-15 个工作日
- 产品负责人提交上线评审申请

排除场景：

- 纯前端 UI 调整（无逻辑变更、无数据处理）
- 内部运营工具（无用户数据、无外部访问）
- 紧急安全补丁（走应急通道）

适用边界：本 Playbook 适用于标准产品上线场景。涉及重大架构变更、核心数据迁移或新技术栈引入的项目，需要在本 Playbook 基础上增加架构评审环节。紧急上线（如修复线上安全漏洞）应走应急通道，但事后需要补充完整评审记录。

建立自助评估机制可以帮助业务方在提交评审申请前自行判断：是否处理用户数据？是否对外开放 API？是否跨境传输？是否涉及第三方集成？用户规模是否超过设定阈值？系统根据回答自动判断是否需要正式评审以及评审深度。这一机制能将大量零风险或低风险变更排除在正式评审流程之外，让 GSBP 团队专注于真正需要专业判断的场景。

### 角色与职责

| 角色 | 责任 (RACI) | 具体职责 |
|-----|-----------|---------|
| GSBP | R + A | 主导评审流程，协调各方，输出评审报告，做出上线决策建议 |
| 产品经理 | R | 提供产品文档，阐述业务逻辑，协调研发配合 |
| 研发负责人 | R | 提供技术文档，配合安全测试，修复安全问题 |
| AppSec 团队 | C | 进行代码审计、渗透测试，提供技术建议 |
| 架构团队 | C | 审查架构设计，评估系统性风险 |
| 隐私/合规 | C | 评估隐私合规（GDPR/PIPL），跨境数据传输 |
| BISO | A（高风险） | 审批高风险上线，重大例外决策 |
| BU 总经理 | I | 了解重大风险，承担业务决策责任 |

### 执行步骤

阶段 1：启动与材料准备（Day 1-2）

Step 1.1 接收评审申请：产品经理通过工单系统提交申请，填写基本信息（产品名称、上线时间、业务影响），附上产品文档、架构图、数据流图。

Step 1.2 初步风险分级：GSBP 根据以下维度快速评估风险等级——用户数据敏感度（PII/支付/健康）、用户规模、跨境数据传输、第三方集成。风险等级分为低/中/高/极高四档。

Step 1.3 确定评审计划：低风险采用 3 天快速评审；中风险采用 5-7 天标准评审；高/极高风险采用 10-15 天深度评审并需要 BISO 审批。

阶段产出：评审启动通知、评审计划表。

阶段 2：文档评审（Day 3-5）

Step 2.1 产品功能审查：业务逻辑是否合理？是否存在滥用风险？用户交互流程是否安全（认证、授权、会话管理）？是否涉及敏感操作（支付、数据导出、权限变更）？

Step 2.2 数据流分析：数据收集（收集哪些数据？是否最小化？）、数据处理（如何存储、传输、使用？）、数据共享（是否共享给第三方？法律基础？）、数据保留（保留多久？如何删除？）。

Step 2.3 架构安全审查：系统架构（云原生/微服务/单体）、网络隔离（是否遵循分层防护）、身份认证（SSO/MFA/OAuth）、访问控制（RBAC/ABAC/最小权限）、数据加密（传输加密 TLS/静态加密）。

Step 2.4 合规性检查：GDPR/PIPL（用户同意、数据主体权利）、PCI DSS（支付数据处理标准）、行业合规（医疗 HIPAA、金融 PSD2 等）、跨境数据（先核查接收方是否落入充分性认定或 EU-US Data Privacy Framework 覆盖，未覆盖时再走 TIA 评估、SCC 协议、数据本地化；双向流动需同时评估入境国如 PIPL 义务）。

阶段产出：文档评审报告、风险清单、待澄清问题。

阶段 3：技术测试（Day 6-10）

Step 3.1 自动化安全扫描：SAST（静态代码分析）、DAST（动态应用测试）、SCA（软件成分分析）、容器扫描。

Step 3.2 渗透测试（高风险产品）：由 AppSec 团队或外部安全公司执行，模拟攻击者视角测试真实攻击场景，重点关注认证绕过、注入攻击、敏感数据泄露。

Step 3.3 配置审查：服务器安全配置（OS hardening、补丁管理）、网络安全配置（防火墙规则、安全组）、应用安全配置（默认密码、调试模式关闭）、密钥管理（API Key、数据库密码轮转）。

阶段产出：安全测试报告、漏洞清单（含严重程度）。

阶段 4：风险评估与决策（Day 11-13）

Step 4.1 风险汇总与评分：整合文档评审与技术测试结果，对每个风险项评分（概率 1-5 分、影响 1-5 分、风险值 = 概率 × 影响）。

Step 4.2 缓解措施建议：高风险（15-25 分）必须修复才能上线；中风险（6-14 分）建议修复或补偿控制；低风险（1-5 分）建议修复，可接受例外。

Step 4.3 上线决策：直接批准（无高风险，可上线）、有条件批准（修复高风险后上线）、延期上线（风险过高，需重大返工）、风险接受（业务接受剩余风险，签署例外）。

阶段产出：风险评估报告、上线决策建议、整改清单。

阶段 5：审批与上线（Day 14-15）

Step 5.1 整改验证：研发团队修复高/中风险问题，GSBP 验证修复效果，关闭风险项。

Step 5.2 审批流程：低/中风险由 GSBP 审批；高风险由 BISO 审批；极高风险由 BISO 与 BU 总经理联合审批。

Step 5.3 上线放行：签发"上线许可"（Go-Live Approval），更新风险登记册，通知运维、监控团队。

Step 5.4 上线后监控：前 7 天加强监控（异常流量、安全告警），收集用户反馈与安全事件，发现问题及时响应。

阶段产出：上线许可文档、监控计划、应急预案。

### 关键检查清单

认证与授权：是否实施多因素认证？会话超时设置是否合理？是否防止暴力破解（账号锁定、验证码）？权限控制是否基于最小权限原则？是否存在越权访问风险？

数据保护：敏感数据是否加密存储？数据传输是否使用 TLS 1.2+？是否有数据泄露检测机制？用户密码是否安全存储（bcrypt/Argon2）？是否支持用户数据导出/删除（满足 GDPR 要求）？

输入验证：是否防止 SQL 注入（参数化查询）？是否防止 XSS 攻击（输出编码）？是否防止 CSRF 攻击（Token 验证）？文件上传是否限制类型与大小？API 是否有速率限制？

日志与监控：是否记录安全事件日志（登录、权限变更）？日志是否包含足够的审计信息？是否有实时安全告警机制？日志是否安全存储（防篡改）？

合规性：是否有隐私政策与用户同意机制？跨境数据传输是否合规（先核查充分性认定 / EU-US DPF 覆盖，未覆盖时走 TIA、SCC；双向流动同时评估入境国义务）？是否满足行业特定合规要求（PCI DSS、HIPAA）？是否完成数据保护影响评估（DPIA）？

基础设施：服务器是否及时打补丁？是否禁用不必要的服务和端口？是否有 WAF（Web 应用防火墙）？是否有 DDoS 防护？备份与灾难恢复计划是否就绪？

第三方依赖：开源组件是否有已知漏洞？第三方 API 是否安全集成？供应商是否通过安全评估？是否有供应商数据处理协议（DPA）？

应急响应：是否有安全事件响应预案？是否有紧急联系人与升级路径？是否有回滚计划（上线失败时）？

### 常见风险与应对

| 风险 | 应对措施 | 责任人 |
|-----|---------|--------|
| 时间压力导致评审不充分 | 要求提前 15 天申请评审；高风险场景不妥协，宁可延期；建立快速通道处理 P0 紧急需求 | GSBP + 产品经理 |
| 研发团队抵触安全要求 | 前置沟通，解释风险与法规要求；提供安全开发指南与工具；必要时升级 BISO 协调 | GSBP |
| 发现高危漏洞但业务要求上线 | 明确风险，要求业务方书面签字接受；设定例外期限；实施补偿控制（WAF、增强监控） | BISO + BU 总经理 |
| 第三方服务延迟导致评审卡壳 | 提前协调外部安全测试公司；备用方案：内部 Red Team 支持 | GSBP |

关键约束：产品上线评审的周期与深度需要在安全控制与业务效率之间取得平衡。过长的评审周期会导致业务绕过安全流程；过短的周期则无法有效识别风险。根据风险等级差异化处理，而非一刀切，是这一平衡的核心设计原则。

验证方法：上线后监控期间是否出现安全事件；合规审计时评审记录是否完整、证据链是否清晰；定期回溯分析评审过程中遗漏的风险。

运行指标：评审周期（从申请到放行的平均天数）、按时完成率（在承诺 SLA 内完成的比例）、上线后安全事件率（上线后 30 天内出现安全事件的产品比例）、返工率（因安全问题导致上线延期的比例）。

### AI 辅助初审与分流

产品上线评审是 BISO 最高频的场景，日常的堵点往往不在难判断的风险，而在量——大量申请里真正需要专业判断的只是少数，剩下的时间耗在核对材料是否齐全、风险分级填得对不对、有没有漏填必答项这类机械环节上。这一层正适合让 AI 打头阵，把 GSBP 的精力留给需要判断的部分。

材料初审是第一步。申请提交后，让 LLM 先对照本 Playbook 阶段 1 的前置条件清单核一遍：产品文档、架构图、数据流图是否齐全，自助评估问卷的关键项（是否处理用户数据、是否对外开放 API、是否跨境传输、是否涉及第三方集成）有没有填、填得是否自相矛盾。缺件或答非所问的，系统直接退回并列出缺什么，不必等 GSBP 排到这个工单才发现材料不全、再来回沟通——阶段 1 里"前置条件不满足应要求业务方补齐而非评审中反复沟通"这条，正好交给自动初审去落。

分流是第二步。材料齐了，让模型按 Step 1.2 的分级维度给一个初判：读数据流图判断用户数据敏感度（有没有 PII、支付、健康数据），读架构说明判断是否对外开放、是否跨境，据此建议一个风险等级和对应的评审档位（3 天快速 / 5-7 天标准 / 10-15 天深度）。这个初判帮 GSBP 快速把明显的低风险变更和明显要走深度评审的分开，纯前端 UI 调整、内部运营工具这类排除场景也能被初步识别出来先挂起。

常见问题自动核对是第三步。对照关键检查清单里那些有客观答案的项，模型能先跑一遍：密码存储用没用 bcrypt/Argon2、传输有没有强制 TLS 1.2+、API 有没有速率限制、开源组件有没有已知漏洞——这些在文档和扫描报告里能找到线索的，模型逐条给出初步核对结果和出处，GSBP 拿到的是一份标好了"疑似不合规"和"待人工确认"的清单，而不是空白的检查表。

这里同样要划清边界，而且比辅助评估那节更该强调，因为放行是产品上线评审的核心产出。模型做的是初审和分流，不是放行——它可以建议档位、可以标出疑点、可以退回缺件的申请，但 Step 5.2、5.3 的审批与放行决策不下放给模型。低/中风险由 GSBP 审批、高风险由 BISO 审批、极高风险联合审批这套权限不变；模型的分级建议只是入口的加速器，不是终点的裁决者。分级会有边界情况，客观核对项也会被文档里的不实描述误导（文档写了"已启用 WAF"不等于真的启用），这些都要人来把关。把 AI 用在初审分流上，省下的时间恰恰是为了让 GSBP 在真正需要判断的高风险评审上投入更多，而不是相反。

## 3.4.3 Playbook 2：营销活动安全风险评估

### 场景定义

场景描述：大型营销活动（大促、新品发布、市场活动）上线前，评估反作弊、系统稳定性、用户体验与合规风险。

适用范围：

- 全站大促（双 11、黑五、618）
- 新用户拉新活动（红包、优惠券）
- 品牌营销活动（抽奖、积分兑换）
- 跨境营销（涉及不同法规）

触发条件：

- 预算超过设定阈值或预期参与用户超过设定规模
- 涉及现金/优惠券/积分发放
- 活动上线前 7-10 天

适用边界：本 Playbook 适用于面向终端用户的营销活动。对于 B2B 营销活动（如渠道激励、经销商返利），需要在本 Playbook 基础上增加合同审计和财务合规环节。

关键约束：营销活动评估的核心挑战在于时间窗口紧迫（通常只有 7-10 天）且业务容错空间小——活动期间系统故障或被黑产攻击的损失难以挽回，而且往往发生在最不希望出问题的时间节点（大促当天凌晨）。这要求 GSBP 具备快速响应能力和对业务场景的深入理解。

### 执行步骤

阶段 1：活动信息收集（Day 1-2）

收集活动目标（GMV 目标、用户增长目标）、活动机制（玩法规则、奖励规则）、技术架构（活动系统、支付系统、库存系统）、预算与规模（总预算、预期流量、峰值 QPS）。

阶段产出：活动信息表。

阶段 2：风险识别（Day 3-4）

反作弊风险：薅羊毛风险（批量注册、刷单、优惠券套现）、黑产攻击（撞库、账号劫持、恶意下单）、内部舞弊（员工泄露规则、内外勾结）。

系统稳定性风险：流量激增（峰值 QPS 是否超过系统容量）、单点故障（关键服务是否有冗余）、数据库压力（库存扣减、订单写入是否会超载）。

合规风险：抽奖合规（是否涉及赌博，各国法规不同）、隐私风险（是否过度收集用户信息）、广告合规（宣传是否虚假夸大）。

阶段产出：风险清单。

阶段 3：风控策略设计（Day 5-7）

反作弊策略：设备指纹（识别批量注册设备）、行为分析（识别异常下单行为）、黑名单（历史作弊用户、IP、设备）、人机验证（验证码、滑块验证）、规则引擎（实时风控规则，如单用户领取上限）。

系统加固：限流（API 限流、用户限流）、缓存（Redis 缓存热点数据）、降级（非核心功能降级保护核心流程）、扩容（提前扩容服务器、数据库）、演练（压力测试、混沌工程）。

合规措施：用户同意（活动规则明示，用户勾选同意）、隐私保护（最小化数据收集，匿名化处理）、客服准备（投诉处理流程、退款机制）。

阶段产出：风控方案文档。

阶段 4：演练与准备（Day 8-9）

执行压力测试（模拟超出预期的峰值流量）、风控演练（模拟黑产攻击，验证风控规则）、应急演练（模拟系统故障，验证应急预案）、监控准备（配置实时监控告警）。

阶段产出：演练报告、应急预案。

阶段 5：活动上线与监控（Day 10+）

上线前检查：最终配置确认、风控规则上线。

实时监控：业务指标（GMV、订单量、转化率）、技术指标（QPS、错误率、响应时间）、风控指标（作弊拦截数、误杀率）。

应急响应：发现异常立即处理（限流、封禁）。

活动复盘：活动结束后 3 天内复盘。

### 关键检查清单

反作弊：是否设置单用户领取上限？是否有设备指纹识别批量注册？是否有黑名单机制？是否有人机验证？是否有实时风控规则引擎？历史作弊用户是否已封禁？

系统稳定性：是否完成压力测试（建议模拟超出预期的峰值流量）？是否有限流保护？是否有服务降级预案？是否提前扩容？是否有实时监控告警？是否有应急回滚方案？

合规性：活动规则是否明示（条款、限制）？抽奖活动是否合规（不涉及赌博）？隐私收集是否最小化？是否有客服投诉渠道？广告宣传是否真实（避免虚假宣传）？

用户体验：是否有排队机制（避免秒杀时系统崩溃）？是否有友好的错误提示？是否有客服应急支持？是否有退款/取消机制？

常见误区：风控规则过于激进，导致正常用户被误杀，投诉激增，反而影响活动效果；压力测试不充分，仅测试预期流量而非峰值场景，活动开始后系统崩溃。

验证方法：活动期间监控风控拦截数与误杀率的平衡；活动后分析黑产攻击情况与拦截效果；收集用户投诉数据评估规则合理性。

运行指标：作弊拦截率、误杀率（正常用户被误拦截的比例）、系统可用性（活动期间的 uptime）、用户投诉率。

## 3.4.4 Playbook 3：供应商接入安全评估（TPRM）

### 场景定义

场景描述：第三方供应商/服务商接入前，进行全面的安全与合规评估，确保供应链安全。

适用范围：

- SaaS 服务商（CRM、HR 系统、支付网关）
- 外包开发商（软件开发、运维）
- 云服务提供商（AWS、Azure、GCP）
- 数据处理商（数据分析、营销工具）

触发条件：

- 供应商需要访问公司数据/系统
- 供应商处理用户数据
- 采购金额超过设定阈值或战略合作

适用边界：本 Playbook 适用于标准供应商接入场景。对于战略级供应商（如核心云服务提供商）或涉及关键基础设施的供应商，需要在本 Playbook 基础上增加现场审计和持续监控机制。

### 执行步骤

阶段 1：供应商分级（Day 1）

高风险供应商：处理核心业务数据（支付、用户 PII）、访问生产环境系统、大规模用户数据处理。评估深度为现场审计 + 渗透测试。

中风险供应商：处理一般业务数据、访问非生产环境、中等规模用户数据处理。评估深度为文档审查 + 远程验证。

低风险供应商：无数据处理或仅公开数据、无系统访问权限。评估深度为问卷调查 + 证书验证。

阶段 2：尽调评估（Day 2-10）

基础信息收集：公司背景（成立时间、注册地、股权结构）、财务状况（是否稳定）、安全认证（ISO/IEC 27001:2022[7]、SOC 2[8]、等保三级）、合规资质（GDPR、HIPAA、PCI DSS v4.0[9]）、保险覆盖（网络安全保险额度）。

安全能力评估：

- 数据加密：传输加密（TLS 1.2+）、静态加密（AES-256）、密钥管理（HSM/KMS）
- 访问控制：身份认证（SSO/MFA）、权限管理（RBAC/最小权限）、账号管理（离职员工权限回收）
- 安全监控：日志审计（保留期限）、异常检测（SIEM/UEBA）、事件响应（响应时间 SLA）
- 漏洞管理：漏洞扫描（扫描频率）、补丁管理（关键补丁修复周期）、渗透测试（测试频率）
- 业务连续性：备份策略、灾难恢复（RTO/RPO）、BCP 演练频率

合规评估：数据保护（用户同意机制、数据主体权利、数据删除/导出）、跨境数据（数据存储位置、跨境传输机制、数据本地化要求）、分包管理（是否有分包商、分包商是否经过评估、数据处理协议）。

现场审计（高风险供应商）：物理安全（机房门禁、监控、访客管理）、人员安全（背景调查、安全培训、保密协议）、开发安全（代码审计、SDL 流程、CI/CD 安全）、运维安全（变更管理、权限管理、审计日志）。

阶段产出：供应商安全评估报告。

阶段 3：合同谈判（Day 11-15）

关键合同条款：

- 数据处理协议（DPA）：明确数据处理目的、范围、期限；禁止未经授权的数据共享；数据删除/归还条款
- 安全 SLA：系统可用性要求、事件响应时间、漏洞修复时间
- 审计权利：年度安全审计权、事件调查权、现场检查权
- 责任与赔偿：数据泄露赔偿上限、网络安全保险要求、责任免除条款限制
- 终止条款：终止通知期、数据迁移支持、数据删除证明

阶段 4：准入决策（Day 16-20）

决策流程：低风险由 GSBP 审批；中风险由 BISO 审批；高风险由 BISO + 采购 + 法务联合审批；极高风险由 BISO + CSO + BU 总经理审批。

决策选项：批准（无重大风险，可接入）、有条件批准（供应商整改后接入）、延期（风险过高，需重新评估）、拒绝（不符合最低安全要求）。

阶段 5：持续监控（Day 21+）

定期复评：高风险供应商季度复评；中风险供应商半年复评；低风险供应商年度复评。

安全事件监控：订阅供应商安全公告、监控公开漏洞披露、关注供应商财务/法律风险。

合同履行监控：SLA 达成情况、安全培训完成情况、审计报告提交情况。

应急响应：供应商安全事件需在约定时间内通知、重大事件启动应急预案、必要时暂停服务。

阶段产出：供应商档案、监控计划、复评时间表。

关键约束：供应商评估的深度与采购周期之间存在张力。过于严格的评估流程会延长采购周期，影响业务效率；过于宽松则无法有效控制供应链风险。建立"预评估供应商名单"机制——对于已通过评估的供应商类型，后续同类供应商可以简化流程——是解决这一矛盾的务实方案。

常见误区：重评估轻监控（供应商接入时评估严格，接入后缺乏持续监控，无法发现供应商安全状态的变化）；过度依赖认证（将 SOC 2、ISO 27001 等认证作为唯一判断依据，忽视认证范围与实际服务范围的匹配度）。

验证方法：定期抽查供应商安全状态；在供应商发生安全事件时评估其影响范围；合同续签时验证 SLA 履行情况。

运行指标：供应商评估周期（从申请到完成的平均天数）、供应商合规率（通过年度复评的供应商比例）、供应商安全事件数（供应商导致的安全事件数量）。

## 3.4.5 Playbook 4：新兴技术安全评估

### 场景定义

场景描述：评估 AI/ML、区块链、Web3、IoT 等新兴技术的安全风险与合规影响，支持业务创新。

口径归口：本 Playbook 负责的是评估流程本身——谁发起、走几步、卡在哪、谁签字。评估过程中要引用的两类判据不在本节定义：EU AI Act 的高风险判定条件、适用日期与各条义务的对应关系见 [18.6 AI 治理与合规落地](../../第06部分_AI驱动的安全创新/第18章_AI系统安全/18.6_AI治理与合规落地.md)（法规时间表近两年变动频繁，引用前须核当期官方文本），模型与数据集的技术风险面见 18.2 与 18.5。GSBP 不需要自己维护一份法规摘要，但需要知道去哪里取当前口径。

适用范围：

- AI/ML 模型应用（推荐系统、风控模型、生成式 AI）
- 区块链/Web3 应用（NFT、智能合约、DeFi）
- IoT 设备接入（智能硬件、传感器）
- 量子计算、边缘计算等

触发条件：

- 新技术 POC（概念验证）阶段
- 计划规模化应用前
- 涉及用户数据或业务核心流程

适用边界：本 Playbook 提供新兴技术评估的框架性指导。由于新兴技术演进迅速，具体的风险类型和控制措施需要根据技术特性和应用场景动态调整。对于尚未形成行业共识的技术领域，建议引入外部专家参与评估。

### 执行步骤（以 AI/ML 为例）

AI/ML 的安全评估不能套用传统软件系统的框架，原因在于风险源从"代码"扩展到了"数据"和"模型"。一段存在漏洞的代码可以被修复，但训练数据被投毒的模型可能需要完全重新训练，代价远不可比。下面的评估框架围绕这一根本差异展开。

前置步骤：EU AI Act 风险分级判定（评估第一步）

在展开技术评估前，先按 EU AI Act（Regulation (EU) 2024/1689[1]）的四级风险分类为该 AI 应用定档，因为分级直接决定后续义务的性质与强度：

- 不可接受风险（如社会评分、实时远程生物识别的禁用场景）→ 禁止部署，评估直接进入 No-Go；
- 高风险（信贷、招聘、关键基础设施等附件所列场景）→ 需完整合规包（风险管理体系、数据治理、技术文档、人工监督、准确性与鲁棒性）；
- 有限风险（如聊天机器人、生成内容）→ 履行透明度义务（告知用户在与 AI 交互、标注 AI 生成内容）；
- 最小风险 → 自愿性最佳实践，无强制义务。

若涉及生成式/基础模型，还需叠加通用目的 AI（GPAI）义务：技术文档、训练数据摘要、版权合规；达到系统性风险阈值的模型另需模型评估、对抗测试与事件报告。关键时间线为：2024-08 生效、2025-02 禁止性条款适用、2025-08 GPAI 义务适用、2026-08 GPAI 执法与罚款启动；原定 2026-08 的高风险义务经 Digital Omnibus 整体后延——独立高风险系统（Annex III）延至 2027-12-02，作为产品安全组件的内嵌高风险 AI（Annex I）延至 2028-08-02。该延期的临时政治协议达成于 2026-05-06、并于 2026-05-13 获成员国代表确认，GPAI 相关义务的时间表不受影响[2]。时效以欧盟官方公报的最终文本为准。

阶段 1：技术调研（Week 1-2）

收集技术原理（模型架构、训练方法、推理流程）、应用场景（业务价值、用户影响、数据依赖）、技术成熟度（TRL 技术就绪度评估）。

阶段产出：技术调研报告。

阶段 2：风险建模（Week 3-4）

风险建模不必从零构造，可直接映射到业界已成熟的标准框架：NIST AI RMF 1.0（AI 风险管理的四项核心功能：GOVERN 治理、MAP 情境映射、MEASURE 度量、MANAGE 管控，其中 GOVERN 为贯穿其余三项的横切功能[3]）、OWASP Top 10 for LLM Applications（针对大模型应用的十类风险，如提示注入、训练数据投毒、敏感信息泄露[4]）、MITRE ATLAS（对抗性 ML 的战术与技术知识库[5]）。下面的四个维度是这些框架在本 Playbook 中的落地视角，彼此有交叉但各有侧重：

模型安全风险：模型投毒（训练数据被恶意篡改）、对抗攻击（输入扰动导致误判）、模型窃取（通过 API 还原模型）、成员推断（推断训练数据）。

数据安全风险：训练数据泄露（模型记忆敏感信息）、数据投毒（恶意样本注入训练集）、隐私泄露（差分隐私保护不足）。

算法公平性风险：算法偏见（性别、种族、年龄歧视）、公平性问题（不同群体准确率差异）。

可解释性与伦理风险：黑盒模型（无法解释决策过程）、监管合规（欧盟 AI Act 要求可解释性）、深度伪造（生成虚假内容）、自动化决策（影响用户权益，如信贷、招聘）。

阶段产出：风险评估矩阵。

阶段 3：控制设计（Week 5-6）

模型安全控制：对抗训练（提高模型鲁棒性）、模型加密（加密模型文件）、API 限流（防止模型窃取）、输入验证（检测对抗样本）。

数据安全控制：数据清洗（过滤恶意样本）、差分隐私（训练时加噪声）、联邦学习（数据不出本地）、数据脱敏（训练前匿名化）。

公平性控制：公平性测试（评估不同群体准确率）、偏见缓解（重新采样、重新加权）、定期审计（监控模型公平性漂移）。

可解释性控制：模型解释工具（SHAP/LIME）、决策日志（记录决策过程与依据）、人工审核（高风险决策人工复核）。

伦理审查：AI 伦理委员会审查、用户知情同意、申诉机制。

阶段产出：控制框架文档。

阶段 4：试点验证（Week 7-10）

安全测试：对抗攻击测试（模拟攻击验证鲁棒性）、红队测试（AI Red Team 攻击演练）、隐私测试（成员推断攻击测试）。

公平性测试：不同群体准确率评估、偏见指标计算（Disparate Impact）。

合规验证：GDPR 第 22 条（数据主体有权不受仅基于自动化处理、且对其产生法律效果或类似重大影响的决定的约束[6]）、EU AI Act（按前置步骤确定的风险等级履行对应义务：高风险合规包 / 有限风险透明度 / 生成式模型的 GPAI 义务[1]）、本地法规（算法备案、算法公示）。

阶段产出：试点报告。

阶段 5：规模推广决策（Week 11-12）

决策框架：Go（风险可控，可规模推广）、Go with Conditions（需补充控制措施）、No-Go（风险过高，不建议推广）、Pivot（调整技术方案或应用场景）。

阶段产出：上线决策报告、规模推广计划。

### AI/ML 安全检查清单

模型安全：是否有模型加密保护？是否有对抗训练提高鲁棒性？是否有 API 限流防止模型窃取？是否有输入验证检测异常输入？是否有模型版本管理与回滚机制？

数据安全：训练数据是否脱敏/匿名化？是否使用差分隐私保护？是否有数据清洗过滤恶意样本？是否有数据访问权限控制？是否有数据溯源与审计？

公平性与偏见：是否评估不同群体模型准确率？是否有偏见缓解措施？是否有定期公平性审计？是否有用户申诉机制？

可解释性：是否有模型解释工具（SHAP/LIME）？是否记录决策依据？高风险决策是否人工复核？是否满足监管可解释性要求？

合规性：是否有用户知情同意机制？是否支持用户拒绝自动化决策（GDPR 第 22 条）？是否已完成 EU AI Act 风险分级并履行对应义务（高风险合规包 / 有限风险透明度 / 生成式模型的 GPAI 义务）？是否完成算法备案（如适用）？

### 用 AI 辅助完成 AI 评估

前面的框架、清单和分级判定，本身工作量不小。一个 GSBP 面对几十个待评审的 AI 应用，逐条对照 NIST AI RMF 的四项功能、逐项填 OWASP LLM 十类风险的检查表、逐个查 EU AI Act 附件判断是否落入高风险，机械劳动占了大头，真正需要专业判断的往往只有其中几处。这类结构清晰、有既定框架可依的工作，正适合让 LLM 打个下手。这里讲的不是"评估 AI 应用"（那是上面的内容），而是反过来——BISO 用 AI 工具把自己这套评估做得更快。

辅助填检查清单是最直接的一档。把待评审应用的技术文档、数据流图、模型说明喂给一个配置了本 Playbook 检查项的 LLM，让它逐条给出初判：这一项"是否使用差分隐私保护"，文档里有没有相关描述、描述到什么程度、还缺什么证据。模型产出的是一份带初步答案和证据出处的清单草稿，GSBP 拿到的不再是空白表格，而是一份"已经填了一半、标好了存疑处"的底稿，把精力集中在模型标红的缺口和自相矛盾的地方。这里有个务实的边界：模型会读文档说了什么，但不会验证文档说的是否属实——"文档声称启用了 TLS 1.2+"和"系统确实启用了 TLS 1.2+"是两回事，后者仍要靠 GSBP 或 AppSec 的实测去确认。

初判 EU AI Act 分级是第二档，也是更需要谨慎的一档。可以让模型读应用的功能描述和使用场景，对照附件所列的高风险类别，给出一个初步定档建议和它的理由——"这个招聘筛选功能可能落入 Annex III 的就业类高风险，依据是……"。这个初判能帮 GSBP 快速把明显的最小风险应用和明显的高风险应用分开，缩小需要深究的范围。但分级的最终判定和放行决策是人的责任，不是模型的：一是附件的边界常有解释空间，某个应用算不算"关键基础设施的安全组件"往往要结合企业实际用法和最新官方口径判断（时间线与判定细节见 3.4.5 前置步骤、18.6.8）；二是定档错误的后果不对称——把高风险误判为有限风险，漏掉的是整套强制合规义务和最高按全球营收计的罚款敞口。所以模型出的是分级草稿，GSBP 审核后签字定档。

生成评估草稿是第三档。在清单和分级的基础上，可以让模型把零散的发现汇总成一份结构化的评估报告初稿——按本 Playbook 的风险评估矩阵组织，列出识别到的风险项、初步评分、建议的控制措施。GSBP 在这份初稿上做的是审阅、修正、补充判断，而不是从空文档开始写。对高频的中低风险评审，这能把单个评估的周期压下来；省下的时间正好投到那些模型处理不了的场景——需要跨部门协调的、需要理解特定业务上下文的、附件边界模糊需要跟法务一起抠的。

这套辅助有一条贯穿始终的红线：AI 出草稿，人做判定。检查清单的最终勾选、EU AI Act 的分级定档、Go/No-Go 的放行决策，责任都在 GSBP 和相应的审批人身上，不因为"模型这么建议"而转移。模型可能漏判、误判，也可能被输入文档里的错误信息带偏，把它的输出当成一份需要审核的草稿而非结论，是使用它的前提。BISO 域内自己用 AI 工具，同样要落在组织的 AI 资产治理范围内——这类辅助工具本身也是要登记、要评估的 AI 资产，登记与治理机制见 3.4.8。

关键约束：新兴技术评估的核心挑战在于风险图谱尚未成熟、行业最佳实践尚在形成。这要求 GSBP 保持对技术演进的持续关注，并在评估过程中预留足够的不确定性裕度。

常见误区：套用传统安全框架（将 AI/ML 系统简单等同于传统软件系统，忽视模型安全、公平性等特有风险）；忽视运行时风险（仅在上线前评估，忽视模型在运行过程中可能出现的漂移、被攻击等动态风险）。

验证方法：建立 AI 系统的持续监控机制，定期评估模型性能漂移和公平性变化；开展 AI 专项红队测试。

运行指标：模型性能漂移指标、公平性指标变化趋势、AI 相关安全事件数、用户对自动化决策的投诉率。

## 3.4.6 Playbook 5：并购安全尽调

### 场景定义

场景描述：企业并购（M&A）过程中，对目标公司进行安全尽职调查，识别风险并指导整合策略。

适用范围：

- 股权收购（Acquisition）
- 资产收购（Asset Purchase）
- 合资（Joint Venture）
- 战略投资（Strategic Investment）

触发条件：

- 进入尽调阶段（Due Diligence 阶段）
- 交易金额超过设定阈值或战略重要性高
- 目标公司有技术资产或用户数据

适用边界：本 Playbook 适用于安全尽调的标准流程。实际执行中，尽调范围和深度需要根据交易类型、目标公司规模、行业特性等因素调整。跨境并购还需考虑目标公司所在地的数据保护法规和网络安全法规。

### 执行步骤（30-60 天）

阶段 1：尽调准备（Day 1-5）

组建尽调团队：BISO/Senior GSBP（领队）、安全专家（AppSec、InfraSec、GRC）、法务、合规、IT 架构。

签署 NDA（保密协议）。

制定尽调计划：尽调范围（技术、数据、合规、人员）、时间安排（30-60 天）、资料清单（需要目标公司提供的文档）。

阶段产出：尽调计划书。

阶段 2：信息收集（Day 6-20）

技术架构评估：系统架构（单体/微服务/云原生）、技术栈（编程语言、框架、数据库）、云服务（AWS/Azure/GCP/私有云）、技术债（遗留系统、过时技术）、开源依赖（许可证合规、已知漏洞）。

数据资产评估：数据类型（用户数据、业务数据、IP）、数据规模（数据量、用户数、数据库大小）、数据敏感度（PII、支付、健康数据）、数据流向（跨境传输、第三方共享）、数据保留（备份策略、归档机制）。

安全能力评估：安全组织（是否有专职安全团队及其规模）、安全认证（ISO 27001、SOC 2、等保）、安全工具（SIEM、EDR、WAF、DLP）、SDL 流程（是否有安全开发生命周期）、事件历史（过去 3 年重大安全事件）。

合规状态评估：法规遵循（GDPR、PIPL、HIPAA、PCI DSS）、审计报告（最近一次审计结果及发现问题）、监管处罚（是否有监管罚款及金额）、诉讼风险（是否有数据泄露相关诉讼）、合同义务（客户合同中的安全承诺）。

供应链评估：关键供应商（云服务、SaaS、外包商）、供应商评估（是否有 TPRM 流程）、供应商依赖（是否过度依赖单一供应商）、供应商风险（供应商是否有安全事件）。

人员评估：安全人员（数量、能力、稳定性）、背景调查（是否有员工背景调查）、安全培训（是否有安全意识培训）、离职风险（关键人员是否有离职风险）。

阶段产出：尽调发现清单。

阶段 3：风险评估（Day 21-30）

风险分类框架对交易决策的影响是递进的，理解这一点有助于 GSBP 在汇报时选择正确的沟通方式：

- P0 交易终止风险（Deal Breaker）：重大数据泄露未披露、严重合规违规（可能导致业务关闭）、关键系统存在致命漏洞
- P1 交易条件调整风险（Price Impact）：需要大量安全投资、合规整改成本高、技术债务严重
- P2 整合风险（Integration Risk）：技术栈差异大整合难度高、安全标准不一致、人员流失风险
- P3 运营风险（Operational Risk）：日常安全运营能力弱、需要补充安全工具与流程

风险量化：计算安全整改成本估算、评估合规罚款风险范围、估算数据泄露风险范围、预估整合时间。

阶段产出：风险评估报告、交易建议。

阶段 4：整合规划（Day 31-45）

整合规划按时间阶段推进：

- Day 1（交割日）：账号权限管理（收回管理员权限）、网络隔离（防止恶意行为）、应急响应（成立联合应急小组）
- Day 1-30（过渡期）：临时安全控制（WAF、监控、日志）、合规快速评估（识别即时合规风险）、关键系统保护（隔离核心资产）
- Day 31-90（稳定期）：安全标准对齐（统一安全政策）、人员整合（安全团队融合、培训）、工具整合（统一安全平台）
- Day 91-180（深度整合）：架构整合（统一技术架构）、流程整合（统一 SDL、TPRM 流程）、文化整合（统一安全文化）
- Day 181+（持续优化）：优化安全能力、知识转移、经验积累

阶段产出：整合路线图、预算计划。

阶段 5：交割执行（Day 46-60）

交割前准备：确认尽调发现已披露、交割日计划（Hour-by-Hour）、应急预案（如发现隐藏问题）。

交割日执行：权限交接仪式、关键系统访问权限变更、安全团队宣布整合计划。

交割后跟进：30 天快速评估、90 天中期评估、180 天整合完成评估。

阶段产出：交割报告、整合进度跟踪。

### M&A 尽调检查清单

技术风险：是否有技术架构文档？是否有未修复的高危漏洞？开源组件是否有许可证风险？是否有遗留系统技术债？关键系统是否有单点故障？

数据风险：数据资产清单是否完整？是否有未授权的数据共享？跨境数据传输是否合规？是否有数据泄露历史？备份与灾难恢复是否可靠？

合规风险：是否有有效的合规认证（ISO 27001、SOC 2）？是否有未披露的监管处罚？客户合同中的安全承诺是否满足？是否有数据泄露相关诉讼？是否满足目标市场合规要求（GDPR、PIPL）？

供应链风险：关键供应商清单是否完整？是否有供应商集中度风险？供应商合同是否可转移？供应商是否有安全事件历史？

人员风险：安全团队规模与能力如何？是否有关键人员保留计划？是否有员工背景调查？离职员工权限是否及时回收？

组织与流程：是否有安全政策与流程文档？是否有事件响应预案？是否有定期安全培训？是否有变更管理流程？

关键约束：M&A 安全尽调通常受限于严格的时间窗口和信息获取限制。尽调期间目标公司可能无法提供完整信息，或出于商业保密考虑限制访问范围。这要求 GSBP 在有限信息下做出风险判断，并在风险评估报告中明确标注信息缺口和不确定性——透明地呈现"我们不知道的"和"我们知道的"同样重要。

常见误区：重交易轻整合（尽调重点放在交易决策，忽视交割后的整合规划，导致整合期间安全风险失控）；低估文化差异（忽视两家公司安全文化差异对整合的影响，导致人员流失或标准执行不一致）。

验证方法：交割后定期评估整合进度与实际风险暴露情况；对比尽调发现与交割后实际发现的偏差；跟踪整合成本与预算的差异。

运行指标：尽调发现准确率（尽调发现与交割后实际发现的匹配度）、整合进度达成率、整合期间安全事件数、关键人员保留率。

## 3.4.7 Playbook 6：GSBP-BISO 与安全中心协作场景

### 场景定义

场景描述：GSBP/BISO 作为业务与集团安全中心（SOC、GRC、AppSec、DataSec 等职能团队）之间的桥梁，在安全事件响应、风险升级、合规审计、威胁情报响应等场景中协调各方，确保安全策略有效传导至业务一线，同时将业务需求与反馈传递回安全中心。

适用范围：

- 安全事件响应中的业务影响评估与协调
- 风险例外申请与升级决策
- 合规审计的证据收集与整改推动
- 威胁情报的业务影响评估与响应协调
- 安全策略发布后的业务落地推动

触发条件：

- SOC 检测到涉及业务线的 P3 及更严重的安全事件
- 业务需求无法满足安全标准，需申请风险例外
- GRC 发起合规审计或下发整改要求
- 威胁情报团队发布针对性威胁预警
- 集团安全中心发布新安全策略或标准

排除场景：

- 纯技术层面的安全运营（漏洞修复、补丁管理、配置变更），由安全中心直接与研发对接
- P4 级低影响安全告警，SOC 自行闭环
- 已有标准化自动化流程处理的场景（如自动化漏洞扫描报告分发）

适用边界：本 Playbook 聚焦 GSBP/BISO 在跨职能协作中的桥梁角色与协调职责。安全中心各职能团队的内部流程不在本 Playbook 范围内，详见各职能团队的标准作业程序。

关键约束：跨职能协作的核心挑战在于信息不对称与优先级冲突。GSBP/BISO 需要在安全团队的技术视角与业务团队的商业视角之间建立共同语言，避免"安全说技术、业务说营收"导致的沟通低效。

常见误区：角色越位（GSBP 试图替代 SOC 进行技术分析，或替代业务方做出业务决策）；传声筒模式（GSBP 仅转发信息而未进行业务上下文翻译和风险解读）；单向沟通（只关注安全中心向业务的策略传导，忽视业务需求向安全中心的反馈）。

验证方法：定期回顾跨职能协作案例，评估信息传递的及时性、准确性和增值程度；通过 VOC 调研收集业务方和安全中心双方对 GSBP 协作效能的反馈。

运行指标：跨职能需求响应 SLA 达成率、协作满意度（业务侧 + 安全中心侧双向评分）、升级率（需要升级至 BISO 或更高层级的需求占比）、协作闭环周期。

### 协作场景一：安全事件响应

#### 场景说明

安全事件发生时，SOC 负责技术检测与遏制，GSBP 负责业务通知与协调，业务方负责业务影响评估与决策，BISO 负责重大事件的响应统筹，GRC 负责合规义务判断。五方协作确保事件得到有效处置，同时将业务影响降至最低。

GSBP 在此场景中最容易犯的错误是"等信息齐全再通知业务方"——这往往让业务方感觉是事后才被告知，而不是在事件发展过程中共同参与决策。正确的做法是在 15 分钟内给业务方一个初步情况，即使此时信息并不完整。

#### 角色与职责

| 角色 | 责任 (RACI) | 具体职责 |
|-----|-----------|---------|
| SOC | R + A（技术层面）| 事件检测与分诊、技术调查与分析、遏制与恢复执行、根因分析、技术复盘 |
| GSBP | R（协调层面）| 接收事件通报并通知业务方、协助业务影响评估、协调业务侧资源配合、同步响应进度 |
| 业务负责人 | R（业务层面）| 确认业务影响范围与程度、做出业务降级/止损决策、验证业务恢复、参与事后复盘 |
| 研发负责人 | R（修复层面）| 配合技术调查、执行代码/配置修复、验证技术修复效果 |
| BISO | A（P2 及更严重事件）| 重大事件响应决策与统筹、业务线高管沟通、跨部门资源协调、主持事后复盘 |
| GRC | C → R（涉及合规时）| 评估监管报告义务、准备合规文档、协助监管沟通 |

上表适用于**事件级**处置。事件按 [16.6.1](../../第05部分_身份网络与业务连续性/第16章_业务连续性与灾难恢复/16.6_危机管理与战时指挥.md) 的判据升级为危机后（影响溢出技术范畴、需要企业最高层持续投入、需要对外承担法律与声誉后果），这张表有三处要让位：向危机管理团队与董事会的汇报收敛为事件指挥（IC）单点通道，BISO 转为在危机管理团队内提供业务影响判断，不再单独向董事会通报；对外口径由 CEO、总法律顾问与公关负责人统一出口，GSBP 与业务负责人不对外表态；监管沟通指定单点，由总法律顾问一手负责。并行的汇报线正是同一起事件对外出现多个版本数字的直接成因，三层结构与决策权限矩阵见 [16.6.2](../../第05部分_身份网络与业务连续性/第16章_业务连续性与灾难恢复/16.6_危机管理与战时指挥.md)。

#### 执行步骤

阶段 1：事件通报与初评（T+0 至 T+30min）

Step 1.1 SOC 检测与分诊：SOC 通过 SIEM/SOAR 平台检测安全事件，完成初步分诊，判定事件等级（P1–P4，定义见 11.5.2）和初步影响范围。

Step 1.2 GSBP 接收通报：P3 及更严重事件涉及 GSBP 负责业务线时，SOC 通过工单系统创建事件工单并通过即时通讯通知 GSBP。P2 及更严重事件同时通知 BISO。通报内容包括：事件类型、发现时间、初步影响范围、当前处置状态。

Step 1.3 GSBP 通知业务方：GSBP 在收到通报后 15 分钟内通知业务负责人，使用业务语言描述事件概况，避免过度技术化导致业务方无法理解。

Step 1.4 业务影响初评：GSBP 协助业务方快速评估业务影响——受影响用户数/订单数、预估收入影响、运营中断程度、客户投诉/舆情风险、合规影响（是否涉及数据泄露报告义务）。

Step 1.5 事件定级确认：根据业务影响评估结果，SOC 与 GSBP 共同确认或调整事件等级。

阶段产出：事件通报记录、业务影响初评表、事件等级确认。

阶段 2：响应决策与执行（T+30min 至 T+4h）

Step 2.1 响应方案制定：

- P3 事件：SOC 主导技术响应，GSBP 协调业务配合，无需召开正式会议
- P2 及更严重事件：BISO 召集联合响应会（SOC Lead、GSBP、业务负责人、研发负责人、必要时 GRC），确定响应策略

Step 2.2 联合响应会议程（P2 及更严重事件，时长 30min 内）：SOC 汇报（事件现状、技术分析、遏制方案）；GSBP 汇报（业务影响评估结果）；业务方确认（业务优先级、可接受的降级方案）；决策（隔离范围、业务降级措施、对外沟通口径、后续行动计划）。

Step 2.3 业务决策执行：业务方根据响应策略做出业务决策并执行——服务降级（如关闭部分功能）、客户通知（如大客户一对一沟通）、内部通报。GSBP 记录业务决策并同步至 SOC。

Step 2.4 技术响应执行：SOC 执行技术遏制措施，研发配合修复。GSBP 保持与业务方的进度同步，每小时（或按约定频率）更新响应状态。

Step 2.5 合规评估（涉及数据泄露时）：GRC 评估是否触发监管报告义务（如 GDPR 72 小时通报、PIPL 事件报告、网安法报告），输出合规评估意见。

阶段产出：响应决策记录、业务降级方案、合规评估意见（如适用）、进度更新记录。

阶段 3：恢复与验证（T+4h 至 T+24h）

Step 3.1 技术恢复：SOC 协调研发执行恢复操作，GSBP 实时同步恢复进度给业务方。

Step 3.2 业务恢复验证：业务方验证业务功能恢复正常、用户影响已消除，确认可以解除降级措施。

Step 3.3 客户沟通执行（如需）：业务方按既定口径执行客户沟通，GSBP 协助准备安全相关 FAQ。

Step 3.4 事件简报（P2 及更严重事件）：BISO 在 24 小时内向高管提交事件简报，内容包括：事件概况、业务影响、响应措施、当前状态、后续计划。

阶段产出：恢复确认记录、客户沟通记录（如适用）、事件简报（P2 及更严重事件）。

阶段 4：复盘与改进（T+7d 内）

Step 4.1 联合复盘会：BISO 主持（P3 事件可由 Senior GSBP 主持），SOC、GSBP、业务方、研发、GRC 参与。复盘内容：时间线回顾（从检测到恢复的完整时间线）、根因分析（技术根因、流程根因、人员根因）、响应评估（及时性、协作顺畅度、决策有效性）、改进识别（技术控制、业务流程、协作机制的改进点）。

Step 4.2 改进行动计划：明确每个改进点的责任人、目标完成时间、验收标准。

Step 4.3 知识沉淀：将事件处置经验沉淀到知识库，更新相关 Playbook 和 FAQ。

阶段产出：复盘报告、改进行动计划、知识库更新。

#### 分级响应矩阵

> 记号说明：本节的事件等级沿用全书统一的 **P1–P4**（定义见 [11.5.2](../../第04部分_安全运营与防御能力/第11章_安全运营/11.5_事件响应.md)，**P1 最严重**）。请注意方向：数字越小越严重，因此"P2 及更严重"包含 P2 与 P1。业务侧不另设一套事件分级：多一套记号就多一次翻译，而事件升级时最没有时间做翻译。

| 事件等级 | 定义 | 主导角色 | GSBP 职责 | BISO 职责 | 业务方职责 | 响应 SLA |
|---------|------|---------|----------|----------|-----------|---------|
| P1（危机）| 全站影响、重大泄露、监管/媒体关注 | CSO + BISO | 全力支持、7×24 待命 | 危机委员会、董事会通报 | BCP 启动、公关配合 | 2h 响应、持续作战 |
| P2（高）| 核心系统、确认数据泄露、大量用户受影响 | BISO + SOC | 业务协调、资源调度、证据收集 | 响应决策、高管沟通 | 业务决策、客户沟通 | 4h 遏制、24h 闭环 |
| P3（中）| 多系统、潜在数据风险、少量用户受影响 | SOC + GSBP | 业务通知、影响评估、进度同步 | 知情 | 确认影响、配合响应 | 8h 遏制、48h 闭环 |
| P4（低）| 单一系统、无数据泄露、用户无感知 | SOC | 知情（按需通知）| — | — | 24h 闭环 |

### 协作场景二：风险例外审批

#### 场景说明

当业务需求无法满足现行安全标准时，需要通过风险例外流程申请临时豁免。GSBP 协助业务方准备申请并设计补偿控制，GRC 负责风险评估与审批建议，BISO 负责中高风险例外的最终审批。例外机制是平衡安全控制与业务效率的重要手段，但必须严格管理以防止滥用——"例外变常态"是这一机制最常见也最危险的失效模式。

#### 执行步骤

阶段 1：例外识别与申请准备（Day 1-3）

Step 1.1 识别例外需求：GSBP 在日常安全评审中识别业务需求与安全标准的冲突，或业务方主动提出例外申请需求。

Step 1.2 替代方案评估：在正式提交例外申请前，GSBP 与业务方、相关安全团队共同评估是否存在可行的替代方案，避免不必要的例外申请。这一步骤经常被跳过，直接导致申请数量膨胀。

Step 1.3 业务必要性论证：GSBP 协助业务方准备业务必要性说明——为什么必须这样做？不做会带来什么业务影响？是否有时间窗口限制？

Step 1.4 补偿控制设计：GSBP 联合相关安全团队设计补偿控制方案——在无法满足原标准的情况下，通过哪些替代措施将风险降至可接受水平。

Step 1.5 整改计划制定：明确例外的临时性质，制定整改计划——何时能够满足原标准？整改的里程碑是什么？

Step 1.6 提交例外申请（通过工单系统）：例外描述（具体哪条标准无法满足、差距是什么）、业务必要性（业务背景、不做的影响、时间紧迫性）、风险评估（初步风险分析）、补偿控制（拟采取的补偿措施及其有效性说明）、整改计划（整改目标、里程碑、预计完成时间）、例外期限（申请的例外有效期）。

阶段产出：例外申请工单（含完整附件）。

阶段 2：风险评估（Day 4-7）

GRC 评估例外带来的风险（类型、等级、合规影响），相关安全团队提供技术评估意见，评估补偿控制有效性，提出审批建议（建议批准/有条件批准/建议拒绝）。

阶段产出：风险评估报告、审批建议。

阶段 3：审批决策（Day 8-10）

根据风险等级确定审批权限：

| 风险等级 | 审批权限 | 最长例外期限 | 复审要求 |
|---------|---------|-------------|---------|
| 低风险 | Senior GSBP | 6 个月 | 到期前 2 周复审 |
| 中风险 | Regional BISO | 3 个月 | 月度复审 |
| 高风险 | Lead BISO + GRC 负责人 | 1 个月 | 双周复审 |
| 超出风险偏好 | 风险委员会 | 逐案决定 | 周度复审 |

批准的例外录入 GRC 例外登记册。

阶段 4：例外执行与监控（例外期间）

补偿控制实施并验证；例外状态监控（补偿控制是否持续有效、是否出现风险事件、整改进度）；定期复审；整改跟踪。

阶段 5：例外关闭（整改完成或到期）

整改完成后验收；关闭例外；到期未整改时评估是否可续期，不可续期则升级至 BISO/风险委员会决策，必要时强制执行安全控制。

#### 关键检查清单

申请完整性：是否清晰描述无法满足的具体标准？是否阐述业务必要性和紧迫性？是否完成初步风险评估？是否设计补偿控制方案？是否制定整改计划和时间表？是否明确申请的例外期限？

审批决策：是否由正确权限层级审批？审批依据是否记录？例外期限和复审要求是否明确？是否录入例外登记册？

执行监控：补偿控制是否按要求实施？是否按要求进行定期复审？整改进度是否按计划推进？例外到期是否及时处理？

### 协作场景三：合规审计协作

#### 场景说明

合规审计（内部审计、外部审计、监管检查、认证审核）过程中，GRC 负责审计规划与协调，GSBP 负责业务侧证据收集与整改推动，BISO 负责重大问题协调与资源调度。高效的审计协作能够提升审计一次通过率，降低整改成本。

GSBP 在审计中的关键价值是"提前发现问题，而非被动应对"。审计前 2-4 周的预收集和预审查，往往是决定审计一次通过率的核心环节——早发现的问题可以在审计前整改，晚发现只能被当成审计发现记录在案。

#### 执行步骤

阶段 1：审计准备（审计前 2-4 周）

GRC 接收并分析审计计划（来自内审、外审或监管）；向 BISO 和相关 GSBP 下发审计通知（审计类型、审计范围、时间安排、证据清单）；GSBP 将证据清单分解至具体责任人；预收集证据并进行预审查（完整性、准确性、是否存在明显控制缺陷）；发现问题，推动业务方在审计前完成整改。

阶段产出：证据收集计划、责任分工表、预审查报告。

阶段 2：审计执行（审计期间）

GSBP 按时间要求协调各方提交证据；审计师现场检查或访谈时，GSBP 协调业务方配合并提供业务上下文；配合澄清材料准备；每日向 BISO 同步审计进展。

阶段产出：证据提交记录、澄清材料、每日进度汇报。

阶段 3：整改推动（审计后 1-3 个月）

GRC 分析审计报告，将发现分类（重大/一般/观察项）；GSBP 协助制定整改计划（整改措施、责任人、目标时间、验收标准）；GRC 审核整改方案有效性；GSBP 每周跟踪整改进度；严重滞后或重大阻塞时升级至 BISO 协调。

阶段 4：整改验收（整改完成后）

GSBP 协调准备整改证据；GRC 内部验收；配合外部验收（如需）；GRC 发送闭环确认。

#### 关键检查清单

审计准备：是否收到并理解审计计划和范围？证据清单是否分解到具体责任人？是否完成证据预收集？预审中发现的问题是否已整改？

整改推动：是否针对每个发现制定整改计划？整改方案是否经 GRC 审核？是否每周跟踪整改进度？重大阻塞是否及时升级？

### 协作场景四：威胁情报响应

#### 场景说明

当威胁情报团队发布针对性威胁预警（如针对特定行业的攻击活动、影响企业使用组件的零日漏洞）时，GSBP 需要快速评估对所负责业务线的影响，协调业务方配合响应。

#### 执行步骤（简化流程）

Step 1 情报接收：SOC/威胁情报团队通过安全简报或即时通讯向 GSBP 推送威胁情报摘要，包括威胁描述、影响范围、建议措施。

Step 2 业务影响评估：GSBP 快速评估威胁对所负责业务线的影响——是否使用受影响的组件/系统？暴露面有多大？业务关键性如何？

Step 3 响应协调：根据评估结果：无影响（记录评估结论，归档）；有影响（通知业务方和研发，协调执行建议措施，如紧急补丁、临时缓解）。

Step 4 状态跟踪：GSBP 跟踪响应措施执行进度，直至威胁解除或风险降至可接受水平。

### 运行指标

事件响应协作：业务通报及时率（P3 及更严重事件 15 分钟内通知 GSBP 的比例，目标 ≥95%）；业务影响评估完成率（30 分钟内完成初评的比例，目标 ≥90%）；复盘行动闭环率（复盘识别的改进项按时完成的比例，目标 ≥85%）。

例外管理：例外审批周期（从申请到审批完成的平均天数，目标 ≤10 天）；例外按时关闭率（在例外期限内完成整改关闭的比例，目标 ≥80%）；补偿控制实施率（批准例外中补偿控制按要求实施的比例，目标 100%）。

合规审计：证据按时提交率（目标 ≥95%）；整改按时完成率（目标 ≥90%）；审计一次通过率（目标 ≥85%）。

整体协作：协作满意度（业务侧和安全中心侧对 GSBP 协作的满意度评分，目标 ≥4.0/5.0）；升级率（需要升级至 BISO 或更高层级的需求占比，目标 ≤15%，过高说明授权不足，过低可能说明该升级的没升级）；跨职能需求 SLA 达成率（目标 ≥90%）。

## 3.4.8 Playbook 7：组织 AI 资产治理（影子 AI 发现与 Agent 登记）

### 场景定义

前面几个 Playbook 处理的是"业务方主动带着一个 AI 应用来找 GSBP 评审"的情形——有明确的申请人、明确的上线时间、明确的评审入口。但组织里真正让 GSBP 头疼的，往往是那些没有走评审流程、没人申报、悄悄跑起来的 AI。市场部用一个 SaaS 工具批量生成文案，工具背后接了大模型；研发在 CI 流水线里挂了个自动写单元测试的 agent；某个运营同学用浏览器插件把客户对话喂给外部模型做摘要——这些没有一件经过 3.4.5 的评估流程，却实实在在地在处理公司数据、调用外部接口、甚至替人做决定。这类"IT 与安全不知情的 AI"就是影子 AI，而本 Playbook 处理的，正是"先把它们找出来、登记清楚，再纳入治理"这件事。

云安全联盟（CSA）2026 年 4 月的一份调研（418 份样本，厂商赞助）称，约 82% 的企业环境中存在 IT 不知情的 AI agent；IBM《2025 数据泄露成本报告》则称约五分之一的受访组织报告过与影子 AI 相关的泄露。**那个 67 万美元要小心用**：它是"影子 AI 使用程度高的组织"与"低或无的组织"之间的**组织级平均成本差**，不是"单起影子 AI 泄露事件比普通事件贵 67 万"。这两种读法差别很大——前者可能混入了组织规模、行业、AI 采用度等一堆共变因素，后者才是因果性的表述，而报告并没有支持后者。两个数字来自不同机构、不同年份、不同样本，不能拼成一条因果链。这两个数字放在一起说明的是同一件事：AI 的引入门槛已经低到业务方一个人、一张信用卡、一个下午就能完成，而组织的发现和治理能力远远跟不上这个速度。

场景描述：系统性地发现组织内已经运行或正在被引入的 AI 系统与自主 agent（含未经申报的影子 AI），完成资产登记、分类分级，并纳入持续治理，让"组织到底有多少 AI、分别在干什么、风险如何"这个问题始终有一个可信的答案。

适用范围：

- 影子 AI 的周期性主动发现（网络流量、SaaS 采购、代码仓库、浏览器插件等多个来源）
- 已知 AI 系统与 agent 的登记建档（AI-BOM、Agent Registry）
- AI 资产的分类分级与责任归属确认
- AI 资产清单的持续更新与治理状态跟踪

触发条件：

- 组织启动 AI 治理体系建设或申请 ISO 42001 认证
- 周期性影子 AI 发现扫描（建议按季度，高变动组织可缩短至月度）
- 新采购的 SaaS/工具被识别为含 AI 能力
- 监管或审计要求提供组织 AI 资产清单

排除场景：

- 单个 AI 应用上线前的安全评估（走 3.4.5 新兴技术评估）
- AI 系统自身遭受对抗攻击、提示注入等的防御机理（属通用防御范畴，机理见 18.3，本节只负责把资产找出来并登记，不复述攻击面防御）

适用边界：本 Playbook 解决的是治理域内"发现—登记—治理"这条循环，不替代针对具体 AI 应用的深度安全评审。发现能力永远无法做到 100% 覆盖，登记也必然滞后于 agent 的实际蔓延速度，因此这里追求的是"持续收敛"而非"一次性清零"——把未知资产的比例压到可控范围，并让新增资产尽快进入登记，而不是幻想某个时点组织内不存在任何影子 AI。

### CSA 五步 AI 治理流程

云安全联盟（CSA）提出的 AI 治理路径可以概括为五个前后衔接的步骤，本 Playbook 的执行步骤即沿这条主线展开：

```
发现 ──▶ 分类 ──▶ 评估 ──▶ 控制 ──▶ 监控
 │        │        │        │        │
找出组织   按数据    评估风险   施加治理   持续跟踪
内所有     敏感度、   等级与    与技术     资产变化
AI/agent   自主性、   合规影响   控制措施   与新增
（含影子）  用途分级                       影子 AI
 │                                        │
 └────────────── 回流：监控发现的新资产重新进入发现-分类 ──┘
```

这条链路是一个环而非一条直线——监控阶段发现的新 agent、被改动用途的旧模型，都要重新回到发现与分类。把它画成一个圈，是为了提醒 GSBP：AI 资产治理没有"完成"的一天，只有"当前收敛到什么程度"。

### 执行步骤

阶段 1：发现（Discovery）

单一手段无法覆盖影子 AI 的全部入口，发现必须是多来源交叉的。常见的发现向量包括：网络出向流量分析（识别流向已知大模型 API 端点的调用）、SaaS 与采购数据比对（从报销、订阅、SSO 登录记录中识别含 AI 能力的工具）、代码仓库扫描（在源码与依赖中查找模型调用、AI SDK、API 密钥）、浏览器插件与终端软件清点、身份与 OAuth 授权审查（哪些第三方 AI 应用被授予了访问企业数据的权限）。

这一阶段可借助专门工具提升覆盖面：Microsoft Agent 365 提供 agent 的统一控制平面并具备影子 AI 发现能力；Arthur ADG 从多个向量做 agent 发现；Mend AI 侧重扫描代码库找出嵌入其中的影子 AI 调用。工具能力各有侧重、覆盖向量不同，没有任何单一产品能穷尽所有入口，实际落地通常需要组合使用并辅以人工访谈。需要如实说明的是，这些工具都是厂商产品，发现率取决于部署范围与集成深度，厂商宣称的覆盖能力应在自己环境中验证后再采信。

阶段产出：影子 AI 发现清单（含来源、置信度、初步用途判断）。

阶段 2：分类（Classification）

发现只是把资产摆上台面，分类决定后续投入多少治理资源。建议至少沿三个维度分级：数据敏感度（该 AI 是否接触 PII、支付、商业机密）、自主性（是被动的内容生成工具，还是能自主调用工具、执行动作、做出决策的 agent）、用途关键性（是否嵌入核心业务流程或对外决策）。自主性维度在 agent 场景中尤为重要——一个能自己调 API、改数据、触发交易的 agent，其风险量级远高于一个只会生成草稿的模型。

阶段产出：AI 资产分级表、责任归属确认（每个资产必须有明确的业务 owner）。

阶段 3：评估（Assessment）

对分级后的资产评估风险等级与合规影响。此处与 3.4.5 的单应用评估衔接：高敏感度、高自主性的资产应触发完整的新兴技术评估流程（含 EU AI Act 风险分级判定，见 3.4.5）；低风险资产则登记备案即可，无需重型评估。评估的目的是给每个资产贴上"该管到什么程度"的标签，避免把有限的评审资源平均撒在所有资产上。

阶段产出：资产风险评估结论、需深度评审的资产清单。

阶段 4：控制（Control）——AI-BOM 与 Agent Registry

治理落到实处，靠的是两份持续维护的清单。

AI-BOM（AI 物料清单）借鉴了软件物料清单（SBOM）的思路，记录一个 AI 系统的构成要素：使用的基础模型及版本、训练或微调数据的来源、依赖的第三方 AI 服务与 API、模型的许可条款、已知的模型层面风险。它回答的是"这个 AI 系统是由什么拼起来的"，在模型出现漏洞、数据合规问题或供应商事件时，AI-BOM 是快速定位影响范围的依据。

Agent Registry（Agent 登记册）则聚焦自主 agent 这一特定类型，登记每个 agent 的身份、owner、被授予的权限与可调用的工具、能访问的数据范围、运行环境。它回答的是"组织里有哪些 agent、各自能做什么、谁为它负责"。随着 agent 数量增长，未登记的 agent 就是未受控的权限，Agent Registry 的价值正在于把这种权限显性化、可审计。

两份清单的字段可以粗略对照如下：

| 维度 | AI-BOM | Agent Registry |
|-----|--------|----------------|
| 登记对象 | AI 系统 / 模型 | 自主 agent |
| 核心字段 | 基础模型、数据来源、第三方依赖、许可、模型风险 | agent 身份、owner、权限与工具、数据访问范围、运行环境 |
| 主要用途 | 供应链与合规溯源、漏洞影响定位 | 权限治理、行为审计、责任归属 |
| 触发更新 | 模型/数据/依赖变更 | agent 上线、权限调整、下线 |

关于这两份清单的落库形态，有一条必须先说清楚，否则很容易被做成两个互不同步的表：**它们是同一本册子的两个视角，不是两个数据库。** 全书的 AI 系统清单只有一份，字段定义以 [18.1.2](../../第06部分_AI驱动的安全创新/第18章_AI系统安全/18.1_AI安全治理框架.md) 的 JSON Schema 为准（一条记录对应一个在册 AI 系统，agent 相关信息落在同一条记录的 agent 能力字段上，不另开一条）。上表右列描述的是"看 agent 时要看哪些字段"，不是"另建一张 agent 表"。分开建册的代价不是多维护一张表，而是两张表会各自漂移——某个 agent 换了底座模型，AI-BOM 更新了、Agent Registry 没更新，事故复盘时就会得到两个互相矛盾的答案。本 Playbook 负责的是这份清单怎么被发现、由谁登记、多久重扫一次；字段填什么、哪些必填、覆盖度怎么机器核查，交 18.1.2。

除了建册，控制阶段还包括对不合规资产施加处置：高风险影子 AI 先隔离或下线、再走正式评估补登记；越权的 agent 收回多余权限；缺少 owner 的资产强制指定责任人。此外可引入 Credo AI 这类 AI 治理平台承载政策、评估与合规映射，用 ISO 42001 作为可认证的 AI 管理体系（AIMS）框架来组织整个治理动作——ISO 42001 是目前可供第三方认证的 AI 管理体系标准，为"组织如何治理 AI"提供了体系化要求。

阶段产出：AI-BOM、Agent Registry、不合规资产处置记录。

阶段 5：监控（Monitoring）

治理不是建完清单就结束。监控阶段持续跟踪已登记资产的变化（模型升级、权限变更、用途漂移）并周期性重跑发现流程，捕捉新增的影子 AI。监控发现的新资产回流到阶段 1，重新走一遍完整流程。这里最现实的难点是：agent 的新增速度往往快于发现周期，两次扫描之间总会有一段"未知窗口"，登记册永远滞后于真实状态。承认这一点，把指标定为"未知资产收敛趋势"而非"零影子 AI"，才是可执行的目标。

阶段产出：AI 资产治理状态报告、新增影子 AI 清单、治理趋势分析。

### 关键检查清单

发现覆盖：是否覆盖网络流量、SaaS 采购、代码仓库、浏览器插件、OAuth 授权等多个发现向量？发现工具的部署范围是否覆盖主要业务网段与终端？是否辅以人工访谈补齐工具盲区？

登记完整：每个已知 AI 系统是否建立 AI-BOM？每个自主 agent 是否登记入 Agent Registry？每个资产是否有明确的业务 owner？登记信息是否包含数据访问范围与权限清单？

分类分级：是否按数据敏感度、自主性、用途关键性完成分级？高自主性 agent 是否被识别并重点关注？高风险资产是否触发了深度评估（衔接 3.4.5）？

控制处置：不合规的影子 AI 是否有明确处置（隔离/下线/补登记）？越权 agent 的多余权限是否已回收？治理动作是否映射到 ISO 42001 等可认证框架的要求？

持续监控：是否设定周期性重扫机制？已登记资产的变更是否被跟踪？新增影子 AI 是否能回流进入发现流程？

关键约束：AI 资产治理的根本矛盾在于发现能力与蔓延速度之间的赛跑。业务方引入 AI 的门槛极低，而任何发现手段都存在覆盖盲区、任何登记都存在滞后，因此这个 Playbook 追求的是把未知资产比例持续压低并稳住，而非承诺某一时点的完全清零。同时，过严的登记要求会把业务方逼向更隐蔽的影子使用，登记流程必须足够轻量，让"申报"比"藏着"更省事，治理才可持续。

常见误区：把发现等同于治理（扫出一份清单就宣告完成，却没有后续的分类、控制与监控，清单很快过期作废）；只治理"申报的 AI"（评审流程只覆盖主动上门的应用，对占比更大的影子 AI 视而不见）；登记与业务脱节（AI-BOM 和 Agent Registry 由安全团队单方面维护，业务方不参与更新，导致清单与实际状态偏离）；工具迷信（认为部署一个发现平台就能穷尽所有影子 AI，忽视工具的覆盖向量局限与厂商宣称与实际效果的差距）。

验证方法：通过独立抽样（如随机访谈若干业务团队、比对采购与 SSO 记录）评估发现清单的实际覆盖率，度量"抽样发现但清单未收录"的比例；在模型或供应商出现安全事件时，检验 AI-BOM 能否快速定位受影响系统；审查 Agent Registry 中的权限记录与 agent 实际持有权限是否一致。

运行指标：AI 资产登记覆盖率（已登记资产占估计总量的比例，及其随时间的收敛趋势）、影子 AI 发现数与处置完成率（发现后完成登记或下线的比例）、高风险资产深度评估完成率、Agent Registry 权限准确率（登记权限与实际权限一致的比例）、发现流程重跑周期（两次扫描的实际间隔）。

## 3.4.9 Playbook 管理与持续优化

### Playbook 生命周期管理

Playbook 不是一次性文档，而是需要持续维护的活性资产。一个 18 个月没有更新的 Playbook，很可能已经和实际流程脱节，GSBP 执行时会发现处处是例外，最终走向弃用。

生命周期八个阶段：

创建：识别高频场景，组织专家工作组，起草 Playbook 初稿。内容必须来源于实际执行经验，而非凭空设计。

试用：在 1-2 个项目试用，收集执行反馈，识别改进点。应选择典型场景，确保反馈的代表性。

验证：验证可行性与有效性，评估时间与成本，确认适用范围。需要量化 Playbook 带来的效率提升和质量改善。

发布：正式发布到知识库，培训团队使用，纳入绩效考核。需要确保所有 GSBP 知晓并理解 Playbook 内容。

执行：按 Playbook 执行项目，记录执行数据，跟踪成功指标。执行阶段的数据积累为后续优化提供依据。

复盘：季度复盘会议，分析执行数据，收集改进建议。应结合 VOC 反馈和执行指标进行。

优化：根据反馈优化，更新版本号，重新发布。保持小步迭代，避免大范围改动导致执行混乱。

归档：场景不再适用时归档，保留历史版本，标注废弃原因。归档的 Playbook 仍可作为新 Playbook 开发的参考。

### Playbook 质量评估

Playbook 质量从五个维度评估：

完整性：是否包含所有必需章节？前置条件是否清晰？执行步骤是否完整？产出物是否明确？

可操作性：新人是否能独立执行？步骤描述是否具体？是否有模板与工具支持？时间估算是否准确？

有效性：是否达到预期目标？风险是否得到控制？业务是否满意？是否有成功案例？

易用性：文档是否易读？是否有流程图/检查清单？是否有常见问题 FAQ？是否易于查找？

维护性：是否定期更新？版本管理是否清晰？修订历史是否记录？负责人是否明确？

质量评估应纳入 Playbook 管理的常规流程，建议每季度对所有 Playbook 进行一次质量审查，识别需要优化或归档的 Playbook。

运行指标：Playbook 使用率（实际使用 Playbook 执行的项目占比）、Playbook 更新频率（平均更新间隔）、Playbook 质量评分（五维度综合得分）。

# 7.8　供应链风险检测与响应

> 导读：本节构建端到端的检测与响应体系，四个层次依次推进：持续监控架构（7.8.1）是基础设施层，威胁情报集成（7.8.2）是输入层，异常检测（7.8.3）是分析层，事件响应（7.8.4）与自动化修复（7.8.5）是执行层。7.8.3 从规则与离群打分往前一步，讲 agentic 恶意包研判如何把"标出可疑包之后"的元数据核对、沙箱观察、维护者比对、最终定性交给一组智能体自主跑；7.8.5 补充 AI 起草依赖修复 PR 的落地与护栏。如果你的组织当前没有任何自动化检测能力，建议从 7.8.2 的 CISA KEV 集成和 7.8.3 的 Prometheus 告警规则开始，这两者实施成本最低但效益最高。Log4Shell 事件的实际响应过程见 7.10 案例四，可作为本节理论框架的对照参考。

传统的周期性漏洞扫描在应对供应链攻击时有根本性缺陷：攻击者可能在两次扫描之间完成入侵、横向移动乃至数据窃取。SolarWinds 攻击在部分目标网络中潜伏数月未被察觉。这意味着"定期检查"的思路需要被"持续监控"替代——检测延迟直接决定损失范围。

## 7.8.1 持续监控架构

### 设计约束与权衡

供应链监控面临的核心挑战：数据源异构（Git 日志、CI/CD 事件、SBOM 数据、扫描结果、威胁情报格式各不相同）、事件量大（大型组织每日产生数十万条相关事件）、关联分析复杂（需要将漏洞信息与实际部署的组件版本精确匹配）。

架构设计时的四个关键权衡：

收集延迟 vs. 存储成本：实时流式收集延迟最低，但原始日志的长期存储成本可观。通常的做法是：原始事件流保留 7-30 天，聚合统计指标长期保留。

灵敏度 vs. 误报率：规则越敏感，越能发现早期攻击信号，但误报也越多。误报率过高会导致告警疲劳——安全团队开始忽略告警。需要在两者间找到平衡点，并持续调优。

覆盖率 vs. 运维复杂度：覆盖的数据源越多，检测盲区越小，但也需要更多工程资源维护数据管道。对于小型团队，从 CI/CD 日志和漏洞扫描结果开始，比建设完整堆栈更实际。

自动化程度 vs. 决策风险：自动化响应速度快，但错误的自动化决策（如误隔离关键服务）可能造成业务中断。建议按事件严重程度分层：CRITICAL 事件触发自动遏制，HIGH 事件触发自动工单创建但需人工决策。

### 可观测性堆栈分层

数据源层（产生原始事件）：Git 提交日志、CI/CD 流水线事件、SBOM 数据、漏洞扫描结果、威胁情报源、运行时遥测、制品仓库访问日志。

收集层（汇聚、解析、路由）：Fluent Bit、Vector 等轻量级日志收集器处理日志流；Kafka 或 NATS 处理高吞吐场景；关键需求是格式标准化——不同工具产生的事件格式差异很大，需要在收集层统一转换。

分析层（存储、检索、关联）：Elasticsearch/OpenSearch 用于全文检索和关联分析；Prometheus/VictoriaMetrics 处理时序指标；Grafana 实现可视化。SIEM（Splunk、Microsoft Sentinel）在此层提供安全专用的关联规则引擎。

响应层（告警分发、自动化处置）：PagerDuty 等工具路由告警到值班人员；与工单系统（Jira）集成自动创建任务；自动化修复触发器（见 7.8.5）。

### 适用边界与常见误区

不适用场景：小型团队（20 人以下开发团队）不需要一开始就构建完整堆栈。GitHub/GitLab 原生的 Security Advisories 和 Dependabot/Renovate 已经可以覆盖大部分基础需求。等到团队规模和代码库复杂度达到一定程度，再投资完整监控堆栈。

常见误区一：只收集不分析。部署了日志收集管道，但缺乏有效的检测规则和专职的分析人员，海量数据沦为存储负担，成本持续产生但没有安全价值。

常见误区二：忽视数据质量。日志格式不统一、时间戳不准确（不同时区、不同精度）、关键字段缺失，导致关联分析失效。数据管道的质量保障（schema 验证、完整性检查）需要与安全规则同等重视。

### 验证方法

- 覆盖率测试：构造测试事件（如在 CI 流水线中模拟引入已知恶意依赖），验证能否在预期时间内被检测到。
- 端到端延迟测量：在数据源产生事件时打上时间戳，与进入分析层的时间戳对比，确认 P95 延迟满足目标。
- 告警链路验证：定期（每月）执行已知会触发告警的操作，验证告警能正确路由到值班人员。

### 运行指标

| 指标名称 | 说明 | 参考阈值 |
|---------|------|---------|
| 事件收集延迟 | 从产生到进入分析层的时间 | P95 < 5 分钟（一般场景）；P95 < 1 分钟（高安全要求） |
| 日志丢失率 | 未成功收集的事件比例 | < 0.1%；关键安全事件要求 0 丢失 |
| 告警触发时间 | 从事件发生到告警产生的时间 | CRITICAL < 5 分钟；HIGH < 15 分钟 |
| 告警处置时间 | 从告警产生到人工确认的时间 | CRITICAL < 30 分钟；HIGH < 2 小时 |

阈值说明：上述阈值为行业实践参考值。建议先建立基线（记录当前实际表现），再设定改进目标，避免直接对标行业最优值而忽视当前组织能力约束。

## 7.8.2 威胁情报集成

### 为什么威胁情报是必要的

内部漏洞扫描只能发现已在扫描数据库中的漏洞，且扫描频率决定了发现延迟。威胁情报的价值在于：能够在漏洞公开披露的第一时间就启动内部影响评估，而不是等到下一次扫描周期。

CISA KEV（已知被利用漏洞目录）是最高优先级的情报源——收录的漏洞已经在野被利用，意味着攻击工具已经广泛可用，延迟修复的风险极高。

### 多源情报体系

CISA KEV：最高优先级，已在野利用。KEV 目录以 JSON/CSV 形式公开发布，可订阅并自动比对本组织 SBOM；美国联邦机构受 BOD 22-01 约束需在目录规定期限内修复，非联邦组织亦可直接借用该期限作为内部 SLA 的锚点[1]。

OSV（Open Source Vulnerabilities）：Google 发起、现由 OpenSSF 托管的开源漏洞数据库与 OSV Schema，覆盖多个生态系统（PyPI、npm、Maven、Go、Rust 等），可直接与 SBOM 数据对接进行自动化关联分析[2]。

EPSS（Exploit Prediction Scoring System）：由 FIRST 维护，给出漏洞在**未来 30 天内被利用的概率估计**（0-1），每日更新[3]。需要强调 EPSS 与 CVSS 的定位差异：CVSS 衡量的是"一旦被利用有多严重"，EPSS 衡量的是"多大概率会被利用"，两者相乘才逼近真实风险，任何一方单独使用都会系统性错配资源。

GitHub Security Advisories + NVD：覆盖广泛，适合作为补充数据源。

### 核心数据模型

以下数据结构展示了威胁情报与 SBOM 关联所需的关键字段。`exploited_in_wild` 和 `epss_score` 是优先级排序的核心依据：

```python
from dataclasses import dataclass, field
from datetime import datetime
from enum import Enum
from typing import List, Optional

class Severity(Enum):
    CRITICAL = "CRITICAL"
    HIGH = "HIGH"
    MEDIUM = "MEDIUM"
    LOW = "LOW"
    INFO = "INFO"

@dataclass
class ThreatIntelligence:
    """威胁情报数据模型"""
    id: str
    source: str                       # 情报来源（CISA KEV / OSV / GitHub 等）
    severity: Severity
    package_name: str
    package_ecosystem: str            # npm / PyPI / Maven 等（与 SBOM 中的 ecosystem 字段对应）
    vulnerability_id: Optional[str]   # CVE ID 或 GHSA ID 等
    description: str
    remediation: str
    published_at: datetime
    epss_score: Optional[float] = None        # 被利用概率，0-1
    exploited_in_wild: bool = False           # 是否在 CISA KEV 中
    references: List[str] = field(default_factory=list)
    
    def priority_score(self) -> float:
        """
        计算综合优先级评分，用于响应排序。
        在野利用是最高加权因子——任何在野利用的漏洞都需要立即响应。
        """
        score = self.severity.value == "CRITICAL" and 4.0 or \
                self.severity.value == "HIGH" and 3.0 or \
                self.severity.value == "MEDIUM" and 2.0 or 1.0
        
        if self.exploited_in_wild:
            score *= 3.0   # KEV 漏洞优先级提升 3 倍
        
        if self.epss_score and self.epss_score > 0.5:
            score *= 1.5   # 高 EPSS 分进一步提升
        
        return score
```

### EPSS 优先级排序矩阵

漏洞数量通常远超修复能力，需要有效的优先级机制。EPSS 与 CVSS 的组合使用：

| CVSS 评级 | EPSS < 0.1 | EPSS 0.1-0.5 | EPSS > 0.5 |
|---------|-----------|-------------|-----------|
| CRITICAL | 7 天内修复 | 3 天内修复 | 立即响应 |
| HIGH | 30 天内修复 | 14 天内修复 | 3 天内修复 |
| MEDIUM | 90 天内修复 | 30 天内修复 | 14 天内修复 |
| CISA KEV | 无论其他评分，立即响应 |||

适用边界：上表的具体修复时限为本书按落地经验给出的建议（示例口径，非行业基准），应结合自身变更窗口与合规要求重新标定；真正需要照搬的是它的结构——用 EPSS 横轴叠加 CVSS 纵轴，并让 KEV 直接短路整张表。EPSS 数据每日更新，评分会随时间变化，一个漏洞的 EPSS 分从低到高是常见现象（随着 PoC 代码公开），需要定期重新评估优先级而非一次性排序[3]。此外，对"漏洞虽存在但在本产品的调用路径中不可达"的情况，应以 VEX（漏洞可利用性交换）文档显式表达，避免下游把不可利用项当作待修项处理[4]。

### 常见误区

误区一：情报过载。订阅过多情报源但缺乏有效过滤，导致每日需要处理数百条告警。选择 2-3 个高质量情报源（CISA KEV、OSV、GitHub Advisories）并与 SBOM 精确关联，比订阅 10 个来源但缺乏关联分析更有价值。

误区二：缺乏资产上下文。仅推送"发现 CVE-XXXX-YYYY"但不关联内部受影响的具体服务与版本，安全团队无法判断是否受影响，只能手动查找，抵消了情报自动化的价值。准确的 SBOM 是情报关联的前提（见 7.3 的 SBOM 体系建设）。

### 验证方法

选取 5 个已知漏洞（包含不同严重级别），验证系统是否在情报更新后能正确识别内部受影响组件，并按预期触发告警。

## 7.8.3 异常检测与告警

### 基于规则的检测

规则检测适用于已知模式，优点是可解释性强、误报可控。以下 Prometheus 告警规则覆盖供应链场景的典型检测点：

规则的 `annotations.action` 字段特别重要——它在告警产生时直接告知值班人员应该采取什么行动，避免在紧急情况下还需要查找响应手册：

```yaml
groups:
  - name: supply_chain_security
    interval: 30s
    rules:
      # 检测点 1：新增 CRITICAL 漏洞
      # 触发条件：SBOM 关联分析发现新的 CRITICAL 级漏洞
      # 为什么需要：CRITICAL 漏洞的修复窗口通常很短，发现即响应
      - alert: NewCriticalVulnerabilities
        expr: |
          sum(vulnerability_severity{severity="CRITICAL"}) by (package_name) > 0
        for: 1m
        labels:
          severity: critical
          category: supply_chain
        annotations:
          summary: "检测到新的 CRITICAL 漏洞"
          description: "组件 {{ $labels.package_name }} 中发现 CRITICAL 漏洞"
          action: "立即停止包含此组件的服务部署，评估影响范围，启动修复流程"

      # 检测点 2：镜像签名验证失败
      # 触发条件：任何镜像在准入控制阶段签名验证失败
      # 为什么需要：签名验证失败可能是镜像被篡改或来源不可信的信号
      - alert: ImageSignatureVerificationFailed
        expr: |
          rate(image_signature_verification_failures_total[5m]) > 0
        for: 1m
        labels:
          severity: critical
          category: supply_chain
        annotations:
          summary: "镜像签名验证失败"
          description: "检测到未签名或签名无效的镜像尝试部署"
          action: "阻止部署，审计镜像来源和推送者身份，检查仓库访问日志"

      # 检测点 3：SBOM 缺失
      # 触发条件：部署时检测到镜像无对应 SBOM
      # 为什么需要：无 SBOM 意味着无法进行漏洞关联分析，违反可追溯性要求
      - alert: MissingSBOM
        expr: |
          sum(deployments_without_sbom) > 0
        for: 5m
        labels:
          severity: high
          category: supply_chain
        annotations:
          summary: "检测到部署缺少 SBOM"
          description: "{{ $value }} 个部署缺少 SBOM"
          action: "拦截部署，要求重新构建并生成 SBOM 后再部署"

      # 检测点 4：依赖变更异常
      # 触发条件：短时间内出现大量依赖更新，超过历史基线的 3 倍
      # 为什么需要：批量依赖替换可能是恶意篡改或自动化工具失控的信号
      - alert: AbnormalDependencyChurn
        expr: |
          rate(dependency_updates_total[1h]) > 
          3 * avg_over_time(rate(dependency_updates_total[1h])[7d:1h])
        for: 10m
        labels:
          severity: high
          category: supply_chain
        annotations:
          summary: "检测到异常依赖变更速率"
          description: "当前依赖变更速率超过历史基线 3 倍以上"
          action: "审查近期依赖变更提交，确认是否为预期的批量更新"
```

### 基于机器学习的异常检测

规则检测的盲区在于未知攻击模式——对于从未见过的攻击手法，规则无法触发。机器学习检测可以发现统计上偏离正常的行为，即使没有预定义的规则。

Isolation Forest 适合检测多维特征空间中的离群点。供应链场景的特征向量可包含：依赖更新频率、版本跳跃幅度（major/minor/patch 级别）、新增/删除依赖数量、维护者变更次数、许可证变更次数、包大小变化率、文件数量变化率。

关键约束：机器学习模型需要足够的历史数据才能建立可靠的基线，且结果可解释性较弱。安全团队需要理解"这个变化为什么被标记为异常"。建议将机器学习告警作为"需要关注"的候选，而非直接触发响应。

常见误区：把机器学习当成万能方案，投入大量资源建设模型，却发现准确率不达预期，最终废弃。正确的做法是：规则检测覆盖已知威胁模式，机器学习作为补充层发现未知异常，两者组合使用。

### 从异常打分到 agentic 恶意包研判

上面的 Isolation Forest 只是把一个可疑的包"标出来"——它给出一个离群分数，告诉你这个包在多维特征上偏离了历史基线，但它不知道这个包到底干了什么，也不会替你做出"拦还是放"的判断。规则命中和离群分数都停在"值得看一眼"这一步，剩下的元数据拉取、行为观察、维护者背景核对、最终定性，还是靠安全工程师一项一项手工做。而恶意包投毒的速度不等人：一个新版本从上传到被 CI 拉进构建，往往只有几分钟。真正的瓶颈不是"标不出来"，而是"标出来之后的研判太慢"。

2025 到 2026 年，供应链安全厂商陆续把这条研判链路交给一组各司其职的智能体自主跑。思路和 11.4.6 的自主狩猎、17.3 的自主调查是同一种：把一个长程、多步、每步需要不同专长的任务，拆成专职 agent 加一个编排器，而不是让单个大模型一把抓。恶意包研判恰好是这样的任务——拉元数据靠仓库 API 知识，跑沙箱靠动态分析能力，核对维护者背景靠发布历史比对，最终定性靠对攻击手法的经验判断。单体智能体一路做下来，容易在中途丢失原始问题、把某一步的误读一路带到底。

一套可自主运行的恶意包研判智能体团队，通常这样分工：

```
        ┌────────────────────────────────────┐
        │  编排器（持有研判目标+沙箱预算上限）    │
        │  串联各 agent、决定拦/放/上报人工      │
        └──┬────────┬────────┬────────┬───────┘
   ┌───────┘        │        │        └────────┐
┌──▼────────┐ ┌────▼─────┐ ┌▼──────────┐ ┌────▼──────┐
│元数据 agent│ │沙箱执行   │ │维护者/发布 │ │ LLM 研判   │
│拉包版本、  │→│agent：隔离 │→│变更关联    │→│agent：汇总 │
│依赖树、    │ │环境跑安装/ │ │agent：比对 │ │上游信号，  │
│脚本、发布  │ │import，观察│ │新维护者、  │ │给出定性+   │
│者、下载量  │ │外连/落盘/  │ │发布节奏突  │ │理由+置信度 │
│           │ │提权行为    │ │变、账号新旧│ │           │
└───────────┘ └───────────┘ └───────────┘ └─────┬─────┘
      ▲                                          │
      │  可疑但证据不足→派生新探查                 │ 够格才拦
      └──────────────────────────────────────────┤
   记忆：已研判包、已知恶意特征、误报样本            ▼
   （承 17.2.2 智能体记忆）回流下一轮      人工闸门 → 拦截/下架 或 放行
```

怎么读这张图：编排器是唯一持有全局目标和沙箱预算的角色，其余 agent 只负责自己那一步。元数据 agent 先把包的静态画像拉齐——版本、依赖树、安装脚本、发布者身份、下载量曲线；沙箱执行 agent 在隔离环境里真正跑一遍安装和 import，观察它是否外连陌生域名、是否往敏感路径落盘、是否尝试提权或读取凭证文件；维护者/发布行为关联 agent 比对这次发布和历史节奏的差异——是不是一个几年没动的包突然发新版本、是不是发布账号刚刚换过人；最后 LLM 研判 agent 把上游所有信号汇总，给出"恶意/可疑/正常"的定性、判断理由和置信度。编排器据此决定：证据确凿就交人工闸门拦截，证据不足就派生新的探查动作再跑一轮。

厂商侧的落点各有不同，理解它们的分野比记住任一家的功能列表更有价值。Socket 走的是 agentic 加实时拦截的主线，对每个新上传的包做行为分析（厂商称对约 150 类信号实时打分），目标是在包进入构建之前就拦下——在 2026 年 4 月针对 PyTorch Lightning 的 PyPI 包（`lightning` 2.6.2/2.6.3，import 即触发凭据窃取）投毒事件中，Socket 称其 AI 扫描在恶意版本发布约 18 分钟后即将其标记出来。Endor Labs、Snyk、Phylum 则把 agentic 能力更多用在依赖分析与研判归类上，把"这个依赖到底要不要管、是不是误报"这类判断交给智能体先过一遍，减少人工要看的量。这些数字与时间都是厂商公开口径，反映的是特定事件下的表现，不等于对所有投毒手法都成立，选型时应在自己的依赖清单上用一批已知样本复测。

用什么数据回测这套研判？本章 7.3 已经记录了 PyPI（2024 年删除恶意包超 12,000 个，typosquatting、依赖混淆、星标劫持）和 npm（依赖混淆、账户劫持、manifest confusion）的真实投毒历史，这些已定性的样本可以直接当作研判智能体的回归靶场——把已知恶意包喂进去，看编排链能否稳定复现"恶意"定性，把已知正常包喂进去，统计误报率。2026 年的几起活跃投毒 campaign 同样是现成靶标：Shai-Hulud（及其变体 Mini）在 npm 上投放约 471 个恶意 artifact（安全厂商披露口径），波及 Mistral、UiPath、TanStack 等多个知名项目的关联包；LiteLLM 的 LLM 网关组件被投毒，恶意版本会窃取部署环境里的 Kubernetes secret。这类针对 AI 基础设施本身的投毒，正是把研判前移到"进构建之前"的现实理由。

能力边界必须交代清楚，两面都要讲明白。agentic 研判扩大了覆盖：它能对每个新版本自动跑完整条链路，而人工只够抽查其中一小部分；它也能捕捉规则写不出来的组合信号（一个刚换维护者、又新增了网络外连、下载量却异常陡增的包）。但它同样放大错误。沙箱不是万能的——有经验的攻击者会让恶意行为只在特定时间、特定环境、或延迟若干天后才触发，专门规避沙箱的短时观察窗口；LLM 研判 agent 也会误判，把一次正常的重构大版本升级读成"行为突变"，或反过来被精心伪装的包骗过。更要紧的是错误会沿链传播：元数据 agent 的一个误读会被沙箱 agent 当成前提、被研判 agent 写进结论，越往后越像真的。这正是"拦截/下架依赖"这类不可逆动作必须留人工闸门的原因——放行一个漏网的恶意包代价大，但错误下架一个团队正在依赖的正常包，会直接打断构建、拖垮交付，两个方向的错误都难以事后无痕回滚。

供应链投毒攻击 AI 生态本身的机理（如投毒模型、恶意 MCP 组件）见 18.3，多智能体编排的单体与多体取舍、编排器设计见 17.2.4，本节只讲这套编排在恶意包研判域怎么落地。

关键约束
- 编排器必须有沙箱预算和研判轮次的硬上限，防止对一个包反复深挖烧掉算力，或自主循环失控
- 拦截、下架、删除依赖这些不可逆动作强制人工闸门，智能体只出定性与证据，不得自动执行处置
- LLM 研判 agent 的定性必须附证据链（哪个沙箱行为、哪条发布记录支撑结论），不接受只给结论不给依据的输出，否则人工无从复核

验证方法
- 回归靶场：用 7.3 已定性的 PyPI/npm 恶意包和一批已知正常包混合喂入，度量恶意召回率与正常误报率
- 沙箱规避测试：构造延迟触发、环境感知的样本，检验沙箱 agent 的观察窗口能否捕获，统计漏检率
- 错误传播测试：故意给元数据 agent 一个错误画像，检验下游研判与人工闸门能否拦下，统计错误沿链传播率

运行指标
- 恶意包召回率与正常包误报率（误报直接对应被错误拦下的正常依赖数，须持续压低）
- 单个包的端到端研判时延（从新版本出现到给出定性）与单次研判的沙箱与模型调用成本
- 自主研判→人工确认→拦截的转化率，以及人工推翻智能体定性的比例

### 告警质量管理

告警过多和告警不足都有问题。衡量告警质量的核心指标：

| 指标名称 | 说明 | 参考阈值 |
|---------|------|---------|
| 日均告警数量 | 每日产生的供应链相关告警 | 每人每日可处理约 20-30 条有效告警 |
| 告警误报率 | 经确认为误报的告警比例 | < 30% 为可接受；> 50% 需立即调优规则 |
| 平均确认时间 | 从告警产生到人工确认的时间 | CRITICAL < 15 分钟；HIGH < 1 小时 |

## 7.8.4 事件响应流程

### 分级与响应时限

供应链安全事件按影响范围和紧急程度分为四级。分级的价值在于：不同级别触发不同的响应机制，避免对所有事件都过度响应（消耗资源）或响应不足（扩大损失）。

P1（Critical）：生产环境中发现已被在野利用的漏洞、确认的恶意代码注入、签名密钥泄露。需要在分钟级启动响应，召集全员战争室。（事件严重级沿用全书唯一的 P1–P4，定义见 [11.5.2](../../第04部分_安全运营与防御能力/第11章_安全运营/11.5_事件响应.md)，**P1 最严重**。注意不要与优先级记号 P0–P4 混用，那一套里 P0 才是最高档，两套记号方向相反。）

P1（高）：CRITICAL 漏洞尚未被利用、未签名镜像部署到生产、SBOM 分析检测到已知恶意包。数小时内启动响应。

P2（中）：HIGH 漏洞、依赖维护者变更、许可证合规问题。当日内处理。

P3（低）：MEDIUM/LOW 漏洞、非关键组件异常。数个工作日内处理。

### P1 事件响应阶段详解

阶段一：检测与初始响应（目标：5 分钟内完成）

自动化系统在告警触发后应立即：通过 PagerDuty 通知值班安全工程师，在 Slack 创建专用事件频道并 @相关团队，自动收集初步证据快照（当前运行的 Pod 列表、近期部署记录、相关指标快照）。

值班工程师收到告警后：确认事件真实性（排除误报），指定事件指挥官（Incident Commander），召集核心响应团队。

阶段二：遏制（目标：30 分钟内完成）

遏制的原则是：快速阻止威胁扩散，哪怕代价是部分业务不可用。具体操作取决于威胁类型：

```bash
# 场景 A：暂停 CI/CD 防止后续部署引入更多受污染组件
# 不同 CI 平台有不同的暂停机制，以下为概念示例
gh workflow disable deploy.yml  # GitHub Actions

# 场景 B：隔离受影响服务（两种方式，按情况选择）

# 方式 1：缩容到 0 副本（适合服务可以完全下线的情况）
kubectl scale deployment/affected-service --replicas=0 -n production

# 方式 2：NetworkPolicy 隔离（适合需要保留服务用于取证的情况）
# 阻断所有入站和出站流量，同时保留 Pod 以供取证分析
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: isolate-affected-service
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: affected-service
  policyTypes:
    - Ingress
    - Egress
  # 没有 ingress/egress 规则 = 默认拒绝所有流量
EOF
```

阶段三：根因分析（与遏制并行推进）

需要回答的核心问题：威胁如何引入（攻击向量）？首次出现时间（感染时间线）？影响范围（blast radius，哪些服务、数据、用户）？是否已有数据外泄？

阶段四：修复（根因明确后）

在确认根因后执行彻底修复：为所有受影响系统应用补丁、轮换可能泄露的密钥和凭证（密钥泄露后必须立即轮换，即使还不确定是否被使用）、加强防御措施。

阶段五：恢复与验证

恢复前必须验证：漏洞扫描无新的高危发现、签名验证通过、监控显示无异常行为。推荐渐进式恢复：先恢复 5-10% 的流量，观察 15 分钟无异常后再逐步扩大。

阶段六：事后复盘

每次 P1/P2 事件都应在 5 个工作日内完成正式复盘，产出包含时间线、根因、影响分析、改进行动项（含责任人和截止时间）的复盘报告。无责文化是复盘有效性的前提——如果团队担心被问责，就不会如实反映真实情况。

### 适用边界与常见误区

误区一：响应手册过时。手册制定后未随架构演进更新，关键时刻发现步骤不适用（如文档中的命令已废弃）。应将手册纳入版本控制，每季度审查一次。

误区二：缺乏演练。"我们有手册"不等于"我们能执行手册"。团队从未实际执行过响应流程，真实事件时手忙脚乱。建议每半年进行一次桌面演练，每年进行一次红蓝对抗。

### 运行指标

| 指标名称 | 说明 | 参考阈值 |
|---------|------|---------|
| 平均检测时间（MTTD） | 从威胁出现到被检测 | P1 < 1 小时；P2 < 4 小时 |
| 平均遏制时间（MTTC） | 从检测到遏制完成 | P1 < 4 小时；P2 < 24 小时 |
| 平均恢复时间（MTTR） | 从遏制到业务完全恢复 | 核心业务 < 4 小时；一般业务 < 24 小时 |

行业背景：根据 IBM Cost of a Data Breach Report 2024，全球平均漏洞发现时间为 204 天。持续监控与威胁情报集成的目标是将内部检测时间缩短至小时级。

## 7.8.5 自动化修复

### 自动化修复的价值边界

自动化修复适合的场景：依赖有明确的新版本修复、变更范围可控（仅更新版本号，无 API 变更）、有充分的自动化测试覆盖可以验证修复没有引入回归。

不适合自动化的场景：major 版本升级（可能有破坏性 API 变更）；无充分测试覆盖的关键业务逻辑；需要代码改造而非简单版本升级的漏洞修复。

对于不适合自动化的情况，自动化工具的价值转变为：自动创建详细的修复任务工单，提供明确的修复指导和优先级排序，而非自动执行修复。

### 自动化修复流程

典型流程的八个步骤，各步骤的关键控制点：

1. 漏洞检测：SCA 工具扫描，筛选出同时满足以下条件的漏洞：存在修复版本、修复版本为 patch/minor 级别（降低回归风险）、当前自动化测试覆盖率满足阈值要求。

2. 创建修复分支：以漏洞 ID 命名分支（如 `security/fix-CVE-2024-XXXX`），便于追踪和审计。

3. 应用修复：根据包管理器类型（npm/pip/Maven/Go）自动更新依赖版本。仅更新目标依赖，不做无关变更。

4. 提交变更：提交信息包含漏洞 ID、受影响组件名称、修复版本，便于日后审计和关联。

5. 创建 Pull Request：PR 描述自动填充漏洞详情、CVSS 评分、EPSS 分、影响的服务列表、测试建议。

6. 自动化测试：CI 流水线执行完整测试套件，结果直接关联到 PR。

7. 人工审核：即使高度自动化，仍建议在合并前进行人工审核。可以配置：CRITICAL 漏洞需要两名高级工程师审核，HIGH 漏洞需要一名高级工程师审核。

8. 渐进式部署：合并后采用 Canary 部署，先将 5% 流量切到新版本，观察错误率和延迟无异常后再完全部署。

### 常见误区

误区一：盲目自动合并。跳过测试和人工审核直接合并，引入兼容性问题，实际上造成比漏洞本身更大的可用性影响。

误区二：忽视升级风险。某些修复版本可能引入新 bug 或性能回退（在 Java 生态中尤为常见）。在测试环境中先验证，性能基准测试是必要的。

### AI 起草依赖修复 PR 的护栏

上面第 3 步的"应用修复"，对于 patch/minor 级的纯版本号变更是确定性的——包管理器改一行版本，行为可预测。但很多依赖漏洞的修复没这么干净：修复版本换了 API、废弃了某个参数、或者干脆需要换一个替代包。这类修复过去只能落到"创建工单，等人来改"，成了自动化修复覆盖不到的那部分。2025 到 2026 年，主流依赖安全工具开始把大模型接到这一步，让它替人起草依赖升级或替换的补丁——不只是改版本号，还顺带改掉因升级而破坏的调用点。

这带来一个和确定性版本升级不同的新变量：AI 起草的补丁是非确定性的。同一个升级让模型改两次，可能给出两版不同的适配代码，甚至一版正确、一版引入新缺陷。这个变量以及应对它的护栏，在 6.4.3.5 已经为应用安全工具链完整讨论过，核心结论是：AI 在修复链路里只能当"起草者"不能当"审批者"，它可以出 PR，但 merge 与关闭发现的权力只属于人。这条边界原样适用于依赖修复场景，无须重述其推导——依赖升级 PR 同样要以 PR 形式提交、禁止直接推保护分支、必须经人工评审才能合并，无论补丁是否被采纳，原始漏洞发现的关闭权都留给人，工具链层面不给 AI 授予自动关闭权限。

依赖场景比应用代码修复多两个要额外守住的点。其一，AI 起草的升级补丁可能顺手改动了目标依赖之外的东西——为了让编译通过而动了别处的调用，或者连带升级了其他依赖。人工评审时要专门核对 diff 的边界，确认它只动了该动的依赖和适配代码，这与前面第 3 步"仅更新目标依赖，不做无关变更"是同一条底线。其二，模型可能建议一个并不存在的替代包版本，或把包名写成一个近似但错误的名字——而近似错误的包名恰好可能是攻击者抢注的投毒包（USENIX 的研究测得大模型生成的软件包名约有 16.6% 是幻觉出来的、真实不存在的，这些幻觉名一旦被攻击者预先抢注，采纳补丁反而会引入恶意依赖）。所以 AI 起草的依赖修复 PR，合并前必须让其引用的每一个新版本、每一个替代包都经过与新增依赖同等的准入校验（存在性、来源、签名、已知漏洞），不能因为它是"修复"就跳过对依赖本身的检查。

### 运行指标

| 指标名称 | 说明 | 参考阈值 |
|---------|------|---------|
| 自动修复覆盖率 | 可自动修复漏洞占总漏洞的比例 | > 60% 表明工具成熟 |
| 修复 PR 通过率 | 自动生成的 PR 中测试通过的比例 | > 80% 为健康水平 |
| 从检测到修复的时间 | 全流程耗时（不含人工等待） | < 4 小时 |

## 7.8.6 检测与响应能力成熟度

成熟度应逐级建设，跳跃式发展往往难以落地：

监控能力：定期扫描 → 集中式日志 + 每日自动化扫描 → 实时威胁情报关联 + SBOM 持续监控 → 机器学习异常检测。

告警能力：邮件告警 → SIEM 集成 + 分级告警 → 上下文感知告警 + 自动去重聚合。

响应能力：书面流程 + 手动修复 → Playbook + 自动化隔离 → 自动化修复 PR + 渐进式部署 → 全自动化修复与验证（含人工审核关卡）。

## 本节要点

持续监控替代周期性扫描：现代威胁的时效性要求从"定期检查"转变为"持续监控"，检测延迟应控制在分钟级而非天级。

威胁情报驱动主动防御：通过集成 CISA KEV、OSV、EPSS 等情报源，在攻击发生前识别风险，而非被动等待内部发现。

自动化是规模化的前提：人工响应速度无法匹配攻击速度，自动化检测、自动化隔离、自动化修复是必然方向，但需要在自动化程度与风险控制之间取得平衡。

agentic 研判扩大覆盖但不越权：把恶意包研判和依赖修复交给智能体自主编排，能追上投毒进构建的速度，但沙箱可被规避、LLM 会误判；拦截、下架依赖、关闭发现这类不可逆动作必须留人工闸门，智能体只出定性与补丁草案。

事后复盘持续改进：每次事件都是学习机会，通过正式的复盘流程识别改进点并跟踪落实。

SBOM 是可追溯性的基础：没有准确完整的 SBOM，威胁情报关联、影响范围评估、修复验证都无从谈起。

## 7.3.0 2024-2025 年重大开源安全事件回顾

技术框架的价值往往需要真实事件来定标。以下四个事件发生在 2024-2025 年间，直接影响了当前开源治理的最佳实践方向。

### XZ Utils 后门事件（CVE-2024-3094）

事件概述：2024 年 3 月，安全研究员 Andres Freund 在调试 SSH 性能问题时意外发现 XZ Utils 5.6.0 和 5.6.1 版本中被植入后门。攻击者通过长达两年的社会工程攻击，逐步获取项目维护权限，最终在构建脚本中注入恶意代码，可导致 SSH 认证绕过。

攻击手法：
- 攻击者"Jia Tan"自 2021 年起以贡献者身份参与项目
- 通过施压原维护者获取 commit 权限
- 后门代码隐藏在测试文件的二进制数据中，仅在特定构建条件下激活
- 影响使用 systemd 的 Linux 系统的 sshd 进程

影响范围：Fedora 40/41、Debian testing/unstable、openSUSE Tumbleweed、Arch Linux 等滚动更新发行版。由于发现及时，多数稳定版发行版未受影响。

教训：
1. 单一维护者项目的供应链风险（Bus Factor = 1）
2. 构建过程审计的重要性——源码审查无法发现构建时注入
3. 社会工程攻击对开源社区的威胁规模比传统估计更大

来源：
- [1] Andres Freund, "backdoor in upstream xz/liblzma leading to ssh server compromise", Openwall oss-security, 2024-03-29
- [2] NIST National Vulnerability Database, CVE-2024-3094, CVSS 10.0 Critical
- [3] CISA Alert, "Reported Supply Chain Compromise Affecting XZ Utils Data Compression Library, CVE-2024-3094", 2024-03-29
- [4] Red Hat, "Urgent security alert for Fedora Linux 40 and Fedora Rawhide users", 2024-03-29（CVE-2024-3094 官方公告）

### Polyfill.io 供应链攻击

事件概述：2024 年 2 月 polyfill.io 域名易主，Cloudflare 与 Fastly 在易主当时即各自上线了替代镜像（**是易主后的预防性举措，不是攻击曝光后的紧急响应**——这个先后顺序常被讲反）；同年 6 月该域名开始向用户分发恶意代码，Sansec 的研究称受影响站点超过 10 万。该 CDN 服务向移动设备用户注入重定向脚本，将用户导向博彩和诈骗网站。

攻击手法：
- 域名及 GitHub 仓库于 2024 年 2 月被收购
- 恶意代码仅在特定条件下激活（移动设备、特定时间段、非管理员 IP）
- 利用 CDN 的信任关系绕过 CSP 策略

影响范围：超过 100,000 个网站受影响，包括多个知名企业网站。Cloudflare、Fastly 紧急提供替代镜像服务。

教训：
1. 第三方 CDN 依赖需要持续所有权审计，而非一次性评估
2. 子资源完整性（SRI）是防止 CDN 劫持的有效控制
3. 开源项目所有权变更应触发重新评估

来源：
- [5] Sansec Threat Research, "Polyfill supply chain attack hits 100K+ sites", 2024-06-25
- [6] Cloudflare Blog, "Polyfill.io now available on cdnjs: reduce your supply chain risk", 2024-06-26
- [7] BleepingComputer, "Polyfill.io JavaScript supply chain attack impacts over 100K sites", 2024-06-25
- [8] Fastly Blog, "New options for Polyfill.io users", 2024-06-26

### PyPI 恶意包攻击浪潮

事件概述：2024 年全年，PyPI 遭受持续的恶意包攻击。攻击者利用 typosquatting（名称抢注）、dependency confusion（依赖混淆）、星标劫持等手法上传恶意包，窃取开发者凭证、加密货币钱包、AWS 密钥等敏感信息。

典型案例：
- requests-darwin-lite：伪装为 requests 库的 macOS 版本，窃取 Keychain 凭证
- aiocpa：针对 Telegram Bot API 开发者，窃取 Bot Token
- ultralytics 仓库劫持（2024 年 12 月）：攻击者利用 CI/CD 漏洞向官方包注入加密货币挖矿代码

攻击规模：据作者调研估算（示例口径，非行业基准），2024 年各方安全厂商在 PyPI 上报告并下架的恶意包数量以万计，且明显高于上一年；由于各家统计口径（是否含自动批量注册、是否去重）差异很大，本书不引用具体数字，建议以所用 SCA 厂商自己披露的口径为准。

教训：
1. 包名验证的重要性（安装前核实包名拼写）
2. 私有包索引优先策略
3. CI/CD 环境的凭证保护不能依赖单一机制

来源：
- [9] Phylum Research, "Evolution of Software Supply Chain Security Threats in 2024", Phylum Blog
- [10] Checkmarx Security Research, "PyPI crypto-stealing malware poses as requests library", 2024-05-28
- [11] ReversingLabs, "Malicious PyPI package aiocpa stole crypto wallet data", 2024-11-15
- [12] SafeBreach Labs, "Ultralytics PyPI Package Compromised via GitHub Actions Cache Poisoning", 2024-12-05

### npm 生态系统供应链事件

事件概述：npm 生态系统在 2024 年持续面临供应链安全挑战，主要表现为依赖混淆攻击和账户劫持。

典型案例：
- everything：恶意包将自身设为几乎所有 npm 包的依赖项，导致其他包无法正常卸载
- manifest confusion（清单混淆）：利用 npm 注册表与实际包内容不一致的漏洞

教训：
1. package-lock.json 锁定的重要性
2. 依赖审计 `npm audit` 的常态化执行
3. 发布前的 provenance 验证

来源：
- [13] Socket Security Research, "The 'everything' package", 2024-03-18
- [14] Darcy Clarke, "npm manifest confusion vulnerability", 2023-06（漏洞持续影响至 2024 年）
- [15] GitHub Blog, "Introducing npm package provenance", 2023-04-19

### 开源治理启示

四个事件揭示了供应链攻击的演进规律：

| 演进维度 | 2021-2023 | 2024-2025 |
|----------|-----------|-----------|
| 攻击复杂度 | 简单 typosquatting | 长期社会工程、CI/CD 渗透 |
| 潜伏周期 | 短期（天-周） | 长期（月-年） |
| 检测难度 | 静态分析可发现 | 需运行时/构建时检测 |
| 影响范围 | 单一项目 | 基础设施级（压缩库、CDN） |

治理建议：依赖最小化；使用 lockfile 固定依赖版本及哈希；对关键依赖建立多渠道监控；确保构建过程可审计、可复现；关注关键依赖项目的维护者活跃度。

## 7.3.1 软件成分分析（SCA）

### 定义与能力边界

软件成分分析（Software Composition Analysis，SCA）是自动识别和分析应用程序中第三方及开源组件的技术与流程。核心能力包括：检测已知安全漏洞、识别许可证合规风险、跟踪组件版本与更新、映射传递依赖关系。

适用边界：SCA 适用于具有显式依赖声明的项目（`package.json`、`pom.xml`、`go.mod` 等）。对于二进制文件、混淆代码、无清单的遗留系统，SCA 的识别率会显著下降，需配合二进制分析工具或人工审计。

关键约束：
- 漏洞数据库时效性：SCA 工具依赖 NVD、GitHub Advisory、OSV 等数据源，数据源更新延迟直接影响检测能力
- 传递依赖深度：深层传递依赖（如 A→B→C→D）可能因依赖解析差异导致漏报
- 误报处理成本：过于激进的策略会产生大量误报，消耗开发团队处理精力

### SCA 工具选型维度

选型应基于以下维度评估，而非单一功能对比：

| 维度 | 评估要点 |
|------|----------|
| 语言支持 | 是否覆盖组织技术栈（Java、Python、JavaScript、Go 等） |
| 集成能力 | 与 CI/CD 流水线、IDE、代码仓库的集成深度 |
| 漏洞数据库 | 数据源范围与更新频率 |
| 许可证检测 | 对 SPDX 标准许可证的识别准确度 |
| 修复指导 | 是否提供可操作的版本升级路径 |
| 开发者体验 | 告警清晰度、低摩擦集成、自动修复 PR 能力 |

典型工具包括 MurphySec（墨菲安全）、Snyk、Dependabot（GitHub）、WhiteSource/Mend、Sonatype Nexus IQ、JFrog Xray、Synopsys Black Duck、Trivy（开源）。各家在中文漏洞情报覆盖、国内开源生态支持、IDE/CI 集成深度、部署模式（私有化 / SaaS）上的差异，是国内选型的主要分歧点。这些差异目前缺少可核验的第三方横评，厂商自述不能直接采信——可行的验证办法是拿本组织真实的依赖清单跑一轮，比对各家的召回率（漏了多少已知 CVE）与误报率（报了多少不可达或不适用的），再看它对内网私有仓库、镜像源和信创组件的解析成功率。

### SCA 实施策略

SCA 实施通常分四个阶段推进。过早进入阻断模式是最常见的失败原因——开发团队在构建被频繁阻断后会寻找绕过方式，反而降低了实际安全效果。

阶段一：发现期——建立基线清单

核心活动：在代码库中部署 SCA 工具，生成初始组件清单，按严重程度分类问题，识别速赢项目（易于修补的高危问题）。

预期产出：完整组件清单（SBOM 前身）、高危/严重漏洞数量、许可证合规问题列表、技术债务量化数据。

阶段二：策略执行——防止新漏洞引入

核心活动：定义安全策略，将 SCA 集成到 CI/CD 门禁，配置自动修复 PR，建立例外审批流程。

策略配置示例（从 WARN 模式开始，逐步收紧）：

```yaml
# SCA 策略配置示例
policies:
  - id: high-severity-block
    rule: severity >= HIGH
    action: FAIL_BUILD      # 第一阶段可先用 WARN，等团队适应后切换到 FAIL_BUILD

  - id: gpl-license-approval
    rule: license IN [GPL-2.0, GPL-3.0, AGPL-3.0]
    action: REQUIRE_APPROVAL

  - id: abandoned-package-warning
    rule: last_update_age > 730  # 两年未更新
    action: WARN

  - id: minimum-nodejs-version
    rule: package == node && version < 15.0.0
    action: FAIL_BUILD
```

阶段三：持续监控——维持安全态势

核心活动：为生产系统部署运行时 SCA，订阅安全公告（GitHub、NVD、OSV），建立漏洞修复 SLA，定期漏洞评审。

漏洞修复 SLA 参考口径（需根据组织实际调整）：严重级别短周期修复，高危中等周期，中危长周期，低危尽力而为。

运行指标：平均检测时间（MTTD，新 CVE 到告警）、平均修复时间（MTTP，告警到生产修复）、漏洞债务（逾期未修复问题）、误报率（无效告警占比）。

阶段四：优化——降低噪音，提高效率

核心活动：基于误报调优策略；实施基于风险的优先级排序（EPSS + CVSS，见 7.3.5）；自动化低风险更新补丁；开展开发者安全依赖选择培训。

常见误区：

1. 策略过于激进：一次性启用所有阻断策略导致大量构建失败，引发开发团队抵触。应从 WARN 模式开始逐步收紧。
2. 忽视传递依赖：只关注直接依赖，忽略传递依赖中的漏洞。Log4Shell 正是通过传递依赖在大量项目中潜伏。
3. 缺乏例外管理：没有建立合理的例外审批流程，导致要么绕过检查、要么阻塞交付。

验证方法：在测试环境引入已知漏洞组件（如历史版本 log4j），验证 SCA 工具是否正确检测并触发告警/阻断；定期审计误报，计算误报率并作为工具调优依据；模拟新 CVE 发布场景，验证从公告发布到组织告警的端到端时间。

## 7.3.2 软件物料清单（SBOM）

### SBOM 基础概念

SBOM（Software Bill of Materials）是包含构建软件所用组件详细信息及供应链关系的正式记录。没有 SBOM，当 Log4Shell 这类漏洞爆发时，组织只能逐应用手工排查，这在大型系统中可能耗时数天；有 SBOM 的组织可以在小时内完成影响范围识别。这个效率差异说明了 SBOM 的运营价值所在。

SBOM 的核心价值场景：
- 漏洞管理：新漏洞披露时快速识别受影响系统
- 许可证合规：系统性跟踪开源许可证义务，避免 GPL copyleft 等法律风险
- 供应链透明度：使下游客户能在采购前评估软件成分风险
- 监管合规：满足 EU CRA 与商业合同的 SBOM 要求（美国 EO 14028 的联邦强制机制已于 2026-02 由 OMB M-26-05 解除，其 NTIA 最小元素规格仍为事实标准）

![SBOM 生命周期](../../../assets/images/chapter_07/02_SBOM_Lifecycle_v6.png)

### SBOM 标准对比

当前主流 SBOM 标准为 SPDX 与 CycloneDX，设计目标不同，适用场景不同。

SPDX（Software Package Data Exchange）

治理机构为 Linux 基金会，已形成 ISO/IEC 5962:2021 标准。SPDX 自 2010 年发展至今，具有最成熟的许可证信息表达能力，强调法律与合规层面的完整性。支持 JSON、XML、YAML、RDF、Tag-Value 等格式。典型用例包括许可证合规审查、并购尽职调查、法律审计。

CycloneDX

治理机构为 OWASP 基金会，设计导向为应用安全。CycloneDX 原生支持 VEX（漏洞可利用性交换），便于将漏洞信息与 SBOM 关联。格式相对轻量，支持 JSON、XML、Protocol Buffers。典型用例包括漏洞管理、DevSecOps 流水线集成、安全运营。

| 维度 | SPDX | CycloneDX |
|------|------|-----------|
| 主要关注点 | 许可证合规 | 安全漏洞 |
| 标准化程度 | ISO 标准 | OWASP 项目标准 |
| VEX 支持 | 有限 | 原生支持 |
| 许可证信息 | 全面 | 良好 |
| 推荐用途 | 法务审计、M&A | DevSecOps、漏洞管理 |

选型建议：运营安全场景优先选择 CycloneDX，法律/合规场景优先选择 SPDX。部分组织选择生成双格式 SBOM 以满足不同利益相关方。

### NTIA 最小元素要求

美国 NTIA 定义了 SBOM 的七个最小必备元素：供应商名称、组件名称、版本、其他唯一标识符（哈希值/PURL/CPE）、依赖关系（直接和传递依赖项）、SBOM 作者（生成工具或人员）、时间戳（生成日期）。

验收口径：确保所选 SBOM 生成工具能输出全部七个元素，并在 CI/CD 流程中验证完整性。

### SBOM 生成实践

常用生成工具：Syft（多语言、容器镜像）、CycloneDX Generators（各语言构建工具插件）、SPDX Tools、Tern（容器镜像 Dockerfile 分析）、Trivy、OSS Review Toolkit。

Syft 适用于广泛覆盖需求，原生构建工具插件（如 Maven CycloneDX Plugin）提供更高精度但需逐项目配置。

以下 CI/CD 集成示例包含了生成、签名、上传、附到 Release 的完整链路。签名步骤是关键——未签名的 SBOM 无法证明其完整性，在供应链审计场景中价值有限：

```yaml
name: Generate SBOM

on:
  push:
    branches: [main]
  release:
    types: [published]

jobs:
  sbom:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build artifact
        run: ./mvnw clean package

      - name: Generate SBOM with Syft
        uses: anchore/sbom-action@v0
        with:
          image: myapp:${{ github.sha }}
          format: cyclonedx-json
          output-file: sbom.cyclonedx.json

      - name: Sign SBOM with Cosign
        # 签名确保 SBOM 在生成后未被篡改
        run: |
          cosign sign-blob --key cosign.key \
            --yes \
            --output-signature sbom.sig \
            sbom.cyclonedx.json

      - name: Upload to SBOM repository
        run: |
          curl -X POST https://sbom.example.com/api/upload \
            -F "sbom=@sbom.cyclonedx.json" \
            -F "signature=@sbom.sig" \
            -F "artifact=myapp-1.0.0.jar"

      - name: Attach to GitHub Release
        if: github.event_name == 'release'
        uses: softprops/action-gh-release@v2
        with:
          files: sbom.cyclonedx.json
```

常见误区：

1. 仅生成不管理：生成 SBOM 后未建立存储、版本关联、查询机制，无法在漏洞披露时快速定位受影响系统。SBOM 的价值在运营中实现，不在生成时。
2. 忽视签名验证：SBOM 未签名或签名未验证，无法保证完整性与真实性。

## 7.3.3 SBOM 漏洞追踪

### 漏洞富化工作流

SBOM 的核心运营价值在于持续漏洞追踪。典型工作流为：SBOM 生成 → 漏洞扫描 → 风险评估 → 通知 → 修复。这是一个循环，而非一次性流程。

### Dependency-Track 平台

Dependency-Track 是开源 SBOM 分析平台，具备集中化 SBOM 仓库、持续漏洞监控（对接 NVD、GitHub Advisory、OSV、VulnDB）、风险评分与优先级（CVSS、EPSS、VEX 支持）、策略执行（严重性阈值、许可证限制）、审计跟踪与报告、自动化 API 集成等核心能力。

架构设计上，Dependency-Track 作为中心枢纽：CI/CD 流水线上传 SBOM，平台持续与漏洞数据库同步，通知系统将告警推送到 Jira/Slack 等工具：

```
┌─────────────┐      ┌──────────────────┐      ┌─────────────────┐
│  CI/CD      │─────>│ Dependency-Track │<────>│ 漏洞数据库      │
│  流水线     │SBOM  │    平台          │      │ (NVD, GitHub)   │
└─────────────┘      │                  │      └─────────────────┘
                     │  ┌────────────┐  │
                     │  │ SBOM 存储  │  │
                     │  │ 策略引擎   │  │
                     │  │ 分析引擎   │  │
                     │  └────────────┘  │
                     │  API             │
                     └─────────┬────────┘
                               │
                     ┌─────────▼────────┐
                     │  通知系统        │
                     │  (Jira, Slack)   │
                     └──────────────────┘
```

策略配置示例（注意 `violationState: FAIL` 配合 webhook 可直接阻断 CI/CD 部署门禁）：

```yaml
policies:
  - name: "阻止生产环境严重漏洞"
    violationState: FAIL
    conditions:
      - subject: SEVERITY
        operator: IS
        value: CRITICAL
      - subject: PROJECT_TAG
        operator: CONTAINS
        value: production
    actions:
      - type: NOTIFICATION
        destination: security-team-slack
      - type: WEBHOOK
        url: https://cicd.example.com/api/deployment-gate
```

验证方法：上传包含已知漏洞组件的测试 SBOM，验证平台是否正确匹配漏洞并触发策略；验证通知到达率（Slack/Jira 工单创建成功率）；审计策略执行日志，确保 FAIL 策略确实阻断了部署流程。

## 7.3.4 开源许可证合规

### 许可证风险分级

许可证合规是开源治理中常被忽视但法律风险极高的领域。并购场景尤其需要注意：GPL 污染可能直接影响估值谈判。

| 许可证类型 | 风险等级 | 主要义务 | 示例 |
|------------|----------|----------|------|
| 宽松许可证 | 低 | 归属声明、无担保 | MIT, Apache-2.0, BSD |
| 弱著作权 | 中 | 修改部分需公开源码 | LGPL, MPL |
| 强著作权 | 高 | 完整源码公开（传染性） | GPL-2.0, GPL-3.0, AGPL |
| 商业许可 | 可变 | 按许可条款、付费 | Oracle, Microsoft |
| 未知许可 | 严重 | 需法务审查 | 非 SPDX 标准、自定义 |

适用边界：
- SaaS 产品需特别警惕 AGPL（网络著作权），即使不分发二进制也可能触发开源义务
- 内部工具对 GPL 的容忍度高于外部产品
- 并购场景需进行完整许可证审计

### 许可证策略示例

策略一：仅宽松许可策略（SaaS 公司）

```yaml
approved_licenses:
  - MIT
  - Apache-2.0
  - BSD-3-Clause
  - BSD-2-Clause
  - ISC

review_required:
  - MPL-2.0
  - EPL-2.0

prohibited:
  - GPL-2.0
  - GPL-3.0
  - AGPL-3.0
  - SSPL
```

策略原因：避免著作权义务触发源代码公开要求。

策略二：GPL 兼容策略（开源项目）

```yaml
approved_licenses:
  - MIT
  - Apache-2.0
  - GPL-2.0+
  - GPL-3.0+
  - LGPL-2.1+
  - LGPL-3.0+

review_required:
  - AGPL-3.0

prohibited:
  - Proprietary licenses
```

策略原因：允许 GPL 以参与开源生态系统。

### 合规流程

许可证合规的四个环节：发现（扫描代码库许可证头部、分析包清单、识别传递依赖许可证）→ 策略执行（自动批准宽松许可证、标记著作权许可证需审查、CI/CD 中阻止禁止的许可证）→ 修复（用替代方案替换禁止的依赖项、与供应商协商双重许可、隔离著作权代码到独立进程）→ 文档化（生成归属声明 NOTICE 文件、维护许可证清单用于审计）。

归属声明示例：

```
MyApp v1.0.0
版权所有 (c) 2025 Example Corp

本产品包含以下开源软件：

1. log4j-core 2.17.1
   许可证: Apache License 2.0
   版权: Apache Software Foundation
   源代码: https://github.com/apache/logging-log4j2

2. express 4.18.2
   许可证: MIT License
   版权: TJ Holowaychuk
   源代码: https://github.com/expressjs/express

（完整许可证文本在 /licenses/ 目录中可用）
```

常见误区：

1. 仅检查直接依赖：传递依赖可能引入不兼容许可证，需递归扫描完整依赖树
2. 忽视许可证变更：同一包的不同版本可能采用不同许可证（如早期 MIT 后期改 GPL），版本升级时需重新审查

## 7.3.5 依赖项漏洞管理

### 优先级框架：EPSS + CVSS

传统漏洞管理仅依赖 CVSS 严重性评分，但 CVSS 无法反映实际利用可能性——CVSS 9.8 的漏洞可能从未被实际利用，而 CVSS 7.0 的漏洞可能已经在野外大规模利用。

EPSS（漏洞利用预测评分系统，由 FIRST.org 开发）基于漏洞利用活动数据训练的机器学习模型，预测漏洞在未来 30 天内被利用的概率（0-1 范围）。结合 CVSS 与 EPSS 构建二维优先级矩阵：

| CVSS 严重性 | EPSS 低 | EPSS 中 | EPSS 高 |
|-------------|---------|---------|---------|
| 严重 (9-10) | P2 | P1 | P0（紧急） |
| 高 (7-8.9) | P3 | P2 | P1 |
| 中 (4-6.9) | P4 | P3 | P2 |
| 低 (0-3.9) | P5 | P4 | P3 |

实例：CVE-2021-44228（Log4Shell）CVSS 10.0、EPSS 极高，应归类为 P0 紧急修复。

适用边界：EPSS 依赖公开漏洞利用数据，对零日漏洞或私有漏洞预测能力有限。应结合威胁情报补充判断。

### 自动化补丁策略

根据变更风险与自动化程度，补丁分四个级别：

| 级别 | 标准 | 自动化程度 | 审批 |
|------|------|------------|------|
| 级别 1：自动合并 | 补丁版本、低 EPSS、测试通过 | 完全自动化 | 无需审批 |
| 级别 2：自动 PR | 次要版本、中等风险 | 自动创建 PR | 团队审查 |
| 级别 3：手动 | 主要版本、破坏性变更 | 手动 PR | 架构师审查 |
| 级别 4：例外 | 无修复方案、需补偿控制 | 在 GRC 中跟踪 | CISO 批准 |

Renovate 配置示例。关键设计：`automerge: true` 仅在分支的必需状态检查（在仓库分支保护规则中配置的 `test`、`security-scan` 等）全部通过后才会自动合并，`minimumReleaseAge: "3 days"` 给新版本发布后的问题一个暴露窗口期：

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:recommended", "security:openssf-scorecard"],
  "schedule": ["before 6am on Monday"],
  "packageRules": [
    {
      "matchUpdateTypes": ["patch"],
      "automerge": true
    },
    {
      "matchPackagePatterns": ["^@opentelemetry/"],
      "groupName": "OpenTelemetry",
      "schedule": ["monthly"]
    },
    {
      "matchDepTypes": ["devDependencies"],
      "automerge": true,
      "minimumReleaseAge": "3 days"
    }
  ],
  "vulnerabilityAlerts": {
    "labels": ["security"],
    "assignees": ["@security-team"],
    "prPriority": 10
  }
}
```

关键约束：自动合并依赖测试套件质量，低覆盖率项目应降低自动化程度；即使补丁版本也可能引入回归，需监控生产环境异常指标。

验证方法：模拟补丁版本发布，验证自动合并流程是否按预期执行；统计自动合并后的回归事件率，作为策略调优依据；审计例外审批记录，确保高风险漏洞未被长期搁置。

运行指标：漏洞债务（逾期未修复数量及增长趋势）；自动合并成功率；平均修复时间（MTTP）按优先级分层统计；例外审批数量及平均存续时间。

## 7.3.6 验证方法汇总

| 能力域 | 验证场景 | 验证方法 | 预期结果 |
|--------|----------|----------|----------|
| SCA 检测 | 已知漏洞组件引入 | 在测试项目中添加历史版本 log4j，运行 SCA 扫描 | 工具正确识别 CVE-2021-44228 |
| SCA 阻断 | 策略门禁有效性 | 提交包含高危漏洞依赖的 PR，观察 CI 状态 | 构建被策略阻断 |
| SBOM 完整性 | NTIA 七要素合规 | 使用 sbom-tool 验证生成的 SBOM 格式 | 全部七个必备字段存在 |
| SBOM 签名 | 完整性验证 | `cosign verify-blob --key cosign.pub --signature sbom.sig sbom.cyclonedx.json` 验证 SBOM 签名 | 签名验证通过 |
| 漏洞追踪 | CVE 关联有效性 | 上传含已知漏洞的 SBOM 至 Dependency-Track | 平台正确匹配漏洞并创建告警 |
| 许可证检测 | GPL 组件识别 | 引入 GPL 许可证依赖，运行许可证扫描 | 工具正确标记为需审查 |
| 自动补丁 | 补丁版本自动合并 | 发布测试包的补丁版本，观察 Renovate 行为 | 自动创建并合并 PR（测试通过后） |

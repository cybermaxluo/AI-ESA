# 7.4　CI/CD 供应链安全

> 导读：CI/CD 管道是供应链攻击的高价值目标——入侵构建系统可在合法签名的掩护下向所有下游用户分发恶意制品。本节从威胁模型出发（7.4.1），覆盖 GitHub Actions/GitLab CI/Jenkins 三个平台的加固基线（7.4.2），然后展开 SLSA Build track（L1-L3）的分级实施路线图（7.4.3），并说明其上的补充控制，最后给出 Hermetic Build 的工程实现（7.4.4）。攻击案例的背景见 7.2（SolarWinds、Codecov），SBOM 生成在 CI/CD 中的集成见 7.3。

CI/CD 系统一旦被攻陷，攻击者可实现：在生产制品中注入恶意代码、窃取构建环境中的密钥与凭证、篡改构建产物同时保留合法签名、在构建过程中植入持久后门。SolarWinds、Codecov、Travis CI 等事件表明，CI/CD 安全是供应链防御的关键控制点。

需要先建立一个基本判断：构建系统是少数几个既能触及全部源代码、又能触及生产签名密钥、还能直接向所有用户交付产物的位置。这三种能力叠加在一起，使得构建系统的信任级别应当等同于——甚至高于——它所服务的任何单个生产系统。本节后续所有加固手段，本质上都是围绕"如何在这样一个高信任节点上收窄攻击者的可操作空间"展开的。

## 7.4.1 CI/CD 攻击面分析

在动手加固之前，先要看清攻击者能从哪里下手。CI/CD 不是一个单点，而是一条从源码到部署的流水线，每个环节都有自己的信任边界和薄弱处。下面的威胁模型按流水线的四个阶段拆解，目的是让读者在阅读后续加固配置时，能把每一条配置项对应回它所封堵的具体攻击向量。

### 威胁模型

CI/CD 供应链攻击沿四个阶段展开，每阶段存在不同的攻击向量。

源代码仓库阶段：恶意 pull request、分支保护绕过、提交签名伪造。攻击者通过社会工程或账户接管提交恶意代码，若分支保护规则配置不当，恶意代码可能直接合入主干。

构建系统阶段：CI 配置文件篡改（如 `.gitlab-ci.yml`、GitHub Actions workflow）、构建脚本注入、环境变量窃取。攻击者可通过修改构建定义执行任意命令，或窃取构建环境中的凭证。

制品仓库阶段：中间人攻击、仓库账户劫持、签名伪造。攻击者可替换合法制品或伪造签名，使下游系统接受恶意产物。

部署环境阶段：Kubernetes API 滥用、secrets 泄露、准入控制绕过。攻击者可利用部署凭证直接操作生产环境。

这四个阶段的排列不是随意的：它们对应着信任沿流水线逐级传递的过程。前一阶段一旦被攻破，其产出会被后一阶段默认信任并放大。这正是为什么单靠某一环节的防御不够——源码阶段的一个恶意合入，会顺着构建、制品、部署一路继承下去，最终以合法签名的形态到达用户。理解这一点，才能理解为什么后续加固强调的是"每一环都要独立验证上一环的输出"，而不是"守住入口就够了"。

### 风险矩阵

有了攻击向量清单，下一步是排优先级——资源有限，不可能同时加固所有环节。下面这张风险矩阵把每个向量的"可能性"与"影响"两个维度交叉评估，并挂上真实案例作为锚点。它的用法是：先看风险等级列锁定"严重"档，把加固预算优先投向这些向量；案例参考列则提供了"这类攻击真实发生过"的证据，便于向管理层证明投入的必要性。

评估维度包括可能性、影响程度、风险等级，并关联已知案例。

| 攻击向量 | 可能性 | 影响 | 风险等级 | 案例参考 |
|---------|-------|------|---------|----------|
| CI 配置文件篡改 | 高 | 高 | 严重 | Codecov (2021) |
| 构建环境投毒 | 中 | 极高 | 严重 | SolarWinds (2020) |
| 密钥窃取 | 高 | 高 | 严重 | Travis CI (2021) |
| 依赖混淆 | 中 | 高 | 高 | 依赖混淆攻击 (2021) |
| 制品替换 | 低 | 极高 | 高 | NPM 供应链事件 (2022) |
| 日志投毒 | 低 | 低 | 中 | —— |

这张表里，可能性和影响并不同向。"构建环境投毒""制品替换"的可能性并不高，但一旦发生影响极大，因此仍被列为严重或高风险——这类"低概率、高破坏"的向量最容易被忽视，恰恰是 SolarWinds 式攻击的落点。反过来，"CI 配置文件篡改""密钥窃取"可能性高，是攻击者的常规切入口，需要靠日常控制手段持续压制。后续 7.4.2 的加固基线正是针对这几个高风险向量逐一给出对策。

适用边界：该风险矩阵适用于使用 Git 托管平台（GitHub、GitLab、Bitbucket）并采用自动化 CI/CD 的组织。对于完全隔离的构建环境或无外部依赖的场景，部分风险等级可能降低。

关键约束：风险等级评估基于典型互联网企业场景，实际评估需结合组织的资产价值、暴露面、现有控制措施进行调整。

## 7.4.2 CI/CD 加固基线

攻击面清楚了，接下来是具体加固。本小节按三个主流平台——GitHub Actions、GitLab CI/CD、Jenkins——分别给出可落地的配置基线。三个平台的语法和机制各异，但加固思路高度一致：收窄权限、固定版本、隔离执行环境、验证制品完整性。

### GitHub Actions 安全配置

GitHub Actions 的安全加固需从权限控制、版本固定、输入隔离三个层面入手。三者缺一不可：权限最小化限制被攻击后的爆炸半径，版本固定防止通过修改 Action 代码发动供应链攻击，输入隔离阻断注入攻击。这三条与 GitHub 官方《Security hardening for GitHub Actions》给出的加固建议一致——其中"用完整 commit SHA 固定第三方 Action"与"避免把不可信输入直接插值进 `run` 脚本"两条尤其关键[2]。

这三个层面为什么"缺一不可"值得展开：它们分别对应攻击链的三个不同环节。权限最小化管的是"攻击者得手后能做多少"，版本固定管的是"攻击者能否通过第三方 Action 混进来"，输入隔离管的是"攻击者能否通过外部可控输入触发命令执行"。任何一层缺失，另外两层的防护都可能被绕过——比如权限收得再紧，若引入了一个被劫持的 Action，攻击者仍在你的权限范围内活动。

权限最小化原则：在 workflow 文件中显式声明 `permissions` 块，默认应为只读权限。

下面这张权限对照表是配置 `permissions` 块时的实用参考。它的价值在于把 GitHub 的权限粒度和真实用途一一对应，便于按需授予而非全盘开放。使用时的原则是：从全部只读起步，然后对照"典型场景"列，只为流水线实际执行的动作追加对应的写权限。比如一个只跑测试和扫描的 workflow，通常只需要 `contents: read` 和 `security-events: write`，绝不该出现 `contents: write`。

| 权限 | 用途 | 典型场景 |
|------|------|----------|
| `contents: read` | 读取仓库内容 | checkout 代码 |
| `contents: write` | 写入仓库内容 | 推送提交、创建 release |
| `pull-requests: write` | 操作 PR | 添加评论、审批 |
| `packages: write` | 推送包 | 发布到 GitHub Packages |
| `id-token: write` | 请求 OIDC token | Sigstore 无密钥签名 |
| `actions: read` | 读取 workflow 信息 | SLSA provenance 生成 |
| `security-events: write` | 上传安全扫描结果 | CodeQL、SARIF 报告 |

表中 `id-token: write` 与 `security-events: write` 这两项容易被误配得过宽：前者一旦授予就允许 workflow 换取 OIDC 令牌，是无密钥签名与云端身份联邦的入口，非必要不开；后者只在需要回传扫描结果时才需要。把它们和普通读权限区别对待，是权限最小化落到细节的体现。

Action 版本固定：使用完整 SHA 哈希固定 Action 版本，而非 tag 或 branch。tag 可被修改指向不同提交，SHA 是唯一不可变标识：

下面这份完整 workflow 把上述三个层面（权限、版本固定、输入隔离）整合到了一起，可以作为一个安全基线模板来读。阅读时建议抓住四个关键位置，它们分别对应一种防护：一是文件顶部的 `permissions` 块（第 74-78 行），显式声明而非依赖默认的宽松权限；二是每个 `uses` 后面跟的 40 位 SHA（如第 92、98 行），把第三方 Action 钉死在某个不可变提交上；三是"Download and verify script"步骤（第 104-109 行），下载外部脚本后先用 `sha256sum -c` 校验哈希再执行，践行"信任内容而非来源"；四是 `persist-credentials: false`（第 94 行），阻止 checkout 把凭证残留在工作区被后续步骤读取。

```yaml
# .github/workflows/secure-workflow.yaml
name: Secure CI/CD Pipeline

on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [main]

permissions:
  contents: read
  pull-requests: write
  id-token: write
  packages: write

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  security-checks:
    runs-on: ubuntu-latest
    timeout-minutes: 30

    steps:
      # 使用 SHA 固定 Action 版本，而非 tag（tag 可被修改）
      - name: Checkout code
        uses: actions/checkout@8e5e7e5ab8b370d6c329ec480221332ada57f0ab # v3.5.2
        with:
          persist-credentials: false
          fetch-depth: 0

      - name: Setup Node.js
        uses: actions/setup-node@64ed1c7eab4cce3362f8c340dee64e5eaeef8f7c # v3.6.0
        with:
          node-version: '18'
          cache: 'npm'

      # 验证外部脚本完整性——信任内容哈希，不信任来源 URL
      - name: Download and verify script
        run: |
          curl -o script.sh https://trusted-source.com/script.sh
          echo "expected_sha256_hash script.sh" | sha256sum -c -
          chmod +x script.sh
          ./script.sh

      - name: Build application
        env:
          NODE_ENV: production
        run: |
          npm ci --production
          npm run build

      - name: Deploy to production
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
        run: |
          ./deploy.sh
```

值得权衡的是 SHA 固定的代价：把 Action 钉死在 SHA 上确实堵住了"tag 被悄悄改指向恶意提交"这条路，但也意味着上游安全更新不会自动生效，团队需要额外的机制（如 Dependabot 之类的更新工具）来周期性升级这些 SHA，否则会长期停留在含漏洞的旧版本。这是"不可变"与"可维护"之间的典型取舍——安全上选择不可变，运维上就得补一套受控的更新流程。此外注意末尾的 `Deploy to production` 步骤单独通过 `env` 注入 `DEPLOY_TOKEN`，把敏感凭证限定在真正需要它的那一步，而非全 job 可见，这也是缩小密钥暴露面的常见做法。

常见误区：

1. 使用 tag 而非 SHA 固定版本——tag 可被修改指向不同提交，SHA 是唯一不可变标识
2. 在日志中输出密钥——即使 GitHub 会自动遮盖，也应避免在调试信息中引用密钥变量
3. 对 PR 标题/内容直接插值执行——可导致命令注入，应使用 `github-script` 等安全方式处理

第三条误区尤其隐蔽，值得多说一句：PR 标题、分支名、issue 内容这些字段是攻击者完全可控的外部输入，如果在 `run:` 脚本里用 `${{ }}` 直接插值，攻击者只需在标题里塞入 shell 元字符就能在你的构建环境里执行任意命令——这正是前面威胁模型中"构建脚本注入"的典型实现路径。安全的做法是把这类值先赋给环境变量再引用，让 shell 按数据而非代码处理它。

验证方法：使用 `actionlint` 工具静态分析 workflow 文件；审查 workflow 执行日志，确认无密钥泄露；定期审计 Action 版本，检查是否存在已知漏洞。

#### 分支保护规则

前面的 workflow 加固管住了"构建阶段"，但威胁模型的第一阶段是源码仓库——恶意代码若能直接合入主干，再严的构建加固也只是在给恶意代码盖章。分支保护正是把守这道入口的控制。这里用 Terraform 而非在 UI 上点选来配置，动机是让保护规则本身成为版本化、可审查、可复现的代码：谁改了保护规则、改了什么，都留在 Git 历史里，避免有人在控制台里悄悄放松一条规则而无人知晓。

分支保护是防止恶意代码合入主干的关键控制。以下 Terraform 配置展示了完整的保护规则设置——特别注意 `enforce_admins: true`，它防止管理员绕过保护规则（这是常见的安全配置漏洞）：

```hcl
# terraform/github_branch_protection.tf
resource "github_branch_protection" "main" {
  repository_id = github_repository.repo.node_id
  pattern       = "main"

  required_status_checks {
    strict   = true
    contexts = [
      "security-checks",
      "unit-tests",
      "integration-tests",
      "code-quality",
    ]
  }

  required_pull_request_reviews {
    dismiss_stale_reviews           = true
    require_code_owner_reviews      = true
    required_approving_review_count = 2
    restrict_dismissals             = true
    dismissal_restrictions = [
      "security-team",
      "lead-engineers",
    ]
  }

  require_signed_commits        = true
  enforce_admins                = true   # 防止管理员绕过保护规则
  allows_force_pushes           = false
  allows_deletions              = false
  required_conversation_resolution = true

  push_restrictions = [
    "ci-bot",
    "release-automation",
  ]
}
```

这段配置里几个字段承担着不同的防线，读时可对照它们各自封堵的手法：`enforce_admins = true` 让管理员也受规则约束，堵住"用高权限账户绕过审查直推主干"这条捷径，注释特意点名它是常见漏洞；`require_signed_commits` 对应威胁模型里的"提交签名伪造"，要求提交必须带可验证签名；`allows_force_pushes = false` 与 `allows_deletions = false` 防止攻击者用强推改写历史或删除分支来掩盖痕迹；`dismiss_stale_reviews` 则确保代码一旦被改动，此前的批准自动失效，避免"审查通过后再偷偷追加恶意提交"。生产环境里最容易踩的坑就在 `enforce_admins`——很多团队为了图管理员操作方便把它关掉，等于给整套保护规则开了一道后门。

CODEOWNERS 配置示例——CI/CD 配置文件变更需要安全团队额外审批，这是防止构建系统攻击的重要控制：

CODEOWNERS 和分支保护是配套使用的：分支保护规定"必须有 code owner 审批"，而由谁来当某个路径的 owner 就由这份文件定义。这里的设计意图是差异化审批——普通业务代码走常规评审，但对高危路径施加额外的安全团队会签。请特别看 `/.github/workflows/` 这一行：它要求任何对构建定义本身的改动都必须经安全团队审批，直接对应风险矩阵里被评为"严重"的"CI 配置文件篡改"（Codecov 事件的落点）。其余几行把密钥文件（`*.key`、`*.pem`）、生产配置、基础设施代码也纳入安全团队的必审范围，逻辑一致：越是能影响信任根的路径，审批门槛越高。

```
# .github/CODEOWNERS
* @security-team @lead-engineers
/.github/workflows/ @devops-team @security-team   # CI/CD 配置变更需要安全团队审批
/infrastructure/ @platform-team @security-team
/src/security/ @security-team
/config/production.yaml @security-team
*.key @security-team
*.pem @security-team
```

运行指标：分支保护绕过尝试次数；未经审查合入的提交数量；签名验证失败率。

### GitLab CI/CD 安全配置

换到 GitLab，加固思路不变，但平台提供的抓手不同：GitLab 把安全扫描做成了可直接 `include` 的官方模板，因此这里的加固更多体现在"把哪些扫描默认打开""在流水线的哪个环节验证签名"这两件事上。下面这份 `.gitlab-ci.yml` 的核心动机是把签名验证嵌入构建与部署两端，形成闭环——构建前验证基础镜像来源可信，部署前再次验证制品未被替换。

GitLab CI/CD 的安全加固重点在于触发规则限制、安全扫描集成、镜像签名验证。注意 `build` 阶段在构建前先验证基础镜像签名（`cosign verify ... || exit 1`），这是防止基础镜像被替换的关键控制：

```yaml
# .gitlab-ci.yml
workflow:
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_MERGE_REQUEST_IID
    - if: $CI_COMMIT_TAG

variables:
  DOCKER_DRIVER: overlay2
  DOCKER_TLS_CERTDIR: "/certs"
  SAST_DISABLED: "false"
  SECRET_DETECTION_DISABLED: "false"
  DEPENDENCY_SCANNING_DISABLED: "false"
  CONTAINER_SCANNING_DISABLED: "false"

stages:
  - security
  - build
  - test
  - scan
  - deploy

include:
  - template: Security/SAST.gitlab-ci.yml
  - template: Security/Secret-Detection.gitlab-ci.yml
  - template: Security/Dependency-Scanning.gitlab-ci.yml
  - template: Security/Container-Scanning.gitlab-ci.yml

sast:
  stage: security
  variables:
    SAST_EXCLUDED_PATHS: "spec,test,tests,tmp,node_modules"
  artifacts:
    reports:
      sast: gl-sast-report.json
    paths:
      - gl-sast-report.json
    expire_in: 1 week

secret_detection:
  stage: security
  variables:
    SECRET_DETECTION_HISTORIC_SCAN: "true"

build:
  stage: build
  image: docker:24-dind
  services:
    - docker:24-dind
  before_script:
    - apk add --no-cache cosign
    # 构建前先验证基础镜像签名，防止基础镜像被替换
    - cosign verify --key cosign.pub $CI_REGISTRY_IMAGE:base || exit 1
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    - syft scan $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.json
    - cosign sign --key cosign.key $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    - cosign attest --key cosign.key --predicate sbom.json $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  artifacts:
    paths:
      - sbom.json
    reports:
      cyclonedx: sbom.json
  only:
    - main
    - /^release-.*$/

container_scanning:
  stage: scan
  variables:
    CS_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    CS_SEVERITY_THRESHOLD: "CRITICAL"
  dependencies:
    - build
  allow_failure: false

deploy_production:
  stage: deploy
  image: bitnami/kubectl:latest
  before_script:
    # 部署前二次验证签名——防止制品在 CI 与部署之间被替换
    - cosign verify --key cosign.pub $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    - cosign verify-attestation --key cosign.pub \
        --type cyclonedx \
        $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  script:
    - kubectl set image deployment/app \
        app=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA \
        --namespace=production
  environment:
    name: production
    url: https://app.example.com
  only:
    - main
  when: manual
```

这份流水线值得点出几处关键设计。其一是 `stages` 的排序把 `security` 放在 `build` 之前——扫描先行，让 SAST、密钥检测、依赖扫描在耗时的构建之前就有机会拦截问题，快速失败。其二是签名验证出现在两端且逻辑呼应：`build` 阶段的 `before_script` 里 `cosign verify ... || exit 1` 在动手构建前先确认基础镜像可信，而 `deploy_production` 的 `before_script` 又对最终制品做了一次 `verify` 加 `verify-attestation`。这个"部署前二次验证"不是冗余，它专门封堵一类真实威胁：制品在构建产出与部署之间的窗口里被人替换或篡改——即便构建时签名正确，部署前不再核对，攻击者仍有可乘之机。其三是 `container_scanning` 的 `allow_failure: false` 配合 `CS_SEVERITY_THRESHOLD: "CRITICAL"`，把"发现严重漏洞就阻断流水线"变成硬约束，而不是仅生成一份被忽略的报告。最后，`deploy_production` 的 `when: manual` 保留了生产部署的人工闸门，在自动化流水线中为最高风险的一步留了一道人为确认。生产环境的常见坑是把签名验证只放在构建端而省掉部署端那次，看似省事，实则放弃了整个"传输中被替换"的防护面。

#### GitLab Runner 加固

流水线定义得再安全，最终执行它的仍是 Runner——如果 Runner 本身是一台特权容器、可写根文件系统、持有全部内核能力，那么任意一个构建任务里的恶意代码都可能逃逸到宿主机，进而污染其他项目的构建。所以 Runner 加固的目标是把每次构建关进一个尽可能受限的盒子里。下面的配置就是在给这个盒子上锁。

Runner 配置直接影响构建环境的隔离性。关键约束：`privileged = false` 禁止特权容器（防止容器逃逸）；`read_only = true` 只读根文件系统（限制持久化能力）；`cap_drop = ["ALL"]` 移除所有 Linux capabilities（按需添加最小必要集合）：

```toml
# /etc/gitlab-runner/config.toml
concurrent = 4
check_interval = 0

[[runners]]
  name = "secure-docker-runner"
  url = "https://gitlab.example.com"
  token = "RUNNER_TOKEN"
  executor = "docker"
  run_untagged = false
  tag_list = ["secure", "production"]

  [runners.docker]
    tls_verify = true
    image = "alpine:latest"
    privileged = false           # 禁止特权容器，防止容器逃逸
    disable_cache = false
    volumes = ["/cache"]
    network_mode = "bridge"
    memory = "2g"
    memory_swap = "2g"
    memory_reservation = "1g"
    cpus = "2"
    security_opt = ["no-new-privileges:true"]
    cap_drop = ["ALL"]           # 移除所有 capabilities，按需添加
    cap_add = ["NET_BIND_SERVICE"]
    read_only = true             # 只读根文件系统，限制持久化
    tmpfs = {"/tmp" = "rw,noexec,nosuid,size=100m"}

  [runners.cache]
    Type = "s3"
    Shared = false
    [runners.cache.s3]
      ServerAddress = "s3.amazonaws.com"
      BucketName = "gitlab-runner-cache"
      BucketLocation = "us-east-1"
      Insecure = false
      AuthenticationType = "iam"
```

这段 TOML 体现的是"默认拒绝、按需放行"的加固范式。`cap_drop = ["ALL"]` 先清空全部 Linux capabilities，再用 `cap_add = ["NET_BIND_SERVICE"]` 精确补回唯一确实需要的那一项，这比"保留默认再删几个"要安全得多。`read_only = true` 让根文件系统只读，攻击者即使执行了恶意代码也无法在容器内落地持久化文件；而构建过程确实需要临时可写空间，于是用 `tmpfs` 单独挂载 `/tmp` 并加上 `noexec,nosuid` 限定，既满足了写需求又禁止从该目录执行程序、禁止 setuid 提权。`run_untagged = false` 配合 `tag_list` 则确保这台加固过的 Runner 只承接明确打了 `secure`、`production` 标签的任务，避免被无关作业随意调度。生产环境的坑往往出在 `privileged`：很多团队为了在 CI 里跑 Docker-in-Docker 图省事直接开 `privileged = true`，等于把容器逃逸的门敞开——更稳妥的路径是改用无需特权的构建工具（本节后文 Jenkins 部分的 Kaniko 就是这一思路的例子）。

### Jenkins 安全加固

Jenkins 与前两者有个根本差异：它是需要自行安装运维的长期服务，攻击面因此多出两块——运行构建的 agent，以及 Jenkins 控制器（controller）本身。所以 Jenkins 的加固分两层来谈：先是 pipeline 层面如何隔离每次构建（下面的 Jenkinsfile），再是 Jenkins 实例本身如何收紧（随后的系统加固脚本）。下面这份 Jenkinsfile 的核心设计是用一次性的 Kubernetes Pod 作为构建 agent，构建结束 Pod 即销毁，避免构建环境在多次任务间残留状态。

Jenkins pipeline 的安全加固需关注 agent 配置、凭证管理、构建隔离。以下配置使用 Kubernetes Pod 作为构建 agent，通过 Pod 安全上下文实现最小权限：

```groovy
// Jenkinsfile
@Library('security-shared-library') _

pipeline {
    agent {
        kubernetes {
            yaml """
apiVersion: v1
kind: Pod
metadata:
  labels:
    jenkins: agent
spec:
  serviceAccountName: jenkins-agent-sa
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 1000
  containers:
  - name: build
    image: maven:3.9-eclipse-temurin-17
    command: ['cat']
    tty: true
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      runAsNonRoot: true
      capabilities:
        drop: ['ALL']
    resources:
      requests:
        memory: "1Gi"
        cpu: "500m"
      limits:
        memory: "2Gi"
        cpu: "1000m"
"""
        }
    }

    options {
        buildDiscarder(logRotator(numToKeepStr: '10'))
        disableConcurrentBuilds()
        timeout(time: 30, unit: 'MINUTES')
        timestamps()
    }

    environment {
        ARTIFACTORY_CREDS = credentials('artifactory-credentials')
        COSIGN_PRIVATE_KEY = credentials('cosign-private-key')
        HOME = "${WORKSPACE}"
        MAVEN_OPTS = '-Dmaven.repo.local=${WORKSPACE}/.m2/repository'
    }

    stages {
        stage('Security Checks') {
            parallel {
                stage('Code Analysis') {
                    steps {
                        container('build') {
                            sh './mvnw spotbugs:check'
                            sh 'trufflehog filesystem --directory=. --json > trufflehog-results.json'
                            recordIssues(tools: [spotBugs()])
                        }
                    }
                }
                stage('Dependency Check') {
                    steps {
                        container('build') {
                            sh './mvnw dependency-check:check'
                            sh 'syft scan . -o cyclonedx-json > sbom.json'
                            // 将 SBOM 上传到 Dependency-Track 进行持续分析
                            dependencyTrackPublisher(
                                artifact: 'sbom.json',
                                projectName: 'myapp',
                                projectVersion: "${env.BUILD_NUMBER}",
                                synchronous: true,
                                failOnError: true
                            )
                        }
                    }
                }
            }
        }

        stage('Build') {
            steps {
                container('build') {
                    sh './mvnw clean package -DskipTests'
                    archiveArtifacts artifacts: 'target/*.jar', fingerprint: true
                }
            }
        }

        stage('Sign & Attest') {
            steps {
                container('build') {
                    script {
                        // 对制品本身签名
                        sh '''
                            cosign sign-blob --key ${COSIGN_PRIVATE_KEY} \
                                --yes \
                                --output-signature=target/app.jar.sig \
                                target/app.jar
                        '''
                        // 生成并附加 SLSA 溯源证明
                        def provenance = generateSLSAProvenance(
                            artifact: 'target/app.jar',
                            builder: 'jenkins',
                            buildDefinition: env.BUILD_URL
                        )
                        writeFile file: 'provenance.json', text: provenance
                        sh '''
                            cosign attest --key ${COSIGN_PRIVATE_KEY} \
                                --predicate provenance.json \
                                target/app.jar
                        '''
                    }
                }
            }
        }

        stage('Container Build') {
            steps {
                container('build') {
                    script {
                        // 使用 Kaniko 进行无 daemon 构建（避免挂载 Docker socket）
                        sh '''
                            /kaniko/executor \
                                --dockerfile=Dockerfile \
                                --context=. \
                                --destination=myregistry.io/myapp:${BUILD_NUMBER} \
                                --cache=true \
                                --push-retry=3
                        '''
                        sh '''
                            trivy image \
                                --severity HIGH,CRITICAL \
                                --exit-code 1 \
                                myregistry.io/myapp:${BUILD_NUMBER}
                        '''
                        sh '''
                            cosign sign --key ${COSIGN_PRIVATE_KEY} \
                                myregistry.io/myapp:${BUILD_NUMBER}
                        '''
                    }
                }
            }
        }
    }

    post {
        always {
            // 清理工作区中的密钥文件——防止残留密钥被后续构建读取
            cleanWs(deleteDirs: true, patterns: [
                [pattern: '**/*.key', type: 'INCLUDE'],
                [pattern: '**/*.pem', type: 'INCLUDE'],
                [pattern: '.m2/settings.xml', type: 'INCLUDE']
            ])
        }
        failure {
            emailext(
                subject: "Security Pipeline Failed: ${env.JOB_NAME} #${env.BUILD_NUMBER}",
                body: """
                    Pipeline failed security checks.
                    Build: ${env.BUILD_URL}
                    Branch: ${env.BRANCH_NAME}
                    Commit: ${env.GIT_COMMIT}
                """,
                to: 'security-team@example.com'
            )
        }
    }
}
```

这份 pipeline 篇幅较长，但骨架清晰，可以顺着几个关键决策来读。首先是 Pod 模板里的 `securityContext`——`readOnlyRootFilesystem`、`runAsNonRoot`、`allowPrivilegeEscalation: false`、`capabilities.drop: ['ALL']` 这一组约束，与前面 GitLab Runner 的加固字段一一呼应，说明同一套"最小权限容器"原则在 Kubernetes 语境下的落地方式。其次是 `Security Checks` 阶段用 `parallel` 把代码分析与依赖检查并行跑，在不牺牲安全覆盖的前提下压缩流水线时长——注意这里同时做了静态分析（spotbugs）、密钥扫描（trufflehog）和依赖检查（dependency-check）加 SBOM 生成，安全动作前置。第三个关键设计是 `Container Build` 里改用 Kaniko 而非直接调用 Docker：注释点明其目的是"无 daemon 构建，避免挂载 Docker socket"——把宿主机的 Docker socket 挂进构建容器几乎等同于授予宿主机 root 权限，是容器化 CI 里最危险的反模式之一，Kaniko 正是为回避这一点而生。最后不可忽视 `post { always { cleanWs ... } }`：它在每次构建收尾时定向清除 `*.key`、`*.pem` 和 Maven settings 文件，防止本次构建注入的密钥残留在工作区被后续任务读取——这正是威胁模型里"密钥窃取"向量在同一 Runner 复用场景下的现实防线。生产环境的常见坑是只在成功路径清理密钥，而 `always` 块保证了即便构建失败密钥也被清除，避免失败任务反而留下敏感残留。

#### Jenkins 系统加固

上面管住了单次构建，但 Jenkins 控制器本身若不加固，攻击者可能绕过 pipeline 直接从管理界面下手——弱授权、CSRF、旧版不安全协议都是常见入口。下面这段 `init.groovy.d` 初始化脚本的价值在于把这些加固项固化为随实例启动自动执行的代码，而非依赖管理员手动在 UI 里逐项勾选（手动配置既易遗漏，也无法版本化审计）。

Jenkins 实例本身需要进行安全加固。以下 Groovy 初始化脚本实现了 CSRF 保护、授权策略配置、禁用不安全协议等关键控制：

```groovy
// /var/jenkins_home/init.groovy.d/security-hardening.groovy
import jenkins.model.Jenkins
import jenkins.security.s2m.AdminWhitelistRule
import hudson.security.*
import hudson.security.csrf.DefaultCrumbIssuer
import jenkins.security.ApiTokenProperty

def instance = Jenkins.getInstance()

// 启用 CSRF 保护
if (instance.getCrumbIssuer() == null) {
    instance.setCrumbIssuer(new DefaultCrumbIssuer(true))
}

// 配置授权策略（矩阵授权）
def strategy = new ProjectMatrixAuthorizationStrategy()
strategy.add(Jenkins.ADMINISTER, "admin")
strategy.add(Jenkins.READ, "authenticated")
instance.setAuthorizationStrategy(strategy)

// 启用 Agent → Controller 访问控制——防止受攻击的 Agent 控制 Controller
// false 表示访问控制开启（保护生效），true 才是关闭保护
def masterKillSwitch = instance.getDescriptor(AdminWhitelistRule.class)
masterKillSwitch.setMasterKillSwitch(false)

import org.jenkinsci.plugins.antisamy.AntiSamyMarkupFormatter
instance.setMarkupFormatter(new AntiSamyMarkupFormatter(""))

// 禁用旧版不安全协议
def protocols = instance.getAgentProtocols() as Set
protocols.removeAll(['JNLP-connect', 'JNLP2-connect', 'JNLP3-connect', 'CLI-connect', 'CLI2-connect'])
instance.setAgentProtocols(protocols)

// 禁用旧版 API Token（强制使用新版带过期控制的 Token）
ApiTokenProperty.DescriptorImpl apiTokenDescriptor =
    instance.getDescriptorByType(ApiTokenProperty.DescriptorImpl.class)
apiTokenDescriptor.setCreationOfLegacyTokenEnabled(false)

instance.save()
```

这段脚本每一节都对应一类 Jenkins 特有的历史弱点，读时可逐块对号入座。`DefaultCrumbIssuer` 开启 CSRF 保护，防止攻击者诱导已登录管理员的浏览器发起伪造的构建/配置请求。`ProjectMatrixAuthorizationStrategy` 把权限从"登录即可操作"收紧为按主体授予——这里明确只有 `admin` 具备 `ADMINISTER`、认证用户仅有 `READ`，遵循最小权限。移除 `JNLP-connect` 等旧版 agent 协议和禁用 legacy API Token，针对的是 Jenkins 生态中长期存在的向后兼容包袱：这些老协议缺乏现代认证与加密，legacy token 又没有过期控制，都是被利用的常见薄弱点，强制切到新版机制即堵住这些历史缺口。`AntiSamyMarkupFormatter` 则对用户可输入的富文本做净化，防止存储型 XSS。需要提醒的一处细节是 `setMasterKillSwitch(false)`——这里传入 `false` 正好是"开启"Agent → Controller 访问控制（kill switch 关闭即保护生效），从而防止受攻击的 agent 反向控制 controller；`true` 才是关闭这层保护。这类"开关取值代表启用还是禁用"的地方语义容易被直觉误判，是运维中最容易配反的坑。补充一点：自 Jenkins 2.326 起该访问控制已内建于核心并始终生效，`AdminWhitelistRule` 被降为空实现，上述调用仅剩日志提示、可安全移除；本例保留它是为了兼容 2.326 之前的旧版本。

## 7.4.3 SLSA 框架实施路线图

前两节的加固回答了"怎么把某个平台配得更安全"，但还缺一个统一的度量标尺来回答"我的构建到底安全到什么程度、下一步该补什么"。SLSA（Supply-chain Levels for Software Artifacts）提供的正是这样一把分级尺子。本节按现行的 SLSA v1.2（2025-11-24 发布）校准[1]——自 v1.0 起该框架被重构为多个 track，Build track 至今仍为 L1/L2/L3 三级；早期四级模型的 Level 4（双人审查 + 密封/可重现构建）已从正式等级中移除，本节将其作为超出 Build track 的补充控制单独说明。v1.2 新增的 Source track 覆盖源码环节，不改变本节的 Build track 结论。它的分级逻辑值得先建立：等级递进的不是制品上贴了多少安全标签，而是构建过程本身的可信程度——高等级意味着连构建平台的运维者都难以在不留痕迹的情况下伪造产物。

SLSA 的核心洞察是：签名本身不够，必须保证签名发生在可信的构建过程中。每个等级递进地提高构建过程本身的保证强度，而不只是制品上的安全属性。

"签名本身不够"这句话是理解整个 SLSA 框架的钥匙。一个有效签名只能证明"某个持有私钥的主体认可了这个制品"，但无法证明"这个制品是由声明的源码、经声明的流程构建出来的"。如果构建环境已被入侵，攻击者完全可以让恶意制品走完正常签名流程，得到一个技术上完全有效的签名。SLSA 因此把关注点从"制品有没有被签"移到"制品是怎么产生的、这个过程能否被独立验证"，这也是它按"构建过程保证强度"而非"制品属性"来分级的根本原因。后面 Build track 的三个等级，保证强度一级级往构建过程深处推进，在此之上还能叠加补充控制。

![SLSA 框架](../../../assets/images/chapter_07/03_SLSA_Framework_v6.png)

### SLSA Build L1：构建证明

目标：记录构建过程的基本信息，为后续审计提供基础溯源能力。

Level 1 是入门门槛，刻意把要求压到最低——只需生成一份记录"谁、何时、用什么定义构建了这个制品"的证明文件，连签名都不强制。这样设计的动机是降低起步阻力：先让组织养成"每次构建都产出可追溯记录"的习惯，建立溯源基线，签名等更强保证留到后续等级再加。下面的 workflow 就是这样一个最小实现。

Level 1 的核心要求是生成构建证明（provenance），记录构建发生的位置、时间、使用的构建定义。此阶段不要求签名，价值在于建立可追溯性基线。格式上，SLSA provenance 以 in-toto Attestation Framework 为载体（in-toto 已于 2025 年 4 月从 CNCF 毕业）[3]，当前应使用 in-toto Statement v1 信封与 `https://slsa.dev/provenance/v1` 谓词类型，早期示例中的 `Statement/v0.1` 与 `provenance/v0.2` 属于历史版本[3]：

```yaml
# GitHub Actions: SLSA Build L1
name: SLSA Build L1

on:
  push:
    branches: [main]
  release:
    types: [published]

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      digest: ${{ steps.build.outputs.digest }}
    steps:
      - uses: actions/checkout@v4

      - name: Build artifact
        id: build
        run: |
          make build
          sha256sum target/app.jar | tee app.jar.sha256
          echo "digest=$(cut -d' ' -f1 app.jar.sha256)" >> $GITHUB_OUTPUT

      - name: Generate basic provenance
        run: |
          cat > provenance.json <<EOF
          {
            "builder": {
              "id": "https://github.com/${{ github.repository }}/actions/runs/${{ github.run_id }}"
            },
            "recipe": {
              "type": "github-actions",
              "definedInMaterial": "${{ github.sha }}",
              "entryPoint": ".github/workflows/build.yaml"
            },
            "metadata": {
              "buildStartedOn": "${{ github.event.head_commit.timestamp }}",
              "buildFinishedOn": "$(date -u +%Y-%m-%dT%H:%M:%SZ)",
              "completeness": {
                "parameters": false,
                "environment": false,
                "materials": false
              },
              "reproducible": false
            }
          }
          EOF

      - uses: actions/upload-artifact@v4
        with:
          name: provenance
          path: provenance.json
```

这段代码有两点值得关注。一是 provenance 的核心内容其实很简单：`builder.id` 指向具体的那次构建运行、`recipe` 记录用哪个 workflow 从哪个 commit 构建、`metadata` 记录起止时间——这就是一条最基本的溯源链，把"制品"和"生成它的那次构建"绑定起来。二是 `completeness` 里三个字段全为 `false`、`reproducible: false`，这是诚实，不是疏漏：Level 1 明确承认自己没有对构建参数、环境、材料做完整性保证，也不保证可重现。这种如实标注很重要，它让下游验证者清楚这份证明的保证边界在哪，不至于把 Level 1 的证明误当作强保证使用。这也预示了后续等级要补的正是这几项"尚未做到"。

Level 1 要求清单：记录构建过程；生成证明文件；签名非必需。

---

### SLSA Build L2：签名证明

目标：为证明添加防篡改签名，确保证明完整性。

Level 1 留下的最大缺口是：那份 provenance 文件本身没有任何保护，谁都能事后改写。Level 2 补的正是这个洞——给证明加上密码学签名，让"证明生成后被篡改"变得可检测。这里采用 Sigstore 的 keyless（无密钥）签名，动机是回避长期私钥的管理与泄露风险：不再需要在某处保管一把签名私钥，而是借助 GitHub Actions 的 OIDC 身份临时换取签名凭证。

Level 2 引入签名要求，使用 Sigstore 等签名服务对证明进行密码学签名。这确保证明在生成后未被篡改。`id-token: write` 权限是 Cosign keyless 签名所需——它允许 GitHub Actions 获取 OIDC token 用于无私钥签名：

```yaml
# GitHub Actions: SLSA Build L2
name: SLSA Build L2

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      id-token: write    # Cosign keyless 签名需要 OIDC token
      contents: read
      packages: write
    outputs:
      # 把制品的 base64(sha256) 摘要作为 job 输出，供下游 generator 消费
      hashes: ${{ steps.hash.outputs.hashes }}
    steps:
      - uses: actions/checkout@v4

      - name: Build
        run: make build

      - name: Install Cosign
        uses: sigstore/cosign-installer@v3

      - name: Sign artifact with Sigstore (keyless)
        run: |
          cosign sign-blob --yes \
            --bundle=app.jar.bundle \
            target/app.jar

      # 计算制品摘要并按 generator 要求编码为 base64(sha256sum 输出)
      - name: Generate subject hash
        id: hash
        run: |
          echo "hashes=$(sha256sum target/app.jar | base64 -w0)" >> "$GITHUB_OUTPUT"

  # SLSA generator 是 reusable workflow，必须作为独立 job 通过 uses 调用，
  # 由 needs 依赖 build、并用 with 传入上游产出的摘要
  provenance:
    needs: [build]
    permissions:
      id-token: write    # generator 需要 OIDC 身份签署 provenance
      contents: write    # 将 provenance 附加到 release 资产
      actions: read      # 读取 workflow 运行信息以填充溯源
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v1.9.0
    with:
      provenance-name: app.jar.intoto.jsonl
      base64-subjects: ${{ needs.build.outputs.hashes }}

  verify:
    needs: [build, provenance]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Verify provenance
        run: |
          slsa-verifier verify-artifact \
            --provenance-path app.jar.intoto.jsonl \
            --source-uri github.com/${{ github.repository }} \
            target/app.jar
```

对比 Level 1，这份 workflow 的差别集中在两处，也正是 Level 2 的实质。其一是引入了 `id-token: write` 权限——这是整个 keyless 签名的前提，它授权 workflow 获取一枚证明"我确实是 GitHub 上这个仓库的这次运行"的 OIDC 令牌，Cosign 拿它去换取一次性签名凭证，签完即弃，无需团队保管任何长期私钥。这也解释了前面权限表里为何特别提示 `id-token: write` 要谨慎授予：它就是身份联邦的入口。其二是流程从"只生成证明"升级为"生成证明并当场验证"——`provenance` job 产出 SLSA provenance 后，独立的 `verify` job 再用 `slsa-verifier verify-artifact` 把它与制品、源仓库比对一遍，形成生成即验证的闭环。这里有一处结构上必须留意的实现细节：`slsa-github-generator` 是一个 **reusable workflow**，不能当作某个 step 的 `uses:` 来调用，而必须作为独立 job 通过 job 级 `uses:` 引入，用 `needs: [build]` 依赖构建、再用 `with` 把 `build` job 输出的 base64 摘要（`needs.build.outputs.hashes`）传进去——generator 消费的是这个摘要而非某个 step 的输出，因此 `build` job 里专门有一步 `id: hash` 计算并通过 `$GITHUB_OUTPUT` 暴露它。此外 generator job 需要自己的 `id-token: write`（签署 provenance）、`contents: write`（附加到 release）、`actions: read`（读取运行信息）权限。这里的权衡是：keyless 签名省去了私钥管理负担，但把信任转移到了 Sigstore 的透明日志与身份提供方，组织需要接受这条外部信任链；对多数团队而言，这个取舍通常是划算的。

Build L2 要求清单：Build L1 所有要求；使用签名服务（Sigstore）；防篡改证明；托管构建平台（非自建）。

### SLSA Build L3：加固构建

目标：隔离的、不可篡改的构建环境——即使构建服务的管理员也无法伪造证明。

Level 2 保证了证明不被事后篡改，但仍有一个更深的漏洞：如果构建过程本身能被干预——比如某人往构建环境里注入额外步骤、或让不同构建互相污染——那么一份"诚实生成"的签名证明反而会为被污染的制品背书。Level 3 的目标就是堵死这一层，把要求推进到构建环境本身：环境必须隔离、不可篡改，理想情况下连构建平台的管理员也无法在不被发现的前提下伪造证明。这需要两样东西配合——一个受限到底的运行环境，和一个从源头就杜绝外部干扰的构建工具。

Level 3 要求构建在隔离环境中执行。容器的 `--read-only` 和 `--security-opt=no-new-privileges:true` 限制了攻击者在构建环境中的持久化能力。使用 Bazel 进行 Hermetic Build 确保构建过程与外部环境隔离：

```yaml
# .github/workflows/slsa-l3.yaml
name: SLSA Build L3

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    container:
      image: cgr.dev/chainguard/wolfi-base:latest
      options: --read-only --security-opt=no-new-privileges:true
    permissions:
      contents: read
      packages: write    # 推送镜像到 GHCR
    outputs:
      # 把镜像 digest 作为 job 输出，供下游 container generator 消费
      image: ${{ steps.build.outputs.image }}
      digest: ${{ steps.build.outputs.digest }}

    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false

      - name: Setup Bazel (hermetic build tool)
        run: |
          wget https://github.com/bazelbuild/bazel/releases/download/6.4.0/bazel-6.4.0-linux-x86_64
          echo "expected_sha256 bazel-6.4.0-linux-x86_64" | sha256sum -c -
          chmod +x bazel-6.4.0-linux-x86_64
          ./bazel-6.4.0-linux-x86_64 version

      - name: Hermetic build and push image
        id: build
        run: |
          ./bazel-6.4.0-linux-x86_64 run //:push_image \
            --spawn_strategy=sandboxed \
            --experimental_strict_action_env \
            --action_env=PATH=/usr/bin:/bin
          # 推送后从 registry 取回不可变的 digest，供 generator 绑定
          IMAGE=ghcr.io/${{ github.repository }}
          DIGEST=$(crane digest "${IMAGE}:${{ github.sha }}")
          echo "image=${IMAGE}" >> "$GITHUB_OUTPUT"
          echo "digest=${DIGEST}" >> "$GITHUB_OUTPUT"

  # container generator 同样是 reusable workflow，作为独立 job 调用，
  # 用 needs 拿到 build 输出的 image 与 digest 生成并推送 provenance
  provenance:
    needs: [build]
    permissions:
      id-token: write    # 签署 provenance
      actions: read      # 读取运行信息填充溯源
      packages: write    # 将 provenance 推送到镜像仓库
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@v1.9.0
    with:
      image: ${{ needs.build.outputs.image }}
      digest: ${{ needs.build.outputs.digest }}
    secrets:
      registry-username: ${{ github.actor }}
      registry-password: ${{ secrets.GITHUB_TOKEN }}

  verify:
    needs: [build, provenance]
    runs-on: ubuntu-latest
    steps:
      - name: Install slsa-verifier
        run: |
          wget https://github.com/slsa-framework/slsa-verifier/releases/download/v2.4.1/slsa-verifier-linux-amd64
          chmod +x slsa-verifier-linux-amd64

      - name: Verify SLSA provenance
        run: |
          ./slsa-verifier-linux-amd64 verify-image \
            ${{ needs.build.outputs.image }}@${{ needs.build.outputs.digest }} \
            --source-uri github.com/${{ github.repository }} \
            --source-tag ${{ github.ref_name }}
```

这份 workflow 相比 SLSA Build L2 引入了三层新的隔离手段，读时可依次定位。第一层是 `container` 的 `options: --read-only --security-opt=no-new-privileges:true`——在只读文件系统里构建，攻击者无法落地持久化产物，`no-new-privileges` 又切断了运行中提权的路径。第二层是构建工具的 hermetic 化：Bazel 以 `--spawn_strategy=sandboxed` 沙箱执行，`--experimental_strict_action_env` 加显式指定 `--action_env=PATH` 把构建可见的环境变量收窄到白名单，目的是让构建结果不再受构建机器上散落状态的影响——这一步已经在为 7.4.4 的可重现构建做铺垫。第三层是把流程拆成 `build`、`provenance`、`verify` 三个独立 job：`build` 完成 hermetic 构建并推送镜像、把 `image` 与不可变 `digest` 作为 job 输出暴露；`provenance` job 作为独立 job 调用 container generator（同样是 reusable workflow，不能塞进某个 step 的 `uses:`），通过 `needs: [build]` 拿到摘要后生成并推送 provenance；`verify` 再在一个干净环境里用 `slsa-verifier` 按 `image@digest` 重新验证。这里有一个和 L2 相同的实现要点：generator 消费的是 `needs.build.outputs.digest` 这个 job 级摘要，而非某个 step 的输出，因此 `build` 里专门有 `id: build` 一步在推送后用 `crane digest` 取回不可变摘要并写入 `$GITHUB_OUTPUT`——这样 provenance 才真正绑定到"推上去的那一份镜像"，而不是一个悬空引用。三层叠加，才共同支撑起"连管理员也难以伪造"这一目标。此外注意下载 Bazel 二进制时同样先 `sha256sum -c` 校验哈希——工具链自身的完整性也被纳入信任链，避免构建工具本身成为被替换的入口。

Build L3 要求清单：Build L2 所有要求；隔离构建环境；防篡改证明生成；不可变基础设施；审计所有构建步骤。官方对 L3 的措辞重点是"构建平台需保证不同构建之间相互隔离，且签署溯源所用的密钥对用户定义的构建步骤不可达"，落地时应对照官方 Build track 要求逐条自查[4]。

### 补充控制（超出 Build track）：双人审查 + 密封/可重现构建

目标：在达成 Build L3 之后，所有变更需要两方独立审查，并通过密封构建确保完全确定性。

> 说明：SLSA 的 Build track 到 L3 为止（v1.0 至 v1.2 均如此）。下面这套"双人审查 + 密封/可重现构建"在早期四级模型中曾是 Level 4，v1.0 已将其从正式等级移除、列为未来 track 的候选控制。本节仍保留它，是因为对金融、关键基础设施这类高保障场景，它们是在 Build L3 之上值得叠加的补充控制。

Build L3 假想的攻击者还停留在"入侵构建环境"这一层。这套补充控制则要防住更强的对手：一个已经拿到应用代码仓库写权限、甚至掌握了某个内部人员账户的攻击者。对付这种威胁，单点控制都不再可靠，于是引入两条结构性防线——一是所有变更强制两方独立审查，让单个被攻陷的账户无法独自推动恶意变更；二是把构建定义从应用代码里彻底分离，存放在独立仓库。后者的设计意图很关键：即便攻击者完全控制了应用代码仓库，也触碰不到构建配置仓库，因而无法直接触发或改写生产构建。

这套控制要求构建定义与源代码分离存储（独立仓库），所有变更需独立审查。使用 HSM 签名替代软件密钥，提供最高等级的密钥保护。这种架构设计意味着：即使攻击者入侵了应用代码仓库，也无法直接触发生产构建——构建配置仓库的独立性是关键防线：

```yaml
# myapp-build-config/.github/workflows/build.yaml
# 构建配置独立仓库，与应用代码分离存储
name: Hermetic Build with Two-Person Review (beyond Build L3)

on:
  repository_dispatch:
    types: [trigger-build]

jobs:
  build:
    runs-on: ubuntu-latest
    container:
      image: gcr.io/company/hermetic-builder:v2.1.0

    steps:
      - name: Checkout application source
        uses: actions/checkout@v4
        with:
          repository: company/myapp
          ref: ${{ github.event.client_payload.sha }}
          persist-credentials: false

      - name: Verify dependencies
        # 所有依赖的哈希值预先声明并锁定，确保构建输入可重现
        run: |
          sha256sum -c DEPENDENCIES_SHA256SUMS

      - name: Build with Bazel
        run: |
          bazel build //... \
            --spawn_strategy=standalone \
            --experimental_strict_action_env \
            --action_env=PATH=/usr/bin:/bin \
            --noexperimental_check_external_repository_files \
            --repository_cache=/workspace/cache

      - name: Generate comprehensive provenance
        run: |
          slsa-provenance-generator \
            --artifact=bazel-bin/app \
            --builder-id="https://github.com/company/myapp-build-config" \
            --materials="$(bazel query 'deps(//...)' --output=json)" \
            --recipe-type="https://slsa.dev/bazel-build/v1" \
            --output=provenance.intoto.jsonl

      - name: Sign with HSM
        # HSM 签名替代软件密钥，提供最高等级的密钥保护
        uses: company/hsm-signer-action@v2
        with:
          artifact: bazel-bin/app
          provenance: provenance.intoto.jsonl
          hsm-url: ${{ secrets.HSM_URL }}
          key-id: ${{ secrets.SIGNING_KEY_ID }}
```

这份配置把这套补充控制的几处"最高等级"要求逐一具象化，读时可对照体会它与 Build L3 的差距。触发方式改成 `repository_dispatch`——构建由独立的配置仓库响应外部事件发起，而非由应用代码的 push 直接触发，这正是"构建配置与应用代码分离"在流水线机制上的落点：应用仓库只能请求构建，不能定义构建怎么跑。`Verify dependencies` 一步用 `sha256sum -c DEPENDENCIES_SHA256SUMS` 对所有依赖逐一核对预先锁定的哈希，把"构建输入完全确定"从口号变成硬校验。`Generate comprehensive provenance` 里通过 `bazel query 'deps(//...)'` 把完整依赖图写进证明的 `materials`，对应"完整依赖图证明"的要求——溯源不再只记录顶层材料，而是覆盖整棵依赖树。最后 `Sign with HSM` 用硬件安全模块替代软件密钥签名：私钥永不离开 HSM，即便构建环境被攻破，攻击者也拿不到可复制的签名密钥。付出的代价也很直白：HSM、独立仓库、双人审查都带来可观的运维复杂度，这也是为什么这套补充控制主要面向金融、关键基础设施这类高保障场景。

补充控制清单：Build L3 所有要求；所有变更需两方审查；构建定义与源代码分离；Hermetic builds（完全确定性）；完整依赖图证明。

适用边界：这套补充控制适用于高安全要求场景，如金融基础设施、关键国家基础设施。对于大多数企业，Build L2-L3 是更务实的目标。

常见误区：

1. 认为达成 SLSA 等级即完成安全建设——SLSA 聚焦构建完整性，不涵盖运行时安全、访问控制等领域
2. 跳过低等级直接追求高等级——各等级是递进关系，跳级可能导致基础薄弱

这两条误区背后是同一个认知偏差：把 SLSA 等级当成安全的"总分"而非"某个维度的刻度"。第一条提醒 SLSA 只度量构建完整性这一条线，运行时防护、访问控制、密钥全生命周期管理各有其框架，达成高 SLSA 等级不等于这些领域也到位。第二条则呼应了前面各等级层层递进的叙述——每一级都建立在下一级已经做到的基础上（L2 的签名前提是 L1 的证明，L3 的隔离前提是 L2 的签名），跳级追高会让上层保证悬空在薄弱地基上，看似达标实则不牢。

## 7.4.4 Hermetic Builds 实现

前面 SLSA Build L3 及其上的补充控制反复提到"hermetic build"和"可重现"，这里专门展开说明。它之所以是高等级 SLSA 的技术基石，是因为它把"制品可信"从"我相信构建者"变成了"任何人都能自己验证"——只要拿到同样的源码和依赖，独立重跑一遍就该得到逐字节相同的产物，对不上就说明构建过程被动过手脚。这种可独立复核的属性，是供应链信任从"人的承诺"升级为"数学事实"的关键一步。

Hermetic build（密封构建）指构建过程完全确定，不依赖构建机器的状态或外部网络。相同输入必须产生相同输出。这一属性对供应链安全至关重要：可重现的构建意味着任何人都可以独立验证制品确实来自声明的源代码，而非被篡改过的构建过程。

要做到"相同输入产生相同输出"，必须消除两大不确定性来源：一是构建机器上散落的状态（不同版本的编译器、环境变量、本地缓存），二是构建期间的外部网络访问（今天拉到的依赖和明天可能不同）。下面分别用 Bazel 和 Nix 演示如何压制这两个变量。

### 使用 Bazel 实现 Hermetic Build

Bazel 的思路是"把一切都显式声明并锁定"：依赖的坐标、版本、乃至工具链的哈希都写进版本控制，构建时在沙箱里执行、禁止访问未声明的资源。下面三段配置分别对应依赖的声明（BUILD.bazel）、来源与锁定（WORKSPACE）、以及带 hermetic 标志的构建命令。

Bazel 通过沙箱执行和依赖锁定确保构建可重现。`--sandbox_default_allow_network=false` 是关键标志——它阻止构建步骤在执行期间访问外部网络，确保所有依赖都来自预先声明和锁定的来源：

```python
# BUILD.bazel
load("@rules_java//java:defs.bzl", "java_binary", "java_library")

java_library(
    name = "mylib",
    srcs = glob(["src/main/java/**/*.java"]),
    deps = [
        "@maven//:com_google_guava_guava",
        "@maven//:org_slf4j_slf4j_api",
    ],
)

java_binary(
    name = "myapp",
    main_class = "com.example.Main",
    runtime_deps = [":mylib"],
)
```

`BUILD.bazel` 定义了构建目标与依赖关系：`mylib` 的 `deps` 明确列出它依赖哪些 Maven 制品，`myapp` 又依赖 `mylib`。关键在于依赖是被显式、精确声明的（`@maven//:...`），而非在构建时才去动态解析——这让 Bazel 能在构建前就掌握完整的依赖图，是沙箱化和可重现的前提。

```python
# WORKSPACE
load("@bazel_tools//tools/build_defs/repo:http.bzl", "http_archive")

http_archive(
    name = "rules_jvm_external",
    sha256 = "expected_sha256_hash_here",  # SHA 锁定确保工具链本身不被篡改
    strip_prefix = "rules_jvm_external-5.2",
    url = "https://github.com/bazelbuild/rules_jvm_external/releases/download/5.2/rules_jvm_external-5.2.tar.gz",
)

load("@rules_jvm_external//:defs.bzl", "maven_install")

maven_install(
    artifacts = [
        "com.google.guava:guava:32.1.2-jre",
        "org.slf4j:slf4j-api:2.0.9",
        "org.slf4j:slf4j-simple:2.0.9",
    ],
    repositories = [
        "https://repo1.maven.org/maven2",
    ],
    maven_install_json = "//:maven_install.json",  # 依赖锁文件
    fetch_sources = True,
)

load("@maven//:defs.bzl", "pinned_maven_install")
pinned_maven_install()
```

`WORKSPACE` 是可重现性的核心所在，两处锁定值得注意。一是 `http_archive` 的 `sha256` 字段对 `rules_jvm_external` 工具链本身做哈希锁定——连构建规则的来源都不放过，因为工具链若被替换，后面一切都无从谈起。二是 `maven_install` 里 `artifacts` 精确到补丁版本（如 `guava:32.1.2-jre`），并通过 `maven_install_json` 指向一个锁文件：这个锁文件记录了每个依赖及其传递依赖的确切哈希，`pinned_maven_install()` 则强制构建只接受与锁文件哈希一致的依赖。二者合起来，就把"从哪拉、拉什么版本、拉到的内容对不对"三个问题全部钉死，这正是相同输入的具体含义。

```bash
# 生成依赖锁文件（首次运行，将结果提交到版本控制）
bazel run @maven//:pin

# Hermetic build 命令
bazel build //myapp:myapp \
  --spawn_strategy=standalone \
  --experimental_strict_action_env \
  --action_env=PATH=/usr/bin:/bin \
  --sandbox_default_allow_network=false \    # 阻止构建期间的外部网络访问
  --incompatible_strict_action_env=true

# 验证构建可重现性（清除缓存后重新构建，哈希应相同）
bazel clean --expunge
bazel build //myapp:myapp
sha256sum bazel-bin/myapp/myapp
```

这段命令把可重现构建的完整节奏走了一遍。首先 `bazel run @maven//:pin` 生成前面提到的锁文件，注释强调要把它提交到版本控制——锁文件不入库，锁定就形同虚设。核心的 `bazel build` 命令堆叠了几个 hermetic 标志，其中最点睛的是 `--sandbox_default_allow_network=false`：它在构建执行期间切断外部网络，逼迫所有依赖只能来自事先声明并锁定的来源，从根上消灭了"构建期偷偷联网拉了个未锁定的东西"这一不确定性；`--experimental_strict_action_env` 与 `--action_env=PATH` 则消除环境变量差异。最后三行是验证环节：`bazel clean --expunge` 彻底清空缓存后重建，再 `sha256sum` 比对哈希——如果两次构建哈希一致，就实证了这套配置确实做到了可重现。这个"清缓存重建再比哈希"的动作，正是 hermetic build 从声明变成可验证事实的落点。

### 使用 Nix 实现 Hermetic Build

Nix 走的是另一条路径。Bazel 靠沙箱和锁文件在构建过程中强制隔离，Nix 则把整个构建建模为一个纯函数：输入（源码、依赖、构建脚本）确定，输出就唯一确定，并用哈希把这种确定性固化下来。呈现给读者的是同一个可重现目标的不同实现哲学——一个偏工程约束，一个偏声明式的数学纯粹性。

Nix 通过声明式依赖管理实现构建可重现性。`outputHash` 字段是 Nix 确保可重现性的机制——它预先声明了构建产物的期望哈希，如果实际产物哈希不匹配，构建失败：

```nix
# default.nix
{ pkgs ? import <nixpkgs> {
    rev = "23.11";
    sha256 = "expected_sha256_here";  # 锁定 nixpkgs 版本
  }
}:

pkgs.stdenv.mkDerivation rec {
  pname = "myapp";
  version = "1.0.0";

  src = ./.;

  nativeBuildInputs = with pkgs; [
    maven
    jdk17
  ];

  buildInputs = with pkgs; [
    jre17
  ];

  buildPhase = ''
    mvn package -o -Dmaven.repo.local=$out/.m2
  '';

  installPhase = ''
    mkdir -p $out/bin
    cp target/*.jar $out/bin/
  '';

  # outputHash 预先声明期望产物哈希，确保构建结果确定性
  outputHashMode = "recursive";
  outputHashAlgo = "sha256";
  outputHash = "expected_output_hash";
}
```

这段 Nix 表达式有两个锁定点和一个细节。第一个锁定在顶部：`import <nixpkgs>` 时指定 `rev = "23.11"` 并带 `sha256`，把整个软件包集合钉在某个确定版本——这意味着 `maven`、`jdk17` 等所有构建输入的版本都被这一次锁定统一固定，避免"换台机器 nixpkgs 版本不同导致工具链漂移"。第二个锁定在底部的 `outputHash`：它预先声明了产物应有的哈希，Nix 构建完成后会比对实际产物哈希，不一致直接失败——等于把"可重现"变成构建成功的前置条件，而非事后靠人去核对。值得一提的细节是 `buildPhase` 里 `mvn package -o` 的 `-o`（offline 离线模式）：它强制 Maven 不联网，只用已声明的依赖，这与 Bazel 的 `--sandbox_default_allow_network=false` 是同一意图在不同工具上的体现——都是为了掐断构建期的网络这个不确定性来源。

```bash
# Hermetic build
nix-build default.nix

# 验证可重现性
nix-build default.nix --rebuild
sha256sum result/bin/myapp.jar
```

验证方式与 Bazel 如出一辙：`nix-build --rebuild` 强制忽略已有缓存重新构建一遍，再用 `sha256sum` 比对产物哈希。两次哈希一致，就证明这次构建确实只由声明的输入决定，不受构建时机或机器状态影响。

验证方法：在不同机器上执行构建，比对产物哈希；清除所有缓存后重新构建，验证哈希一致性；记录构建环境信息，用于审计和回溯。

关键约束：Hermetic build 要求所有依赖预先声明并锁定版本；构建过程不能访问外部网络；初始设置成本较高，需要完整的依赖分析。

这里的"初始设置成本较高"是选型时绕不开的权衡，值得如实提醒：把一个历史项目改造成 hermetic build，往往意味着要梳理清楚它全部的隐式依赖——那些平时靠构建机器上"恰好装了"的工具和库悄悄满足的依赖，都得被翻出来显式声明和锁定。这个梳理过程通常比预期费力，也是很多团队在 hermetic 化上受阻的现实原因。因此它更适合对可重现性有硬性要求（如追求 SLSA L3/L4）的项目，对一般项目则需权衡投入产出。

## 7.4.5 实践检查清单

前面各节给出的是"怎么做"，这份检查清单则回答"做到什么程度"以及"按什么顺序做"。它把散落在各小节的加固项按第一到第四阶段分层排列，与 7.4.3 的 SLSA 等级大致对应——先夯实访问控制、密钥管理这类地基（第一阶段），再逐层叠加构建加固、SLSA 证明、hermetic build，直至专家级的双人审查与 HSM。它是一份自上而下逐项落地的团队安全成熟度自评量表，而非一次性全部达成的清单。

### 基础安全（第一阶段）

访问控制：
- [ ] 所有 CI/CD 账户启用 MFA
- [ ] 使用基于角色的访问控制（RBAC）
- [ ] 定期审计访问权限
- [ ] 使用服务账户而非个人账户

密钥管理：
- [ ] 使用原生密钥管理（GitHub Secrets、GitLab CI Variables）
- [ ] 密钥不在日志中显示
- [ ] 定期轮换密钥
- [ ] 使用短期令牌（OIDC）

pipeline 配置：
- [ ] 分支保护规则已启用
- [ ] 需要代码审查才能合并
- [ ] pipeline 文件变更需要安全团队审查

### 中级安全（第二阶段）

构建安全：
- [ ] 使用 SHA 固定 Action/镜像版本（非 tag）
- [ ] 验证外部脚本完整性
- [ ] 隔离构建环境
- [ ] 最小权限 pipeline（显式 `permissions` 块）

制品安全：
- [ ] 生成 SBOM
- [ ] 基础制品签名（Cosign）
- [ ] SCA 扫描集成
- [ ] 容器镜像扫描

监控与审计：
- [ ] 记录所有 pipeline 执行
- [ ] 异常活动告警
- [ ] 定期安全审计

### 高级安全（第三阶段）

SLSA 实施：
- [ ] SLSA Build L2 证明
- [ ] Sigstore/Cosign keyless 签名
- [ ] 准入控制（OPA/Kyverno）

构建完整性：
- [ ] Hermetic builds（Bazel/Nix）
- [ ] 构建可重现性验证
- [ ] 依赖锁定与哈希验证

### 专家级安全（第四阶段）

- [ ] 达成 SLSA Build L3 并叠加双人审查、密封/可重现构建等补充控制
- [ ] 构建定义与源代码分离（独立仓库）
- [ ] HSM 签名密钥

运行指标：pipeline 安全扫描覆盖率；密钥轮换周期达标率；分支保护规则绕过事件数；SBOM 生成覆盖率；制品签名验证通过率。

## 本节要点

CI/CD 是供应链的关键控制点：从 SolarWinds 到 Codecov，主要供应链攻击均涉及 CI/CD 系统入侵。构建环境的安全性直接决定最终制品的可信度。

最小权限原则贯穿始终：pipeline 应仅获得完成任务所需的最小权限。显式声明权限、禁用不必要的凭证持久化、隔离敏感操作。

SLSA 提供渐进式进阶路径：Build track 从 L1 的基础证明到 L3 的加固构建，之上还可叠加双人审查、密封/可重现构建等补充控制，组织可根据风险承受能力和资源约束选择目标等级。

hermetic build 是可重现性的技术基础：通过 Bazel、Nix 等工具实现完全确定的构建过程，确保相同输入产生相同输出，支持审计与回溯。

自动化验证是规模化的前提：人工审查无法跟上现代 CI/CD 的速度与规模，需依赖自动化扫描、签名验证、准入控制形成防线。

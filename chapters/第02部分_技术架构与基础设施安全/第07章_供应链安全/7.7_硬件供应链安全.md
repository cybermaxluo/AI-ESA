# 7.7　硬件供应链安全

> 导读：硬件供应链安全的独特挑战在于攻击发生在软件防御层之下——一旦固件或硬件被植入恶意代码，操作系统级别的安全工具对此几乎盲视。本节先在 7.7.1 建立威胁态势视图，在 7.7.2–7.7.3 介绍 TPM 和 Secure Boot 两个核心技术机制，再在 7.7.4 建立供应商评估框架，最后在 7.7.5 提供完整性基线检测实现。读者如果主要关注实操，可从 7.7.4 的供应商评估清单开始，遇到技术原理问题再回到 7.7.2–7.7.3。容器和软件供应链的控制层与本节形成纵深防御，参见 7.4–7.5。

硬件供应链的全球化使得设备在到达企业之前可能经过数十个国家和环节。Bloomberg 2018 年关于"服务器主板被植入间谍芯片"的报道使"硬件植入"成为安全圈的热议话题，但需要明确指出：报道中被点名的 Supermicro、Apple、Amazon 均公开且明确否认，至今未有独立证实的技术证据公开[1]，因此本节把它作为"引发行业关注的争议性报道"而非已证实案例引用。更为确定的是固件层的风险——美国国家标准与技术研究院已专门发布 SP 800-193《平台固件韧性指南》，给出固件的保护、检测与恢复要求[2]，说明固件层攻击面已被视为需要标准化应对的现实问题。

## 7.7.1 硬件供应链威胁态势

### 五阶段攻击面

要理解硬件供应链防御为什么难，先要看清攻击可以从哪里下手。软件供应链的攻击面大体收敛在代码与构建环节，而硬件的链条从晶圆到机架横跨制造、物流、固件、驱动、运行时五个阶段，每个阶段的责任主体、可见度和可用控制手段都不一样。把攻击面按阶段拆开，本质上是在回答一个部署问题：在这条链的哪一环，我方还有能力施加控制？越靠近制造端，企业的话语权越弱、只能依赖供应商与渠道信任；越靠近运行时，企业自有的检测与隔离手段才逐渐接管。下面五段正是沿着这条"控制力递增"的脉络展开：

制造阶段：在硬件制造过程中植入恶意芯片或修改电路板。这类攻击技术要求极高，通常被归因于国家行为者。代工厂、组装厂的物理访问控制是主要防线。

供应链运输阶段：设备在运输途中被拦截并修改后重新封装（supply chain interdiction）。防御方法：验证包装完整性（防拆标签、封条）、通过可信渠道采购、比对制造商提供的硬件指纹。

固件层：BIOS/UEFI、BMC（Baseboard Management Controller）、网卡固件等均可能被植入恶意代码。固件层的恶意代码能在操作系统重装后存活，且可在操作系统安全工具完全看不到的层级运行。

操作系统与驱动层：驱动签名绕过、内核模块注入、rootkit 植入。此阶段处于软件防御层可见范围内，但利用固件层特权的驱动攻击可绕过传统安全工具。

运行时：运行中的侧信道攻击（如 Spectre/Meltdown 利用 CPU 微架构特性）、物理篡改（针对物理上可访问的设备）。

这五个阶段解释了为什么本节后续把重心放在固件层与运行时基线：制造与运输阶段企业主要靠采购治理（7.7.4）间接施加控制，而固件层的持久化威胁需要 TPM 测量（7.7.2）与 Secure Boot 信任链（7.7.3）这类硬件级手段才能触及。

### 硬件攻击案例参考

下表把上面五个阶段的抽象威胁落到具体的攻击类型上。它的价值不在于罗列手段，而在于最后一列——每种攻击对应的"防御侧重"说明单一控制点无法覆盖全部攻击面，固件植入靠 Secure Boot、拦截靠渠道管控、侧信道靠微码更新，它们分属不同的技术栈和责任团队。"目标层"与"防御侧重"的对应关系，正是后续 7.7.2–7.7.5 各小节分工的索引：

| 攻击类型 | 目标层 | 典型技术手段 | 防御侧重 |
|---------|-------|------------|---------|
| 固件植入 | UEFI/BIOS | UEFI 模块替换，利用 SPI Flash 写权限 | Secure Boot + 固件完整性验证 |
| BMC 漏洞利用 | 带外管理 | 默认凭证，未修补的 BMC 固件漏洞 | 网络隔离 + 固件更新管理 |
| 供应链拦截 | 物理层 | 设备在运输途中被拆封修改 | 采购渠道管控 + 物理完整性验证 |
| 侧信道攻击 | CPU/内存 | Spectre、Meltdown 类微架构利用 | 微码更新 + 进程隔离 |

需要注意的是，表中"防御侧重"列里每一项都是必要而非充分条件：Secure Boot 能挡住未签名的固件模块，却挡不住运输途中被换掉的整块主板；渠道管控能降低拦截概率，却无法验证已到货设备内部的固件是否被改。这也是为什么真实防御必须把这几条控制叠加成纵深，而非择一采用。

## 7.7.2 TPM 与硬件信任根

### TPM 的核心作用

TPM（Trusted Platform Module）是硬件信任根的基础组件，其规范由可信计算组织（TCG）维护，现行为 TPM 2.0 Library 规范，并已被采纳为 ISO/IEC 11889[3]。其核心价值不是"存储密钥"（软件密钥库也能做到），而是提供不可软件篡改的测量与证明机制：攻击者即使控制了操作系统，也无法伪造 TPM 记录的平台状态。

这一句判断是理解整个 TPM 设计的钥匙。软件层面的任何完整性检查都有一个死结——检查者本身运行在被检查的系统之上，一旦系统被攻破，检查逻辑也可能被篡改或欺骗。TPM 打破这个死结的方式，是把"记录测量值"和"用私钥证明测量值"两件事下沉到一块操作系统无法写入的独立芯片里。下面三个功能，正是围绕"测量—绑定—证明"这条链条展开的：

平台测量（PCR 机制）：PCR（Platform Configuration Register）以哈希链的方式记录系统启动序列——从 BIOS/UEFI 到引导加载程序到操作系统内核的每个阶段，计算该阶段代码/配置的哈希并"扩展"到对应 PCR 寄存器。扩展操作是单向的（新值 = Hash(旧值 || 测量值)），意味着 PCR 值是启动序列所有阶段的累积摘要，任何单一阶段的改变都会导致最终 PCR 值不同。

密封存储（Sealing）：密钥或机密数据可以与特定 PCR 状态绑定。只有当当前 PCR 值与密封时的值匹配时，TPM 才会释放被密封的数据。典型应用：BitLocker/LUKS 的磁盘加密密钥，仅在系统以"已知好的"状态启动时才被自动释放。

远程证明（Remote Attestation）：TPM 使用其私钥对当前 PCR 值签名，生成 Quote。依赖方（如云服务提供商或企业管理平台）通过验证 Quote 的签名和 PCR 值，可以在不进行物理检查的情况下验证远端设备是否以可信状态运行。这是云环境中零信任架构的重要基础。

这三个功能有一条清晰的递进关系：测量提供事实（系统当前是什么状态），密封把这个事实变成一道本地的访问闸门（状态不对就拿不到密钥），证明则把这个事实可信地传递给远端（让别人相信你的状态）。理解了这条链条，就能明白为什么下面的模拟代码要按 `extend_pcr → generate_quote → verify_platform_state` 的顺序组织。

### 教育性演示代码

下面这段 Python 用最短的代码把 PCR 扩展、Quote 生成、状态验证三件事串起来，在没有真实 TPM 硬件的情况下呈现这套机制的数据流。这里用模拟而非直接调用 `tpm2-tools` 的原因很实际：真实 TPM 的命令行工具输出格式繁杂、依赖硬件在位，会把注意力从"机制本身"引开；而用几十行纯哈希运算就能复现 PCR 的单向累积特性和 Quote 的签名结构，信噪比更高。注意：这是教育性模拟，真实 TPM 操作需通过 tpm2-tools、tpm2-tss 或平台特定的 API 进行。这段代码有三个关键点：`extend_pcr` 里那行 `SHA256(旧值 || 新哈希)` 是整套机制的地基，`generate_quote` 里的 nonce 是抗重放的关键，`verify_platform_state` 的逐项差异返回是把"不可信"落地成"哪一步不可信"的可运维形式。

```python
import hashlib
import hmac
import os
import json
from dataclasses import dataclass, field
from typing import Dict, List

@dataclass
class TPMSimulator:
    """
    TPM 2.0 核心机制的教育性模拟。
    真实 TPM 操作需使用 tpm2-tools 或 tpm2-tss 库。
    
    PCR 索引分配（TPM 2.0 规范）：
    - PCR 0: BIOS/UEFI 固件代码
    - PCR 1: BIOS/UEFI 配置
    - PCR 4: 引导加载程序（MBR、UEFI 应用）
    - PCR 7: Secure Boot 状态与证书数据库
    - PCR 8-9: GRUB 配置与内核命令行
    """
    pcr_registers: Dict[int, bytes] = field(default_factory=lambda: {
        i: bytes(32) for i in range(24)  # PCR 0-23，初始值全零
    })
    
    def extend_pcr(self, pcr_index: int, measurement: str) -> str:
        """
        PCR 扩展操作：new_pcr = SHA256(current_pcr || SHA256(measurement))
        
        这个操作是单向累积的：
        1. 无法从最终 PCR 值反推出测量历史
        2. 任何中间阶段的修改都会影响最终结果
        3. 相同的启动序列总是产生相同的 PCR 值（可重复性）
        """
        if pcr_index not in self.pcr_registers:
            raise ValueError(f"PCR index {pcr_index} out of range")
        
        # 计算测量值的哈希
        measurement_hash = hashlib.sha256(measurement.encode()).digest()
        # 扩展：Hash(当前值 || 测量哈希)
        new_pcr = hashlib.sha256(
            self.pcr_registers[pcr_index] + measurement_hash
        ).digest()
        
        self.pcr_registers[pcr_index] = new_pcr
        return new_pcr.hex()

    def generate_quote(self, pcr_indices: List[int], nonce: bytes) -> dict:
        """
        生成 PCR Quote：将当前 PCR 值与随机数一起签名。
        
        nonce（随机挑战值）的作用：防止重放攻击——
        验证方每次提供不同的 nonce，确保 Quote 是新鲜生成的，
        而非攻击者重放的历史 Quote。
        
        实际实现使用 TPM 的 AIK（Attestation Identity Key）私钥签名，
        此处用 HMAC 模拟签名结构。
        """
        pcr_values = {idx: self.pcr_registers[idx].hex() for idx in pcr_indices}
        
        # 构造被签名的数据
        quote_data = {
            'pcr_values': pcr_values,
            'nonce': nonce.hex(),
        }
        
        # 模拟 TPM 签名（真实场景使用 TPM AIK 私钥）
        quote_bytes = json.dumps(quote_data, sort_keys=True).encode()
        signature = hmac.new(
            b'simulated_tpm_key',  # 实际为 TPM 内部不可导出私钥
            quote_bytes,
            hashlib.sha256
        ).hexdigest()
        
        return {
            'quote_data': quote_data,
            'signature': signature
        }

    def verify_platform_state(self, expected_pcr_values: Dict[int, str]) -> dict:
        """
        验证当前 PCR 值是否与预期基线匹配。
        
        返回详细的差异信息，便于识别是哪个启动阶段发生了变化。
        """
        results = {}
        for pcr_idx, expected_hex in expected_pcr_values.items():
            current_hex = self.pcr_registers.get(pcr_idx, bytes(32)).hex()
            match = current_hex == expected_hex
            results[pcr_idx] = {
                'match': match,
                'expected': expected_hex,
                'current': current_hex
            }
        
        all_match = all(r['match'] for r in results.values())
        return {'platform_trusted': all_match, 'pcr_details': results}


# 演示：模拟启动序列测量
tpm = TPMSimulator()

# 模拟 BIOS 固件测量（PCR 0）
uefi_hash = tpm.extend_pcr(0, "UEFI_firmware_v2.1.4_hash")
print(f"PCR[0] after UEFI measurement: {uefi_hash[:16]}...")

# 模拟 Secure Boot 状态测量（PCR 7）  
secure_boot_hash = tpm.extend_pcr(7, "SecureBoot=Enabled,PK=hash_abc123")
print(f"PCR[7] after Secure Boot state: {secure_boot_hash[:16]}...")

# 记录"已知好的"基线
baseline = {
    0: tpm.pcr_registers[0].hex(),
    7: tpm.pcr_registers[7].hex(),
}

# 验证当前状态与基线匹配
verification = tpm.verify_platform_state(baseline)
print(f"Platform trusted: {verification['platform_trusted']}")
```

几个值得深挖的设计取舍。其一，`extend_pcr` 用哈希链而非简单覆盖，代价是失去了"直接读出某一阶段测量值"的能力（注释里第 1 点说的不可反推），换来的是任何一步被改都会污染最终值的强完整性——这是刻意的取舍，安全场景宁可牺牲可读性也要保证不可绕过。其二，`generate_quote` 里用 HMAC 加一个固定密钥字符串来"模拟签名"，这在真实场景中是绝对不能照搬的：真实 Quote 必须用 TPM 内部不可导出的 AIK 私钥做非对称签名，否则任何拿到那个密钥的人都能伪造 Quote，证明的信任基础就塌了——代码注释特意用"实际为 TPM 内部不可导出私钥"标注了这个边界。其三，`verify_platform_state` 返回的是每个 PCR 的逐项 `match/expected/current`，而不是一个笼统的布尔值，这个设计直接对应生产运维需求：当验证失败时，运维人员需要立刻知道是 PCR[0]（固件变了）还是 PCR[7]（Secure Boot 配置变了），才能判断是一次合法的固件升级还是一次可疑改动。

也正因如此，把这套机制搬到生产要提防几个常见坑。最典型的是"合法变更引发的 PCR 漂移"：一次正常的 BIOS 升级、Secure Boot 证书轮换甚至加装一块内存都可能改变 PCR 值，如果基线管理不跟上，密封的磁盘密钥就会拒绝释放、机器无法自动解锁启动。因此 PCR 基线必须随每次授权的固件/配置变更同步更新，并纳入变更管理流程——这一点在 7.7.4 的入场检查里对应"导出 TPM 初始 PCR 值"的动作。另一个坑是 nonce 若被复用或可预测，抗重放就形同虚设，验证方必须保证每次挑战都是一次性的随机值。

## 7.7.3 Secure Boot 信任链

### Secure Boot 工作机制

Secure Boot 解决的核心问题：在操作系统之前加载的代码（引导加载程序）如何被验证为可信？没有 Secure Boot，攻击者可以用恶意引导程序替换 GRUB 等引导加载程序，实现对系统的完全控制，且操作系统级别的安全工具对此无感知。

如果说 7.7.2 的 TPM 回答的是"如何证明系统启动成了什么状态"，那么 Secure Boot 回答的是更前置的问题："如何在启动的每一步只允许受信任的代码被加载"。二者是互补的：TPM 事后测量、Secure Boot 事前拦截。下面这条信任链的关键在于它是"逐级验证"的——上一级用密钥为下一级背书，形成一条从硬件根一直延伸到内核驱动的信任传递链，任何一环无法通过验证，加载就被拒绝：

UEFI Secure Boot 由 UEFI 规范定义（PK / KEK / db / dbx 四类密钥库及其验证流程见规范的 Secure Boot 章节）[4]，建立了一个完整的签名验证链：

```
平台密钥(PK) → 密钥交换密钥(KEK) → 签名数据库(db/dbx)
                                           ↓
                              验证引导加载程序签名
                                           ↓
                              引导加载程序验证内核签名
                                           ↓
                              内核验证驱动签名（DKMS/IMA）
```

这张链路图要从上往下读：越靠上的密钥权限越大、变更越敏感。PK 是整条链的锚点，它不直接验证引导程序，而是控制谁能修改 KEK；KEK 再控制 db/dbx 的更新权限；真正在每次开机时逐个验证引导程序、内核、驱动签名的，是最底层的 db/dbx。这种分层授权的意义在于把"信任的根"和"信任的日常执行"分开——企业换掉 PK 就等于夺回了整条链的控制权，而无需触碰底层每一次的验证逻辑。下面四段分别对应链路图里的四类密钥/数据库：

PK（Platform Key）：最高信任锚，由 OEM 或企业自持。控制 KEK 的更新权限。企业若要使用自定义签名密钥，需要替换默认 PK。

KEK（Key Exchange Key）：控制 db（允许列表）和 dbx（拒绝列表）的更新。Microsoft 等操作系统厂商持有 KEK，用于分发签名更新。

db（签名允许数据库）：包含被信任的证书和哈希值，引导程序签名必须能被 db 中的证书验证。

dbx（签名拒绝数据库）：已撤销的签名列表，即使在 db 中有对应证书，如果 dbx 中有对应条目，仍会被拒绝加载。BootHole 漏洞（2020）修复的关键步骤之一就是更新所有 Windows/Linux 设备的 dbx，吊销包含漏洞的 GRUB 版本的签名。

这里 db 与 dbx 的"允许/拒绝"双数据库设计值得留意：dbx 优先级高于 db，是一个刻意的"撤销总能压过许可"的安全默认。BootHole 事件正是这套机制的实战写照——当一个曾经合法签名的 GRUB 版本被发现有洞时，无法收回已经签发的证书，唯一的补救就是把有洞版本的哈希塞进 dbx 全网拉黑。这也提醒实践者：dbx 更新本身就是一项需要纳入补丁管理的运维工作，漏掉它，Secure Boot 就形同一份过期的白名单。

### Secure Boot 状态检查

有了机制理解，落到运维就需要一个能快速回答"这台机器到底有没有开 Secure Boot、TPM/IMA 处于什么状态"的现场工具。下面的 bash 脚本正是为此设计：它不修改任何配置，只做只读的状态盘点，适合在设备入场检查（7.7.4）或例行审计时批量执行。脚本刻意做了容错分层——优先用 `mokutil` 这个发行版常见工具，若不可用则回退到直接读 EFI 变量，这种"工具优先、原始接口兜底"的写法是为了在最小依赖的环境（如精简的服务器镜像）里也能拿到结果。脚本自身的四段输出结构就是它的脉络：Secure Boot 状态、引导程序签名、IMA 状态、TPM 存在性，每一段对应信任链上的一个可观测点。

```bash
#!/bin/bash
# 检查 Secure Boot 状态并验证关键配置

check_secure_boot() {
    echo "=== Secure Boot 状态检查 ==="

    # 检查 Secure Boot 是否启用
    if command -v mokutil &> /dev/null; then
        SB_STATE=$(mokutil --sb-state 2>/dev/null)
        echo "Secure Boot: ${SB_STATE}"
    elif [ -d /sys/firmware/efi ]; then
        # 通过 EFI 变量直接检查（需要 efivarfs 挂载）
        SB_VAR="/sys/firmware/efi/efivars/SecureBoot-8be4df61-93ca-11d2-aa0d-00e098032b8c"
        if [ -f "$SB_VAR" ]; then
            # EFI 变量前 4 字节是属性，第 5 字节是值
            SB_ENABLED=$(hexdump -e '"%d"' -s 4 -n 1 "$SB_VAR" 2>/dev/null)
            if [ "$SB_ENABLED" = "1" ]; then
                echo "Secure Boot: enabled"
            else
                echo "Secure Boot: DISABLED  <- 安全风险"
            fi
        fi
    else
        echo "无法检测 Secure Boot 状态（非 UEFI 系统或权限不足）"
    fi

    echo ""
    echo "=== 引导加载程序签名验证 ==="
    
    # 检查 GRUB 是否通过 shim 加载（Shim 持有 Microsoft 签名，用于验证发行版 GRUB）
    BOOTX64="/boot/efi/EFI/BOOT/BOOTX64.EFI"
    if [ -f "$BOOTX64" ]; then
        SHIM_SIG=$(file "$BOOTX64" 2>/dev/null | grep -i "PE32+")
        echo "引导程序类型: $(file "$BOOTX64" 2>/dev/null | awk -F': ' '{print $2}')"
    fi
    
    # 检查内核是否通过 IMA（Integrity Measurement Architecture）验证
    echo ""
    echo "=== IMA 状态 ==="
    if [ -f /sys/kernel/security/ima/policy ]; then
        echo "IMA: 已启用"
        echo "IMA 策略条目数: $(wc -l < /sys/kernel/security/ima/policy)"
    else
        echo "IMA: 未启用"
    fi
    
    # 检查 TPM 是否存在
    echo ""
    echo "=== TPM 状态 ==="
    if [ -e /dev/tpm0 ] || [ -e /dev/tpmrm0 ]; then
        TPM_VER=$(cat /sys/class/tpm/tpm0/tpm_version_major 2>/dev/null || echo "未知")
        echo "TPM: 已检测到 (版本: $TPM_VER)"
    else
        echo "TPM: 未检测到"
    fi
}

check_secure_boot
```

脚本里有两处细节体现了对生产环境的考量。一是直接读 EFI 变量那段注释——"前 4 字节是属性，第 5 字节是值"——说明脚本作者清楚 efivarfs 暴露的原始变量带有属性头，不能把整段字节当作布尔值直接判断，这正是绕过 `mokutil` 时最容易出错的地方。二是它把 Secure Boot、IMA、TPM 三者放在一份报告里输出，因为三者常被误当作同一件事：Secure Boot 管的是"加载前拦截"，IMA 管的是"运行时文件度量"，TPM 管的是"测量的可信存储与证明"，任何一项缺失都会在信任链上留下缺口，合在一起看才能判断这台机器的信任根是否完整。

需要提醒的坑有两处。其一，脚本对引导程序只做了 `file` 类型识别（是不是 PE32+），并没有真正校验签名有效性——它回答"这是不是一个引导程序文件"，而非"这个引导程序的签名是否被 db 信任"，真正的签名校验发生在固件层，运维不应把这行输出误读为"签名已验证"。其二，几乎所有检查都依赖 efivarfs 已挂载且进程有足够权限，因此有了脚本末尾对适用边界的明确声明：

适用边界：此脚本需要在具备适当权限（部分检查需要 root）的 Linux 系统上运行，且系统需要挂载 efivarfs（通常在现代发行版中默认启用）。

## 7.7.4 硬件供应商安全评估

### 采购安全控制

前面的 TPM 与 Secure Boot 都是设备到手之后的技术控制，但硬件供应链最靠前、也最省力的控制点其实在采购环节。原因很直接：设备一旦进了机房，你只能验证它现在的状态，无法追溯它在运输途中经历了什么；而在采购阶段选对渠道，就能从概率上大幅压低"拿到的就是被动过手脚的设备"这种风险。

硬件供应链风险的首要控制点是采购渠道——从授权渠道采购可以显著降低供应链拦截风险。NIST SP 800-161r1 把这类要求归入采购与合同控制，建议在合同中明确来源可溯、防篡改包装与交付验证条款[5]：

渠道控制：
- 直接从制造商或授权经销商采购，避免灰市渠道
- 建立供应商授权经销商白名单，新渠道采购需要审批
- 对高价值、高敏感设备（服务器、网络核心设备）要求制造商直接发货
- 保留完整的采购记录和设备序列号台账

物理完整性验证：
- 接收时检查包装完整性（防拆标签、封条、包装箱物理状况）
- 比对制造商提供的硬件指纹或设备证书（部分企业级设备支持）
- 对高敏感设备，考虑拍照记录拆箱过程
- 建立异常报告流程（包装损坏、序列号不符等情况）

这两组控制是配套的：渠道控制降低"设备被拦截修改"的发生概率，物理完整性验证则在设备到货时提供一次事后检测的机会。二者都属于"信任但验证"的思路——即便走的是授权渠道，收货时依然要核验封条与序列号，因为渠道信任无法覆盖运输最后一公里的物理风险。

### 供应商安全评估框架

渠道和收货控制解决的是"这一批设备有没有被动手脚"，而供应商评估要解决的是更长期的问题："这家供应商在未来数年里，有没有能力和意愿持续保障其硬件与固件的安全"。这是一个尽职调查性质的判断，因此下表把它拆成六个可提问、可取证的维度。表格的用法不是打分求和，而是看第三列"高风险信号"——每一条都是一个可以直接触发"不予采用"或"降级使用"决策的红线，比泛泛地打分评估更能落地：

对关键硬件供应商（服务器、网络设备、安全设备）进行安全评估时，需覆盖以下维度：

| 评估维度 | 关键问题 | 高风险信号 |
|---------|---------|---------|
| 供应链透明度 | 核心芯片与组件的来源追溯能力？ | 无法提供 BOM（Bill of Materials）的详细来源 |
| 固件安全开发 | SBOM 是否覆盖固件组件？固件签名机制？ | 固件无签名或使用弱签名算法 |
| 安全更新机制 | 固件漏洞响应时间 SLA？历史漏洞修复记录？ | 关键漏洞披露后超过 90 天才发布补丁 |
| Secure Boot 支持 | 是否支持 Secure Boot？是否支持自定义密钥（企业级）？ | 不支持 Secure Boot 或禁止自定义 PK |
| 远程管理安全 | BMC/iDRAC/iLO 的默认凭证策略？网络隔离支持？ | 默认凭证无法修改，或 BMC 无法与生产网络隔离 |
| 硬件证明 | 是否提供硬件证书或可验证的设备身份（如 Device ID）？ | 无任何硬件完整性验证手段 |

这张表和前面的技术小节其实是呼应的：Secure Boot 支持一行对应 7.7.3，硬件证明一行对应 7.7.2 的远程证明能力，固件安全开发与安全更新机制则决定了设备上线后你能否持续维护 7.7.5 的固件基线。换句话说，供应商评估验证的是"这家供应商的产品是否具备本节其余控制手段所依赖的前提条件"，而非一份孤立的采购清单——如果供应商连自定义 PK 都不支持，那么企业自持信任锚的整套 Secure Boot 方案就无从落地。

### 部署入场检查

供应商评估和渠道控制筛掉了不合格的来源，但每一台具体到货的设备仍需要一道标准化的入场检查，把"合规采购"落实为"可信上线"。下面这份清单按四个环节组织，从最外层的包装一路检查到最内层的完整性基线，顺序本身就是从物理到软件的逐层深入：

设备到达后、上线前的安全检查清单：

```
[ ] 包装完整性验证
    - 防拆封条完整
    - 外包装无明显损坏迹象
    - 序列号与采购订单匹配

[ ] 固件版本检查
    - 当前固件版本与制造商最新发布版本比对
    - 必要时更新至最新安全版本（在隔离环境中进行）
    - 记录固件版本作为基线

[ ] 默认配置安全加固
    - 修改所有默认密码（BMC、管理接口等）
    - 禁用不需要的远程管理协议
    - 配置 BMC 网络隔离（独立管理网络）
    - 启用 Secure Boot

[ ] 完整性基线建立
    - 记录硬件配置（见 7.7.5 的自动化工具）
    - 导出 TPM 初始 PCR 值（若支持）
    - 记录固件哈希值
```

清单里有两个容易被忽视但关键的细节。一是固件更新明确要求"在隔离环境中进行"——因为设备尚未加固、默认凭证仍在，若在生产网络里刷固件，等于让一台未经审查的设备直接暴露在网络中；先隔离更新再加固上线，是入场流程的正确顺序。二是最后一步"完整性基线建立"是承前启后的枢纽：它把这台设备当下"已知可信"的状态固化下来（硬件配置指纹、TPM PCR 值、固件哈希），而这个基线正是 7.7.5 那套自动化检测工具后续用来比对的参照物。没有这一步，后面所有的偏差检测都失去了参照系。

## 7.7.5 硬件完整性基线检测

### 自动化完整性监控

入场检查里"完整性基线建立"这一步如果靠人工记录，既不可扩展也难以保证一致性。下面这个 Python 工具把它自动化：核心思路极其朴素——在已知可信的时刻给硬件配置拍一张"指纹快照"，此后定期重拍并与快照比对，任何偏差都是需要人工确认的信号。之所以采用"基线—比对"而非"实时监控"，是因为硬件配置本身变化频率极低，一台服务器的主板、CPU、PCIe 拓扑在正常运行期间几乎不动，用低频快照比对既足够灵敏又几乎不消耗运行时资源。

以下 Python 工具实现硬件配置的基线记录与偏差检测。核心思路：在已知可信状态下记录硬件指纹，后续定期重新采集并比对，偏差即为告警信号：

```python
import hashlib
import json
import subprocess
import platform
from datetime import datetime
from pathlib import Path

class HardwareIntegrityChecker:
    """
    硬件完整性基线检测工具。
    
    工作原理：
    1. 基线阶段（首次运行或已知可信状态）：采集硬件配置信息，
       计算配置指纹，存储为基线文件
    2. 验证阶段（定期运行）：重新采集配置，计算指纹，与基线比对
    3. 偏差报告：列出发生变化的配置项，供安全团队人工确认
    
    注意：此工具检测的是可通过软件读取的配置信息，
    无法检测纯物理层面的硬件植入。
    """
    
    def __init__(self, baseline_path: str = "/etc/hardware_baseline.json"):
        self.baseline_path = Path(baseline_path)
    
    def _run_command(self, cmd: list) -> str:
        """执行系统命令并返回输出，捕获错误避免工具因单个命令失败而中断"""
        try:
            result = subprocess.run(
                cmd, capture_output=True, text=True, timeout=30
            )
            return result.stdout.strip()
        except (subprocess.TimeoutExpired, FileNotFoundError, PermissionError) as e:
            return f"ERROR: {e}"

    def collect_hardware_info(self) -> dict:
        """
        采集硬件配置信息。
        
        覆盖的检测维度及其安全意义：
        - DMI/系统信息：检测主板、BIOS 的变更（固件更新或替换）
        - CPU 信息：检测 CPU 型号变化（物理替换或虚拟化层欺骗）
        - PCI 设备：检测新增/删除的 PCIe 设备（硬件植入常通过 PCIe 卡实现）
        - 网卡 MAC：检测网卡更换（硬件 MAC 在网卡更换后改变）
        - UEFI 变量：检测 Secure Boot 状态和启动配置的变更
        """
        info = {
            'timestamp': datetime.now().isoformat(),
            'platform': platform.node(),
            'components': {}
        }
        
        # DMI 信息（系统/主板/BIOS 信息）
        if platform.system() == 'Linux':
            for dmi_type, key in [('system-product-name', 'system_product'),
                                   ('bios-version', 'bios_version'),
                                   ('bios-release-date', 'bios_date'),
                                   ('baseboard-product-name', 'board_name')]:
                value = self._run_command(['dmidecode', '-s', dmi_type])
                info['components'][key] = value
        
        # CPU 信息
        cpu_info = self._run_command(['lscpu'])
        info['components']['cpu_info'] = cpu_info
        
        # PCI 设备（检测新增或移除的 PCIe 设备）
        pci_devices = self._run_command(['lspci', '-n'])  # -n 输出设备 ID，避免驱动名称变化导致误报
        info['components']['pci_devices'] = pci_devices
        
        # 网络接口 MAC（网卡层面的变更检测）
        # 使用固定格式避免 interface 名称重命名导致误报
        mac_info = self._run_command(['ip', 'link', 'show'])
        info['components']['network_interfaces'] = mac_info
        
        # UEFI/Secure Boot 状态
        if Path('/sys/firmware/efi').exists():
            sb_state = self._run_command(['mokutil', '--sb-state'])
            info['components']['secure_boot_state'] = sb_state
            
            # 启动顺序（检测启动项被篡改）
            boot_order = self._run_command(['efibootmgr', '-v'])
            info['components']['boot_order'] = boot_order
        
        return info
    
    def generate_fingerprint(self, hardware_info: dict) -> str:
        """
        计算硬件配置的 SHA-256 指纹。
        排除 timestamp 以确保相同配置在不同时间产生相同指纹。
        """
        components = hardware_info.get('components', {})
        fingerprint_data = json.dumps(components, sort_keys=True)
        return hashlib.sha256(fingerprint_data.encode()).hexdigest()
    
    def establish_baseline(self) -> dict:
        """在已知可信状态下建立基线——建议在新设备首次部署时执行"""
        print(f"正在采集硬件配置基线...")
        hardware_info = self.collect_hardware_info()
        fingerprint = self.generate_fingerprint(hardware_info)
        
        baseline = {
            **hardware_info,
            'baseline_fingerprint': fingerprint,
            'baseline_established_at': hardware_info['timestamp']
        }
        
        self.baseline_path.write_text(json.dumps(baseline, indent=2, ensure_ascii=False))
        print(f"基线已保存至: {self.baseline_path}")
        print(f"基线指纹: {fingerprint}")
        return baseline
    
    def verify_integrity(self) -> dict:
        """与基线比对，返回偏差报告"""
        if not self.baseline_path.exists():
            return {'error': '基线文件不存在，请先运行 establish_baseline()'}
        
        baseline = json.loads(self.baseline_path.read_text())
        current_info = self.collect_hardware_info()
        current_fingerprint = self.generate_fingerprint(current_info)
        baseline_fingerprint = baseline.get('baseline_fingerprint', '')
        
        integrity_ok = current_fingerprint == baseline_fingerprint
        
        # 逐项比对，识别具体差异
        changes = []
        for key in baseline.get('components', {}):
            baseline_val = baseline['components'].get(key, '')
            current_val = current_info['components'].get(key, '')
            if baseline_val != current_val:
                changes.append({
                    'component': key,
                    'baseline': baseline_val[:100] + '...' if len(baseline_val) > 100 else baseline_val,
                    'current': current_val[:100] + '...' if len(current_val) > 100 else current_val
                })
        
        return {
            'integrity_ok': integrity_ok,
            'verified_at': current_info['timestamp'],
            'baseline_established_at': baseline.get('baseline_established_at'),
            'changes_detected': len(changes),
            'changes': changes
        }


# 使用示例
if __name__ == "__main__":
    checker = HardwareIntegrityChecker()
    
    # 首次运行：建立基线（在已知可信状态下执行）
    # checker.establish_baseline()
    
    # 后续运行：验证完整性
    result = checker.verify_integrity()
    if result.get('integrity_ok'):
        print("硬件完整性验证通过")
    else:
        print(f"检测到 {result.get('changes_detected')} 处变化，需要人工确认：")
        for change in result.get('changes', []):
            print(f"  - {change['component']}: 基线值与当前值不符")
```

这个工具最见功力的地方不是采集，而是它对"误报"的防范——因为一个整天喊狼来了的完整性工具很快会被运维忽略。几处设计都指向降噪：`generate_fingerprint` 刻意把 `timestamp` 排除在指纹之外，否则每次采集时间不同就会导致指纹永远不一致；`lspci -n` 用数字设备 ID 而非人类可读名称，是因为驱动名称会随内核版本变化，用 ID 才能在升级后依然稳定；`ip link show` 的注释也点明了同样的意图——避免接口重命名导致误报。这三处放在一起，传达的是一个生产工具必须遵循的原则：只对"真正的硬件变更"报警，而不对"表述方式的变化"报警。

再看两个稳健性设计。`_run_command` 用 try/except 把超时、命令不存在、权限不足三类异常统一转成 `"ERROR: ..."` 字符串返回，而不是抛出异常中断整个采集——这样即使某台机器缺了 `dmidecode`，其余维度的检测照常进行，注释里"避免工具因单个命令失败而中断"说的正是这个。`verify_integrity` 除了返回一个总体的 `integrity_ok` 布尔值，还逐项列出具体变了哪个 component（并对超长值截断到 100 字符），这与 7.7.2 的 `verify_platform_state` 是同一种运维思维：告警必须可定位，光说"不一致"没有意义，要说清是 PCIe 设备变了还是启动顺序变了，人工才能判断这是一次合法升级还是一次可疑改动。

必须清醒认识这个工具的能力边界，它的注释和适用边界都反复强调了同一件事：它读的是软件能读到的配置，因此能发现"多了一块 PCIe 卡""BIOS 版本变了""Secure Boot 被关了"这类变更，却完全看不见芯片级植入、主板级改造这类不改变软件可读配置的物理攻击。也就是说，它是 7.7.1 五阶段攻击面里"运行时可观测"那一层的哨兵，而非万能探测器；对制造与运输阶段的物理攻击，仍要靠 7.7.4 的采购治理与物理验证来兜底。

适用边界：此工具适用于 Linux 系统，需要安装 `dmidecode`、`lspci`、`mokutil`（可选）等工具，部分命令需要 root 权限。工具检测的是软件可读的配置信息，无法检测纯物理层面的硬件改动（如芯片级植入）。

验证方法：在测试环境中人为修改配置（如修改网络接口）后运行验证，确认工具能正确检测差异；定期在生产设备上运行并记录日志，建立变更告警流程。

## 7.7.6 实施检查清单

前面五个小节从威胁态势讲到具体工具，容易让人产生"要全部做到才算及格"的畏难感。这份分级清单的意义正在于把纷繁的控制拆成可以分批落地的四级——按"投入产出比"和"实施难度"排序，从当天就能做的默认密码修改，一路推进到需要半年以上建设的远程证明与 HSM。读的时候不必纠结于绝对的时间数字，关键是理解这个递进逻辑：先用低成本手段堵住最常被利用的入口（默认凭证、灰市渠道），再逐步叠加需要工程投入的深度控制。

### 第一级：基础控制（立即可实施）

- [ ] 建立硬件采购渠道白名单，要求通过授权渠道采购
- [ ] 制定设备接收检查标准（包装完整性、序列号核对）
- [ ] 所有服务器、网络设备接收后立即修改默认密码
- [ ] 配置 BMC/IPMI 使用独立管理网络，与生产网络隔离
- [ ] 建立硬件台账，记录设备型号、序列号、固件版本

### 第二级：完整性管理（1-3 个月）

- [ ] 对所有生产服务器启用 Secure Boot
- [ ] 建立固件版本基线和更新管理流程
- [ ] 部署 7.7.5 的硬件完整性检测工具，建立初始基线
- [ ] 建立固件漏洞监控（订阅 CISA KEV 中硬件相关漏洞告警）
- [ ] 对关键设备建立 TPM PCR 基线（若设备支持 TPM 2.0）

### 第三级：持续监控（3-6 个月）

- [ ] 定期（季度）对生产服务器执行完整性验证
- [ ] 建立固件更新的测试与部署流程（测试环境先验证）
- [ ] 对关键硬件供应商完成安全评估（参考 7.7.4 评估框架）
- [ ] 配置 BMC 审计日志集中收集与告警

### 第四级：高级能力（6-12 个月）

- [ ] 实施基于 TPM 的远程证明（云环境中的设备身份验证）
- [ ] 部署硬件安全模块（HSM）用于关键密钥管理
- [ ] 建立供应商安全评估年度复查机制
- [ ] 考虑加入行业硬件供应链安全信息共享圈（如 UEFI 论坛安全工作组）

这四级之间存在明确的依赖关系，而非简单的时间先后：第二级的"建立初始基线"是第三级"定期完整性验证"的前提，没有基线就无从比对；第一级的 BMC 网络隔离是第三级"BMC 审计日志集中收集"的基础；而第四级的远程证明则建立在第二级已经把 TPM PCR 基线做扎实之上。因此推进时不宜跳级——越级实施高阶控制，往往会因为缺少下层的基线与隔离而流于形式。

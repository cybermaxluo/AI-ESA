# 5.7　DevSecOps 实践

本节建立从 CI/CD 流水线安全集成到漏洞全生命周期管理的完整 DevSecOps 工程体系，覆盖基础设施即代码扫描、容器镜像供应链安全、安全左移工程实践与自动化质量门禁设计。安全控制前置到设计与开发阶段，是降低修复成本的核心机制——越晚发现，修复越贵（业界流传的"生产环境修复成本是编码阶段 100 倍"追不到可核实的原始出处，不要把它写进立项材料——真正稳定的规律只是"修复成本随发现阶段后移显著上升"，具体倍数须用本组织的缺陷跟踪数据自行测算）。

> 导读：5.7.1 比较 CI/CD 平台安全特性，设计七层安全门禁策略；5.7.2 对比 IaC 扫描工具（Checkov/tfsec/Terrascan），含综合扫描脚本；5.7.3 讲解 CloudFormation 安全扫描（cfn-nag/cfn-guard）与安全模板；5.7.4 对比镜像签名方案（Cosign/Notation），演示 Kubernetes 准入控制签名验证；5.7.5 介绍 IDE 插件、Pre-commit Hook 与开发者分级培训体系；5.7.6 设计 Quality Gate 动态阻断策略；5.7.7 对比 SAST/DAST/SCA 工具，展示完整 GitLab CI 流水线；5.7.8 讲解漏洞生命周期管理与动态 SLA 计算。DevSecOps 的产出——镜像扫描告警、IaC 违规——与 5.6 工具链和 5.8 安全运营直接衔接。

## 5.7.1 CI/CD 安全集成

### CI/CD 平台安全特性对比

DevSecOps 的一切自动化控制都要挂载在某个 CI/CD 平台上，平台的原生能力决定了安全集成的成本与上限。有的平台把凭证管理、RBAC、审计日志、容器隔离做进了内核，安全团队只需配置策略；有的平台把这些能力交给插件生态，灵活但需要自己组装并承担维护成本。下表从这几个维度横向对照四个主流平台，帮助在选型阶段就把"安全债"算进去：

| 平台 | Jenkins | GitLab CI | GitHub Actions | CircleCI |
|------|---------|-----------|----------------|---------|
| 部署模式 | Self-hosted/Cloud | Self-hosted/SaaS | Cloud | Cloud |
| 凭证管理 | Credentials Plugin | CI/CD Variables | Secrets | Contexts |
| RBAC | 插件支持 | 内置 | 内置 | 内置 |
| 审计日志 | 插件支持 | 内置 | 内置 | 有限 |
| 签名验证 | 插件 | 内置 | 有限 | 有限 |
| 安全扫描集成 | 丰富插件 | 内置+插件 | Marketplace | Orbs |
| 隔离性 | 配置依赖 | 容器隔离 | 容器隔离 | 容器隔离 |
| 最佳场景 | 企业自建（高定制需求） | GitLab 生态 | GitHub 生态 | 快速配置 |

这张表的主线是：能力是"内置"还是"插件/配置依赖"，直接决定谁来承担安全的运维责任。Jenkins 几乎所有安全能力都靠插件，换来的是极高的可控性与定制空间，代价是隔离性"配置依赖"——默认不隔离，需要自行加固；GitLab CI 和 GitHub Actions 把多数能力做成内置或原生集成，减少了组装成本，但也带来对各自生态的绑定。据此，选型关键点是：企业自建环境优先 Jenkins（可控性高、定制能力强）；GitLab/GitHub 生态优先原生 CI（减少工具切换成本）；对容器隔离有强需求时，避免单纯依赖 Jenkins 配置隔离（需额外加固）。

### 安全门禁的七层防护策略

选定平台之后，真正的工程决策是"在流水线的哪些位置插入哪些检查"。这里采用的组织原则是纵深防御：不指望任何单一工具拦住所有问题，而是按软件从提交到部署的时间顺序设置七道检查点，每道解决一类不同的风险、由不同的工具负责，形成层层过滤。之所以要分层而非把所有扫描堆在一处，是因为不同扫描的执行成本、误报特征、失败后果差异巨大，越靠前的检查越应该"快而狠"，越靠后的检查越可以"慢而全"。下面逐层说明每一层拦什么、为什么放在这个位置、以及它的适用边界：

第一层：代码提交验证。GPG 签名验证确保代码来源可信，防止供应链投毒。在代码进入代码库前触发，阻断未签名提交。

第二层：秘密扫描。TruffleHog 或 GitGuardian 扫描全历史提交与当前代码，检测硬编码 API 密钥、数据库凭证、私钥。发现泄露立即阻断。适用边界：仅扫描代码仓库，不覆盖运行时配置文件。

第三层：SAST（静态应用安全测试）。SonarQube 或 CodeQL 检测 SQL 注入、XSS、不安全反序列化等代码漏洞。设置 Quality Gate 阈值（Critical 漏洞=0）。关键约束：SAST 误报率可能达初次扫描结果的 80%，需建立基线与白名单机制。

第四层：SCA（软件成分分析）。MurphySec/Snyk 检测依赖库 CVE 漏洞。仅 Critical 级别自动阻断，High 级别生成修复工单但允许通过，避免阻塞业务交付。

第五层：容器镜像扫描。Trivy 检测基础镜像与应用层漏洞，Cosign 验证镜像签名。阻断包含高危漏洞的镜像推送到生产 Registry。

第六层：IaC 扫描。Checkov 或 tfsec 检测 Terraform/CloudFormation 配置风险（S3 公开读写、安全组过度开放）。适用边界：仅检测基础设施配置，不覆盖应用层配置文件。

第七层：DAST（动态应用安全测试）。Staging 环境使用 OWASP ZAP 执行被动扫描与主动攻击测试。关键约束：DAST 扫描时间较长（30 分钟至数小时），不适合每次 PR 触发，建议仅主分支合并后执行。

七层的排布顺序本身就是一种权衡：秘密扫描、SAST 这类快、后果确定的检查放在最前，让开发者在提交后几秒内就得到反馈；DAST 这类慢、误报多的检查压到最后且不逢 PR 必跑。这样既保证了高置信度问题被尽早拦截，又不让重量级扫描拖垮每一次提交的节奏。

### 门禁阻断策略

七层检查解决了"查什么"，但查出问题后是否一律拦停，是另一个必须显式设计的决策——门禁的核心在于权衡安全风险与交付效率。全拦会拖垮交付、逼出绕过行为，全放又形同虚设。这里的思路是按"修复成本"与"风险等级"把处置分成三档：

- 强制阻断：秘密泄露、Critical 级 SAST 漏洞、Critical 级容器漏洞、IaC 违反合规要求（如数据库公网暴露）。修复成本低、风险高，零容忍。
- 警告允许通过：High 级 SAST 漏洞（数量 ≤ 阈值）、Medium 级依赖漏洞。生成工单跟踪，不阻断紧急发布。
- 仅记录不阻断：Low 级代码质量问题、Medium 级依赖漏洞。记录到技术债台账，定期清理。

这三档的分界线不是安全严格程度，而是"拦停的收益是否大于代价"：秘密泄露改一行就能修、风险却极高，值得零容忍；High 漏洞往往牵涉遗留代码、短期修不完，硬拦只会逼出例外申请。

常见误区：一刀切阻断所有 High 漏洞 → 遗留系统无法通过门禁，频繁例外申请降低门禁权威性；未建立基线 → 首次启用时数千条历史告警淹没新增问题。

### Jenkins 安全门禁实现

理论上的七层与三档策略，落到 Jenkins 上就是一份 Pipeline。Jenkins 的 Groovy 声明式语法把"每个 stage 就是一道门禁"这件事表达得最直白——每个 `stage` 对应七层中的一层，`error`/`abortPipeline` 对应"强制阻断"，不抛错则对应"警告通过"。下面这份配置只保留了核心四道门禁作为骨架，关键在于每个 stage 用什么方式决定"过还是不过"：

```groovy
// CI/CD 安全门禁 - 核心阶段配置
pipeline {
  agent any

  stages {
    // 决策点 1：Secret 扫描前置，最早发现凭证泄露
    stage('Secret Scanning') {
      steps {
        // trufflehog --json 输出为 JSONL（每行一个结果）而非 JSON 数组，
        // 不适合直接 readJSON；改用 --fail：发现有效凭证即以非零退出码返回，
        // 由 sh 步骤失败驱动流水线阻断。
        sh 'trufflehog filesystem . --fail'
      }
    }

    // 决策点 2：SAST Quality Gate 阻断 Critical 漏洞
    stage('SAST') {
      steps {
        withSonarQubeEnv('SonarQube') {
          sh 'mvn sonar:sonar -Dsonar.qualitygate.wait=true'
        }
        timeout(time: 10, unit: 'MINUTES') {
          waitForQualityGate abortPipeline: true  // Quality Gate 失败则阻断
        }
      }
    }

    // 决策点 3：SCA 扫描允许 High 漏洞但记录（不阻断）
    stage('SCA') {
      steps {
        sh 'snyk test --severity-threshold=critical --json > snyk-report.json'
        script {
          // High 漏洞生成 Jira 工单但不阻断业务交付
          sh 'python3 scripts/create-vuln-tickets.py snyk-report.json'
        }
      }
    }

    // 决策点 4：容器签名验证供应链安全
    stage('Container Build & Sign') {
      steps {
        sh 'docker build -t ${IMAGE_TAG} .'
        sh 'trivy image --exit-code 1 --severity CRITICAL ${IMAGE_TAG}'  // Critical 漏洞阻断
        sh 'cosign sign --key cosign.key ${IMAGE_TAG}'                   // Sigstore Cosign 签名
      }
    }
  }

  post {
    always {
      // 归档扫描报告，保留 30 天用于合规审计
      archiveArtifacts artifacts: '**/*-report.json', allowEmptyArchive: true
    }
  }
}
```

这四个 stage 对应三档策略：决策点 1（Secret）里的 `trufflehog --fail` 和决策点 4 里的 `trivy --exit-code 1` 都是"强制阻断"——发现即以非零退出码让 `sh` 步骤失败、Pipeline 直接中止；决策点 3（SCA）刻意不抛错，而是调脚本生成工单，对应"警告允许通过"。这种"同一份流水线里，不同 stage 用不同失败语义"的写法，正是把上文三档策略翻译成可执行代码的方式。

其中 `waitForQualityGate abortPipeline: true` 的设计是 SonarQube 安全门禁的核心：Quality Gate 检查在服务端异步执行，Pipeline 等待结果，Quality Gate 不通过则 Pipeline 直接 fail——这比在流水线里解析扫描报告文件更可靠，因为报告解析的判定逻辑分散在各处、容易写错或被绕过，而 SonarQube 服务端统一保证了规则执行的完整性。这也解释了为什么外层要套一个 `timeout(10, MINUTES)`：异步等待若因服务端故障挂起，超时能兜底避免构建资源被无限占用。

关键配置注意事项：所有敏感信息（Docker Registry 密码、SonarQube Token、Cosign 私钥）必须从 Vault 或 AWS Secrets Manager 动态获取，禁止硬编码在 Jenkinsfile 中——否则第一层 Secret 扫描反而会扫到门禁配置自己的凭证，形成讽刺的自打脸；设置全局超时（1 小时）防止异常构建占用资源；所有扫描报告（JSON 格式）通过 `post { always }` 存档 30 天，`always` 保证即便前面某个 stage 阻断失败，报告仍会归档，用于合规审计与趋势分析。

### GitHub Actions 安全流水线

同样一套门禁逻辑，换到 GitHub Actions 上会呈现出不同的工程重心。相比 Jenkins 靠脚本和插件手工拼装，GitHub Actions 的价值在于原生集成：SARIF 报告能直接进 Security 标签、OIDC Token 能实现 Keyless 签名、job 之间用 `needs` 声明依赖。因此下面这份流水线除了复现七层门禁，还额外演示了两个 Jenkins 版没有的要点——权限最小化与阶段依赖编排，分别落在 `permissions` 和 `needs` 上：

```yaml
# .github/workflows/security-pipeline.yml
name: Security CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

# 关键：权限最小化，仅授予必需权限（默认 write 需显式降级）
permissions:
  contents: read          # 读取代码
  security-events: write  # 上传 SARIF 报告到 Security 标签
  pull-requests: write    # PR 评论

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  secret-scan:
    name: Secret Scanning
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # 全历史扫描：检测历史提交中的泄露

      - name: TruffleHog Secret Scan
        uses: trufflesecurity/trufflehog@v3.63.0  # 固定版本，避免 @main 移动标签导致构建不可复现
        with:
          path: ./
          base: ${{ github.event.repository.default_branch }}
          head: HEAD

  sast-scan:
    name: SAST Scanning
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Initialize CodeQL
        uses: github/codeql-action/init@v3
        with:
          languages: java, javascript

      - name: Build
        run: mvn clean package -DskipTests

      - name: Perform CodeQL Analysis
        uses: github/codeql-action/analyze@v3

      - name: SonarCloud Scan
        uses: SonarSource/sonarcloud-github-action@v2.3.0  # 固定版本，避免 @master 移动标签
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

  container-scan:
    name: Container Image Scanning
    runs-on: ubuntu-latest
    needs: [sast-scan]  # 依赖 SAST 通过后才构建镜像
    permissions:
      contents: read
      packages: write
      security-events: write
      id-token: write     # OIDC Keyless 签名必需

    steps:
      - uses: actions/checkout@v4

      - name: Build Image
        run: docker build -t ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }} .

      - name: Scan with Trivy
        uses: aquasecurity/trivy-action@0.24.0  # 固定版本，避免 @master 移动标签
        with:
          image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
          format: 'sarif'
          output: 'trivy-results.sarif'
          severity: 'CRITICAL,HIGH'
          exit-code: '1'   # 发现高危漏洞则失败，阻止推送

      - name: Upload Trivy results to GitHub Security
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: 'trivy-results.sarif'

      - name: Install Cosign
        uses: sigstore/cosign-installer@v3

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Push Image (only after scan passed)
        run: docker push ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}

      # Keyless 签名：无需管理私钥，使用 GitHub OIDC Token
      - name: Sign Image with Cosign (Keyless)
        run: cosign sign --yes ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}

  security-gate:
    name: Security Quality Gate
    runs-on: ubuntu-latest
    needs: [secret-scan, sast-scan, container-scan]
    steps:
      - name: All security checks passed
        run: echo "All security scans passed - ready for deployment"

      - name: Post PR Comment
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: 'Security scans passed. Safe to merge.'
            })
```

这份配置有三条脉络。其一是顶部的 `permissions` 块：GitHub Actions 默认给的 token 权限偏宽，这里显式降级为 `contents: read`，只在需要写的地方（如上传 SARIF 的 `security-events: write`、Keyless 签名的 `id-token: write`）逐项放开——这是把最小权限原则落到 CI token 上的具体做法。其二是 `needs` 声明的依赖编排：`container-scan` 依赖 `sast-scan`，意味着代码层扫描没过就根本不构建镜像，避免在有已知代码漏洞的基础上浪费构建和推送成本；末尾 `security-gate` 依赖前三者全部成功，充当"总闸"。其三是构建—扫描—推送—签名的严格顺序：Trivy 的 `exit-code: 1` 放在 `docker push` 之前，确保有高危漏洞的镜像永远进不了 Registry，签名则放在推送之后，因为签名针对的是已入库的镜像摘要。

值得单独点出的是 `fetch-depth: 0`，这是 Secret 扫描的关键参数——默认 `checkout@v4` 只获取最新 commit（shallow clone），TruffleHog 无法扫描历史提交。全历史扫描（`fetch-depth: 0`）确保不遗漏已被提交过的密钥（即使后续 commit 删除了该行，Git 历史中仍然存在）。这是新手最常踩的坑：Hook 装了、Action 配了，却因为浅克隆而对历史泄露视而不见，产生"扫过了"的虚假安全感。

## 5.7.2 IaC 安全扫描

### Terraform 扫描工具对比

基础设施即代码把"机房配置"变成了可被扫描的文本，于是 IaC 扫描成为在资源创建之前拦住错误配置（公开 S3、放开的安全组）的最后关口。市面上主流的几款工具能力交叠但各有侧重：有的胜在规则数量与多格式覆盖，有的胜在速度与低误报，有的靠策略语言（Rego）适配混合环境。下表沿这些维度对照，目的是让选型不凭直觉而凭"IaC 采用哪种格式、更怕漏报还是误报"：

下表的"规则数"为量级参考、"误报表现"为作者在自有 Terraform 代码库上的 POC 观感（示例口径，非行业基准）——同一工具在不同代码风格下的误报差异很大，务必用自己的仓库跑一遍再下结论。另需注意 tfsec 已由 Aqua 归并入 Trivy 的 IaC 扫描能力、进入维护状态[1]，新项目建议直接评估 Trivy。

| 工具 | Checkov | tfsec | Terrascan | Snyk IaC |
|------|---------|-------|-----------|---------|
| 开发者 | Bridgecrew/Palo Alto | Aqua Security（已并入 Trivy） | Tenable | Snyk |
| 开源 | 是 | 是 | 是 | 部分 |
| 规则数（量级） | 千条 | 数百条 | 数百条 | 数百条 |
| IaC 支持 | TF/CFN/K8s/Helm | Terraform | TF/CFN/K8s | TF/K8s/ARM |
| 自定义规则 | Python | JSON/Rego | Rego | 有限 |
| 误报表现（作者 POC 观感） | 中 | 低 | 中 | 低 |
| 最佳场景 | 全面检查、多 IaC 格式 | Terraform 专精 | 混合 IaC 环境 | CI/CD 集成 |

这张表体现两组张力。第一组是"规则数 vs 误报率"：Checkov 规则最多（覆盖最全），代价是误报率中等；tfsec 规则少些但误报率低、速度快。这不是谁更好，而是漏报和误报之间的取舍——门禁前期怕误报干扰开发者，成熟后更怕漏报。第二组是"IaC 支持范围 vs 自定义规则语言"：只写 Terraform 就用专精的 tfsec；跨 TF/CFN/K8s/Helm 多种格式则 Checkov 更省心，而它用 Python 写自定义规则，对多数团队比 Rego 更容易上手。据此，选型决策：开源优先选 Checkov（规则最丰富）或 tfsec（速度最快、误报率低）；纯 Terraform 环境选 tfsec；同时使用多种 IaC 格式选 Checkov 或 Terrascan；商业支持需求选 Snyk IaC。

常见误区：仅依赖单一工具导致规则覆盖不全——建议组合使用（如 Checkov+tfsec），通过并集覆盖更多风险点。

### Checkov 实战

选定 Checkov 后，真正影响推广成败的往往是"怎么把结果的严重程度和阻断力度调到团队能接受"，能不能扫倒在其次。Checkov 功能最全面，支持自定义 Python 规则，下面三条命令刻意展示了从粗到细、从硬到软的三种用法，对应推广的不同阶段：

```bash
# 扫描 Terraform 代码
checkov -d /path/to/terraform \
  --framework terraform \
  --compact --quiet \
  --output cli \
  --output json \
  --output-file checkov-report.json

# 指定特定严重性（减少噪音）
checkov -d . --compact --quiet --check CKV_AWS_20,CKV_AWS_21

# 软失败模式（仅警告，不阻断构建）—— 初期推广阶段使用
checkov -d . --soft-fail
```

三条命令是一条推广路径的三个阶段：第一条是"全量扫描 + 双格式输出"，CLI 给人看、JSON 给机器读；第二条用 `--check` 只跑指定规则，是当全量结果噪音太大时的收敛手段，先聚焦几条最关键的检查；第三条 `--soft-fail` 是初期推广的关键开关——它让扫描只报告不返回失败码，团队先建立"看得到问题"的习惯，等基线清理干净、误报调优完毕，再撤掉这个开关切换到强制阻断。跳过 `--soft-fail` 直接硬上，几乎必然在首次扫描时被历史告警淹没并引发反弹。

将它接入流水线时，同样先以软失败起步：

```yaml
# .gitlab-ci.yml
checkov-scan:
  stage: security
  image: bridgecrew/checkov:latest
  script:
    - |
      checkov -d terraform/ \
        --framework terraform \
        --output cli \
        --output junitxml \
        --output-file checkov-report.xml \
        --soft-fail   # 初期仅警告，成熟后移除此参数改为强制阻断
  artifacts:
    reports:
      junit: checkov-report.xml
    when: always
  only:
    - merge_requests
```

这段 CI 有两个值得学的细节：一是输出选了 `junitxml` 而非 JSON，因为 GitLab 能把 JUnit 报告直接渲染进 MR 界面，开发者不必翻日志就能看到违规项；二是 `--soft-fail` 注释里明确写了"成熟后移除"，把"当前处于推广哪个阶段"这个团队约定固化在代码里，避免它永远停留在软失败而失去门禁意义。`only: merge_requests` 则限定只在 MR 时扫，不拖累每一次 push。

当内置的上千条规则仍无法表达组织特有的合规要求（比如强制打标签）时，Checkov 允许用 Python 补充自定义规则：

```python
# custom_checks/S3BucketCustomCheck.py
from checkov.terraform.checks.resource.base_resource_check import BaseResourceCheck
from checkov.common.models.enums import CheckResult, CheckCategories

class S3BucketRequireTags(BaseResourceCheck):
    def __init__(self):
        name = "Ensure S3 bucket has required organizational tags"
        id = "CKV_AWS_CUSTOM_001"
        supported_resources = ['aws_s3_bucket']
        categories = [CheckCategories.GENERAL_SECURITY]
        super().__init__(name=name, id=id, categories=categories,
                         supported_resources=supported_resources)

    def scan_resource_conf(self, conf):
        """
        检查 S3 Bucket 是否包含必需的组织标签
        适用边界：仅检查标签存在性，不验证标签值合法性（需额外规则）
        """
        required_tags = ['Environment', 'Owner', 'CostCenter']

        if 'tags' in conf:
            tags = conf['tags'][0]
            missing_tags = [tag for tag in required_tags if tag not in tags]
            if missing_tags:
                return CheckResult.FAILED

        return CheckResult.PASSED

check = S3BucketRequireTags()
```

这段自定义规则的骨架就是 Checkov 扩展模型的全部：`__init__` 里声明"这条规则是谁、编号多少、管哪类资源"（`supported_resources = ['aws_s3_bucket']` 决定只对 S3 资源触发），核心逻辑集中在 `scan_resource_conf`——拿到资源配置字典 `conf`，判断后返回 `PASSED` 或 `FAILED`。核心是它的判定：只检查 `required_tags` 里的键是否存在，缺任意一个就判 FAILED。docstring 里已点明其适用边界——它只验证标签"有没有"，不验证标签值"对不对"，例如 `Environment` 标了个拼错的值也会通过。这正是自定义规则常见的坑：容易把"存在性检查"误当成"合法性检查"，若要校验取值还需再写一条规则。

```bash
# 使用自定义规则运行扫描
checkov -d terraform/ --external-checks-dir ./custom_checks/
```

### 综合 IaC 扫描脚本

前面对比表已经点出"单一工具规则覆盖不全"，这一节就把"组合使用 Checkov + tfsec"落成一个可直接运行的脚本。它要解决的现实问题是：两个工具各扫一遍、各出一份格式不同的报告，人怎么知道整体过没过？脚本用一段内联 Python 把两份报告归一化汇总，并以统一退出码决定门禁成败。其中"错误如何传播"和"两份报告如何合并"是两处关键：

```bash
#!/bin/bash
# iac-security-scan.sh - 综合 IaC 扫描脚本
set -e

RED='\033[0;31m'; GREEN='\033[0;32m'; YELLOW='\033[1;33m'; NC='\033[0m'

mkdir -p reports

# 1. Checkov 扫描（规则最全面）
# 追加 || true：Checkov 发现问题时返回非零，set -e 会在此中断脚本、
# 导致后续 tfsec、汇总、上传都不执行。用 || true 吞掉退出码，再单独取 $?。
echo -e "${YELLOW}[1/3] Running Checkov...${NC}"
checkov -d terraform/ --framework terraform --compact --quiet \
  --output cli --output json --output-file reports/checkov-report.json || true
CHECKOV_EXIT=$?

# 2. tfsec 扫描（误报率低，速度快）
echo -e "${YELLOW}[2/3] Running tfsec...${NC}"
tfsec terraform/ --format json --out reports/tfsec-report.json \
  --minimum-severity MEDIUM || true
TFSEC_EXIT=$?

# 3. 汇总报告
echo -e "${YELLOW}[3/3] Generating summary...${NC}"
python3 <<'EOF'
import json
from pathlib import Path

def load_json(file):
    try:
        with open(file) as f:
            return json.load(f)
    except Exception:
        return {}

checkov = load_json('reports/checkov-report.json')
tfsec   = load_json('reports/tfsec-report.json')

checkov_failed = checkov.get('summary', {}).get('failed', 0)
tfsec_issues   = len(tfsec.get('results', []))

print("=" * 50)
print("IaC Security Scan Summary")
print("=" * 50)
print(f"Checkov: {checkov.get('summary', {}).get('passed', 0)} passed, {checkov_failed} failed")
print(f"tfsec:   {tfsec_issues} issues found")
print("=" * 50)

total = checkov_failed + tfsec_issues
if total > 0:
    print(f"Total {total} security issues found")
    exit(1)
else:
    print("All IaC security scans passed!")
    exit(0)
EOF

# 上传报告到 S3（可选）
if [ -n "$REPORTS_S3_BUCKET" ]; then
  aws s3 cp reports/ s3://$REPORTS_S3_BUCKET/iac-scans/$(date +%Y%m%d)/ --recursive
fi
```

脚本的骨架分三段：分别跑 Checkov 和 tfsec 并各存一份 JSON，再用内联 Python 归一化汇总。汇总段是理解全脚本的钥匙——`load_json` 用 try/except 把"报告缺失或损坏"降级为空字典，避免因一份报告读不出来就整段崩溃；随后从两份结构完全不同的报告里分别取出失败计数（Checkov 读 `summary.failed`，tfsec 读 `results` 的长度），相加得到 `total`，非零就 `exit(1)`。这个 `exit(1)` 正是把"两个工具的并集结果"转成"一个门禁裁决"的地方。

这个脚本的设计考量与几处易错点值得留意：两个工具并集覆盖——Checkov 规则数量多但误报率稍高，tfsec 专注 Terraform 且误报率低，两者结合比单独使用任一工具覆盖率更高。开头的 `set -e` 保证意外命令失败（如目录不存在、工具未安装）时立即退出。但 Checkov 与 tfsec 在"发现安全问题"时也会返回非零退出码，若不处理，`set -e` 会在扫描一发现问题时就中断脚本，导致后续汇总与上传永不执行——因此两条扫描命令都追加了 `|| true` 吞掉退出码，再用 `$?` 单独捕获，把最终裁决交给汇总段的 Python 统一判定。报告统一上传到 S3 并按日期归档，支撑跨构建的趋势分析。

## 5.7.3 CloudFormation 安全扫描

### cfn-nag 实战

5.7.2 的工具主打 Terraform，AWS 原生的 CloudFormation 则需要专门的扫描器。cfn-nag 是其中最直接的一款，专注检测 IAM 过度权限、加密缺失这类模板级风险。它真正值得学习的不是扫描命令本身，而是它处理"例外"的方式——用抑制文件而非代码注释来管理豁免，这是安全治理能不能审计的分水岭：

```bash
gem install cfn-nag

# 扫描模板（JSON 输出用于 CI/CD 集成）
cfn_nag_scan --input-path cloudformation/ \
  --output-format json > cfn-nag-report.json

# 管理例外（通过抑制文件，而非注释代码）
cfn_nag_scan --input-path template.yaml \
  --blacklist-path cfn-nag-suppressions.yml
```

两条命令的分工很清楚：第一条是常规扫描并输出 JSON 供 CI 消费；第二条通过 `--blacklist-path` 引入一份抑制文件，让扫描跳过其中列明的规则。关键在这份抑制文件的写法：

```yaml
# cfn-nag-suppressions.yml — 统一管理审批过的例外
RulesToSuppress:
  - id: W28
    reason: "Resource names explicitly set for organizational naming requirements"
  - id: F1000
    reason: "Missing egress rule accepted for security group in private subnet (reviewed by Security Team 2024-Q3)"
```

这份文件里 `reason` 字段最见分量——每条豁免都被强制写明理由，第二条甚至记录了"由安全团队在某季度评审通过"。这就是抑制文件相较代码内注释的意义：通过集中文件管理例外（而非在代码中散落注释），安全团队可以在一处统一审查所有豁免项，并通过 Git 历史追踪每条豁免是谁、何时、为何加入。生产环境里例外管理失控是常见退化路径——豁免散落在几十个模板的注释里，无人清点、无从追责，最终门禁被例外掏空；把例外收拢进一份受版本控制的抑制文件，正是对抗这种熵增的手段。

### CloudFormation Guard 策略即代码

cfn-nag 查的是"通用的坏味道"，但企业往往有自己的硬性合规要求（如所有 S3 必须加密、必须禁公开）。CloudFormation Guard 用一套自定义 DSL 把这些要求写成可执行的策略规则，属于"策略即代码"路线——合规标准不再是文档里的一句话，而是能进流水线自动核验的代码：

```bash
cargo install cfn-guard

# 验证模板
cfn-guard validate \
  --data cloudformation/ \
  --rules rules/ \
  --show-summary all
```

`validate` 命令的三个参数构成了策略即代码的基本形态：`--data` 指向被检查的模板、`--rules` 指向策略规则目录、`--show-summary all` 输出完整结果。真正的表达力在规则文件里：

```
# s3-security-rules.guard — S3 安全配置必需项
rule s3_bucket_encrypted {
  Resources.*[ Type == 'AWS::S3::Bucket' ] {
    Properties {
      BucketEncryption exists
      BucketEncryption.ServerSideEncryptionConfiguration[*] {
        ServerSideEncryptionByDefault {
          SSEAlgorithm in ['aws:kms', 'AES256']
        }
      }
    }
  }
}

rule s3_bucket_block_public_access {
  Resources.*[ Type == 'AWS::S3::Bucket' ] {
    Properties {
      PublicAccessBlockConfiguration {
        BlockPublicAcls == true
        BlockPublicPolicy == true
        IgnorePublicAcls == true
        RestrictPublicBuckets == true
      }
    }
  }
}
```

这段 DSL 本质上是"对模板结构的断言"。每条 `rule` 先用 `Resources.*[ Type == 'AWS::S3::Bucket' ]` 筛出所有 S3 资源，再在其 `Properties` 上逐条断言必须满足的条件。`s3_bucket_encrypted` 表达的是"必须开加密，且算法只能是 KMS 或 AES256"——注意 `BucketEncryption exists` 这一句，它先确保加密配置块存在，再往下断言算法取值，这个"先存在后取值"的顺序不能省，否则对不存在的字段取值会报错而非判为违规。`s3_bucket_block_public_access` 则把四个禁公开开关一次性钉死为 `true`，四个都要满足才算合规。相比 cfn-nag 的内置规则，这种写法的价值是让企业的硬性标准以人可读、可评审、可进 Git 的形式沉淀下来。

### 安全 S3 Bucket CloudFormation 模板

规则定义了"什么样的模板算合规"，接下来给出一份本身就满足这些规则的参考模板。它不只是"能通过扫描"，更把一个常被忽视的设计理念做进了模板：让加密强度由数据敏感度自动驱动，而非一刀切。这份模板的主线是 `DataClassification` 参数如何一路影响到密钥创建、加密算法和上传策略：

```yaml
# secure-s3-bucket.yaml — 数据分类驱动加密策略
AWSTemplateFormatVersion: '2010-09-09'
Parameters:
  BucketName:
    Type: String
  DataClassification:
    Type: String
    Default: Confidential
    AllowedValues: [Restricted, Confidential, Internal, Public]

Conditions:
  IsHighSensitivity: !Or
    - !Equals [!Ref DataClassification, Restricted]
    - !Equals [!Ref DataClassification, Confidential]

Resources:
  # Restricted/Confidential 数据使用 KMS 加密，Internal/Public 使用默认 AES256
  BucketEncryptionKey:
    Type: AWS::KMS::Key
    Condition: IsHighSensitivity
    Properties:
      Description: !Sub 'Encryption key for ${BucketName}'
      KeyPolicy:
        Version: '2012-10-17'
        Statement:
          - Sid: RootAccess
            Effect: Allow
            Principal:
              AWS: !Sub 'arn:aws:iam::${AWS::AccountId}:root'
            Action: 'kms:*'
            Resource: '*'

  SecureS3Bucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Ref BucketName
      PublicAccessBlockConfiguration:         # 阻止所有公共访问
        BlockPublicAcls: true
        BlockPublicPolicy: true
        IgnorePublicAcls: true
        RestrictPublicBuckets: true
      VersioningConfiguration:
        Status: Enabled                       # 版本控制防勒索删除
      BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault:
              SSEAlgorithm: !If [IsHighSensitivity, 'aws:kms', 'AES256']
              KMSMasterKeyID: !If [IsHighSensitivity, !GetAtt BucketEncryptionKey.Arn, !Ref AWS::NoValue]
            BucketKeyEnabled: true            # 减少 KMS API 调用成本
      LoggingConfiguration:
        DestinationBucketName: !Ref LoggingBucket
        LogFilePrefix: !Sub '${BucketName}/'
      Tags:
        - Key: DataClassification
          Value: !Ref DataClassification

  SecureS3BucketPolicy:
    Type: AWS::S3::BucketPolicy
    Properties:
      Bucket: !Ref SecureS3Bucket
      PolicyDocument:
        Statement:
          - Sid: DenyInsecureTransport
            Effect: Deny
            Principal: '*'
            Action: 's3:*'
            Resource:
              - !GetAtt SecureS3Bucket.Arn
              - !Sub '${SecureS3Bucket.Arn}/*'
            Condition:
              Bool:
                'aws:SecureTransport': false
          - Sid: DenyUnencryptedUploads
            Effect: Deny
            Principal: '*'
            Action: 's3:PutObject'
            Resource: !Sub '${SecureS3Bucket.Arn}/*'
            Condition:
              StringNotEquals:
                's3:x-amz-server-side-encryption': !If [IsHighSensitivity, 'aws:kms', 'AES256']

  LoggingBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Sub '${BucketName}-logs'
      PublicAccessBlockConfiguration:
        BlockPublicAcls: true
        BlockPublicPolicy: true
        IgnorePublicAcls: true
        RestrictPublicBuckets: true
      LifecycleConfiguration:
        Rules:
          - Id: DeleteOldLogs
            Status: Enabled
            ExpirationInDays: 90
```

这份模板的设计逻辑，围绕一个 `Condition` 展开：`IsHighSensitivity` 判断数据是否属于 Restricted/Confidential 高敏感级，随后它像一根总开关贯穿三处——第一，控制 `BucketEncryptionKey` 这个 KMS 密钥资源是否被创建（`Condition: IsHighSensitivity`），避免低敏感 Bucket 白白承担密钥管理成本；第二，在桶加密里用 `!If` 在 `aws:kms` 与 `AES256` 之间切换算法；第三，在桶策略的 `DenyUnencryptedUploads` 里同步切换要求的加密头，确保上传时强制的加密方式与桶配置一致。这种"一个条件驱动多处联动"的写法，好处是数据分类一改，整套加密策略自动对齐，坏处是要小心三处的 `!If` 保持同步——若只改了加密配置却忘了改上传策略的断言，就会出现"桶要求 KMS 但策略只拦非 AES256"的错配。

除了分类驱动，模板里还藏着几个值得学的纵深防护默认项：`VersioningConfiguration: Enabled` 用版本控制对抗勒索删除；桶策略的 `DenyInsecureTransport` 强制 HTTPS 传输；独立的 `LoggingBucket` 承接访问日志并设 90 天生命周期自动清理，日志桶自身也关闭了公开访问。而 `BucketKeyEnabled: true` 是成本侧的关键——它通过引入 Bucket 级数据密钥减少对 KMS 的直接调用频次，在高吞吐写入场景显著降低 KMS 调用成本，是"安全"与"账单"之间少见的双赢项，值得默认开启。

## 5.7.4 容器镜像供应链安全

### 镜像签名方案对比

IaC 保证了"环境配置对"，但部署上去的镜像是不是构建时的那一个、有没有被中途替换，是另一个供应链问题。镜像签名就是回答"这个镜像可信吗"的机制。落地时首先要在几套方案里做取舍——它们在 OCI 兼容性、Kubernetes 集成难度、密钥管理方式和社区活力上差异明显：

下表的"学习曲线""社区活跃度""推荐度"为作者按落地经验给出的判断（示例口径，非厂商或基金会评级），其余各行为可对照官方文档核实的客观特性。另需注意命名：早期的 "Notary v2" 现已定名为 Notary Project，其签名工具为 Notation，v1.0 于 2023 年 8 月发布[2]。

| 方案 | Cosign | Notary Project / Notation（原 Notary v2） | Docker Content Trust |
|------|--------|-----------|---------------------|
| 开发者 | Sigstore（OpenSSF） | Notary Project（CNCF） | Docker |
| OCI 支持 | 是 | 是（OCI 标准） | 有限 |
| Kubernetes 集成 | 易（Policy Controller） | 易 | 难 |
| 密钥管理 | 灵活（含 Keyless） | 简化 | Docker Hub |
| 学习曲线 | 低 | 中 | 中 |
| 社区活跃度 | 高 | 中（增长中） | 低 |
| 推荐度 | 推荐（首选） | 推荐（长期标准） | 不推荐 |

"密钥管理"这一行是签名方案落地最大的运维负担。Cosign 支持 Keyless 模式，由 Sigstore 的 Fulcio CA 基于 OIDC 身份签发短期证书、并把签名记录写入 Rekor 透明日志[3]，意味着不必生成、保管、轮换一把长期私钥——这正是它学习曲线低、被推荐为首选的核心原因；Notation 靠 OCI 标准取胜，适合对合规兼容性有硬要求的场景；Docker Content Trust 绑定 Docker Hub、Kubernetes 集成"难"、社区活跃度"低"，实际是被淘汰的选项。据此，新项目优先选 Cosign：学习曲线低、Keyless 模式无需管理私钥、生态支持好；对 OCI 标准合规性有要求时选 Notation；避免 Docker Content Trust（仅限 Docker Hub，已停止主要开发）。

### Cosign 实战：签名与验证

对比表推荐了 Cosign，下面把它的完整工作流走一遍。这里刻意并列展示"密钥对签名"和"Keyless 签名"两种方式，以凸显 Keyless 到底省掉了什么——同样是签名，一个要自己造钥匙、藏钥匙，一个借临时身份换取一次性证书：

```bash
# 安装 Cosign
brew install cosign

# 方式 1：密钥对签名（需管理私钥）
cosign generate-key-pair
aws secretsmanager create-secret \
  --name cosign-private-key \
  --secret-string file://cosign.key   # 私钥存储到 Secrets Manager

cosign sign --key cosign.key myregistry.io/myapp:v1.0.0

# 方式 2：Keyless 签名（推荐，无需管理私钥）
# 使用 OIDC Token（GitHub Actions ID Token）签名，身份由 Sigstore Fulcio CA 颁发
cosign sign --yes myregistry.io/myapp:v1.0.0

# 验证签名（用于 CI 或部署前检查）
cosign verify --key cosign.pub myregistry.io/myapp:v1.0.0

# 生成 SBOM 并附加到镜像（供应链透明度）
cosign attest --key cosign.key \
  --predicate sbom.spdx.json \
  --type spdxjson \
  myregistry.io/myapp:v1.0.0
```

对照两种方式读：方式 1 需要先 `generate-key-pair` 造出私钥，再郑重其事地把它塞进 Secrets Manager——从这一步就能预感到后续的轮换、权限、泄露风险都得自己扛；方式 2 的 `cosign sign --yes` 后面没有任何 `--key`，因为它用运行环境的 OIDC 身份向 Sigstore 的 Fulcio CA 换取一张短期证书完成签名，签完即弃，没有需要长期保管的私钥。最后 `cosign attest` 把 SBOM 作为 attestation 附加到镜像上，让"这个镜像里装了哪些组件"也成为可验证的供应链事实，而不只是签个名了事。

把 Keyless 签名接进 CI，就得到一条构建—扫描—推送—签名—生成 SBOM 的完整链路：

```yaml
# GitHub Actions — 构建、扫描、签名、生成 SBOM
name: Build and Sign Image
jobs:
  build-sign:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
      id-token: write  # OIDC Keyless 签名必需

    steps:
      - uses: actions/checkout@v4

      - name: Install Cosign
        uses: sigstore/cosign-installer@v3

      - name: Build Image
        run: docker build -t ghcr.io/${{ github.repository }}:${{ github.sha }} .

      - name: Trivy Scan (before push)
        uses: aquasecurity/trivy-action@0.24.0  # 固定版本，避免 @master 移动标签
        with:
          image-ref: ghcr.io/${{ github.repository }}:${{ github.sha }}
          severity: 'CRITICAL'
          exit-code: '1'  # CRITICAL 漏洞时失败，不推送

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Push Image
        run: docker push ghcr.io/${{ github.repository }}:${{ github.sha }}

      # Keyless 签名：GitHub OIDC Token 由 Sigstore Fulcio CA 颁发证书
      - name: Sign Image (Keyless)
        run: cosign sign --yes ghcr.io/${{ github.repository }}:${{ github.sha }}

      # 生成 SBOM 并附加为 Attestation（可审计的供应链信息）
      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          image: ghcr.io/${{ github.repository }}:${{ github.sha }}
          format: spdx-json
          output-file: sbom.spdx.json

      - name: Attest SBOM
        run: |
          cosign attest --yes \
            --predicate sbom.spdx.json \
            --type spdxjson \
            ghcr.io/${{ github.repository }}:${{ github.sha }}
```

这条流水线有两个关键约束。其一是 step 的先后顺序不可颠倒：Trivy 扫描（`exit-code: 1`）排在 push 之前，保证有 CRITICAL 漏洞的镜像根本不会进 Registry；签名和 SBOM attestation 排在 push 之后，因为它们签的是已入库镜像的摘要。其二是 `id-token: write` 权限——它是 Keyless 签名成立的前提，正因为 job 拿到了 OIDC token 才能向 Fulcio 换证书。少了这一行，`cosign sign --yes` 会因拿不到身份而失败，这是把 Keyless 签名搬进 CI 时最容易漏配的一处。

### Kubernetes 准入控制：强制签名验证

到此为止镜像已被签名，但签名只是"贴了封条"，封条有没有人查才是关键——签名只有在部署阶段被强制验证才真正有效，否则攻击者大可推一个未签名的镜像照样部署。Kubernetes 侧通过准入控制来做这道强制验证，下面给出两种实现，核心差异是"引入新组件"还是"复用已有的 Gatekeeper"。

方式一：Sigstore Policy Controller（推荐）：

```yaml
# ClusterImagePolicy：要求所有来自 myregistry.io 的镜像必须有有效签名
apiVersion: policy.sigstore.dev/v1beta1
kind: ClusterImagePolicy
metadata:
  name: require-signed-images
spec:
  images:
    - glob: "myregistry.io/**"   # 只对内部 Registry 强制验证
  authorities:
    - key:
        data: |
          -----BEGIN PUBLIC KEY-----
          <cosign.pub 内容>
          -----END PUBLIC KEY-----
```

这段 `ClusterImagePolicy` 的表达力集中在两个字段：`images.glob` 划定"对哪些镜像强制验签"，这里刻意只框住内部 Registry（`myregistry.io/**`），因为对公共基础镜像强制验签既不现实也会拦停正常拉取；`authorities.key` 给出验签用的公钥。策略生效后，任何匹配该 glob 但签名缺失或无效的镜像都会在准入阶段被拒。

```bash
# 部署 Sigstore Policy Controller
kubectl apply -f https://github.com/sigstore/policy-controller/releases/latest/download/policy-controller.yaml

# 验证：尝试部署未签名镜像（预期：Pod 创建失败，返回签名验证错误）
kubectl run test --image=myregistry.io/myapp:unsigned
# 预期响应：Error: image signature verification failed
```

这里有一个可操作的验证方法：装好 Policy Controller 后，故意 `kubectl run` 一个未签名镜像，若准入控制生效，Pod 会直接创建失败并返回签名验证错误。这一步不能省——很多团队配了策略却从不做反向验证，结果策略因命名空间选择器或 webhook 未就绪而静默失效，真正的攻击镜像照样放行。

方式二：OPA Gatekeeper（适合已有 Gatekeeper 环境）：

```yaml
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: cosignimageverification
spec:
  crd:
    spec:
      names:
        kind: CosignImageVerification
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package cosignimageverification
        violation[{"msg": msg}] {
          container := input.review.object.spec.containers[_]
          not verified(container.image)
          msg := sprintf("Image %v is not signed or signature invalid", [container.image])
        }
        verified(image) {
          # 调用 cosign-verifier sidecar API
          result := http.send({
            "method": "POST",
            "url": "http://cosign-verifier:8080/verify",
            "body": {"image": image}
          })
          result.status_code == 200
        }
```

Gatekeeper 版的逻辑写在 Rego 里，遵循"先遍历、再判定、不满足就报违规"的结构：`violation` 规则遍历 Pod 里每个容器，对 `not verified(container.image)`（即未通过验证）的镜像生成一条违规消息。而 `verified` 这个辅助函数本身并不做密码学验证，它通过 `http.send` 把镜像名 POST 给一个外部的 `cosign-verifier` sidecar，靠返回的 `status_code == 200` 来判断。这就点出了两种方式的本质区别与那个坑——Gatekeeper 自己不会验签，必须额外部署并运维 cosign-verifier sidecar，而且 Rego 里对外部 HTTP 的依赖意味着 sidecar 挂了验签就失效。

适用边界：Gatekeeper 方式需要额外部署 cosign-verifier sidecar，复杂度高于 Policy Controller，但适合已有 Gatekeeper 环境，避免引入新工具。新项目优先 Policy Controller。

## 5.7.5 安全左移实践

### Pre-commit Hooks：提交前自动检查

前面几节的门禁都发生在代码提交之后的 CI 环节，而安全左移的极致是把检查再往前挪到"提交之前"。Pre-commit Hooks 在代码进入仓库前于开发者本机执行，是最低成本、最高效率的安全左移手段——问题在离开开发者电脑前就被拦下，连一次 CI 运行都省了。下面这份配置编排了从秘密扫描到 Dockerfile lint 的多道本地检查，其中 Hook 的排序和每道检查的执行代价是两处要点：

```yaml
# .pre-commit-config.yaml
repos:
  # 秘密扫描（最重要，最先执行）
  - repo: https://github.com/trufflesecurity/trufflehog
    rev: v3.63.0
    hooks:
      - id: trufflehog
        args: ['filesystem', '.', '--fail']  # v3 用位置参数指定路径，无 --directory 选项

  # Terraform 安全扫描
  - repo: https://github.com/antonbabenko/pre-commit-terraform
    rev: v1.86.0
    hooks:
      - id: terraform_fmt       # 格式化（非安全，但统一风格）
      - id: terraform_validate  # 语法验证
      - id: terraform_tfsec
        args:
          - --args=--minimum-severity=MEDIUM

  # Python 安全扫描
  - repo: https://github.com/pycqa/bandit
    rev: 1.7.5
    hooks:
      - id: bandit
        args: ['-r', 'src/', '-ll']   # -ll: 只报告 Medium 以上问题

  # Dockerfile 安全检查
  - repo: https://github.com/hadolint/hadolint
    rev: v2.12.0
    hooks:
      - id: hadolint

  # 提交消息规范（Conventional Commits，非安全，但保持 Git 历史整洁）
  - repo: https://github.com/commitizen-tools/commitizen
    rev: v3.13.0
    hooks:
      - id: commitizen
        stages: [commit-msg]
```

这份配置的编排有讲究。秘密扫描放在最前且注释标"最重要"，因为凭证一旦提交进历史就极难彻底清除，必须在提交那一刻拦住；`bandit` 用 `-ll` 只报 Medium 以上、`tfsec` 设 `--minimum-severity=MEDIUM`，都是在本地阶段刻意抬高门槛，用降低噪音换取开发者不反感；`commitizen` 挂在 `commit-msg` 阶段而非文件检查阶段，是因为它校验的是提交消息而非代码。整体原则是：本地只放"快且高价值"的检查。

```bash
pip install pre-commit
pre-commit install          # 安装到 .git/hooks/
pre-commit run --all-files  # 手动测试配置
```

`pre-commit install` 把这套 Hook 真正挂进 `.git/hooks/`，之后每次 `git commit` 自动触发；`--all-files` 则用于首次配置时手动全量跑一遍验证。

生产陷阱：这正是本地 Hook 最反直觉的失败模式——Pre-commit Hook 执行时间超过 30 秒，开发者会开始使用 `git commit --no-verify` 绕过检查，而这比没有 Hook 更危险（团队以为"安全检查已完成"，实际被普遍绕过，产生错误的安全感知）。优化策略与上文的编排原则一致：Pre-commit 只执行快速检查（Secret 扫描、Dockerfile lint 这类秒级操作），把完整 SAST/SCA 这类可以承受几分钟的重扫描留给 CI/CD。判断一道检查该放本地还是放 CI，标尺就是它会不会慢到逼开发者伸手去按 `--no-verify`。

### IDE 插件集成

Pre-commit 在"提交时"拦截，IDE 插件则把反馈再前移到"敲代码时"——开发者边写边看到问题，是左移链条上最靠前的一环。这里给出一份团队统一的 VS Code 配置，重点不在装了哪些插件，而在如何让本地插件与 CI 用同一套规则，避免"本地和 CI 各说各话"：

```jsonc
// .vscode/settings.json — 推荐团队统一配置（JSONC，允许注释）
{
  "extensions": {
    "recommendations": [
      "trufflesecurity.trufflehog",             // Secret 扫描（保存时触发）
      "snyk-security.snyk-vulnerability-scanner", // 依赖漏洞扫描
      "sonarsource.sonarlint-vscode",            // SAST（实时提示）
      "hashicorp.terraform",                     // Terraform 语法
      "ms-azuretools.vscode-docker"              // Docker 支持
    ]
  },
  "sonarlint.connectedMode.project": {
    "projectKey": "my-project"  // 连接 SonarQube 服务端，同步规则配置
  },
  "snyk.severity": "high",         // 只显示 High 以上问题（减少噪音）
  "trufflehog.scanOnSave": true    // 保存时自动扫描
}
```

配置里最该学的是 `sonarlint.connectedMode`。它把本地 SonarLint 连到 SonarQube 服务端，让 IDE 复用与 CI/CD 完全相同的规则配置（Quality Profile）——于是开发者在本地就能看到 CI 会拦截的同一批问题，而不是到 CI 才被打回。若不开连接模式，本地插件用的是各自的默认规则，容易与 CI 规则不一致，形成"本地能过但 CI 失败"的低效往返。其余几项如 `snyk.severity: high`、`trufflehog.scanOnSave` 则延续了"降噪 + 即时反馈"的一贯思路：只报高危、保存即扫，让提示恰好落在开发者心流之内而非之外。

### 开发者分级安全培训体系

工具能拦住已知模式，却拦不住开发者对安全的无感——工具只是手段，开发者安全意识才是根本。硬把所有安全知识一次性灌给新人既学不进也用不上，因此这里采用分级培训：按入职时间线，让不同阶段的开发者获得与其当下工作匹配的安全能力，能力随职责逐级加码：

| 级别 | 时机 | 核心内容 | 考核方式 | 时长 |
|------|------|---------|---------|------|
| Level 1（基础意识） | 入职第 1 周 | OWASP Top 10（现行版本为 2025，其中"软件供应链失效"升至 A03，培训教材需跟版）[4]、共享责任模型、秘密管理、公司安全政策 | 在线测试 80 分及格 | 4 小时 |
| Level 2（工具使用） | 入职第 2 周 | IDE 插件配置、Pre-commit 设置、Trivy/Checkov/Snyk 使用 | 修复 5 个实际漏洞 | 4 小时动手实验 |
| Level 3（安全开发） | 入职第 1 个月 | 威胁建模（STRIDE）、安全设计模式、输入验证、加密最佳实践 | 完成 1 个功能的威胁建模 | 8 小时分 2 周 |
| Level 4（云安全专精） | 入职第 3 个月 | IAM 最小权限、网络安全架构、容器/K8s 安全、DevSecOps 流水线 | AWS Security Specialty / CKS 认证 | 40 小时自学+实验 |

这张表有两条递进线索。一是时机与内容的匹配：第 2 周才教工具使用，恰好接上前两小节的 IDE 插件与 Pre-commit，让培训紧贴开发者当周真正要用的东西；Level 4 云安全专精压到第 3 个月，因为它对应的是能独立设计流水线的资深职责，新人前期用不上。二是考核方式的升级：从 Level 1 的"在线测试"到 Level 2 的"修复 5 个实际漏洞"再到 Level 3 的"完成一次威胁建模"，考核从"知道"逐步逼近"能做"，避免培训沦为走过场。

持续学习（每季度）：参加内部 CTF 比赛、Purple Team 演练、月度安全技术分享会、新工具评估。

验证方法：培训后 3 个月统计开发者引入的安全漏洞数量，目标下降 50%；季度安全意识测试通过率 ≥90%。

## 5.7.6 安全门禁设计

### Quality Gate 策略

前面各节分别实现了单点检查，但要让它们合起来构成一道可发布/不可发布的"闸门"，需要一张统一的裁决表——Quality Gate 定义发布前必须满足的安全质量标准，核心是把每类检查项归入"阻断"还是"警告"，并给每类问题配一个修复 SLA。下表的价值在于把散落的规则收敛成一份人人可查的发布契约：

| 检查项 | 阻断 | 警告 | 修复 SLA |
|--------|------|------|---------|
| Critical 漏洞（SAST/SCA/容器） | 是 | | 立即（< 24 小时） |
| High 漏洞（SAST） | 是（≤ 设定阈值时通过） | | 7 天 |
| High 漏洞（SCA） | | 是 | 30 天（等待上游补丁） |
| 秘密泄露 | 是 | | 立即 |
| IaC 合规（Critical 规则） | 是 | | 14 天 |
| 代码覆盖率（新增代码） | | 是（< 80%） | — |
| License 合规（GPL 许可证） | | 是 | — |

同为 High 漏洞，SAST 阻断而 SCA 只警告，这处看似矛盾的设计最见门道。原因在于 High SAST 与 High SCA 的差异——SAST 检测到的代码漏洞是自家代码里的问题，开发者可以直接动手修（7 天可控）；SCA 检测到的依赖漏洞要等上游软件包发布修复版本，时间不由自己掌控（30 天），硬阻断只会把交付卡死在别人手里，因此改为生成工单跟踪。这条差异化处置正是整张表的设计精髓——阻断与否不看严重级别，而看"这个问题是否修得动、修得起"。

### SonarQube Quality Gate 配置

上表是人读的策略，SonarQube 需要把它翻译成机器可执行的门禁配置。下面这段 JSON 只是策略表里 SAST 相关几行的落地，每个 `metric` 和它的阈值都与上表一一对应：

```json
{
  "name": "Production Quality Gate",
  "conditions": [
    {
      "metric": "new_vulnerabilities",
      "operator": "GREATER_THAN",
      "error": "0"
    },
    {
      "metric": "new_security_hotspots",
      "operator": "GREATER_THAN",
      "error": "3"
    },
    {
      "metric": "new_coverage",
      "operator": "LESS_THAN",
      "error": "80"
    }
  ]
}
```

各 `metric` 的含义：`new_vulnerabilities` 是新增漏洞数（只看 PR 新增，不惩罚历史债务，阈值 0）；`new_security_hotspots` 是需人工审查的潜在风险点（允许 ≤3，避免过度阻断）；`new_coverage` 是新增代码的测试覆盖率。**注意 JSON 规范不支持行内注释**——把说明写进 `//` 会让 SonarQube 的配置导入直接失败，这类"文档里能看、贴进去就报错"的写法在 CI 配置中要特别当心。


这段配置的关键全在三个 `metric` 名字的 `new_` 前缀上。它们分别针对新增漏洞、新增安全热点、新增代码覆盖率，而非项目的绝对值。这样设计的关键原因是：只检查 PR 新增问题，不要求解决所有历史技术债务。否则一个历史上有上千个低风险告警的大型遗留项目，任何 PR 都会因为这些存量问题无法通过 Quality Gate，最终团队只能整体关掉门禁，反而形同虚设。此外 `new_security_hotspots` 允许 ≤3 个而不是零容忍，也是同一克制思路——安全热点是"需人工审查的疑似点"而非确证漏洞，卡死为零会把大量误报变成阻断，反噬门禁的可用性。

## 5.7.7 SAST/DAST/SCA 集成

### 工具对比

七层门禁里代码与依赖层的检查由 SAST/SCA/DAST 三类工具承担，它们分别从静态代码、依赖成分、运行时行为三个角度查漏，互为补充而非替代。选型时每一类内部又要在语言覆盖、误报率、集成难易之间取舍，下面三张表分类对照：

SAST 工具：

| 工具 | 语言支持 | 误报率 | 最佳场景 |
|------|---------|--------|---------|
| SonarQube | 25+ | 中 | 通用，CI/CD 集成成熟 |
| CodeQL | 10+ | 低 | 深度语义分析，GitHub 生态 |
| Semgrep | 20+ | 中 | 自定义规则，速度快 |
| Checkmarx | 30+ | 低 | 企业级，支持最广泛 |

SCA 工具：

| 工具 | CVE 覆盖 | License 检查 | 最佳场景 |
|------|---------|------------|---------|
| MurphySec（墨菲安全） | 广（含中文漏洞情报） | 是 | 中国企业，本土漏洞情报 |
| Snyk Open Source | 广 | 是 | 开发者集成，多语言 |
| Dependabot | 中 | 否 | GitHub 生态，自动 PR |
| OWASP Dependency-Check | 中 | 是 | 开源，无预算场景 |

DAST 工具：

| 工具 | 扫描类型 | CI/CD 集成 | 最佳场景 |
|------|---------|----------|---------|
| OWASP ZAP | 主动/被动 | 易 | 开源项目 |
| StackHawk | 主动 | 易（为 DevSecOps 优化） | CI/CD 内 DAST |
| Burp Suite | 主动 | 难 | 专业手工渗透测试 |

三张表放在一起读，能看出各类工具的选型主轴不同。SAST 表的主轴是"误报率 vs 覆盖广度"：CodeQL 误报低但语言支持较窄，Checkmarx 支持最广、偏企业级。SCA 表的主轴是"漏洞情报来源与是否管 License"：MurphySec 含中文漏洞情报适合国内环境，Dependabot 胜在自动发 PR 但不查 License。DAST 表则几乎由"CI/CD 集成难易"决定去留：ZAP、StackHawk 易于集成适合自动化流水线，Burp Suite 集成难、定位于人工渗透测试。选型时先确定"这一类里我最在意哪根主轴"，再对号入座即可。

### 完整 GitLab CI 安全流水线

前面单独看过各类工具，这一节把 SAST、SCA、容器扫描、DAST 全部编排进一条完整的 GitLab 流水线，展示它们如何按阶段串联、哪些并行、哪些阻断、哪些只警告。这是本节最能体现"门禁分级"落地的一段代码，每个 job 的 `allow_failure` 与 `when` 两个字段是关键——它们决定了每道检查是"硬闸"还是"软提示"：

```yaml
# .gitlab-ci.yml — 完整 SAST + SCA + 容器扫描 + DAST
stages:
  - pre-commit
  - sast
  - build
  - sca
  - container-scan
  - deploy-staging
  - dast
  - report

# ==================== 秘密扫描（第一道防线）====================
secret-scan:
  stage: pre-commit
  image: trufflesecurity/trufflehog:latest
  script:
    - trufflehog filesystem . --json --fail
  allow_failure: false

# ==================== SAST 扫描（并行）====================
sonarqube-sast:
  stage: sast
  image: sonarsource/sonar-scanner-cli:latest
  script:
    - sonar-scanner
      -Dsonar.projectKey=$CI_PROJECT_NAME
      -Dsonar.sources=src
      -Dsonar.host.url=$SONAR_HOST_URL
      -Dsonar.login=$SONAR_TOKEN
      -Dsonar.qualitygate.wait=true      # 等待 Quality Gate 结果
  allow_failure: false
  only:
    - merge_requests
    - main

semgrep-sast:
  stage: sast
  image: returntocorp/semgrep:latest
  script:
    - semgrep ci --config auto --sarif > semgrep-report.sarif
  artifacts:
    reports:
      sast: semgrep-report.sarif
  allow_failure: true   # Semgrep 作为补充扫描，不阻断构建

# ==================== 构建 ====================
build-app:
  stage: build
  script:
    - mvn clean package -DskipTests
  artifacts:
    paths:
      - target/*.jar

# ==================== SCA 依赖扫描（并行）====================
snyk-sca:
  stage: sca
  image: snyk/snyk:node
  script:
    - snyk test --severity-threshold=high --json > snyk-report.json
  artifacts:
    reports:
      dependency_scanning: snyk-report.json
  allow_failure: true   # High SCA 漏洞警告但不阻断

# ==================== 容器镜像扫描（并行）====================
build-image:
  stage: container-scan
  services:
    - docker:dind
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

trivy-scan:
  stage: container-scan
  image: aquasec/trivy:latest
  script:
    - trivy image
      --exit-code 1
      --severity HIGH,CRITICAL
      --format sarif
      --output trivy-report.sarif
      $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  allow_failure: false  # High/Critical 容器漏洞强制阻断

# ==================== 部署到 Staging ====================
deploy-staging:
  stage: deploy-staging
  script:
    - kubectl set image deployment/myapp myapp=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -n staging
    - kubectl rollout status deployment/myapp -n staging
  environment:
    name: staging
    url: https://staging.myapp.com
  only:
    - main

# ==================== DAST 动态扫描（手动触发，耗时长）====================
zap-dast:
  stage: dast
  image: ghcr.io/zaproxy/zaproxy:stable  # owasp/zap2docker-* 镜像已弃用，迁移至 ghcr.io/zaproxy/zaproxy
  script:
    - zap-baseline.py
      -t https://staging.myapp.com
      -r zap-baseline-report.html
      -J zap-baseline-report.json
      || true   # DAST 发现问题不阻断构建，供安全团队审查
  artifacts:
    paths:
      - zap-baseline-report.html
  only:
    - main
  when: manual   # 手动触发：DAST 耗时 30 分钟+，不适合每次自动执行
```

看懂这条流水线的关键，是把 `stages` 顺序、`allow_failure` 与 `when` 三者连起来读。`stages` 列表定义了 pre-commit → sast → build → sca → container-scan → deploy-staging → dast → report 的时间轴，检查越靠前越靠近提交。而每个 job 的 `allow_failure` 才是门禁的真正开关：`secret-scan`、`sonarqube-sast`、`trivy-scan` 都设 `allow_failure: false`——秘密泄露、SAST Quality Gate 不过、High/Critical 容器漏洞都是硬闸，失败即拦停；而 `semgrep-sast`（补充扫描）和 `snyk-sca`（依赖漏洞受制于上游）设 `allow_failure: true`，只警告不阻断，正好对应 5.7.6 那张表里"SCA High 只警告"的策略。这套 `false/true` 的分配，就是把上一节的分级策略在流水线里逐 job 兑现。

DAST 那个 job 一次性示范了 DAST 的两个特殊约束。`when: manual` 让它只在手动触发时才跑——DAST 扫描时间长（30 分钟至数小时），在 Staging 环境运行真实攻击测试，每次 PR 都触发会让 Pipeline 迟迟无法完成；更合适的节奏是主分支合并后手动触发（每日/每周一次）或绑进 release 流程（发布前强制执行）。脚本尾部的 `|| true` 则让 DAST 即便发现问题也不返回失败码，报告照常归档供安全团队分析——这么处理是因为 DAST 误报率相对较高，不宜作为自动阻断门禁，硬拦会频繁误伤正常发布。

## 5.7.8 漏洞全生命周期管理

### 漏洞 SLA 标准

前面的门禁负责"把漏洞挡在门外"，但总有漏洞会进入生产、或在既有系统里被扫出——这就需要一套修复时限（SLA）来约束"多久必须修好"。最朴素的做法是按 CVSS 评分套一张固定 SLA 表：

| 严重性 | CVSS 评分 | 基础 SLA | 升级路径 | 例外政策 |
|--------|---------|---------|---------|---------|
| Critical | 9.0-10.0 | 24 小时 | 立即通知 CISO | 不允许 |
| High | 7.0-8.9 | 7 天 | 每日更新提醒 | CISO 审批 |
| Medium | 4.0-6.9 | 30 天 | 每周更新 | 安全负责人审批 |
| Low | 0.1-3.9 | 90 天 | 月度报告 | 团队 Leader 审批 |

这张表除了给出时限，还配了"升级路径"和"例外政策"两列，让 SLA 不只是数字而是可执行的治理约定——Critical 不允许例外、越往下审批权越下放。但这张静态表有其局限：CVSS 评分只是 SLA 的起点，不是终点。一个 CVSS 7.5 的 SQL 注入，若在公网暴露的支付服务上，实际危险远高于分数本身，SLA 理应缩短。为了让时限贴合真实风险而非停留在纸面分数，下面引入动态 SLA 计算。

### 动态 SLA 计算逻辑

动态 SLA 要解决的正是上面那个错配：同一个 CVSS 分数，跑在公网支付服务上和跑在内网工具上，紧迫程度天差地别。这段代码用"基础 SLA 乘以若干风险系数"的方式，把暴露度、可利用性、数据敏感度这三个静态评分没充分反映的维度纳进来。三个系数如何相乘，以及 docstring 里预先算好的两个对照示例，是这段代码的重点：

```python
def calculate_dynamic_sla(vuln: dict) -> int:
    """
    基于多维度计算动态 SLA（单位：小时）

    参数：
        vuln: 漏洞信息字典，包含：
            - severity: 'Critical' / 'High' / 'Medium' / 'Low'
            - publicly_accessible: bool，资产是否公网可访问
            - exploit_available: bool，是否存在公开 PoC 或在野利用
            - data_sensitivity: bool，是否处理敏感数据（PII/PCI/PHI）

    适用边界：
        - 仅适用于常规漏洞修复，紧急 0-day 需走应急响应流程（IR Playbook）
        - 暴露度判断依赖资产管理系统准确性，需定期校验

    示例：
        CVSS 7.5 SQL 注入，公网暴露，无 PoC，处理 PCI 数据：
        168 × 0.5 × 1.0 × 0.5 = 42 小时（基础 7 天 → 实际 1.75 天）

        CVSS 9.0 RCE，内网工具，无 PoC，无敏感数据：
        24 × 1.0 × 1.0 × 1.0 = 24 小时（不缩短）
    """

    # 基础 SLA（小时）
    base_sla = {
        'Critical': 24,    # CVSS 9.0+
        'High':     168,   # CVSS 7.0-8.9，7 天
        'Medium':   720,   # CVSS 4.0-6.9，30 天
        'Low':      2160   # CVSS < 4.0，90 天
    }[vuln['severity']]

    # 各维度系数（条件成立时 SLA 减半）
    exposure_factor  = 0.5 if vuln['publicly_accessible'] else 1.0  # 公网暴露
    exploit_factor   = 0.5 if vuln['exploit_available']   else 1.0  # 存在公开利用
    data_factor      = 0.5 if vuln['data_sensitivity']    else 1.0  # 处理敏感数据

    final_sla = int(base_sla * exposure_factor * exploit_factor * data_factor)
    return final_sla


def auto_create_vuln_ticket(vuln: dict, sla_hours: int) -> dict:
    """
    自动化工单创建：基于服务名称查找责任人，创建带 Due Date 的 Jira 工单
    关键依赖：服务注册中心（Consul）、CODEOWNERS 文件、LDAP/AD
    """
    import boto3
    from datetime import datetime, timedelta
    from jira import JIRA

    # 1. 通过服务名称查询代码仓库（需维护服务→仓库映射）
    service_repo = lookup_service_repository(vuln['service_name'])

    # 2. 解析 CODEOWNERS 确定负责团队
    owner_team = parse_codeowners(service_repo, vuln['file_path'])

    # 3. 从 LDAP 获取团队 Leader 的 Jira 账号
    assignee = get_team_leader_jira_account(owner_team)

    # 4. 创建 Jira 工单
    jira = JIRA(server='https://jira.company.com',
                basic_auth=('svc-security', 'API_TOKEN'))

    due_date = datetime.now() + timedelta(hours=sla_hours)

    issue = jira.create_issue(fields={
        'project': {'key': 'SEC'},
        'summary': f"[{vuln['severity']}] {vuln['title']} in {vuln['service_name']}",
        'description': (
            f"CVE: {vuln.get('cve_id', 'N/A')}\n"
            f"CVSS: {vuln['cvss_score']}\n"
            f"Component: {vuln['component']}\n"
            f"Fix Available: {vuln.get('fix_version', 'No fix available')}\n\n"
            f"Dynamic SLA: {sla_hours} hours (基础 SLA × 风险系数)\n"
            f"Due Date: {due_date.strftime('%Y-%m-%d %H:%M')}"
        ),
        'assignee': {'name': assignee},
        'priority': {'name': 'Critical' if vuln['severity'] == 'Critical' else 'High'},
        'duedate': due_date.strftime('%Y-%m-%d'),
        'labels': ['security-vuln', vuln['severity'].lower(), vuln['source_tool']]
    })

    return {'jira_key': issue.key, 'due_date': due_date.isoformat(), 'assignee': assignee}
```

`calculate_dynamic_sla` 的核心是一行乘法：先按严重级从 `base_sla` 字典取基础时限，再乘以三个各自取 0.5 或 1.0 的系数。每个系数的语义都很直白——公网可达、已有公开利用、处理敏感数据，任一条成立就把时限砍半；docstring 里那个"CVSS 7.5 但公网+处理 PCI 数据"的例子，168 小时经两次减半变成 42 小时，正好演示了静态表里 High=7 天如何被现实风险压到不足两天。

紧随其后的 `auto_create_vuln_ticket` 承接上一步算出的 `sla_hours`，把它落成一张带 Due Date 的 Jira 工单。它的四步骨架是"服务名 → 仓库 → CODEOWNERS 团队 → LDAP 找到人"的责任人定位链，最终 `due_date = now + timedelta(hours=sla_hours)` 把动态 SLA 变成工单上一个具体的到期日。这段代码的坑在 docstring 里已标明——它高度依赖服务→仓库映射、CODEOWNERS、LDAP 三处外部数据的准确性，任一处失准，工单就会指派给错误的人或算错到期日，让自动化派单反而制造混乱。

动态 SLA 的设计逻辑最后要落到一个数量级上：三个系数（公网暴露、存在利用、处理敏感数据）可以叠加。最严苛情况下（三个条件全满足），SLA 缩短至基础值的 1/8——Critical 漏洞 24 小时 × 0.125 = 3 小时，已接近实时应急响应。这套乘法的真正意图不是精算，而是驱使团队优先处理真正高风险的漏洞，而不是按 CVSS 分数机械排队。

### 漏洞管理流程（从发现到关闭）

上面两段代码分别对应"排优先级"和"派单"两个环节，它们只是完整闭环里的两步。把动态 SLA 与自动派单放回全流程，一个漏洞从被发现到被关闭要走完七步：

1. 发现：SAST/SCA/DAST/容器扫描自动发现，或渗透测试/漏洞赏金手动发现
2. 分类：CVSS 评分初步分类（Critical/High/Medium/Low）
3. 优先级排序：计算动态 SLA（叠加暴露度、可利用性、数据敏感度）
4. 分配：自动查询 CODEOWNERS 分配责任人，创建带 Due Date 的工单
5. 修复：开发团队修复，提交 PR，SAST/SCA 重新扫描验证修复有效性
6. 验证：安全团队复测确认漏洞已修复，无新引入问题
7. 关闭：归档漏洞详情、补丁、验证报告，用于审计与趋势分析

这七步里，第 3 步正是 `calculate_dynamic_sla` 落地处、第 4 步正是 `auto_create_vuln_ticket` 落地处，可见前面的代码是流程中的两颗齿轮，并非孤立片段。流程末端还有一层保障——每日 SLA 合规监控：定时任务扫描未关闭的安全工单，超期工单发 Slack 告警至团队并抄送 CISO，Critical 超期则自动创建 PagerDuty 事件触发 7×24 值班响应。这道监控确保"派了单"不等于"就没事了"，SLA 到期而未修复会被自动升级，形成闭环而非单向派发。

## 5.7.9 本节小结

DevSecOps 的核心价值在于：将安全控制从"事后补救"变为"流程内建"。漏洞在编码阶段发现的修复成本，远低于生产环境发现后的修复成本（包括业务中断、合规审查、客户信任损失）。七层门禁提供覆盖软件生命周期全阶段的安全检查，动态 SLA 确保高风险漏洞优先处理。

常见误区：

| 误区 | 后果 | 正确做法 |
|------|------|---------|
| 一刀切阻断所有 High 漏洞 | 遗留系统无法通过门禁，例外申请泛滥 | 基于历史基线设定阈值，逐步收紧 |
| 仅 SAST，不做 DAST/SCA | 遗漏运行时漏洞和依赖库漏洞 | SAST + DAST + SCA 组合覆盖 |
| Pre-commit Hook 过慢 | 开发者使用 --no-verify 绕过 | Pre-commit 只做快速检查（< 15 秒） |
| 首次启用 SAST 无基线 | 历史告警淹没新增问题 | 首次扫描批量标记历史问题为"已接受风险" |
| SLA 只依赖 CVSS 评分 | 高风险漏洞排队等待，低分高危漏洞被忽视 | 动态 SLA：CVSS × 暴露度 × 可利用性 × 数据敏感度 |
| 签名但不验证 | 供应链攻击仍然有效（签名没有强制验证） | Kubernetes 准入控制强制验证签名 |

这张误区表可视作全节的反向索引：每一行都对应正文某处的正面论述——"一刀切阻断"呼应 5.7.1 的门禁三档策略，"Pre-commit 过慢"呼应 5.7.5 的 `--no-verify` 陷阱，"签名但不验证"呼应 5.7.4 的 Kubernetes 准入控制，"SLA 只依赖 CVSS"呼应 5.7.8 的动态 SLA。把易犯的错与对应正解并列，便于读完后快速自查。

运行指标（参考基线）：
- 完整 Pipeline 执行时间（不含 DAST）：目标 ≤15 分钟（中型项目）
- Critical 漏洞 SLA 合规率：目标 ≥95%
- SAST 误报率：目标 ≤20%（通过调优白名单持续改进）
- 开发者 Pre-commit 绕过率：目标 ≤5%（通过提高 Hook 性能控制）
